## 分类简介

F1 覆盖「一个新人拿到一台新 Mac，到让 OpenClaw 跑起来、接上模型、加载 skills」这一段的所有坑。这一段的特点是：**错误现象往往指向错误的地方**——版本对不上会报模型不存在，权限没开会被当成 gateway 崩溃，workspace 路径搞错会显示「0 个 skill」。

本分类的核心判断原则：

- 先确认**版本真名**（`openclaw --version`），再谈其它。
- 先确认**路径真名**（`~/.openclaw/workspace/`），再谈配置。
- 先确认**License 真名**（MIT），再谈分发。
- 每问都给可执行命令；凡未在本机复现的，标 ⏳ 待实测。

## F1-1 · 问：文档和调研报告说 OpenClaw 是 `2026.3.2`，我本机却是 `2026.9.4`，谁对？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：`docs/05-openclaw-positioning.md` 写「本机安装 2026.3.2 ⚠」，`REPORT.md` E.5 也照抄这个数字，但你在终端敲命令，输出的是 `OpenClaw 2026.9.4 (3a9d69d)`。不知道该信哪个。

**原因**：调研线采信的是一个**过期的环境快照**。早期调研没有以 `openclaw --version` 为准，而是从别的间接来源（或旧会话）拿了 `2026.3.2`，之后一路传抄进报告。OpenClaw 的真名（canonical name/version）只有一个来源是权威的——**本机 CLI 实测输出**。三源（CLI + npm registry + 本机 json）中 CLI 优先级最高。

**解法**：把版本号的唯一真源钉死为命令输出，任何文档引用版本前必须重跑：

```bash
# 权威三源交叉验证
openclaw --version                       # CLI 真源
npm view openclaw version 2>/dev/null    # npm registry（对比）
cat ~/.openclaw/config.json | python3 -c "import sys,json;print(json.load(sys.stdin).get('version','?'))"  # 本机 json
```

统一后在文档里把旧的 `2026.3.2` 标注为「调研线旧快照 · 已作废」，并在 [术语对照表 v3.0 第 34 条](../00-术语对照表·v3.0行业标准版.md) 记一笔。

**验证命令**：

```bash
openclaw --version 2>&1 | grep -q "2026.9.4" && echo "✅ 版本真名 = 2026.9.4" || echo "❌ 版本对不上，重查"
```

**预防**：所有文档模板里的版本占位符统一写 `OpenClaw 2026.9.4 (3a9d69d)`，禁止手写历史版本号。⏳ 若未来升级，需先跑三源验证再批量替换。

## F1-2 · 问：装完了，但 `openclaw` 命令 `command not found`？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：按文档装了 OpenClaw，开新终端敲 `openclaw --version` 报 `zsh: command not found: openclaw`。

**原因**：安装器把可执行文件放进了某个目录（npm global bin / Homebrew bin / 自解压目录），但这个目录**不在当前 shell 的 `PATH` 里**——常见于装完没 `source` 配置、或用了与安装时不同的 shell（zsh vs bash）。OpenClaw 是自带 runtime 的本机应用，不同安装方式落点不同。

**解法**：先定位真实落点，再决定入 PATH 还是建软链：

```bash
# 1) 找出 openclaw 真实落点
find /usr/local /opt/homebrew ~/.openclaw ~/.npm-global -maxdepth 4 -name openclaw -type f 2>/dev/null | head

# 2a) 若是 npm 全局包
npm bin -g    # 或 npm config get prefix
# 2b) 加入 PATH（写进 ~/.zshrc）
echo 'export PATH="$HOME/.openclaw/bin:$PATH"' >> ~/.zshrc && source ~/.zshrc
```

**验证命令**：

```bash
which openclaw && openclaw --version
# 期望：打印落点路径 + OpenClaw 2026.9.4 (3a9d69d)
```

**预防**：安装后立刻开一个**新**终端验证，而不是在安装脚本所在 shell 里验证；不同 shell 各配一次 `PATH`。

## F1-3 · 问：workspace 到底在哪？`cd ~/.openclaw` 之后看不到 skills 和 agents。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：文档反复提 `~/.openclaw/workspace/skills/`，但 `cd ~/.openclaw` 后 `ls` 看不到 `workspace`，或看到了却是空的。

**原因**：OpenClaw 的目录是**两级结构**——`~/.openclaw/`（应用根：配置、日志、缓存）与 `~/.openclaw/workspace/`（工作区：skills/agents/references/memory）。很多人停在第一级就以为「什么都没有」；另一些人用了自定义 `OPENCLAW_HOME` 或 profile 目录，真实工作区在别处。

**解法**：用环境变量与配置文件确认根，别靠猜：

```bash
# 1) 应用根（默认 ~/.openclaw）
echo "${OPENCLAW_HOME:-$HOME/.openclaw}"

# 2) 工作区（skills 所在的真实位置）
ls -d "${OPENCLAW_HOME:-$HOME/.openclaw}/workspace"

# 3) 若有 profile，工作区可能在此
ls -d ~/.openclaw/profiles/*/workspace 2>/dev/null
```

**验证命令**：

```bash
WS="${OPENCLAW_HOME:-$HOME/.openclaw}/workspace"
test -d "$WS/skills" && echo "✅ workspace=$WS" && ls "$WS" | head || echo "❌ 路径不对，检查 OPENCLAW_HOME/profile"
```

**预防**：把 `WS` 变量写进自己的排查脚本；所有跨 agent 的文件路径**一律用绝对路径**，不写 `~/` 简写（见 [openclaw-agent-workspace-protocols 约定]）。

## F1-4 · 问：skills 目录里有 200 多个 skill，agent 却说「无可用 skill」？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：`ls ~/.openclaw/workspace/skills/ | wc -l` 显示 236（本机实测已到 238），但 agent 会话里让它用某个 skill，它说「没有这个技能」。

**原因**：目录里「有文件」≠「被注册」。skill 要被加载，至少三件事齐全：(1) 目录名即 skill 名；(2) 内含合法 `SKILL.md`（含 YAML frontmatter `name`/`description`）；(3) 该目录位于**当前 profile 有效的 skills 搜索路径**下。缺任一条，文件在、但不入编。历史上（「18 坏 skill 修复」事件）正是有一批目录缺 `SKILL.md` 或 frontmatter 不合法，导致「装了 200+ 实际可用远少于此」。

**解法**：批量做「入编体检」，把坏 skill 挑出来：

```bash
SK="$HOME/.openclaw/workspace/skills"
for d in "$SK"/*/; do
  name=$(basename "$d")
  if [ ! -f "$d/SKILL.md" ]; then echo "❌ 缺 SKILL.md: $name"
  elif ! head -5 "$d/SKILL.md" | grep -q '^---'; then echo "⚠ 无 frontmatter: $name"
  fi
done | tee /tmp/bad-skills.txt
echo "坏 skill 数：$(wc -l < /tmp/bad-skills.txt)"
```

对 `❌` 项补 `SKILL.md`；对 `⚠` 项补 `name`/`description` frontmatter 后重启 gateway。

**验证命令**：

```bash
# 合规 skill 计数应接近目录总数
find "$HOME/.openclaw/workspace/skills" -maxdepth 2 -name SKILL.md | wc -l
```

**预防**：新增 skill 后跑一次上面的体检循环；把「SKILL.md 存在 + frontmatter 合法」列为 skill 入库硬门槛。

## F1-5 · 问：从 `2026.3.2` 升到 `2026.9.4` 后，旧配置失灵、模型报错。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：升级 OpenClaw 后，原本能跑的模型调用报「model not found」，或旧 config 字段被忽略。

**原因**：跨 6 个小版本的升级里，配置 schema 与默认值都变过。典型两例：(1) 旧文档里写的 `reserveTokensFloor` 在新版里**根本不存在**，真名是 `CompactionRequestBudget.reserveTokens` + `MAX_COMPACTION_RESERVE_RATIO = 0.25`（这是 v1.0 的著名误植，v4.0 已勘误）；(2) 模型 provider 列表结构、默认模型字段变化。旧字段留着不报错，但也不生效，于是表现为「莫名失灵」。

**解法**：升级后用「字段真名核对」替代「凭记忆改配置」：

```bash
# 1) 备份（升级前必做）
cp ~/.openclaw/config.json ~/.openclaw/config.json.bak.$(date +%F)

# 2) 查已知误植字段是否还在用
grep -n "reserveTokensFloor" ~/.openclaw/config.json && \
  echo "⚠ 发现误植字段，请改为 CompactionRequestBudget.reserveTokens"

# 3) 校验 json 合法性
python3 -m json.tool ~/.openclaw/config.json > /dev/null && echo "✅ JSON 合法"
```

**验证命令**：

```bash
openclaw doctor 2>/dev/null || openclaw --version
# 期望：doctor 不报 config schema 错误 / 或版本正常
```

**预防**：跨版本升级前先 `git init` 管住 `~/.openclaw/config.json`，升级后 `git diff` 一眼看清哪些字段被新默认覆盖。⏳ 具体 schema 差异以对应版本 release notes 为准。

## F1-6 · 问：gateway 启动失败 / 端口被占，日志说「address already in use」。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：`openclaw` gateway 起不来，日志里 `EADDRINUSE` 或「address already in use」。

**原因**：多半是**上一个 gateway 进程没死透**（残留在后台），新进程抢不到同一端口；或另一个服务（Hypercorn/uvicorn 类本地服务）占了默认端口。注意：gateway「看起来没起」和「真的没起」是两回事——**必须用端口/进程实测**，别靠界面判断（见 [launchd-daemon-display-delay-vs-real-death]）。

**解法**：先找出占端口的真凶，再决定杀谁：

```bash
# 1) 查默认端口占用（按需替换端口号）
lsof -nP -iTCP -sTCP:LISTEN | grep -E "openclaw|node" 

# 2) 精确定位监听该端口的 PID
lsof -nP -iTCP:8787 -sTCP:LISTEN 2>/dev/null

# 3) 确认是残留 gateway 后再杀
kill <PID>   # 先温和；不行再 kill -9
```

**验证命令**：

```bash
# 端口应无输出（=已释放），随后能正常重启
lsof -nP -iTCP:8787 -sTCP:LISTEN 2>/dev/null || echo "✅ 端口已释放"
```

**预防**：重启 gateway 前先跑端口检查；把「先验端口后重启」写进启动脚本。

## F1-7 · 问：自定义 model provider 配了，但报「model not found」。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：`config.json` 里加了 provider 与 model，会话里选这个模型却报找不到。

**原因**：OpenClaw 里「provider 声明」与「model 可见」是两层。模型要真正可用，需要：(1) provider base_url + api_key 正确；(2) model 名与上游真实 model id **逐字一致**（大小写、版本后缀都不能差）；(3) provider 的模型列表被 OpenClaw 成功探测/加载（有些 provider 需要显式声明 models 数组）。历史上常见「声明了但 Hermes/OpenClaw 找不到」的根因就是名不对或探测失败。

**解法**：先探测端点连通性与真实 model id，再写配置：

```bash
# 1) 直连 provider 看真实 model 列表
curl -s -H "Authorization: Bearer $API_KEY" "$BASE_URL/models" | python3 -m json.tool | head -30

# 2) 校验 config 里 model 名与上一步逐字一致
grep -n '"model"' ~/.openclaw/config.json
```

**验证命令**：

```bash
# 用真实 model id 发一次最小请求
curl -s "$BASE_URL/chat/completions" -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"<真实model_id>","messages":[{"role":"user","content":"ping"}],"max_tokens":5}'
# 期望：返回 choices，不是 model not found
```

**预防**：新增 provider 时把「探测真实 model 列表」作为第一步，配置里的 model 名从探测结果**复制粘贴**，不手敲。

## F1-8 · 问：skill 里跑 shell 全部 `permission denied` / 读不到用户目录。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：某个 skill 要求执行命令或读 `~/Documents`，返回 permission denied；或 macOS 弹窗被无视。

**原因**：macOS 的 TCC（Transparency, Consent, and Control）对「全磁盘访问」「辅助功能」有独立授权。OpenClaw 进程（或其宿主终端/App）若没被授予这些权限，子进程读写受限目录、驱动 UI 时都会被拦。这是**操作系统层**的门，不是 OpenClaw 的 bug。

**解法**：确认并授予正确的宿主进程权限（不是给 `openclaw` 二进制，而是给它实际运行的宿主）：

```bash
# 1) 查看宿主进程
ps aux | grep -iE "openclaw|node" | grep -v grep | head

# 2) 判权限：能读到受限目录说明已授权
ls ~/Library/Messages 2>&1 | head -1
```

- 打不开 → 到 **系统设置 → 隐私与安全性 → 完全磁盘访问权限 / 辅助功能**，把宿主 App / 终端加进去并勾选。
- 改完**重启宿主进程**（授权在启动时读取）。

**验证命令**：

```bash
# 授权后应能列出受限目录
ls ~/Library/Messages >/dev/null 2>&1 && echo "✅ 已获全盘访问" || echo "❌ 仍需授权"
```

**预防**：新机器初始化 checklist 第一条就是给宿主进程开全盘访问 + 辅助功能；⏳ 具体 App 名称依你的安装形态（CLI / DMG）而定。

## F1-9 · 问：开着代理/VPN，插件下载或 skill 调用却超时。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：浏览器能上外网，但 OpenClaw 下载 skill / 调外部 API 超时；关掉代理反而通，或反之。

**原因**：CLI 进程**不一定继承**系统的代理设置。图形应用走系统网络代理，终端进程靠 `HTTP(S)_PROXY` 环境变量；两者不一致时，表现为「浏览器通、CLI 不通」。此外 macOS 上还存在 DNS 污染导致海外域名解析到黑洞的情况。

**解法**：给 CLI 显式设代理，并确认 DNS：

```bash
# 1) 显式导出代理（按你的端口替换）
export HTTPS_PROXY="http://127.0.0.1:7890"
export HTTP_PROXY="http://127.0.0.1:7890"

# 2) 验证出口 IP 与目标域名
curl -s --max-time 8 https://api.ipify.org; echo
dig +short registry.npmjs.org | head -3
```

**验证命令**：

```bash
curl -s --max-time 8 -o /dev/null -w "%{http_code}\n" https://registry.npmjs.org/openclaw
# 期望：200；若超时 → 代理/DNS 未生效
```

**预防**：把代理导出写进 shell 启动脚本；排查网络时先用 `curl` 判「CLI 视角通不通」，不要用浏览器结论代替。

## F1-10 · 问：OpenClaw 的 License 到底是 MIT 还是 NOASSERTION？能不能商用/分发 plugin？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：GitHub 仓库页显示 `NOASSERTION`，但你打开 `LICENSE` 文件看到的是 MIT 文本。想基于它做 plugin 分发，又怕踩法律雷。

**原因**：`NOASSERTION` 是 **GitHub 的 badge 自动识别结果**，不是法律文本。GitHub 的 license 检测器没把该 LICENSE 文件匹配到标准模板时，就显示 `NOASSERTION`——它表示「平台没识别出」，**不等于「没有 license」**。真正有法律效力的是仓库里的 `LICENSE` 文件文本。本项目的核实结论：**文件文本确凿为 MIT**，plugin 分发可行。

**解法**：以文件文本为准，存档核实证据：

```bash
# 取仓库 LICENSE 文本并识别
curl -s https://raw.githubusercontent.com/openclaw/openclaw/main/LICENSE | head -20
# 应看到 "MIT License" / "Permission is hereby granted, free of charge..."
```

**验证命令**：

```bash
curl -s https://raw.githubusercontent.com/openclaw/openclaw/main/LICENSE | grep -qi "MIT License" && \
  echo "✅ License = MIT（文件文本）" || echo "⚠ 需人工复核文本"
```

**预防**：任何「License 未知」的告警都要**回到 LICENSE 文件文本**判断，不采信 badge；对外文档统一写「MIT（GitHub badge NOASSERTION 仅显示问题）」。

## F1-11 · 问：装到一半报 Node/运行时版本不兼容。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：安装脚本中途报 `Unsupported engine` / `requires node >=xx`。

**原因**：OpenClaw 是自带 runtime 的本机应用，但**插件/构建工具链**仍可能依赖宿主 Node。宿主 Node 过旧（或过新）会触发 engine 检查失败；用系统自带 Node 与 nvm 管理的 Node 之间切换也常导致版本错乱。

**解法**：查清当前与所需版本，切到合规版本再装：

```bash
node -v; npm -v
# 若版本不合，用 nvm 切
nvm install --lts && nvm use --lts
node -v
```

**验证命令**：

```bash
node -e "console.log('node ok', process.version)" && openclaw --version
```

**预防**：把 `node -v` 纳入「环境就绪」清单首项；插件类任务固定用 LTS。

## F1-12 · 问：plugin 装了，但 manifest 不识别 / `openclaw plugins list` 里没有。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：把 plugin 目录拷进去了，`openclaw plugins list` 看不到，或报 manifest schema 错误。

**原因**：plugin 要被识别，需要合法 `manifest`（如 `openclaw.plugin.json`）+ 位于插件搜索路径 + manifest 的 `name`/`entry`/`version` 字段齐全。缺一项就「装了没挂上」。这与 skill 的「有文件≠入编」是同一类问题，只是层级更高。

**解法**：校验 manifest 合法性，并确认落点：

```bash
# 1) 校验 manifest JSON 合法性
python3 -m json.tool ~/.openclaw/plugins/*/openclaw.plugin.json >/dev/null && echo "✅ manifest JSON 合法"

# 2) 列插件，确认被识别
openclaw plugins list 2>/dev/null | grep -i "<你的plugin名>"
```

**验证命令**：

```bash
openclaw plugins list 2>/dev/null | grep -qi "<你的plugin名>" && echo "✅ plugin 已挂载" || echo "❌ 未识别，检查 manifest 字段"
```

**预防**：plugin 开发时以官方模板起步，`name`/`entry`/`version` 三字段先填全再谈逻辑；装完必跑 `plugins list` 复核。
