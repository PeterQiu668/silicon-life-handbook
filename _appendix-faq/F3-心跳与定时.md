## 分类简介

F3 覆盖「一个 Agent 不在对话里时，如何按时醒、按时干活、按时报告」的全部故障面：**心跳（Heartbeat）**负责「多久醒一次、醒来干什么」，**定时（Cron）**负责「到点执行某个动作」。这一段的特点是：**故障往往无声**——不像对话报错会当场看见，定时任务错过了、心跳停了，你不主动查根本不知道。9/21 飞书推送事故与「能力矩阵 26 天未续期」都是这类**静默失效**的真实代价。

本分类核心判断原则：

- **先验「进程是否真死」再重启**——界面延迟显示 ≠ 服务已死（见 [launchd-daemon-display-delay-vs-real-death]）。
- **定时任务必须有「心跳 + 告警」**——没有回执的 cron 等于薛定谔的任务。
- **主动 ≠ 越界**——heartbeat 唤醒的动作仍受 USER 协议三档边界约束（见 [F2-3](./F2-协议-SOUL-AGENTS-USER.md)）。
- 凡是「没执行/错过/静默」类问题，答案里必须有一条**回执日志**命令。

## F3-1 · 问：heartbeat 根本不触发，Agent 该醒的时候没醒。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：配置了 HEARTBEAT.md（约定每 N 分钟醒一次），但观察很长一段时间，Agent 一次都没醒。

**原因**：heartbeat 要触发，需 (1) HEARTBEAT.md 存在且被加载；(2) 托管它的**守护进程/调度器活着**；(3) 间隔配置合法（非 0、非超大）。最常见是第 (2) 条——宿主进程/launchd 守护已死，但界面还显示「运行中」，于是你以为心跳在跑。**必须先验证进程真死，再谈配置。**

**解法**：先证「真死」，再重启：

```bash
# 1) 查调度器进程是否真的在监听/存活
lsof -nP -iTCP -sTCP:LISTEN | grep -iE "openclaw|heartbeat" 
ps aux | grep -iE "openclaw.*heartbeat|openclaw.*daemon" | grep -v grep

# 2) 看心跳日志最后一条时间
tail -5 ~/.openclaw/workspace/logs/heartbeat.log 2>/dev/null
```

若进程真没了，用 launchd 重新拉起（见 F3-15）。

**验证命令**：

```bash
# 等待一个预期间隔，确认新心跳产生
tail -1 ~/.openclaw/workspace/logs/heartbeat.log
# 期望：时间戳随间隔推进
```

**预防**：heartbeat 健康度纳入每周期检查（F3-9）；守护进程配自启 + 崩溃重拉。⏳ 精确日志路径以本机为准。

## F3-2 · 问：cron 任务到点没执行，静默错过。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：`openclaw cron list` 里有任务，但约定时间过了，产物没出现，也没报错。

**原因**：cron 静默错过通常是「注册了但没挂到活的调度器上」「任务定义合法但不匹配任何触发时刻」「调度器进程不在」。**没有回执的 cron 是无从判断的**——所以第一步不是改 cron，而是找**执行记录**。

**解法**：按「注册 → 匹配 → 执行」三条链逐段查：

```bash
# 1) 任务是否注册
openclaw cron list 2>/dev/null

# 2) 调度器是否在跑
ps aux | grep -iE "cron|scheduler" | grep -v grep | head

# 3) 是否有执行记录 / 上次运行时间
openclaw cron list --json 2>/dev/null | python3 -c "import sys,json;[print(t.get('name'),t.get('last_run'),t.get('next_run')) for t in json.load(sys.stdin)]" 2>/dev/null
```

**验证命令**：

```bash
# 手动触发一次，验证任务本体没问题
openclaw cron run <task-name> 2>/dev/null
# 期望：产物出现 / 有回执
```

**预防**：每个 cron 必配「回执落盘」（F3-10）；`last_run`/`next_run` 纳入巡检。

## F3-3 · 问：cron 时区与系统不一致，任务在错误时间跑。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：你设「每天 08:00 推送日报」，实际在凌晨 00:00（或 16:00）跑。

**原因**：cron 表达式默认按某个时区解释。系统时区（macOS `Asia/Shanghai`）与调度器内部时区（可能 UTC）不一致时，8 小时的偏移就出现了。这是**跨时区调度**的通病，不是 OpenClaw 独有。

**解法**：统一时区来源，并在任务里显式声明：

```bash
# 1) 查系统时区
sudo systemsetup -gettimezone 2>/dev/null || date +%Z
date

# 2) 查调度器时区（若可配）
grep -iE "timezone|tz" ~/.openclaw/config.json
```

在任务定义里显式写时区（如 `TZ=Asia/Shanghai`），避免依赖隐式默认。

**验证命令**：

```bash
date +"%Y-%m-%d %H:%M %Z"
# 与任务的 next_run 时间比对，二者应为同一时区口径
openclaw cron list --json 2>/dev/null | grep -o '"next_run":"[^"]*"' | head
```

**预防**：任务定义强制带时区；日报类任务在产物里打印「生成时区」。

## F3-4 · 问：cron 任务失败后如何自动恢复？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：cron 任务因一次网络抖动/依赖超时而失败，之后就不再重试，直到下次周期。

**原因**：默认 cron 语义是**到点执行一次**，失败不自动重试。对「日报/续期/同步」这类**幂等任务**，一次失败意味着一个周期的缺口。要恢复，需要**重试策略 + 失败可见**。

**解法**：两层恢复——任务内重试 + 任务级告警：

```bash
# 任务内：幂等 + 重试封装
for i in 1 2 3; do
  openclaw cron run <task> && break || sleep $((i*30))
done
```

```text
# 任务级：失败写一条到失败日志/事件流
if ! openclaw cron run <task>; then echo "$(date -Iseconds) FAIL <task>" >> ~/.openclaw/workspace/logs/cron-failures.log; fi
```

**验证命令**：

```bash
# 制造一次失败，确认被记录并重试
tail -5 ~/.openclaw/workspace/logs/cron-failures.log 2>/dev/null
```

**预防**：任务按「幂等性」分类；非幂等任务加锁（F3-7）后再启重试；失败日志纳入巡检告警。

## F3-5 · 问：heartbeat 频率设太高，把机器/额度拖垮。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：设了「每分钟醒一次」，结果模型调用额度和 CPU 飙升，正常任务被拖慢。

**原因**：每次 heartbeat 唤醒都可能触发一次模型调用 + 工具执行。频率 × 唤醒成本 = 负载。频率设得太激进，等于让 Agent 24×7 空转。**心跳不是越多越好——它要匹配「现实中需要多快响应」**。

**解法**：按业务响应需求定频率，并让「无事可做就空转结束」成为默认：

```bash
# 量化当前心跳密度（每分钟条数）
grep "$(date +%Y-%m-%d)" ~/.openclaw/workspace/logs/heartbeat.log 2>/dev/null | \
  awk -F: '{print $1":"$2}' | sort | uniq -c | sort -rn | head
```

把间隔从「1 分钟」提到「5/15/30 分钟」或改事件驱动，通常能砍掉大部分空转。

**验证命令**：

```bash
# 调频后对比单位时间调用量应下降
grep -c "" ~/.openclaw/workspace/logs/heartbeat.log 2>/dev/null
```

**预防**：设「最小间隔下限」；把空转（醒来无任务）记为一次「无效心跳」，占比过高即调频。

## F3-6 · 问：主动任务越界——heartbeat 醒来自己干了不该干的事。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：Agent 在心跳里「自作主张」发了消息 / 改了文件 / 花了钱，而你没让它做。

**原因**：heartbeat 让 Agent 获得了**主动性**，但主动性必须被 **USER 协议三档边界（Allowed / Forbidden / Needs-Confirm）** 约束。若 HEARTBEAT.md 里的「醒来干什么」超出了 USER.md 的 `allowed`，就会越界。**这是「主动」与「失控」的分界线**——v1.0 卷五模块5 专门为此设三档制。

**解法**：把心跳动作**逐条对齐** USER 三档，凡命中 forbidden/needs-confirm 的动作一律改为「先提案」：

```yaml
# HEARTBEAT.md —— 醒来动作必须 ⊆ USER.allowed
wake_actions:
  - type: summarize            # allowed：只读
  - type: notify-owner         # needs-confirm：需确认后才发
  # - type: spend-money        # forbidden：禁止
```

```bash
# 审计：把心跳动作与 USER.allowed 做集合差
grep -A20 "wake_actions" ~/.openclaw/workspace/agents/<agent>/HEARTBEAT.md
grep -A5  "allowed"      ~/.openclaw/workspace/agents/<agent>/USER.md
```

**验证命令**：

```bash
# 越界动作应被拒绝/转提案，审查日志
grep -iE "forbidden|needs-confirm|proposal" ~/.openclaw/workspace/logs/*.log | tail
```

**预防**：心跳动作集 ⊆ USER.allowed 列为硬校验；跨档动作一律走「自主目标生成」提案流程（F3-14）。

## F3-7 · 问：定时任务重入 / 重复执行，同一件事干了三遍。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：一次该发一条的日报，发出去三条；一次该结算一次的账，算了两遍。

**原因**：任务执行时间**超过调度间隔**，上一轮还没跑完，下一轮又启动（重入）；或同一任务被注册到**两个调度器**（OpenClaw cron + launchd 各一份，见 F3-8）。前者是「没加锁」，后者是「重复注册」。

**解法**：加**单实例锁**，并在启动前判「上一轮完成没」：

```bash
# 简单文件锁（幂等保护）
LOCK=/tmp/<task>.lock
if [ -e "$LOCK" ]; then echo "上一轮未完成，跳过"; exit 0; fi
trap 'rm -f "$LOCK"' EXIT
touch "$LOCK"
# ...任务主体...
```

同时排查重复注册：

```bash
openclaw cron list 2>/dev/null | grep -c "<task-name>"   # 期望：1
launchctl list 2>/dev/null | grep -i "<task-name>"        # 若也有，说明双注册
```

**验证命令**：

```bash
# 触发一次重叠执行，确认第二次被锁跳过
grep -i "skip\|lock" ~/.openclaw/workspace/logs/*.log | tail
```

**预防**：所有可能重入的任务默认加锁；调度器唯一化（要么 OpenClaw cron，要么 launchd，别都上）。

## F3-8 · 问：cron 与 macOS launchd 混用，两个调度器打架。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：同一个「日报」任务，OpenClaw cron 有一份、launchd plist 也有一份，结果跑撞车、日志互相覆盖。

**原因**：macOS 上有两套调度：OpenClaw 自己的 cron，和系统级 **launchd**。两者都能定时拉起进程，若同一业务两处都注册，就是**双头调度**。常见于「先用 launchd 跑通，后来改用 OpenClaw cron 却没删旧 plist」。

**解法**：确立单一调度权威，清理冗余：

```bash
# 1) 列出 launchd 里所有相关守护
launchctl list 2>/dev/null | grep -iE "openclaw|<task>"

# 2) 列 OpenClaw cron
openclaw cron list 2>/dev/null

# 3) 决策：二选一，卸载另一套
launchctl bootout gui/$(id -u)/<label> 2>/dev/null   # 卸 launchd 版
# 或 openclaw cron remove <task>                       # 卸 OpenClaw 版
```

**验证命令**：

```bash
launchctl list 2>/dev/null | grep -c "<task>"   # 与 openclaw cron 计数之和应为 1
```

**预防**：约定「长驻/自愈型用 launchd，业务定时用 OpenClaw cron」，同一任务不跨两套。

## F3-9 · 问：heartbeat 健康度怎么测？它到底活着没？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：没有任何报错，但也说不清心跳是不是在正常工作。

**原因**：心跳的健康不是「有没有报错」，而是**三个可观测指标**：唤醒节奏是否连续、唤醒后是否产出、产出是否被消费。v1.0 卷五模块6「每周体检清单（Weekly Health Checklist）」正是为此设计——把「心跳健康度」列为固定体检项。

**解法**：做一份「心跳体检」脚本：

```bash
LOG=~/.openclaw/workspace/logs/heartbeat.log
# 1) 连续两次心跳的间隔（应≈配置间隔）
tail -2 "$LOG" | awk '{print $1,$2}'
# 2) 最近一小时心跳次数
grep "$(date -v-1H +%Y-%m-%dT%H)" "$LOG" 2>/dev/null | wc -l
# 3) 有效率：有心跳但无产出的比例（过高=空转）
```

**验证命令**：

```bash
# 期望：间隔稳定、次数≈预期、有产出
tail -3 "$LOG"
```

**预防**：把上述三条并入每周体检；设定阈值（如「连续 2 个间隔无心跳」即告警）。⏳ 日志格式以本机为准。

## F3-10 · 问：cron 任务静默失败，没人知道怎么办？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：某个定时任务很久没成，但一直没触发任何告警，直到业务方来问。

**原因**：**没有回执就不会有告警**。默认 cron 只负责「启动」，不负责「确认结果」。要让失败可见，必须让任务**显式落一条可被巡检的结果记录**（成功/失败/时间/产物路径）。

**解法**：统一「任务回执」规范——每个 cron 结束时写一行结构化结果：

```bash
#!/bin/bash
TASK=daily-report
OUT=$(openclaw cron run "$TASK" 2>&1)
RC=$?
echo "{\"task\":\"$TASK\",\"rc\":$RC,\"ts\":\"$(date -Iseconds)\"}" \
  >> ~/.openclaw/workspace/logs/cron-receipts.jsonl
```

再让「巡检任务」扫回执，异常即告警。

**验证命令**：

```bash
# 扫最近回执里非 0 的任务
tail -50 ~/.openclaw/workspace/logs/cron-receipts.jsonl 2>/dev/null | grep '"rc":[^0]'
```

**预防**：所有 cron 强制写回执；巡检任务本身也要有回执（避免「看门狗自己死了」）。

## F3-11 · 问：记忆/能力矩阵续期任务 26 天没跑，数据断更了。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：本应「每日/每周续期」的能力矩阵（或记忆索引）数据出现 26 天空洞，事后才发现。

**原因**：**续期型任务最怕静默停摆**——它不像业务任务有人天天盯，它停了没人喊，于是「26 天未续期」却无人告警。根因通常是：调度器进程死过一次后没自愈，或任务在某次失败后没重试（F3-4），此后一直空转。这是「能力矩阵续期断更」这类真实事件的典型形态。

**解法**：给续期任务加「最大允许间隔」守卫，超期即告警：

```bash
# 取能力矩阵最近更新时间
LAST=$(stat -f %m ~/.openclaw/workspace/references/.../capability-matrix.json 2>/dev/null)
NOW=$(date +%s)
AGE_DAYS=$(( (NOW - LAST) / 86400 ))
echo "能力矩阵已 $AGE_DAYS 天未续期"
[ "$AGE_DAYS" -gt 2 ] && echo "⚠ 超过阈值（2 天），触发告警"
```

**验证命令**：

```bash
# 期望：AGE_DAYS ≤ 阈值
echo "gap_days=$AGE_DAYS"
```

**预防**：续期任务配「新鲜度守卫」（本问脚本）；把「最大允许间隔」写入任务定义元数据。⏳ 数据文件真实路径以本机为准。

## F3-12 · 问：9/21 飞书推送事故——定时任务发消息失败。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：9/21 当天，定时任务本该把报告推送到飞书，结果群/私聊没收到，任务本身却「显示成功」。

**原因**：**推送类任务的成功判据错了**。任务把「消息请求已发出」当成成功，但实际**消息投递失败**（凭证过期、群 ID 错、webhook 被限流、网关连接冲突）。根因是「发送」与「送达」之间的**语义鸿沟**——请求 200 不代表用户收到。这类事故在飞书/IM 集成的排查里非常典型（含配对成功但消息无响应、连接冲突等）。

**解法**：推送任务必须以**投递回执**为成功判据，并保留重投：

```bash
# 1) 校验凭证与目标有效性（示例：飞书 webhook）
curl -s -o /dev/null -w "%{http_code}\n" -X POST "$FEISHU_WEBHOOK" \
  -H "Content-Type: application/json" \
  -d '{"msg_type":"text","content":{"text":"probe"}}'
# 期望：200 且响应体 code==0（业务成功），而非仅 HTTP 200

# 2) 失败进重投队列，不吞错
```

**验证命令**：

```bash
# 检查推送回执日志里是否有业务层错误码
grep -iE "code|errcode|deliver" ~/.openclaw/workspace/logs/feishu-push.log | tail
# 期望：code=0
```

**预防**：所有 IM 推送任务区分「HTTP 成功」与「业务成功（code=0）」；失败进重投 + 告警。⏳ 具体 webhook/凭证字段以本机飞书配置为准。

## F3-13 · 问：8/19 军团断线——通道失效后 heartbeat 无人应答。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：8/19 军团级断线，多个 Agent 的心跳照跑，但对外通道失效，agent 之间/对用户「失联」，心跳空转无应答。

**原因**：**通道失效与进程存活是两回事**。心跳进程可能还活着、还在唤醒，但**通信通道（网关/连接）断了**，于是「有心跳无应答」。这类级联失效最怕扩散——一个通道挂了，依赖它的所有 Agent 一起失联。v1.0 卷七附录 A「A2A 协议补丁·反脆弱三层」（fallback 健康检查 + 通道守门员 + 协同事件日志）正是为防全军级联失败而设。

**解法**：加「通道守门员」——心跳顺带探通道，断了就 fallback：

```bash
# 心跳里附带通道健康探针
probe_channel() {
  curl -s --max-time 5 "$GATEWAY_HEALTH_URL" >/dev/null && echo "up" || echo "down"
}
STATE=$(probe_channel)
[ "$STATE" = "down" ] && echo "$(date -Iseconds) CHANNEL_DOWN" >> ~/.openclaw/workspace/logs/channel.log
```

**验证命令**：

```bash
# 期望：通道 up；down 时有 fallback 记录
tail -3 ~/.openclaw/workspace/logs/channel.log 2>/dev/null
```

**预防**：心跳=「唤醒 + 通道探针」二合一；primary/fallback 去重防级联；结构化协同事件日志让失败模式可传递。

## F3-14 · 问：自主目标生成（响应型→提案型）怎么做调度？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：想让 Agent 不只「等任务」，而是心跳醒来时主动提案，但不知道接在哪个环节。

**原因**：**自主目标生成（Autonomous Goal Generation, Response → Proposal）**是本书对业界的关键差异化——业界所有主流框架（LangGraph/AutoGen/CrewAI/Claude SDK/OpenAI Agents）都是**响应型**（接指令才动），没有「主动提案」原语。要落地，得把 heartbeat 空闲周期接成「提案生成 → 提案队列 → 人工/三省评审」。

**解法**：在 heartbeat 里挂「提案生成」段，产出进队列而非直接执行：

```yaml
# HEARTBEAT.md
on_idle:
  - generate_proposals: true     # 空转时生成提案
  - output: proposal_queue       # 进队列，不直接执行
  # 提案经三省评审（提议/复核/终审）后才执行 → 见卷七
```

```bash
# 查看提案队列
ls ~/.openclaw/workspace/proposals/ 2>/dev/null | tail
```

**验证命令**：

```bash
# 期望：空转后队列新增提案文件，且未被自动执行
ls -la ~/.openclaw/workspace/proposals/ 2>/dev/null
```

**预防**：提案一律进队列走评审；禁止计划外直接执行（与 F3-6 边界约束一致）。

## F3-15 · 问：launchctl bootstrap 被拒，守护进程起不来。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：用 `launchctl bootstrap gui/$(id -u) xxx.plist` 注册守护进程，被拒（`Bootstrap failed` / `Operation not permitted`）。

**原因**：macOS 对 `launchctl bootstrap` 有 SIP/权限约束，在受限环境（或从 agent 会话内）执行会被拦。已知可行替代是走 `launchctl load`/`-w` 老接口，或把 plist 放进用户 `~/Library/LaunchAgents/` 后用会话外方式加载。

**解法**：改用兼容路径加载：

```bash
# 1) 先把 plist 放到用户 LaunchAgents
cp mydaemon.plist ~/Library/LaunchAgents/
# 2) 用 load 接口（若 bootstrap 被拒）
launchctl load -w ~/Library/LaunchAgents/mydaemon.plist
# 3) 确认注册
launchctl list | grep mydaemon
```

**验证命令**：

```bash
launchctl list | grep -q mydaemon && echo "✅ 已加载" || echo "❌ 未加载"
```

**预防**：守护加载走 `LaunchAgents` + `load -w` 路线；bootstrap 被拒时不要在循环里硬重试。⏳ 具体行为随 macOS 版本（本机 26.5.1）变化，以实测为准。
