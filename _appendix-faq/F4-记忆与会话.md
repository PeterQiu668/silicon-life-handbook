## 分类简介

F4 覆盖「Agent 记得什么、怎么记、记不下了怎么办」的全部故障面：**会话压缩（Session/Context Compaction）**解决「上下文装不下」，**MEMORY 协议**解决「跨会话该留什么」。这一段的特点是：**故障表现为「变笨」而非「报错」**——压缩过头会忘事、记忆写不进去会答非所问，但日志里一切正常。历史上最著名的坑是 **`reserveTokensFloor` 误植**：这个字段**根本不存在**，写进配置不报错、不生效，让人误以为「已经调好了压缩」。

本分类核心判断原则：

- **先核对字段真名**，再谈压缩调优（真名见本卷 banner）。
- **记忆问题先分清「写不进」还是「读不出」**——两条链路查法不同。
- **压缩是预算问题，不是人格问题**：压缩过头先调 `reserveTokens`，别改 SOUL。
- 凡「忘了/答非所问」类问题，答案里必须有一条**命中率/时间戳**类命令。

## F4-1 · 问：会话压缩后 Agent「忘了」前面说的话。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：长对话进行到后面，Agent 对前面已经确认过的信息「不认账」，回答前后矛盾。

**原因**：这是**会话压缩（Session Compaction）**的正常行为——上下文超出预算时，旧内容被摘要/丢弃，给新内容腾空间。问题只在**压缩触发过早 / 保留太少**，于是「还没聊到关键处就忘了」。它**不是记忆丢失**（MEMORY 还在），是**当前会话窗口**变小了。

**解法**：先量化压缩发生点，再调预算：

```bash
# 1) 看会话里压缩发生的时间点/次数
grep -iE "compact|compress|reserve" ~/.openclaw/workspace/logs/session*.log 2>/dev/null | tail

# 2) 核对压缩预算字段真名（见 F4-2）
grep -nE "reserveTokens|MAX_COMPACTION_RESERVE_RATIO" ~/.openclaw/config.json
```

若要跨会话保住关键事实，**写进 MEMORY 协议**而非依赖会话窗口。

**验证命令**：

```bash
# 调预算后，同一场景下压缩触发应更晚
grep -c -i "compact" ~/.openclaw/workspace/logs/session*.log 2>/dev/null
# 期望：同一长度对话下压缩次数下降
```

**预防**：长任务开始前先落一份 MEMORY 摘要；会话预算与任务长度匹配。⏳ 日志路径以本机为准。

## F4-2 · 问：`reserveTokensFloor` 误植——压缩配置其实根本没生效。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：按旧文档在 `config.json` 里设了 `reserveTokensFloor: 8000`，以为压缩预算调好了，但行为毫无变化。

**原因**：**`reserveTokensFloor` 这个字段根本不存在**。这是 v1.0 的著名误植，v4.0 已勘误。真名是 `CompactionRequestBudget.reserveTokens` + 常量 `MAX_COMPACTION_RESERVE_RATIO = 0.25`。写不存在的字段时，配置解析器**静默忽略**——不报错、不生效，于是你以为调了其实是幻觉。

**解法**：改用真名字段：

```jsonc
// config.json —— 正确字段
{
  "compaction": {
    "requestBudget": {
      "reserveTokens": 8000          // 真名
    }
  }
  // MAX_COMPACTION_RESERVE_RATIO = 0.25 为内置上限常量，非 config
}
```

```bash
# 清除误植字段
sed -i.bak '/reserveTokensFloor/d' ~/.openclaw/config.json   # 先备份 .bak
python3 -m json.tool ~/.openclaw/config.json >/dev/null && echo "✅ JSON 合法"
```

**验证命令**：

```bash
grep -n "reserveTokensFloor" ~/.openclaw/config.json && echo "❌ 误植仍在" || echo "✅ 误植已清"
grep -n "reserveTokens"      ~/.openclaw/config.json          # 应命中真名
```

**预防**：所有压缩相关配置以 [术语对照表 v3.0 第 31 条](../00-术语对照表·v3.0行业标准版.md) 为准；配置校验加一条「禁止误植字段」的 lint。

## F4-3 · 问：MEMORY.md 太大了，拖慢每次会话加载。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：MEMORY.md 涨到几万字，Agent 每次启动/会话都要读它，响应变慢、预算被占。

**原因**：MEMORY.md 若被当成「什么都往里塞的流水账」，它就和 SOUL 过长（见 [F2-11](./F2-协议-SOUL-AGENTS-USER.md)）一样，成为**每次加载的固定成本**。记忆的正确姿势是**分层**：常驻的少（身份级事实），检索的多（可搜索的归档）。

**解法**：MEMORY.md 只留「高频、必须常驻」的事实；其余转入可检索归档：

```bash
# 量化体积（字符数 ≈ token 量级）
wc -c ~/.openclaw/workspace/agents/<agent>/MEMORY.md
# 目标：常驻段精简；长尾转 memory 归档目录
```

```text
分层建议：
MEMORY.md            → 身份级常驻事实（小而稳）
memory/archive/*.md  → 可检索长尾（多可搜）
memory/index         → 索引入口
```

**验证命令**：

```bash
# 常驻体积下降 + 归档仍可检索
wc -c ~/.openclaw/workspace/agents/<agent>/MEMORY.md
ls ~/.openclaw/workspace/agents/<agent>/memory/archive/ 2>/dev/null | wc -l
```

**预防**：MEMORY 增改时默认「先问是否该进归档」；常驻段设体积上限并纳入体检（F4-12）。

## F4-4 · 问：记忆「写进去了」但「读不出来」——写进和读出怎么分清？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：明明让 Agent 记下了一件事，再问它却不知道。

**原因**：记忆有**两条独立链路**——写入（write）与检索（read/search）。先要分清断在哪条：

- 写不进：目录只读、写入被边界拦、写到了「另一个 profile 的记忆」。
- 读不出：写入成功但不在检索范围、索引没更新、检索关键词不匹配。

**解法**：分链路定位：

```bash
# 链路A：确认写入（文件是否新增/更新）
ls -la ~/.openclaw/workspace/agents/<agent>/memory/
grep -rn "<刚记的内容关键词>" ~/.openclaw/workspace/agents/<agent>/memory/ | head

# 链路B：确认检索（真名 memory/search）
openclaw memory search "<关键词>" 2>/dev/null | head
```

若 A 有、B 无 → 索引/检索范围问题；若 A 无 → 写入链路问题（查边界/路径）。

**验证命令**：

```bash
openclaw memory search "<关键词>" 2>/dev/null | head
# 期望：能命中刚写入的内容
```

**预防**：写入后立刻 `memory search` 回读一次（写读闭环）；记忆目录纳入 git（F4-15）。

## F4-5 · 问：多个 Agent 共用一个 memory，记忆串味。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：A Agent 问「我上次做了什么」，答出的是 B Agent 的事。

**原因**：多个 Agent 指向了**同一份记忆存储/同一索引**。记忆是身份的一部分（对位 SOUL 的 F2-5），共享即串味。Fleet（原：军团）里应「一 agent 一记忆域」，跨 agent 共享只能通过**受控的协同事件/接口**，不能直接共用存储。

**解法**：隔离记忆域，跨 agent 只共享「事件」不共享「存储」：

```bash
# 检查是否有多个 agent 指向同一记忆路径
find ~/.openclaw/workspace/agents -name "MEMORY.md" -exec sha256sum {} \; | awk '{print $1}' | sort | uniq -d
# 出现重复 = 有 agent 共用同一记忆文件

# 期望：每 agent 独立 memory 目录
ls -d ~/.openclaw/workspace/agents/*/memory 2>/dev/null
```

**验证命令**：

```bash
find ~/.openclaw/workspace/agents -name "MEMORY.md" -exec sha256sum {} \; | awk '{print $1}' | sort | uniq -d
# 期望：无输出
```

**预防**：记忆域隔离列入新 Agent 上编 checklist；跨 agent 信息走协同事件日志（见 [F3-13](./F3-心跳与定时.md)）。

## F4-6 · 问：会话压缩把关键信息压没了，怎么保底？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：压缩后，一个关键决策/约束被摘要丢掉，后续行为偏离。

**原因**：压缩器的摘要是**有损**的，它无法判断哪句对你重要。凡「关键」，都必须**显式外置**——压缩器只保会话，保不住你没告诉它要保的东西。

**解法**：把关键信息「钉」在压缩之外：

```text
钉住三处（任选或全用）：
1) MEMORY.md      → 跨会话常驻事实
2) USER.md 边界   → 约束（needs-confirm/forbidden）
3) 会话内「PIN」标记 → 显式要求保留的段落
```

```bash
# 审计：关键约束是否都在协议文件里（而非只在对话里）
grep -rn "禁止\|必须\|不可" ~/.openclaw/workspace/agents/<agent>/USER.md ~/.openclaw/workspace/agents/<agent>/MEMORY.md | head
```

**验证命令**：

```bash
# 长对话后，关键约束仍被 Agent 遵守
grep -c "needs-confirm" ~/.openclaw/workspace/agents/<agent>/USER.md
```

**预防**：约定「凡关键，必外置到协议文件」；会话里不保留唯一副本。

## F4-7 · 问：记忆检索命中率低，`memory search` 找不到明明有的内容。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：内容确实记过，但 `openclaw memory search "<词>"` 返回空或不相干结果。

**原因**：检索依赖**索引 + 分词/相似度**。常见：(1) 索引没更新（写入了但没重建）；(2) 关键词与存储用词不一致（同义词/中英混写）；(3) 检索范围排除了该记忆域。

**解法**：先确认索引新鲜度，再用宽口径回捞：

```bash
# 1) 索引是否含该记忆域 / 是否新鲜
find ~/.openclaw/workspace/agents/<agent>/memory -newer /tmp/stamp -type f 2>/dev/null | head
# 2) 宽口径 grep 直搜文件（绕过索引）
grep -rn "<近义词A>\|<近义词B>\|<英文alias>" ~/.openclaw/workspace/agents/<agent>/memory/ | head
# 3) 重建索引（若 CLI 提供）
openclaw memory reindex 2>/dev/null || echo "⏳ 无 reindex 子命令，走重建"
```

**验证命令**：

```bash
openclaw memory search "<词>" 2>/dev/null | head
# 期望：命中
```

**预防**：写入后触发索引更新；记忆条目统一「中文 + 英文 alias」双写以便检索。⏳ reindex 子命令以本机为准。

## F4-8 · 问：memory 和 skills 到底什么关系？别把记忆当技能用。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：把「怎么做一件事的步骤」写进 MEMORY，指望 Agent 会「照着做」，结果不生效。

**原因**：两者定位不同：**MEMORY = 记得什么（事实/状态）**，**skills = 会做什么（可复用能力/流程）**。把流程写进记忆，Agent 能「回忆起来」，但你每次还得告诉它「现在用这个」；把流程做成 skill，它才**自动可调用**。业界对位：Anthropic Skills / OpenClaw `skills/` 是**能力单元**；MemGPT 的 core/archival 是**记忆**，两者不可互替。

**解法**：按「事实 vs 能力」分流：

| 内容 | 归属 |
|---|---|
| 事实、状态、历史决策 | **MEMORY** |
| 可复用流程、步骤、工具编排 | **skill（SKILL.md）** |
| 身份/价值观 | SOUL |

```bash
# 把一个流程沉淀为 skill（最小骨架）
mkdir -p ~/.openclaw/workspace/skills/<my-skill>
cat > ~/.openclaw/workspace/skills/<my-skill>/SKILL.md <<'EOF'
---
name: my-skill
description: Use when <trigger>.
---
# 步骤
1. ...
EOF
```

**验证命令**：

```bash
# skill 入编校验（对照 F1-4 体检）
test -f ~/.openclaw/workspace/skills/<my-skill>/SKILL.md && head -5 ~/.openclaw/workspace/skills/<my-skill>/SKILL.md
```

**预防**：沉淀时先问「这是事实还是能力」；能力进 skills，事实进 MEMORY。

## F4-9 · 问：会话历史膨胀，越聊越慢、越聊越贵。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：同一个会话聊得越久，响应越慢、token 消耗越高。

**原因**：每次请求都携带历史上下文，长度线性增长 → 成本与延迟同步上升，直到触发压缩。这是**会话卫生（Session Hygiene）**问题：该收尾的会话不收尾，该分段的会话不分段。

**解法**：量化长度并主动分段：

```bash
# 1) 看当前会长/历史规模
du -sh ~/.openclaw/workspace/sessions/ 2>/dev/null
ls -lt ~/.openclaw/workspace/sessions/ 2>/dev/null | head

# 2) 长会话按主题切分；完成后归档
# 3) 归档前把结论沉淀进 MEMORY（避免丢上下文）
```

**验证命令**：

```bash
# 期望：单会话规模受控；归档后活跃会话数下降
ls ~/.openclaw/workspace/sessions/ 2>/dev/null | wc -l
```

**预防**：约定「一个任务一个会话」；任务结束即沉淀 + 归档。

## F4-10 · 问：记忆全息网络（Holographic Network）怎么落地？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：知道「记忆全息网络」是好概念，但不知从哪下手。

**原因**：**记忆全息网络**（v1.0 卷八模块2）指记忆不是孤立的条目，而是**互相链接的图**——任一条目的上下文都能通过链接还原「全息」。落地的关键是**显式建链**，而不是把所有东西塞进一个文件（那只是「大文件」，不是「网络」）。

**解法**：用「条目 + 链接」结构建最小全息网络：

```text
memory/
├── nodes/            # 每条记忆一个文件（原子化）
│   ├── decision-001.md
│   └── incident-20260921.md
└── links.md          # 显式交叉引用：[节点A] ↔ [节点B] 原因
```

```bash
# 统计节点数与链接数（网络密度）
ls ~/.openclaw/workspace/agents/<agent>/memory/nodes/ 2>/dev/null | wc -l
grep -c "↔\|->" ~/.openclaw/workspace/agents/<agent>/memory/links.md 2>/dev/null
```

**验证命令**：

```bash
# 期望：节点数>0 且 链接数>0（是网络不是列表）
echo "nodes=$(ls ~/.openclaw/workspace/agents/<agent>/memory/nodes/ 2>/dev/null | wc -l)"
```

**预防**：新增记忆时强制「至少连一条已有节点」；定期检查孤立节点（无链接者）。

## F4-11 · 问：压缩预算到底怎么调？`MAX_COMPACTION_RESERVE_RATIO` 设多少？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：不知道该给压缩留多少余量，留少了老压缩、留多了装不下。

**原因**：压缩需要一个**预留池**（reserve）来放「摘要 + 系统协议文件」。预留池真名 = `CompactionRequestBudget.reserveTokens`，其上限由常量 `MAX_COMPACTION_RESERVE_RATIO = 0.25` 约束（即最多占总预算 25%）。**注意：`MAX_COMPACTION_RESERVE_RATIO` 是内置常量，不是 config 项**，别往配置里写。

**解法**：按「协议文件体积 + 摘要需求」估预留池：

```bash
# 1) 估算协议文件占比（SOUL+AGENTS+USER+MEMORY 字符数）
cat ~/.openclaw/workspace/agents/<agent>/{SOUL,AGENTS,USER,MEMORY}.md 2>/dev/null | wc -c
```

## F4-12 · 问：记忆一致性怎么检测？记的和事实不符。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：Agent 坚持一个已经过期的「事实」（如旧版本号、旧路径），因为记忆没更新。

**原因**：记忆是**写时快照**，事实变了不会自动回改。这是**文档漂移**在记忆维度的体现——协议文件漂移（F2-12）之外，记忆条目也会漂移。业界无人做「记忆一致性」，本书将其纳入每周体检。

**解法**：建「记忆 ↔ 事实源」的一致性哨兵：

```bash
# 检查记忆里是否残留已作废的值（示例：旧版本号）
grep -rn "2026.3.2\|reserveTokensFloor" ~/.openclaw/workspace/agents/*/memory/ 2>/dev/null
# 命中即「记忆与事实漂移」，需回改

# 期望：无输出（记忆里不含作废值）
```

**验证命令**：

```bash
grep -rn "2026.3.2\|reserveTokensFloor" ~/.openclaw/workspace/agents/*/memory/ 2>/dev/null || echo "✅ 记忆无作废值"
```

**预防**：事实变更时同步回改相关记忆条目；把「作废值黑名单」纳入巡检（对位每周体检清单）。

## F4-13 · 问：坏 skill 污染记忆 / 拖累加载怎么办？

**原因**：「18 坏 skill 修复」事件的根因就是一批目录不合规却混在搜索路径里。坏 skill 会让注册/加载阶段反复报错或跳过异常，进而影响与之耦合的检索流程。**这是环境层问题（对位 [F1-4](./F1-环境与安装.md)），但会表现为记忆/会话层症状**。

**解法**：先清坏 skill，再验证记忆加载恢复：

```bash
SK="$HOME/.openclaw/workspace/skills"
find "$SK" -maxdepth 2 -name SKILL.md | wc -l          # 合规数
ls -d "$SK"/*/ | wc -l                                  # 目录总数
# 差值 = 疑似坏 skill 数；逐个补 SKILL.md 或移出搜索路径
```

**验证命令**：


**预防**：skill 入库硬门槛（SKILL.md + frontmatter）；定期体检；坏 skill 移入 quarantine 而非留在路径里。

## F4-14 · 问：会话压缩和 heartbeat 会互相干扰吗？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：心跳醒来后，发现当前会话被压缩过、上下文变了，导致它「记不起」刚才在做的事。

**原因**：压缩与心跳共用一个**上下文预算池**。心跳唤醒本身要加载协议文件（SOUL/USER/HEARTBEAT），会**推高占用**，间接促使压缩提前触发。两者不是独立通道，而是**共享预算**。

**解法**：把「心跳所需的最小上下文」与「长任务上下文」错峰/分层：

```bash
# 1) 量心跳唤醒时的上下文占用（对比会话）
grep -i "reserve\|compact" ~/.openclaw/workspace/logs/heartbeat.log 2>/dev/null | tail
# 2) 长任务期间降低心跳频率（见 F3-5），避免挤压预算
```

**验证命令**：

```bash
# 长任务期间压缩次数应下降
grep -c -i "compact" ~/.openclaw/workspace/logs/session*.log 2>/dev/null
```

**预防**：长任务期临时降频心跳；心跳动作只用轻上下文（不带长记忆）。

## F4-15 · 问：记忆怎么备份与迁移？换机就失忆。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：换到新 Mac 或重装后，Agent 的 MEMORY / 会话 / skill 全没了。

**原因**：记忆、会话、skill 都散在 `~/.openclaw/workspace/` 下的多个目录里，**默认不会自动同步**。没有备份 = 单点故障。这是治理上「没有账本就没有真正的治理」（v1.0 卷七模块4）在记忆维度的延伸——没有备份就没有连续性。

**解法**：把「身份四件套 + 记忆 + skills」纳入统一备份：

```bash
# 备份（身份/记忆/技能/协议）
tar -czf ~/openclaw-backup-$(date +%F).tgz \
  -C ~/.openclaw/workspace \
  agents skills references/memory 2>/dev/null
ls -lh ~/openclaw-backup-*.tgz | tail -1
```

```bash
# 迁移到新机：解包后校验哈希一致
tar -xzf ~/openclaw-backup-YYYY-MM-DD.tgz -C ~/.openclaw/workspace/
find ~/.openclaw/workspace/agents -name MEMORY.md -exec sha256sum {} \; | head
```

**验证命令**：

```bash
# 期望：备份文件存在 + 解包后关键文件哈希可核对
tar -tzf ~/openclaw-backup-*.tgz | grep -c MEMORY.md
```

**预防**：定期备份 + 纳入 git（F2-15）；备份文件异地存一份；恢复后跑一次记忆检索回归（F4-4/F4-7）。
