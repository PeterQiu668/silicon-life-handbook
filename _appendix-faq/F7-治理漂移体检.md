## 分类简介

F7 覆盖「Agent 跑久了，怎么知道它没坏、坏了怎么修」这一段的所有坑。这一段的特点是：**故障表现为「慢性」（越跑越偏）且「不报错」**——文档慢慢漂、人格慢慢变、能力矩阵慢慢过期，日志里一切正常，直到某天发现 agent「不认识自己」。

本分类的核心判断原则：

- **漂移看 diff、不看感觉**：任何「感觉它变了」都要变成**两条可 diff 的文本**（v1.0 **卷五模块4**「文档漂移与人格漂移」）。
- **完成要有证据（TEV）**：没有证据不算完成（v1.0 **卷六模块3「三证验真」**：新产物 / 前后 Diff / 测试日志）。
- **治理靠账本**：没有审计账本就没有真治理（v1.0 **卷七模块4「治理账本」**）。
- **体检是周期动作**：能力矩阵 / 每周体检必须挂 cron，纸面清单 = 0 次执行。
- 凡「漂移/体检」类问题，答案里必须有一条**可 diff / 可打分**的命令。
- 每问都给可执行命令；凡未在本机复现的，标 ⏳ 待实测。

## F7-1 · 问：文档漂移（Document Drift）告警——文档和事实对不上怎么办？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：手册/协议里写的字段、版本、路径与实际不符（如文档写 `2026.3.2`，本机是 `2026.9.4`；写 `reserveTokensFloor`，真名是 `reserveTokens`）。人一读就被带偏。

**原因**：**文档漂移（Document Drift）** 是 v1.0 **卷五模块4「文档漂移与人格漂移-为什么 agent 会不认识自己」** 的核心概念，业界空白赛道。漂移不会报错，只会「慢慢和事实脱节」——最典型就是**版本号传抄**：调研线采信一个过期快照（`2026.3.2`）后一路传抄进多份文档。

**解法**：把「真名」钉死为命令输出，任何文档引用前重跑：

```bash
# 版本真名（三源交叉验证）
openclaw --version                    # 唯一权威
npm view openclaw version 2>/dev/null # registry 对比
# 字段真名反查（误植字段应为 0 命中）
grep -rn "reserveTokensFloor" ~/.openclaw/workspace/references 2>/dev/null | wc -l
grep -rn "2026\.3\.2" ~/.openclaw/workspace/references 2>/dev/null | wc -l
```

**验证命令**：

```bash
openclaw --version 2>/dev/null | grep -q "2026.9.4" && echo "✅ 版本真名=2026.9.4" || echo "❌ 版本漂移，重查"
```

**预防**：文档模板版本占位符统一写 `OpenClaw 2026.9.4 (3a9d69d)`；任何「License/字段/路径」引用回到**文件文本 / 主仓**核实（见 F7-5 TEV）。

## F7-2 · 问：人格漂移（Personality Drift），agent 越聊越不像它自己。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：Agent 说话风格、价值观、边界感逐渐偏离 SOUL.md 定义——原本克制的开始话痨，原本严谨的开始编造。

**原因**：**人格漂移（Personality Drift）**（v1.0 **卷五模块4**）源于：SOUL/IDENTITY 长期未校准、会话污染累积、记忆写入了与人格冲突的内容、或 SOUL 被会话中的临时指令带偏。它和「文档漂移」是一对：**文档漂了人会读到错信息，人格漂了 agent 会做出错判断**。

**解法**：定期把「当前行为画像」与 SOUL.md diff：

```bash
# 1) 看 SOUL 最后更新时间（漂移高危信号）
ls -l ~/.openclaw/workspace/agents/*/SOUL.md 2>/dev/null | head
# 2) 抽取近期会话关键词，与 SOUL 的价值词做 diff（示意）
grep -iE "克制|严谨|边界|价值" ~/.openclaw/workspace/agents/<id>/SOUL.md | head
# 3) 漂移触发阈值：SOUL > 90 天未更新 → 自动建整改单（见 F7-8）
```

**验证命令**：

```bash
# 期望：SOUL.md 近期有校准痕迹（mtime 不早于上次体检）
find ~/.openclaw/workspace/agents -name "SOUL.md" -mtime -30 2>/dev/null | wc -l
```

**预防**：SOUL 校准纳入每周体检（F7-3）；> 90 天未更新即漂移告警；人格冲突写入即回滚记忆。

## F7-3 · 问：每周体检不通过（Weekly Health Checklist）怎么办？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：跑每周体检，一堆项标红：协议陈旧、心跳没跑、能力矩阵过期、坏 skill 未清。

**原因**：**每周体检清单（Weekly Health Checklist，v1.0 卷五模块6「长期稳定性检查清单-如何每周给 agent 做体检」）** 是周期动作，业界空白。不通过的根因常是**「机制存在但没跑」**——v2026.9 附录 A 新认知一实测：USER/SOUL/AGENTS 配置存在率 100% 但**跑齐率仅 60%（陈旧 5 月）**，HEARTBEAT 协议存在率 100% 但**跑齐率 0%**。

**解法**：跑结构化体检并逐项打分：

```bash
# 体检五项（示意）
echo "1) 协议陈旧："; find ~/.openclaw/workspace/agents -name "*.md" -mtime +90 2>/dev/null | wc -l
echo "2) 坏 skill："; bash /tmp/bad-skills-check.sh 2>/dev/null || echo "见 F5-1"
echo "3) 能力矩阵："; find ~/.openclaw/workspace/agents -name "*能力矩阵*" 2>/dev/null | head
echo "4) cron 失败："; openclaw cron list 2>/dev/null | grep -i "error\|fail" | head || echo "⏳ CLI 为准"
echo "5) 备份："; ls ~/openclaw-backup-*.tgz 2>/dev/null | tail -1
```

**验证命令**：

```bash
# 期望：五项均绿；红项转成修复工单（F7-7）
echo "体检完成，红项数：$(find ~/.openclaw/workspace/agents -name '*.md' -mtime +90 2>/dev/null | wc -l)"
```

**预防**：每周体检挂 cron（对齐 v4.0 待办 §2.11「缺每周体检 cron plist」）；红项自动建单。

## F7-4 · 问：Trust Score 失信 / 信誉分下降，怎么结算与恢复？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：某 Agent 的信任评分持续走低，任务被降级或需人工复核。

**原因**：**信任评分 / 功绩账本（Trust Score / Merit Ledger，原：信誉分 / 军功簿，术语表 v3.0 第 12 条）** 是 v1.0 **卷六模块5「信誉分与军功簿-没有结算治理就是空话」** 的核心。原版口径：成功调用 +5% / 失败调用 -15%。失信多因**失败未复盘、整改不及时**——本机整改单实战实测「整改及时率 2/2 = 100%、复盘完成率 2/2 = 100%，但**主动出击率 0%（未启动）**」（`volume-06/附录A`）。

**解法**：按维度计分 + 分档处置：

```bash
# 1) 看当前整改单完成情况
ls ~/.openclaw/workspace/agents/*/memory/decisions/整改单/ 2>/dev/null | head
# 2) 计分维度（对齐附录 A）
#    任务成功率 / 整改及时率 / 复盘完成率 / 主动出击率
```

分档处置（A 90%+ 享优先权 / B 70–90% 标准 / C 50–70% 需关注 / D <50% 需整改）。

**验证命令**：

```bash
# 期望：整改及时率 + 复盘完成率均 100%
find ~/.openclaw/workspace/agents -name "*整改*" -o -name "*修复工单*" 2>/dev/null | wc -l
```

**预防**：Trust Score 纳入月度能力矩阵（F7-6）；主动出击率是当前最大短板（0% 未启动）。

## F7-5 · 问：TEV 三证据验证怎么做——「说完成」凭什么算完成？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：Agent 报「任务已完成」，但拿不出可核对的证据；事后无法确认到底做没做。

**原因**：**三证据验证（Three-Evidence Verification / TEV，原：三证验真，术语表 v3.0 第 10 条）** 是 v1.0 **卷六模块3「三证验真-没有证据就不是完成」** 的验收口径：**① 新产物 ② 前后 Diff ③ 测试日志**，三者齐才算完成。业界无此层，故 Agent 习惯「口头完成」。

**解法**：每次交付强制落三证据：

```bash
# 证据 1：新产物
ls -l 交付物路径
# 证据 2：前后 Diff
diff <(git show HEAD:file) file   # 或 cp 前后对比
# 证据 3：测试日志
命令 2>&1 | tee /tmp/test-$(date +%F).log && tail -5 /tmp/test-*.log
```

**验证命令**：

```bash
# 期望：三证据文件均存在
test -f /tmp/test-$(date +%F).log && echo "✅ 有测试日志" || echo "❌ 缺证据3"
```

**预防**：TEV 三证据写入验收标准（Task Card / Acceptance Criteria）；无三证据 = 未完成。

## F7-6 · 问：能力矩阵 26 天未续期，怎么自动续期？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：季度/月度能力矩阵停在旧版本，**自 2026-09-01 后无新更新，已 26 天未续期**；晨报发现「最近活跃日志」仍是旧版。

**原因**：**能力矩阵月度更新 cron（`cron_a2d4eb3d4399`）** 是 v2026.9 新识别的事故样本（`volume-08/模块1-动态进化机制·v2026.9增量补丁.md` §1.2 #10）：触发器没挂到可执行钩子上，于是「机制存在、0 次执行」。8 个 P0 **stub 自指悖论**（§1.3）里多个正与此相关——它们本应被「任务失败+可归因」触发自动补全，但触发器没工作。

**解法**：把月度续期挂 cron + 落取证四元组：

```bash
# 1) 查能力矩阵最后更新
find ~/.openclaw/workspace/agents -name "*能力矩阵*" -exec ls -l {} \; 2>/dev/null | head
# 2) 查该 cron 是否在跑
openclaw cron list 2>/dev/null | grep -i "能力矩阵\|a2d4eb3d4399" | head || echo "⏳ CLI 为准"
# 3) 续期落点（v2026.9 §1.2 #10）
#    ~/.openclaw/workspace/agents/<id>/memory/YYYY-MM-DD-能力矩阵月度更新.md
```

**验证命令**：

```bash
# 期望：能力矩阵 mtime 在 30 天内
find ~/.openclaw/workspace/agents -name "*能力矩阵*" -mtime -30 2>/dev/null | wc -l
```

**预防**：能力矩阵续期纳入月度 cron + 每周体检项；**26 天未续期**即触发 `delegate_task goal='刷新能力矩阵'`（v2026.9 §1.2 #10）。

## F7-8 · 问：整改单自动触发条件怎么配（不靠人肉发现）？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：故障靠人发现才建单，晚了好几小时。

**原因**：靠人肉 = 有延迟。8/19 与 9/21 事故的教训就是**缺自动探针**——9/21 的 `attempts=2471` 积压无人发现。附录 A 已给自动触发条件表，但需挂到 cron/探针上才生效。

**解法**：按附录 A 触发器表配置：

| 触发器 | 阈值 | 自动建单 |
|---|---|---|
| cron 连续失败 | `consecutiveErrors ≥ 3` | ✅ 立即 |
| 飞书账号 disconnected | > 5 min | ✅ 立即 |
| clobbered 文件 | 月度 ≥ 1 | ✅ 立即 |
| 模型 empty response | 同一 Agent 24h 内 ≥ 5 | ✅ 立即 |
| SOUL 漂移 | > 90 天未更新 | ✅ 立即 |
| 备份爆炸 | 同名 `.bak` > 10 | ⚠️ 每周汇总 |

```bash
# 自查各触发器现状
openclaw cron list 2>/dev/null | grep -i "consecutiveErrors\|error" | head || echo "⏳ CLI 为准"
find ~/.openclaw/workspace -name "*.bak.*" | wc -l   # >10 → 备份爆炸
```

**验证命令**：

```bash
# 期望：cron 无 consecutiveErrors≥3；bak 数 <10
openclaw cron list 2>/dev/null | grep -c "consecutiveErrors.*[3-9]" || echo "0"
```

**预防**：触发器挂 launchd/cron 常驻；`state.consecutiveErrors >= 3` 自动进错误退避 + 建单（8/19 时曾有 **15 个 cron 进入此状态**）。

## F7-10 · 问：漂移检测脚本不会写，怎么给文档/人格漂移做自动检测？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：知道要做漂移检测，但不知道从哪写起。

**原因**：v4.0 待办明确「**缺卷五 M4 漂移检测的具体脚本**」（`v4.0-refactor-checklist.md` §2.9）。漂移检测的本质是**基线 diff**：把「应然」（SOUL/协议/字段真名）与「实然」（当前行为/配置）比对，超阈值即告警。

**解法**：三段式检测脚本骨架：

```bash
#!/bin/bash
# drift-check.sh — 漂移检测骨架（示意，⏳ 待按本机路径落地）
# 1) 版本漂移
cur=$(openclaw --version 2>/dev/null | grep -o '2026\.[0-9.]*')
```

## F7-13 · 问：会话污染导致「越说越乱」，怎么治理？

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：长会话里 Agent 被错误信息带偏，越答越乱，甚至「记错人设」。

**原因**：**会话污染与清理**（v1.0 **卷五模块3「会话污染与清理-为什么 agent 会越说越乱」**）：错误事实进了上下文后会持续影响后续生成。它与会话压缩（Session Compaction）交互：压缩不当会把「污染」固化进摘要，也会把「关键事实」压没。

**解法**：清理污染 + 核对压缩字段真名：

```bash
# 1) 找出会话里压缩/污染迹象
grep -iE "compact|compress|reserve" ~/.openclaw/workspace/logs/session*.log 2>/dev/null | tail
# 2) 核对压缩预算真名（reserveTokensFloor 为误植）
grep -nE "reserveTokens|MAX_COMPACTION_RESERVE_RATIO" ~/.openclaw/openclaw.json
# 3) 清理：重开会话 / 修正 MEMORY 后 reindex
```

**验证命令**：

```bash
# 期望：无 reserveTokensFloor 误植；污染事实已从 MEMORY 清除
grep -c "reserveTokensFloor" ~/.openclaw/openclaw.json   # 期望 0
```

**预防**：发现错误事实立即修正 MEMORY 并重开会话；压缩预算用真名 `CompactionRequestBudget.reserveTokens`（见 [F4](./F4-记忆与会话.md)）。

## F7-15 · 问：能力矩阵月度更新 cron 连续失败，红了没人管。

> 环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27

**现象**：能力矩阵更新 cron 报 `error`（**能力矩阵 26 天未续期**的根因之一），但没人发现，直到晨报扫描才暴露。

**原因**：v2026.9 新认知一实测：**「进化报告」跑齐率为 `error (4x)`**——**cron 连续失败（`consecutiveErrors ≥ 3`）会自动进入错误退避模式**，越退越不跑，形成「失败→退避→更失败」的恶性循环。8/19 事故时曾有 **15 个 cron 进入此状态**。

**解法**：查连续失败 + 重置 + 建单：

```bash
# 1) 列出连续失败的 cron
openclaw cron list 2>/dev/null | grep -iB1 -A2 "consecutiveErrors" | head -40 || echo "⏳ CLI 为准"
# 2) 重置退避（手动触发一次成功运行后应归零）
openclaw cron run <job_id> 2>/dev/null || echo "⏳ 以本机命令为准"
# 3) 给该 cron 建修复工单（F7-7）
```

**验证命令**：

```bash
# 期望：目标 cron 的 consecutiveErrors 归零
openclaw cron list 2>/dev/null | grep -A2 "能力矩阵" | grep -c "consecutiveErrors.*0" || echo "⏳ 手工核对"
```

**预防**：`consecutiveErrors ≥ 3` 自动建单（F7-8 触发器表）；cron 健康纳入每日巡检（对齐 `cron-last-active-writer` / `launchd-truth-check` 手法）。
