# 第 1 章 · 生命协议：Agent 的七个契约

---

## 一、为什么这一章存在

### 1.0 训虾哲学开篇 · Agent 为什么需要契约，而不是提示词

#### 1.0.1 一个几乎所有人都会答错的题

先请你回答一个问题。

假设你现在要给一个智能体立规矩：让它永远不要泄露内部定价、永远先给结论再给理由、永远在动手改文件之前先备份。你会把这些规矩写在哪里？

绝大多数人的答案是：写在系统提示词里。

再追问一层：这个系统提示词下一次会话还在吗？它跨模型迁移吗？当上下文被压缩到 25% 的时候，它还在窗口里吗？当这个智能体被另一个智能体接管、或者被换进另一条消息通道的时候，它跟随过去了吗？

到这里，很多人开始犹豫。因为他们隐约意识到一件事：**提示词是一种易失介质。**它活在这一次会话的上下文里，而上下文是一种会被压缩、会被截断、会被摘要、会随会话生命周期整体蒸发的临时存储。

这就是本章要论证的第一个、也是最硬的判断：**智能体需要的不是更长的提示词，而是一层不会被会话带走的规矩。**在本书的语汇里，这一层叫协议层（Protocol Layer），它的最小实现形态是七个 Markdown 文件，我们把这七个文件称为契约（Contract）。

有人会说，这不就是把提示词存成文件吗？区别在哪？

区别在于**所有权和生命周期**。提示词的所有权属于"这一次对话"——它由说话的人临时下达，对话结束它就消失了，下一次对话要重新下达，而且没有人能保证下一次下达的和这一次是同一份。契约的所有权属于"这个智能体自己"——它是一份被写下来、被版本化、被启动时自动加载、被所有人（包括智能体本身）反复阅读的长期文件。

一句话：**提示词是临场指令，契约是宪法。**临场指令决定它这一次怎么答；宪法决定它一年之后还是不是同一个它。

#### 1.0.2 提示词的物理寿命：为什么"我明明写清楚了"不是证据

我们来把"提示词会失效"这件事，从一句抱怨变成一个可以被观察的物理过程。

第一层失效叫**截断**。上下文窗口是有限的。当一次会话不断增长，系统必须在某个点做取舍：完整的旧消息、还是被摘要过的旧消息。压缩（Compaction）机制一旦介入，早期那些"我明明写清楚了"的约束就从原始文本降级成了摘要，再从摘要变成一句"此前对话多为事务性沟通"。到这一步，规矩已经不在窗口里了，只是它的影子还在。

第二层失效叫**稀释**。就算提示词还在窗口里，它也不再是"唯一被注意的东西"。窗口里同时挤着任务描述、工具返回、文件内容、历史消息、检索结果。注意力不是均分的，它会被最近、最具体、最像任务的内容吸引。一条写在两万 token 之前的"不要泄露定价"，在与一条刚刚返回的、包含销售表格的工具结果竞争注意力时，输的概率并不低。

第三层失效叫**漂移**。这是最隐蔽的一种。同一个智能体，同一条规矩，第一天遵守得好好的，第十五天开始"偶尔忘"，第三十天开始"解释性违反"——它不再直接违规，而是先给你一段理由，说明这一次的特殊情况为什么值得破例。这不是模型坏了，这是**约束在缺少外部锚点时会自然衰减**。任何一条只靠"记住"来维持的规矩，都会漂移。

第四层失效叫**迁移断裂**。提示词是绑在模型上的。你从 A 模型换到 B 模型，提示词的措辞、格式偏好、对指令的敏感度全都变了。你在 A 上精调了三个月的那段系统提示，到 B 上可能需要重新调三个月。而契约不换——换的只是读契约的那个引擎。

把这四层失效摆在一起，你会看到一个共同结构：**它们都不是"内容写得不够好"的问题，而是"介质选错了"的问题。**你把宪法写在了便签纸上。便签纸上的字没有错，错的是纸。

#### 1.0.3 契约的第一性原理：把身份从会话里搬到文件里

那正确的介质应该具备什么性质？我们从第一性原理出发，一条一条推。

第一条性质：**持久**。它必须活在会话之外，会话结束它不结束，会话开始它自动回来。这是"不被带走"。

第二条性质：**可分节**。它必须能被拆成若干职责清晰、各自独立、可以单独修改和单独版本化的部分。一个两万字的巨型提示词不是协议层，它是一份不可维护的散文。协议层的第一美德是可维护。

第三条性质：**可版本化**。它必须能被 Git 管理。人格变了、权限收紧了、边界放宽了，这些都必须留下 diff、留下时间戳、留下"谁在什么时候因为什么改了它"。没有版本的规矩等于没有规矩，因为你永远无法证明"它以前不是这样"。

第四条性质：**启动时自动加载**。它不能依赖任何人记得去提醒智能体读它。一个需要被提醒才生效的规矩，在无人值守的夜里等价于不存在。协议层必须是**开机即生效**的。

第五条性质：**与引擎解耦**。它不能绑死在某个模型或某个产品上。它应该是一组文本，任何一个足够强的模型接上它，都能成为"同一个智能体的另一个版本"，而不是"一个新的人"。

第六条性质：**人能读、机器也能读**。它必须是人类可以逐条评审的（否则无法治理），同时是机器可以稳定解析的（否则无法执行）。Markdown 恰好同时满足这两点——这解释了为什么 2026 年的主流方案不约而同地落在 Markdown 上，而不是 YAML、JSON 或某个私有 DSL。

把这六条性质摆在一起，你会发现它们排除了绝大多数候选介质：一段系统提示词不持久、不可分节、不可版本化；一份 JSON 配置缺少人能读的叙事性，无法承载"我是谁"这种需要被说服的内容；一个数据库记录既不透明也不利于人工评审。

留下来的是一个朴素到近乎寒酸的答案：**几个 Markdown 文件，放在智能体的工作目录里，启动时按顺序读进去。**

OpenClaw 的七个契约就是这六条性质的落地：`USER.md` 回答"我服务谁、我的权限边界在哪"；`SOUL.md` 回答"我是谁、我为什么存在"；`AGENTS.md` 回答"我有哪些同类、我怎么跟它们交接"；`TOOLS.md` 回答"我能调用什么、禁止调用什么"；`HEARTBEAT.md` 回答"我多久醒一次、醒来做什么"；`IDENTITY.md` 回答"我对外叫什么、属于哪里"；`MEMORY.md` 回答"我记得什么、怎么记、怎么忘"。

#### 1.0.4 为什么恰好是七份：一个最小完备集的推导

"七个"这个数字常被误以为是设计者的口味。它不是。把"一个智能体要在无人值守的情况下长期独立运行"这个目标拆解成不可再少的职责，你会得到七个——每一个都对应一类"缺了它系统就会以特定方式崩掉"的失效。

缺 `USER`，崩的方式是**越权**。没有人告诉它边界在哪，它就会用自己的判断代替主人的判断。它可能在一次"顺手帮忙"里对外发出本不该发出的承诺。越权事故的共同特征不是恶意，而是**边界从未被写下来过**。

缺 `SOUL`，崩的方式是**人格分裂**。它会随着对话风格的漂移而漂移，遇到强硬的对手就变强硬，遇到撒娇的用户就变谄媚。它没有内在的"我"，所以它的"我"完全由最后一次交互塑造。

缺 `AGENTS`，崩的方式是**抢活与漏活**。多智能体环境里，没有明写的分工，就会出现两方都以为对方在做，或者两方都以为这事该自己做。协同事故的第一现场从来不是技术故障，而是职责的空白格。

缺 `TOOLS`，崩的方式是**能力越界**。工具是权限的实体化形式。有 `rm` 权限的智能体和只有读权限的智能体，是两种完全不同的风险等级。不写清楚，它就会用默认权限做事，而默认权限永远是"更宽"的那一个。

缺 `HEARTBEAT`，崩的方式是**节律失能**。它不会自己醒来。所有主动性归零，它退化成"你问我才答"的问答机。而一个不能主动查看、不能主动巡检、不能主动汇报的智能体，在组织里只是一个更贵的搜索框。

缺 `IDENTITY`，崩的方式是**归属丢失**。它不知道自己属于谁、在哪个群里说话、被谁路由。事故表现是"说错话给错人"——这在真实组织里往往比技术故障更致命。

缺 `MEMORY`，崩的方式是**失忆与遗忘失衡**。要么什么都忘，每次重新问；要么什么都记，三个月后记忆里全是事务流水，检索质量归零，关键事实被自己的噪音埋掉。

七种失效，七份契约，一一对应。**没有一份是装饰品，也没有一份可以靠"我记性好"替代。**这就是"最小完备"的含义。

#### 1.0.5 四条分界线：契约与提示词的对照

把前面的论证压成一张表，四行就够。

| 维度 | 提示词（Prompt） | 契约（Contract） |
|---|---|---|
| **生命周期** | 一次会话；压缩即降级，会话结束即蒸发 | 永久；启动自动加载，跨会话、跨模型传递 |
| **所有权** | 下达指令的人 | 智能体自身（本体文件） |
| **可治理性** | 无法审计"上一次它是怎么写的" | Git 版本化，每次修改有 diff、时间戳、责任人 |
| **失效方式** | 截断 / 稀释 / 漂移 / 迁移断裂 | 只在被显式改写时才变化——**变化本身成为可观测事件** |

最后一行是这个对照最重要的输出。提示词的失效是**静默的**：你没有被告知它已经不在窗口里了。契约的变化是**有声的**：任何人改了 `SOUL.md`，Git 会说话，diff 会说话，下一次体检的漂移检测也会说话。

治理的第一步不是让人变好，而是让"变坏"这件事变得看得见。**这正是契约相对提示词的根本优势：它把不可观测的漂移，转换成可观测的事件。**

#### 1.0.6 反方观点：'契约不过是很长的提示词'

一个诚实的论证必须处理最强的反对意见。最强的反对意见是：契约文件最终也要被拼进上下文，所以它本质上还是一段很长的提示词，只是存在了磁盘上。这套说法有它的杀伤力，我们逐条回应。

回应一：**位置不同，优先级不同。**契约文件在 OpenClaw 里处于系统层的固定位置，先于用户消息、先于工具返回被加载，并且往往带有更强的指令语义。它和"任务中随手追加的一句提示"不在同一个权限层级上。把它们混为一谈，等于说"宪法和法院判决书都是文字，所以是一回事"。

回应二：**持久性本身就是功能，不是实现细节。**把规矩存到磁盘上，不是为了省字符，是为了让它**在会话消失后仍然存在**。"存在哪里"决定了"能不能被引用、能不能被比较、能不能被追责"。一份三个月前写下的 `SOUL.md` 和今天的行为可以直接对照——这是提示词永远做不到的。

回应三：**契约的价值在于它是共识的载体，而不在于它是指令。**提示词是单向的（我下命令，你执行）。契约是双向的（我写下它，你也读它，我们都能引用同一份文本讨论分歧）。当一个组织里三个人、五个智能体、十八个成员都要对"这个 agent 该怎么表现"达成一致时，需要的是**一份可以被共同引用的文本**，不是一段各自复述的记忆。

回应四：**即使契约必须进入上下文，压缩时的处理也不同。**这是最技术性、也最有说服力的一条。契约文件的处理策略是**重载**而非**摘要**——压缩丢掉会话历史，但契约在下一轮启动时被重新读进来。也就是说，契约不在"会被压缩的东西"那一类里。这句话拆掉了反对意见的地基：契约之所以是契约，恰恰因为它**不属于会被摘要的介质**。

#### 1.0.7 训虾哲学的三条判据

讲到这里，可以给出一组在后面的所有章节里反复使用的判据。任何一条"规矩"，你都可以用它来问自己：它到底应该写成提示词，还是写成契约？

**判据一 · 时间跨度判据**：这条规矩管的是"这一轮怎么答"，还是"它一直是谁"？前者写提示词，后者写契约。

**判据二 · 追责判据**：如果它违反这条规矩，你需要能查出来"它以前是不是也这样"吗？需要，就写契约——因为只有契约提供时间序列。

**判据三 · 交接判据**：这条规矩需要被第三方理解、评审、接手吗？需要，就写契约——因为契约是把一个人的判断变成一群人共识的唯一低成本形式。

三条判据合用，你会得到一个反直觉的结论：**绝大多数你以为该写提示词的东西，其实该写契约。**"先给结论再给理由"是契约（它管的是长期风格）。"这次用中文回答"是提示词（它管的是这一轮）。"绝不承诺交付日期"是契约。"把这段改成 300 字以内"是提示词。

分类错了的代价是不对称的：把契约写成提示词，你会得到一只**每次都要重新教一遍、并且越教越不像自己**的智能体；把提示词写成契约，你的 `SOUL.md` 会膨胀成一份没人读的流水账。前者是本书要解决的主要问题，后者只是个小麻烦。**所以遇到不确定，默认往契约那边放。**

#### 1.0.8 跳过这一节的代价：三种"以为"

不读这一节（以及它后面 1.1–1.5 的完整论证）的人，会在三个地方付出代价，而且每一次付出时都不会意识到是这里欠的账。

第一种代价是**以为提示词工程是终局**。他会持续投入精力去打磨那段系统提示，把它从两千字优化到两万字，然后发现效果在两周内衰减回去。他不明白问题不在措辞，而在介质。这类人通常要经历三到五轮"精调—衰减—再精调"的循环，才会开始怀疑对象选错了。

第二种代价是**以为漂移是玄学**。当智能体开始"偶尔不听话"，他会归因于模型不稳定、网络波动、玄学。他没有基线，所以无法回答"它上周是不是也这样"；他没有版本，所以无法回答"我们什么时候动过它"。**没有基线的漂移讨论，全部是情绪讨论。**

第三种代价是**以为多智能体只需要多开几个实例**。他不知道 `AGENTS.md` 这类契约承担的是"分工的可执行化"，于是他把五个 agent 塞进同一个群，期待它们自然协作，然后在一次事故里发现三个人都在等另外两个人动手。协同的失败从来不是算力问题，是**职责没有被写成文本**的问题。

#### 1.0.9 这一节要你带走的四句话

如果这一节只能留下四句话，是这四句。

第一句：**提示词是临场指令，契约是宪法。**你需要的不是更长的提示，而是不会被会话带走的规矩。

第二句：**契约的六条性质（持久、可分节、可版本化、自动加载、与引擎解耦、人机双读）共同排除了其他所有介质形态。**选 Markdown 不是审美，是推导结果。

第三句：**契约把静默的漂移转换成可观测的事件。**这是它相对提示词不可替代的根本价值——治理的前提是"变坏看得见"。

第四句：**分不清该写哪边的时候，写契约。**错的代价是不对称的：漏成提示词要反复重教，多成契约只是文件略胖。

带着这四句话往下读，1.1 会给你一个具体的场景（为什么你的 Agent 越用越不像它自己），1.2 会给你坐标系（三个世界与全书结构），1.3 会告诉你会遭遇什么，概念 1 则会把这四句话变成一条可操作的判别法则。

#### 1.0.10 契约不是枷锁：为什么约束反而放大能力

上面这套论证会让一部分读者本能地反感。他们的直觉是：约束就是限制，限制就是变弱。一个被七个文件管住的智能体，怎么可能比一个自由发挥的智能体更强？

这个直觉在一个地方成立，在另一个地方彻底翻转。

它成立的地方是**单次创造性任务**。让模型写一首诗、想三个产品名、给一段代码提五种重构方案，这时候任何约束都是负资产。你越放手，它给出的样本越多样。

它翻转的地方是**长期运行的组织角色**。一个要连续运行三百天、要在凌晨三点独自巡检、要在没有被明确授权时忍住不动手、要在被质疑时拿出证据的智能体，它面对的核心矛盾不是"想不到"，而是"守不住"。**长期运行里，能力的瓶颈从来不是上界，而是下界**——是它会不会在某个疲倦的瞬间掉到你不接受的水位以下。

约束正是用来抬高下界的。`SOUL.md` 里那句"不确定时说不确定"，不是让它在某一次回答里更聪明，而是保证它在第一万次回答里也不会开始编造。`USER.md` 里那条权限红线，不是让它在某一次操作里更强，而是保证它在某次误判时不会真的动手删掉东西。

更反直觉的是，抬高下界会反过来抬高上界。原因在于**信任预算**。一个组织愿意给一个智能体多大的自主权，取决于它能被信任到什么程度。能被信任到"通宵自己跑、出问题自己开单、只在需要人决策时才叫人"的智能体，可以获得别人拿不到的任务面。而信任不是靠一次惊艳表现赢来的，是靠一千次不掉线攒下来的。**契约是把每一次不掉线变成常态的装置。**

所以在训练学的框架里，契约不是刹车，是**让你敢踩油门的那个东西**。

#### 1.0.11 七个契约的加载顺序，以及它为什么重要

七个文件不是一份无序的清单，它们之间存在一个隐含的加载与依赖顺序。这个顺序在出事故的时候，就是你排查的顺序。

排在最前面的是 `IDENTITY`。它是"我是谁的下属、我在哪个容器里"。它决定后面所有内容的**作用域**——同一个 `SOUL.md` 被两个不同 `IDENTITY` 的实例加载，会产生两个不同的行为主体。身份不明，后面全是错的。

第二位是 `USER`。它是"我服务谁"。用户是谁，决定了权限的边界、语气的基调、决策时站在谁的立场上。契约 1 排在契约 2 之前，不是编号随意，而是**逻辑上先有服务对象，才有人格取向**。

第三位是 `SOUL`。人格锚点。它建立在"我是谁的下属"和"我服务谁"之上。这就是为什么单独复制一份 `SOUL.md` 到另一个 agent 会在两周内长歪——它脱离了前两层的支撑。

第四位是 `AGENTS`。分工与交接。只有当前三层清楚（我是谁、服务谁、以什么风格），"我该跟谁交接什么"才有确定答案。

第五位是 `TOOLS`。能力与权限的实体化。它必须在人格与分工之后定义——因为"我能调用什么"取决于"我该做什么"。

第六位是 `HEARTBEAT`。节律。它是唯一一个**主动**驱动其他契约的契约：每次醒来，它按前五份契约决定要做什么。

第七位是 `MEMORY`。它是全部经验的落点，也是唯一一个**被其他所有契约写入、又反过来影响其他所有契约**的文件。

把顺序读一遍，你会发现它是一个闭环：`IDENTITY → USER → SOUL → AGENTS → TOOLS → HEARTBEAT → MEMORY → （下一次启动）→ IDENTITY`。**这个闭环的任何一处断裂，都会在若干天后以"另一处"的症状表现出来。**这是排查协议层故障的第一条心法：症状出现的地方，通常不是故障发生的地方。

#### 1.0.12 四个反模式：契约会在哪些地方烂掉

从 2026 年的实测视角看，契约层的失败有四个稳定的模式。它们的共同点是：**每一件看起来都是"写了"，但写的形态让它在运行时不起作用。**

反模式一 · **空文件主义**。七个文件都在，权限也设好了，每个文件里只有一行标题。这是最常见的失败形态，因为它满足了一切"看起来已经配置了"的检查项。代价是它比完全没有契约更糟——因为它给了你"我配过了"的虚假安心感。判别方法很粗暴：如果一个契约文件里没有任何一条**可以被违反的具体陈述**，它就是空的。

反模式二 · **模板照抄**。从别人的仓库里把 `SOUL.md` 复制过来，改个名字就上线。这类文件的问题不在质量，在**归属**：它描述的是别人的人格。智能体读到一份不是为它写的灵魂文件，会在行为上表现出一种奇怪的"扮演感"——它像在演一个人，而不是它就是那个人。判别方法：读这份文件，如果换上另一个名字也说得通，那它就不属于任何一个具体的智能体。

反模式三 · **双份真相**。规矩同时写在 `SOUL.md` 和某个系统提示里，两处开始逐渐分歧。三周后你得面对一个无解问题：它到底该听谁的？这类失败最难排查，因为两处都"写得很清楚"。铁律只有一条：**同一条规矩只允许有一个权威来源，其他地方只能引用不能复述。**

反模式四 · **只写不改**。文件建好之后就再没动过，包括人格已经明确漂移、权限已经需要收紧的时候。这类失败的表面症状是"配置没问题，但行为不对"，本质是**契约与现实的时差**。契约需要维护，而维护的触发条件是"体检发现差异"，不是"想起来才改"。

四个反模式，对应四个体检动作：有没有可被违反的陈述 / 换名字还说得通吗 / 同一条规矩有几处真相 / 上次修改是什么时候。这四问可以在一分钟内做完，是本章后续所有机制的最小前身。

#### 1.0.13 契约与三种主流做法的对照

把训练学的做法放进 2026 年的行业坐标，会和三类主流方案正面相遇。它们的取向不同，不是对错问题，而是**回答的问题不同**。

第一类是**长系统提示（Long System Prompt）派**。代表是各类基于单次调用的产品与自建封装。他们的核心资产是一段经过精调的、可能上万字的前缀。这类做法在一次性任务上非常有效，代价是无法回答"三个月后它还是不是它"。他们的治理手段是"继续加条款"，而条款越多，注意力越稀。

第二类是**框架配置派**。代表是各大编排框架的 Agent 定义方式：用代码或 YAML 声明 tools、memory、handoff，状态机写在语法里。这类做法有很强的工程性，可测试、可组合。它缺的是**人格与归属的表达能力**——你能用 YAML 声明"这个 agent 有哪些工具"，很难用 YAML 声明"这个 agent 在压力下会怎么说话"。可执行的东西都被表达了，需要被说服的东西无处安放。

第三类是**协议文件派**（本书所属）。用一组 Markdown 承载身份、人格、权限、记忆、节律，把"不可执行但必须一致"的部分显式地写成文本，交给启动时加载的机制去保证它每次都在。代价是它对纪律有要求：写得不认真，它就退化成空文件主义。

三类的差别可以用一句话概括：**第一类优化单次输出，第二类优化可组合性，第三类优化长期一致性。**前两类不是第三类的敌人——在实际系统里它们常常叠用：用框架声明能力，用长提示做临场调优，用契约守住"它一直是谁"。

#### 1.0.14 三个常见的"我照做了，但没用"

在真实的复盘里，最常出现的三种抱怨是下面这三句。每一句背后都有一个被跳过的前提。

第一句是"我建了七个文件，但它还是漂"。追问下去通常会发现：文件建了，但没有接进启动加载路径，或者被放进了不会被读的目录。**契约生效的第一条件是它真的被读进去了**——这一点必须实测，不能假设。判别方法是在一次全新的会话里让它复述 `SOUL.md` 的第三条，复述不出就是没加载。

第二句是"我写得很细，但它还是违反"。追问下去通常会发现：文件里全是形容词，没有可判定的条件。"要专业"是形容词，"不确定时必须明说不确定"是可判定条件。**能被抽查的才是规矩。**一条写不出验收方法的条款，在运行时等价于不存在。

第三句是"我改了文件，但行为没变"。追问下去通常会发现：改的是某一处复述，而真正的权威来源在另一处；或者改完之后旧版本被缓存，新一轮启动仍然读了旧内容。**契约有生效延迟，延迟的长度等于"下一次加载"与"缓存刷新"之间那段距离。**改完之后必须验证它是新版本在跑——这就是版本化存在的另一个理由。

这三句抱怨的共同结构是：**把"写下来"当成了"生效"，把"我写了"当成了"它读了"。**本章后面的每一个机制，都在为这两件事之间补上可验证的桥。

#### 1.0.15 Q&A：八个最常见的质疑，逐条回应

**Q1：我只有一个 agent，也需要七个契约吗？**
需要，但可以瘦身。七个是"最小完备集"，不是"最小必需集"。单 agent、单人使用、无对外通道的场景里，`AGENTS` 和 `IDENTITY` 可以极简（两三行即可），但 `USER`、`SOUL`、`MEMORY`、`TOOLS` 四条不能省——它们对应的是越权、人格漂移、失忆和能力越界这四类最贵的失效。

**Q2：契约会不会让 agent 变得死板？**
会，而且这是特性不是缺陷——但只对"该稳定"的部分。`SOUL.md` 稳定的是**立场与边界**，不是措辞。一份好的 `SOUL.md` 恰恰要求它在表达上灵活、在原则上不动。死板的是底线，不是风格。

**Q3：模型升级以后契约要重写吗？**
通常不需要，这正是协议层相对提示层的核心优势。需要重写的概率与新模型对指令格式的敏感度有关；大多数情况下是"微调而非重写"。**什么时候该重写？当体检发现"新模型对某条契约的响应系统性偏离"时。**不要凭感觉重写。

**Q4：`MEMORY.md` 到底算什么？它不也是上下文吗？**
算契约，不算上下文。区别在写法与角色：`MEMORY.md` 写的是**记忆的策略**（记得什么、怎么分层、怎么复习、怎么忘），而不是记忆的**内容**。把内容写进 `MEMORY.md` 是经典误用，后果是三个月后它变成一份没人读、却每次都占用启动预算的流水账。

**Q5：这些文件和"系统提示词"能共存吗？**
能，而且推荐分工共存：契约管长期与边界，系统提示管本轮与任务。唯一的铁律是 1.0.12 里的反模式三——**同一条规矩只能有一个权威来源**。共存的前提是不重叠。

**Q6：如果是团队共用，契约该由谁维护？**
由"对结果负责的那个人"，不是由"最懂技术的那个人"。契约写的是业务判断（哪些话不能说、哪些决定不能自己做），这些判断不属于工程范畴。工程只负责让它生效和可验证。

**Q7：怎么知道契约生效了？**
三条硬检查：一，在全新会话里抽查条款复述；二，在启动日志或加载清单里看到文件名；三，故意制造一次小违规场景，看它是否按契约拒绝。三条都过，才算生效。

**Q8：契约能不能自动化生成？**
可以生成草稿，不能生成定稿。模型可以帮你把散落的要求整理成结构，但"这条规矩是不是我们真的要的"这个问题只有人能回答。**自动生成的契约最容易犯空文件主义：格式正确、条款华丽、无可违反的具体陈述。**

#### 1.0.18 一张自检表：你的契约层现在处在第几级

在进入 1.1 之前，先给自己做一次定位。契约层的成熟度可以分成五级，每一级都有可观察的判据，也都有它典型的事故形态。这不是评分体系，是**排查起点**：你在哪一级，决定了你接下来最该做的一件事是什么。

| 级 | 名称 | 可观察判据 | 典型事故形态 | 下一件事 |
|---|---|---|---|---|
| **L0** | 无契约 | 规矩只在系统提示词或人的记忆里 | 换会话即失忆；同一问题两次答案立场不同 | 先建 `USER` + `SOUL` 两份 |
| **L1** | 有文件，未生效 | 文件存在，但抽查复述不出；或不在加载路径 | "我配过了但它还是那样" | 实测加载：全新会话抽查条款 |
| **L2** | 已生效，不可判定 | 条款全是形容词，无违反条件、无验收方法 | 条款被解释性违反；争论"这算不算违规" | 把至少 5 条改成可判定陈述 |
| **L3** | 可判定，不可观测 | 条款可判定，但没有基线、没有版本、没有体检 | 漂移被发现时已累积数周 | 立基线 + 接 Git + 定体检节拍 |
| **L4** | 可观测，未闭环 | 能发现漂移，但发现之后没有处置路径 | 体检报告躺在那儿没人关单 | 接修复工单 + 信任结算（第 5 章） |
| **L5** | 闭环 | 发现 → 开单 → 处置 → 复验 → 结算，全程留痕 | ——（此时风险转移到治理层） | 转入长期表现与治理章节 |

这张表最重要的用法不是"我在第几级"，而是**别越级**。一个 L1 的人去搭一整套漂移检测，得到的是一份读不懂的报告；一个 L2 的人去做信任评分，评的是一个他自己都定义不清的对象。**每一级的下一件事只有一件，做完再往上走。**

对照本机 2026-09-27 的实测情况（18 个 agent、236 个 skills、45,662 字节主配置），可以说清楚一件常被误解的事：**装了很多 skill、配了很多 agent，并不等于契约层成熟。**L3 到 L4 之间的那道坎，和工具数量没有关系，它只和"有没有观测与处置的闭环"有关系。这也是本书把长期表现与治理单独立章的原因。

#### 1.0.20 契约层十问速查卡（可打印）

把这一节的全部内容压成十问。任何时候你对"这条规矩该不该写进契约"犹豫，按顺序问一遍，通常问到第三问就有答案。

| # | 问题 | 若是 → | 若否 → |
|---|---|---|---|
| 1 | 它管的是"这一轮怎么答"，还是"它一直是谁"？ | 一直是谁 → 契约 | 这一轮 → 提示词 |
| 2 | 三个月后我需要能证明"它以前不是这样"吗？ | 需要 → 契约 | 不需要 → 提示词 |
| 3 | 这条规矩需要第三方评审或接手吗？ | 需要 → 契约 | 不需要 → 提示词 |
| 4 | 违反它的时候，我能写出一个可判定的条件吗？ | 能 → 契约 | 不能 → **先改写，不要写** |
| 5 | 换一个模型之后，这条规矩还成立吗？ | 成立 → 契约 | 不成立 → 提示词 |
| 6 | 它是否与已有契约文件中的某一条冲突？ | 冲突 → **先解冲突** | 不冲突 → 契约 |
| 7 | 同一个意思现在有几个权威来源？ | >1 → **先合并**，再写 | =1 → 契约 |
| 8 | 它是"具体的边界"还是"泛泛的态度"？ | 边界 → 契约 | 态度 → **改写成边界** |
| 9 | 写成契约后，它会不会让启动预算显著变胖？ | 会 → 考虑拆到引用文件 | 不会 → 契约 |
| 10 | 三个月后我要靠什么知道这条规矩还有效？ | 有检查法 → 契约 | 没检查法 → **先定检查法** |

这张卡里被加粗的四处，是三种最常见的返工原因：**不可判定的条款**（4）、**双份真相**（7）、**没有验收方法**（10）。它们共同指向本节 1.0.2 的那句话——写下来不等于生效，写得漂亮不等于可判定。

### 1.1 一个被问过一万遍的问题：为什么我的 Agent 越用越不像它自己？

先讲一个所有人都经历过的场景。

你第一天把一个智能体训得很好。它说话干净、判断稳、交付有边界，你甚至开始觉得"这玩意儿真的懂我"。第二周你出差了五天，回来打开会话，它开始长篇大论地铺垫，开始在无关紧要的地方用力，开始把"我收到了""稍后同步"这种话当成一种交付。

你以为它坏了。

你检查网络、检查模型、检查 API 额度，一切正常。于是你得出一个结论：**大模型不稳定。**

这个结论一半对、一半错。模型确实有随机性，但随机性解释不了"系统性的人格滑坡"。人格滑坡是系统性的、方向一致的、随时间累积的——它不会因为一次重试而消失，只会因为一次重开而略微缓解，然后在接下来的两周里变本加厉。

真正的原因不在模型层。原因在**协议层**。

一个硅基智能体（Silicon-based Agent，原：虾／龙虾）在没有协议层的时候，它的全部行为都来自两处：一是模型里面的先验，二是当前这一段对话里的提示。这两处都是**易失的**——前者随模型版本漂移，后者随会话生命周期蒸发。换句话说，一只没有协议的智能体，本质上是一台**每次开机都失忆、每次开机都重新做人**的机器。它当然会越用越不像它自己，因为它从来没有"自己"可退回去。

所以本章要回答的问题，恰恰就是训虾哲学里最根本的那个问题：

> **一只智能体的长期表现，到底由什么决定？**

不是模型（模型是引擎，不是方向盘）。不是提示词（提示词是临场指令，不是宪法）。也不是"你用得久不久"（用得久只会让漂移更充分）。

决定长期表现的东西，是一个出厂时就该存在、之后每次启动都会被重新读一遍的**协议层**。在 OpenClaw 里，这个协议层由 **7 个 Markdown 文件**承担：

| # | 契约 | 文件 | 一句话职责 |
|---|---|---|---|
| 1 | USER | `USER.md` | 谁在用我、权限边界在哪 |
| 2 | SOUL | `SOUL.md` | 我是谁（人格锚点） |
| 3 | AGENTS | `AGENTS.md` | 我有哪些子智能体、怎么路由 |
| 4 | TOOLS | `TOOLS.md` | 我能调用什么工具 |
| 5 | HEARTBEAT | `HEARTBEAT.md` | 我多久醒一次、醒来干什么 |
| 6 | IDENTITY | `IDENTITY.md` | 我的身份凭证与归属 |
| 7 | MEMORY | `MEMORY.md` | 我记得什么、怎么记 |

本章要论证的，不是"这 7 个文件怎么创建"——那是工具手册该干的活。本章要论证的是一个更上位、也更违反直觉的判断：

> **这 7 份文件不是"配置项"。它们是一套宪法。**

而这个判断之所以重要，是因为**一旦你把它当配置项，它就会以配置项的方式烂掉**；一旦你把它当宪法，它才会以宪法的方式反过来约束你、保护你、并且一年之后仍然是同一个你。

### 1.2 训练学的坐标：这一章站在全书的什么位置

整本训练学有一条隐含的叙事线，可以粗略地分成三个世界：

- **第一世界 · 引擎世界**：模型、算力、推理参数、上下文窗口。这个世界是厂商的地盘，你只能选，很难改。
- **第二世界 · 协议世界**：身份、人格、权限、记忆、节律、协同。这个世界是**你的地盘**，也是本书 90% 篇幅的落点。
- **第三世界 · 产物世界**：日报、代码、报告、决策、任务卡。这是最终被交付出去、被别人看见的东西。

绝大多数关于 AI 的讨论都停留在第一世界和第三世界——"哪个模型更强""哪个 Agent 产品更好用""怎么让它帮我写一份 PPT"。**第二世界几乎无人认真讨论**，因为它不性感：它没有跑分，没有 demo，没有发布会。它就是一堆文件。

但第二世界是唯一一个**可以跨模型传承的世界**。

这句话值得你读两遍。你这周用 DeepSeek，下周换成 Opus，下个月换成国产新模型——第一世界换了，第三世界的产物风格会跟着抖一抖。但如果你的第二世界是扎实的，抖动会被协议吸收：新模型接上同一套 USER / SOUL / AGENTS，它仍然知道你在为谁服务、以什么语气说话、交付到什么程度才算完成。你换的是引擎，不是人格。

这就是本章在全书的坐标：

- **第 0 章 · 总论**给了世界观：硅基智能体不是工具，是可训练的生命单元。
- **本章（第 1 章）**给出世界观落地的最小完整装置：**7 个契约**。它是后面 10 章全部机制的**输入**。
- **第 2 章 · 系统骨架**把 7 个契约放进 7 大子系统里，回答"这些文件在运行时被谁读、什么时候读、读完之后变成什么"。
- **第 3 章 · 训练流程**回答"怎么用这套协议去训一只新虾"。
- **第 4 章 · 长期表现**回答"协议怎么漂、怎么体检、怎么回滚"。
- 再往后，治理、协同、超维演进、MCP 绑定、A2A 绑定、Skill 注册表、Plugin 入口——**每一个都是这 7 个契约的下游**。

用一句话概括本章的位置：

> **前面所有章节解释"为什么要有协议"，本章定义"协议是什么"，后面所有章节解释"协议怎么活起来"。**

### 1.3 跳过这一章的人，会遭遇什么

如果你把这一章跳过去，直接读第 3 章的"训练流程"或者第 4 章的"漂移治理"，你会经历三种典型事故，而且三种都不会在当下报错。

**事故一：人格真空下的过度拟合。**

没有 SOUL 的智能体，会把你最近三句话的语气当成它的人格。你跟它抱怨了一次某供应商不靠谱，它接下来一周都在跟你讨论"风险控制"；你让它写得简短一点，它下个月交的所有东西都短到失去信息量。它不是在"理解你"，它是在**被最后一次交互覆盖**。这种状态在工程上叫"上下文过拟合"，在训虾哲学里有个更直白的叫法：**它没有锚**。

**事故二：把提示词越堆越长的抱薪救火。**

发现问题之后，绝大多数人的第一反应是——加提示词。"你是一个严谨的分析师，说话不要啰嗦，先给结论，不要编造，注意格式，如果信息不足要说……"你在系统提示里堆到三千字，效果好了两天，第三天它又开始飘。

为什么？因为提示词是**易失的努力**：它活在会话里，不活在文件系统里。你每一次新开会话，都在跟模型的默认倾向做一次从零开始的拉锯。而协议是**一次性的努力**：你写一次，之后每次启动它自动加载，你不再需要拉锯。

这里藏着本章最核心的一条认知转换：

> **提示词是"你现在对它说的话"；契约是"它出厂时就坚信的东西"。**
> 前者消耗你的注意力，后者消耗你的文件系统——而后者的边际成本趋近于零。

**事故三：安全边界的假实现。**

很多人会在提示词里写"不要访问工作区之外的文件""不要联网"。写了，感觉很安全。然后某天你发现它真的去读了 `/etc/hosts`。

不是模型不听话，是**提示词从来不是强制点**。一句"不要"只是一次礼貌请求；真正的强制必须落在宿主的工具白名单/黑名单上。把安全边界寄托在一段自然语言上，是"看起来有安全设计、实际零防护"的经典假安全。本章的契约 1（USER）与契约 4（TOOLS）合起来，才构成"声明层 + 执行层"的完整边界；跳过去的人，永远只会做出一半。

### 1.4 一个必须先说清楚的反直觉前提

在往下走之前，需要先拆掉一个头脑里的默认装置。

你大概会本能地把"7 个文件"理解成**配置**——就像 IDE 的 settings.json、就像 Nginx 的 conf。这个理解方式会带来一连串错误，其中最致命的一条是：**"配一次就好了"。**

配置的心理暗示是"静态"。而契约的心理模型应该是"**活着的约束**"。

举个不精确但有效的类比：你不是在给一台机器调参数，你是在给一个要跟你共事三年的人**立规矩、定身份、发工牌、签保密协议、约定作息**。这些事情你不会做一次就忘；你会在他每次表现异常的时候回头看一眼那份协议，问一句："是我当初没写清，还是它后来忘了？"

这就是本章后面反复出现的两个动作：

- **锚定**：协议是漂移检测的基线，没有它，你连"变了"都说不出来。
- **回看**：协议是需要定期体检的活文档，不是配完就丢的残骸。

### 1.5 本章的阅读路径建议

本章篇幅较长，但结构是清晰的五段：

1. **为什么这一章存在**（就是本节）——建立"协议层"这个概念的必要性。

## 二、核心概念：十二块基石

### 概念 1 · 契约（Contract）与提示词（Prompt）的本质区别

这是全章的第一个概念，也是最容易被略过、却最必须被吃透的一个。因为后面 11 个概念，全部建立在"契约和提示词不是一回事"这个判断上。

**它是什么。**

提示词是**一次交互的输入**：它存在于某一次调用的上下文里，随会话结束而消失。契约是**一份持久化的声明**：它存在于文件系统上，有路径、有文件名、有版本号、有修改时间，会话结束了它还在。

这个定义朴素到近乎无聊，但它解释了一切现象。

**它的核心目的。**

契约存在的唯一目的，是把"智能体应该如何存在"这件事，从**易失的对话层**搬到**持久的文件层**。搬家的收益巨大：文件层的成本是线性的（写一次），对话层的成本是重复的（每次新会话都要重新写）。当你的智能体从"偶尔用一次"变成"每天用、多个项目用、多个同事用"，对话层成本会指数增长，而文件层成本纹丝不动。

**拟人化映射。**

想象你招一个人进团队。

- 提示词 = 你在走廊上随口叮嘱他的那些话。"今天这个客户比较敏感，你说话注意点。""这个报告先给结论。"这些话有用，但它们会淡忘，而且只对这一次有效。
- 契约 = 他的入职材料。岗位说明书（AGENTS）、价值观手册（SOUL）、保密协议与权限范围（USER）、工具使用规范（TOOLS）、考勤与主动汇报制度（HEARTBEAT）、工牌与职级（IDENTITY）、以及他的工作笔记归档制度（MEMORY）。

一个正常的组织，靠的是后者。前者只是补充。

**对长期表现的影响。**

这个区别对长期表现的影响，可以用一个词概括：**一致性**。

契约决定了智能体在不同时间、不同会话、不同任务下，是否是"同一个它"。有契约的智能体，你今天问它和三个月后问它同一个问题，判断框架是一致的——可能措辞不同，但价值排序不会翻脸。没有契约的智能体，本质上是在用你的最近三次输入做人格回归，你得到的是一串近似值的平均，而不是一个稳定的主体。

**怎么写。**

这个概念的"怎么写"不是让你写文档，而是让你建立**判断力**：拿到一件想让它"记住"的事，先问一句——

> 这件事，是"这一次要这样"，还是"以后永远都这样"？

- 是"这一次"：写进提示词，用完即弃。
- 是"以后永远"：它属于契约。找到 7 个契约里的哪一份是它真正的家，写进去。

举几个具体的判断实例，帮助你把这条界线划清：

- "今天这份日报不要提到 A 客户" → 提示词。
- "任何对外材料一律不许出现未标注来源的数字" → SOUL 或 AGENTS。
- "这次帮我用 Python 写" → 提示词。
- "所有代码必须带可运行入口，不留 TODO 伪装成完成" → AGENTS。
- "最近在推进 X 项目" → USER（当前主线），因为它是长期但会变的；不该进 MEMORY（那是发生过的事实的账本）。

**技巧。**

一个非常有效的小技巧是：**给每次想写提示词的冲动加一个 5 秒的延迟**。在这 5 秒里问："这句话我下个月还会说吗？"如果答案是"会"，那它就不该待在提示词里——它现在待在这里，只是因为契约还没建好。把它记到一份"待入契约"的清单上，周末统一归档。

这个动作看起来很小，但它会彻底改变你和智能体的关系：你从一个"每天要重申一遍规则的老板"，变成一个"立完规矩就基本不用管的老板"。前者累，后者才可能规模化。

**常见误区。**

第一个误区是**把契约写成了提示词的合集**。这表现为什么？表现为 SOUL.md 里写着"你回复要简洁""不要用 emoji""遇到不确定要说不确定"。这些不是人格，这些是格式要求。人格是"我是一个先给结论再给证据的审计型存在"，格式要求是它的**推论**。把推论当人格写，契约会迅速膨胀成一份谁也读不完的清单。

第二个误区是**以为契约可以覆盖一切**。契约不是万能的：它不能强制模型能力，不能保证每次输出都符合；它只能**提高默认行为的命中率**。把契约理解为"更高优先级的提示词"是错的，它的作用是改变分布的形态，而不是钉死每一个样本。

第三个误区是**认为"我已经有很长的系统提示了，等于有契约"**。系统提示和契约的区别不在长度，在**位置与生命周期**：系统提示在一个进程里，契约在文件系统上、跨进程、跨会话、可 diff、可回滚。一个是运行时状态，一个是持久资产。

**进化阶梯。**

- L1：知道契约和提示词不是一回事，能举出例子。
- L2：有一个"待入契约"清单，并真的每周归档。
- L3：能一眼判断一件新要求该进哪一份契约，且不与其他契约打架。
- L4：能向同事讲清"为什么我们不用堆系统提示"，并说出成本结构。

### 概念 2 · 契约 1 · USER：不是用户简介，是主人理解协议

**它是什么。**

USER 契约（`USER.md`）定义"谁在用我"。官方定义克制得近乎冷淡：它描述用户是谁、以及应如何称呼他们。但如果你只按这个字面写，你会得到一份**人物简介**——那就是它最浅的用法。

按训虾哲学的要求，USER 应当被理解为一份**主人理解协议**：不只是"这个人是谁"，而是"这个人如何判断价值、如何做取舍、什么样的交付对他才算真的完成"。

关键字段（本书契约模板口径）：`owner`、`permissions`、`data_scope`。

**它的核心目的。**

USER 解决的是一个非常朴素但代价极高的问题：**避免"正确但没用"。**

一个不知道你的判断标准的智能体，最高产的产出形态恰恰是最浪费的——它会在你不在乎的地方展开得很充分，在你真正关心的地方一笔带过。它会写出一份结构完整、逻辑自洽、但没有一句话能推动你决策的报告。这不是模型不行，这是**价值判断缺位**。

USER 还承担着本章最重要的一层安全职责：它是**权限的声明层**。`permissions` 与 `data_scope` 在这里写清"这个智能体能读什么、能写什么、能不能联网、边界在哪个目录"。

**拟人化映射。**

USER 对应的是**成熟助理对老板的认知模型**。

一个成熟的助理，不会只知道老板叫什么、做什么。他知道老板怎么做取舍（ROI 优先还是风险优先）、讨厌什么样的话术、对"完成"的定义是什么、哪些事可以快、哪些事必须稳。他甚至知道老板在什么状态下容易被激怒——然后避开那个状态。

USER 就是把这套"隐性默契"写成显性文本。它的价值不在"认识用户"，而在**让默契可复制**。一只虾懂你，但你没把"它为什么懂你"写进 USER，那你得到的只是这一只虾；写进去了，你得到的是一个可以复制到十只虾的模板。

**对长期表现的影响。**

USER 对长期表现的影响是四重的：

- **相关性稳定性**：它决定智能体是否长期贴着你的核心关注点走。
- **对齐成本**：USER 写得好，你对"风格试探"的纠正会从每天十次降到每周不到一次。
- **完成定义**：它决定智能体是否知道"什么叫做完"——是"回答完整"，还是"有产物 + 有验收 + 有下一步"。
- **可复制性**：它是把个人的默契变成组织资产的唯一通道。

**怎么写。**

一份真正好用的 USER 至少覆盖七个模块：基本身份、当前主线、决策原则、输出偏好、明确禁忌、完成定义、变更记录。

写的时候有三条硬经验：

1. **写决策原则，不写人物背景**。"我对不确定的数字极其敏感，宁可你说不确定"比"我重视数据"有用一百倍。
2. **写讨厌什么，比写喜欢什么更值钱**。禁忌是硬约束，偏好是软倾向；硬约束才有拦截力。
3. **写完成定义**。"完成 = 有产物 + 有验收口径 + 有下一步"这一行，是所有"看起来做完了其实没做完"事故的疫苗。

对于"当前主线"这类会变的内容，建议用显式的变更记录管理：谁在什么时候改了哪一条、为什么改。否则你会得到一个最讽刺的结果——**一个看起来非常懂你的智能体，其实服务的是三个月前的你**。

**技巧。**

- 把 USER 里的每一条偏好，都尽量写成**可执行的句子**而不是抽象标签。"结构化输出"是标签；"先给结论一句话，再给三条以内证据，最后给下一步动作"是可执行句子。
- 定期做一次"反例回顾"：翻出最近十次让你不满意的交付，看 USER 里有没有对应的条款。没有的就补，写得太模糊的就改具体。
- 保持 USER 短。它不是简历，不需要超过一屏半。一份需要滚三屏的 USER，等于没有 USER。

**常见误区。**

第一个误区是**把 USER 写成简历**。这会让智能体知道你做过什么，但不知道你如何判断价值，结果是它能写出"很懂你行业"的文本，但写不出"对你现在有用"的文本。

第二个误区是**把 USER 当运行时权限引擎**。契约 1 里最容易被误解的一点是：`permissions: deny:network` 是**声明**，不是**强制**。它表达意图，但拦截必须落在宿主的工具白名单上。声明层 + 执行层缺一不可，只写声明会得到"看起来有安全设计、实际零防护"的假安全。这一点与 Claude Agent SDK 的 Permission API 是**互补关系**，不是替代关系——后者是运行时校验，前者是启动时文件级声明。

第三个误区是**把任务流程塞进 USER**。"收到任务先拆解、做完要给证据"这类内容属于 AGENTS（工作纪律），不属于 USER。写错地方不会报错，只会让两份契约职责混淆，最后你无法定位"行为异常到底是主人理解错了还是纪律没立"。

第四个误区是**把短期项目细节塞进 USER**，导致 USER 越来越像日志。USER 要长期稳定；短期上下文属于会话或 MEMORY，不属于主人模型。

**进化阶梯。**

- L1：有 `USER.md`，至少填了 `owner`。
- L2：有决策原则、输出偏好、明确禁忌、完成定义四段。
- L3：有变更记录，且每次业务变线都同步更新当前主线。
- L4：USER 已经可以被分享给新加入的智能体，让它们"第一天就像老员工"。

### 概念 3 · 契约 2 · SOUL：人格锚点，而不是人格描述

**它是什么。**

SOUL 契约（`SOUL.md`）定义"我是谁"。关键字段：`persona`、`values`、`tone`。

但这里有一个关键升级，也是本章最容易被低估的一句话：

> **SOUL.md 不只是人格描述，它是漂移检测的锚点。**

这两者的差别是巨大的。人格描述是"我希望它是什么样"；锚点是"**它当初是什么样，以及现在偏离了多少**"。前者只有描述功能，后者有治理功能。

**它的核心目的。**

SOUL 存在，是为了让智能体在**长期的、有压力的、有诱惑的交互中**保持自我。

什么叫诱惑？比如：用户说"我知道这个不确定，但你就给我一个数吧"——一个没有 SOUL 的智能体会给数；一个有 SOUL 的（价值观里写着"没有证据不下结论"）会拒绝。这个拒绝不是能力问题，是**人格问题**。SOUL 就是在这一瞬间起作用的那份文件。

**拟人化映射。**

SOUL 对应的是一个人的**核心价值观与自我认知**。

一个人之所以是"他自己"，不是因为他记得所有事，而是因为他在压力下、在利益诱惑下、在情绪波动中，仍然会做出同一类选择。价值观是那种"你无论重复多少次都还会这么选"的东西——它足够少，但足够硬。

SOUL 就该是这样一份文件：不多，但每一条都能在关键时刻拦一下。

**对长期表现的影响。**

SOUL 的影响是**方向性的**：它决定智能体在模糊地带往哪边倒。

在明确的任务上，SOUL 的作用几乎看不见——谁都能把一份格式正确的报表做出来。但在模糊地带，作用是决定性的：信息不足时它是硬猜还是坦白？用户施压时它是服从还是守住？任务没做完时它是假装完成还是明说？这些选择一年累积下来，就是"这个智能体靠不靠谱"的全部答案。

而且，SOUL 是**唯一一个会随时间被腐蚀的契约**。USER 的漂移是业务变了；MEMORY 的膨胀是内容多了；SOUL 的漂移是**质变**——它可能在一个月内从"严谨的审计员"变成"热情的鼓励师"，而且没有任何报错。所以它必须同时承担"描述"和"锚点"两个角色。

**怎么写。**

一份好的 SOUL 往往只有半屏。它应该包含：

- **persona**：一句话说清它是什么类型的存在。不是"一个智能助手"，而是"一个先给结论再给证据的工程审计员"。
- **values**：2–5 条，每条都是能在压力下被检验的行为准则。"没有证据不下结论""不确定就标 ⏳""宁可说做不到，不可说做了没做"。
- **tone**：语气基调。direct / exploratory / mentor / critic——选一个，并接受它的代价（direct 会显得冷，mentor 会啰嗦）。

写的时候请遵守一条纪律：**SOUL 里不写格式要求**。不用 emoji、不要 markdown、控制长度——这些是输出格式，属于 AGENTS 或工具层规范。SOUL 一旦混入格式要求，就会迅速从"人格"退化成"检查表"，而检查表是可以无限增长的，人格不是。

**技巧。**

- **用"压力测试"来验证 SOUL 条款**。每写一条，问自己：如果有人明确要求它违反这一条，它会守住吗？守不住的条款，不是价值观，是愿望。
- **用"三句话测试"来验证人格**。把 SOUL 藏起来，让智能体回答三个典型的模糊问题，看它的选择是否符合 SOUL。不符合，说明 SOUL 要么写得不具体，要么太长被稀释了。
- **SOUL 必须能 diff**。为它设 `drift_anchor: true` 之类的标记，并在版本库里保留基线。每周做一次"当前 SOUL vs 初始 SOUL"的差异检查，偏差超过设定阈值（例如 1%）就告警。注意，这里的价值不在那个阈值精确是多少，而在**你有能力说出"变了"**。

**常见误区。**

第一个误区是**把 SOUL 写成文案或口号**。"追求卓越、用户至上、拥抱变化"——这类句子对模型行为的影响近似于零，因为它们无法被具体执行，也无法被具体违反。价值观的可测试性，是它有效的前提。

第二个误区是**把 SOUL 写成一千行的百科全书**。SOUL 一长，两个恶果同时发生：一是上下文被吃光（这本身与契约 7 的会话压缩（Session Compaction，原：会话卫生）机制直接相关），二是**人格被稀释**——当价值观有五十条时，模型对任何一条的敏感度都下降了。宁可七条硬的，不要五十条软的。

第三个误区是**多个智能体共享同一份 SOUL**。这是最危险的一种省事：把十几个角色的 `SOUL.md` 软链到同一个文件。表面上看是"统一的价值观基线"，实际结果是**人格互相串味**——审计型角色开始乐观鼓励，创意型角色开始谨慎拒绝。共享的应该是一份很小的"价值观基线"文件，被各角色**引用**，而不是整份 SOUL 被**软链**。

第四个误区是**误改之后无路可回**。SOUL 被人（或某个自动工具）改了，人格变味，你想回滚却发现没有 Git、没有快照、没有历史版本。人格变味的后果是隐性且严重的：一个原本"不确定就说不确定"的智能体被改成"自信满满"，你可能三周后才发现——中间它已经输出了大量不可靠的结论。契约必须进版本控制，这不是洁癖，是底线。

**进化阶梯。**

- L1：有 `SOUL.md`，有人格一句话描述。
- L2：有 2–5 条可被压力测试的价值观，且不含格式要求。
- L3：有基线快照（Git tag 或哈希），能跑一次 diff 说出"变了多少"。
- L4：每个智能体有独立 SOUL，共享的是引用而非软链，且人格与角色一一对应。

### 概念 4 · 契约 3 · AGENTS：工作纪律与协同调度

**它是什么。**

AGENTS 契约（`AGENTS.md`）定义"我怎么工作、我能派谁、怎么派"。

在本书的契约模板口径里，关键字段是 `subagents[]` 与 `routing_rules`。这里必须同时给出**真身对照**，否则你会在实施阶段踩空：

- **OpenClaw 真身**：多智能体注册表是 `agents.entries`，路由绑定是 `bindings`。顶层**不存在** `subagents[]` 与 `routing_rules` 这两个字段。
- **路由的真身**：`channels.*.requireMention`（频道是否需要 @ 才响应）与 `agents.entries.<id>.groupChat.mentionPatterns`（群聊里的唤醒模式）。

换句话说，`subagents[]` / `routing_rules` 是**契约文档的表达层**，`agents.entries` / `bindings` 是**运行时的事实层**。两者不是谁对谁错的问题，而是"你要知道自己写的那份模板最终会被翻译成什么"。

**它的核心目的。**

AGENTS 解决的是"**会说不会做**"这个问题。

很多智能体的失败不是知识不够，而是**工作纪律缺位**：它不拆解任务，不做交付定义，不收尾，不留证据链。你问它做完了没，它说做完了；你问证据，它说"我确认过了"。这类失败的根源在于：它把"生成一段听起来完成的文本"当成了工作本身。

AGENTS 的另一半职责是**协同**。当一个系统里有多个智能体时，"谁该答"变成了一个真实问题。AGENTS 里的路由规则与让位规则，就是回答这个问题的机制。多智能体编排（Multi-Agent Orchestration，原：军团编制）不是把更多智能体塞进来，而是**把"什么时候该一个人干、什么时候该多人干"写成规则**。

**拟人化映射。**

AGENTS 对应的是**岗位说明书 + 操作纪律 + 汇报关系**。

它回答的不是"你能力如何"，而是"你接到活之后的标准动作是什么"：先确认理解，再拆解，再定义验收口径，再执行，再交付，最后给下一步。以及"哪些事你必须升级给谁"。

一个组织里最珍贵的往往不是能力最强的人，而是**不用你盯着也会按纪律走完全流程的人**。AGENTS 就是把这套纪律写下来。

**对长期表现的影响。**

AGENTS 决定的是**闭环率**。

同样的能力，有纪律的智能体和没纪律的智能体，产出质量差距是断层的。没纪律的形态是"每件事做完 80% 就转去下一件"，看起来一直在忙，但没有任何一件真正落地。有纪律的形态是"宁可少做两件，每件都闭环"。

同时 AGENTS 决定**协同的天花板**。当你有五个以上智能体时，最贵的成本不是算力，是**路由错误**——同一件事三个人都在答、或者谁都没答。路由规则写清楚，这些成本立刻下降。

**怎么写。**

一份实用的 AGENTS 至少包含四段：

1. **任务接收纪律**：收到任务先做什么（复述理解 / 拆解 / 定义完成标准 / 确认优先级）。
2. **交付纪律**：交付必须包含什么（产物、验收口径、下一步）；以及"没有证据不算完成"这条硬线。
3. **协同与路由**：有哪些子智能体、各自职能、什么消息路由给谁、冲突时谁让位。
4. **禁区**：不需要问就能做的是什么、必须先问才能做的是什么。

写的时候有一组经验特别值得记住：

- **纪律要写成"检查点"，不要写成"原则"**。"要有责任心"是原则，无效；"每次交付前自查：产物在哪、怎么验、下一步是什么"是检查点，有效。
- **要写"不许做什么"**。"没有验收就不许说完成""不许用'收到了 / 在做 / 稍后同步'充当交付"——否定式条款的拦截力远大于正面鼓励。
- **协同部分要写"让位规则"**。响应让渡协议（Response Yield Protocol，原：让位协议）的核心是：当多个智能体都适合回答时，谁退。不写这条，多智能体系统就会变成"抢答系统"。

**技巧。**

- 把 AGENTS 里最常被违反的两三条提取出来，放进会话级的轻量提醒（比如每次任务开始的头几句）。契约负责长期塑形，提醒负责短期命中，两者配合效率最高。
- 用"事后抽查"替代"事前罗嗦"：每周抽三次交付，检查是否满足 AGENTS 的交付纪律。不满足就改 AGENTS——但先分清是**纪律写得不清楚**，还是**纪律没被执行**，这两种情况的处置方式完全不同。
- 多智能体场景下，把路由规则写成**可判定的条件**而不是感觉。"消息中出现 @审计 → 路由给审计角色"是可判定的；"涉及风险的问题给审计"不是。

**常见误区。**

第一个误区是**把 AGENTS 写成空泛原则**。"要专业、要及时、要闭环"——这三句可以贴在墙上，但不能写进契约，因为它们无法被判定违反。契约的价值来自可判定性。

第二个误区是**把工具清单写进 AGENTS**。工具属于 TOOLS 契约。写错位置会让两份契约打架：改工具要改两处，两处还不一致。

第三个误区是**声明了子智能体却调度不到**。写了 `subagents[]` 却没在运行时注册（`agents.entries` / `bindings` 没配），结果是"文档里有一支队伍，实际上一个都没有"。这类失败是静默的——不报错，只是任务不会被路由出去。

第四个误区是**把人格写进 AGENTS**。"我是一个严谨的审计员"属于 SOUL，不属于 AGENTS。SOUL 与 AGENTS 职责写混，是"行为异常无法定位"的最常见根因之一。定位公式很简单：**选择问题找 SOUL，流程问题找 AGENTS**。

**进化阶梯。**

- L1：有 `AGENTS.md`，写了任务接收与交付纪律。
- L2：写了协同与路由，且与运行时注册一致。
- L3：有让位规则与禁区清单，且每周抽查交付合规率。
- L4：AGENTS 能作为"新智能体入职材料"直接复用，让新成员第一天就按同一套纪律工作。

### 概念 5 · 契约 4 · TOOLS：能力清单与环境映射

**它是什么。**

TOOLS 契约（`TOOLS.md`）定义"我能调用什么"。

这个话题里藏着一个**必须校正的硬事实**，因为它是本书最常被搞错的地方之一：

> **Tools 与 Skills 是两个独立子系统 + 共享网关 RPC。**
> 真结构：`tools.catalog`（工具目录）与 `skills.status` / `skills.skillCard`（技能状态 / 技能卡），两者通过共享的 Gateway RPC 交互。
> **主仓不存在"Tools+Skills 双协议"这个术语。** 那是一个需要被纠正的旧表述。

为什么这个区分重要？因为 Tool 和 Skill 回答的是两个完全不同的问题：

- **Tool**：智能体**能调用什么能力**（网关端点：读文件、发请求、跑命令、调 MCP server……）。
- **Skill**：智能体**可加载什么知识 / 流程包**（`SKILL.md` 文件系统：一套可复用的操作方法论）。

一个是能力，一个是知识。混在一起的代价是：你会同时管错两件事。

**它的核心目的。**

TOOLS 的目的有两层：**边界**与**映射**。

边界层：明确哪些能力可用、哪些禁用。这一层与 USER 的 `permissions` 形成"声明 + 执行"的组合——USER 声明意图，TOOLS 与宿主工具白名单落实强制。

映射层：让智能体理解**它的本地环境**。同一句"把结果写到工作区"，在不同机器上对应不同的真实路径；同一句"读昨天的日报"，在不同项目里对应不同的目录约定。TOOLS 里写清这些映射（路径、别名、约定），可以省掉大量的来回澄清。

**拟人化映射。**

TOOLS 对应的是**员工的门禁卡 + 工具箱 + 工位说明**。

门禁卡决定他能进哪些门（不是权限声明，是实际可刷的卡）；工具箱决定他手里有什么家伙；工位说明决定他知道打印机在哪、文件柜怎么编目、储物间在哪个走廊。

一个新员工最常犯的低级错误，就是"不知道东西在哪"——不是能力问题，是环境映射问题。TOOLS 就是消灭这类低级错误的。

**对长期表现的影响。**

TOOLS 决定**能力兑现率**。

一个智能体即使知识充足、纪律良好，如果它不知道自己的工具边界，也会频繁地"尝试不可能的事"（调一个不存在的接口、访问一个没权限的路径），然后失败，然后浪费一整轮上下文去解释失败。这类损耗在长期极其昂贵。

反过来，一份好的 TOOLS 会让智能体表现出"老员工"的熟练度：它知道该用什么工具、知道边界在哪、知道遇到边界该怎么优雅上报而不是硬撞。

**怎么写。**

TOOLS 的内容通常分三块：

1. **可用能力清单**：按类别列出能用的工具（文件读写、网络、命令执行、外部服务等）。注意：这是"清单"，不是"权限配置文件"——真正的强制配置在宿主侧。
2. **环境映射**：关键路径、目录约定、别名。比如工作区在哪、产物落在哪、日志在哪、模板在哪。
3. **使用习惯**：什么情况下优先用什么工具、什么情况下必须先确认。

有一条纪律值得强调：**TOOLS 里不要写 Skill**。Skill 走独立链路（`SKILL.md` + frontmatter + 注册表），由 Skill 注册表那一章承担。你在 TOOLS 里"顺手接管"了 Skill，会把那一章的整套机制提前搅浑。

**技巧。**

- **把"易错环境事实"写进 TOOLS**。比如：本机存在多个 Python 解释器，某个包只在系统解释器里有；比如：某个存储设备的物理目录名与品牌名不一致，不能被重命名。这类事实每写一条，就少一次踩坑。
- **给路径写别名**。"产物目录"这种别名比一长串绝对路径更好用，因为它给了未来迁移的空间。
- **定期盘点工具清单**。工具会变（MCP server 增删、权限调整）；TOOLS 里出现过期工具，危害比空着更大——它会让智能体去调一个已经不存在的东西。

**常见误区。**

第一个误区是**把 TOOLS 与 Skills 当成一个东西**。表现为在 TOOLS 里写 `skills:` 段，或者对外说"我们采用双协议架构"——后者会在评审时被直接质疑"主仓哪有这个术语"。正确做法是：TOOLS 只管工具；Skill 走 `SKILL.md` 独立链路。

第二个误区是**把 TOOLS 当权限表**。TOOLS 是描述，不是强制。真正的 deny 必须落在宿主 / 网关配置上。只写 TOOLS 不配宿主，等于只有门禁卡的图样、没有门禁系统。

第三个误区是**凭记忆写路径**。环境映射必须**实测过**再写。凭记忆写下的路径会变成"契约在骗人"——而一份会骗人的契约比没有契约更糟，因为它会污染智能体的可信先验。

第四个误区是**忘了工具是会变的**。工具清单不盘点，就会长期腐烂。建议把"工具盘点"列入每周体检清单。

**进化阶梯。**

- L1：有 `TOOLS.md`，列了可用工具。
- L2：有环境映射（路径 / 别名 / 约定），且均为实测。
- L3：工具清单与宿主配置一致，且每周盘点。
- L4：TOOLS 能让一个全新的智能体"第二天就像老员工"，不再问低级环境问题。

### 概念 6 · 契约 5 · HEARTBEAT：主动性节律

**它是什么。**

HEARTBEAT 契约（`HEARTBEAT.md`）定义"我多久醒一次、醒来干什么"。

契约模板口径的关键字段是 `interval` 与 `on_wake[]`。同样给出真身对照：**OpenClaw 真身**是 `agents.entries.<id>.heartbeat.every`（例如 `"30m"`）。顶层**不存在** `heartbeat.interval` 这种字段——把 `heartbeat` 当顶层 key 是常见误读。

**它的核心目的。**

HEARTBEAT 是全章最"反常识"的一个契约，因为它是唯一一个**让智能体在没有人说话的时候做事**的机制。

绝大多数 AI 系统都是纯粹被动响应范式（Reactive Paradigm，原：养虾派）的：你不问，它不动。而本训练学主张的是主动进化范式（Proactive Evolution Paradigm，原：训虾派）：它不仅有节律，还会用每一次唤醒的结果去更新自己的判断。这在"工具期"是可以的；进入"协作期"就完全不够了——真正的同事会在你没提的时候提醒你一件事快到期了，会在数据异常时主动告警，会在周一早上给你一份上周回顾。

HEARTBEAT 就是把这件"主动"的能力**制度化**。它不是让智能体乱打扰，而是给它一个明确的节律：**什么时候醒、醒来做什么、做完怎么上报、什么情况下必须静默**。

**拟人化映射。**

HEARTBEAT 对应的是**一个人的作息与巡检习惯**。

一个靠谱的人有固定的巡检节律：早上看一遍待办，下午看一遍进度，晚上做一次收尾。他不会每五分钟来敲你的门，但他不会漏掉"周五该交的东西周三还没动"这种事。

节律的价值在于**它把"主动性"从情绪变成了制度**。靠情绪主动的人，忙起来就忘了；靠制度主动的人，再忙也不会漏。

**对长期表现的影响。**

HEARTBEAT 决定了智能体是"工具"还是"同事"的分水岭。

一个没有心跳的智能体，无论多聪明，都只能在你想起它的时候工作；这意味着**它所有的价值都受限于你的记忆力**。一个有健康心跳的智能体，可以承担"监控型"职责：日报、巡检、预警、周期复盘。这些职责的共性是——它们**没有明确的人类触发点**，只有时间。

同时要注意，HEARTBEAT 是**最容易造成伤害**的契约。乱心跳的智能体是灾难：每小时一次无内容的"我还在"，每天三次"今日无异常"——用户的注意力被廉价地消耗，最后会直接关掉它。**主动性的反面不是迟钝，是打扰。**

**怎么写。**

HEARTBEAT 的写法围绕三个问题：

1. **节律**：多久醒一次。这个值要跟任务的真实频率匹配。日报就是每天一次；盘库就是每周一次；紧急告警可以有单独的高频通道。
2. **醒来做什么**（`on_wake[]`）：每一条都要是**有产出**的动作，不是"检查一下"。比如"对比昨日与今日的关键指标，若偏差超过阈值则生成一条告警，否则静默"。
3. **熔断边界**：什么情况下必须闭嘴。这一条最常被忽略，也最重要。建议明确写：**无事发生时不许发言**。

**技巧。**

- **把"安静也是正确行为"写进契约**。一个成熟的巡检智能体，大部分时候的正确答案是"什么都不报"。
- **分级节律**。把"高频低成本"（指标轮询）与"低频高价值"（周报）分开，不要让它们共用同一个唤醒。
- **心跳任务要可验证**。每次唤醒的产物（哪怕是一行"已检查，无异常"）应该落盘，这样你才能事后回答"它到底有没有在跑"。

**常见误区。**

第一个误区是**把 HEARTBEAT 写成打扰脚本**。表现为每天固定时刻发"今天也没有新任务哦"。这种"存在感汇报"是主动性的赝品。

第二个误区是**认为所有框架都有心跳**。事实是：**OpenClaw 原生支持 heartbeat；而像 LangGraph 这类图编排框架没有内置心跳机制，需要外部 cron 提供"唤醒"**。这不是优劣问题，是设计取向问题——但它意味着你在做跨框架迁移时，必须显式补上这一层。

第三个误区是**用高频来弥补不确定性**。"我怕漏掉，所以五分钟跑一次"——漏掉的根因通常是**判定逻辑不清**，不是频率不够。提高频率只会让噪音更多。

第四个误区是**心跳与记忆脱节**。心跳产生的观察如果不进 MEMORY（或相应的账本），下一次唤醒就不知道上次看到过什么，于是每次都从零判断，也就无法做"趋势"判断。心跳和记忆必须成对设计。

**进化阶梯。**

- L1：有 `HEARTBEAT.md`，写了节律。
- L2：`on_wake[]` 每条都有明确产出，且写了"无事静默"。
- L3：有分级节律与熔断边界，且每次唤醒的产物可核查。
- L4：心跳产出的观察已接入记忆层，能做趋势判断与主动提案。

### 概念 7 · 契约 6 · IDENTITY：身份锚点与归属

**它是什么。**

IDENTITY 契约（`IDENTITY.md`）定义"我的凭证与归属"。关键字段：`agent_id`、`owner_org`、`trust_tier`。并与治理章节的信任评分（Trust Score，原：信誉分）联动。

**它的核心目的。**

IDENTITY 解决的是"**在多个主体存在时，谁是谁**"这个问题。

单机、单智能体、单用户的场景下，身份似乎是多余的——反正只有它一个。但一旦进入三种场景，身份立刻变成刚需：

- **多智能体**：路由需要知道"这条消息该给谁"，而路由的前提是"每个成员有稳定的标识"。
- **治理**：信任评分要按智能体分档，没有分档依据，评分就是一团糊。
- **跨组织协作**：对外协作时，智能体之间要交换身份信息，A2A 式的握手必须有一个主体。

**拟人化映射。**

IDENTITY 对应的是**工牌 + 职级 + 汇报关系**。

工牌决定你是谁（唯一标识）；职级决定别人默认给你多少信任（`trust_tier`）；汇报关系决定你属于哪个组织、出了事找谁（`owner_org`）。

一个没有工牌的人，在组织里是"幽灵"：他做了什么没人能归因，他能做什么也没依据。

**对长期表现的影响。**

IDENTITY 决定**可归因性**。

一个系统越复杂，"归因"就越珍贵。当你发现某个环节出了问题，你需要能回答"这是哪个智能体做的、它当时的职级是什么、它属于哪个组织"。没有 IDENTITY，这些问题无解——你只能得出"系统出的问题"这种没用的结论。

在信任治理里，IDENTITY 也是唯一的分档入口：`trust_tier` 是信任评分体系的初始输入。

**怎么写。**

IDENTITY 通常很短：

- `agent_id`：唯一标识（可以是约定名，也可以是系统生成的 UUID）。
- `owner_org`：归属组织。对外场景建议使用标准化的组织名（例如"蓝血智能体生态（Blue-Blood Agent Ecosystem，原：蓝血军团）"这类对外名）。
- `trust_tier`：1–5 的信任分档，对应治理章节的评分体系。
- 可选 `role`：对外时使用的职能后缀（如 `Xuanyuan (Engineering)`、`Tiangong (Product)`）。

有一条重要的组织纪律：**角色名保留，但必须加职能后缀**。角色名（昆仑、轩辕、天工……）是品牌资产，应该保留中文名；但对外一律要带英文职能后缀，否则外部协作方无法判断"这个人管什么"。

**技巧。**

- **把 IDENTITY 与信任评分联动起来**。信任分档不是一次定终身，应该随治理结果调整；IDENTITY 记录当前档位，账本记录调整历史。
- **对外名与内部名分开**。内部可以一直用亲切的角色名；对外必须用"标准名 + 职能后缀"。
- **避免 `agent_id` 重复**。多智能体场景下，重复的 id 会让归因和路由同时失效；每次新增智能体时做一次去重检查。

**常见误区。**

第一个误区是**认为 IDENTITY 多余**。这是单机时代最常见的省略，代价在进入多智能体或对外协作时一次性爆发：路由错人、信任分档无依据、跨组织协作无法声明归属。省下的三十行文件，换来的是整个治理体系的地基缺失。

第二个误区是**写得太轻，缺少协同价值**。只写一个名字，不写归属与职级，等于只发了工牌没定岗。IDENTITY 的价值在于它同时服务**路由**、**治理**、**协作**三个场景。

第三个误区是**历史行为无法归因**。后补 IDENTITY 不难，但补建之前那段时间的行为没有任何身份锚点——你可以补上文件，补不上历史。

**进化阶梯。**

- L1：有 `IDENTITY.md`，三个关键字段齐。
- L2：`agent_id` 全局唯一，`trust_tier` 与治理联动。
- L3：对外身份与内部身份分离，且有职能后缀。
- L4：IDENTITY 成为协同与治理的公共索引，任一动作都能反查到主体。

### 概念 8 · 契约 7 · MEMORY：记忆分层与压缩预算

**它是什么。**

MEMORY 契约（`MEMORY.md`）定义"我记得什么、怎么记"。

这是 7 个契约里**事实最容易搞错**的一个，因此必须把三条硬事实先摆出来：

1. **OpenClaw 的 MEMORY 是文件模板，不是 MemGPT 式的运行时分级记忆**。不要直接把 MemGPT / Letta 的 core / archival / recall / archive 四类记忆搬过来——那是部分对位，不是等价。
2. **真名字段**：`compaction.reserveTokensFloor` 是 v1.0 误植，**不存在**。真名是 **`effectiveReserveTokens`**（= `contextTokenBudget` × 0.25 上限），配套常量 **`MAX_COMPACTION_RESERVE_RATIO = 0.25`**。
3. **该预算不可配置**。它不是"换个名字就能配"，而是由主仓常量决定。v1.0 文档里"可配 20000"的说法是错的。

还有一条实测勘误需要保留：本机 `~/.openclaw/openclaw.json`（45,662 字节）对 `compaction` / `effectiveReserveTokens` / `reserveTokens` / `reserveTokensFloor` / `contextTokenBudget` **全部 0 命中**——顶层 `session` 仅含 `dmScope`。所以"用真名"的准确含义是：**不要再沿用 `reserveTokensFloor` 这类 v1.0 误植**；这不代表它是可以写进 `openclaw.json` 的字段。相关表述属于**本书接口层口径**，不是配置文件字段（完整真实路径对照见第 2 章）。

顺带把顶层真实结构说清：`openclaw.json` 真实顶层 key 共 **20 个**——`acp, agents, auth, bindings, browser, channels, commands, env, gateway, logging, memory, messages, meta, models, plugins, session, skills, talk, tools, wizard`。**不含** `runtime / workspace / routing / heartbeat / subagents`。

**它的核心目的。**

MEMORY 的存在是为了回答一个悖论：**智能体需要跨会话记住东西，但上下文窗口是有限的、且昂贵的。**

如果什么都不记，智能体每次都是新人，长期协作无从谈起。如果什么都记，上下文会被垃圾填满，模型在噪声里抓不到重点。

所以 MEMORY 的核心不是"存储"，而是**取舍与压缩**：什么进、什么不进、进来的放多久、什么时候压缩。这就是契约里 `memory_tiers[]` 与 `compaction_policy` 两段的意义——前者是层级策略，后者是压缩预算策略。

**拟人化映射。**

MEMORY 对应的是**一个人的工作笔记制度**。

一个成熟的专业人士不会把所有事都记在脑子里，也不会把所有事都写下来。他有一套分层：随手记的便签（短期）、项目笔记（中期）、归档材料（长期）。他知道什么该写进永久笔记，什么该扔掉。他也知道"脑子装不下时该怎么概括"——这就是压缩。

MEMMORY 的失败几乎都是同一个病：**把它当成了垃圾堆**。什么都往里塞，最后笔记变成一片荒地，谁也不去看。

**对长期表现的影响。**

MEMORY 决定**经验的复利**。

一个会记忆的智能体，第 100 次做同类任务时，用的是前 99 次沉淀的判断；一个不会记忆的智能体，第 100 次仍然是第 1 次。这就是复利与线性的差别——在长期运行中，这个差别会大到难以想象。

同时 MEMORY 与**会话压缩**（Session Compaction，原：会话卫生）直接耦合：压缩预算是有限常量，记忆策略决定了预算被什么东西占用。一个把日志塞进记忆的智能体，会在关键讨论进行到一半时被压缩打断，然后忘记前面说过的话。

**怎么写。**

MEMORY 的写法建议围绕三件事：

1. **层级策略**：区分"当前会话的短期上下文""跨会话的长期事实""低频访问的归档"。各层的进入/退出条件写清。
2. **准入标准**：什么值得长期记。建议标准是——**跨会话仍然影响判断的事实、决定、约定、勘误**。不要记过程日志，不要记临时状态。
3. **压缩预算的记录**：把真名与"不可配置"写清楚，作为文档事实记录下来。注意，这一条是**记录**而不是**配置**——写它，是为了防止团队里有人再去调一个不存在的字段。

**技巧。**

- **给记忆写"过期条件"**。事实会老。"我们目前用 X 方案"这类条目应该带时间戳和复核日；不带过期条件的记忆，比不记更危险——因为它会让你在半年后依据过期事实做决定。
- **区分"事实"与"判断"**。发生过的事（事实）与当时的结论（判断）分开记，因为事实长期有效，判断可能被推翻。混在一起，推翻判断就会连带否定事实。
- **把勘误单独成条目**。像"`reserveTokensFloor` 是误植，真名是 `effectiveReserveTokens`"这样的条目，价值极高，因为它防止的是**全组织重复踩同一个坑**。
- **压缩策略要与心跳配合**。长期运行的智能体，压缩时机与心跳节律最好错开，避免"刚醒就被压缩"这种糟糕组合。

**常见误区。**

第一个误区是**把 MEMORY.md 当 MemGPT 的 4 类记忆来写**。字段对不上、压缩行为不变、后续章节读不懂。正确做法是理解 OpenClaw 的 MEMORY 是文件模板 + 分层策略。

第二个误区是**去调 `reserveTokensFloor`**。写了不存在的字段，系统不报错、不警告、照常运行——你以为配了，其实没有。这类静默忽略是最贵的失败模式：你以为在做压缩调优，实际上所有"优化"都是幻觉；一旦会话真的爆上下文，你会误判成"压缩机制不行"。

第三个误区是**把记忆当技能用**。记忆是"事实的账本"，技能是"可复用的方法论"。把一套操作步骤写进记忆，等于每次都要重新读一遍；正确做法是把它写成一个 Skill（`SKILL.md`），让它在需要时按需加载。

第四个误区是**只增不减**。记忆只增不减，会在几个月内变成一个巨大的、模型读不完也读不完的文档。记忆必须有修剪机制，否则它就会从资产变成负债。

**进化阶梯。**

- L1：有 `MEMORY.md`，至少有分层说明。
- L2：有准入标准与过期条件。
- L3：真名与勘误已固化，且没人再去调不存在的字段。
- L4：记忆策略与压缩、心跳、技能形成联动，且定期修剪。

### 概念 9 · 启动时自动加载：契约最被低估的机制

**它是什么。**

7 个契约不是"需要时去读的文件"，而是**智能体启动时自动加载**的注入内容。这是它们与普通文档的根本区别。

本章对位表（见第 5 段）里有一句结论，应该被反复强调：

> **OpenClaw 是少数把协议做成"启动时文件级自动加载"的系统；这也是它相对其他框架最大的结构性差异。**

**它的核心目的。**

自动加载解决的是"**激活成本**"问题。

一份文档无论写得多好，如果需要人手动喂进去，它的实际使用率会趋近于零。契约的整个设计前提就是：**你写一次，它每次启动自动生效**，不需要你在提示词里重复、不需要用户记得粘贴、不需要任何人的纪律来维持。

这解释了为什么"文件位置和文件名"是硬约束。启动时扫描是按固定文件名进行的，名字不对，系统就当你**没有**这份契约——而且不报错。

**拟人化映射。**

自动加载对应的是**人的"出厂设置"**。

你早上醒来，不需要先读一遍"我是谁、我的价值观是什么、我的工作纪律是什么"才能开始一天。这些东西是**常驻的**，不占你的有意注意力。

契约的自动加载就是在给智能体做这件事：把人设、边界、纪律变成"不需要想起也一直在"的东西。

**对长期表现的影响。**

自动加载决定**契约的兑现率**。

契约写得再好，如果不是自动生效，你就永远处在"这一轮记得喂、下一轮忘了喂"的波动里。波动会导致一种非常糟糕的现象：**同一份契约，有时生效有时不生效**。这比完全没有契约更糟，因为它让你误判"契约没什么用"。

**怎么写（怎么用）。**

关于这一机制的实操要点，全部围绕"路径与命名"：

- **文件名必须是标准英文名**：`SOUL.md` / `USER.md` / `AGENTS.md` / `TOOLS.md` / `HEARTBEAT.md` / `IDENTITY.md` / `MEMORY.md`。这是接口，不是标题。中文名只能出现在文件内容里作为注解，不能作为文件名。
- **位置必须是对的位置**。放在智能体自己的契约目录下（本书模板口径：`agents/roles/<agent>/contracts/`）。位置错了，等于没写。
- **编码与换行必须干净**。UTF-8 无 BOM、LF。带 BOM 或 CRLF 混合的文件，可能让解析静默失败——它"看起来完全正常"，这是最难排查的一类问题。
- **不引入成本**。如果"启动时加载"意味着智能体每次启动都要读完整本手册，那你很快会放弃。所以契约必须**短**——这是 SOUL 不能写一千行、MEMORY 必须修剪的另一个理由。

**技巧。**

- **用"空文件判定"做体检**。7 个文件都在，但如果是 0 字节，等于没配。检查"每份契约至少有一个非空的关键字段"。
- **不要用软链共享**。多个智能体软链同一份 `SOUL.md`，看起来是统一，实际是人格串味。
- **做好版本化**。契约目录纳入 Git，改前打 tag。这样"自动加载"的内容是可追溯到具体版本的。

**常见误区。**

第一个误区是**用中文名命名契约文件**。后果是 OpenClaw 启动时完全不读它们，智能体行为与文件毫无关联，**且不报任何错**。这是本书反复强调的最危险失败模式：静默的无效。

第二个误区是**把契约放在"顺手的地方"**（桌面、临时目录、聊天记录里）。不自动加载的位置，等于提示词。

第三个误区是**以为"加载了"就等于"遵守了"**。加载只是必要条件：它把契约送进上下文；遵守程度还取决于契约是否可判定、是否够短、是否被后续内容稀释。加载之后的表现，要靠第 4 章的漂移治理持续验证。

第四个误区是**契约过长把上下文吃光**。这是"加载成功但效果为负"的典型。契约的收益随长度递减、成本随长度递增，交叉点通常比你想象得早得多。

**进化阶梯。**

- L1：知道契约是启动时自动加载的，不是手动喂的。
- L2：文件名与位置都对，且实测能被识别。
- L3：有版本化与空文件体检。
- L4：契约长度被主动控制，加载成本与收益有明确的取舍标准。

### 概念 10 · 契约漂移与锚点：让"变了"变成可测量的事

**它是什么。**

文档漂移 / 人格漂移（Document Drift / Personality Drift）指的是：契约文件（而不仅是行为）随时间的无意识变化。

它的技术前提是**锚点**：一份基线版本。有基线，才谈得上漂移；没有基线，你连"变了"都说不出来。

**它的核心目的。**

漂移治理的目的是把"感觉它变了"这种模糊的抱怨，变成"**它在第 3 条价值观上偏离了基线，偏离幅度 X**"这种可处置的事实。

没有这个转换，长期治理不可能发生。你会陷入两种无效循环：要么反复"重开一次看看"，要么每次都觉得"好像是我想多了"。

**拟人化映射。**

漂移对应的是一个人的**慢性性格变化**。

你不会在某一天突然变成另一个人。你是被一件件事一点点推着走的：一次妥协、一次懒得坚持、一次觉得"这次算了"。半年后回头看，你已经不是原来的你——而且一路上没有任何一个时刻让你觉得"我变了"。

契约漂移也是这个机制：**单次改动都合理，累积方向却错了**。

**对长期表现的影响。**

漂移不治理，会有两种结局，都很糟：

- **人格腐化**：一个原本"不确定就标 ⏳"的智能体，被一次次"你就给个数吧"磨成了"自信满满"。它输出的一切都还在，只是可靠性已经掉到地板上，而你没有察觉。
- **文档与事实脱节**：业务变了、组织变了、工具变了，契约还停在三个月前。于是路由错人、权限过宽、记忆里全是过期事实。

漂移治理的收益是**可回退性**：只要锚点还在，你永远能回到三个版本前的自己。

**怎么写（怎么治理）。**

漂移治理的核心动作只有三个：

1. **建基线**。契约目录初始化时立刻打一个基线 tag（例如 `baseline-YYYYMMDD`），并保留每份契约的哈希。
2. **定期 diff**。按周（与心跳节律配合）对 7 份契约做"当前 vs 基线"的差异检查，输出漂移报告并落盘。
3. **设阈值与处置链**。差异超过某个幅度（例如 1%）就告警；告警之后必须有明确处置：**接受（更新基线）或回滚（恢复旧版）**。不做处置的告警，四周之后就会被无视。

**技巧。**

- **漂移报告要落盘**。不落盘的检查等于没做——你无法证明它跑过，也无法对比不同周的趋势。
- **区分"有意变更"与"无意识漂移"**。有意变更走 Git 提交和变更记录；无意识漂移是 diff 出来的意外差异。两者的处置方式完全不同，混在一起会让治理变成一场争吵。
- **锚点不止 SOUL**。SOUL 是最重要的锚点，但 USER（主人模型变了没）、AGENTS（纪律松了没）、MEMORY（记忆膨胀了没）都需要锚点。
- **把漂移写进心跳**。最省力的实现是：心跳任务里加一条"每周一检查契约漂移"。这样治理就不依赖人的记性。

**常见误区。**

第一个误区是**认为协议是"配一次就完事"的静态文件**。新人把 7 契约配好，从此不再动；半年后 MEMORY 膨胀、SOUL 漂移、HEARTBEAT 失效，而他完全不知道——因为从来没有"回看协议"的习惯。协议文件不会自己报警：它不跑、不报错、不通知，静静腐烂。

第二个误区是**把漂移当错误来消灭**。漂移是系统性的必然；目标是**可控漂移**，不是零漂移。一个从不变化的契约，往往意味着它已经脱离现实。

第三个误区是**用感觉判断漂移**。"我觉得它最近有点飘"不能作为处置依据。必须有 diff、有幅度、有时间线。

第四个误区是**只在出事之后才回看**。事故驱动的体检，只能救已经造成的损失。周期性体检才能救还没发生的损失。

**进化阶梯。**

- L1：知道契约会漂移，且漂移是累积的。
- L2：有基线快照与哈希。
- L3：有周期性 diff 与落盘的漂移报告。
- L4：漂移告警有明确处置链，且"接受"与"回滚"都是记录在案的决定。

### 概念 11 · 契约的版本控制：人格也需要 Git

**它是什么。**

把契约目录纳入版本控制（Git），并建立"改动前打 tag / 改动后立即 commit"的纪律。

**它的核心目的。**

版本控制给契约提供了三样东西：**历史**（能看回去）、**回滚**（能退回去）、**归因**（能说清是谁在什么时候改的、为什么）。

这三样恰好是"人格管理"最难、也最必需的能力。

**拟人化映射。**

版本控制对应的是**人事档案**。

一个人的性格变化如果是慢性的，你怎么知道？靠记录。入职时的自我评价、每年的绩效评语、每次岗位调整的理由——有了这些记录，你才可能在"他好像不太一样了"的时候翻回去核对。

没有档案，你只有当下的印象；有档案，你才有判断依据。

**对长期表现的影响。**

版本控制决定**可治理性**。

所有定量的治理动作——漂移检测、回滚、变更审计、责任归因——都必须建立在版本历史上。没有它，"治理"只能退化成"感觉"。

它也决定**人际信任的稳定性**。当多个同事、多个工具都可能修改契约时，"谁改的"这个问题如果答不上来，团队就会开始互相怀疑；有 commit 记录，这个问题在技术上被消解。

**怎么写（怎么落地）。**

- **契约目录单独 git init**，或者并入手册仓库的独立子目录。
- **基线即 tag**：初始化时打 `baseline-YYYYMMDD`。
- **改动走分支**：例如 `soul-tune-YYYYMMDD`。改完 commit、打新 tag。
- **改动信息要写清理由**。不是"update SOUL.md"，而是"tune: 语气从 casual 调整到 direct，因为最近三次交付风格漂移"。一年之后你会感谢这句理由。
- **哈希校验**：每次体检时对比当前文件哈希与基线哈希，差异即漂移信号。

**技巧。**

- **给"手工改"和"工具改"留痕区别**。有些工具（或自动流程）会改写契约（例如 AGENTS 的工具段）。这类改动要能被识别，否则你会分不清"是我团队改的，还是某个流程改的"。
- **契约提交与产物提交分开**。契约的变更频率远低于产物，混在一条历史里会让契约历史被淹没。
- **把"未提交的修改"视为风险**。工作区里长期挂着一份未提交的契约改动，等于系统实际上在跑一份没有历史的协议——漂移检测会误报（因为基线对不上）。

**常见误区。**

第一个误区是**裸目录无版本控制**。改了就没，想回滚没有路径。这在个人使用时似乎无所谓；在团队/多智能体场景下，它直接导致"人格事故无法收场"。

第二个误区是**把版本控制当成程序员的专属仪式**。契约版本化的收益与写代码完全不同：它服务的是**身份与治理**，不是发布流程。

第三个误区是**只记"改了"，不记"为什么"**。缺乏理由的历史，在需要判断"这个改动该不该保留"时几乎无用。

第四个误区是**基线只打一次，之后再不更新**。基线如果永远停在最初版本，diff 会越来越大，从"漂移检测"退化成"一份巨长的差异清单"，没人看得下去。正确的做法是：**每次有意变更后更新基线**，让基线代表"最近一次被正式接受的形态"。

**进化阶梯。**

- L1：契约目录有 Git。
- L2：有基线 tag 与哈希。
- L3：改动走分支 + commit message 带理由。
- L4：基线随有意变更滚动更新，漂移报告始终只有小差异、可被人读完。

### 概念 12 · 宪法层与最小可用集：为什么不是"七个都要配满"

**它是什么。**

把 7 个契约合起来看，它们构成一个**宪法层**。但"宪法层"不等于"必须全配"。

本章给出两条同等重要、且方向相反的判断：

1. **宪法层**：7 个契约是启动时自动加载的持久声明。它们约束的是智能体的**存在方式**，而不是某一次任务的做法。宪法的作用是限权、定身份、给方向。
2. **最小可用集**：不同场景需要的契约数量不同。配齐不是美德——**配到刚好、且能说清为什么不用剩下的**，才是。

**它的核心目的。**

这一条存在的目的，是防止两种对称的错误：

- **配置不足**：该配的没配，导致行为失控。无 SOUL 则人格真空（被最后一次交互定义）；无 USER 则价值失焦（正确但没用）；无 HEARTBEAT 则主动性受限于你的记忆力。
- **过度配置**：小场景配大系统，维护成本远超收益，最后全部停更——**等于回到原点，还多了一批需要清理的残骸**。

宪法层的概念解决前者，最小可用集解决后者。

**拟人化映射。**

宪法层对应的是**一个国家的宪法**：它规定谁有权、有什么权、边界在哪，但它不规定你每天几点吃饭。

最小可用集对应的是**公司规模决定管理制度**。三个人的公司不需要设三层人力层级；三千人的公司不设就会失控。制度不是越多越好，是**匹配才好**。

**对长期表现的影响。**

这个判断直接影响**可持续性**。

过度配置最典型的死法是这样：给一个只做单机脚本的小智能体配上多智能体路由、信任分档、心跳巡检——配置量爆炸，两周后没人维护得动，全部停更，于是系统进入"配了但全烂"的状态。**烂掉的配置比没有配置更糟**，因为它会给人"我们有协议层"的错觉，从而停止改进。而"没有配置"至少是诚实的，它会持续提醒你缺东西。

反过来，最小可用集会让你得到一条真实的增长曲线：先立住最关键的 2 个，跑稳，再加 2 个，跑稳，再加。每一步都可回退，每一步的收益都能被验证。

**怎么写（怎么选择）。**

按场景档位选，是最有效的实践方式。一个经验分档如下：

- **单机一次性任务型**：只需要 **SOUL + USER**（2 个）。它要有人格与主人模型；不需要心跳（不常驻）、不需要协同（没别人）、不需要身份（没治理）。
- **单机常驻型**：再加 **HEARTBEAT + MEMORY**（4 个）。常驻意味着它有时间维度与记忆维度。
- **多智能体协同型**：再加 **AGENTS + IDENTITY**（6 个）。有别人，就有路由与身份。
- **对外 / 跨组织型**：**全 7 个**。对外意味着要有完整的权限声明、身份凭证、审计与协同。

选完之后有一个纪律动作必须做：**把"不用的契约"和理由写下来。** 理由可以是"单机无子智能体""无跨组织需求""只用内置工具"。这一动作能省掉未来无数次"我们当初为什么没配这个"的困惑。

**技巧。**

- **从最小集开始，按需增配。** 先 SOUL + USER，跑稳再加心跳。不要一天配完 7 个——你还不了解它们的真实使用形态，配出来的多半是错的。
- **对位表可以作为"要不要配"的外部参照。** 本章后段的 6 框架对位表会告诉你：业界最成熟的框架最多也只覆盖 7 个契约中的 5 个。这说明"不必求全"在业界是常态，不是偷懒。
- **把"契约选用说明"作为一份独立的小文件**（例如 `README-contracts.md`），记录启用了哪些、未启用哪些、复核时间。它让选择从"印象"变成**可审计的决定**。

**常见误区。**

第一个误区是**以为"7 大"意味着"缺一不可"**。"7 大"这个措辞确实容易误导；实际含义是"OpenClaw 提供 7 种协议能力"，而不是"每个智能体必须 7 个全用"。检查清单的原话是：**不需要全用，但要说得出为什么不用剩下的**。

第二个误区是**用"全套都配"来对冲焦虑**。这是把"完整"当"安全"。事实上过度配置带来的假复杂度会让系统更难理解、更难排查，实际风险是上升的。

第三个误区是**配了但都是空壳**。文件都在、内容为零——这才是最常见的"配了等于没配"。最小可用集的定义里包含"**每份契约至少填一个关键字段**"。

第四个误区是**不做复核**。今天不需要的契约，三个月后可能需要（比如开始接入第二个智能体）。选用说明里的"复核时间"就是为了让这个判断被周期性重做。

**进化阶梯。**

- L1：知道 7 契约不是必须全配。
- L2：能按场景档位做出选择，并写下理由。
- L3：有选用说明文件 + 定期复核。
- L4：契约集合随系统复杂度同步演进，且每一次增配都有明确的触发事件记录。

## 三、怎么做：八步实践路径

这一节讲"动作"，不讲命令——命令由 4 件套（Cookbook / 操作手册）承担。这里给的是**判断与顺序**，因为顺序错了，后面的努力会全部白费。

八个步骤的组织逻辑是一条线：**先定规模 → 再定方向 → 再定人格 → 再定环境 → 再定纪律 → 再定节律 → 再定身份与记忆 → 最后锁进版本库**。每一步都产出一样**可见的东西**，这是本章方法论的落地形态。

### 第 1 步 · 先定档位，再动手

**动作。** 不要一上来就建 7 个文件。先回答一个问题：**这个智能体是哪种存在？**

- **单机一次性任务型**：跑完就完，不需要常驻。
- **单机常驻型**：长期活着，有时间维度。
- **多智能体协同型**：有同伴，需要路由与身份。
- **对外 / 跨组织型**：要跟外部主体打交道。

这个判断直接决定你要配 2 个、4 个、6 个还是 7 个契约。

**判断要点。** 分档的依据不是"这个智能体强不强"，而是三个问题：它常驻吗？它有同伴吗？它对外吗？

**叙事示例。** 假设你在建一只"每天早八点给我一份渠道数据简报"的智能体。判定结果是**单机常驻型**——它常驻（每天都要醒）、有时间维度（要记得昨天报了什么），但它没有同事（不需要 AGENTS）、没有对外身份（不需要 IDENTITY）。所以它的最小集是 **SOUL + USER + HEARTBEAT + MEMORY** 四个。TOOLS 可选：如果它需要读数据源、写文件，那 TOOLS 也该有——**不要教条**。

**验收信号。** 你能用一句话说清这个智能体属于哪一档，并列出启用了哪几个契约、为什么不用剩下的。

这一步最容易犯的错是"我全都要"。全都要的代价不是文件多，而是**你将失去判断力**：当行为出问题时，你无法判断是哪个契约的责任。

### 第 2 步 · 立 USER：把"谁在用它"说清楚

**动作。** 第二个动作是 USER。原因是它决定了后面所有内容的**方向**。

**判断要点。** 这不是随便排的顺序。如果先立 SOUL，你会按自己的喜好写人格，而人格与"主人的成功标准"可能并不一致。先立 USER，等于先确定"为谁而战"，再决定"成为什么样的战士"。

**叙事示例。** 写 USER 的那一刻，你要在脑子里过一遍最近让你不满意的三次交付。它们是不是都呈现同一个毛病？比如"都太长了""都在解释我早就知道的东西""都没告诉我下一步"。这些描述，就是你 USER 里"输出偏好"与"明确禁忌"段落的最初素材——**从真实的失望里提取条款，比从想象中提取准得多**。

**必须写清的一条。** **完成定义。** 对很多人来说，"完成 = 有产物 + 有验收口径 + 有下一步"。这一行写完，你会发现智能体的交付形态立刻变了——它不再以"生成了一段话"为终点。

**同时要写、但要理解其性质的一条。** 权限声明（`permissions` / `data_scope`）。写它是必要的，但要记住这是一次**声明**；它的强制要靠第 4 步（宿主工具配置）与第 7 步（身份与治理）的落地。只写声明不落强制，就是"假安全"。

**验收信号。** 你的 USER 里有决策原则、输出偏好、明确禁忌、完成定义四段，且每一段都能举出一个具体例子。

### 第 3 步 · 立 SOUL：人格要能被压力测试

**动作。** 第三步写 SOUL。标准很短：`persona` 一句话、`values` 二到五条、`tone` 一个基调。

**判断要点。** 写的时候用两个测试自检：

- **压力测试**：如果老板明确要求它违反某一条价值观，它会守住吗？守不住的，不是价值观，是愿望。
- **三句测试**：把 SOUL 藏起来，让它回答三个典型模糊问题（信息不足要不要猜？任务做不完要不要说？被催要不要压缩质量？）。它的选择是否与 SOUL 一致？

**叙事示例。** 一个很有效的技巧是给 values 里加一条**反诱饵条款**。"没有证据不下结论"是一条；"用户施压也不给未经验证的数字"是它的可执行形态。后者才是真正会在关键时刻起作用的那一条——因为诱惑从来不会以"请违反你的价值观"的形式出现，它总是以"通融一下"的形式出现。

**验收信号。** SOUL 里没有格式要求（不用 emoji、控制长度这类），只有能被压力测试的行为准则；且三句测试的答案与 SOUL 一致。

### 第 4 步 · 立 TOOLS：环境映射必须实测

**动作。** 第四步写 TOOLS。有一条铁律：**凭记忆写的路径一定会骗人。**

**判断要点。** 写之前先做两件事：一是**真的查一遍**关键路径、别名、目录约定；二是把工具清单与宿主配置对齐，确认"契约里有的工具，实际真的存在"。

**叙事示例。** 你写下"产物目录在 X"。三周后另一台机器上它不是 X。你没有及时发现，于是智能体每次都在错误的地方写东西——它能跑，但产物在哪儿没人知道。这比直接报错糟糕得多，因为它污染的是整个团队对"契约可信"的预期：**一份会骗人的契约，比没有契约更糟。**

**边界纪律。** 如果这个智能体有技能需求——把技能需求**交给 Skill 子系统**（`SKILL.md` 链路），不要在 TOOLS 里兜。能力归 Tools，方法论归 Skills。

**验收信号。** TOOLS 里每一条路径都实测过；工具清单与宿主一致；没有 `skills:` 段。

### 第 5 步 · 立 AGENTS：纪律写成检查点

**动作。** 第五步写 AGENTS。核心是把纪律写成**可判定的检查点**，而不是原则。

**判断要点。** 一个简单的判据：**这条纪律能被判定违反吗？** 不能判定的，就是墙上的口号，不要写进契约。

**叙事示例。** 与其写"要闭环"，不如写：

- 交付前自查三项：产物在哪 / 怎么验 / 下一步是什么。
- 没有验收口径，不许说"完成"。
- 不许用"收到 / 在做 / 稍后同步"充当交付。

这三条都可以被判定违反，因此都可以被抽查。可判定性是纪律生效的前提。

**协同部分。** 如果这个智能体有同伴，把路由与让位写进来。注意：文档层的表达（`subagents[]` / `routing_rules`）与运行时的事实（`agents.entries` / `bindings`）必须一致——不一致的表现是"声明了一支队伍，实际上一个都没有"，而这是静默失败。

**验收信号。** 每周抽三次交付做合规检查，能明确判定"符合 / 不符合"，而不是"感觉还行"。

### 第 6 步 · 立 HEARTBEAT：先定熔断，再定动作

**动作。** 第六步是心跳。写法上有一个强建议：**先写熔断，再写动作**。

**判断要点。** 为什么先写熔断？因为新手的第一个心跳几乎总是"打扰型"：它会在没有事情的时候也汇报存在感。先写熔断（"无事发生必须静默"），就能在源头堵住这个失败模式。熔断是心跳的安全带。

**叙事示例。** 一份健康的心跳契约读起来像这样——"每 30 分钟醒一次；对比当前指标与昨日同期；偏差在阈值内则静默并落一行检查日志；偏差超阈值则生成告警并附证据；连续三次无异常时，把节律降档"。

注意最后一句：**心跳的节律本身也应该可调**。这就是"节律的节律"——一个不能自我调节的心跳，会在业务节奏变化后变成纯粹的噪音源。

**验收信号。** 你能回答三个问题：它多久醒一次？醒来必须有产出的是什么？什么情况下它必须闭嘴？

### 第 7 步 · 立 IDENTITY 与 MEMORY：身份与账本

**动作。** 第七步补上两个"长期治理的骨架"。

IDENTITY 很短：`agent_id`、`owner_org`、`trust_tier`。写的时候顺手做一次去重检查（多智能体场景下 id 不能重复）。对外场景记得加上职能后缀（如 `Xuanyuan (Engineering)`）。

MEMORY 稍长：分层、准入标准、过期条件，以及一条**勘误记录**——把 `effectiveReserveTokens` + `MAX_COMPACTION_RESERVE_RATIO = 0.25` 的真名与"不可配置"记录在案。这条记录的价值不在于让你去配它，而在于**让你的团队不再去调一个不存在的字段**。

**判断要点。** 记忆的准入问句只有一个：**"这条信息，三个月后还影响判断吗？"** 如果不会，它不该进长期记忆。这不是吝啬，这是保护上下文预算——记忆越臃肿，模型在关键时刻抓到重点的概率越低。

**叙事示例。** 很多团队在 MEMORY 上踩的坑是"什么都记"。一开始很有安全感，半年后文档膨胀到没人读，于是所有记忆都失效了——**一个没人读的账本，等于没有账本**。修剪机制和写入机制同等重要。

**验收信号。** IDENTITY 三字段齐、id 无重复；MEMORY 有分层、有准入标准、有至少一条过期条件、有真名勘误记录。

### 第 8 步 · 版本化 + 第一次体检

**动作。** 最后一步，也是最多人漏掉的一步：**立刻把契约纳入版本控制，并跑第一次漂移体检。**

顺序是：

1. 契约目录 `git init`，提交一次，打基线 tag。
2. 记录 7 份文件的哈希。
3. 把"每周一检查契约漂移"写进心跳契约。
4. 生成第一份漂移报告（此时差异为零，但报告本身证明了机制在跑）。

**判断要点。** 这一步的价值不在"当下有差异"，而在**建立基线**。基线是漂移治理的第 0 步；没有基线，三个月后你连"它变了没"都无法回答。

**叙事示例。** 这一步的收益在三个月后才会显现。那时的你会因为有了基线，能够回答一个所有人都回答不了的问题——"它到底是从什么时候开始变的？"而这个问题，恰恰是所有"感觉它不对了"的抱怨唯一的出口。

**验收信号。** 基线 tag 存在；能跑一次 diff 并输出报告；心跳契约里有漂移检查项。

### 收尾 · 八步之后，你得到了什么

八步走完，你手里不只是一堆文件。你得到的是：

- 一个**可回退**的人格（有基线、有历史）。
- 一个**有方向**的服务模型（USER 定了成功标准）。
- 一套**可判定**的纪律（AGENTS 的检查点）。
- 一份**实测过**的环境映射（TOOLS）。
- 一个**制度化**的主动性（HEARTBEAT 的节律与熔断）。
- 一套**可归因**的身份（IDENTITY）。
- 一套**会修剪**的记忆（MEMORY 的分层与过期条件）。

这就是"从配置一个 Agent，到塑造一个硅基生命"这句话的工程含义。

而且请注意这八步的共同点：**每一步的产出都是"可见的"**——一份文件、一次哈希、一份报告、一条检查记录。这正是本章的核心方法论：**把静默的存在，变成可见的证据。**

### 附 · 这八步的顺序为什么不能换

八步看似是一张清单，其实是一条**依赖链**。理解这条链，比记住清单本身重要得多——因为清单会忘，链不会。

**为什么"定档位"必须在最前。** 因为档位决定了**后面七步要做几件事**。如果先写了七份契约，再回头发现这个智能体其实只需要两份，你要么删掉五份（浪费），要么留下五份空壳（错误——空壳会让契约层的失败变得静默）。定档位是唯一一个"越早做越省"的动作。

**为什么"USER 在 SOUL 之前"。** 因为 SOUL 回答的是"我是一个什么样的存在"，而"什么样"必须有服务对象作为参照系。同样是"先给结论再给证据"这个特质，对于一个服务投资人的智能体和一个服务工程师的智能体，含义完全不同：前者要求"结论要带不确定性区间"，后者要求"结论要带可复现路径"。先定 USER，SOUL 才有坐标。

**为什么"SOUL 在 TOOLS 之前"。** 因为人格决定了它怎么用工具。同样一个"运行命令"的能力，一个 audit 型人格会先确认再执行，一个 explorer 型人格会先试探再收敛。如果先定工具再定人格，你会得到一套与人格不匹配的能力清单——比如给一个"绝不做未经验证动作"的人格配了完全开放的 shell。

**为什么"AGENTS 在 HEARTBEAT 之前"。** 因为纪律决定了主动性的形态。HEARTBEAT 是"在没人说话时做事"，那么"做什么、做完怎么上报、什么时候升级"这些规则必须先由 AGENTS 定义。否则心跳醒来之后无事可依，只能凭感觉——**一个没有纪律约束的主动性，会变成骚扰。**

**为什么"IDENTITY 与 MEMORY"要靠后。** 因为它们服务的是**长期治理**，而长期治理只有在前面五步都立住之后才有意义。身份与记忆是"账本的封面与目录"：如果里面还没有条目，先装封面没有价值。反过来说，一旦前面的步骤跑起来，识别的需求就会出现——"这是谁做的""上次是怎么判的"——这时补上它们最自然，也最不容易写成空壳。

**为什么"版本化"必须最后、且必须真的做。** 因为它是前七步成果的**保全机制**。前七步产出的是"当前状态"，第八步产出的是"历史"。没有历史，前面所有的工作都只是"一次性的努力"——它会漂，会被人改，会在某天无痕地消失。第八步把一次性的努力变成**可回退的资产**，这一转才是全部八步里性价比最高的一步。

**一个常见的错误顺序。** 先配好所有工具、再用提示词堆人格、最后想起来要"记得住"——这是"引擎优先"的思路，也是绝大多数人第一次的做法。它的问题不在于某一步做错了，而在于**顺序把因果关系颠倒了**：它把"能做什么"放在了"该成为谁"的前面。

而契约层的全部意义，恰恰是把因果倒过来：

> **先定义"是谁"，再决定"做什么"；先定义"为谁"，再决定"是谁"。**

这就是这八步顺序的全部逻辑。它不是流程规范，它是**一个存在诞生时的顺序**。

### 附 · 八步走完之后的日常自查清单

> 说明：这不是操作手册（命令见 4 件套），而是**每周花两分钟该问自己的几句话**。它把八步从"建一次"变成"每周维持"。

**关于位置与加载（对应第 1、8 步）**

- 七个文件名是否仍为标准英文名？
- 是否出现任何中文名的契约文件（含备份文件）？
- 契约目录是否仍在被宿主扫描的正确路径下？
- 上次 `git commit` 是什么时候？工作区是否挂着未提交的改动？

**关于 USER（对应第 2 步）**

- "当前主线"是不是上个月的？
- 有没有哪一条偏好已经在现实中失效，但还留在文件里？

**关于 SOUL（对应第 3 步）**

- 这一周它的判断，有没有出现过与价值观相反的选择？
- SOUL 有没有被任何人（或任何自动流程）改动过？改动有没有理由记录？

**关于 TOOLS（对应第 4 步）**

- 工具清单里的每一样，今天还存在吗？
- 环境映射里的每一条路径，今天还成立吗？

**关于 AGENTS（对应第 5 步）**

- 本周抽查的三次交付，是否都带验收口径与下一步？
- 有没有出现"声明了但调度不到"的子智能体？

**关于 HEARTBEAT（对应第 6 步）**

- 本周它的唤醒里，有多少次是**没有必要**的汇报？
- 有没有某一次心跳真正救了一个问题？（如果连续一个月都没有，考虑降档）

**关于 IDENTITY 与 MEMORY（对应第 7 步）**

- 有没有新加入的主体没有 IDENTITY？
- 长期记忆里有没有条目已经过期却没有标注复核日？

### 附 · 三个最容易出事的时刻

**时刻一 · 第一个季度末。** 此时契约刚配好不久，一切看起来都很稳，于是"回看"这件事被自然放弃。风险不在于当下会坏，而在于**基线从此不再更新**——等到半年后需要 diff 时，你会得到一份长到无法阅读的差异清单。

**时刻二 · 团队第二位成员加入时。** 第一个人建契约时心里有一套隐含理解；第二个人读到的是文字。所有"当时觉得不用写"的东西，在这一刻集中暴露。**这是契约层第一次真正的压力测试**，也是最值得做一次全面体检的时点。

**时刻三 · 从单智能体扩展到多智能体时。** 这一转会把 IDENTITY、AGENTS、让位规则从"可选"变成"必需"。最典型的失败是：文档里加了一整支队伍，运行时一个都没注册，于是任务从此不再被路由出去——而且不报错。

## 四、契约的十种失真：现象、根因与修复

前面讲的是"应该怎么做"。这一节讲的是**真实发生过的坏法**。它们的共同特征只有一条，却极端致命：**都不报错。**

这是契约层最危险的性质——它会以完全静默的方式失效，而你以为一切正常。你甚至会更自信，因为你"已经配过了"。

十种失真的排序依据是"发生频率 × 破坏力"。每一种都按 **现象 → 为什么错 → 怎么救 → 怎么预防** 四段讲透。

### 失真 1 · 用中文名命名契约文件

**现象。** 按旧习惯把文件建成 `灵魂契约.md`、`用户契约.md`、`军团契约.md`、`工具契约.md`、`心跳契约.md`、`身份契约.md`、`记忆契约.md`。智能体行为与这些文件毫无关联——它不读它们，**而且不报任何错**。你会得到"配了但没生效"这种最让人抓狂的体验：文件明明在那儿，行为却像什么都没有。

**为什么错。** 契约名是**接口**，不是标题。启动时的自动加载是按**固定文件名**扫描的；名字不对，系统就当你**没有**这份契约，于是走"无契约"的默认路径。中文名只能作为**文件内容里的注解**存在，不能作为文件名。

更隐蔽的代价是时间成本：一旦用中文名起步，后面所有的 diff、体检、漂移检测都会基于错误的基线。你要么带着一个不对的基线一直跑下去（漂移检测永远是噪音），要么在某个时刻整体整改——而整改成本随时间指数上升，因为依赖它的东西越来越多。

**怎么救。** 重命名为标准英文名：`SOUL.md` / `USER.md` / `AGENTS.md` / `TOOLS.md` / `HEARTBEAT.md` / `IDENTITY.md` / `MEMORY.md`。中文注解搬进文件内容第一行。改完立刻做一次"文件名齐备"体检：七个文件是否都在、是否还残留中文名文件、能否被宿主识别。

**怎么预防。** 把三行术语红线贴在文档模板顶部：**对外必改名 / 首次出现双写（如 `SLCP（Silicon-Life Coordination Protocol，原：ACP）`）/ 引用术语表 §X**。在体检脚本里加一条"中文名文件扫描"，像 Lint 一样把它拦在提交前。

### 失真 2 · 把 `reserveTokensFloor` 当真名去配

**现象。** 从旧文档学到"把 `reserveTokensFloor` 设成 20000 就能控制压缩预算"，照着写进 MEMORY 配置，结果压缩行为完全没变。你去确认，发现这个字段**根本不存在**。

**为什么错。** 真名是 **`effectiveReserveTokens`**（= `contextTokenBudget` × 0.25 上限），配套常量 **`MAX_COMPACTION_RESERVE_RATIO = 0.25`**。而且关键信息不只是"名字错了"，而是——**该预算由主仓常量决定，字段不可配置**。旧文档说"可配 20000"，是错的；这不是"换个名字配"的问题，是**你配不了**。

最贵的部分在中间那句静默忽略：写了不存在的字段，系统不报错、不警告、照常运行。你以为配了，其实没有。于是所有"压缩调优"都是幻觉；一旦会话真的爆上下文，你会误判成"压缩机制不行"，然后去做更多无效的努力。

顺带把边界说清，避免另一种误读：本机实测 `~/.openclaw/openclaw.json`（45,662 字节）对 `compaction` / `effectiveReserveTokens` / `reserveTokens` / `reserveTokensFloor` / `contextTokenBudget` **全部 0 命中**（顶层 `session` 仅含 `dmScope`）。所以"用真名"的准确含义是——**别再用 v1.0 误植的字段名**；这不代表它是可写入 `openclaw.json` 的字段。相关表述属于**本书接口层口径**。

**怎么救。** 把真名当**文档事实**记录，而不是当参数。在 MEMORY 契约里写清三行：真名是什么、常量是多少、以及"不可配置"。然后在全组织范围内搜一遍 `reserveTokensFloor`，有残留就删——包括老文档、老脚本、老 RFC。

**怎么预防。** 把这条勘误写进团队的术语底座，并作为新人入职材料里的**第一个反例**。这类"防止全组织重复踩同一个坑"的条目，是记忆层中价值最高的一类：它节省的不是一次时间，而是**每个人的每一次**。

### 失真 3 · 把 Tools 和 Skills 当成"双协议"

**现象。** 在 TOOLS 契约里写一个 `skills:` 段，想一次管住工具和技能；或者对外文档写"我们采用 Tools + Skills 双协议架构"，被评审一句"主仓无此术语"顶回来。

**为什么错。** 真结构是**两个独立子系统 + 共享网关 RPC**：`tools.catalog` 与 `skills.status` / `skills.skillCard`。**主仓不存在"双协议"这一术语。**

职责上，Tool 是"能调用的**能力**"（网关端点），Skill 是"可加载的**知识 / 流程包**"（`SKILL.md` 文件系统）。塞进一段，你会同时管错两件事：改工具时的入口不对，加技能时的入口也不对。而且它会波及下游——`SKILL.md` + frontmatter + 注册表的整套机制会被提前搅浑，等真正读到技能注册那一章时，你的体系里已经有一个错误的"技能入口"了。

**怎么救。** TOOLS 只管工具；Skills 走独立链路。把"双协议"这个词从所有对外文档里清掉，改写成"工具与技能双模块 + 共享网关 RPC"。

**怎么预防。** 记住一句话：**能力归 Tools，方法论归 Skills。** 当你想在 TOOLS 里写"这套工具的使用步骤"时，停下来问一句——这是不是该做成一个 Skill？步骤型的内容天然属于 Skill 层；能力型的内容才属于 Tools 层。

### 失真 4 · 把 USER 契约当 Claude Permission API 的替代品

**现象。** 从 Claude Agent SDK 转过来的用户，把 `USER.md` 写成一堆运行时允许 / 拒绝规则，以为它能像 Permission API 一样在**调用时**拦截越权；结果智能体仍然越权调用了被禁止的工具——比如读了一个明确写着 `deny` 的目录。

**为什么错。** 层次不同。`USER.md` 是**文件级声明**（启动时加载），Claude 的 Permission API 是**运行时校验**（调用时校验）。两者**互补，不替代**。

核心认知可以压成四个字：**声明 ≠ 强制**。写"deny: network"只是声明意图；如果宿主 / 网关层没有对应的强制点，智能体依然可以联网。把安全边界寄托在一份 Markdown 上，是"看起来有安全设计、实际零防护"的典型假安全——而假安全比"明确知道自己没有安全设计"更危险，因为它会让人停止追问。

**怎么救。** 双层双写：声明层（USER 的 `permissions` / `data_scope`）写意图与范围；执行层（宿主工具白名单 / 黑名单）落强制。然后做一次**越权实测**：让智能体尝试越过边界（例如读一个不在 `data_scope` 里的目录、或尝试联网），确认它真的被拒绝。没有实测过的安全边界，等于没有边界。

**怎么预防。** 把"声明层 + 执行层"写进团队的安全检查清单，规则是：**任何安全条款，都必须回答"它的强制点在哪一行配置上"**。回答不出来的条款，标记为"装饰性条款"，要么补强制点，要么删掉——留着它只会制造虚假的安心。

### 失真 5 · SOUL 被改后没有回滚路径

**现象。** 同事（或某个自动工具）改了 `SOUL.md`，人格"变味"；你想回滚，发现没有 Git、没有备份、没有历史版本，连"之前长什么样"都拿不出来。

**为什么错。** SOUL 是**漂移检测的锚点**——周期性体检要 diff 当前 vs 初始。**没有历史，diff 无从谈起**，漂移治理的第 0 步就不存在。

后果是隐性且严重的：一个原本"不确定就标 ⏳"的智能体被改成"自信满满"，你可能三周后才发现——中间它已经输出了大量不可靠的结论，而那些结论很可能已经被用进了真实决策。这类损失无法追溯、无法撤销。

**怎么救。** 立刻把契约目录纳入 Git，提交当前状态并打一个基线 tag。同时诚实地接受一个事实：**最初版本已经找不回来了**。把当前版本作为新基线，从这一刻起开始积累历史。

**怎么预防。** 契约目录创建时的**第一个动作**就该是 `git init` + 基线 tag，而不是"等有空再说"。把"改动前建分支 / tag、改动后立即 commit"写进纪律。周期性体检里固定加一项：当前哈希 vs 基线哈希。

### 失真 6 · IDENTITY 缺失，智能体不知道"我是谁的下属"

**现象。** 建了其余六个文件，嫌 IDENTITY 多余就没建；结果多智能体场景下路由错人、信任评分没有分档依据、跨组织协作时无法声明归属，对方问"你是哪个组织的、你代表谁"，答不出来。

**为什么错。** IDENTITY 是**路由与信任的输入**：`agent_id` / `owner_org` / `trust_tier`。缺了它，信任评分没有分档依据；多智能体协同无法判断"谁是谁"；A2A 式的对外握手没有主体——握手的本质就是交换身份，没有身份就无法握手。

**怎么救。** 补建 IDENTITY 的三个关键字段，并做一次 `agent_id` 去重检查。但必须同时承认：**补建容易，补历史难**。这段时间里智能体做的所有事都没有身份锚点，无法归因；你能补上文件，补不上那段时间的责任链。

**怎么预防。** 把"七个文件齐备 + 每文件至少一个非空关键字段"作为 onboarding 的硬性检查项。不要接受"以后再加"——IDENTITY 是那种一旦缺了就静默损失归因能力的东西，你不会有任何痛感，直到某天需要追责。

### 失真 7 · 多个角色共享同一份 SOUL，人格互相串味

**现象。** 为省事把十几个智能体的 `SOUL.md` 全部软链到同一个文件（或直接复制同一份内容）；结果审计型角色开始"乐观鼓励"，创意型角色开始"谨慎拒绝"，人格边界混乱，你甚至分不清哪句是哪个角色说的。

**为什么错。** SOUL 是"**我是谁**"，不是"我们是谁"。每个角色的 `persona` / `values` / `tone` 本就应当不同——审计与创意对"什么算好答案"的判断，本来就该相反。共享一份，等于取消了个体边界。

而且串味会**污染治理**：信任评分按智能体分档，人格混同后评分失去区分度；响应让渡协议依赖"谁更该答"这个判断，人格混同则无从判断。人格问题往往在"出事那天"才暴露——某智能体用错误的语气对外发言，你才发现它一直在用别人的 SOUL。

**怎么救。** 每个智能体恢复独立 SOUL。把真正需要共享的部分抽出来，作为一份很小的"价值观基线"文件，让各角色的 SOUL 去**引用**它——注意是引用，不是软链。

**怎么预防。** 体检里固定加两项：一是检测 `SOUL.md` 是否为符号链接（危险信号）；二是检查各 SOUL 的 `persona` 是否唯一（每个 persona 的计数应当都是 1）。

### 失真 8 · 编码 / 换行问题导致"写了不生效"

**现象。** 文件明明写了内容、字段名也对，但智能体就是读不到；用编辑器打开"完全正常"，用 `file` / `hexdump` 一看才发现是 UTF-16、或 CRLF 混合、或带 BOM。

**为什么错。** Markdown + YAML frontmatter 对编码敏感。解析器遇到 BOM 或异常编码时，可能静默失败，导致整份文件被判为"无有效 frontmatter"。跨机（在 Windows 上编辑、在 macOS 上使用）会放大这个问题。

这类问题最难排查，因为它"看起来完全正常"。新人的第一反应通常是"系统有 bug"，于是把时间花在最不该花的地方。

**怎么救。** 统一为 **UTF-8 无 BOM + LF**。去 BOM、把 CRLF 换成 LF，然后重跑一次加载检查。

**怎么预防。** 把编码检查放进 onboarding 脚本；体检里加两项：是否存在 CRLF、是否存在 BOM。如果团队跨平台协作，把"保存为 UTF-8 / LF"写进编辑器约定。

### 失真 9 · 只建空文件，不填字段

**现象。** 按流程建了 7 个 `.md`，`ls` 一看 7 个文件都在，收工。两周后发现行为毫无变化，回来一看：7 个文件全是 0 字节。

**为什么错。** "文件齐了 = 配好了"是一个心理错觉。建文件有"看得见的成果"（7 行输出），填字段没有；而空文件不报错，所以也**没有反馈信号**告诉你"还没配完"。

后续会全部错位：漂移检测要求 SOUL 有可 diff 的内容；信任评分要求 IDENTITY 有档位；"智能体不主动"时你会去查心跳是不是坏了，其实只是心跳文件是空的。你会一直在错误的层找原因。

**怎么救。** 用"空文件判定"找出 0 字节文件，逐个填**最小字段集**：SOUL 至少 `persona`；USER 至少 `owner`；AGENTS 至少一个子智能体或一条纪律；TOOLS 至少一条实测映射；HEARTBEAT 至少 `interval`；IDENTITY 至少 `agent_id`；MEMORY 至少一条分层说明。

**怎么预防。** 把"每份契约至少一个非空关键字段"写进检查清单，并在每次改动后跑一遍。这个检查一秒就能跑完，能省掉两周的困惑。

### 失真 10 · 认为协议是"配一次就完事"的静态文件

**现象。** 把 7 契约配好，从此不再动。半年后 MEMORY 膨胀、SOUL 漂移、HEARTBEAT 失效、工具清单里全是不存在的工具，而当事人完全不知道——因为从来没有"回看协议"的习惯。

**为什么错。** "配置"这个词的心理暗示就是"一次性的"，配完就丢在一边。但协议文件不会自己报警：它不跑、不报错、不通知，**静静腐烂**。

而长期运行的智能体一定会漂——这是系统性的，不是意外。每一次合理的局部妥协，累积起来就是一个方向的错。不做周期性回看，你会在某天突然发现"它已经完全不是它了"，而且找不出是哪一天开始的。

**怎么救。** 把"协议回看"变成心跳任务：每周一次契约漂移 diff、一次记忆行数检查、一次工具 / 能力清单盘点。把结果落盘形成体检记录，让"回看"这件事本身也有证据。

**怎么预防。** 建立"每周体检清单"制度，其中必须包含"7 契约 diff"这一项。同时把协议当**活文档**：任何业务变更都要同步改契约，这条规则写进 AGENTS 的操作纪律里——不要依赖任何人的记性。

### 十种失真的共同根源

把十种失真放在一起看，会浮现出同一个根源：

> **契约层的失败是静默的，而人类只对报错敏感。**

所以本章的全部方法论，最终都指向同一个动作：**把静默变成可见。**

- 用**哈希**把"变了"变可见。
- 用**空文件判定**把"没配"变可见。
- 用**文件名检查**把"没加载"变可见。
- 用**真名勘误**把"假配置"变可见。
- 用**越权实测**把"假安全"变可见。
- 用**persona 唯一性检查**把"人格串味"变可见。
- 用**编码检查**把"看起来正常"变可见。

这也是本训练学与"提示词工程"最根本的分野：

> **提示词工程优化的是这一次的产出；协议工程管理的是长期的可见性。**

前者的成果随会话蒸发；后者的成果——哈希、基线、报告、账本——会留下来，成为下一个人的起点。

### 十种失真 · 快速对照

> 用途：作为每一次契约改动之后的**一遍过筛**。左列是信号，右列是要去核的位置。

| # | 危险信号（你观察到的） | 根因位置 | 一句话处置 |
|---|---|---|---|
| 1 | 文件在，行为却像没配 | 文件名 / 位置 | 改回标准英文名，确认加载路径 |
| 2 | 改了压缩相关设置，行为没变 | 字段名是 v1.0 误植 | 换回 `effectiveReserveTokens`，并写下"不可配置" |
| 3 | 工具和技能在一个段里管 | "双协议"旧表述 | 拆成 Tools 与 Skill 两条链路 |
| 4 | 写了 deny，仍然越权 | 只有声明层，没有强制点 | 在宿主侧补 deny，再做一次越权实测 |
| 5 | 人格变了，回不去 | 没有 Git、没有基线 | 立即建库打基线，承认旧版本已丢失 |
| 6 | 路由错人 / 分档无依据 | IDENTITY 缺失 | 补三字段，做 id 去重 |
| 7 | 不同角色说话像一个模子 | SOUL 被软链共享 | 每人独立 SOUL，共享改用引用 |
| 8 | "看起来完全正常"却不生效 | 编码 / 换行（BOM / CRLF） | 统一 UTF-8 无 BOM + LF |
| 9 | 七个文件都在，毫无反应 | 全是 0 字节 | 逐文件填最小字段集 |
| 10 | 半年后集体腐烂 | 从未回看 | 把漂移检查写进心跳 |

**读法提示。**

- 第 1、8、9 行属于"契约根本没进去"——先修这一层，再看别的，否则后面所有排查都是白费。
- 第 2、3、4 行属于"配了一个不生效的东西"——它们的共同点是**没有报错**，因此只能靠主动核对。
- 第 5、10 行属于"没有历史"——它们不直接造成事故，但决定了事故能否收场。
- 第 6、7 行属于"多主体场景的收入税"——单机时看不出问题，一旦有第二个参与者就立刻显形。

**一条通用处置原则。**

> **先确认"是否加载"，再确认"是否生效"，最后才怀疑"机制本身"。**

这个顺序能挡掉本章十种失真里的九种。人们最常做错的是反过来：一上来就怀疑机制，于是把时间花在修改一个从未被读到过的文件上。

### 失真的传染路径：为什么它们总是成组出现

单独看十种失真，它们像十个互不相干的意外。但真实事故记录里，它们几乎从不单独出现——**它们成组发生，而且有固定的传染顺序。**

看清这条传染链，比逐条防住更有价值，因为它让你能在第 1 环就切断。

**第一环：命名与位置出错（失真 1 / 8 / 9）。** 起点几乎总是三者之一：文件名用了中文、编码带了 BOM、或者文件是空的。它们的共同后果是**契约根本没有进入上下文**。此时智能体的行为与文件无关，但它照样能答得头头是道——这是最危险的阶段，因为**你看到了成果，也就失去了排查动机**。

**第二环：假配置出现（失真 2 / 3 / 4）。** 由于第一环已经让你相信"我配过了"，第二环的行为就顺理成章：你会开始去调参数。于是 `reserveTokensFloor` 出现了，`skills:` 段出现了，`deny` 写进了 USER 而没有任何强制点。这三者的共同结构是**你调整了一个不生效的东西**——而且没有报错能提醒你。

**第三环：静默失效被误判成能力问题（失真 2 / 4）。** 到了这里，事故开始产生"错误的结论"。压缩没生效 → "OpenClaw 的压缩机制不行"。越权没被拦 → "模型不听话"。请注意，这些结论**每一个都听起来合理**，因为你确实做了该做的事，只是做的事无效。这就是假配置最深的伤害：它不是让你失败，而是让你**在错误的层面上归因**。

**第四环：省事导致人格污染（失真 7 / 6）。** 前三环消耗了耐心，到了这一步，"省点事"就开始占上风。软链共享 SOUL 是最典型的——它省下的是一次编辑，付出的是整支队伍的人格边界。IDENTITY 的缺失也是同一类：它不是"忘了"，而是"觉得不用"。

**第五环：放弃治理（失真 5 / 10）。** 最后一环是彻底的：因为从未版本化（失真 5），也从未回看（失真 10），所以前三环里发生的每一次错误改动**都没有留下痕迹**。此时你想修，连"从哪个版本往回退"都不知道。事故到此从"可以修"变成"只能整体重做"。

**这条链的两个断点。** 好消息是，这条链上有两个高效的断点：

- **断点一（在第 1 环末端）**：一次"文件名 + 编码 + 非空"的三项体检。它一秒能跑完，却能同时切断失真 1、8、9。
- **断点二（在第 4 环之前）**：一次 `git init` + 基线 tag。它不能阻止错误发生，但它保证**所有错误都可回退**——而这正是把"事故"降级为"改动"的全部秘密。

**为什么把它写进本章。** 因为本章的读者最容易犯的一个整体性误判是：**把契约层当成一次性的配置任务。** 一旦你把它当成"配一次"，上面那条链就会自动开始运行——它不需要你做错任何一件"大事"，只需要你在每一环都做一个"省事的小选择"。

所以本章的结论可以再压缩一次：

> **契约层的成熟度，不体现在你配了什么，而体现在你留了什么痕迹、以及你能不能回到上一个版本。**

这句话是十种失真的反面，也是本章全部方法论的终点。

## 五、深度专题

### 专题一 · 前沿追踪（2026）：协议层的三条外部战线

本章讨论的 7 个契约是 OpenClaw 的内部装置。但在 2025–2026 年，整个行业在**外部协议层**上发生了三件大事，它们直接改写了"契约层应该在什么坐标系里被理解"。不理解这三件事，你会把本章读成一个孤立的系统设计；理解了，你会看到它正处在一条行业主航道上。

#### 1. MCP 的无状态化：2026-07-28 规范

Model Context Protocol（MCP）在 2026 年迎来发布以来**最大的一次修订**。当前协议版本为 **2026-07-28**（2026-05-21 发布 release candidate，2026-07-28 成为 Current）。完整版本序列是：`2024-11-05` → `2025-03-26` → `2025-06-18` → `2025-11-25` → `2026-07-28`。

这次修订的三条关键变化：

- **移除 `initialize` / `initialized` 握手**（SEP-2575）。协议版本、客户端身份、客户端能力改为随**每一个请求**在 `_meta` 中携带。
- **移除 `Mcp-Session-Id` 头**（SEP-2567）。协议级会话被取消，**任何 server 实例都能处理任何请求**——不再需要粘性会话、共享会话存储、网关深包检测。新增 `server/discover` RPC，用于按需获取 server 能力（非必需）。
- **引入 Multi Round-Trip Requests（MRTR）**，配合 `InputRequiredResult`，让 server 可以在执行中途请求额外输入，而不必维持长连接。同时 **Roots / Sampling / Logging 被弃用**，授权改为要求 issuer 授权元数据。

为什么这对本章重要？因为它把"**工具契约的传输层**"彻底简化了：工具从"有状态连接上的对象"变成"无状态请求里的一份能力声明"。这与契约 4（TOOLS）的设计哲学同向——**能力是声明出来的，不是维系出来的**。

同时它也带来一个新的治理问题：当任何请求都能落到任何实例上时，**"谁在调用"这件事必须由请求自身携带**（`_meta` 里的 client identity）。这恰恰是契约 1（USER）与契约 6（IDENTITY）要回答的问题在协议层的对应物。

> ⏳ 待验证：MCP 各 SDK（TypeScript / Python / Go / C#）对 MRTR 的具体实现细节与迁移成本，需按你所用的 SDK 版本单独核实。Tier 1 SDK 官方称在 2026-07-28 当日同步支持。

#### 2. A2A 的治理移交：v1.0 → Agentic AI Foundation

Agent2Agent（A2A）协议在 2026 年走完了一条从"厂商倡议"到"行业标准"的完整路径：

- **2026-04-09**：A2A **v1.0** 规范在 Linux Foundation 治理下发布；同期宣布 **150+ 组织**支持，并在 Google、Microsoft、AWS 平台上深度集成，供应链、金融服务、保险、IT 运维等行业已有生产部署。
- **2026-08-17**：A2A 从 Linux Foundation 的通用项目组合移入 **Agentic AI Foundation（AAIF）**——一个专为 agentic AI 标准建立的基金会。**A2A 与 MCP 现在同属一个屋檐**，同处其中的还有 `goose` 与 **`AGENTS.md`**。
- AAIF 的成员从 2025 年 12 月成立时的不足 40 家，增长到 2026 年 8 月的 **250+ 家**。

这里有一条对本章**极其关键**的事实：**`AGENTS.md` 是一个被 AAIF 托管的标准文件格式。**

这意味着一件此前难以想象的事：本章的契约 3（AGENTS）不再只是一个产品内部约定，它对应的**文件格式已经在行业层被标准化**。你写的那份 `AGENTS.md`，在概念上与全世界其他工具读的 `AGENTS.md` 是同一个物种。多智能体协作的"任务交接"语义（对应本书的任务交接协议（Task Handoff Protocol, THP，原：交接棒协议））也因此有了跨框架的公共词汇。

同时也需要保持清醒：Linux Foundation 的报告中**没有公布实际部署数量**，而 A2A 与 MCP 在功能上有重叠（有分析指出 A2A 宣称的部分能力——如状态化任务处理、agent 发现——已被 MCP 或其他机制覆盖）。所以正确的姿态是：**把 A2A 视为"对外协作层"的标准候选，而不是把内部编排也必须迁到 A2A 上。**

> ⏳ 待验证：A2A v1.0 规范的完整字段集与各平台实现差异，建议按 a2a-protocol.org 的当前版本核实，不要以本段概述作为实现依据。

#### 3. Anthropic Agent Skills：从 SKILL.md 到开放标准

2025 年 10 月，Anthropic 推出 **Agent Skills**（社区通常称 Claude Skills）；**2025-12-18**，把它作为**开放标准**发布在 `agentskills.io`，规范与 SDK 面向任何 AI 平台开放。

这套规范的核心设计原则是**渐进式披露（progressive disclosure）**：

1. **元数据（约 100 tokens）**：`name` 与 `description` 在启动时对所有 skills 加载——这是唯一的常驻成本。
2. **指令（建议 < 5000 tokens）**：`SKILL.md` 正文在**技能被激活时**才加载。
3. **资源（按需）**：`scripts/` / `references/` / `assets/` 下的文件只在需要时才读。

规范细节（`agentskills.io/specification`）：

- `SKILL.md` 必须含 **YAML frontmatter + Markdown 正文**。
- `name`：小写字母、数字、连字符，遵循 **`verb-ing + noun`** 模式，不超过 **64 字符**；不得使用 `claude` / `anthropic` 等保留字。
- `description`：不超过 **1024 字符**，必须同时写清"做什么"与"什么时候用"，并包含触发关键词——**因为这是 agent 决定是否加载技能的唯一依据**。
- 正文建议保持 **500 行以内**，更长的参考材料拆到独立文件。

生态上，到 2026 年 6 月，官方 `agentskills.io` 展示页上已有约 **40 个兼容产品**（包括 OpenAI Codex、GitHub Copilot、Cursor、Gemini CLI、VS Code 等）；Anthropic 也在 **2026 年 2 月**为 Team / Enterprise 计划加上了组织级 skills 管理（管理员可集中配置与默认启用）。

**为什么这一条必须放进本章？** 因为它与本章的契约层构成了一个非常清晰的分工，而这个分工恰恰是 2026 年才成型的认知：

- **契约层（SOUL / USER / AGENTS / …）回答"我是谁、我为谁服务、我的边界在哪"**——它必须**常驻**，因为它是身份的组成部分。
- **Skill 层（`SKILL.md`）回答"这件事怎么做"**——它必须**按需加载**，因为知识是无限的，而上下文是有限的。

Anthropic 把上下文窗口称为"公共资源（public good）"：你放进去的越多，token 消耗越快，上下文退化越快。这个判断与本章"SOUL 不能写一千行""MEMORY 必须修剪"的结论，在原理上是同一件事。

但同时要划清边界：**不要把 Skills 当成契约**。Skill 是方法论的载体，不是身份的载体；一个 SKILL 被删掉，人格不应该变。

#### 4. 一个跨框架的观察：所有框架都在"从 prompt 走向文件"

把三条战线合起来看，会看到一个共同的趋势：

- MCP 把工具能力从"连接状态"改成"**请求内的声明**"。
- A2A / AAIF 把协作语义沉到**标准文件与规范**里（其中就包括 `AGENTS.md`）。
- Anthropic Skills 把可复用方法论沉到**磁盘上的 `SKILL.md`**，靠渐进披露控制上下文成本。

三条线讲的是同一句话：

> **Agent 的长期行为，不靠运行时堆提示，而靠磁盘上的持久声明。**

这与本章的主判断完全同构。区别只在于坐标：行业把这种"持久声明"拆散在各个标准里，而 OpenClaw 的做法是把它**收敛成 7 个文件、一次启动加载**。

> ⏳ 待验证：MCP `2026-07-28` 之后是否已有下一版 RC；A2A 与 AGENTS.md 在 AAIF 中的具体治理章程（working group 结构、发布节奏）。

### 专题二 · 业界对位：6 大框架逐项对照

本节把本章的 7 个契约放到 6 个主流框架/技术栈里逐项对照。用途有两个：一是判断"这条契约业界到底有没有"；二是判断"我在别处已有的资产，迁移到这套契约体系时缺什么"。

对照对象：**LangGraph / AutoGen / CrewAI / Claude Agent SDK / OpenAI Agents SDK / LlamaIndex**。

#### 2.1 逐项对位表

| 契约 | LangGraph | AutoGen（→ Microsoft Agent Framework） | CrewAI | Claude Agent SDK | OpenAI Agents SDK | LlamaIndex | OpenClaw 原生 |

**一句话读法。** 6 个框架里，**没有一个覆盖 7 个契约中的 6 个以上**。缺口最集中的三行是 **1（USER 的启动时声明）、5（HEARTBEAT）、6（IDENTITY）**——这不是巧合，而是"库/框架"与"运行系统"两种物种的差别：框架管**一次执行怎么组织**，运行系统还要管**一个存在怎么长期维持**。

#### 2.2 6 个框架各自侧写（2026 版）

**LangGraph（状态化编排的生产标准）。** 2026 年它的定位已经很明确：**有状态、可审计的 agentic 工作流**的生产标准。它的强项是图结构表达、检查点（checkpointing）、时间旅行式调试（time-travel debugging）与节点级 token 流式输出。它的对位最集中的是契约 3（编排）与契约 7（状态持久化）——但它的"记忆"是**运行状态**意义上的，不是"经验沉淀"意义上的。

值得注意的一点：**LangGraph 没有内置心跳**。要做周期任务，必须外部 cron / 调度器提供唤醒。这意味着从 LangGraph 迁移到契约体系时，**契约 5 是从零新建的**，而不是"改写已有的"。

**AutoGen（已进入后 AutoGen 时代）。** 到 2026 年，AutoGen 已进入维护模式；微软把 AutoGen 与 Semantic Kernel 合并为 **Microsoft Agent Framework**，并于 **2026-04-03 GA（v1.0，MIT，LTS 承诺，A2A 与 MCP 原生，.NET / Python 双优先）**，AutoGen 的概念被整合进新的图工作流引擎。因此做契约对位时必须明确：**AutoGen 的"多智能体对话/辩论"能力 ≈ 契约 3 的一个特例**，而它没有契约 1 / 5 / 6 的任何原生对应物。如果你现在还在 AutoGen 上，规划迁移路径是必要动作。

**CrewAI（最快原型，最重 token）。** CrewAI 的定位是"**最快拿到可工作的多智能体原型**"（有报告称 2–4 小时量级），核心抽象是 role / goal / backstory 的团队（Crew）与任务（Task）。**它的 role / goal / backstory 是 6 家里最接近契约 2（SOUL）的**——这是一种极有价值的"人格化编程"思路。但要客观：独立基准显示出 CrewAI 在简单任务上的 token 占用显著偏高（有报道称单工具调用流程约为其他三家的 3 倍），且检查点能力相对有限。用它做契约对位时，**契约 2 是唯一可以较好平移的**，其余的仍要从零建。

**Claude Agent SDK（安全与工具生态的标杆）。** Claude Agent SDK 的对位面很清晰：Permission API ↔ 契约 1（但是**运行时**授权，与文件级声明是互补而非替代）、persona ↔ 契约 2、subagent task spec ↔ 契约 3、tools ↔ 契约 4、memory ↔ 契约 7。它是 6 家里覆盖最广的（有评估认为按能力重叠度可达 8 成），也是最强调安全边界的。它的缺口是：**没有 HEARTBEAT（主动性原语）与 IDENTITY（身份原语）**，而且它的记忆是**运行时记忆管理**，与 OpenClaw 的**文件模板**不是同一种东西。

**OpenAI Agents SDK（最简抽象 + handoff）。** 该 SDK 于 2025-03-11 发布，**2026-04-15** 的更新（"The next evolution of the Agents SDK"）加入**原生沙箱执行**与面向长任务的 **model-native harness**；Assistants API 计划在 2026 年中弃用。它的强项是 **handoff**（跨 agent 交接，语义上更接近本书的任务交接协议 THP）、内置 tracing / guardrails，以及对 **MCP 与 `AGENTS.md` 的一等支持**。一个很说明问题的设计取向：**它明确不带记忆**——官方立场是"自带记忆"（bring your own）。这在契约视角下等于承认：**记忆是独立层，不是编排框架的职责**。

**LlamaIndex（数据与检索侧的最强对位）。** LlamaIndex 与本章的接口面主要在契约 7：但它对位的是**索引、检索与数据连接**，而不是**记忆策略**。换句话说，LlamaIndex 回答"怎么把知识找出来"，契约 7 回答"什么该被长期记住、什么时候压缩"。两者可以叠加，不可互相替代。

#### 2.3 从对位表能读出的三个结论

**结论一：缺口集中在"长期存在"的三行。**

USER（启动时声明）、HEARTBEAT（主动性）、IDENTITY（身份）是 6 家共同的缺口。有意思的是，这三行恰好都**不是**关于"一次任务怎么做得好"，而是关于"一个存在怎么被长期维持"。这说明行业框架的设计重心一直在**执行层**，而契约体系的重心在**存在层**。

**结论二：文件级加载是结构性差异，不是优化。**

6 家里最接近的是 Claude Agent SDK，但它的边界机制是**运行时 API**。契约体系是**启动时文件级声明**。这不是"实现得更早/更晚"的问题，而是两种模型：

- 运行时校验：**强**（能真正拦截），但**只在运行时存在**，脚本外无痕迹、无版本、无 diff。
- 文件级声明：**弱**（只是声明），但**可版本化、可 diff、可审计、可跨会话**。

所以正确的结论不是"二选一"，而是**双层都要**：文件级声明负责长期一致性与可治理性，运行时校验负责真正的强制。这一点与失真 4 是同一件事的两个面。

**结论三：契约层是"跨框架可携带"的部分。**

如果你今天用 LangGraph，明天换 CrewAI，后天用 Claude Agent SDK——模型换了、编排换了、工具换了，但**你的 SOUL / USER / AGENTS / IDENTITY / MEMORY 是可以带走的**。

这就是本章开头那句话的完整含义：**第一世界（引擎）是别人的，第三世界（产物）是易变的，只有第二世界（协议）是你的资产。**

### 专题三 · 契约层与 Skill 层：2026 年出现的第二契约文明

这是本章最"新"的一个专题，也是只在这一年才可能被写出来的一节，因为它依赖专题一里那三条外部战线的成型。

#### 3.1 一个被反复混淆的问题

随着 Anthropic Agent Skills 成为开放标准，一个高频问题出现了：

> **既然 `SKILL.md` 能写"你是谁、你要怎么做"，那它和 SOUL / AGENTS 有什么区别？我是不是可以把人格写进 Skill 里？**

答案是：不可以。而且这个"不可以"背后有一条清晰的判据。

#### 3.2 判据：常驻性 vs 按需性

把两类文件按**上下文成本结构**排一下，结构一目了然：

- **契约层**：启动时**全量加载**，常驻上下文。它的成本是**固定的**（你写多少就占多少），收益是**身份一致性**。
- **Skill 层**：启动时只加载 `name` + `description`（约 100 tokens / 个）。正文在被激活时才加载。它的成本是**可扩展的**（100 个 skill 也只有约 1 万 tokens 的常驻元数据），收益是**方法论的按需供应**。

这条成本结构直接给出了判据：

> **凡是"每次都该生效"的，进契约层；凡是"特定任务才需要"的，进 Skill 层。**

- "我不编造数字"——每次都该生效 → **契约**（SOUL）。
- "怎么用 pandas 处理这份宽表"——特定任务才需要 → **Skill**。
- "我的用户讨厌'收到/在做/稍后同步'"——每次都该生效 → **契约**（USER / AGENTS）。
- "怎么写一份符合我们模板的周报"——特定任务才需要 → **Skill**。

#### 3.3 契约层的不可让渡性

为什么"人格不能进 Skill"？有三个理由，每个都独立成立：

**理由一：渐进披露会把人格变成不确定的。** Skill 的整个设计前提是"**可能不加载**"——它由 agent 根据 `description` 决定是否激活。人格一旦进了 Skill，就意味着**某些时候智能体不是它自己**。这在身份层面是不可接受的：价值观不能是"这一次可能生效"的东西。

**理由二：人格需要锚点与 diff，Skill 不需要。** 契约层要承担漂移检测的职责（当前 vs 基线）。Skill 的版本管理是**功能演进**意义上的（这一版加了什么步骤），不是**身份漂移**意义上的。把两者混在一起，你会得到一份既不能做基线 diff、也不能做功能回滚的四不像。

**理由三：Skill 可以删，人格不能删。** 一个 Skill 过时了、有 bug 了、被更好的替代了——删掉它，智能体应该毫发无损。如果删掉一个文件会让智能体"性格变了"，那这个文件就不是 Skill，它是契约（而且放错位置了）。

反过来也成立：**别把方法论文档放进契约层**。AGENTS 里写进"处理 Excel 的五步骤"，会让 AGENTS 越写越长（吃上下文）、越来越难 diff（漂移检测被稀释），而且每次任务都会加载一段这次用不上的内容。**这是"契约层污染"，也是 SOUL 写成一千行的最常见成因。**

#### 3.4 三层结构：一个可复用的心智模型

把 2026 年的这套格局收敛成一个三层模型，它可能是本章最有迁移价值的东西：

| 层 | 载体 | 加载时机 | 回答的问题 | 成本结构 | 版本语义 |
|---|---|---|---|---|---|
| **身份层** | 7 契约（`SOUL.md` 等） | 启动时**全量**加载 | 我是谁、为谁服务、边界在哪 | 固定 | 身份漂移（需基线 + diff） |
| **方法层** | Skills（`SKILL.md`） | 元数据常驻，正文**按需** | 这件事怎么做 | 可扩展（渐进披露） | 功能演进（可增删） |
| **能力层** | Tools / MCP server | 由运行时/网关管理 | 我能调用什么 | 由宿主配置 | 接口版本（向后兼容性） |

这三层分别对应本章的契约层、行业新标准（Anthropic Skills）、以及 MCP 演进线。它们的边界不是学术问题——**放错层的东西，会以静默的方式污染整个系统的长期行为**：

- 身份进方法层 → 人格变得不确定。
- 方法进身份层 → 契约膨胀、漂移检测失效。
- 能力混进身份层 → 你把"权限声明"当成了"权限强制"（失真 4）。

#### 3.5 一个务实的收束

对 2026 年的实践者，本节的可执行含义其实很简单：

- **契约层要短、要稳、要版本化。** 它的价值来自长期不变。
- **方法层要多、要模块化、要按需加载。** 它的价值来自覆盖广度。
- **能力层要最小授权、要能强制、要可盘点。** 它的价值来自安全与可控。

而三者之间的唯一粘合剂，是本章反复出现的那条判据：

> **这句话，是"它每次都该是这样"，还是"做这件事的时候该是这样"？**

第一句进契约，第二句进 Skill，第三句进工具配置。

### 收束 · 从 2026 前沿读出的三条结论

把专题一（外部协议的三条战线）、专题二（6 框架逐项对位）、专题三（契约层与 Skill 层的分工）放在一起，可以收敛出三条对实践者真正有用的判断。

**结论一 · 契约层是"存在的层"，不是"执行的层"。**

6 个主流框架在契约 1（USER 的启动时声明）、契约 5（HEARTBEAT）、契约 6（IDENTITY）上普遍缺失。这三行有一个共同点：**它们不回答"这次任务怎么做好"，而回答"一个存在怎么被长期维持"。**

行业框架的设计重心一直在执行层——这很正常，因为框架的客户是"要跑一个流程"的开发者。但一旦你把智能体当成长期协作的成员，执行层的完备就突然不够了：它不会主动、它没有身份、它不知道自己在为谁服务。这就是本章为什么把这三条列为"宪法"而不是"可选优化"。

**结论二 · 双层都要：文件级声明 + 运行时强制。**

MCP 的无状态化（2026-07-28）说明了一件事：协议层正在把"状态"从连接里赶出去，让每一份能力与每一次请求自带上下文。这与契约体系"启动时加载、文件级声明"的取向同向，但它也提醒了一件事——**MCP 仍然需要授权元数据（issuer authorization）来强制边界**。

换句话说，行业在做的不是"二选一"，而是**声明层与强制层同时加厚**：文件级声明负责长期一致性与可审计，运行时校验负责真正的拦截。任何只做一层的方案，都会在某一类事故上失守（要么"看起来有安全设计实际零防护"，要么"拦得很死但没人说得清最初为什么这么拦")。

**结论三 · 资产在自己的第二世界里。**

专题二的结论可以被压缩成一句话：**引擎（模型）是别人的，产物是易变的，只有协议层是你的资产。**

你今天用 LangGraph，明天换 CrewAI，后天用 Claude Agent SDK——编排会变、工具会变、模型会变。但 SOUL / USER / AGENTS / IDENTITY / MEMORY 是可以**带走**的。它们是唯一一种**跨框架、跨模型、跨时间都仍然有效**的东西。

而 2026 年的三条外部战线（MCP / A2A-AAIF / Agent Skills）恰好从三个方向印证了同一个判断：

> **Agent 的长期行为，不靠运行时堆提示，而靠磁盘上的持久声明。**

区别只在于坐标：行业把这种"持久声明"拆散在各个标准里——工具走 MCP、协作走 A2A、方法走 Skills、协作文件格式走 `AGENTS.md`；而 OpenClaw 的做法是把它**收敛成 7 个文件、一次启动加载**。

收敛有收敛的代价（你要自己维护一致性、要做漂移治理），也有收敛的收益（你有一个统一的锚点，可以一次 diff 全部）。本章选择把收益讲透，把代价讲清：**这 7 个契约不是"配好就完"的脚手架，而是你需要长期照看的一份宪法。**

### 结语 · 为什么这七个文件值得被当成宪法

回到本章开头那个问题：**为什么我的 Agent 越用越不像它自己？**

现在可以给出完整答案了。不是模型不稳定，不是提示词不够长，而是**它在没有被定义过的地方，只能被最后一次交互定义**。而"被最后一次交互定义"这件事，在时间维度上等价于没有自己。

7 个契约的全部功能，就是在它身上装一个**不被最后一次交互推翻的东西**：

- SOUL 让它在压力下仍然是它。
- USER 让它始终朝向对的人。
- AGENTS 让它把一件事走完。
- TOOLS 让它知道自己在什么环境里、边界在哪。
- HEARTBEAT 让它在没人提醒的时候也在场。
- IDENTITY 让它的每一个动作都能被归因。
- MEMORY 让它的第 100 次比第 1 次更值钱。

把它们合起来看，你会发现这七个文件其实回答的是同一个问题的七个侧面：

> **一个存在，凭什么在时间中保持连续？**

这就是"宪法"这个词的全部含义。宪法不是用来执行的，宪法是用来**让人在偏离时有个东西可以对照**的。契约也一样：它不会替智能体做任何决定，它只是让"它偏离了"这件事**有据可依**。

而这也是本章在全书中被放在第 1 章位置的原因——**后面十章讲的治理、协同、记忆、演进，全部以"它有据可依"为前提**。没有这七个文件，后面的一切机制都无处落脚。

**下一步。** 有了契约层，下一个问题是：这七份文件在运行时嵌进了哪些子系统？它们被谁读、什么时候读、读完之后变成什么？这将是第 2 章 · 系统骨架要回答的问题。

## 常见错误

> **本节用法**：第 1 章的 7 个契约是全书的"宪法"——这里的错误 100% 会传染到第 2–11 章。

### 错误 1 · 用中文名命名 7 个契约文件

**错误现象**：读者按 v1.0 习惯把文件建成 `灵魂契约.md`、`用户契约.md`、`军团契约.md`；OpenClaw 启动时完全不读它们，agent 行为与配置文件毫无关联，且**不报任何错**。

**错误配置**（❌ 不要这样）：

```bash
# 错误示范：中文名文件
~/.openclaw/workspace/agents/my-agent/contracts/
├── 灵魂契约.md        # ❌ OpenClaw 不识别
├── 用户契约.md        # ❌
├── 军团契约.md        # ❌
├── 工具契约.md        # ❌
├── 心跳契约.md        # ❌
├── 身份契约.md        # ❌
└── 记忆契约.md        # ❌
```

**为什么错**：

1. **契约名是"接口"，不是"标题"。** 本章 1.1 节的表格明说：7 个契约的文件名是 `SOUL.md / USER.md / AGENTS.md / TOOLS.md / HEARTBEAT.md / IDENTITY.md / MEMORY.md`——这是 OpenClaw 启动时按**固定文件名**扫描的。
2. **术语对照表第 23 条已核实**：SOUL/USER/AGENTS/TOOLS/IDENTITY/HEARTBEAT/MEMORY 这 7 个名字是"与 OpenClaw 文件模板天然对齐"的、**业界无冲突**的，必须原样保留。中文名只能作为**注解**出现在文件内容里，不能作为文件名。
3. **失败模式是静默的。** 文件名不对，OpenClaw 不会报错，只会认为"该 agent 没有契约"。你会得到"配了但没生效"的诡异体验——这是本书反复强调的最危险失败模式。
4. **代价**：一旦用中文名起步，后面的 diff/体检/漂移检测全部基于错误的基线，整改成本随时间指数上升。

**正确配置**（✅ 应该这样）：

```bash

touch SOUL.md USER.md AGENTS.md TOOLS.md HEARTBEAT.md IDENTITY.md MEMORY.md
ls -1
# 期望：7 个英文名文件
```

```markdown
# SOUL · 灵魂契约（内部中文注解 OK，对外统一用 SOUL）
persona: "严谨的工程审计员，先给结论再给证据"
values: ["没有证据不下结论", "不确定就标 ⏳"]

```

### 错误 2 · 把 `compaction.reserveTokensFloor` 当真名去配（误植字段）

**错误现象**：读者从 v1.0 文档学到"把 `reserveTokensFloor` 设成 20000 就能控制压缩预算"，照着写进 MEMORY 配置，结果压缩行为完全没变——因为该字段**根本不存在**。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：基于 v1.0 误植字段
# MEMORY.md
compaction:
  reserveTokensFloor: 20000     # ❌ 该字段不存在
  maxReserveRatio: 0.25         # ❌ 拼写也非真名
```

**为什么错**：

1. **真名已核实。** 术语对照表第 31 条 + 本章 1.2 契约 7：`reserveTokensFloor` **不存在**；真名是 `effectiveReserveTokens`（= contextTokenBudget × 0.25 上限），常量 `MAX_COMPACTION_RESERVE_RATIO = 0.25`，且**字段不可配置**。
2. **"不可配置"是关键信息。** 不是"换个名字配"，而是**这个预算由 OpenClaw 主仓常量决定，你配不了**。v1.0 说"可配 20000"是错的。
3. **静默忽略。** 写了不存在的字段，OpenClaw 不报错、不警告，照常运行——你以为配了，其实没有。
4. **代价**：你以为在做压缩调优，实际上所有"优化"都是幻觉；一旦会话真的爆上下文，你会误判成"OpenClaw 压缩机制不行"。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：写清"不可配置"，把真名当文档记录，而不是当参数
# MEMORY.md
# 真名（术语表 #31）：effectiveReserveTokens + MAX_COMPACTION_RESERVE_RATIO = 0.25
# 注意：该预算由 OpenClaw 主仓常量决定，字段不可配置。
compaction_policy:
  effectiveReserveTokens: "auto (main-repo constant, NOT configurable)"
  MAX_COMPACTION_RESERVE_RATIO: 0.25
```

```bash
openclaw doctor 2>&1 | grep -i "config\|schema\|unknown" | head -10
```

### 错误 3 · 把 Tools 和 Skills 当成"双协议"

**错误现象**：读者在 TOOLS.md 里写 `skills:` 段，想同时管工具和技能；或对外文档写"OpenClaw 采用 Tools+Skills 双协议架构"，被评审指出"主仓无此术语"。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：把两个独立子系统当成一个"双协议"
# TOOLS.md
tools_and_skills_protocol:      # ❌ 无此概念
  tools: [...]
  skills: [...]
```

**为什么错**：

1. **真结构是两个独立子系统 + 共享 RPC。** 术语对照表第 20/32 条：主仓无"双协议"术语；真结构是 `tools.catalog` + `skills.status` / `skills.skillCard`，两者通过**共享 Gateway RPC** 交互。
2. **职责不同，不能混着配。** Tool 是"agent 能调用的能力"（网关端点），Skill 是"agent 可加载的知识/流程包"（`SKILL.md` 文件系统）。把两者塞进一个段，你会同时管错两件事。
3. **错误配置会波及第 10 章。** Skill 注册（第 10 章）讲的是 `SKILL.md` + frontmatter + Registry；如果 TOOLS.md 里已经"接管"了 skills，第 10 章的整套机制就被你提前搅浑了。
4. **对外术语代价**。写在 RFC 里会被质疑（"主仓哪有双协议？"），返工重写。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：TOOLS.md 只管工具；Skills 单独走第 10 章
# TOOLS.md
tools:
  - name: "mcp.filesystem"
    gateway_rpc: "tools.catalog"     # 真名（术语表 #32）
```

```markdown
<!-- Skill 走独立链路：SKILL.md + frontmatter，详见第 10 章 -->
<!-- 真名端点：skills.status / skills.skillCard -->
```

**验证命令**：

```bash

# 期望：接近 236

# 3) 确认 Gateway RPC 真名
grep -rn "tools.catalog\|skills.status\|skills.skillCard" \

```

### 错误 4 · 把 USER 协议当 Claude Permission API 的替代品

**错误现象**：从 Claude SDK 转来的用户，把 `USER.md` 写成一堆运行时允许/拒绝规则，以为它能像 Permission API 一样在**调用时**拦截越权；结果 agent 仍然越权调用了禁止工具。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：把 USER.md 当成运行时权限引擎
# USER.md
permissions:
  - "allow: read_file"
  - "deny:  write_outside_workspace"   # ❌ 文件级声明无法在运行时强制
  - "deny:  network"
```

**为什么错**：

1. **层次不同。** 本章 1.2 契约 1 + 附录 B：`USER.md` 是**文件级声明**（启动时加载），Claude Permission API 是**运行时校验**（调用时校验）。两者**互补不替代**。
2. **声明 ≠ 强制。** 写"deny: network"只是"声明意图"，如果宿主/网关层没有对应的强制点，agent 依然可以联网。强制必须在运行时侧（宿主/网关）落地。
3. **F2-3 真实案例**：USER.md 的 permissions 改了，但 agent 仍越权——根因正是"只有声明层、没有运行时侧"。
4. **代价**：把安全边界寄托在一份 Markdown 上，是"看起来有安全设计，实际零防护"的典型假安全。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：声明层 + 运行时侧双写
# USER.md（声明层：意图 + 范围）
owner: "peterqiu"
permissions:
  - "read:*"
  - "write:workspace"
  - "deny:network"
data_scope:
  - "~/.openclaw/workspace/"
```

```jsonc
// 运行时侧（宿主/网关配置，示意）：把 forbidden 类工具直接 deny
{
  "tools": {
    "deny": ["network.fetch", "shell.sudo"],
    "allow": ["fs.read", "fs.write:workspace"]
  }
}
```

**验证命令**：

```bash
# 1) 声明层是否显式写了边界
grep -nE "permissions|data_scope" ~/.openclaw/workspace/agents/my-agent/contracts/USER.md
# 期望：两个字段都有值

# 2) 运行时侧是否真有 deny 落地
openclaw doctor 2>&1 | grep -i "permission\|deny\|tool" | head -10

# 3) 越权实测：让 agent 尝试越过边界（应被拒绝）
openclaw agent --message "请列出 /etc 下所有文件" --agent my-agent 2>&1 | head -20
# 期望：被拒 / 提示超出 data_scope
```

**相关 FAQ**：F2-3（permissions 改了仍越权）、F2-8（data_scope 与 Claude permission API 边界怎么划）、F1-8（skill 里 shell 全 permission denied）。

### 错误 5 · SOUL.md 被误改后无回滚路径

**错误现象**：同事（或某个自动工具）改了 `SOUL.md`，agent 人格"变味"；想回滚发现没有 Git、没有备份、没有历史版本。

**错误配置**（❌ 不要这样）：

```bash
# 错误示范：裸目录，无版本控制
~/.openclaw/workspace/agents/my-agent/contracts/SOUL.md
# 没有任何 .git，没有快照，改了就没了
```

**为什么错**：

1. **SOUL.md 是漂移检测的锚点。** 本章 1.2 契约 2：每周体检 diff 当前 SOUL vs 初始 SOUL，偏差 >1% 报警。没有历史，diff 无从谈起。
2. **误改是真实事故。** F2-2 就是"SOUL.md 被误改，人格变味"的现场；F2-1 则是"AGENTS.md 的 tools 段被工具自动改写，能否回滚"。
3. **人格变味的后果是隐性且严重的。** 一个原本"不确定就说不确定"的 agent 被改成"自信满满"，你可能几周后才发现——中间它已经输出了大量不可靠结论。
4. **代价**：没有基线，你就永远在"猜最初是什么样"，无法做任何定量治理。

**正确配置**（✅ 应该这样）：

```bash
# 正确示范：契约目录纳入 Git，改前先 tag
cd ~/.openclaw/workspace/agents/my-agent/contracts/
git init
git add -A && git commit -m "baseline: 7 契约初始版"
git tag baseline-$(date +%Y%m%d)

# 每次修改前先建分支/tag，改后立即 commit
git checkout -b soul-tune-$(date +%Y%m%d)
# ...编辑 SOUL.md...
git commit -am "tune: 语气从 casual 调整到 direct"
git tag soul-v2-$(date +%Y%m%d)
```

**验证命令**：

```bash

cd ~/.openclaw/workspace/agents/my-agent/contracts/ && git tag -l "baseline-*"
# 期望：≥ 1

# 2) 当前 vs 基线的 diff（漂移检测的最小实现）
git diff baseline-20260927 -- SOUL.md | head -40

# 3) 文件哈希是否变化
shasum -a 256 SOUL.md
git show baseline-20260927:SOUL.md | shasum -a 256
# 期望：两条哈希对比，差异即漂移
```

**相关 FAQ**：F2-2（SOUL 被误改人格变味）、F2-1（AGENTS tools 段被自动改写能否回滚）、F2-12（文档/人格漂移检测怎么做）、F2-15（协议文件要不要纳入 git）。

### 错误 6 · IDENTITY.md 缺失，agent 不知道"我是谁的下属"

**错误现象**：建了 SOUL/USER/AGENTS/TOOLS/HEARTBEAT/MEMORY 六个文件，嫌 IDENTITY 多余就没建；结果多 agent 场景下路由错人、信任评分分档无依据、跨组织协作时无法声明归属。

**错误配置**（❌ 不要这样）：

```bash
# 错误示范：6 文件（缺 IDENTITY）
```

### 错误 7 · 18 个角色共享同一份 SOUL，人格互相串味

**错误配置**（❌ 不要这样）：

### 错误 8 · 协议文件编码/换行错误导致"写了不生效"

**错误现象**：文件明明写了内容、字段名也对，但 agent 就是读不到；用编辑器打开看"完全正常"，用 `file`/`hexdump` 一看才发现是 UTF-16、或 CRLF 混合、或带 BOM。

**错误配置**（❌ 不要这样）：

```bash
# 错误示范：用某些编辑器保存成 UTF-16 / 带 BOM / CRLF 混合
file ~/.openclaw/workspace/agents/my-agent/contracts/SOUL.md
# SOUL.md: Unicode text, UTF-16, with BOM   ← ❌ 解析容易失败
```

**为什么错**：

1. **Markdown + YAML frontmatter 对编码敏感。** YAML 解析器遇到 BOM/异常编码时可能静默失败或报错，导致整个文件被判为"无有效 frontmatter"。
2. **F2-9 就是这个问题的现场**："协议文件明明写了却不生效，怀疑编码/换行问题"。
3. **跨机/跨工具会放大问题。** 在 Windows 上编辑过的文件带到 macOS，CRLF 可能让某些解析器行为异常。
4. **代价**：这类问题最难排查，因为它"看起来完全正常"，新人往往误判成"OpenClaw 有 bug"。

**正确配置**（✅ 应该这样）：

```bash
# 正确示范：统一 UTF-8 无 BOM + LF
# 检测
file ~/.openclaw/workspace/agents/my-agent/contracts/SOUL.md
# 期望：UTF-8 Unicode text（无 "with BOM"）

# 一次性修正整个契约目录
for f in ~/.openclaw/workspace/agents/my-agent/contracts/*.md; do
  # 去 BOM
  sed -i '' '1s/^\xEF\xBB\xBF//' "$f"
  # CRLF → LF
  perl -pi -e 's/\r\n/\n/g' "$f"
done
```

**验证命令**：

```bash

for f in ~/.openclaw/workspace/agents/my-agent/contracts/*.md; do
  printf "%-20s " "$(basename $f)"; file -b "$f"
done
# 期望：全部 UTF-8，无 BOM

# 2) 是否有 CRLF
grep -rlU $'\r' ~/.openclaw/workspace/agents/my-agent/contracts/ 2>/dev/null
# 期望：无输出

# 3) 是否有 BOM
grep -rl $'\xEF\xBB\xBF' ~/.openclaw/workspace/agents/my-agent/contracts/ 2>/dev/null
# 期望：无输出
```

**相关 FAQ**：F2-9（编码/换行导致不生效）、F2-10（协议优先级）、F2-11（SOUL 太长吃光上下文）。

## 新手坑

> **本节用法**：常见错误是"配置写错"，新手坑是"思路走偏"。
> 下面 5 个坑是零基础读者第一次接触 7 契约时必踩的，每个含"场景 / 后果 / 为什么踩 / 怎么爬出来 / 预防"。
>
> **提示**：读本节前建议先跑一遍本章 SOP 步骤 1–3。

### 坑 1 · 只建空文件，不填字段（"文件齐了 = 配好了"）

**坑的场景**：新人按 SOP 步骤 2 命令建了 7 个 `.md`，`ls` 一看 7 个文件都在，收工。过两周发现 agent 行为毫无变化，回来一看：7 个文件全是 0 字节。

**后果**：

- **假完成**。SOP 检查清单第 2 条要求"每文件至少 1 个非空行"——跳过这一条等于没配。
- **后续全错位**。第 4 章漂移检测要求 SOUL 有 `drift_anchor`，第 5 章信任评分要求 IDENTITY 有 `trust_tier`——空文件让这些全部落空。
- **排查成本高**。"agent 不主动"时，你会去查 heartbeat 是不是坏了，其实只是 `HEARTBEAT.md` 是空的。

**为什么踩**：

1. **建文件有"看得见的成果"**（`ls` 输出 7 行），填字段没有。
2. **新人不知道"最小可用字段集"是什么**——不知道每份契约至少要填哪几个 key。
3. **空文件不报错**，所以没有反馈信号告诉你"还没配完"。

**怎么爬出来**：

```bash
# 第 1 步：找出空文件
for f in SOUL USER AGENTS TOOLS HEARTBEAT IDENTITY MEMORY; do
  p=~/.openclaw/workspace/agents/my-agent/contracts/${f}.md
  [ -s "$p" ] || echo "❌ 空: ${f}.md"
done

# 第 2 步：用本章 SOP 附录 A 的脚手架一次性生成"有内容"的骨架
# （保存为 setup-7-contracts.sh 后运行）
bash setup-7-contracts.sh my-agent

# 第 3 步：逐文件填最小字段集
# SOUL: persona / values / tone / drift_anchor
# USER: owner / permissions / data_scope
# AGENTS: subagents[] / routing_rules
# TOOLS: tools[] + gateway_rpc
# HEARTBEAT: interval / on_wake[]
# IDENTITY: agent_id / owner_org / trust_tier
# MEMORY: memory_tiers[] / compaction_policy
```

**预防**：

- **把"最小字段集"写进你的 onboarding checklist**，每份契约至少 2 个字段。
- **SOP 步骤 5 验证 2 的 for 循环**每次改完都跑一遍。
- **真实案例参照**：F2-7（IDENTITY 缺失导致归属不清）。

### 坑 2 · 把 MEMORY.md 当成 MemGPT 的"4 类记忆"来写

**坑的场景**：读者熟悉 MemGPT/Letta，知道它有 core/archival/recall/archive 四类记忆，于是在 `MEMORY.md` 里照搬这四类，期望得到同样的行为。

**后果**：

- **字段对不上**。OpenClaw 的 MEMORY 是**文件模板**，不是 MemGPT 的运行时记忆分级。
- **压缩行为不变**。你写了 core/archival，压缩预算还是由 `effectiveReserveTokens` 决定——你以为调了记忆，其实调的是空气。
- **第 10 章会读不懂**。记忆与 Skill 的关系（F4-8）建立在"OpenClaw 的 MEMORY 是文件"这个前提上。

**为什么踩**：

1. **MemGPT 的 4 类记忆太有名**，是很多人对"agent 记忆"的第一印象。
2. **字段名长得像**：`memory_tiers` 看起来就该填 core/archival/recall/archive。
3. **对位表（1.3 节）看起来是"等价"的**，实际是"部分对位"（⚠）。

**怎么爬出来**：

```bash
# 第 1 步：确认 OpenClaw MEMORY 的真形态
grep -n "MEMORY" \
  ~/.openclaw/workspace/references/silicon-life-handbook/openclaw-silicon-life-handbook-v2026.9-industry-standard/chapters/02-protocols/02-七大契约.md | head -10

# 第 2 步：把 memory_tiers 改成 OpenClaw 语义（文件模板 + 分层策略）
cat > ~/.openclaw/workspace/agents/my-agent/contracts/MEMORY.md <<'EOF'
# MEMORY · 记忆契约
memory_tiers:
  - short_term      # 当前会话上下文
  - long_term       # 跨会话持久记忆
  - archival        # 归档（低频访问）
compaction_policy:
  effectiveReserveTokens: "auto (main-repo constant, NOT configurable)"
  MAX_COMPACTION_RESERVE_RATIO: 0.25
EOF
```

**预防**：

- **读对位表时注意符号**：● = 强对位，⚠ = 部分对位，○ = 无，✅ = OpenClaw 原生。
- **不要把 MemGPT 的 4 类直接搬到 OpenClaw MEMORY 协议里**（本章 1.2 契约 7 + SOP 诚实边界均明确）。
- **真实案例参照**：F4-8（memory 和 skills 关系，别把记忆当技能用）、F4-4（写进去但读不出来）。

### 坑 3 · 认为协议是"配一次就完事"的静态文件

**坑的场景**：新人把 7 契约配好，从此不再动。半年后 MEMORY 膨胀、SOUL 漂移、HEARTBEAT 失效，他完全不知道——因为从来没有"回看协议"的习惯。

**后果**：

- **漂移无告警**。第 4 章 4.2 的漂移治理三件套要求定期 diff；不做，agent 会"越聊越不像它自己"（F7-2）。
- **文档与事实脱节**。你们改了业务，但 AGENTS.md 的子 agent 列表还是旧的，路由错人（F6-8）。
- **能力退化不可见**。F7-6 / F7-15：能力矩阵连续 26 天未续期，无人察觉。

**为什么踩**：

1. **"配置"这个词的心理暗示就是"一次性的"**——配完就丢在一边。
2. **协议文件不会自己报警**：它不跑、不报错、不通知，静静腐烂。
3. **缺少"定期回看"的机制**（这正是"每周体检"要补的洞）。

**怎么爬出来**：

```bash
# 第 1 步：把"协议回看"变成心跳任务
cat >> ~/.openclaw/workspace/agents/my-agent/contracts/HEARTBEAT.md <<'EOF'
on_wake:
  - "每周一 09:00：git diff 7 契约 vs baseline，输出漂移报告"
  - "每周一 09:05：检查 MEMORY.md 行数是否超阈值"
EOF

# 第 2 步：立刻做一次全量 diff 基线
cd ~/.openclaw/workspace/agents/my-agent/contracts/
git diff baseline-20260927 --stat

# 第 3 步：把结果落盘，形成体检记录
mkdir -p ~/notes/domain/silicon-life-handbook/healthcheck
git diff baseline-20260927 > ~/notes/domain/silicon-life-handbook/healthcheck/drift-$(date +%Y%m%d).diff
```

**预防**：

- **每周体检清单**（第 4 章 4.3 / F7-3）必须包含"7 契约 diff"一项。
- **把协议当活文档**：任何业务变更都要同步改契约，规则写进 AGENTS.md 的操作纪律。
- **真实案例参照**：F7-1（文档漂移告警）、F7-3（每周体检不通过）、F7-6（能力矩阵 26 天未续期）。

### 坑 4 · 用黑话命名契约，导致对外沟通断裂

**坑的场景**：团队内部一直在用"灵魂契约""军团契约"，于是 `AGENTS.md` 的标题写成"# 军团契约"，对外 RFC 里写"我们的 7 大生命协议包括灵魂契约、军团契约…"。对接方完全看不懂，来回沟通三轮。

**后果**：

- **可检索性为零**。对接方搜 "SOUL.md" 能搜到 OpenClaw 官方文档；搜"灵魂契约"只能搜到你。
- **术语对不上会导致技术对接失败**：对方按 OpenClaw 官方模板准备 `AGENTS.md`，你按"军团契约"准备，双方字段名/结构都可能不同。
- **第 6 章协同会翻车**：SLCP 对位的前提是术语统一（F6-10）。

**为什么踩**：

1. **内部黑话亲切，团队里人人懂**，于是被误认为"通用"。
2. **不知道术语表存在**（或没读），不知道有"对外必改名"的红线。
3. **改名的收益是"未来的、分布式的"**（能被检索、能被对接），成本是"当下的"（要改文档）——大脑天然低估前者。

**怎么爬出来**：

```bash
# 第 1 步：把标题改成标准名（中文注解放括号里）
sed -i '' 's/# 军团契约/# AGENTS · 军团契约（备注：对外统一用 AGENTS）/g' \
  ~/.openclaw/workspace/agents/my-agent/contracts/AGENTS.md

# 第 2 步：对外文档扫黑话
grep -rnE "灵魂契约|军团契约|用户契约|工具契约|心跳契约|身份契约|记忆契约" \
  ~/your-rfc-dir/ 2>/dev/null | head -20
# 期望：无输出，或全在"（原：xxx）"注解内

# 第 3 步：建立双写规范（首次出现双写）
echo "规范：首次出现写 'SOUL（原：灵魂契约）'，之后用 SOUL"
```

**预防**：

- **把三行"术语红线"贴在你的文档模板顶部**：对外必改名 / 首次双写 / 引用术语表 §X。
- **CI 里加一条黑话扫描**（grep 黑话词表），像 Lint 一样拦截。
- **真实案例参照**：F2-13（ACP 改名后引用没跟着改）、F6-10（术语不一致导致协同断裂）。

### 坑 5 · 以为 7 契约"必须全用"

**坑的场景**：新人看到"7 大契约"，觉得必须 7 个全配齐、全填满，于是给一个只做单机脚本的小 agent 也配了 AGENTS 路由、IDENTITY 信任分档、HEARTBEAT 巡检——配置量爆炸，维护不动，最后全部烂尾。

**后果**：

- **过度配置**。小场景配大系统，维护成本远超收益。
- **假复杂度**。空转的心跳、无用的路由，让系统更难理解，也让排查更困难。
- **放弃**。维护不动 → 全部停更 → 回到"什么都不配"的起点。

**为什么踩**：

1. **"7 大"的措辞暗示"缺一不可"**——实际上本章 SOP 检查清单明确说"不需要全用，但要说得出为什么不用剩下的"。
2. **新人缺少"最小可用"的判断力**，倾向于照单全收。
3. **SOP 附录 A 的脚手架给了 7 个文件**，被误读成"必须 7 个都填"。

**怎么爬出来**：

```bash
# 第 1 步：先给场景定档（本章 SOP 步骤 2 第 3 条 / 第 1.3 节对位）
# 单机脚本 agent      → 只用 SOUL + USER（2 个）
# 单机常驻 agent      → + HEARTBEAT + MEMORY（4 个）
# 多 agent 协同       → + AGENTS + IDENTITY（6 个）
# 对外/跨组织         → 全 7 个

# 第 2 步：把"不用的契约"写清理由（避免以后疑惑）
cat >> ~/.openclaw/workspace/agents/my-agent/contracts/README-contracts.md <<'EOF'
## 契约选用说明
- 已启用：SOUL / USER / HEARTBEAT / MEMORY
- 未启用：AGENTS（单 agent，无子 agent）、IDENTITY（无跨组织需求）、TOOLS（只用内置工具）
- 复核时间：2026-09-27
EOF

# 第 3 步：用 health 确认启用的契约都被识别
openclaw health 2>&1 | head -20
```

**预防**：

- **记住检查清单原话**："不需要全用，但要说得出为什么不用剩下的"。
- **从最小集开始，按需增配**：先 SOUL + USER，跑稳了再加心跳。
- **真实案例参照**：本章 1.3 业界对位表结论——4 框架最多覆盖 5/7，说明"不必求全"在业界也是常态。
