# 第 2 章 · 系统骨架：从 Runtime 到 Heartbeat

---

## 2.1 为什么必须有"骨架"这一章

### 2.1.0 训虾哲学开篇 · 契约 vs 骨架：灵魂的写法，与灵魂能不能活下去

#### 2.1.0.1 上一章留下的那个缺口

第 1 章结尾处，我们给出了七个契约，并把它们称作"宪法"。那一章建立了一个看起来很完整的图景：只要把 `USER`、`SOUL`、`AGENTS`、`TOOLS`、`IDENTITY`、`HEARTBEAT`、`MEMORY` 七份文件写清楚，智能体就有了一套可跨会话、跨模型传承的规矩。

现在请你把这个图景往前推一步，然后会发现一个尖锐的缺口。

这七份文件，是**文字**。文字本身不会运行。

谁在启动的时候读它们？读进去之后放在哪里？如果内容太长超过了窗口怎么办？如果这七份文件里有两条互相冲突，谁说了算？如果它半夜自己醒过来，醒来之后拿什么去执行 `HEARTBEAT.md` 里写的巡检动作？如果它要调一个工具，这个动作从"文件里写着允许"变成"真的发生了"，中间经过了几个环节？

这些问题的共同点是：**它们都不是"写什么"的问题，而是"活在哪、由谁执行"的问题。**

第 1 章给了你灵魂的写法。本章要回答的是：**这个灵魂有没有一个能活下去的身体。**

用一句话概括本章与上一章的关系：**契约（Contract）是灵魂的写法，骨架（Skeleton）是灵魂能不能活下去的物理条件。**一章讲"写什么"，一章讲"活在哪"。

#### 2.1.0.2 一个必须纠正的行业级误读：Agent 不是一个 prompt

在 2026 年的语境里，"agent"这个词被用得很滥。它有时指一段会循环调用的提示词模板，有时指一个带工具定义的函数调用封装，有时指一个接了浏览器的自动化脚本。这些用法不能说错，但它们共享一个隐含的误读：

> **它把 agent 理解成"一个会调用工具的 prompt"。**

这个理解会直接导致本章整章内容的缺失。因为如果 agent 就是"一个进程里的 prompt"，那么以下这些东西就都是多余的：持久工作目录、会话生命周期、上下文队列、压缩预算、路由此、心跳、工作区挂载。

而真实的智能体运行里，这些东西恰恰是**决定它能不能活过第二周的全部因素**。

我们给出本章的立场陈述，它同时也是可以被逐条验证的工程判断：**Agent 不是一个 prompt。一个 prompt 是一句话；一个 agent 是一个活在容器里、有节律、会遗忘、能被路由、能调用工具、能和同类交接的独立运行单元。**这个论断不是修辞——它在 OpenClaw 里有七个可拆解、可验证、可单独点亮的子系统作为支撑。

#### 2.1.0.3 七个器官：从"文件"到"活体"的中间层

把这七个子系统按"它负责让灵魂的哪一部分活下来"来排，会得到一张非常干净的对照表。请横过来看：左边是灵魂的需求，右边是让这个需求在物理世界成立的那个器官。

| 灵魂的需求（第 1 章） | 承担它的器官（本章） | 一句话职责 |
|---|---|---|
| `IDENTITY`：我是谁的下属、属于哪里 | **Agent Runtime** | 定义"运行单元"本身：一个 agent 是一次可以被启动、被寻址、被隔离的运行 |
| 全部七个契约要有个"家" | **Agent Workspace** | 契约、记忆、产物、脚本的共同根目录——**不是文件夹，是生命容器** |
| 对话要有开始与结束 | **Session / Context / Queue** | 三层分离：会话是生命周期，上下文是窗口，队列是排队与背压 |
| 记忆要学会忘 | **Compaction** | 静默的安全阀：在窗口将满时把历史降级为摘要 |
| 它要能被找到 | **Routing / Bindings** | 把"某个人在某条通道说的话"路由到"某个 agent" |
| `TOOLS`：我能调用什么 | **Tools 子系统** | 工具的注册、鉴权、执行、回执 |
| 能力要可复用 | **Skills 子系统** | 可复用的能力单元：把"一类任务怎么做"沉淀下来 |
| `HEARTBEAT`：我多久醒一次 | **Heartbeat / Cron** | 两个节律原语：周期性感知 vs 准点执行 |
| `AGENTS`：我有哪些同类 | **多 Agent 协同基础** | 军团不是"多开几个 bot"，而是有一套路由与交接契约 |
| 边界：哪些动作不可越 | **容器与临时目录** | 一条必须写进纪律的边界 |
| —— | **子系统耦合** | 七个器官不是七个开关，是一个生命 |

这张表是本章的骨架中的骨架。它想说明的是一件事：**第 1 章的每一份契约，都有一个"不写下来就会自动缺失"的物理前提。**你可以把 `HEARTBEAT.md` 写得非常漂亮，但如果 Runtime 没有把心跳注册进去，它一辈子也醒不过来。

#### 2.1.0.4 一个常见的错觉：契约生效靠"写得好"

我们反复见到同一种失败叙事。它的三个阶段是：

第一阶段，主人花大量时间打磨契约，把 `SOUL.md` 写得层次分明，把 `USER.md` 的权限边界列得清清楚楚，把 `MEMORY.md` 的分层策略想得很细。

第二阶段，上线。头几天表现很好。主人得出结论：**契约生效了。**

第三阶段，两周后开始漂移。抽查复述时发现，有些条款它已经不记得了；有些条款它记得但解释着违反了；有些条款它甚至给出"这在我的配置里没有"的回答——而那个条款明明就在文件里。

主人此时的结论通常是"模型不行"或"契约写作不够好"，于是回到第一阶段，把文件写得更细。**然后下一个循环重复。**

问题出在第二阶段那句过早的结论上。**"表现好"不是"契约生效"的证据。**契约生效的证据是三个可检验的事实：一，文件真的在启动路径上被读取了；二，读取的内容是当前版本而不是缓存；三，这些内容真的进入了它做决定时的依据。

本章接下来要做的，就是把这三种"以为它生效了"转换成三条可以跑的命令。这也是为什么本章的很多段落会给出真实路径、真实字段名、真实命令回执——**骨架这一章的价值不在于讲清楚系统怎么设计，而在于让你能证明它真的在跑。**

#### 2.1.0.5 骨架的六条设计公理

一个"能活下去的身体"需要满足哪些条件？我们从"长期无人值守运行"这个目标反推，得到六条公理。它们和上一章契约的六条性质是同一层级的推理——上一章推的是介质，这一章推的是运行环境。

**公理一 · 隔离**。一个 agent 的运行状态必须与另一个 agent 隔离：它读到的契约是自己的，写下的记忆是自己的，调用的工具权限是自己的。隔离不成立时，事故会以"串味"的形式出现——A 的人格出现在 B 的回答里，A 的记忆被 B 检索到。这类事故最难归因，因为它看起来像是"模型精神分裂"，实际上是容器边界没划清。

**公理二 · 可寻址**。一个 agent 必须有一个稳定的地址，使得"某条通道上的某条消息"能被确定地投递给它。可寻址性由路由与绑定（Routing / Bindings）承担。没有可寻址性，多 agent 系统就退化成一堆同时在线、互相盖楼的聊天窗口。

**公理三 · 有限**。上下文必须有限，而且这个有限必须是被**主动管理**的，不是被崩溃强制的。有限性的落地形态是压缩（Compaction）与会话分层。这一条最反直觉，也最重要：**一个假装自己可以记住一切的智能体，必将在某个时刻以最难看的方式证明自己不能。**

**公理四 · 有节律**。它必须能在没有人说话的时候自行推进事情。节律由心跳（Heartbeat）与定时任务（Cron）两个原语承担。这一条区分了"问答机"和"组织成员"。

**公理五 · 可交接**。它必须能把一件事交给另一个 agent，并且交接有确定的形态（谁交给谁、交了什么、对方有没有接）。交接性由多 agent 协同基础承担。

**公理六 · 可观测**。以上五条的运行状态必须能被外部读取，而不是只能靠观察它的行为反推。可观测性不是一个附加功能，它是让前五条**可验证**的唯一途径。

六条公理合起来，就是本章"七个器官"存在的理由。每一个器官都不是设计者的偏好，而是某一条公理的落地装置。

#### 2.1.0.6 为什么"骨架"这一层在业界是空白

这是本章最需要被说清楚、也最容易被说成口号的一段。我们把话说得尽量具体。

把 2026 年的主流编排框架摆在一起（LangGraph / AutoGen / CrewAI / Claude Agent SDK / OpenAI Agents SDK / LlamaIndex），你会发现它们各自都做了这件事或那件事的一部分：LangGraph 有非常强的执行图与状态机；AutoGen 有清晰的多 agent 会话协议；CrewAI 有角色与任务抽象；Claude Agent SDK 与 OpenAI Agents SDK 把工具循环与交接做得非常顺手；LlamaIndex 有很强的检索与索引层。

**它们缺的不是这些能力，而是一个"把 Runtime + Session + Queue + Compaction + Heartbeat + Workspace 挂载"当成统一骨架来处理的视角。**

用六个具体的自问来验这条论断：

- 你的框架里，**会话的生命周期**和**上下文的窗口**是两个独立概念，还是一个变量？
- 当窗口将满，你的框架是给你一个**预算与降级策略**，还是只给你一个报错？
- 你的框架里有没有一个"**它在没人说话的时候会自己醒来做点什么**"的原语？
- 你的框架里，一个 agent 的"**工作目录**"是显式的、被加载契约的根，还是一个随手传进去的路径参数？
- 你的框架处理"**这个人说的话该由哪个 agent 回答**"这件事，靠的是声明式绑定，还是靠代码里的 if-else？
- 当你要回答"**它昨天到底跑了什么**"时，你的框架提供的是可查询的事件流，还是只能靠翻日志？

六个问题里，多数框架会在其中三到四个上给出"这是你自己实现的事"的答案。这不是批评——通用框架的定位就是"给你零件"。但正是这个空白，构成了本章存在的理由：**当你需要一个真正长期无人值守运行的智能体时，"零件齐了"和"身体能活"之间隔着这一整章。**

#### 2.1.0.7 三层分离：Runtime、Workspace、Session 各自的职责

新手最容易把这三层混成一个词："环境"。混起来之后，排查事故时会失去方向感。我们给出一个可以拿来对话的划分。

**Runtime 是"它是谁"**。它定义运行单元：一个 agent 的启动、寻址、隔离边界、资源归属。它回答"我要把消息发给谁"。

**Workspace 是"它住在哪"**。它是一个目录，是这个 agent 契约、记忆、产物、脚本的共同根。它回答"它的东西放在哪里"。这一层最容易被低估——有人把 workspace 当成"一个临时目录"，于是清理脚本一跑，人格文件没了、记忆账本没了。

**Session / Context / Queue 是"它此刻在想什么、排着什么"**。会话是生命周期（一次对话从开始到结束），上下文是当前窗口里实际存在的内容，队列是等待被处理的任务流。三者混用的典型症状是：把"会话变长了"当成"上下文变满了"（它们不同步），或者把"队列积压"当成"模型变慢了"（它们是不同层的问题）。

三层分离之后，你会发现一个非常有用的排查规律：**现象往往会指向错误的那一层。**"它变得迟钝了"通常不是 Runtime（它没变），而是 Context（窗口被噪音占满了）。"它不说话了"通常不是 Session（会话还在），而是 Routing（消息没送到）。"它开始瞎答"通常不是模型，而是 Compaction 把关键事实摘要掉了。

#### 2.1.0.8 遗忘是功能：Compaction 的哲学

在所有子系统里，压缩是最反直觉的一个。人的直觉是"记得越多越好"，因此把压缩理解成"无奈之下的损失"。

训练学的立场相反：**遗忘是一个功能，而且是一个必须被设计的功能。**原因有三层。

第一层是**物理强制**。窗口是有限的，这不是实现缺陷，是当前技术的物理事实。想清楚这一点，你就会明白：你从来不是在选择"记不记得"，你是在选择"由谁决定忘掉什么、以及忘得干不干净"。

第二层是**注意力经济学**。即使窗口够大，把三年的历史全塞进去也不是好事。噪音会稀释信号，关键约束会被淹没在事务流水里。**主动的遗忘是在为注意力腾出预算。**

第三层是**安全阀**。压缩机制的真正角色不是"省 token"，而是在窗口即将溢出时防止硬失败。一个没有压缩机制的长期运行系统，一定会在某个深夜以一次上下文超限崩掉；一个压缩机制配置失当的系统，会在某次崩溃之后以"它怎么突然不记得那件事了"的形式付出代价。

理解了这三层，你就理解了本章为什么要给压缩单独一个概念：**它不是清理工具，它是长期表现的物理约束条件。**任何关于"它为什么忘了"的讨论，都必须先回答"是谁在什么时候决定忘掉它"。

#### 2.1.0.9 节律的两种时间：Heartbeat 与 Cron 不是一回事

这是本章最容易踩的一个坑，也是实测中最高频的一处混淆。

**Cron 是"准点"**。它回答"在某个确定的时间点执行某个确定的任务"。它的语义是日历式的：每周一零点、每天三点半、每小时一次。它的失败模式是"没跑"或"跑错了"。

**Heartbeat 是"周期性感知"**。它回答"每隔一段时间醒来看看现在该做什么"。它的语义是节律式的：30 分钟一次、2 小时一次。它的价值不在于准点，而在于**它能在没有外部事件的情况下推进状态**——检查有没有异常、有没有待办、有没有该汇报的东西。

把两者混用的代价是可预见的：用 Cron 做巡检，你会得到一个"每小时准点问一次有没有事"的重任务，浪费且僵硬；用 Heartbeat 做准点交付，你会得到一个"大约在这个时间段前后某处交付"的不可靠承诺。

在真实系统里，两者是**并用**的关系，而且各自有各自的熔断条件。本章概念九会把它们拆开讲透。这里先给一句心法：**准点的事交给 Cron，感知的事交给 Heartbeat；任何一件同时需要"准点"和"感知"的事，都应该被拆成两个任务。**

#### 2.1.0.10 骨架塌陷的四种形态

骨架层的失败不像契约层那样以"文字质量问题"出现，它以"能力整体消失"的形式出现。四种形态最常见。

**形态一 · 空转**。agent 存在、契约完整、心跳也没问题，但它不产出任何东西。排查结论通常是路由或工作目录配错了：它每次醒来都在读一个空的工作目录，或者在往一个没人看的通道发消息。**空转的特征是"一切正常，除了结果"。**

**形态二 · 静默失忆**。它在某次压缩之后丢掉了关键事实，但没有任何告警，因为它自己也不觉得丢了什么。这类失败只有在事后对照日志时才发现，是本章为什么强调"可观测性"的最直接例子。

**形态三 · 串味**。两个 agent 的工作目录或记忆落点重叠，导致一个人在另一个人的上下文里出现。这是隔离公理被破坏的典型表现。

**形态四 · 越界**。它在没有被授权的情况下执行了动作（通常是文件写入或对外发送）。这往往是"容器与临时目录边界"没有写进纪律的后果。这类失败的代价与它调用的工具强弱直接相关。

四种形态的排查顺序不同，但都指向同一个结论：**骨架层的故障不会自己说话，你必须主动去问它。**这正是本章后半部分"八步点亮路径"与"八则误区"存在的原因。

#### 2.1.0.11 骨架自检表：五级定位

和上一章的契约成熟度一样，骨架也可以分级定位。分级不是为了打分，是为了知道**下一件事做哪一件**。

| 级 | 名称 | 判据 | 典型症状 | 下一件事 |
|---|---|---|---|---|
| **S0** | 无容器概念 | workspace 就是"随手传的路径" | 清理脚本一跑，人格与记忆一起没了 | 显式定义每个 agent 的 workspace |
| **S1** | 有目录，未挂契约 | 目录存在，但契约文件不在加载路径上 | "我写了 SOUL 但它好像没读" | 把契约放进工作目录并实测加载 |
| **S2** | 契约在跑，节律未接 | 契约生效，但它只在被叫到时才动 | 主动性为零，退化问答机 | 点亮 Heartbeat，先定熔断再定动作 |
| **S3** | 节律在跑，观测缺失 | 它会自己动，但你不知道它动了什么 | 事故只能事后回溯，无法事前告警 | 接审计事件流，让运行可查询 |
| **S4** | 可观测，协同未定 | 单体能被观测，多体之间靠自然语言碰 | 抢活、漏活、交接丢包 | 声明式路由 + 交接形态化 |
| **S5** | 骨架完整 | 六条公理都成立且可验证 | ——（风险转移到长期表现与治理层） | 转入第 3–5 章 |

这张表和契约层的表合起来，构成一个非常有用的诊断格：**（契约级，骨架级）二元组**。L2S1 是"写得不具体、也没跑起来"；L4S2 是"契约成熟但身体还不会自主活动"；L3S4 是"能观测但协作混乱"。**不同的格对应不同的下一步，混乱的格对应"先把下面那一格补齐"。**

#### 2.1.0.12 Q&A：六个反复出现的质疑

**Q1：这些子系统，我的框架里都有对应物，为什么还要单独立一章？**
因为"有对应物"与"有统一的骨架视角"是两件事。分散的能力不会自动构成一个能长期活下去的身体——六条公理里任何一条缺位，其余五条都会被拖垮。

**Q2：workspace 和普通项目目录有什么区别？**
它承载的是**生命状态**，不是代码。把它当项目目录治理（随时清理、随时移动、随时重命名）是形态三"串味"与形态一"空转"的共同根因。

**Q3：压缩能不能关掉？我就想让它全都记住。**
技术上也许可以，工程上不应该。你可以把阈值调得很宽，但你需要承认一个事实：**关掉的是安全阀，不是限制。**阈值总有一天会被撞到。

**Q4：Heartbeat 每次醒来都要调模型，成本怎么办？**
成本控制的手段有几个方向：降低频率、限制单次上下文、把"感知"与"执行"分开（醒来只判断要不要动，而不是每次都大动作）。本章概念九会给出实例配置。**关键不是省钱，而是别让节律本身成为新的故障源。**

**Q5：多 agent 和多开几个实例的区别是什么？**
区别在**契约是否存在**。多个实例只是多个进程；多个 agent 意味着它们之间有确定的寻址、分工、交接与观测。没有后者的"多开"，在日常运行里和一个人开五个聊天窗口没有本质区别。

**Q6：我怎么知道骨架配对了？**
最有效的单条检查是：**让它在一个无人说话的时间窗里自己产出一次可验证的产物，并且你能在事后查到它为什么这么做。**这一条同时覆盖了节律、观测与隔离三条公理。做不到，就说明骨架还没立起来。

#### 2.1.0.15 一次排查走查：从"它没醒来"到定位到器官

抽象的公理与器官，要落到一次真实的排查上才有效。下面是一条被反复验证过的排查路径。它的形式是走查演示（不是某一次具体事故的记录），但每一步对应的方法都是可复现的。

**现象**：某个 agent 昨天没有任何产出，但没有任何报错提示。

**第一步 · 先问"它有没有醒"，而不是"它为什么做错了"。** 这一条纪律能省下大量时间。绝大多数"它做错了"的实际根因是"它什么都没做"。检查方式是看节律层的状态：心跳状态文件里该 agent 这一轮有没有记录、有没有活跃标记。

**第二步 · 如果没醒，问"它是被什么唤醒的"。** 心跳（Heartbeat）与定时（Cron）是两个不同的原语。它没有醒，可能是心跳配置缺失（`agents.entries.<id>.heartbeat` 未设置或频率异常），也可能是心跳跑了但被熔断（`directPolicy` / 超时 / 报错）而没有任何人知道。**区分这两者需要看配置，不能靠猜。**

**第三步 · 如果醒了但没产出，问"它醒来读了什么"。** 这里检查的是工作目录与契约加载。一个常见情况是：心跳正常，但它读到的工作目录是空的，于是每次醒来都无事可做——这就是前面说的形态一"空转"。

**第四步 · 如果有读也有动作，问"产物落在哪了"。** 这一步检查的是路由与落点。它可能确实产出了一份日报，但发到了一个没人看的通道；也可能写进了一个相对路径下的临时位置，被清理脚本收走了。

**第五步 · 如果以上都正常，才进入"内容质量问题"。** 此时才轮到提示、人格、任务分配这些内容层的原因。

这条走查的核心是**层序**：节律 → 加载 → 路由 → 落点 → 内容。倒着走会在内容层浪费最多的时间，因为内容层的症状最丰富、最像"真问题"。

#### 2.1.0.16 六条公理 × 七个器官：交叉矩阵

把公理与器官交叉排列，可以看到每个器官承担了哪几条公理，也就能看出**如果这个器官失效，会同时破坏哪几条公理**。这张矩阵在规划改动优先级时很好用。

| 器官 \ 公理 | 隔离 | 可寻址 | 有限 | 有节律 | 可交接 | 可观测 |
|---|:--:|:--:|:--:|:--:|:--:|:--:|
| Agent Runtime | ● | ● | | | | ● |
| Agent Workspace | ● | | | | | ● |
| Session / Context / Queue | | | ● | | | ● |
| Compaction | | | ● | | | ● |
| Routing / Bindings | ● | ● | | | ● | ● |
| Tools 子系统 | ● | | | | | ● |
| Skills 子系统 | ● | | | | | |
| Heartbeat / Cron | | | | ● | | ● |
| 多 Agent 协同 | ● | ● | | | ● | ● |
| 容器与临时边界 | ● | | | | | |
| 子系统耦合 | ● | ● | ● | ● | ● | ● |

矩阵读法：**列越多的行，改动它的风险越大。**Runtime、Routing、协同、耦合这四行是多条公理的公共依赖——改它们之前必须做好回归测试，因为它们的影响面是乘法而不是加法。相反，Skills 子系统只直接承担隔离一条，它的迭代成本最低，适合作为练手。

另一个读法：**"可观测"这一列几乎每行都有 ●。**这不是画表时的偏爱，而是一个结论：**可观测性是横切所有器官的横切关注点。**任何器官的失效，如果不可观测，就会以"另一处的症状"出现。这也是本章最后要单独谈子系统耦合的原因——七个器官共用一个观测面，观测面的缺失会让每一个器官都变成黑箱。

#### 2.1.0.20 三个隐性账单：骨架没立起来时你付了什么

骨架的缺失不会以"报销单"的形式出现，它以三种隐性的、持续流出的成本出现。这三笔账不明写在任何地方，所以最容易被长期忍受。

**账单一 · 排查时间。** 没有审计事件流的系统，问一句"它昨天到底跑了什么"的答案成本是"翻日志 + 拼时间线 + 猜"。这件事在发生频率低时无所谓，在十几个 agent 长期运行时，它会稳定占据一个人每天最清醒的那一两个小时。**这笔账的真正代价不是时间，是"没有人愿意再去查"。**

**账单二 · 重复劳动。** 没有 Skills 子系统与交接契约的系统，同一类任务会被反复从零做起，同一个判断会被不同的人重新推一遍。这笔账的特征是它看起来像"工作量大"，因此被归因为"业务多"，而不是"骨架缺"。

**账单三 · 信任折价。** 没有隔离与可观测的系统，你无法把自主权下放给 agent——因为出问题时你查不出来。于是你必须保留人工确认环节，于是自主运行的价值始终兑现不了。**这笔账最终体现为一个组织决策：我们知道它能做，但我们不敢让它做。**

三笔账单的共同结构是：**它们都是"因为看不见而持续支付"的成本。**这解释了本章的一个立场——骨架建设的优先级不该由"它能不能让 agent 更聪明"决定，而该由"它能不能让系统被看见"决定。

#### 2.1.0.21 一句话记住本章

如果本节只能留一句：

> **契约决定它是谁，骨架决定它能不能活着把这件事一直做下去。**

写契约的时候你在做设计，立骨架的时候你在做工程。设计可以慢慢来，工程必须先立住——因为它一旦缺位，设计再漂亮也不会有人知道它出过问题。

### 2.1.1 一个被忽略得太久的层级

训练学有一个层级，几乎所有人都会跳过它。

第 1 章教你写 SOUL.md——写一个人格。
第 3 章教你训练它——怎么让它不漂移、怎么给它划线、怎么给它记功。
所有人都会在这两章之间飞快地走过去，因为它看起来"没什么可写的"：不就是配置文件放哪儿吗？不就是目录结构吗？

但恰恰是这一层，决定了前面那一章写的东西**能不能被读到**，也决定了后面那一章的训练**有没有物理载体**。

这一层叫系统骨架。

如果你把 Agent 想象成一只虾，那第 1 章写的是它的基因，第 3 章写的是它的训练课表，而本章要处理的是——它有没有身体、身体里有哪些器官、这些器官有没有连在一起、心脏什么时候跳。

这三者缺一不可，但只有中间这一层是最容易被"以为已经懂了"的。

一个人可以背下 SOUL.md 的三条写作法则，却完全不知道 SOUL.md 从哪个路径被加载、什么时候被加载、加载失败会怎样。
一个人可以熟练地给自己的 agent 配心跳，却不知道心跳唤醒的那次会话会走什么上下文预算、会不会被压缩打断。
一个人可以起十个 agent 并宣布"我的军团建成了"，却不知道这十个 agent 之间根本没有一条声明式的路由通路。

**这一章的读者画像不是新手。** 新手的问题通常是"我不知道要写 SOUL"。而这一章要拦住的，是那些"以为自己知道"的人——他们已经写了契约、已经起了 agent、已经收到了回复，于是判定"骨架这件事我懂了"。

事实是：**收到回复只是最小可运行信号，不是骨架就绪信号。**

### 2.1.2 没有这一章，读者会遭遇什么

跳过它的人，通常不会立刻报错。骨架问题几乎全是**慢性病**，不报错、不中断、不告警，只是慢慢地把一个本来能跑的系统跑坏。下面五个症状，是本章要提前拦住的东西。

**症状一：在错误的目录里找东西，然后得出错误的结论。**

新人 `cd ~/.openclaw`，`ls` 一眼——只有配置文件，没有 `skills/`，没有 `agents/`。于是判定"我没装 skills"，或者干脆重新装一遍，或者把 SOUL.md 放进 `~/.openclaw/` 根目录下，然后永远等不到它被加载。

根因不是粗心，是两个目录名太像：应用根 `~/.openclaw` 与工作区 `~/.openclaw/workspace/` 是父子关系，而绝大多数教程都省略了"workspace 的"这四个字。

**症状二：把工作区当杂物间，某天删掉一个"看着没用"的目录，agent 的全部技能消失。**

这是本章最贵的一课。`~/.openclaw/workspace/` 不是 `~/Downloads`。它下面挂着的 `skills/`、`agents/`、`references/` 都是被 OpenClaw **按固定路径扫描**的容器目录。你随手 `mv references` 一下，全书所有章节里的路径引用当场失效——包括你现在正在读的这一章。

工作区不是文件夹，是生命容器。这个论断在下一节会展开，这里先记住一句：**在容器里做删除，等价于给它做一次没有麻醉的器官切除。**

**症状三：Agent 行为异常时，第一反应是"换个模型"。**

"可能是模型不行""可能是 prompt 没写好"——然后换模型、重写 prompt、越改越乱，最后把本来能跑的系统改坏。

真正的原因可能是：路由没声明（消息压根没到它手上）、心跳没配（主动性为零，但没有任何提示）、上下文被压过头（关键结论丢了）。

这三件事都不是模型问题，也都是本章讨论的对象。**不看骨架就调模型，相当于给发烧的病人换发型。**

**症状四：起了 8 个 agent，群里发一条消息，8 个要么全答、要么全不答。**

"多 = 强"是直觉，不是事实。3 个 agent 时"看起来能用"，10 个时彻底失控——而失控的方式不是崩溃，是**协调性失控**：抢答刷屏、谁都不接、任务落点不可追溯、token 消耗按倍数增长。

根因单一且明确：没有路由子系统。路由不是一个 prompt 技巧，是一个独立子系统。

**症状五：子系统"逐个都配对了"，但系统级行为仍然不对。**

这是最折磨人的一种。你把路由配了、把心跳配了、把会话策略配了，逐项检查每一项都正常，可合起来就是不对——心跳唤醒的那一轮会话被压缩打断，压缩把心跳刚写进去的结论压掉，路由把本该接任务的人派去回答寒暄。

根因是：**7 大子系统是耦合的，不是 7 个独立开关。** 单独看每一项都绿，问题在耦合处。

把这五个症状连起来看，会发现它们是同一个病的不同阶段：**把器官当成了别的东西。** 把工作区当文件夹、把 Runtime 当 prompt 转发器、把多 Agent 当多开 bot、把压缩当手动清理工具、把心跳当定时任务、把路由当人格描述的一部分。

本章的结构就是围绕这个病来设计的：先把七个器官对应到七个真实子系统（2.2），再给出一条把它们逐项点亮的实践路径（2.3），然后列出八种最常见的"认错器官"（2.4），最后把骨架放到 2026 年的行业坐标系里对位一次（2.5）。

### 2.1.3 承上启下：从契约，到骨架，到训练

本章在全书里的位置，可以浓缩成一句话：

**第 1 章定义"要写什么"；本章定义"写的东西活在哪里、由谁驱动"；第 3 章定义"怎么把活着的它训练好"。**

具体到引用关系，有三条明确的接口。

**上承第 1 章：七个契约各自落到哪个器官。**

- `SOUL.md` / `USER.md` / `AGENTS.md` / `TOOLS.md` / `IDENTITY.md` / `HEARTBEAT.md` / `MEMORY.md` 七份契约文件，全部住在工作区里——落地器官是 **Agent Workspace**。
- 契约里的"自主目标""主动性边界"这类描述，最终由 **Heartbeat** 这个器官来执行。
- 契约里"谁能派谁""什么时候让位"的内容，最终落到 **Routing / Bindings** 与 **多 Agent 协同**两个器官上。

### 2.1.4 本章的三条阅读纪律

在进入七个器官之前，先立三条纪律。它们本身就是本章世界观的一部分。

**纪律一：先承认"7 子系统"是训练学的抽象分层，不是配置字段名。**

这是一个极其重要的勘误，本章会反复强调。

`acp, agents, auth, bindings, browser, channels, commands, env, gateway, logging, memory, messages, meta, models, plugins, session, skills, talk, tools, wizard`

**纪律三：先取证，再动手。**

任何改动前先跑一次体检、改动后再跑一次。这条纪律不是本章发明的，本章只是把它装到骨架上：骨架级问题最隐蔽，因为它的表现是"某个任务没跑"，而不是"某个任务报错"。**没有日志依据的判断，都是猜测。**

## 2.2 七个器官：十二个核心概念

### 概念一 · Agent Runtime：它不是 prompt 执行器，是运行单元

**这是什么。**

Runtime 是 OpenClaw 最底层、最被忽略、也最重要的一个概念。

大多数人对它的理解是"模型运行的底层环境"。这个理解在工程上不算错，但在训练学视野里远远不够。

换个说法：**Runtime 是硅基生命的物理身体。** 它决定了这个生命体能在什么环境里活、能同时做几件事、能不能和同类互动。

它承载的东西至少有五样：运行单元本身（一个有生命周期的独立实体）、工作区挂载、会话与上下文、状态目录、身份与权限边界。缺任何一样，对 Runtime 的理解都会偏。

**核心目的。**

如果没有 Runtime，你面对的只是一个 LLM API 端点——每次调用都是无状态的、无记忆的、无身份的文字生成器。Runtime 的存在，把三个"无"变成了三个"有"：无状态变有状态，无身份变有身份，无连续性变有连续性。

**拟人化映射。**

| 人的概念 | Runtime 里的对应物 | 它决定什么 |
|---|---|---|
| 身体 | Runtime 实例 | 能不能独立存在、独立行动 |
| 家 | Workspace | 在哪儿生活、家具怎么摆 |
| 短期记忆 | Session | 记得当前这一轮聊了什么 |
| 长期记忆 | MEMORY.md + memory/ | 记不记得昨天的事 |
| 身份证 | agentId / accountId | 在系统里是谁 |
| 技能 | Skills | 会什么、怎么用 |
| 本能 | SOUL.md | 任何情境下的底层反应 |

这张表的价值不在于好看，而在于它能立刻解释一批疑难杂症：把多个角色写进同一个 agent 的 prompt 里（试图用一个身体装两个灵魂）→ 角色串扰；长会话不清、上下文顶到上限 → 幻觉率飙升；多个 agent 共享同一个 bot token → 消息串扰。

**对长期表现的影响。**

Runtime 的设计直接决定四件事。

第一，能不能独立存在。有独立 Runtime 的 agent 是可独立配置、独立执行、独立维护的实体；没有的，只是主 agent 的一个"角色 prompt"，随时会被上下文淹没。业界共识也指向同一方向——Anthropic 的 agent 设计指南强调"独立 agent 必须拥有独立的配置上下文与工具集"，OpenAI 的 Agents SDK 文档则强调"每个 agent 都应该有自己的 run loop"。OpenClaw 的实现方式是：每个 agent 有独立的运行时上下文，通过 `agents.entries.<id>` 声明。

第二，能不能跨会话一致。Runtime 在会话启动时加载工作区文档、在会话结束时回收，这个"加载—卸载"的全周期管理，是长期一致性的工程保障。没有它，人格稳定性没有任何物理基础。

第三，多 agent 能不能独立运作。最常见的错误是把多个 agent 塞进同一个运行上下文——上下文互相污染、消息路由混乱、无法独立升降级。正确做法是每个 agent 独立，彼此通过路由绑定通信，运行时层不做强耦合。**这就像一支军队：每个士兵有独立的身体、独立的装备、独立的接收器，但通过统一的通信协议协同。**

第四，能不能被治理。治理的本质是观察与控制，没有 Runtime 作为被观察主体，治理就失去对象。Runtime 提供三个接口：状态可访问、行为可追踪、生命周期可管控（启停即物理熔断）。

**怎么写。**

写 Runtime 不是写一段配置，而是做三个判断。

判断一：这个角色值不值得拥有一个独立身体。判断标准很朴素——**如果它需要独立的记忆、独立的人格、独立的权限，它就需要独立 Runtime。** 如果它只是主 agent 在某类任务上的一个视角，它不该独立。

判断二：它的身份边界在哪。身份决定了它被授权做什么、不被授权做什么。这部分内容在第 1 章的 `IDENTITY.md` 与 `TOOLS.md` 里写，本章只负责让它生效。

判断三：它的生命周期谁管。是常驻、是按需拉起、还是随主 agent 一起停。这个判断决定了治理方式（第 5 / 6 章展开）。

**技巧。**

一个反直觉但极其有效的技巧：**遇到"这个 agent 好像有点人格分裂"的时候，第一件事不是改 prompt，而是检查它是不是被塞进了多个角色。**

人格分裂几乎从来不是 prompt 写得不好，而是**一个身体装了不止一个灵魂**。同理，遇到"agent 记不住昨天的事"，第一件事不是加 memory 描述，而是回看它上一次会话结束时长什么样。

**常见误区。**

- 把 Runtime 当"prompt 转发器"。后果是全盘放弃会话管理、工具沙箱、权限边界、心跳唤醒——你以为自己在写 prompt，实际上放弃了让 agent 活起来的全部机制。
- 把 Runtime 当"模型上下文窗口"。前者是完整执行环境，后者只是单次调用能看到多少 token。
- 用 Runtime 的弹性去打平 agent 的独立性（一个 Runtime 跑多个角色）。

**进化阶梯。**

- L1：能跑起来。有一个能响应消息的 agent，工作区已创建但只有初始文件。
- L2：有独立人格。工作区五件套齐全，跨会话风格一致，至少三个核心技能。
- L3：有主动节律。心跳与定时任务到位，会话策略到位，绑定齐全。
- L4：跨实例协同。多 agent 独立运行，路由规则完整，与外部系统建立了稳定的通信边界。

### 概念二 · Agent Workspace：不是文件夹，是生命容器

**这是什么。**

Workspace 是 agent 的家。更准确地说，它是 agent 的**生命容器**——不仅是文件存放处，还是被 OpenClaw 按固定路径主动扫描的运行时资产。

真实的容器目录形态是 `~/.openclaw/workspace/`（✅ 本机实测存在）。它下面挂着的，是这本手册的权威位：`references/`（手册与宪章，如 v1.0 八卷与本书）、`knowledge/`（索引）、`skills/`（技能入口）、`roles/`（角色七件套）。

注意一个极易混淆的点：应用根 `~/.openclaw` 与工作区 `~/.openclaw/workspace/` 是**父子关系，不是同一个东西**。OpenClaw 主配置 `~/.openclaw/openclaw.json` 住在父目录；agent 的家当住在子目录。而 `workspace/` 下面**没有** `openclaw.json`（✅ 实测确认）。

配置里，工作区的路径以叶子字段的形式出现：`agents.defaults.workspace`（默认）与 `agents.entries.<id>.workspace`（按 agent 覆盖）。**它不是顶层 key**——早期版本曾误称存在 `workspace.path`，实测不存在。

**核心目的。**

Workspace 解决的是"这个 agent 的家当放在哪、谁在扫描它"这个问题。

一个没有容器的 agent，是流浪的：它的契约文件写在某个随手建的目录里，没人加载；它的技能散落在各处，没人索引；它的长期记忆没有落点，压缩一次就没了。

容器给的是三样东西：**一个稳定的路径（可被引用）、一次固定的扫描（可被加载）、一个可备份的边界（可被保护）。**

**拟人化映射。**

| 人的生活 | Workspace 里的对应物 |
|---|---|
| 家 | 工作区的根目录 |
| 家具与藏书 | references/ 与 knowledge/ |
| 工具箱 | skills/ |
| 衣柜与身份 | roles/ 与七份契约文件 |
| 保险柜 | 备份目标 |

这个映射的真正用处是：**当你把工作区当"家"看时，你就不会在里面随地丢垃圾，也不会随便拆墙。**

**对长期表现的影响。**

第一，决定资产可被引用。全书所有章节都在引用 `~/.openclaw/workspace/references/silicon-life-handbook/...`。这不是随便写的路径，而是容器的稳定契约。移动一次，引用全断。

第二，决定资产可被加载。SOUL / AGENTS / MEMORY 写在容器里才会被扫到；写在容器外——比如 `~/.openclaw/` 根目录——agent 永远读不到，而你不会有任何报错。

第三，决定灾难能否回滚。容器是一个可备份的边界；边界之外的东西，备份工具不一定覆盖。

**怎么写。**

写 Workspace 的本质，是**划清"容器目录"与"临时目录"的界线**。

容器目录：由 OpenClaw 管辖，禁止随意增删。`skills/`、`agents/`、`references/`、`knowledge/` 都在这一侧。

临时/个人目录：放别处。草稿、实验品、下载物、一次性脚本，统统不放进容器。这是一条只要遵守就能省下无数事故的纪律。

**技巧。**

技巧一：**记住三行路径**——应用根、工作区、agent 目录。三行都记不住的时候，不要猜、不要全盘 find，让工具报路径。

技巧二：**任何破坏性操作前先备份**。备份不是仪式，是"删除不可逆"这个物理事实的唯一对冲。

技巧三：**给工作区设一个短别名**（例如 `alias ocw='cd ~/.openclaw/workspace'`）。走错门的人，多半是因为门太多。

**常见误区。**

- 把工作区当杂物间，随手建 `tmp` / `junk` / `misc`。
- 把 agent 目录、技能目录挪来挪去，以为是"整理"。
- 把 SOUL.md 放进应用根目录，以为"放根目录最保险"。
- 删除前不备份。删除是不可逆的——至少在没有备份的情况下。

**进化阶梯。**

- L1：知道工作区在哪儿，容器目录没有被污染。
- L2：容器目录结构清晰，契约文件与技能目录各就各位。
- L3：容器有备份策略，破坏性操作前有固定动作。
- L4：容器可迁移、可重建、可审计——换一台机器，家能整体搬走。

### 概念三 · Session / Context / Queue：三层分离，别合并理解

**这是什么。**

这是本章最容易"看着都懂、实际全错"的一组概念，因为它们在日常语言里几乎是同义词。

- **Session（会话）**：一次交互的单元。它有创建、有延续、有结束。
- **Context（上下文）**：当前这一轮实际送进模型的窗口。它是**预算**，不是仓库。
- **Queue（队列）**：等待被处理的消息序列。它决定了"多条消息同时到来时，按什么顺序、由谁消费"。

三者是三个不同的东西。合并理解的代价，是在规模上来之后必然踩坑。

配置侧的真实情况（✅ 实测）：顶层 key `session` 存在，但本机内容非常简洁——`{"dmScope": "per-channel-peer"}`。**没有** `compaction` 子字段，**没有** `effectiveReserveTokens`，**没有** `contextTokenBudget`（全部 0 命中）。

**核心目的。**

三层分离解决的是三个不同的问题：会话解决"这轮对话的边界在哪"，上下文解决"这一轮模型能看到多少"，队列解决"消息怎么排队、怎么不丢"。

把三者混成一个"聊天天记录"，就会同时失去这三个问题的答案。

**拟人化映射。**

| 人的概念 | 系统对应物 | 失效时会怎样 |
|---|---|---|
| 一段对话的来回 | Session | 前后话题串味、上下文互污 |
| 此刻脑子里同时能想的事 | Context | 注意力被塞满，开始胡言乱语 |
| 待办便签队列 | Queue | 消息丢失、乱序、重复消费 |

**对长期表现的影响。**

第一，上下文是预算，不是仓库。会话越聊越长，预算被塞满，就会触发压缩；压缩后关键信息可能丢失。**这是生产环境里最常见的失败模式之一——不是模型能力退化，而是累积对话历史导致的上下文污染。**

第二，污染是渐进的。你通常在第一百轮之后才发现 agent 开始前后矛盾，此时已经浪费了大量 token 与时间。

第三，队列的语义决定了"多消息并发"时的行为。**同一时间来了三条消息，是排队、是并行、是丢弃？** 这个问题不回答，多 agent 场景下的行为就是不确定的。

**怎么写。**

写法可以浓缩成三条纪律。

纪律一：分清单轮与长期。单轮结论留在会话里，长期结论落盘到 MEMORY。**判据很简单——"未来还要不要用"。要用的，当轮落盘。**

纪律二：给会话设"寿命"。不要试图用一个会话做完所有事。不同任务、不同主题，开不同会话。**主题切换就是会话该换的时候。**

纪律三：会话结束前输出落盘清单。让"我记住了"这件事有可见的证据，而不是停留在感觉上。

**技巧。**

技巧一：把"压缩前落盘"写成纪律。压缩是静默的——它不会提示你"我压掉了什么"。所以真正的保护措施不是调压缩参数（那是常量），而是**在压缩之前，把该进长期记忆的东西写进磁盘**。

技巧二：用"跨会话复现"做验收。一个结论如果换一个会话就复现不了，它就不算被记住。

**常见误区。**

- 以为"会话历史 = 记忆"，把关键结论留在会话里不落盘。
- 以为会话可以"永久保留"。这个字段不存在，而且这个意图本身就是错的——问题不在于留不留，而在于**什么该进上下文**。
- 把"清理"当变快的手段，手动删会话、删记忆文件，删掉了不该删的长期结论。

**进化阶梯。**

- L1：知道 Session / Context / Queue 是三个东西。
- L2：关键结论当轮落盘，会话有主题边界。
- L3：有明确的落盘确认机制（会话结束前输出清单）。
- L4：上下文策略可解释——你能说清"为什么这条进上下文，那条不进"。
### 概念四 · Compaction：静默的安全阀，而不是手动清理工具

**这是什么。**

Compaction（会话压缩 / 上下文压缩）是会话逼近上下文窗口上限时的自动机制：把较早的历史总结成一份紧凑摘要，保留近期消息，让会话能继续活下去。

它的重点不是"记住全部细节"，而是"在模型窗口有限的前提下，让会话继续运行"。

这一节要先把名字钉死，因为这是本章勘误最密集的地方。

- ✅ 实测：本机 `~/.openclaw/openclaw.json`（45,662 字节）里，`compaction` / `effectiveReserveTokens` / `reserveTokens` / `reserveTokensFloor` / `contextTokenBudget` **全部 0 命中**；顶层 key `session` 只有 `dmScope`。
- ✅ 实测：`maxTokens` 只出现在 `models.providers.<p>.models[].maxTokens`（本机 2 处，取值 384000 与 65536）。它不是上下文预算字段。
- ⏳ 源码口径（未在本机验证）：常量 `MAX_COMPACTION_RESERVE_RATIO = 0.25`，以及由它算出的 `effectiveReserveTokens`。
- ❌ 已作废：v1.0 曾说"可配 `compaction.reserveTokensFloor = 20000`"。这个名字不存在，而且即使存在也**不可配置**——常量 0.25 决定了上限。

结论一句话：**压缩预算不是用户字段，是运行时算出来的值。**

**核心目的。**

压缩解决的是一个纯粹的物理问题：模型的上下文窗口是有限的。

它存在的意义，不是"帮你清理"，而是"让一个超长的会话不至于当场崩掉"。它是一道**安全阀**：平时不动，压力到顶时自动泄压。

**拟人化映射。**

人脑不会把几千轮对话一字不漏地顶在前额叶里。人会做压缩、抽象、保留近因——远事记结论，近事记细节。Compaction 就是这件事的系统实现。

而与它配套的第二个动作更关键：**在压缩之前，把该长期保留的东西写进外部笔记。** 人的做法是"脑子快装不下时赶紧记笔记"；系统的做法是压缩前的静默记忆刷写轮次——在上下文即将被压扁之前，提醒 agent 把真正该长期保留的决策、偏好、状态写入工作区的记忆文件。

**对长期表现的影响。**

第一，压缩是不可逆的信息损失。它把"逐字历史"换成"摘要"，摘要必然丢细节。**关键决策如果只存在于会话里，压缩一次就没了。**

第二，压缩是静默的。它不会告诉你"我压掉了什么"。这意味着损失没有告警，你只会在几天后发现 agent "忘了"某件事。

第三，把压缩当可调参数，会导致长期的错误方向。你会一直在"调参"上用力，而真正的问题（什么进了上下文）从未被解决。

**怎么写。**

写法只有一句：**承认它不可配，转而控制"入窗量"。**

具体到三个动作。

动作一：明确"启动时加载什么"。SOUL / USER / AGENTS 等契约该在启动时加载，这是基线上下文。

动作二：明确"永不加载什么"。归档类内容、历史日志、与本轮任务无关的大块材料，不该进窗口。

动作三：明确"何时落盘"。压缩前、会话结束前、关键决策产生的当轮——三个落盘时机，缺一个都会漏。

**技巧。**

技巧一：**把"落盘"设计成交付标准的一部分。** 一个结论产生了，就算它的交付标准是"已写入长期记忆并输出确认"。

技巧二：**用"换会话能不能复现"做压缩安全的验收。** 开一个新会话问同一件事，答不上来，说明它没有真正落在磁盘上。

技巧三：2026 年的实践视角——**压缩不是唯一解，也不是默认解。** 有团队在实测后发现，配合提示缓存（prompt caching）时，"全量保留上下文"有时比"压缩"更便宜、更快、且记得更准。所以 2026 年的正确表述是：**压缩应该是对一个已命名约束的自觉回应，而不是默认动作。** 与之并列的还有另外两条路：结构化笔记（把进度写进外部笔记文件，让进展活过窗口）、子 agent 上下文隔离（专门 agent 用干净窗口干活，只把一页摘要交回主会话）。

**常见误区。**

- 把压缩当"手动清理工具"，手动删会话、删记忆文件，删掉不该删的长期结论。
- 认为"配个阈值就能控制压缩时机"。这个字段不存在，而且这个思路是错的。
- 用"压缩参数没调好"解释"agent 忘事"。真相通常是"该落盘的没落盘"。

**进化阶梯。**

- L1：知道压缩是自动的，不是手动工具。
- L2：有当轮落盘纪律，知道真名与误植名的区别。
- L3：有三条落盘时机（压缩前 / 会话结束前 / 关键决策当轮），并有确认机制。
- L4：能在"压缩 / 笔记 / 子 agent 隔离"三条策略之间按任务形态做选择，而不是只会一招。

### 概念五 · Routing / Bindings：谁该答，是系统路由问题

**这是什么。**

Routing 决定"这条消息由谁处理"；Bindings 是路由的声明式载体。

这是本章第二个重灾区，因为"路由"这个词在配置里**没有对应的顶层 key**。

✅ 实测事实：

- 不存在 `routing` 顶层 key。
- `requireMention` 的真实路径是 `channels.feishu.requireMention`（本机为 `true`），以及 `channels.telegram.accounts.<acct>.groups.<gid>.requireMention`。**本机共 41 处：37 处 `true`、4 处 `false`。**
- `mentionPatterns[]` 的真实路径是 `agents.entries.<id>.groupChat.mentionPatterns`。**本机 18 个 agent 各 1 条。**
- `bindings` 是**真实的顶层 key**，承担 agent 与渠道之间的绑定关系。

早期版本曾声称是 `routing.requireMention: true` 且"10 处"——**`routing` 这个 key 与"10 处"这个数字，都不成立。**

**核心目的。**

Routing 解决的是多主体环境下的一个根本不确定性问题：**同一句话进来，谁有权、有责、有能力回答？**

在单 agent 世界里这个问题不明显。在多 agent 世界里，它是所有混乱的源头：抢答、无人应答、答错人、成本翻倍。

Routing 的答案是：**把"谁该答"从模型即兴判断，变成系统声明式匹配。**

**拟人化映射。**

| 组织里的概念 | 系统对应物 |
|---|---|
| 组织架构图 | `agents.entries` |
| 岗位职责与工位 | `bindings` |
| "点名才发言"的会议纪律 | `requireMention` |
| 被叫到名字才应答的规则 | `mentionPatterns` |
| 谁应该接手这件活 | 声明式路由规则 |

**对长期表现的影响。**

第一，确定性。靠 prompt 猜路由 = 不确定：模型判断随上下文波动，同一句话两次可能给出不同结果。声明式 bindings 是确定性的。

第二，可归因。任务落到谁头上是明确的，事故可以追溯。反之，出问题时无从判断"这句话本该谁接"。

第三，可扩展。3 个 agent 时靠"感觉"还能撑，10 个时必然失控——而且失控是**协调性**的，不是单点故障。

第四，成本。没有路由的多 agent 群里发一条消息，最坏情况是所有 agent 同时响应，token 消耗按 agent 数量线性放大。

**怎么写。**

写法核心是三个层次。

第一层：声明"我被哪条渠道找到"。这是 bindings 的职责——渠道、账号、对等方。

第二层：声明"我什么时候该出声"。在群里，默认不是"看到就答"，而是"被点到才答"。这正是 `requireMention` 的用途——本机 41 处里 37 处为 `true`，说明默认纪律是克制的。

第三层：声明"我叫什么"。每个 agent 的 `mentionPatterns` 决定它认哪个名字（本机 18 个 agent 各 1 条）。

**技巧。**

技巧一：**路由规则要写成结构化的条件，不要写成散文。** "如果消息里含 @某人 → 派给某人"是结构化规则；"你要在恰当的时候想到找同事"是散文——后者必然不确定。

技巧二：**一定要有默认兜底。** 当没有任何规则命中时，落到一个明确的默认承接者（通常是监督层）。没有兜底的路由，在边界情况下就是"全军哑火"。

技巧三：**让位规则要显式写。** 两个 agent 同时有资格回答时，谁让谁？这个规则不写，就是随机抢答。

**常见误区。**

- 把路由写进人格描述，期待模型"自己理解"。这是把系统层问题推给概率。
- 在 `openclaw.json` 里找 `routing` 顶层 key。它不存在。
- 引用"`routing.requireMention` 有 10 处"。真名与计数都错。
- 只配 `requireMention` 不配 `mentionPatterns`（或反之）——一个管"要不要点名"，一个管"点名认不认"，单独一个都不能闭环。

**进化阶梯。**

- L1：知道路由是独立子系统，不是 prompt 技巧。
- L2：有声明式路由规则，有默认兜底。
- L3：有让位规则，路由行为可预测、可解释。
- L4：路由规则与外部协议对齐（A2A 的 Agent Card 语义），跨系统仍可发现与委派。

### 概念六 · Tools 子系统：工具不是智能，工具设计决定上限

**这是什么。**

Tools 是 agent 与世界交互的手：读写文件、调用接口、执行命令、查询数据。

`tools` 是 `openclaw.json` 的**真实顶层 key**之一（✅ 实测）——这一点与 Routing / Heartbeat 不同，它是名副其实的顶层子系统。

一个必须立住的观点：**工具不是智能。** 工具是能力边界。智能决定"想做什么"，工具决定"做得到什么"。

2026 年的行业坐标系里，Tools 这一侧已经基本收敛到一个标准：**MCP（Model Context Protocol，模型上下文协议）**。它是 agent 连接到工具与数据源的事实标准，并且已经成为 Linux Foundation 项目。本章 2.5 节会展开它 2026 年的重大演进。

**核心目的。**

Tools 解决的是"agent 如何安全、可控、可复用地产出副作用"这个问题。

注意"副作用"三个字。查询不改世界，写入改变世界。工具的绝大部分设计难点，都在于**如何让改变世界的动作既有能力，又有边界。**

**拟人化映射。**

| 人的概念 | 工具层对应物 |
|---|---|
| 手与脚 | Tool 调用 |
| 工具与器械库 | Tool 目录（catalog） |
| 持证上岗 | 权限边界与审批 |
| 安全护具 | 沙箱与隔离 |

**对长期表现的影响。**

第一，工具的设计质量直接决定 agent 的上限。一个语义模糊的工具（参数含义不清、错误信息不可读）会让 agent 反复试错；一个语义清晰的工具会让同样的模型表现得聪明得多。**很多时候"agent 不够聪明"，其实是"工具不够清楚"。**

第二，工具的权限边界决定事故半径。同一个 agent，在有边界与无边界两套工具集下，做错事的后果量级完全不同。

第三，工具的稳定性决定长期可用性。工具是外部依赖，外部依赖会变；没有版本与失效检测的工具层，会在某个时刻静默失效。

**怎么写。**

写法上有四条纪律。

纪律一：**先问"这个工具改变世界吗"。** 只读工具与写入工具必须分开对待，前者可以宽松，后者必须收窄。

纪律二：**参数语义要能自解释。** 一个参数如果需要靠文档才能理解，它在 agent 眼里就是模糊的。

纪律三：**错误信息要可被 agent 消费。** 错误不是给人看的调试信息，而是给 agent 看的下一步线索。

纪律四：**能力对外接入优先走标准协议。** 2026 年的现实是：与其为每个服务写一套私有适配，不如让工具以 MCP 的形态接入，让工具层与 agent 框架解耦。

**技巧。**

技巧一：**从"最小可用工具集"起步。** 工具越多，选择成本越高，误用概率越大。一个 agent 有 30 个工具时的表现，通常不如它有 8 个精选工具。

技巧二：**把危险动作做成"两段式"。** 分析型动作直接执行，破坏型动作先报告再执行。这条纪律在丘总的实际环境里被反复验证过：查看/分析型会被批准，破坏/覆盖型会被拒绝——所以正确的做法是**先用 append 或新建，不要一上来就 reset**。

技巧三：**工具也要做"体检"。** 工具失效不会告警，只会让某个任务静默失败。

**常见误区。**

- 认为"工具只是给模型的函数"。它是权限边界，也是事故半径的定义者。
- 无限扩张工具集。工具越堆越多，选择质量反而下降。
- 给一个 agent 开满权限，省事但把事故半径拉满。
- 把 MCP 当成"又一个插件格式"，忽略它其实是工具层的协议收敛。

**进化阶梯。**

- L1：有可用工具，能完成基本动作。
- L2：只读与写入分离，危险动作有两段式。
- L3：工具集经过减法，错误信息可被 agent 消费。
- L4：工具以标准协议接入，与框架解耦，可被审计与替换。

### 概念七 · Skills 子系统：Skill 不是 prompt，是可复用的能力单元

**这是什么。**

Skills 是 agent 的"程序性记忆"——不是"知道什么"，而是"怎么做事"。

在 OpenClaw 里，`skills` 是**真实的顶层 key**（✅ 实测），并且它与 `tools` 是**两个独立子系统**，不是一个合并的 `tools_skills`。本机实测已盘点 **236 skills**。

一个 Skill 的最小形态，是一个带有 `SKILL.md` 的目录。它里面写的不是"人格"，而是**一套可复用的做事流程**：触发条件、步骤、坑、验证方式。

2026 年，Skills 这一侧同样已经标准化的对手：**Agent Skills（Anthropic Skills）**。Anthropic 在 2025 年 10 月发布 Agent Skills，2025 年 12 月 18 日在 agentskills.io 上把规范作为开放标准发布；到 2026 年 6 月，官方展示页上已有约 40 个兼容产品，包括 OpenAI Codex、GitHub Copilot、Cursor、Gemini CLI、VS Code 等。这是"技能格式跨框架收敛"的直接证据。

**核心目的。**

Skills 解决的是"重复劳动"问题。

没有 Skills 的 agent，每次遇到同一类任务都要重新想一遍怎么做。有 Skills 的 agent，遇到同类任务直接调出已验证的流程。

这里的核心差别不是效率，而是**质量的下限**。自由发挥的下限很低，调用成品的下限高得多。

**拟人化映射。**

| 人的概念 | Skills 层对应物 |
|---|---|
| 肌肉记忆 | 反复验证过的执行流程 |
| 操作手册 | `SKILL.md` |
| 熟练工与新手的差距 | 有 Skill 与没 Skill 的差距 |
| 师承 | Skill 的复制与传播 |

**对长期表现的影响。**

第一，Skill 是"教训的固化"。每一次踩坑之后，把避坑方式写进 Skill，就是把这个坑从"会再踩"变成"不会再踩"。

第二，Skill 是"能力的可移植形态"。人的经验带不走，Skill 可以——换个项目、换个 agent，把目录拿来即可。

第三，Skill 的写法质量直接决定触发准确率。描述写得太泛，该触发时不触发；写得太窄，不该触发时乱触发。

第四，2026 年的现实：Skill 是可被审计的。企业侧已经开始做组织级的 Skill 管控（Anthropic 在 2026 年 2 月为 Team/Enterprise 计划加入了组织级管理与默认启用）。这意味着 Skill 不再只是个人技巧，而是**组织资产**。

**怎么写。**

写 Skill 的四条纪律。

纪律一：**触发条件写在最前面，且要自足。** 读者（也就是未来的 agent）需要在前几十个字符里判断"这是不是我要的"。

纪律二：**步骤要可执行，不要可欣赏。** 每一步都要能落地成动作，而不是"要注意质量"。

纪律三：**坑要写全。** 一个 Skill 的价值，一半在步骤，一半在"我知道这里会出什么问题"。

纪律四：**控制体积，渐进披露。** 不要把一个大任务的全部细节塞进一个文件；把细节放进引用文件，按需加载。这正是 2026 年 Skills 生态里最重要的工程实践之一——**渐进披露（progressive disclosure）**。

**技巧。**

技巧一：**Skill 从"我刚做过一次的事"里长出来。** 刚踩完坑的记忆最完整，此时写成 skill 成本最低、质量最高。

技巧二：**Skill 要能被维护。** 用的时候发现过时、缺步骤、有错，当场改。**不维护的 Skill 是负债。**

技巧三：**区分"Skill 该不该存在"和"Skill 写得好不好"。** 有些东西根本不该是 Skill（一次性任务），有些该是 Skill 但写得太差（触发不了）。

**常见误区。**

- 把 Skill 当 prompt 写。Skill 是流程，不是人格描述。
- 把 Tools 和 Skills 当一个子系统，配了工具就以为技能也好了。
- 把 Anthropic Skills 当 OpenClaw Skills。前者是**只读的技能市场/格式标准**，后者是 OpenClaw 的原生子系统——同名，不同物，对位在"技能端"。
- 写了一个 Skill 就以为万事大吉，从不回头维护。

**进化阶梯。**

- L1：知道 Skill 是目录 + `SKILL.md`。
- L2：有自己的 Skill，触发条件自足。
- L3：Skill 有坑与验证段，用过即改。
- L4：Skill 形成体系，可被组织级审计与分发；能用渐进披露控制加载体积。

### 概念八 · 双模块 + 共享网关 RPC：一个必须澄清的术语

**这是什么。**

这是本章最重要的术语澄清（术语对照表 #20）。

v1.0 曾把这一层称作"**Tools+Skills 双协议**"。这个表述**已作废**。真实的结构是：

**工具与技能双模块 + 共享网关 RPC**
（Tools / Skills Dual Modules + Shared Gateway RPC）

✅ 实测支撑：

- `tools` 与 `skills` 是 `openclaw.json` 里**两个独立的顶层 key**（不是合并的 `tools_skills`）。
- 两者**共享同一个网关 RPC 通道**，端点为：`tools.catalog`（工具侧）+ `skills.status` / `skills.skillCard`（技能侧）。
- 集成测试位于主仓的 `qa/scenarios/runtime/gateway-rpc-tools-skills.yaml`（⏳ 该路径是**相对主仓根目录**的相对路径，本机未跑通验证）。

**核心目的。**

澄清"协议"和"RPC"的区别，不是文字游戏。

- **协议（Protocol）是契约**：约定双方长什么样、说什么话、怎么握手。SOUL.md 是契约，A2A 是协议，MCP 是协议。
- **RPC（Remote Procedure Call）是调用**：一次远程过程调用，请求—响应，做完就结束。

把"共享 RPC"说成"共享协议"，会导出两个错误推论：以为 Tools 与 Skills 是同一个东西的两个面；以为只要遵循某个"双协议规范"就能让两者互通。

真相是：**它们是两个独立子系统，出于工程效率共用了同一根调用管道。**

**拟人化映射。**

| 人的概念 | 系统对应物 |
|---|---|
| 左手与右手 | Tools 模块与 Skills 模块 |
| 各自不同的技能 | 一个是"能做什么"，一个是"会怎么做" |
| 同一套神经通路 | 共享的网关 RPC |
| 左手知道右手在干什么 | 通过同一网关可被统一查询（catalog / status） |

**对长期表现的影响。**

第一，影响排障方向。当"技能调不起来"时，你会知道要同时检查两件事：技能是否被注册（`skills.status` 这一侧），以及它依赖的工具是否可用（`tools.catalog` 这一侧）。**这是两个独立的失败面，不是一个。**

第二，影响可观测性。共享网关意味着两者可以被同一个入口枚举——这正是"我本机到底有多少能力"这个问题的答案来源。

第三，影响架构判断。理解了"独立子系统 + 共享管道"，就不会去做"把两者合并成一个模块"这种错误重构。

**怎么写。**

写法上只有一条：**在文档、RFC、plugin 里，一律用真名。** "'双协议'是误植"这件事本身要写清楚，否则它会一代一代传下去。

**技巧。**

技巧一：**遇到术语，先问"它是契约还是调用"。** 这个二分法能瞬间分开一大类混乱。

技巧二：**清单化两个模块各自的"健康信号"。** 工具侧看目录能否枚举、技能侧看状态与卡片能否读取。两边都绿，才叫"能力层就绪"。

**常见误区。**

- 把"双协议"当 OpenClaw 术语用。
- 把 Tools 和 Skills 当同一个子系统，配了工具就以为技能也齐了。
- 把集成测试路径当绝对路径去找，然后报"文件不存在"（它是相对主仓根目录的）。

**进化阶梯。**

- L1：知道有 Tools 和 Skills 两个模块。
- L2：知道两者共享网关 RPC，能说出三个端点名。
- L3：能用两个模块各自的健康信号做独立排障。
- L4：能在文档与对外材料里稳定使用真名，并主动纠正"双协议"这类误植。

### 概念九 · Heartbeat / Cron：节律的两个原语，别混用

**这是什么。**

这一组是"主动性"的物理基础。三个概念并列：**Heartbeat**（固定节律唤醒）、**Cron**（日历式定时）、**Compaction**（上下文压缩，见概念四）。

先说它最容易被搞错的地方：**`heartbeat` 不是顶层 key。**

✅ 实测真实路径：`agents.entries.<id>.heartbeat.every`——它是**按 agent 配置的**。本机取值形如 `kunlun: "30m"`、`peter: "2h"`。

早期版本曾声称存在顶层 `heartbeat.interval`——**不存在**。这个差别不是格式问题，而是语义问题：**心跳是每个 agent 的生理参数，不是全局开关。**

**核心目的。**

Heartbeat 解决"周期性感知"：每隔一段时间醒一次，看看有没有急事、有没有要提醒人的事、有没有该继续推进的事。它的重点不是精确，而是**周期性 + 上下文感知**。

Cron 解决"精确定时执行"：每天固定时刻发日报、每周固定时刻跑复盘。它的重点不是理解上下文，而是**在指定时间可靠执行**。

两者分工明确，合起来才构成"主动性系统"。而 2026 年的行业视角里，第三个问题变得越来越重要：**长时任务的持久执行**——任务跑到一半机器重启了怎么办？答案在于带有持久化与检查点能力的运行时，让任务能从检查点恢复，而不是把几小时的成果交给一次重启。

**拟人化映射。**

| 人的概念 | 系统对应物 |
|---|---|
| 时不时扫一眼四周 | Heartbeat 周期性巡检 |
| 手机上 9 点的日程提醒 | Cron 准点执行 |
| 工作的记忆整理 | Compaction |
| 脑子装不下时赶紧记笔记 | 压缩前的记忆刷写 |

**对长期表现的影响。**

第一，主动性的四个前提条件。真正稳定的主动性至少要满足四条：有节律（不是随时触发，有频率、有活跃时段、有冷却边界）；有场景分工（周期感知用心跳、精确定时用 Cron、事件驱动用钩子）；有上下文治理（跑得越久越容易脏，没有压缩迟早失真）；有长期记忆沉淀（如果只是"感觉它记得"，那是会话幻觉，不是记忆）。

第二，混用的后果最隐蔽。任务只是"没跑"，不报错。你往往在数据断更几天之后才发现。

第三，调度器打架是真实存在的。除了心跳与定时任务，操作系统层还有第三个调度器（macOS 上是 launchd，Linux 上是 systemd 与 crontab）。三个调度器混用，会出现"两边都在跑""两边都不跑""跑到一半被另一个打断"这三种典型症状。

第四，主动性容易滑向噪音。没有节律边界、没有熔断条件、没有升级链路的自动化，会迅速从"主动"退化为"烦人的提醒器"。

**怎么写。**

写法上有一条极重要的分界线：**固定节律写进心跳，日历时刻写进定时任务，两者不要互换。**

心跳里写 cron 表达式是无效的——它不认这套语法；反过来，需要"每天 09:00 准点"的任务写进心跳的唤醒动作里，也永远准不了点。

**技巧。**

技巧一：**心跳唤醒的动作要"上下文无害"。** 心跳唤醒的那一轮会走会话与上下文预算，所以要显式声明它用什么会话、结果落到哪。典型做法是：心跳使用独立会话（不复用长会话），结果落盘到长期记忆，不依赖会话上下文。

技巧二：**给主动性配边界。** 频率、活跃时段、冷却时间、熔断条件——四个都要有。没有边界的主动性，等于把"该不该说话"交给运气。

技巧三：**把"到点有没有跑"变成可观测项。** 调度类问题是静默的，唯一有效的对冲是主动检查产物是否落盘。

**常见误区。**

- 在心跳里写 cron 语法。
- 在配置文件里找 `heartbeat.interval`（不存在；真名是按 agent 的 `heartbeat.every`）。
- 把心跳当"更频繁的定时任务"。它管感知，不管精确。
- 让三个调度器同时管同一件事。
- 让心跳与压缩互相干扰——唤醒的那轮会话被压缩打断，或刚写进去的结论被压掉。

**进化阶梯。**

- L1：知道心跳与定时任务是两个原语。
- L2：心跳节律按 agent 配置，定时任务按日历配置，两者不混。
- L3：心跳用独立会话、结果落盘，有冷却与熔断边界。
- L4：主动性可观测、可追溯、可审计；长时任务有持久执行与检查点保障。
### 概念十 · 多 Agent 协同基础：军团不是"多开几个 bot"

**这是什么。**

多 Agent 子系统处理的是"多个独立 agent 之间如何组成一个组织"。

✅ 实测真实结构：

- agent 注册表 = `agents.entries`（按 id 索引的条目集，本机 18 个 agent）。
- agent 与渠道/对等方的绑定 = `bindings`（**真实顶层 key**）。
- 不存在 `subagents[]` 这个顶层字段——早期版本曾如此声称，实测不成立。

训练学上，这一层的正式名是**多智能体编排**
（Multi-Agent Orchestration，原：军团编制）。

它强调"编排"。这两个字是这一节的全部要害：**军团是组织系统，不是 bot 数量。**

**核心目的。**

多 Agent 子系统解决的是"分工之后如何不混乱"这个问题。

分工本身很容易——起更多 agent 就完成了。难的是分工之后的四件事：互相知道对方存在、知道谁能干什么、知道什么时候该让、出了事能追溯。

少任何一层，"多 agent"就只是"多个人在一个房间里同时说话"。

**拟人化映射。**

| 组织里的概念 | 系统对应物 |
|---|---|
| 花名册 | `agents.entries` |
| 岗位与汇报线 | `bindings` |
| 互相认识 | 各 agent 在 `AGENTS.md` 里互相声明 |
| 抢话筒与让话筒 | 响应让渡协议（Response Yield Protocol，原：让位协议） |
| 交接班 | 任务交接协议（Task Handoff Protocol, THP，原：交接棒协议） |
| 会议纪要可查 | 治理审计账本（Governance Audit Ledger，原：治理账本） |
| 值班经理 | 监督层（Supervisor Layer，原：监军） |

**对长期表现的影响。**

第一，规模效应是反的。没有协同结构的多 agent 系统，在 3 个 agent 时"看起来能用"，在 10 个时彻底失控。

第二，失控形态是协调性的。不是某个 agent 崩了，而是"任务落点不确定""同一件事被做三遍""没人做的事也没人知道"。这种故障没有单点可修。

第三，事故不可追溯。没有共享治理账本，出事后无法回答"这次是谁决定的、依据是什么"。

第四，成本是乘性的。没有让位规则，一条消息触发 N 个 agent 同时响应，成本按 N 倍增长。

**怎么写。**

写法核心是"先定组织，再定人头"。顺序反了，后面全部要重做。

第一步：**互相声明。** 每个 agent 在自己的契约文件里声明"我知道还有谁、谁能干什么、我什么时候把活交给谁"。单向声明不算声明——A 声明了 B，B 也要声明 A。

第二步：**让位规则。** 明确写"如果你更该答，我就让"。让位的判据通常是领域匹配 + 在线状态。

第三步：**交接协议。** 任务在 agent 之间转移时，交付什么、验收标准是什么、失败了回到谁——这三件事要写下来。

第四步：**共享治理。** 关键决策进一份可查的账本。

**技巧。**

技巧一：**从 2 个 agent 起步。** 两个稳定单体跑通协同，再谈第三个。这是"先单体跑稳、再上多 agent"的第一铁律的具体执行方式。

技巧二：**把"不接"当成一种能力设计。** 一个健康的 agent 应该能明确地说"这件事不该我接"。没有拒绝能力的多 agent 系统，就是抢答系统。

技巧三：**让协同结构可被机器读出。** 组织关系写在自然语言里只能给人看；写成结构化声明，系统才能据此路由。

**常见误区。**

- 批量起 agent 就宣布军团建成。没有互相声明、没有让位、没有治理，这不是军团。
- 在配置里找 `subagents[]`。它不存在；真名是 `agents.entries` + `bindings`。
- 把 A2A 协议当成"协同"的全部。A2A 是**协议侧**（agent 之间怎么通信），不含组织设计与治理——那部分是你自己的训练学任务。
- 让所有 agent 共享同一个工作区。共享意味着互相覆盖。

**进化阶梯。**

- L1：有多个 agent，能各自响应。
- L2：互相声明成对，路由规则明确。
- L3：有让位规则、有交接协议、有治理账本。
- L4：跨系统协同——与外部 agent 之间通过标准协议（A2A）互相发现与委派，组织边界不阻隔协作。

### 概念十一 · 容器与临时：一条必须写进纪律的边界

**这是什么。**

这是一个"属于骨架但不属于配置文件"的概念：**容器目录与临时目录的边界。**

容器目录：由 OpenClaw 管辖、被固定路径扫描、禁止随意增删的那一部分——`~/.openclaw/workspace/` 下的 `skills/`、`agents/`、`references/`、`knowledge/`。

临时目录：一切"写坏了也不影响系统"的东西。草稿、实验、下载物、一次性脚本。

这条边界在本章被单列为概念，是因为**它是骨架类事故里性价比最高的一条预防措施**：几乎零成本，能拦住一大批灾难。

**核心目的。**

它解决的是"哪些操作是不可逆的"这个问题。

在工作区里做删除，与在临时目录里做删除，物理上一样，后果上差一个量级。前者的后果包括：一个 agent 的全部技能消失、全书的路径引用失效、跨会话的长期记忆被清空。

**拟人化映射。**

| 人的概念 | 系统对应物 |
|---|---|
| 身体器官 | 容器目录 |
| 桌面的草稿纸 | 临时目录 |
| 手术同意书 | 破坏性操作前的备份与批准 |
| 术前影像 | 操作前的体检与取证 |

**对长期表现的影响。**

第一，决定事故是否可逆。有备份边界，事故是"恢复"；没有，事故是"重来"。

第二，决定引用是否稳定。全书的路径引用都建立在容器的稳定性上。容器一动，文档全体失效。

第三，决定纪律能否形成肌肉记忆。**能 append 或新建，就不要覆盖；非要覆盖或重置，先报告"我要做 X、影响 Y"，等批准。** 这条纪律一旦形成，就能拦住绝大多数"手滑"。

**怎么写。**

写法就是两条明文。

明文一：**容器目录禁止随意增删。** 任何破坏性操作前先备份。

明文二：**临时物一律放容器外。** 想试验就在容器外建目录。这一条能让"整理"这个动作从危险变成安全。

**技巧。**

技巧一：**把"先备份"写成操作前置条件，而不是事后补救。** 备份不是仪式，是对"不可逆"这个物理事实的唯一对冲。

技巧二：**区分审批分级。** 观察/分析型动作可以直接做；破坏/覆盖型动作必须先报告并等待明确批准。这不是流程繁琐，而是把"事故半径"显式化。

技巧三：**迁移必须复制，不能用自包含型软链。** 移动目录时，软链会把"看起来搬走了、实际指向原地"这个陷阱埋进新位置。要复制，不要链接。

**常见误区。**

- 把工作区当 `~/Downloads`。
- 在一个 agent 的工作区里"顺手整理"，挪动别人的目录。
- 用覆盖代替追加。能 append 就 append。
- 迁移用软链，然后在三个月后发现问题。

**进化阶梯。**

- L1：知道容器目录在哪、哪些不能动。
- L2：临时物不放进容器。
- L3：破坏性操作前有固定备份动作，且遵守审批分级。
- L4：容器可整体重建；迁移有可验证的 round-trip 检查，而不是"看起来搬完了"。

### 概念十二 · 子系统耦合：七个器官，一个生命

**这是什么。**

这是本章的收束性概念，也是前面十一个概念的粘合剂。

7 大子系统不是 7 个独立开关。它们之间有明确的因果链：

**Heartbeat 唤醒 → 新建或续用 Session → 消耗 Context 预算 → 可能触发 Compaction；**
**Routing 决定这一轮派给谁 → 谁的 Tools 与 Skills 被调用 → 结果落盘或被压缩掉。**

任何一个环节被单独优化，都可能在别处制造问题。

**核心目的。**

这个概念解决的是"为什么每个子系统单独看都正常，合起来还是不对"这个最折磨人的问题。

答案是：**耦合处没有契约。**

单独配置每个子系统，本质是在配置零件。而系统行为由零件之间的接口决定。接口没定义，零件再完美也组不成系统。

**拟人化映射。**

| 人的概念 | 系统对应物 |
|---|---|
| 器官之间靠血管、神经、激素相连 | 子系统靠会话、上下文、事件相连 |
| 一个器官出问题，全身有反应 | 心跳唤醒打断压缩，压缩压掉心跳的结论 |
| 体检要看指标组合，不只看单项 | 骨架要靠子系统一致性检查 |

**对长期表现的影响。**

第一，耦合故障最难定位。每个子系统单独看都正常，问题只在交界处。

第二，耦合故障是渐进的。它不会让系统崩，只会让它慢慢变得不可靠——这正是"慢性病"的定义。

第三，耦合是可设计的。你可以在契约层面**显式声明**子系统之间怎么协作，而不是期待它们自己协调好。

**怎么写。**

写法是"显式声明协作契约"。最有代表性的两个例子：

例子一：**心跳与压缩。** 心跳唤醒的动作里要写清"使用独立会话（不复用长会话），避免被压缩打断"，以及"结果落盘到长期记忆，不依赖会话上下文"。这两句话写下来，耦合故障就消失了。

例子二：**路由与能力。** 路由把任务派给某个 agent 之前，要确认它的能力层（工具与技能）可用。否则会出现"活派过去了，但对方做不了，且没人知道"。

**技巧。**

技巧一：**做一致性检查，而不是单点检查。** 心跳策略、会话策略、压缩策略三者的声明应该互相自洽——把它们放在一起读一遍，冲突会立刻显形。

技巧二：**把"耦合处"变成体检项。** 第 5 章会展开每周体检清单；本章的贡献是：**体检必须包含"子系统交界处"的项，否则永远查不到真因。**

**常见误区。**

- 逐个配置子系统，认为配完七个就是配完了系统。
- 用"每个都配对了"作为就绪判据。
- 遇到耦合问题，回到单点去调参。

**进化阶梯。**

- L1：知道子系统之间有耦合。
- L2：能识别至少一条耦合链（心跳 → 会话 → 压缩）。
- L3：在契约里显式声明子系统间的协作关系。
- L4：子系统一致性检查成为常规体检的一部分，耦合故障在发生前被拦住。

## 2.3 怎么把骨架立起来：八步点亮路径

前面十二个概念讲的是"是什么"。这一节讲"怎么点亮"。

有两条前置纪律要先说清。

第一，**这一节的步骤不是命令手册。** 具体命令由本书的操作手册类附录承担；这里给的是**叙事式的路径与判据**——每一步该问什么问题、看到什么算通过、没通过怎么办。

第二，**顺序不能跳。** 这八步是有依赖关系的：容器没立，后面的配置都无处安放；会话没分层，后面的节律会互相打架。

### 第一步 · 盘清家底：先知道你手上是什么

在改任何东西之前，先回答四个问题：**版本是多少、主配置在哪、顶层到底有哪些 key、工作区在哪。**

为什么这一步不能省？

因为本章出现的几乎所有勘误，都来自"没验证就断言"。早期版本误称 `runtime` / `workspace` / `routing` / `heartbeat` / `subagents` 是配置顶层字段——这五个名字实测都不存在。如果连"我手上这份配置长什么样"都没确认，后面所有的判断都是空中楼阁。

**判据**：你能自己列出本机配置的全部顶层 key 数量与名字（本机基准：**20 个**），并能指出工作区是应用根的**子目录**而不是同一个目录。

**没过怎么办**：回到概念二与概念三，重读路径部分。不要用全盘搜索去找路径——那会让机器卡死，而且结果不可信。

### 第二步 · 立容器边界：先划不可动的线

第二步不是配置，是**立纪律**。

在容器目录之外建一个临时区，从此所有草稿、实验、一次性脚本都放那里。然后在心里（最好也在文档里）标出不可随意增删的四个目录。

**判据**：你能一口气说出"哪些目录属于容器、哪些属于临时区"，并且未来的实验不会再落进容器。

**没过怎么办**：说明你还在把工作区当文件夹。回到概念二与概念十一。

这一步之所以排在配置之前，是因为**容器是配置的物理底座。** 边界不立，后面每一步都在流沙上做。

### 第三步 · 点亮 Runtime 与 Workspace

现在开始点亮器官。

Runtime 与 Workspace 放同一步，是因为它们共同回答"这个 agent 活着吗"。

要问的问题有三个：运行时是健康的吗？工作区被挂载了吗？容器目录完整吗（`skills/` / `agents/` / `references/` 都在）？

**判据**：三条都成立，且你能看到本机的基准数字（本机：236 个 `SKILL.md`、18 个 agent 目录）。

**没过怎么办**：**先取诊断，再动手。** 不要猜"可能是模型不行"。骨架级问题的排查顺序永远是——先做体检，再看运行时健康，最后才动配置。

### 第四步 · 会话分层：定义"入窗、落盘、寿命"

这是最容易糊过去的一步，也是长期表现的分水岭。

要定三件事。

**入窗**：启动时加载什么（契约文件是基线）、永不加载什么（归档内容、历史日志）。

**落盘**：三个落盘时机——压缩前、会话结束前、关键决策当轮。落盘要有确认，不能停留在"我记得说了"。

**寿命**：会话什么时候该换。判据是主题，不是长度。换主题就换会话。

**判据**：你能说清"这条信息为什么进上下文、那条为什么不进"；并且在一个新会话里能复现出上一个会话的关键结论。

**没过怎么办**：说明你还在把"会话历史 = 记忆"。回到概念三与概念四。

### 第五步 · 声明路由：让"谁该答"变成确定的事

这一步只有一个目标：**把"谁该答"从模型的即兴判断，变成系统的声明式匹配。**

要声明四样东西：绑定（我被哪条渠道找到）、出声规则（被点到才答）、我叫什么（认得自己的名字）、默认兜底（没人匹配时谁接）。

**判据**：发一条带点名的消息，落到正确的人；发一条不带点名的消息，落到兜底位；不会出现"全答"或"全不答"。

并且你要能在配置里指出这四样东西的**真实路径**——渠道侧的出声规则、按 agent 的提及模式、以及作为顶层 key 的绑定。

**没过怎么办**：如果你在配置文件里找 `routing` 顶层 key，停下——它不存在。回到概念五。

### 第六步 · 能力层体检：两个模块，分开点亮

能力层由两个独立子系统构成：工具模块与技能模块。它们共享同一根网关 RPC，但**健康状态要分开看**。

工具侧要问：工具目录能枚举吗？危险工具是不是收窄的？

技能侧要问：技能总数是多少（本机基准 236）？能不能读出技能状态与技能卡片？

**判据**：两侧都绿。并且你能说出共享网关的三个端点名——这意味着你理解了"两个子系统 + 一根管道"的真实结构。

**没过怎么办**：如果技能调不起来，别急着怀疑模型——先判断是"技能没注册"还是"依赖的工具不可用"，这是两个独立的失败面。

### 第七步 · 配节律：心跳管感知，定时管准点

这一步的关键不是"配上"，而是"配对"。

心跳：**按 agent 配**（真实路径在 agent 条目下的心跳节律字段），明确唤醒动作的内容、使用独立会话、结果落盘。

定时：按日历配准点任务。**不要和心跳互换场景**，也不要在心跳里写日历语法。

边界：频率、活跃时段、冷却时间、熔断条件——四项都要有。

**判据**：心跳按节律触发，唤醒的那一轮不打断长会话、不依赖会话上下文；定时任务准点执行且产物落盘；你能回答"到点到底跑没跑"，答案有证据而不是印象。

**没过怎么办**：先区分是"心跳不触发"还是"定时任务静默错过"——这是两个不同的问题，混在一起永远查不出来。另外留意操作系统层的第三个调度器是否在管同一件事。

### 第八步 · 建协同结构：先定组织，再定人头

最后一步，也是唯一"面向多个 agent"的一步。

顺序不能反：**先定协同结构，再决定 agent 数量。**

要做四件事：互相声明（成对）、让位规则（谁更该答）、交接协议（交付什么、怎么验、失败回谁）、共享治理（关键决策进账本）。

**判据**：随便挑两个 agent，它们互相都认识；一条本该让位的消息确实被让出去了；一次任务交接有明确的交付物与验收标准；出事后能查到是谁决定的。

**没过怎么办**：如果你发现自己"已经在批量起 agent、但还没定结构"，那就停下扩张。从两个稳定单体重新开始，跑通协同再加第三个。

### 九 · 八步的依赖图与失败模式速查

八步不是一份清单，是一张有向图。先说依赖，再给失败模式。

**四条硬依赖。**

- **第二步先于第三步**：容器边界没立，后面所有配置都建在流沙上。
- **第四步先于第七步**：节律会消耗上下文，会话没分层，节律一开就互相打架。
- **第五步先于第八步**：没有声明式路由，多 agent 协同根本无从建立——组织里没有点名规则，人再多也只是同时说话。
- **第六步先于第八步**：能力层没体检，"活派过去了但对方做不了"是协同里最典型的空转，而且不会报错。

把这四条连起来读，会看到一条清晰的骨架顺序：**先立物理边界，再点亮单体，再治长期，再接节律，最后才谈组织。**

**八步失败模式速查。**

| 步 | 这一步在答什么 | 典型失败模式 | 你会看到的症状 |
|---|---|---|---|
| 1 盘家底 | 我手上是什么 | 不验证就断言 | 引用不存在的字段名，照着幻觉配置改 |
| 2 立边界 | 哪些不能动 | 把工作区当杂物间 | 某次"整理"之后技能或引用集体消失 |
| 3 点亮运行与容器 | 它活着吗 | 不看诊断就猜 | 换模型、重写 prompt，问题照旧 |
| 4 会话分层 | 什么进窗口、什么落盘 | 把会话历史当记忆 | 一百轮后开始前后矛盾 |
| 5 声明路由 | 谁该答 | 靠人格描述猜路由 | 抢答刷屏，或全军哑火 |
| 6 能力层体检 | 它能做什么 | 把两个模块当一个看 | 技能调不起来，却去怀疑模型 |
| 7 配节律 | 什么时候醒 | 心跳与定时混用 | 到点没醒，或醒得太频繁 |
| 8 建协同结构 | 组织怎么运转 | 先扩人头、后定结构 | 三个 agent 能用，十个失控 |

**逐条补充说明。**

**第一步的失败模式最隐蔽，因为它的症状是"自信"。** 一个没验证过配置结构的人，会非常确信地去找 `runtime` 顶层 key、去改 `heartbeat.interval`、去调 `routing.requireMention`——这三个名字都不存在，但他不会怀疑自己的前提，只会怀疑"我是不是哪儿写错了"。

**第二步的失败模式最贵。** 它不需要任何配置错误，只需要一次"顺手整理"。而且它的发作有延迟：删掉一个目录的当天一切正常，几天后某个 agent 突然不会做某件事。

**第三步的失败模式最常见。** "不看诊断就猜"是人类在不确定性下的默认反应，它的问题不是耗时，而是**方向错**：你在模型层用力，问题在骨架层。

**第四步的失败模式最慢性。** 污染不会中断任何一次对话，只会让质量单调下降。所以它最容易被误判为"模型退化了"。

**第五步的失败模式最戏剧。** 它的症状是二元的：要么全答，要么全不答。二元的症状通常好定位，但它的根因常被误判为"模型不听话"。

**第六步的失败模式最容易误诊。** "技能调不起来"至少要分成两种：技能没被注册、技能依赖的工具不可用。这两个是不同的失败面，混在一起排查，就会在两个面之间来回跳。

**第七步的失败模式最静默。** 调度类问题只表现为"任务没跑"，不报错。所以它必须配一个可观测项——产物是否落盘。

**第八步的失败模式最贵，也最容易被激励。** "起更多 agent"是一个有即时反馈的动作（看起来能力变强了），"先定协同结构"是一个没有即时反馈的动作。**所以人总是先做错的那件事。** 唯一有效的对冲是纪律：先结构，后人头。

**一个统一的自检问句。**

八步走完之后，用一句问话做总验：

**"如果现在有七个子系统里任何一个静默失效，我能多快发现？"**

- 回答"一周内会发现"——说明有体检习惯，骨架是活着的。
- 回答"等出问题才知道"——说明八步只是"配过了"，不是"点亮了"。

这个区别，就是本章和一份配置说明书的区别。

### 八步之后

八步全绿，意味着七个子系统全部点亮——这时候系统骨架才算立起来。

要特别强调一句：**"装完就自动就绪"是幻觉。** 安装有终点，"就绪"没有终点。不会有任何提示告诉你"✓ 全部就绪"。7 个子系统不像插件那样列在清单里，不主动验证就看不见。

反面教材是真实存在的：曾经出现过"某个子系统以为就绪、实际没跑"的事故——比如能力矩阵连续 26 天没有续期、任务连续失败没人管、心跳字段没配导致主动性为零但毫无报错。这类事故的共同点是：**没有任何一个红灯，因为根本没人去点灯。**

所以八步点亮之后，还有一句话要刻进纪律里：**每周复跑一次。** 不是怀疑你配错了，而是"配了就烂"是常态——配置会漂，依赖会变，节律会被打断。骨架是需要定期体检的，不是一次建成永逸。

### 八步点亮勾选清单

把八步的判据压成一张可以逐项打勾的清单。它不适合当手册查，适合当**每次复跑时的对照面**。

- **一 · 盘家底**——我能自己列出本机配置的顶层 key 数量与名字，并知道工作区是应用根的子目录。
- **二 · 立边界**——我能说出哪些目录属于容器、哪些属于临时区；未来的实验不会再落进容器。
- **三 · 点亮运行与容器**——运行时健康、工作区已挂载、容器目录完整，且我知道本机的技能数与 agent 数基准。
- **四 · 会话分层**——我能说清"这条信息为什么进上下文"；并且换一个新会话，关键结论仍能复现。
- **五 · 声明路由**——点名消息落到正确的人，未点名消息落到兜底位；不会全答，也不会全不答。
- **六 · 能力层体检**——工具侧与技能侧两个失败面各自是绿的；我能说出共享网关的三个端点名。
- **七 · 配节律**——心跳按节律唤醒且不打断长会话；定时任务准点执行且产物落盘；"到点跑没跑"有证据。
- **八 · 建协同结构**——任取两个 agent 互相都认识；该让位的让出去了；交接有交付物与验收标准；事故可追溯。

**怎么用这张清单。**

第一次是逐项做。之后是**每周对照着看一遍**，重点看两件事：哪些项从绿变黄了（配置漂移），哪些项"你以为还绿但没验证过"（自查空洞）。

两个真实的教训值得写在这里：曾经出现过某个子系统**连续 26 天没有续期**却无人察觉，也曾出现过任务连续失败、没有任何人接手。这两个事故的共同点不是技术难度，而是——**清单上那一项从来没被人看过。**

八步点亮的真正产物不是绿灯，而是**"会不会去看"这个习惯**。习惯在，骨架就活着；习惯不在，八步走完的当天就是它最好的状态。

## 2.4 骨架级误区八则：把器官当成别的东西

这一节的八个误区有一个共同特征：**它们都不会立刻报错。**

它们不会让你看到红色的失败信息，只会让系统在几十天里慢慢变得不可靠。这正是骨架类问题难缠的原因——**没有痛感的错误，没人会去查。**

每一个误区按四段展开：**现象 → 为什么错 → 怎么救 → 怎么预防。**

### 误区一 · 把 Workspace 当成普通文件夹

**现象。**

新人在工作区里随手建目录、丢文件、删目录，把它当下载目录用。某天删掉一个"看起来没用"的目录，agent 的全部技能消失，或者全书的路径引用集体失效。

**为什么错。**

因为工作区是"生命容器"，不是文件夹。

它下面挂着的 `skills/`、`agents/`、`references/`、`knowledge/` 都是被 OpenClaw **按固定路径扫描**的运行时资产。移动或删除一个目录，等于**物理删除一个 agent 的全部上下文**。而且 `references/` 里放着这本书本身——动它，全书所有命令示例当场失效。

代价是不可逆的：至少在没有备份的情况下，删除就是删除。

**怎么救。**

第一步，先备份，再动手。第二步，用 append 或新建替代覆盖。第三步，如果一定要重置，先报告"我要做 X、会影响 Y"，等明确批准——观察/分析型操作可以直接做，破坏/覆盖型必须等批准，这不是流程繁琐，是把事故半径显式化。

**怎么预防。**

记住三行路径：应用根、工作区、agent 目录。在容器外建一个临时区，从此草稿与实验一律不进容器。把"任何破坏性操作前先备份"写成条件反射。

### 误区二 · 把 Session / Context / Queue 当成一回事

**现象。**

作者以为"会话历史就是上下文"，把所有东西都往一个会话里塞。聊到两百轮之后，agent 开始胡言乱语、前后矛盾、把三天前的结论说反。

**为什么错。**

Session、Context、Queue 是三个不同的东西：会话是交互单元，上下文是当前送进模型的窗口，队列是待处理消息的顺序。合并理解，就必然踩坑。

更根本的错误是把上下文当"仓库"。**上下文是预算。** 会话越聊越长，预算被塞满，就触发压缩；压缩把较早历史换成摘要，关键信息可能就此消失。这是生产环境里最常见的失败模式——**不是模型能力退化，而是累积对话历史导致的上下文污染。**

污染是渐进的。你通常在一百轮之后才发现，此时已经浪费了大量 token 与时间。

**怎么救。**

立刻做两件事：把关键结论落盘到长期记忆，并输出写入确认；把"关键结论必须当轮落盘"写成操作纪律。

**怎么预防。**

分清单轮与长期：单轮结论留会话，长期结论落盘。给会话设"寿命"，判据是主题不是长度。会话结束前输出落盘清单。用"换个会话还能不能复现"做验收。

### 误区三 · 用 prompt 猜路由，不用声明式路由

**现象。**

多 agent 场景下，作者在人格描述文件里写一大段"如果用户问 X 就找 Y，请自行判断该由谁来回答"。结果路由随机、抢答、答错人。

**为什么错。**

**路由是系统层的事，不是人格层的事。**

它应该按声明式规则匹配，而不是靠模型即兴判断。模型的判断会随上下文波动，同一句话两次可能给出不同结果；声明式规则是确定性的。

靠 prompt 猜路由的第二个后果是成本：没有规则的群里发一条消息，最坏情况所有 agent 同时响应。

第三个后果是可扩展性：3 个 agent 时看起来还行，10 个时彻底失控——而且失控是协调性的，不是单点故障。

**怎么救。**

把路由规则从人格描述里搬出来，写成结构化的条件式；补上默认兜底（无人匹配时落到监督层）；补上让位规则（谁更该答）。

**怎么预防。**

在配置里认准真实路径：出声规则在渠道侧（如飞书渠道的 `requireMention`），提及模式在按 agent 的分组会话字段下，绑定是真实顶层 key。**不要去找 `routing` 顶层 key——它不存在。** 也不要引用"10 处"这类早期误报的数字。

### 误区四 · 把 Heartbeat 和 Cron 混为一谈

**现象。**

需要"每小时巡检"的人，把日历语法写进了心跳；需要"每天 09:00 发日报"的人，把任务塞进了心跳的唤醒动作。结果两者都不按预期工作。

**为什么错。**

心跳与定时任务是两个原语，分工不同：**心跳管周期性感知**（固定节律、上下文感知，重点不是精确）；**定时任务管准点执行**（日历时刻，重点不是理解上下文）。压缩是第三个并列原语。

混用的后果是"到点没醒"或"醒太频繁"。而且这类故障最隐蔽——任务只是没跑，不报错。你往往在数据断更之后才发现。

还有第三个调度器在暗处：操作系统层（macOS 上是 launchd，Linux 上是 systemd 与 crontab）。三个调度器管同一件事，会出现"两边都跑""两边都不跑""跑到一半被打断"。

**怎么救。**

把日历语法从心跳里移出去，把准点任务交给定时器；检查操作系统层的调度器是否与它们重叠；确认心跳的节律是**按 agent 配置**的，而不是全局一个数。

**怎么预防。**

在心跳的唤醒动作里显式声明"使用独立会话、结果落盘"，避免唤醒轮与压缩、与长会话互相干扰。给主动性配齐四项边界：频率、活跃时段、冷却时间、熔断条件。

### 误区五 · 把 Compaction 当成手动清理工具

**现象。**

机器变慢，第一反应是"清一下上下文""清一下记忆"，于是手动删会话、删记忆文件，删掉了不该删的长期结论。

**为什么错。**

两个错都在这里：**压缩是自动安全阀，不是手动工具；压缩预算不可配置。**

本机实测：`compaction` / `effectiveReserveTokens` / `reserveTokensFloor` / `contextTokenBudget` 在主配置里**全部 0 命中**。顶层会话 key 的内容只有渠道私聊作用域一项。也就是说，早期文档里"可配 `compaction.reserveTokensFloor = 20000`"是**误植**——这个名字不存在，而且即使存在也不可配。

第三个错是归因错误：把"agent 忘事"归因到"压缩参数没调好"，于是长期在错误方向上用力，真正的问题（什么进了上下文、什么落盘了）从未被解决。

**怎么救。**

承认不可配，转而控制"入窗量"：明确启动加载什么、永不加载什么、三个落盘时机。想调整压缩相对空间，唯一有意义的杠杆是上下文预算本身相关的配置，而不是那些不存在的心想字段。

**怎么预防。**

把"该落盘的没落盘"作为"agent 忘事"的第一嫌疑，而不是压缩。把"压缩前落盘"写成纪律。记住真名与误植名的区别，并在文档里主动纠正。

### 误区六 · 把多 Agent 协同当成"多开几个 bot"

**现象。**

需要多个角色协作，做法是"再起五个 agent，名字不同"，以为这就是军团。结果它们互相不知道对方存在，无法接力，无法避让，任务落点不可追溯。

**为什么错。**

**军团是组织系统，不是 bot 数量。**

多智能体编排（Multi-Agent Orchestration，原：军团编制）强调"编排"。它至少包含四层：互相声明、路由、让位协议、共享治理。

- 没有互相声明 → 无法路由。
- 没有让位规则 → 抢答。
- 没有共享治理 → 事故不可追溯。
- 没有交接协议 → 任务在边界处蒸发。

少任何一层，都不是军团。3 个 agent 时"看起来能用"，10 个时彻底失控。

**怎么救。**

停下扩张。从两个稳定单体开始，先把"互相声明成对 + 让位规则 + 交接协议 + 治理账本"这四件事补齐，再谈第三个 agent。

**怎么预防。**

先定协同结构，再决定 agent 数量。把"不接"设计成一种能力——健康的 agent 应该能明确说"这件事不该我接"。

### 误区七 · 把 Runtime 当成 prompt 执行器

**现象。**

作者以为 Runtime 只是"把 prompt 发给模型"，于是所有行为设计都围绕"写好 prompt"；忽略了工作区挂载、工具调用、队列、生命周期这些能力。

**为什么错。**

因为 **Agent 不是一个 prompt，而是独立运行单元。**

把 Runtime 降维成转发器，等于放弃了它的核心能力：会话管理、工具沙箱、权限边界、节律唤醒。你以为自己在写 prompt，实际上放弃了让 agent 活起来的全部机制。

这个误区的破坏力在于它自我印证：只要 prompt 写得够好，短会话里确实能跑得不错。于是错误信念被强化，直到长会话、多 agent、主动任务出现——此时所有缺的器官同时暴露。

**怎么救。**

改写心智模型三行：Runtime 是独立运行单元（挂载工作区 + 队列 + 工具 + 生命周期）；prompt 是一次输入，运行在 Runtime 之上；契约是持久挂载的七份文件，启动时加载。

**怎么预防。**

遇到"人格分裂"，先查是不是一个身体装了多个灵魂；遇到"记不住昨天的事"，先查工作区文件是不是写全了、是不是被加载了。

### 误区八 · 认为 7 大子系统是"7 个独立开关"

**现象。**

逐个配置子系统——配了路由不管会话，配了心跳不管压缩。结果子系统之间互相干扰：心跳唤醒的那轮会话被压缩打断，压缩把心跳刚写进去的结论压掉。

**为什么错。**

因为**子系统是耦合的**。

它们之间存在明确的因果链：心跳唤醒 → 新建或续用会话 → 消耗上下文预算 → 可能触发压缩；路由决定这一轮派给谁 → 谁的工具与技能被调用。

单独看每一项都正常，问题在耦合处。这类故障最难定位，因为每个子系统单独看都通过了检查。

**怎么救。**

在契约层面显式声明子系统之间怎么协作：心跳的动作里写明用独立会话、结果落盘；路由派活前确认对方能力层可用。

**怎么预防。**

做一致性检查，而不是单点检查。把心跳策略、会话策略、压缩策略放在一起读一遍，冲突会立刻显形。把"子系统交界处"列为固定体检项——不查交界处，永远找不到真因。

### 八则之后：三种母体病与一条排查顺序

把八个误区再往上抽象一层，会发现它们其实是三种母体病的不同表现。

**母体病一：把"器官"当成"零件"。**

症状是——把工作区当文件夹（误区一）、把压缩当手动清理工具（误区五）、把七个子系统当七个独立开关（误区八）。共同点是：**把有生命的东西降维成可任意搬运的物件。**

这种病的根因是没有"容器"这个概念。一旦你承认工作区是容器、压缩是安全阀、子系统有耦合，这三个误区会同时消失。

**母体病二：把系统层问题推给模型层。**

症状是——用 prompt 猜路由（误区三）、把 Runtime 当 prompt 执行器（误区七）。共同点是：**在一个错误的方向上用力，而且用力得很认真。**

这种病最危险的地方在于它自我印证：短会话里，prompt 写得好的确能跑得不错；于是"一切靠 prompt"这个信念被不断强化，直到长会话、多 agent、主动任务同时出现，所有缺的器官一起暴露。

**母体病三：把"数量"当"结构"。**

症状是——把多 agent 协同当多开几个 bot（误区六）。它其实是母体病一的另一个面：**以为增加同类的数量就能产生新的性质。**

三个 bot 不是军团，就像三块砖不是房子。

**一条排查顺序。**

骨架级问题有一条固定的排查顺序，请把它当成肌肉记忆：

**先做体检 → 再看运行时健康 → 最后才动配置。**

顺序不能反。反过来做（先动配置）会导出三种典型后果：越改越乱，最后把能跑的系统改坏；把系统层问题误判成模型问题，换了模型也没用；没有日志依据，同样的坑下次再踩。

这条顺序的价值不在于它快，而在于它**保证你的每一次改动都有依据**。骨架问题没有痛感，所以唯一能对抗它的，是纪律——而不是直觉。

## 2.5 深度专题

### 专题一 · 2026 前沿追踪：协议层、技能层、运行时安全的三条新战线

本章讲的七个器官，在 2024 年的行业图景里几乎都是"各框架自己造轮子"。到了 2026 年，其中三条战线已经出现了明确的收敛。这一节追踪这三条战线，并说明它们对本章骨架的影响。

#### 战线一 · 工具层：MCP 走向无状态

**事实（✅ 已核实，据官方发布与多家厂商工程博客）。**

Model Context Protocol 的当前规范版本是 **2026-07-28**：它在 2026-05-21 作为候选版本发布，于 2026-07-28 正式成为当前版本，同时把前一个版本（2025-11-25）转为 Final。规范版本序列为：

`2024-11-05 → 2025-03-26 → 2025-06-18 → 2025-11-25 → 2026-07-28`

据维护者自己的表述，这是**协议自发布以来最大的一次修订**。核心变化有五项：

**一、核心无状态化。** 移除了协议级会话与 `Mcp-Session-Id` 头。

**二、移除初始化握手。** `initialize` / `initialized` 两步握手被整段删除（SEP-2575）；协议版本、客户端信息、客户端能力改为随**每一个请求**通过 `_meta` 传递；新增 `server/discover` 方法，让客户端按需获取服务端能力，而不是在上线时一次性确定。

**三、引入多轮往返请求（Multi Round-Trip Requests, MRTR）。** 允许服务端在执行中途请求额外输入，而不必维护长连接会话。

**四、废弃三项旧特性**：Roots、Sampling、Logging。

**五、HTTP 面标准化。** 一组小而明确的 HTTP 头被标准化，把中间件真正关心的字段搬出 JSON-RPC 正文——例如 `tools/call` 会带上方法名与工具名头，任何工具参数都可以被提升为头字段（SEP-2243）。这让负载均衡、代理、网关、WAF、可观测性工具**不必做深度包检测**就能处理 MCP 流量。

**生态侧同步信号**：四大一级 SDK 在同一天（2026-07-28）发布对新规范的支持；C# SDK 直接跳到 v2.0；有基于 SDK v2 的开源框架报告包体缩小约 83%、速度提升约 25%，其理由是新的客户端—服务端拆分。

**为什么这对本章重要。**

第一，它印证了本章"工具模块 + 技能模块共享一根网关 RPC"这个结构的合理性——**协议收敛的方向是"调用面标准化"，而不是"能力面合并"。**

第二，无状态化直接降低了工具层与运行时生命周期耦合的强度。对本章的骨架含义是：工具层可以更彻底地从会话状态中解耦，工具调用的可路由性、可观测性、可治理性都上升了一个台阶。

第三，也意味着一个现实的注意点：**2026 年之后，"会话"这一概念在 MCP 侧不存在了，它完全归属运行时。** 谁是会话的主人？答案更清楚了——Runtime 与它的 Session 子系统。这正是本章把 Session 单列为一个器官的意义。

> ⏳ 边界说明：上述 SEP 编号与个别措辞出自二手工程报道，未逐条比对官方规范原文；引用到具体编号时请以官方规范为准。

#### 战线二 · 协同层：A2A 走向生产可用

**事实（✅ 已核实，Linux Foundation 官方发布 + 项目文档）。**

Agent2Agent（A2A）协议由 Google 于 2025 年 4 月发布，2025 年 6 月 23 日捐赠给 **Linux Foundation**；2026 年 3 月 12 日发布**首个稳定、生产就绪的 v1.0 规范**，2026 年 5 月发布 v1.0.1。

2026 年 4 月 9 日，Linux Foundation 宣布：A2A 项目已获得**超过 150 家组织**支持，在 Google Cloud、Microsoft Copilot Studio 与 Foundry、Amazon Bedrock AgentCore 等平台上有深度集成，并已在多个行业出现生产部署。

官方定位非常明确：**A2A 与 MCP 互补。** A2A 定义 agent 之间如何通信与协调（跨组织边界），MCP 定义 agent 如何连接内部工具与数据源。两者共同构成互操作多智能体系统的基础层。生态上层还出现了支付与加密方向的扩展（如 AP2 与 x402 扩展）。

**为什么这对本章重要。**

第一，它印证了本章把"多 Agent 协同"单列为一个器官的正确性——协同不是某一个框架的特性，是**协议层**的事。

第二，也是关键的边界提醒：**A2A 只覆盖协同的协议侧。** 它管"agent 之间怎么说话"，不管"agent 之间怎么分工、怎么让位、怎么记功"。后者是训练学的任务，也是本章"互相声明 + 让位协议 + 交接协议 + 治理账本"这四层要解决的问题。**协议给你通路，组织设计给你秩序，两者不可互替。**

第三，迁移警告：v1.0 相对早期版本改动了方法名、参与者模型、Agent Card 接口与若干字段名。如果要做升级，请走官方迁移指南——这类改动不会向后兼容。

#### 战线三 · 技能层：Agent Skills 成为跨框架标准

**事实（✅ 已核实，据 Anthropic 发布与生态分析）。**

Anthropic 于 2025 年 10 月发布 **Agent Skills**（即大众熟知的 Claude Skills），并在 2025 年 12 月 18 日通过 agentskills.io 把规范作为**开放标准**发布。一个 Skill 的本质是"一个包含 `SKILL.md` 的目录"。

到 2026 年 6 月，官方展示页上约有 **40 个兼容产品**，覆盖 OpenAI Codex、GitHub Copilot、Cursor、Gemini CLI、VS Code 等。Anthropic 官方还发布了 `skill-creator`（写技能的技能）等元工具，并在 2026 年 2 月为 Team / Enterprise 计划加入组织级技能管理与默认启用，同时提供财务、法务、人力等方向的成品插件。

生态分化为两类目录：**官方策展目录**（小而经过审核，含 Atlassian、Canva、Cloudflare、Figma、Notion、Ramp、Sentry、Stripe、Zapier 等合作伙伴技能）与**社区目录**（巨大、开放、基本未经审计）。

**为什么这对本章重要。**

第一，它印证了"Skill 是可复用能力单元"这个定位，且这个定位已经跨框架成立。

第二，它把本章概念七里那条工程纪律抬到了标准层面：**渐进披露（progressive disclosure）** ——技能目录按需加载，不要一次性把全部细节塞进上下文。这和本章概念四（压缩与入窗量治理）是同一件事的两个切面。

第三，一个必须写清的区分：**Anthropic Skills 是格式标准与技能市场（对 OpenClaw 而言是"只读"的外部资产），而 OpenClaw 的 Skills 是原生子系统。** 两者同名，不同物。

第四，安全含义：社区目录基本未审计。**技能是"程序性记忆"，也是可执行内容的载体。** 引入未审计技能，等价于在有边界的工作区里执行未知流程。这一点在下一小节会更清楚。

#### 战线四 · 上下文层：从"提示工程"到"上下文工程"

**事实（✅ 已核实，行业共识已成文）。**

2026 年，"上下文工程"（context engineering）已经取代"提示工程"成为主流表述。它的定义是：**决定模型在每一次调用中看到什么**——系统提示、工具定义、对话历史、旧的工具输出、检索到的文档、当前问题，全部在竞争同一份有限的注意力预算。

行业把常见策略归纳为四类：**写入（write）**——把上下文存到窗口之外；**选择（select）**——把需要的拉进窗口；**压缩（compress）**——只保留完成任务所需的 token；**隔离（isolate）**——拆开上下文，让每个任务有干净窗口。

三条主流长时策略各有适用面：**压缩**适合大量往来的会话；**结构化笔记**（把进度写进外部笔记文件）适合有明确里程碑的迭代工作；**子 agent 架构**适合并行研究与分析——每个子 agent 在自己的窗口里可能消耗数万 token，但只交回一两千字的浓缩摘要。

一个值得注意的反直觉发现：有团队在生产环境实测后报告，配合提示缓存时，"保留全量上下文"常常比"压缩"更便宜、更快、且记得更准；因此他们的结论是——**压缩应该是对一个已命名约束的自觉回应，而不是默认动作。**

另一个概念被正式命名：**上下文腐烂（context rot）**——如果质量随会话变长而下降，那不是提示写得不好，是上下文腐烂。

**为什么这对本章重要。**

第一，它把本章概念三、概念四从"OpenClaw 的一处机制"提升为"行业公认的独立学科"。Session / Context / Queue 的三层分离，正是这一学科的系统实现。

第二，"隔离"这条策略直接对应本章概念一（独立 Runtime）：**子 agent 上下文隔离，是大型任务里最有效的上下文工程模式之一**——每个子 agent 有独立窗口与独立工具权限，主会话只保留编排层信息，不被文件级细节污染。

第三，"压缩不是默认解"这一条，是对本章概念四最有力的外部印证：**不要把压缩当清洁工，要把它当一次有理由的决策。**

#### 战线五 · 安全层：运行时隔离成为硬需求

**事实（✅ 已核实，多家平台工程文档与安全公告）。**

2026 年，AI agent 的代码执行沙箱已经成为独立的基础设施品类。

隔离强度的分层很清晰：**microVM**（如 Firecracker，每个工作负载独立内核，硬件级边界，能拦住整类内核攻击）> **用户态内核**（如 gVisor，强隔离但无完整 VM 开销）> **加固容器**（seccomp / AppArmor / 能力收紧，**仅在执行的代码是你审查过并信任的时候**才够用，因为容器共享宿主内核）。

平台侧的代表：E2B（Firecracker microVM）、Modal（gVisor，scale-to-zero）、Daytona（默认 Sysbox，其文档称"无硬件虚拟化开销的 VM 级隔离"，注意该产品在 2026 年 6 月转为闭源，最后开源版本为 v0.190.0）、Vercel Sandbox（Firecracker microVM）、Cloudflare 与 Docker 的沙箱方案。

这些平台强调了几个 2026 年才被普遍接受的工程判断：

- **有状态性比冷启动速度更重要。** 对真实 agent 而言，关键是"工作量能累积而不是每次重置"——前一步的产物是后一步的输入。把沙箱只按冷启动速度排名，是选错了坐标轴。
- **沙箱不是万能。** 2026 年初出现过一个真实案例：某自动化平台的 JavaScript 表达式求值器存在严重的沙箱逃逸漏洞，修补于 1.123.17 与 2.5.2 版本。这个事件强化了一个结论——**运行时隔离本身不够；工作流级控制、凭据收窄、分层执行，才是当任何单层失效时仍能兜住的东西。**
- **纵深防御是标准做法**：沙箱 + 监控 + 审批门 + 签名产物。并且**限制 agent 的作用域**——从窄而明确的任务起步，让失败的爆炸半径可控，再逐步扩能力。

**为什么这对本章重要。**

第一，它把本章概念一（Runtime）与概念六（Tools）的共同命题"事故半径"落到了具体技术层：运行时隔离不是一个可选项，是执行不可信代码的**前置条件**。

第二，它对本章的实践路径有直接影响：**"危险动作两段式"（先报告、等批准）与"只读/写入分离"不是保守，而是与行业纵深防御同构的做法。**

第三，它给"通道守门员"这类角色提供了技术底座——在军团语境里，守门员的职责（守在容器门口、拦住不该动的操作）在 2026 年的对应物就是运行时边界的执行者。

#### 战线六 · 执行层：长时任务需要持久执行

**事实（✅ 已核实，运行时平台侧共识）。**

2026 年，运行时选型被明确分成两类需求：**执行代码/编码型 agent**，优先选有按会话隔离的沙箱运行时（硬边界 + 快速冷启动最重要）；**长时自主型 agent**，优先选有**持久执行（durable execution）** 能力的运行时——例如 LangGraph Platform、Cloudflare Durable Objects、Amazon Bedrock AgentCore Runtime 这类，可以从检查点恢复，而不是把几小时的成果交给一次重启。

**为什么这对本章重要。**

它正面回应了本章概念九里那个容易被忽略的问题：**心跳唤醒的主动性，只有在"醒来之后能不丢进度"时才有长期价值。** 一个每隔 30 分钟醒一次、但每次醒来都从零开始的 agent，不是主动的 agent，是失忆的闹钟。

#### 前沿追踪小结：三条收敛与一条空隙

把六条战线压成一句判断：

**工具层在收敛（MCP 无状态化）、协同层在收敛（A2A 生产可用）、技能层在收敛（Agent Skills 跨框架）——而"运行时骨架"这一层，仍然没有收敛到任何一个框架里。**

各家仍然各占一到两个器官：有人长于编排，有人长于沙箱，有人长于数据，有人长于协议。**没有任何一家把"独立运行时 + 工作区挂载 + 会话分层 + 上下文压缩 + 节律唤醒 + 协同治理"当成一个统一骨架来交付。**

这正是本章存在的最强论据，也是下一节对位表要逐项展示的东西。

#### 逐家说明

**LangGraph —— 最接近 Runtime 的同思路者，但没有心跳。**

LangGraph 的运行时是图：节点做事（模型调用、工具调用、检索），边控流，状态在节点之间传递。这个"有状态的有向图"与本章概念一（独立运行单元）思路高度重叠，估计重叠度约 70%。

它最强的地方是**持久化**：0.3.x 系列把检查点 API 打磨得更锋利，并提供了 Postgres 检查点实现与工具输出的流式能力；到 2026 年，状态持久化与人在环路检查点被进一步强化。

它的关键缺口有三个：**没有原生心跳与定时**（要周期唤醒，得外挂调度器）；**没有工作区生命容器概念**；**没有压缩**（上下文治理要自建）。另外它的图路由不等于声明式绑定——路由是"图的一部分"，不是"独立的声明式规则层"。

**AutoGen —— 2026 年发生了身份变更。**

AutoGen 的多 agent 对话能力（群聊、发言者选择、可插拔记忆）在 2024–2025 年是最完整的协同实现之一。它在 2026 年 2 月发布了 1.0 GA，把 v2 的事件驱动架构提升为正式版（老版本代码不能原样运行）。

但更重要的是它 2026 年的**身份变更**：Microsoft 把 AutoGen 与 Semantic Kernel 合并为一个继任者——**Microsoft Agent Framework**，其 1.0 在 2026 年 4 月 3 日正式发布。AutoGen 本身进入维护模式：现有部署可以继续运行、继续拿安全修复，但新功能落在继任框架里。

对本章读者的含义有两条。第一，AutoGen 是"协同充分、骨架缺失"的典型：它有很好的对话与协同，但没有工作区、没有心跳、没有压缩、没有运行时隔离。第二，选型时要注意生命周期风险——**一个框架进入维护模式，意味着它后面的骨架缺口不会有人补。**

> ⏳ 版本与 star 数在不同来源之间不一致（本手册 2026-09-27 实拉口径与部分第三方统计差异明显），引用具体数字前请自行复核。

**CrewAI —— 角色编排最简单，也最薄。**

CrewAI 的心智模型是"角色扮演的团队"：定义角色、任务、流程，让它们协作。它的学习曲线最平缓，2026 年的版本在企业级可观测性与调度上有明显加强。

它的优势与缺口是同一件事的两面：**上手最快，但骨架最薄。** 它没有工作区容器、没有心跳原语、没有上下文压缩、没有运行时隔离、也没有信任结算。角色编排是"多 Agent 协同"的简化版——它给你角色，不给你秩序。

**Claude Agent SDK —— 运行时的"身体感"最强的一家。**

Claude Agent SDK 从 Claude Code 的运行时里长出来。它暴露的和长时编码工作一样的那套 agent loop：文件操作、shell 命令、网络访问、MCP 服务、会话控制、子 agent、权限、生命周期钩子。到 2026 年 6 月，其版本推进到 v0.2.104 一线；TypeScript 侧把原生 Claude Code 二进制打进了包，省掉独立安装。会话以文件形式落盘（`~/.local/share/claude/sessions/` 这类路径），可以续用最近一次会话。

它是本章对位表里**最接近"独立运行单元"** 的一家：有原生运行循环、有工具沙箱、有权限模型、有子 agent 隔离、有原生 Skills。缺的是：**没有工作区生命容器概念**（文件系统与工具沙箱不等于"人格 + 记忆 + 技能的固定挂载"）、**没有心跳**、**没有自动压缩作为骨架的一部分**。

**OpenAI Agents SDK —— 原语最干净，handoff 最像路由。**

OpenAI Agents SDK 把 agent loop 包在一小组原语上：agents、tools、handoffs、guardrails、sessions、人类审批、tracing。它默认走 Responses API，同时也支持其他模型提供者。2026 年 4 月的一次重要演进把它推向"能检查文件、运行命令、编辑代码、在受控沙箱里做长时任务"的方向——加入可配置记忆、沙箱感知编排、类 Codex 的文件系统工具，并把模型拒绝显式暴露为错误类型（而不是返回空文本或重试循环）。

它的 **handoff 是本章 Routing / Bindings 在业界最接近的实现**（虽然语义上是"转交"而非"声明式绑定"），sessions 与 tracing 也确实是原生原语。缺的是：没有工作区容器、没有心跳、没有把压缩当成骨架组件。

**LlamaIndex —— 数据层最强，运行时最弱。**

LlamaIndex 强在数据与索引：文档摄取、索引、检索、查询引擎、工具化查询。对本章而言，它对位的主要是"记忆的存储侧"与"检索型工具"。

缺的几乎全部：没有独立运行单元、没有工作区、没有会话分层、没有压缩、没有心跳、没有协同组织、没有运行时隔离。**它不是本章要对比的同类物，而是本章某个器官（记忆的存储底）的强力外部实现。**

#### 对位后的三条结论

**结论一：业界各占一到两个器官，没有一家交付统一骨架。**

把整张表纵向读一遍，会看到一条斜线：每家的 ✅ 都集中在 1–2 行上，其余行是 ➖ 或 ❌。**没有一家把"运行时 + 工作区 + 会话 + 压缩 + 路由 + 节律 + 协同治理"当成一个整体契约。**

**结论二：三个器官是行业空白——Workspace、Compaction、Heartbeat。**

这三行是六家共同的空白。而它们恰好是"长期表现"的三个关键变量：**没有容器 → 长期资产无家可归；没有压缩 → 长期会话必污染；没有心跳 → 主动性无物理基础。**

这就是为什么本书把它们当成一个骨架来讲，而不是当成三个可选项。

**结论三：能收敛的已经收敛，不能收敛的必须自己设计。**

工具层已收敛到 MCP，协同协议层已收敛到 A2A，技能格式层已收敛到 Agent Skills。这三层，**跟随标准即可。**

但"骨架"这一层没有人替你交付——**独立运行时怎么划、工作区怎么挂、会话几层、压缩怎么落盘、节律怎么配边界、组织怎么定让位与治理。** 这些必须自己设计，因为你自己的业务形态、你自己的团队规模、你自己的风险边界，没有任何框架替你决定。

一句话：**协议跟标准，骨架靠自己。** 这是本章对 2026 年行业形势最核心的判断。

#### 本章的方法论边界

最后交代一件更重要的事：**本章的"7 子系统"不是从 OpenClaw 主仓源码里读出来的分类，而是从训练学需要出发做的抽象分层。**

### 附录 B · `effectiveReserveTokens` 深度说明（必读 · 附实测勘误）

> **⚠ 实测勘误（2026-09-27）**：本机 `~/.openclaw/openclaw.json`（45,662 字节）中
> **不存在** `compaction` / `effectiveReserveTokens` / `reserveTokensFloor` / `contextTokenBudget` 任一字段
> （顶层 key `session` 仅含 `dmScope`）。以下内容为 v4.0 接口层口径，**源码路径与函数名均为推测，未在本机验证**，
> 请勿据此到配置文件里查找这些字段。

**为什么 `effectiveReserveTokens` 字段不可配置？**

OpenClaw 主仓源码（截至 2026.9.4）定义了常量：

```typescript
// OpenClaw 主仓 src/session/compaction.ts（推测路径，实际以仓库为准）
export const MAX_COMPACTION_RESERVE_RATIO = 0.25;

export function computeEffectiveReserveTokens(
  contextTokenBudget: number
): number {
  return Math.floor(contextTokenBudget * MAX_COMPACTION_RESERVE_RATIO);
  // 例：200K context → 50K reserve；128K context → 32K reserve
}
```

也就是说 `effectiveReserveTokens` **不是用户字段**——它是 OpenClaw 主仓**函数返回值**，由你的 `contextTokenBudget × 0.25` 动态算出。

**v1.0 的错误**：v1.0 文档说"可配 `compaction.reserveTokensFloor = 20000`"——这是误植：
- `reserveTokensFloor` 这个名字不存在
- 即使存在也不可配置（常量 0.25 决定了上限）
- 想调整 reserve 大小只能调整 `contextTokenBudget`

**实测验证**（在你本机跑）：
```bash

grep -c "contextTokenBudget" ~/.openclaw/openclaw.json   # 本机：0
```

## 常见错误

> **本节用法**：第 2 章讲的是 OpenClaw 的 7 大子系统——Runtime / Workspace / Session-Context-Queue / Routing-Bindings / Tools-Skills / Heartbeat-Cron-Compaction / 多 Agent 协同。
> 这里的错误都是"把子系统当成了别的东西"，因此不会立刻报错，而是长期慢性病。
> 下面 8 个错误按子系统顺序排列，每个附六段式。
>
> **实测环境**：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27 · macOS 26.5.1。

### 错误 1 · 把 Workspace 当成普通文件夹

**错误现象**：新人在 `~/.openclaw/workspace/` 里随手建目录、丢文件、删目录，把它当 `~/Downloads` 用；某天删掉一个"看起来没用"的目录，agent 的全部 skills 消失了。

**错误配置**（❌ 不要这样）：

```bash
# 错误示范：把 workspace 当杂物间
cd ~/.openclaw/workspace
mkdir tmp junk misc
rm -rf skills_bak      # ❌ 可能是 skills 的备份/软链目标
mv agents/roles others/  # ❌ 移动 agent 目录
```

**为什么错**：

1. **Workspace 是"生命容器"，不是文件夹。** 第 2 章 2.1 节明确：Workspace 是 agent 的宿主体——`skills/`、`agents/`、`references/`、协议文件都在这里，且被 OpenClaw **按固定路径扫描**。
2. **移动/删除目录 = 物理删除一个 agent 的全部上下文**。这是 8/19 军团断线事故里"通道守门员"缺失的同类问题——没人守在容器门口。
3. **`references/` 里放着本书**。你随手 `mv references` 就可能让全书路径失效（本书所有章节命令都引用 `~/.openclaw/workspace/references/silicon-life-handbook/...`）。
4. **代价**：删除是不可逆的（至少在没有 `openclaw backup create` 的情况下）。

**正确配置**（✅ 应该这样）：

```bash
# 正确示范：区分"容器目录"与"临时目录"
# 容器（受 OpenClaw 管辖，禁止随意增删）：
#   ~/.openclaw/workspace/{skills,agents,references,...}
# 临时/个人目录（放别处）：
mkdir -p ~/scratch/tmp ~/scratch/junk
```

```bash
# 任何破坏性操作前先备份（真名：openclaw backup create）
openclaw backup create --help 2>&1 | head -20
openclaw backup create 2>&1 | tail -20
```

**验证命令**：

```bash
# 1) 确认容器目录完整（本机基准）
for d in skills agents references; do
  [ -d ~/.openclaw/workspace/$d ] && echo "✓ $d" || echo "❌ $d 缺失"
done

# 2) 数 skills（本机 2026-09-27 实测 236）
find ~/.openclaw/workspace/skills -maxdepth 2 -name "SKILL.md" 2>/dev/null | wc -l

# 3) 数 agents
ls -1d ~/.openclaw/workspace/agents/*/ 2>/dev/null | wc -l

# 4) 容器体检
openclaw doctor 2>&1 | tail -30
```

### 错误 2 · 忽略 Session / Context / Queue 的三层分离（长会话污染）

**错误现象**：以为"会话历史就是上下文"，把所有东西都往一个会话里塞；聊到第 200 轮后 agent 开始胡言乱语、前后矛盾——就是典型的"会话污染"。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：把长会话当主记忆，不设清理
session:
  keep_forever: true          # ❌ 无此字段，意图本身就是错的
context:
  include_all_history: true   # ❌ 会拖垮上下文
```

**为什么错**：

1. **Session / Context / Queue 是三个不同的东西。** 第 2 章 2.2 节把它们拆成独立子系统：Session 是会话单元，Context 是**当前送进模型的窗口**，Queue 是待处理消息队列。合并理解，就必然踩坑。
2. **上下文是"预算"，不是"仓库"。** 会话越聊越长，Context 预算被塞满，触发压缩（Compaction）；压缩后关键信息可能丢失（F4-1）。
3. **F7-13 / 卷五模块 3 就是这个事故**："会话污染导致越说越乱，怎么治理"。
4. **代价**：污染是渐进的，你通常在第 100+ 轮才发现，此时已浪费大量 token 与时间。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：分清单轮 vs 长期，给会话设"寿命"
# MEMORY.md（对应 Session/Context/Queue 子系统的策略面）
session_policy:
  max_turns: 80            # 到点触发压缩
  on_overflow: "compact"   # 压缩而非丢弃
memory_tiers:
  - short_term   # 当前会话
  - long_term    # 跨会话（重要结论落盘）
  - archival
```

```bash
# 把关键结论"落盘"而非留在会话里（真名：openclaw agent --message）
openclaw agent --message "把本次会话的关键结论写入 long_term 记忆" --agent my-agent 2>&1 | head -10
```

**验证命令**：

```bash
# 1) 会话长度是否超阈值
openclaw health 2>&1 | grep -i "session\|context\|queue" | head -10

# 2) 压缩配置是否生效（真名核对）
grep -rn "effectiveReserveTokens\|MAX_COMPACTION_RESERVE_RATIO" ~/.openclaw/workspace/agents/*/contracts/MEMORY.md 2>/dev/null

# 3) 排查残留的幻觉字段
grep -rn "keep_forever\|include_all_history" ~/.openclaw/workspace/agents/*/contracts/ 2>/dev/null
# 期望：无输出
```

**相关 FAQ**：F4-1（压缩后忘事）、F4-9（历史膨胀越聊越慢）、F7-13（会话污染治理）。

### 错误 3 · 用 prompt 猜路由，而不用 Routing / Bindings

**错误现象**：多 agent 场景下，作者在 SOUL/AGENTS 里写一大段"如果用户问 X 就找 Y"，期待 agent 自己判断；结果路由随机、抢答、错人。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：把路由写进人格描述，靠模型"理解"
# SOUL.md
persona: |
  当用户问到工程问题时，你应该想到要找 Xuanyuan；
  问到产品问题时找 Tiangong；问到财务时找 CFO。
  请自行判断该由谁来回答。
```

**为什么错**：

1. **路由是系统层的事，不是人格层的事。** 第 2 章 2.2 节的 Routing / Bindings 子系统正是为"谁该答"设计的——它按**声明式规则**匹配，不靠模型即兴判断。
2. **靠 prompt 猜 = 不确定。** 模型的判断会随上下文波动，同一句话两次可能给不同结果；声明式 bindings 是确定性的。
3. **F6-1 / F6-8 就是这个事故**：两个 agent 抢答、路由错人。根因不是模型不聪明，而是没有 bindings。
4. **代价**：多 agent 系统在 3 个 agent 时看起来还行，到 10 个就彻底失控。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：声明式路由规则（AGENTS.md 的 routing_rules）
subagents:
  - name: "xuanyuan"
    role: "engineering"
    routing_keyword: "@xuanyuan"
  - name: "tiangong"
    role: "product"
    routing_keyword: "@tiangong"
routing_rules:
  - "if message contains '@xuanyuan' → dispatch to xuanyuan"
  - "if message contains '@tiangong' → dispatch to tiangong"
  - "default → supervisor layer (原：监军)"
```

**验证命令**：

```bash
# 1) 路由规则是否声明式（不是散文）
grep -nA3 "routing_rules" ~/.openclaw/workspace/agents/my-agent/contracts/AGENTS.md
# 期望：形如 "if ... → dispatch to ..." 的结构化规则

# 2) 没有路由关键字时是否落到默认
grep -n "default" ~/.openclaw/workspace/agents/my-agent/contracts/AGENTS.md

# 3) 实测路由（发一条带 @ 的消息）
openclaw agent --message "@xuanyuan 汇报工程侧状态" 2>&1 | head -20
```

**相关 FAQ**：F6-1（抢活刷屏）、F6-2（让位失效）、F6-8（路由错人）。

### 错误 4 · 把 Heartbeat 和 Cron 混为一谈

**错误现象**：作者需要"每小时巡检"，于是在 `HEARTBEAT.md` 里写了一个 cron 表达式；或需要"每天 09:00 发日报"，却写进了 heartbeat 的 `on_wake`。结果两者都不按预期工作。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：heartbeat 里写 cron 表达式
# HEARTBEAT.md
schedule: "0 9 * * *"    # ❌ cron 语法，heartbeat 不认
```

**为什么错**：

1. **Heartbeat 与 Cron 是两个原语，分工不同。** 第 2 章 2.2 节的 Heartbeat-Cron-Compaction 子系统把三者并列：Heartbeat = 固定节律唤醒（`interval`），Cron = 日历式定时（cron 表达式），Compaction = 上下文压缩。
2. **混用会导致"到点没醒"或"醒太频繁"**。F3-1（heartbeat 不触发）、F3-2（cron 静默错过）、F3-5（频率太高拖垮机器）都是这两者混用的后果。
3. **launchd 是第三个调度器，更易打架。** F3-8：cron 与 macOS launchd 混用，两个调度器冲突。
4. **代价**：调度类问题最隐蔽——任务只是"没跑"，不报错，你往往在数据断更后才发现。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范 A：Heartbeat 只管"固定节律"
# HEARTBEAT.md
interval: 3600          # 每小时醒一次（固定间隔）
on_wake:
  - "检查 cron 产物是否落盘"
  - "检查 openclaw health 是否绿"
```

```yaml
# 正确示范 B：Cron 管"日历时刻"
# cron 任务（示意：每天 09:00 发日报）
schedule: "0 9 * * *"
task: "生成昨日日报并推送"
```

**验证命令**：

```bash

grep -nE "interval|on_wake" ~/.openclaw/workspace/agents/my-agent/contracts/HEARTBEAT.md
grep -nE "^\s*schedule:.*\*" ~/.openclaw/workspace/agents/my-agent/contracts/HEARTBEAT.md && echo "❌ 混用了 cron 语法"

# 2) cron 任务列表
crontab -l 2>/dev/null | head -20
launchctl list 2>/dev/null | grep -i openclaw | head -10

# 3) 健康度
openclaw health 2>&1 | grep -i "heartbeat\|cron" | head -10
```

**相关 FAQ**：F3-1（heartbeat 不触发）、F3-2（cron 静默错过）、F3-8（cron 与 launchd 打架）、F3-9（heartbeat 健康度怎么测）。

### 错误 5 · Compaction 触发条件理解错误

**错误现象**：作者认为"压缩是手动清理工具"，或认为"配个阈值就能控制压缩时机"；结果在长会话中压缩突然触发，关键信息被压掉，或压缩根本不触发导致请求被拒。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：以为压缩可以自由配置
compaction:
  trigger_at_tokens: 50000   # ❌ 非真名
  keep_last_n: 20            # ❌ 非真名
  reserveTokensFloor: 20000  # ❌ 术语表 #31 已核实不存在
```

**为什么错**：

1. **压缩预算是主仓常量，不可配置。** 术语对照表 #31 + 第 1 章契约 7：真名 `effectiveReserveTokens`（= contextTokenBudget × 0.25 上限），常量 `MAX_COMPACTION_RESERVE_RATIO = 0.25`，**字段不可配置**。
2. **压缩是"自动安全阀"，不是"手动清理"。** 它由上下文预算触发，不需要你"调时机"；你该做的是**控制进入上下文的量**（会话策略 + 落盘）。
3. **F4-6 就是这个坑**："会话压缩把关键信息压没了，怎么保底"——答案是"重要结论落盘到 long_term"，而不是"调压缩参数"。
4. **代价**：误以为可配 → 一直在错误方向上"调优"，实际问题从未被解决。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：承认不可配，转而控制"入窗量"
# MEMORY.md
compaction_policy:
  effectiveReserveTokens: "auto (main-repo constant, NOT configurable)"
  MAX_COMPACTION_RESERVE_RATIO: 0.25
# 真正的策略在"什么该进上下文"
context_policy:
  load_on_start:
    - "SOUL.md / USER.md / AGENTS.md（7 契约）"
  never_load:
    - "archival 归档内容"
```

**验证命令**：

```bash

# 期望：无输出

# 2) 确认真名命中
grep -rn "effectiveReserveTokens\|MAX_COMPACTION_RESERVE_RATIO" ~/.openclaw/workspace/ | head -5

# 3) 长会话实测压缩
openclaw agent --message "连续汇报 30 条状态" --agent my-agent 2>&1 | grep -i "compact" | head -5
```

**相关 FAQ**：F4-1（压缩后忘事）、F4-2（reserveTokensFloor 误植）、F4-6（压没了怎么保底）、F4-11（压缩预算怎么调）。

### 错误 6 · 把多 Agent 协同当"多开几个 bot"

**错误现象**：需要多个角色协作，作者的做法是"再起 5 个 agent，名字不同"，以为这就是军团；结果互相不知道对方存在，无法接力，无法避让。

**错误配置**（❌ 不要这样）：

```bash
# 错误示范：批量起 agent，不建协同结构
for n in a1 a2 a3 a4 a5; do openclaw agents add $n; done
# ❌ 没有 AGENTS.md 互相声明、没有让位规则、没有共享治理
```

**为什么错**：

1. **军团是"组织系统"，不是"bot 数量"。** 第 2 章 2.2 节的多 Agent 协同子系统包含：互相声明（AGENTS.md）、路由、让位协议（Response Yield Protocol）、共享治理。少任何一层，都不是军团。
2. **没有互相声明 → 无法路由**（F6-8）。没有让位规则 → 抢答（F6-1/F6-2）。没有共享治理 → 事故不可追溯（F6-11）。
3. **多智能体编排（Multi-Agent Orchestration，原：军团编制）** 是术语表 #6 的标准名——它强调"编排"，不是"多开"。
4. **代价**：3 个 agent 时"看起来能用"，10 个时彻底失控；且失控是**协调性**的，不是单点故障。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：先定协同结构，再起 agent
# 1) 每个 agent 声明"我能派谁"（AGENTS.md）
subagents:
  - name: "a2"
    role: "reviewer"
    routing_keyword: "@a2"
# 2) 让位规则（谁更该答）
yield_rules:
  - "if domain == a2.role and a2.online → yield to a2"
# 3) 共享治理（治理审计账本，原：治理账本）
governance:
  audit_ledger: "~~/notes/governance/ledger.jsonl"
```

**验证命令**：

```bash
# 1) 互相声明是否成对（A 声明 B，B 也声明 A）
for d in ~/.openclaw/workspace/agents/*/; do
  echo "== $(basename $d)"; grep -c "name:" "$d/contracts/AGENTS.md" 2>/dev/null
done

# 2) 让位规则是否存在
grep -rn "yield" ~/.openclaw/workspace/agents/*/contracts/AGENTS.md 2>/dev/null | head -10

# 3) 协同健康
openclaw health 2>&1 | head -20
```

**相关 FAQ**：F6-1（抢活）、F6-2（让位失效）、F6-8（路由错人）、F6-14（共享 workspace 互相覆盖）。

### 错误 7 · 把 Runtime 当成 prompt 执行器

**错误现象**：作者以为 OpenClaw 的 Runtime 只是"把 prompt 发给模型"，于是所有行为设计都围绕"写好 prompt"；忽略 Runtime 提供的 workspace 挂载、工具调用、队列、生命周期等能力。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：把 Runtime 当 API 转发器
runtime:
  mode: "prompt-forward"     # ❌ 无此字段
comments: "只要 prompt 写好，Runtime 无关紧要"
```

**为什么错**：

1. **Agent 不是一个 prompt，而是独立运行单元。** 第 2 章 2.1/模块 1 的核心论断：Runtime 负责 agent 的**独立运行**——它挂载 workspace、管理队列与生命周期、执行工具调用。
2. **把 Runtime 降维成"转发器"，会放弃它的核心能力**：会话管理、工具沙箱、权限边界、心跳唤醒都在 Runtime 层。
3. **代价**：你以为自己在"写 prompt"，实际上放弃了"让 agent 活起来"的全部机制。

**正确配置**（✅ 应该这样）：

```markdown
# 正确心智模型（写进你的 README）
Runtime = 独立运行单元（挂载 workspace + 队列 + 工具 + 生命周期）
Prompt  = 一次输入，运行在 Runtime 之上
Protocol = 持久挂载的 7 契约（启动时加载）
```

```bash
# 用 doctor 看到 Runtime 的真实职责
openclaw doctor 2>&1 | head -40
```

**验证命令**：

```bash
# 1) 确认 Runtime 在管什么
openclaw health 2>&1 | head -30

# 2) 确认 workspace 被挂载
ls -d ~/.openclaw/workspace 2>/dev/null && echo "✓ workspace 挂载"

# 3) 确认工具层可用（真名：openclaw tools / plugins）
openclaw plugins list 2>&1 | head -20
```

**相关 FAQ**：F1-3（workspace 路径）、F1-12（plugin 不识别）、F5-9（Skill 与 Tool 分不清）。

### 错误 8 · 认为 7 大子系统是"7 个独立开关"

**错误现象**：作者逐个配置子系统，把它们当独立模块——配了 Routing 不管 Session、配了 Heartbeat 不管 Compaction；结果子系统之间互相干扰（如心跳唤醒的会话被压缩打断）。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：逐个子系统独立配，不管耦合
routing: { ... }        # 只配路由
heartbeat: { ... }      # 只配心跳
# ❌ 完全没考虑 heartbeat 唤醒的会话会走 Session/Context/Compaction
```

**为什么错**：

1. **7 大子系统是耦合的。** 第 2 章 2.1 节的结构图显示：Heartbeat 唤醒 → 新建/续用 Session → 消耗 Context → 可能触发 Compaction；Routing 决定把这轮消息派给谁 → 谁的工具/Skills 被调用。
2. **F4-14 就是耦合问题的现场**："会话压缩和 heartbeat 会互相干扰吗"——答案是会，如果不设计的话。
3. **代价**：单子系统都"配对了"，但系统级行为仍不对；排查时每个子系统单独看都正常，问题在耦合处。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：显式声明子系统间的协作契约
# HEARTBEAT.md
interval: 3600
on_wake:
  - "使用独立 session（不复用长会话），避免被压缩打断"
  - "结果落盘到 long_term memory，不依赖会话上下文"
```

**验证命令**：

```bash
# 1) 心跳任务是否用独立会话
grep -nA5 "on_wake" ~/.openclaw/workspace/agents/my-agent/contracts/HEARTBEAT.md

# 2) 压缩与心跳是否互相干扰（观察日志）
openclaw health 2>&1 | grep -iE "compact|heartbeat|session" | head -15

# 3) 三件套一致性体检
grep -rn "on_wake\|session_policy\|compaction_policy" ~/.openclaw/workspace/agents/my-agent/contracts/ | head -15
```

**相关 FAQ**：F4-14（压缩与心跳互相干扰）、F3-6（主动任务越界）、F7-13（会话污染治理）。

## 新手坑

> **本节用法**：常见错误是"配错子系统"，新手坑是"根本不知道该有子系统"。
> 下面 5 个坑，是新人第一次面对 OpenClaw 系统骨架时的典型反应。
>
> **提示**：读完本节后建议跑一遍第 2 章 SOP 步骤 1–3，把 7 子系统逐个点亮。

### 坑 1 · 在 `~/.openclaw` 根目录找 workspace

**坑的场景**：新人 `cd ~/.openclaw`，`ls` 只看到配置文件，找不到 `skills/` 和 `agents/`，于是判定"我没装 skills"，或者开始乱改配置文件。

**后果**：

- **错误结论**（"没装"），进而做出错误决策（重装、换框架）。
- **配置放错位置**：把 SOUL.md 放进 `~/.openclaw/` 根目录，agent 永远读不到。
- **时间黑洞**：全盘 find 让机器卡死。

**为什么踩**：

1. **两个目录名太像**：应用根 `~/.openclaw` 与工作区 `~/.openclaw/workspace/` 是父子关系。
2. **教程常说"放 skills 里"**，省略了"workspace 的"。
3. **有 profile 时路径更不确定**（可能在 `~/.openclaw/profiles/<name>/workspace`）。

**怎么爬出来**：

```bash
# 第 1 步：直接问工具，不要猜
openclaw health 2>&1 | grep -i workspace
ls -d ~/.openclaw/workspace 2>/dev/null
ls -d ~/.openclaw/profiles/*/workspace 2>/dev/null

# 第 2 步：一旦确认，设个别名
echo "alias ocw='cd ~/.openclaw/workspace'" >> ~/.zshrc && source ~/.zshrc
```

**预防**：

- **记住三行路径**（应用根 / 工作区 / agent 目录）。
- **禁用全盘 find**，用 `openclaw doctor` 让工具报告路径。
- **真实案例参照**：F1-3（workspace 到底在哪）、F1-4（skills 有 200+ 但 agent 说无可用）。

---

### 坑 2 · 以为"会话历史 = 记忆"

**坑的场景**：新人认为 agent 能记住会话里的所有内容，于是把关键结论留在会话里不落盘。一次压缩后，agent "忘了"前面说过的关键决策。

**后果**：

- **失忆**。压缩（Compaction）会压缩旧内容，未落盘的关键信息直接丢失（F4-1）。
- **不可复现**。会话是易失的，重启/新会话后归零。
- **协作断裂**。其他 agent 读不到"只存在于某个会话里"的结论。

**为什么踩**：

1. **聊天式交互给人的直觉是"它记得"**——短期确实记得，长期不一定。
2. **不知道 short_term / long_term / archival 分层**（第 1 章契约 7）。
3. **压缩是"静默的"**，不会提示你"我压掉了什么"。

**怎么爬出来**：

```bash
# 第 1 步：立刻把关键结论落盘
openclaw agent --message "把本次会话的所有关键决策写入 long_term 记忆，并输出写入确认" --agent my-agent 2>&1 | head -20

# 第 2 步：检查 MEMORY 分层是否存在
grep -nA5 "memory_tiers" ~/.openclaw/workspace/agents/my-agent/contracts/MEMORY.md

# 第 3 步：写一条纪律进 AGENTS.md
cat >> ~/.openclaw/workspace/agents/my-agent/contracts/AGENTS.md <<'EOF'
操作纪律：
- 关键结论必须在当轮落盘到 long_term，不依赖会话上下文。
- 会话结束前输出"本次落盘清单"。
EOF
```

**预防**：

- **规则**：任何"未来还要用"的结论，当轮落盘。
- **把"落盘确认"写进交付标准**（第 3 章训练流程的验收口径）。
- **真实案例参照**：F4-1（压缩后忘事）、F4-6（压没了怎么保底）、F4-15（换机就失忆）。

---

### 坑 3 · 起一堆 agent，却没有 routing

**坑的场景**：新人为了"军团化"，起了 8 个 agent，每个都配了 SOUL；但从没配过 routing/bindings。群里发一条消息，8 个 agent 要么全答，要么全不答。

**后果**：

- **抢答刷屏**（F6-1）或 **全军哑火**（F6-5）。
- **无法归因**：任务落到谁头上不确定，事故不可追溯（F6-11）。
- **成本失控**：8 个 agent 同时响应，token 消耗 8 倍。

**为什么踩**：

1. **"多 = 强"的直觉**：起更多 agent 看起来更有能力。
2. **不知道 routing 是独立子系统**（第 2 章 2.2 节）。
3. **前 2–3 个 agent 时"看起来能用"**，问题在规模上来后才暴露。

**怎么爬出来**：

```bash
# 第 1 步：先停掉多余的 agent（保留 2–3 个）
openclaw plugins list 2>&1 | head -20
openclaw health 2>&1 | head -20

# 第 2 步：为保留的 agent 配 routing_rules（声明式）
# 见"常见错误 3"的正确配置

# 第 3 步：加默认兜底（无人匹配时落到监督层）
grep -n "default" ~/.openclaw/workspace/agents/*/contracts/AGENTS.md
```

**预防**：

- **先设计协同结构，再决定 agent 数量**。
- **从 2 个 agent 起步**，跑稳了再加。
- **真实案例参照**：F6-1（抢活）、F6-5（业军级联失败）、F6-8（路由错人）。

---

### 坑 4 · 把 Compaction 当成"手动清理工具"

**坑的场景**：新人看到机器变慢，第一反应是"清一下上下文"、"清一下 memory"，于是手动删会话、删记忆文件；结果删掉了还不该删的长期记忆。

**后果**：

- **误删长期记忆**：手动删 MEMORY 文件会丢失所有跨会话结论。
- **压缩机制被绕过**：真正的压缩是自动的安全阀，手动干预只会打乱它。
- **不可逆**。

**为什么踩**：

1. **"清理 = 变快"的朴素直觉**。
2. **不了解压缩是自动触发、预算不可配**（术语表 #31）。
3. **没有备份习惯**。

**怎么爬出来**：

```bash
# 第 1 步：先备份（真名：openclaw backup create）
openclaw backup create 2>&1 | tail -20

# 第 2 步：不要删 MEMORY，改为"归档"（archival）
# MEMORY.md 里把低频内容标为 archival，而非删除
grep -n "archival" ~/.openclaw/workspace/agents/my-agent/contracts/MEMORY.md

# 第 3 步：变慢先查真因（不是压缩的锅）
openclaw doctor 2>&1 | tail -40
```

**预防**：

- **任何删除前必 `openclaw backup create`**。
- **理解"压缩是自动的、预算是常量的、策略在入窗量"**。
- **真实案例参照**：F4-9（历史膨胀越聊越慢）、F4-11（压缩预算怎么调）、F4-15（记忆备份与迁移）。

### 坑 5 · 不看 Runtime 日志就猜问题

**坑的场景**：agent 行为异常时，新人开始凭直觉猜原因——"可能是模型不行""可能是 prompt 没写好"；从不看 Runtime 日志，也不跑 `openclaw doctor`。

**后果**：

- **盲改**：越改越乱，最后把能跑的系统改坏。
- **误判**：把系统层问题（如路由未配）误判成模型问题，换了模型也没用。
- **无法沉淀**：没有日志依据，同样的坑下次再踩。

**为什么踩**：

1. **日志看起来"难读"**，不如直接改配置有反馈。
2. **不知道 `openclaw doctor` / `openclaw health` 是"先看诊断"的入口**。
3. **缺少"先取证再动手"的纪律**（这正是本书 TEV 三证据验证要训练的）。

**怎么爬出来**：

```bash
# 第 1 步：先拿诊断，别猜
openclaw doctor 2>&1 | tail -40
openclaw health 2>&1 | head -30

# 第 2 步：看 gateway 日志（路径按本机实际情况）
ls -lt ~/.openclaw/logs/ 2>/dev/null | head -10
tail -n 100 ~/.openclaw/logs/*.log 2>/dev/null | grep -iE "error|warn" | head -20

# 第 3 步：把发现写成"现象→原因→解法→验证"四段（本书 FAQ 格式）
echo "现象: ... / 原因: ... / 解法: ... / 验证: ..." >> ~/notes/domain/silicon-life-handbook/incident-log.md
```

**预防**：

- **纪律：任何改动前先跑 `openclaw doctor`，改动后再跑一次**。
- **把日志路径写进你的 onboarding 文档**。
- **真实案例参照**：F1-6（gateway 端口被占）、F3-9（heartbeat 健康度怎么测）、F7-3（每周体检）。

### 坑 6 · 以为 7 大子系统"装完就自动就绪"

**坑的场景**：新人装完 OpenClaw，看到 `openclaw --version` 有输出，就默认"Runtime / Workspace / Session / Routing / Tools-Skills / Heartbeat / 多 Agent 协同"七大子系统全部可用、全部已配。于是从不逐项点亮，也从不逐项验证。

**后果**：

- **子系统静默缺失**。例如 Heartbeat 字段没配 = 主动性为零，但没有任何报错提示你。
- **故障定位错误**。出现"agent 不主动"时，你会怀疑模型或网络，而真因是 `HEARTBEAT.md` 空着。
- **连锁失能**。Tools 没配 → Skills 调不起来 → 协同里的 agent 无法完成需要工具的交接（第 6 章 THP）。
- **能力矩阵 26 天未续期**这类事故，本质就是"某个子系统以为就绪、实际没跑"。

**为什么踩**：

1. **安装有明确终点，子系统就绪没有终点**——没有"✓ 全部就绪"的提示。
2. **7 子系统是"隐式的"**：它们不像插件那样列在 `plugins list` 里，不主动验证就看不见。
3. **术语陌生**：新人不知道 Runtime/Queue/Compaction 是独立子系统，自然想不到要逐项检查。

**怎么爬出来**：

```bash
# 第 1 步：逐子系统点亮 + 验证（本章 2.2 节的 7 项）
# 1) Runtime
openclaw health 2>&1 | head -10
# 2) Workspace
ls -d ~/.openclaw/workspace && ls ~/.openclaw/workspace | head
# 3) Session/Context/Queue
openclaw health 2>&1 | grep -iE "session|context|queue"
# 4) Routing/Bindings
grep -nA2 "routing_rules" ~/.openclaw/workspace/agents/*/contracts/AGENTS.md
# 5) Tools/Skills
openclaw plugins list 2>&1 | head -10
find ~/.openclaw/workspace/skills -maxdepth 2 -name SKILL.md 2>/dev/null | wc -l
# 6) Heartbeat/Cron/Compaction
grep -nE "interval|on_wake" ~/.openclaw/workspace/agents/my-agent/contracts/HEARTBEAT.md
crontab -l 2>/dev/null | head
# 7) 多 Agent 协同
ls -1d ~/.openclaw/workspace/agents/*/ | wc -l

# 第 2 步：把 7 项写成 checklist，每项标 ✅/❌
mkdir -p ~/notes/domain/silicon-life-handbook
cat > ~/notes/domain/silicon-life-handbook/skeleton-check.md <<'EOF'
# 7 子系统就绪自检（2026-09-27）
- [ ] 1 Runtime
- [ ] 2 Workspace
- [ ] 3 Session/Context/Queue
- [ ] 4 Routing/Bindings
- [ ] 5 Tools/Skills
- [ ] 6 Heartbeat/Cron/Compaction
- [ ] 7 多 Agent 协同
EOF
```

**预防**：

- **把"7 子系统就绪自检"作为新 agent 的必过关卡**，未全绿不得进入训练（第 3 章准备清单第 1 项）。
- **每周体检（第 4 章 4.3 / F7-3）复跑这 7 项**，防止"配了就烂"。
- **真实案例参照**：F3-1（heartbeat 不触发）、F6-5（业军级联失败）、F7-6（能力矩阵 26 天未续期）、F7-15（任务连续失败没人管）。

## 附录 · 扉页元信息（原章首 banner 后移 · 一字未删）

> **本章是什么**：第 1 章讲的是"契约"——SOUL / USER / AGENTS / TOOLS / IDENTITY / HEARTBEAT / MEMORY 七个文件写什么、为什么这么写。
> 本章讲的是"骨架"——这七份契约被塞进 OpenClaw 的哪几个器官里、由谁加载、由谁执行、由谁叫醒、由谁压缩。
> 契约是灵魂的写法，骨架是灵魂能不能活下去的物理条件。一章讲"写什么"，一章讲"活在哪"。
>
> **本章的立场**：Agent 不是一个 prompt。一个 prompt 是一句话，agent 是一个活在容器里、有节律、会遗忘、能被路由、能调用工具、能和同类交接的**独立运行单元**。
> 这个论断不是修辞。它在 OpenClaw 里有 7 个可拆解、可验证、可单独点亮的子系统作为支撑。
>
> **实测环境**：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27 · macOS 26.5.1 · 本机 236 skills · 18 个 agent。
> 本章所有"真实路径"均出自 `~/.openclaw/openclaw.json`（45,662 字节）实测；凡未实测者一律标 ⏳。
>
> **诚实边界速览**：✅ 已实测——20 个真实顶层 key、`heartbeat` 的 per-agent 真实路径、`requireMention` 41 处、`mentionPatterns` 18 处、Tools 与 Skills 为两个独立顶层 key。
> ⏳ 待验证——`MAX_COMPACTION_RESERVE_RATIO = 0.25` 与 `effectiveReserveTokens` 为源码口径（本机配置 0 命中）、集成测试 `qa/scenarios/runtime/gateway-rpc-tools-skills.yaml` 的相对路径未在本机跑通、六大框架 2026 年版本号以官方发布为准。
>
> **业界对位**：本章 7 大子系统与 LangGraph / AutoGen / CrewAI / Claude Agent SDK / OpenAI Agents SDK / LlamaIndex 六大框架的重叠度约 70–80%；但**没有任何一家把"Runtime + Session + Queue + Compaction + Heartbeat + Workspace 挂载"当成一个统一骨架**。这正是本章存在的理由。
