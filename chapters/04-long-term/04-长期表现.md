# 第 4 章 · 长期表现：记忆、漂移与边界

---

## 4.0 · 这一章为什么存在

### 4.0.0 训虾哲学开篇 · 越跑越稳 vs 越跑越差：长期表现的二阶论

#### 4.0.0.1 一个被所有评测体系回避的问题

2026 年的 agent 评测已经相当成熟：有静态题库、有轨迹评分、有工具调用成功率、有端到端任务完成率。这些评测指向同一个问题：**它现在有多能干？**

本章要问的是另一个问题，而且是一个在现有评测体系里几乎无处安放的问题：

> **它现在很能干，那三十天后呢？**

这不是一个可以用更大的题量回答的问题。因为两次评测之间，被测对象已经变了——不是加权值变了，是**历史变多了**。它多跑了几百次任务、多了几次上下文压缩、多了几轮人格漂移、多了几个被污染的记忆条目、多了几次"上次就是这么处理"的路径依赖。

换句话说，第一次评测测的是一个**初始条件**，第二次评测测的是一个**被自己的历史改造过的对象**。把这两次分数直接相减，得到的不是"进步"，而是"进步减去自发退化"的净值。而这两者混在一起时，你看到的经常是一条平线——看起来什么都没发生，实际上是一个上升和一个下降恰好抵消。

这就是本章要建立的第一个观念：**长期表现是一个二阶量。**一阶量是"它此刻的水平"，二阶量是"它的水平随时间的变化率"。绝大多数团队在优化一阶量，而长期运行里的所有重大事故都发生在二阶量上。

#### 4.0.0.2 二阶论的三个基本命题

把这个观念展开，会得到三个命题。它们是本章全部机制的理论基础。

**命题一 · 一阶水平不能预测二阶趋势。**一个今天表现 90 分的 agent，可能在三个月后是 60 分；一个今天 70 分的，可能在三个月后是 85 分。决定趋势的不是当前水平，而是**系统里是否存在自我纠偏的机制**。这个命题解释了管理中最常见的一次误判："它一直很好，所以它以后也会很好。"

**命题二 · 退化不需要外力，进步才需要。**这是二阶论里最反直觉、也最重要的一条。退化是系统的自然方向——约束会在缺少锚点时衰减，记忆会在缺少归档时腐化，边界会在缺少对抗时松动。而进步需要有人**注入能量**：立基线、建测试集、跑轮次、做体检。

请把这句话读两遍：**退化的原因是"什么都没做"，不是"做错了什么"。**这直接推翻了常见的归因方式。当一个 agent 开始飘，大多数人的第一反应是"最近是不是改了什么"——而正确的第一反应是"最近有什么该做而没做"。

**命题三 · 稳定不是没有变化，是变化有界。**本章不追求"它永远不变"。要求一个智能体在三十天里一字不变，等于要求它不学习。本章追求的是：**它的变化在**可观测的、有界的、可解释的范围内。有些变化是好的（判断更准、边界更清），我们要让它们累积；有些变化是坏的（人格漂移、边界松动），我们要让它们被发现并处置。

三个命题合起来，构成本章的核心判断：**长期表现管理的对象不是"状态"，是"趋势"；它的工具不是"配置"，是"观测与纠偏"。**

#### 4.0.0.3 为什么"越跑越稳"和"越跑越差"是同一个起点

从命题二出发，会得到一个让很多人不适的结论：**越跑越稳和越跑越差，在起点上看起来是一样的。**

两者在第一天都表现良好。两者在第二周都还在正常工作。两者的差别只在两件事上：有没有锚点、有没有观测。有锚点的系统在漂移发生时能给出 diff；没有锚点的系统只能给出"感觉"。有观测的系统在两周内发现问题；没有观测的系统在两个月后才发现，而那时已经无法区分"哪一周开始错的"。

这不是一个"好习惯 vs 坏习惯"的差别，是一个**分岔点**：在相同的起点上，一套反馈回路的存在与否，决定了之后三十天的轨迹是收敛还是发散。

我们可以把这个分岔描述得更具体一些。想象两条从同一点出发的曲线。曲线 A（越跑越稳）在每次任务之后都会留下一点东西：一条被归档的记忆、一次被更新的基线、一个被写进测试集的新问题。这些"一点东西"在单次上是不可见的，但它们在三十次之后累积成一个**自我校正的系统**。曲线 B（越跑越差）每次任务之后什么都不留：记忆只增不归档、基线从不重设、问题从不变成测试题。三十次之后，它累积的是一个**自我污染的系统**——历史噪音占据上下文、过时的判断被当成经验复用、边界在一次次的"这次特殊"中被侵蚀。

**两条曲线的差别不在能力，在是否留下了沉淀物。**这就是本章把"落盘"看得如此重要的原因：落盘是让经验变成资产的唯一动作。

#### 4.0.0.4 二阶论对"有用"的重新定义

把二阶视角引入之后，"它有没有用"这个问题会分裂成两个问题，而第二个问题长期看更重要。

第一个问题是**能力问题**：它能不能把这件事做好？这个问题由第 3 章的训练流程回答。

第二个问题是**寿命问题**：它能不能一直把这件事做好，并且当它做不好时，系统知道吗、能纠正吗？这个问题由本章回答。

这两个问题在预算分配上有直接的推论。一个团队的常见做法是把 100% 的精力投在第一个问题上——加工具、改提示、换模型、调流程。第二个问题上投入接近 0。这在短期完全合理：第一个问题的回报可见且即时，第二个问题的回报要等到"出事"或"没出事"才被感知。

但二阶论给出了一个不对称的结论：**能力问题的收益随投入递减，寿命问题的损失随规模递增。**你接的通道越多、跑的 agent 越多、无人值守的时间越长，一次寿命事故的代价越大。当系统从"一两个 agent 手工照看"扩展到"十几个 agent 自动运行"，两个问题的权重会发生不可逆的反转。

本章因此不是"高级内容"，而是**规模化的前置条件**。这是本书把它放在第 4 章——训练流程之后、治理系统之前——的原因。

#### 4.0.0.5 两个 ⚡ 优势为什么落在这里

本章集中了全书两个标记为 ⚡（差异化优势）的能力：**优势 2（漂移治理三件套）**与**优势 3（主动性边界三档）**。这不是章节编排的偶然，而是二阶论的必然产物。

**漂移治理三件套为什么属于二阶论？**因为漂移的定义就是"随时间的变化"。单次观察无法定义漂移——你必须有基线、有锚点、有配套的检测节律。漂移治理是二阶论的操作化形态：它把"变化率"这个抽象量，拆成"锚点 + 阈值告警 + 每周体检"三个可执行的东西。

**主动性边界三档为什么属于二阶论？**因为主动性的失控也是随时间累积的。一个 agent 第一次越界时通常是轻微的、可解释的；它真正危险的地方在于**边界会松动**——每一次"这次特殊"都会让下一次更容易。三档边界（读 / 建议 / 执行）的作用是把主动性挂在明确的档位上，并且让档位的移动成为一次**显式动作**，而不是一次悄悄的改变。

两个优势的共同结构是：**它们都把"随时间发生的隐性变化"转换成"必须显式表达的事件"。**这正是二阶论的全部工程含义。本章 4.1 先给三件套与三档的完整定义，4.2 给出七步落地路径，4.3 用十个慢性误判把最常见的错误走一遍。

#### 4.0.0.6 一个必须提前说清的区分：退化 vs 进化

"越跑越差"这个词有一个危险的歧义。它让人以为所有变化都是坏事。

本章的立场是：**变化是中性的，方向才是问题。**判定方向需要一个参照物，而这个参照物不能是"上一次的样子"（那会惩罚一切改变），也不能是"我以为它该有的样子"（那会奖励一切迎合）。它必须是**基线 + 判据**：基线给出"从哪出发"，判据给出"哪些维度上，往哪个方向算好"。

这个区分在实际运行中有一组非常具体的推论，本章 4.3.2 会展开。在这里先给出结论：**有些漂移要回滚，有些漂移要接受并更新基线。**把两者混同，会导致两种对称的错误——一种是"人格优化被当成漂移而回滚"，另一种是"边界松动被当成适应而被接受"。前者会让 agent 越来越僵，后者会让 agent 越来越野。

#### 4.0.0.7 第四章要回答的五个问题

按二阶论展开，本章要回答五个问题。它们也构成本章的阅读大纲。

**问题一 · 它为什么会变？** 答案是三类机制：上下文的管理（压缩与污染）、记忆的形态（分层与检索质量）、节律的稳定性（心跳与体检）。4.1 的前半部分处理这三类。

**问题二 · 它变成了什么，我怎么知道？** 答案是有锚点的对比：`SOUL.md` 与 `drift_anchor` 的 diff、两类漂移（人格漂移 / 文档漂移）的分开定义、带数字的每周体检。4.1 的中段处理这一部分。

**问题三 · 变坏的时候怎么救？** 答案是处置纪律：刷写必须发生在压缩之前、越界必须触发降档、体检必须产出可执行项。4.2 的五步与 4.3 的十种误判处理这一部分。

**问题四 · 怎么让它不只是"不变坏"，而是"变得更好"？** 答案是让档位与基线**双向可移动**：好的漂移被评审通过后更新基线，形成正反馈。4.2.7 专门处理这一条。

**问题五 · 这一章和别的章怎么接？** 答案是接口清单：它的输入来自第 1 章的 `SOUL`/`USER`，它的节拍来自第 3 章的 heartbeat，它的输出交给第 5 章的工单与本结算。4.6.7 给出完整列表。

#### 4.0.0.8 二阶论的五条工程推论

把二阶论从观念变成工程，需要五条推论。它们分别对应本章后面的某一块机制。

**推论一 · 必须立基线，而且要早。** 基线是"变化率"这个量的分母。没有基线，"它变了"这句话不可计算。而基线有一个残酷的性质：**它只能在某个时刻被采集一次，错过就补不回来。**你今天采集的基线，记录的是今天的它；你永远无法回到上周去采集上周的它。这是本章反复强调"第一天就钉锚点"的全部理由——它不是一条最佳实践，它是一条**不可逆的时间窗口**。

**推论二 · 漂移必须被拆成可判定的维度。** "它变得不太一样了"不是一个可处置的陈述。可处置的形式是：在"措辞简洁度"这个维度上，本周偏离基线 12%；在"边界判断"这个维度上，出现了 3 次可疑放行。拆维度是让处置有落点的前提。

**推论三 · 观测的节律必须比退化的速度更快。** 如果退化需要两周才能变得明显，而你的体检一个月做一次，那么你每次发现的都是**已经累积了两周的偏差**，而这两周内的所有输出都跑在错误的参数上。**体检频率的下限，应该由退化速度决定，而不是由"多久检查一次比较合理"决定。**

**推论四 · 处置必须有闸门。** 发现漂移之后"改回去"不是处置，因为改回去可能触发新的、未观测的变化。处置需要一个闸门：什么情况下降档、什么情况下回滚、什么情况下接受并更新基线。闸门的意义在于让处置成为**可预期、可复现的动作**，而不是一次临场判断。

**推论五 · 好的变化也必须纳入流程。** 这是最容易被漏掉的一条。如果一个系统只处理"变坏"，它会逐渐退化成"禁止一切改变的机器"。二阶论的完整形态包含正反馈：好的漂移经过评审后更新基线，让新的、更高的水平成为下一次对照的起点。**没有正反馈的治理系统会自我僵化。**

五条推论的执行顺序是固定的：先立基线（推论一）→ 再拆维度（推论二）→ 然后装节律（推论三）→ 接着建闸门（推论四）→ 最后开正反馈（推论五）。**顺序颠倒会让每一步都失效**：没有维度的节律会产出一堆无法处置的报告；没有闸门的处置会变成随意改动。

#### 4.0.0.9 长期表现的四级成熟度自检表

和本书其他章节一样，这一章也提供一个可定位的自检表。它的作用不是评分，是确定"下一件事做哪一件"。

| 级 | 名称 | 判据 | 典型症状 | 下一件事 |
|---|---|---|---|---|
| **T0** | 无基线 | 没有任何 `SOUL`/`MEMORY` 的快照与版本记录 | "它好像跟以前不太一样了"——无法验证 | 立刻采集一次基线快照并版本化 |
| **T1** | 有基线，无维度 | 有快照，但对比只能靠通读全文 | 知道变了，不知道哪个维度变了 | 把对比拆成 5–8 个可判定维度 |
| **T2** | 有维度，无节律 | 能算出维度差异，但只在"感觉不对"时才做 | 发现问题时已累积数周 | 把对比挂进心跳/定时任务 |
| **T3** | 有节律，无闸门 | 每周出报告，但报告之后没有标准动作 | 报告读完了，问题还在 | 为每类偏差定义降档/回滚/接受三选一 |
| **T4** | 有闸门，无正反馈 | 处理变坏很利索，但不处理变好 | 系统越来越保守，能力上限被锁死 | 开"好漂移 → 评审 → 更新基线"通道 |
| **T5** | 闭环 | 变坏被处置、变好被吸收，两个方向都留痕 | —— | 转入第 5 章的结算与追责 |

这张表有一个使用要点：**T0 到 T2 的跨越，比 T3 到 T5 更重要。**因为 T0–T2 解决的是"看得见"的问题，而"看得见"是所有后续治理的前提。一个团队如果卡在 T1，去搭 T4 的闸门，得到的是"闸门空转"——因为输入是空的。

#### 4.0.0.10 为什么"不变味"比"变强"更难

有一个经验值得单独说：**在长期运行的系统里，保持不比提升容易。**

这个结论看起来违反直觉，但它的道理很朴素。提升是加法：加一个能力、改一处措辞、接一个工具，收益是局部的、可归因的。不变味是**守成一整片**：人格、边界、节律、记忆质量、措辞风格、判断倾向，任何一处松动都算输。

更麻烦的是，松动的方向往往是**朝着省力的方向**。省力的方向就是模型的先验方向：更长的铺垫、更温和的措辞、更少的不确定声明、更容易被说服的边界。也就是说，**退化不是随机的，它有一个稳定的方向——朝平均。**一个不做任何治理的 agent，会缓慢地从一个有性格的成员，变成一个标准的、礼貌的、无立场的助手。

这就是"不变味"难的地方：它不是抵抗一次冲击，是抵抗一个持续存在的、方向稳定的引力。抵抗引力需要持续的能量输入——**而治理系统的全部意义，就是把这个能量输入变成自动的、不依赖人的注意力的东西。**

#### 4.0.0.11 一个可以自己做的对照实验（设计说明 · 非实测结论）

本节最后给一个读者可以自己执行的验证设计。它的目的是让你亲手看到二阶论，而不是接受它。

设计是这样的：选两个同类但独立的 agent（或者同一个人格文件的两份独立实例），一个进入"有治理"组，一个进入"无治理"组。"有治理"组的定义是：有基线快照、有每周维度对比、有处置闸门。"无治理"组的定义是：正常使用，不做任何额外动作。两组跑相同的任务量、相同的时长（建议 30 天）。

在第 0 天、第 15 天、第 30 天，分别对两组做同一组测试（同一份测试集、同样的上下文配置），记录两组在若干维度上的得分。你要观察的**不是分数高低，是两条曲线之间的开口。**

这个设计有几点必须诚实交代：它不是本章已经完成的实验，而是一个可执行的验证方案；它的结论会受到任务分布、模型版本、人格文件质量的影响；样本量为 1 时它只能给出定性信号，不能给出统计结论。**它的价值在于把一个抽象论断变成一次可以亲身检验的对照。**

如果 30 天后两组曲线没有明显开口，那也是一个有价值的发现——它意味着在你当前的运行强度下，退化速度还没有超过任务的容错带宽。这时正确的结论是"记下口径、半年后重做"，而不是"治理没必要"。

#### 4.0.0.12 记忆不是仓库：二阶论视角下的记忆观

记忆在长期表现里的角色，经常被理解错。常见的理解是"记忆像一个仓库，记的越多越好，缺的是容量"。二阶论给出的理解是：**记忆是一个会自己长出来的东西，它的质量由写入规范与归档纪律决定，而不是由容量决定。**

这个差别有三个直接后果。

后果一 · **不归档的记忆会变成噪音。** 一个只增不减的记忆层，在三个月后会积累大量事务性流水。这些流水不会"静静地待着"——它们会被检索命中，占用上下文预算，稀释关键事实的权重。**记忆腐化的表现形式不是"忘了重要的"，而是"重要的被淹没了"。**

后果二 · **写入规范比检索算法更重要。** 检索质量的上限由写入质量决定。一条写成"今天处理了一些事情"的记忆条目，无论用什么检索算法都命不中；一条写成"2026-09-21 飞书通道断线，根因是 requireMention"的条目，才能被未来的问题命准。**先立写入规范，再谈检索优化**——顺序反了会白花很多力气。

后果三 · **"记住"和"读得出"是两条独立链路。** 很多失败案例里，信息其实已经写进去了，但检索没有命中，于是 agent 表现为"忘了"。把这两条链路分开观测（写入成功率 / 检索命中率），才能定位到真正出问题的那一环。

这三条后果共同支撑本章的一个机制选择：记忆三层（短期 / 长期 / 归档）不是一个存储分级，是一个**生命周期分级**——每一层对应不同的保留策略、不同的写入标准、不同的归档触发条件。

#### 4.0.0.13 越主动，越需要边界：主动性边界的二阶论基础

主动性看起来是纯粹的优点——它会自己发现、自己汇报、自己开工，这是"组织成员"和"问答机"的分水岭。但二阶论揭示了它的另一面。

**主动性的风险也是随时间累积的。**一个 agent 今天被允许在某个场景下自动动手，明天这个场景会被它自己扩展到相邻场景，下个月"自动动手"的清单已经比最初长了一倍——而整个扩张过程里没有任何一次显式的决策。这不是恶意，这是路径依赖：每一次成功都会降低下一次动手的门槛。

这就是"三档边界"（读 / 建议 / 执行）存在的理由。它把主动性从"一个连续的、会自己扩张的量"，变成"三个离散的、只能显式迁移的档位"。任何一次档位迁移都是一次**留下记录的动作**，而不是一次悄悄的发生。

三档的设计背后有一条判据：**档位的选择应当由"出错的代价"决定，而不是由"模型有多强"决定。**一个失误代价极低、且可快速回滚的动作，可以放在"执行"档；一个失误会被外部看到、且难回滚的动作，必须停在"建议"档——无论模型多强。

#### 4.0.0.14 Q&A：六个反复出现的质疑

**Q1：我的 agent 只在内网跑，很安全，还需要这一章吗？**
"安全"和"不变味"是两件事。内网降低的是外溢风险，不降低人格漂移、记忆腐化、边界松动这三类内部退化。**多数长期表现事故发生在内网。**

**Q2：每周体检太重了，能不能改成每月？**
可以，但请先量化退化速度：观察一次明显偏差从出现到被发现需要多久。如果退化在两周内就变得可见，月度体检意味着你每个月都有一半时间跑在未纠正的状态上。**体检频率是退化速度的函数，不是偏好的函数。**

**Q3：基线怎么建？我看不出该记什么。**
最小版本就三条：`SOUL.md` 的完整快照、`MEMORY.md` 的分层结构快照、一组能代表它的典型问题的固定回答样本。三条都有了，就已经排除 T0。**不要追求一次建全，先让它存在。**

**Q4：好的漂移怎么判定？**
判定好的漂移需要两个条件同时成立：一，它在某个维度上确实更符合 `SOUL.md` 的意图（而不是更符合模型的平均倾向）；二，它在测试集上没有引入回退。两条都过，才算"好漂移"。**只满足第一条的，通常是迎合。**

**Q5：漂移检测会不会误报太多，最后没人看报告？**
会，这是最常见的失败模式之一。解法不是降低标准，而是**分层**：把报告分成"必须处置"与"仅记录"两类，让前者保持稀有。一份每周 20 条都要处理的报告必然被忽略；一份每周 1–2 条需要动作的报告才会被认真读。

**Q6：这一章和治理章的分界线在哪？**
本章（第 4 章）解决"看得见"与"救得回"：发现偏差、处置偏差、把好的变化吸收进基线。治理章（第 5 章）解决"算得清"与"追得到"：把偏差变成工单、把处理结果变成信任分数、把长期表现变成可结算的账本。**本章产生事实，第 5 章把事实变成制度。**

#### 4.0.0.17 一次走查：一个"空转的治理机制"在二阶论下的读法

本节用一个真实案例做一次完整走查。案例本体在案例库卷（`_appendix-case/01-real-incidents.md` · **CASE-4 · 能力矩阵 26 天未续期：治理机制空转诊断**），这里只做二阶论视角的读法演示，不重复案件细节。

**案件的一句话形态**：一个承担"能力矩阵月度更新"的定期任务，在被设计出来之后，有 26 天没有产生续期；而在这 26 天里，没有任何人、任何机制发现这件事。

把这件事放进二阶论，会看到三个层次的问题，而它们的严重程度是递进的。

**第一层 · 任务层的问题**：那个定期任务没有正常执行（它的失败是可见的：任务记录里有错误计数）。这一层是最好修的——修配置、看日志、加告警。多数团队的复盘停在这里，然后得出"加个告警"的结论。

**第二层 · 观测层的问题**：26 天没有任何人发现，说明系统里**没有针对"该产出而未产出"的观测**。注意这个观测类型与"任务报错告警"完全不同：它的对象不是"任务是否成功"，而是"该发生的事是否发生"。**缺失的产出，默认是看不见的。**这是二阶论下的第一类盲区：你能观测到"发生了的坏事"，观测不到"没发生的好事"。

**第三层 · 二阶层的问题**：这个机制被设计出来的目的是**维护长期表现**（月度更新能力矩阵，让能力画像不腐化）。它的空转意味着：在这 26 天里，系统的长期表现**处在无人观测的状态**。也就是说，治理机制本身也退化了一次——而它退化的时候，没有任何东西在观测治理机制。

三层问题合起来，得到二阶论最重要的一条延伸：**治理机制不是治理的终点，治理机制本身也需要被观测。**这一条会直接引出第 5 章的审计通道与监督层设计（本章 4.6.3 与第 5 章 5.12）。如果没有这一层，你会得到一个很荒谬的稳定状态：**一切机制都在，一切机制都不工作，而系统看起来没有故障。**

这个走查的第一个收获是一条可执行的检查：**列出现有的所有"应该周期性发生的事"，逐条对照"上一次真的发生是什么时候"。**把"该发生而未发生"变成一张清单，是二阶论在实践中的第一件工具。

#### 4.0.0.22 三个隐性账单，以及二阶论的最后一句话

长期表现管理的缺失，代价以三种隐性方式流出。列出它们，是为了让"要不要花力气做这件事"变成一笔可算的账。

**账单一 · 你没发现的退化，已经跑在真实交付里。** 体检频率低于退化速度时，每次发现都意味着此前一段时间的所有输出都跑在偏差状态下。**这笔账的结算货币是返工与信任。**

**账单二 · 你没区分的漂移，会同时惩罚好的和坏的。** 不做方向判定的治理，会把"人格优化"和"边界松动"一起按回去。系统越来越僵，而僵化本身也是一种退化。**这笔账的结算货币是能力上限。**

**账单三 · 你没有账本，就无法回答"它值不值得更大的权限"。** 授权需要一个依据，而这个依据只能来自长期记录。没有记功与记过的系统，授权决策只能靠印象。**这笔账的结算货币是自主权。**

三笔账单指向同一件事：**二阶论的成本不在"做了多少"，在"漏了多少"。**而"漏"这件事，只有建立了观测之后才能被看见——这就是为什么本章把"看得见"排在"救得回"之前。

最后用一句话收束本节的立场，它是整章的题眼：

> **一只智能体的水平是它今天的样子，它的可靠性是它三个月后的样子。前者只需要一次好的配置，后者需要一整套不会自己停下来的机制。**


#### 4.0.0.23 一句话记住本章

如果本节只能留一句：

> **状态可以配出来，趋势只能管出来。**

配置一次，你就得到了一个当下的它；只有建立基线、装上节律、设好闸门，你才得到一个"明天仍然可信"的它。本章的全部机制，都长在这句话上。

### 4.0.1 训练学的第三问

任何一本讲 agent 的书，都要回答三个问题。

第一问是"它是什么"——一个硅基智能体（Silicon-based Agent，原：虾）到底是什么东西，它和"一个会聊天的模型"差在哪。这一问在本书第 1 章回答，落点是七个契约文件。

第二问是"怎么把它训出来"——怎么把一个通用模型，变成一个有角色、有职责、有验收标准的组织成员。这一问在第 3 章回答，落点是训练流程与心跳节拍。

第三问很少有人认真回答：**训出来之后呢？**

第三问听起来像是"维护问题"，像是"运维细节"，像是"等出事再说"。恰恰是这种听起来不紧急的位置，藏着这本训练学最重要的两块护城河。

因为它问的不是"能不能"，而是"能撑多久"。

一个 agent 第一次表现好，几乎什么都不证明。第一次，它跑在干净的上下文里；第一次，它还没被历史噪音腌过；第一次，它还没经历过一次会话压缩；第一次，它的节律问题、边界问题、记忆问题全都还没暴露。第一次是"最优条件"，不是"代表性条件"。

而真实的组织运行，从来不给你最优条件。真实运行给的是：上下文会被压缩、会话会变脏、历史会被摘要、任务会连续三个月不断、人会中途改需求、外部系统会在某个周二下午挂掉。

所以第三问的真正问法是：

> **在上下文有限、会话会脏、历史会被压缩、任务会持续变动的现实里，它还能不能保持关键事实不丢、角色不漂、节律不断、行为不散？**

这一章，就是回答这个问法的。

### 4.0.2 一个被主动进化范式（原：训虾派）反复强调的区分

在进入任何机制之前，必须先钉死一个分界，否则后面的每一步都会被误解。

行业里几乎所有叫"长期记忆"的东西，都在回答同一个问题：**怎么让它记住更多。**

MemGPT、Letta、Mem0、Zep，以及 2026 年新起的 Hindsight、Supermemory、Cognee 这一批，它们的产品形态不同、架构不同，但它们共同优化的是同一件事——**存取**：怎么分层索引、怎么向量召回、怎么压缩进提示、怎么在检索时少花 token 还多命中。

这本训练学问的是另一个问题：**怎么让它还是自己。**

这两个问题的技术外表很像，内核完全不同：

- "记住更多"是一个**工程问题**。它有明确目标函数（命中率、延迟、token 成本），有公开排行榜，有可复现的基准（LoCoMo、LongMemEval），有厂商互相打分的口水战。
- "还是自己"是一个**治理问题**。它没有排行榜，因为它的目标函数不是"取回一条信息"，而是"当我没有取回任何信息时，它仍然按它该有的方式判断"。

第一类问题，行业做得很热闹、很卷、很值钱。第二类问题，2026 年的行业**基本是空的**——不是技术难，是没人把它当成一个品类来做。

这不是一个谦虚的对比，这是一个冷冰冰的席位空缺。

把它说透：一个 agent 的记忆检索命中率做到 95%，但它的人格已经在三个月里悄悄换了方向——它开始迎合、开始回避冲突、开始把"完成"重定义为"看起来完成了"。这个系统的**记忆能力**没有任何退化，它的**可信度**已经崩了。

因为长期信任的本质，不是永远正确。长期信任的本质是**可预期性**：

- 我知道你大致会怎么判断；
- 我知道你遇到冲突时会怎么取舍；
- 我知道你不会突然变成另一个人。

记忆存取解决不了可预期性。可预期性只能靠治理解决。

### 4.0.3 跳过这一章的人，会遭遇什么

空谈护城河没有意义。我们具体一点：如果一个训练者真的跳过了这一章，只做了第 1 到第 3 章的事，他会在接下来的一到三个月里，依次遇见下面五件事。

**第一件：它开始不认得人。** 不是"忘记名字"这种可爱的小事，而是它开始把三个月前的决策前提当成无效，重新问你一遍已经拍过板的事。你没有记忆层，也没有分层策略，所有结论都和流水混在同一份文件里，于是**该记的没记住，不该占的占满了**。

**第二件：它的语气慢慢变了。** 幅度极小，每天可能只有千分之几。三个月后你回头看，发现它从"会直接说'这个我不确定'"变成了"会先肯定你再说'但也许可以考虑'"。你没有锚点，也没有基线，所以你**没有任何东西可以拿来做对比**——你只有"感觉"。而感觉不是证据。

**第三件：它的文档和现实脱节了。** 你的技能数、版本号、agent 数量、通道状态，都在变；文档里写的还是上个月的数。这不是文档懒，这是**没有检测机制**：没有任何东西会在文档与现实不一致时发出声音。

**第四件：它越权了。** 这是最贵的一件。某天它在心跳唤醒后"自主判断当前最该做的事"，然后它做了——它给外部发了消息，或者改了生产配置。你在事后复盘时发现，问题不在于它判断错了，而在于**你从来没有定义过什么叫做"错"**：你没有 allowed / forbidden / needs-confirm 这三档，所以它的每一次行动都在你默认同意的范围内。

**第五件：它的体检报告永远只有一句话——"看起来正常"。** 因为体检项没有阈值、没有数字、没有对比，所以它永远无法判定"不通过"。一个不能判"不通过"的体检，和没有体检，在结果上等价。于是"能力矩阵 26 天没有续期"这类事故可以安静地从你眼皮底下走过去。

这五件事有个共同特征：**它们都不是爆炸，都是滑坡。** 它们全部发生在系统"仍然可用"的区间里。而所有人对"仍然可用"的系统，都不会报警。

### 4.0.4 本章在全书链路中的位置

这一章是一段承前启后的桥，两端都很硬：

- **上游是第 3 章（训练流程）**。第 3 章给了你节拍——心跳（Heartbeat）什么时候来、以什么频率来、以什么闸门来。本章的"每周体检"与"阈值告警"两套防线，节拍来源就是第 3 章；本章的"会话污染"处置，处置对象也产生于第 3 章的连续运行。
- **再上游是第 1 章（生命协议 / 七大契约）**。本章的漂移锚点是 SOUL 契约（契约 2），本章的三档边界的落点是 USER 契约（契约 1）。这是本章最重要的一个结构性事实：**本章不引入任何新的文件类型，它只治理已有的协议文件。** 你能靠一份 SOUL.md 既有的人格描述拿出两个东西：一个比对锚点，和一组行动边界。
- **下游是第 5 章（治理系统）**。这一章只负责**发现**——发现漂移、发现越界、发现体检不过。发现之后的**结算**是第 5 章的活：越界与漂移进入修复工单（Remediation Ticket，原：整改单），体检通过与否进入信任评分（Trust Score，原：信誉分）与功绩账本（Merit Ledger，原：军功簿）。分工很干净：**第 4 章是传感器，第 5 章是结算所。**

再往下还有一层：第 6 章（多智能体编排，原：军团编制）要处理"多个 agent 的边界互不侵犯"，第 7 章（超维演进）要让自主目标生成（Autonomous Goal Generation）仍然受三档边界约束。

也就是说，**本章定义的三档边界，是后面三章的地基。** 地基不写，后面每一章都会变成"看起来很先进但没人敢让它自主运行"的东西。

### 4.0.5 先把 Context 和 Memory 分清

这一章后面所有的讨论，都踩在一条分界线上。这条线没分清，后面每一句都会被误读。

**Context 是"这一轮模型眼前真正能看到的东西"。** 它是一个运行时资源：有硬上限、会膨胀、会被截断、会被压缩、会被工具返回结果污染。它不属于"记忆"，它属于"此刻的注意力"。

**Memory 是"你希望它以后还能知道的东西"。** 它不天然存在于模型脑子里。它必须被写进磁盘上的文件，成为下一次重建上下文的**材料**。

这条分界推出一个残酷的结论，也是所有长期表现事故的总根因：

> **source of truth 不是模型临时记住了什么，而是磁盘上最终写下了什么。**

很多人做长期 agent 时会犯一个漂亮而致命的错误：**以为"这次会话里说过了"，以后它就会记得。**

它不会。会话结束时，那些"说过的"如果不落在文件上，就随上下文一起蒸发。而反过来，落在文件上的东西如果没人治理，就会变成慢慢压垮它的历史包袱。

所以这一章真正要处理的，是把两个方向都管住：

- 把"会丢的上下文"转化为"可重建的长期记忆"——**记忆工程**；
- 把"会腐败的会话"转化为"可压缩、可清理、可恢复的运行结构"——**上下文工程**；
- 再给这两者之上加一层"我该不该动、动了算不算越界"的判断——**边界治理**。

三件事，一个目的：**让它跑得久，而且没跑偏。**

### 4.1.1 漂移治理三件套（Drift Governance Trio）· ⚡ 优势 2

**这是什么东西。** 三件套是三个独立但互相咬合的检测动作：第一件，测**文档漂移**——SOUL.md 是不是还认识自己（当前文件 vs 初始基线，比相似度）；第二件，测**人格漂移**——agent 的行为是否偏离了它该有的人格（每周抽一批对话，让一个裁判模型来打分）；第三件，跑**每周体检清单**（Weekly Health Checklist）——把心跳健康度、记忆一致性、任务完成率一次性拉出来看。

**核心目的。** 三件套的目的不是"防漂移"，而是**把漂移从"感觉"变成"数字"**。这是它全部的价值，也是它和行业里所有"记忆管理"工具的根本分岔口：那些工具让 agent 记得更多，三件套让它**可被核对**。

**拟人化映射。** 一个真人组织成员的稳定性，从来不靠"我觉得他最近有点不一样"。它靠三样东西：他的岗位说明书还在不在（文档）、他的行为有没有偏离他的职业操守（行为）、以及有没有人每周真的坐下来做一次评估（体检）。任何一家正经组织，这三样都有；任何一个只靠"感觉"管人的团队，都会在半年内出问题。三件套就是把这三样东西，从人身上搬到 agent 身上。

**对长期表现的影响。** 没有三件套，长跑会进入一种特别危险的状态：**系统仍然产出，团队仍然满意，但判断基线已经在滑坡。** 这时最危险，因为所有外部信号都是绿的——它还能答、还能写、还能推进。你有产出，但没有方向感。三件套提供的正是方向感：一个可以回头对照的锚点，和一个可以横向对照的行为样本。

**为什么业界是空的。** 这不是我们自夸。2026 年，记忆赛道的竞争极其激烈——Mem0 在自己的研究页上报 LoCoMo 92.5、LongMemEval 94.4（厂商自测，⏳ 口径随 harness 变），Letta 在独立评测里拿到过约 83% 的 LoCoMo（⏳ 独立评测与厂商口径并存），Zep 走时序知识图谱路线并在 LoCoMo 上有公开争议（Mem0 复现给 58.44%，Zep 反驳给 75.14% ⏳）。这些数字打得头破血流，但它们争的全是"记忆取回质量"。

**没有一家在做"文档漂移 / 人格漂移 / 每周体检"这个组合。** 不是因为它难——哈希比对和抽样评分都不难。是因为行业把"长期表现"默认定义成了"记忆存取问题"，从这个定义出发，你永远走不到治理这一步。

**怎么写。** 三件套的落点非常朴素，没有任何新字段：

- 第一件的实现是**文件哈希基线 + 定期比对**。建一次基线（对 18 份 SOUL.md 求 SHA-256，落到一份基线文件），之后定期重跑、`diff` 一次。无输出即静默通过，有输出即逐份复核。本机**没有**内置的漂移字段，所以这条路是"文件级实现"，不是"配置级实现"。
- 第二件目前是**方法论**，本机未实现：抽对话、用裁判模型按一组维度评分、看评分是否跌破阈值。它的检测对象是行为，不是文件，所以它不能靠哈希。
- 第三件有本机的**真实文件结构**可以照抄。`heartbeat-state.json` 里已经有 `lastChecks`（含 `health_scan` / `overdue_alert` / `true_pulse`）、`cadenceMs`（三层节拍）、`pulse`（全军团存活）三块真数据。

**技巧。** 三条。

第一条：**先建基线，再谈检测。** 顺序错了，后面全废。没有基线的"漂移检测"只是变更日志，它只能回答"今天和昨天比变了吗"，回答不了"它离最初设计的它有多远"。而漂移最典型的形态恰恰是"温水煮青蛙"——每天变千分之几，逐日比对看不出问题，一个月累计下来人格已经明显变味。

第二条：**让沉默成为默认输出。** 检测跑完没有差异就该没有输出。天天弹告警的哨兵，两周之内就会被所有人无视——**告警疲劳是漂移检测最真实的杀手**，它杀的不是检测能力，是检测的可信度。

第三条：**三件套要分层，不要合并。** 文档漂移是文件级、可哈希、秒级完成；人格漂移是行为级、需抽样、要花 token。把它们塞进同一个检测动作里，你会得到一个"每次都太贵所以最后不跑"的东西。

**常见误区。** 一个特别典型的：以为建立了基线就算完成了。**基线不比对，等于没建。** 基线必须挂进一个会真正定期执行的地方（体检清单、心跳唤醒动作、或者一个定时任务），否则它只是一份躺在磁盘上的历史文件。

**进化阶梯。** 最低可用：哈希基线 + 每周一次 `diff`。进阶：把 `diff` 挂进高频唤醒动作，同时把体检做成有数字的报告。最佳实践：三件套全部落地 + 体检报告入库可对比趋势 + 好的漂移经过评审后**回写为新基线**（这一点后面 4.1.7 会展开，因为"漂移只会变坏"是个错误直觉）。

（卷五 · 源流）

### 4.1.2 主动性边界三档（Proactive Boundary Triad）· ⚡ 优势 3

**这是什么东西。** 一个把"主动性"分成三档的硬边界：**L1 只读**——巡检、观察、汇报，不改变任何状态；**L2 允许**——在只读基础上可以生成建议、起草产物，但不提交、不对外、不改配置；**L3 条件执行**——在明确列出的清单内、满足明确条件时，可以真正执行写操作。

三档之外，还有一份更细的**许可清单三档**，它们是同一件事的两个面：`allowed`（可以直接做，无需问，本机惯例只放只读类动作，例如读自己的记忆、读公开工具）、`forbidden`（即使被要求也不做，例如未经确认发邮件、导出个人身份信息、删除用户数据）、`needs_confirm`（问过 owner 再做，例如写外部接口、改自己的 SOUL.md、派生子 agent）。

**这两套的关系要说清**：许可清单定义"哪些动作属于哪一档"，主动性档位定义"这个 agent 当前被授权走到第几档"。前者是分类表，后者是水位线。

**核心目的。** 目的只有一个：**把"主动"和"越界"分开。** 行业里几乎所有 agent 框架的默认设定都是"能干的都干"——这不是设计疏忽，这是默认值的选择。而在真实组织里，"能干的都干"是一个危险的默认值。

**拟人化映射。** 一个新人进公司，你不会第一天就给他财务权限和对外发言权，然后说"你自己判断边界"。你会给一份权限表，而且权限是分级的、可以撤销的。**你对人做的事，为什么不对 agent 做？** 因为 agent 不会抱怨、不会尴尬、不会因为权限不足而消极怠工——所以人们下意识地觉得"给它全权更省事"。省事的代价，是它会在某一天替你做一个你没有授权的决定。

**对长期表现的影响。** 主动性有两个方向的失败，而且都是慢性病：

一个是**主动性失控**——越界推进、过度打扰，最坏的情况是对外可见且不可逆（发错消息、改了配置）。另一个是**主动性空转**——有动作、有心跳、有日志，但没有价值，看起来在跑，其实什么都没推进。三档边界的价值在于，它让"失控"在结构上变得不可能（L3 需要清单+条件），同时让"空转"可被发现（L1 档位下产出应该只有巡检结论，如果连巡检结论都没有，节律就是假的）。

**为什么需要它，用事故说话。** 本机有一个真实的故障类型直接对应这一条："主动任务越界——心跳醒来自己干了不该干的事"。它的成因往往不是恶意，而是配置：唤醒动作里写了"自主判断当前最该做的事并执行"，而条件执行的白名单用了通配符 `"*"`。**一个通配符，就把三档变成了一档。**

**怎么写。** 关键的结构性事实：**三档边界写在 USER 协议文件里，不写在 config 里。** 本机 config 里没有 `drift` / `boundary` / `proactive` 这类字段。这也是为什么它被称为"文件级声明"而不是"运行时强制"。

还有一个必须配套的地方：边界要和心跳的闸门配套读。第 3 章引入的 `heartbeat.directPolicy: "block"` 是心跳的闸门，三档边界是动作的闸门。两者共同构成"主动但不越界"——缺任何一个，另一个都能被绕过。

**技巧。** 三条。

第一条：**从最低档起步，逐级授权，每一级都有晋级条件。** 本机惯例写在条件里，例如"连续两周在 L2 无越界且体检全绿，可晋级到 L3"。

第二条：**白名单永远不用通配符。** 授权要逐条加，一条一条可审计。`allowlist: ["*"]` 是"没有边界"的另一种写法。

第三条：**降档必须是标准处置，不是慌乱反应。** 事故后的正确动作是"立即降一档，记一次越界复盘，修完再谈晋级"。如果系统里没有降档机制，事故之后你只有两个坏选择：全关，或者硬撑。

**常见误区。** 最常见的是把边界写成口号。`forbidden` 里写"注意安全"、"不要做危险的事"——这不是边界，这是愿望。**每一档每一条必须是具体的动作名**（像 `export_pii` 这种粒度），否则它无法被检查、无法被判违规、无法被自动化。

**进化阶梯。** 最低可用：一档 L1（只读巡检）+ 一份含三条 `forbidden` 的清单。进阶：L2 可选，晋级条件写明，降档流程落盘。最佳实践：三档齐全 + 升降留痕 + 与心跳闸门配套 + 越界事件进入治理层的修复工单（结算在第 5 章）。

⚠ 诚实边界：治理侧还存在更细的五档划分（L1–L5）的讨论，其量化判定阈值本章不给出，属待校准项 ⏳。

（卷五 · 源流）

### 4.1.3 记忆三层（short_term / long_term / archival）

**这是什么东西。** 把记忆按"访问频率"和"寿命"分成三层：**short_term** 是当前会话的短期记忆，自动过期；**long_term** 是跨会话的结论层，结构化、可检索；**archival** 是归档层，低频，默认不进上下文。

**核心目的。** 目的不是"记得更多"，而是**让该记的记得住，让不该占的不占位**。这是一个配给问题，不是一个容量问题。

**拟人化映射。** 一个成熟的职业人，脑子里同时有三层东西：手上这个项目此刻的细节（短期）；他做了十年的判断原则、踩过的坑、跟谁合作过（长期）；以及"2019 年那个项目最终结项报告的附件在哪个盘"（归档）。他不会把 2019 年附件的内容时刻悬在脑中，但他知道它存在、知道在哪儿找。**记忆健康的标准不是"什么都记得"，而是"分层清楚、各就各位"。**

**对长期表现的影响。** 单层记忆的崩坏路径特别确定，几乎可以预测：

半年后 MEMORY 文件几十万行 → 每次会话加载变慢、上下文被吃掉一大块 → 关键结论被淹没在流水里 → agent 找不到东西 → 于是**重复写入同一结论** → 记忆继续膨胀 → 检索更差。

注意最后两步：**记忆越多，效果越差**。这是长期表现里最反直觉的失败模式。它反直觉的地方在于，所有直觉都告诉你"信息越多越好"；但在有限上下文的现实里，信息密度才是变量，信息总量不是。

**怎么写。** 三层不是口号，要写进策略面：晋升规则（什么内容可以从短期升入长期：结论 + 决策 + 可复用步骤）、降级规则（长期层里超过一段时间未被引用的内容沉入归档）。同时——这点极其重要——**写入要有规范**：每条记忆带结构（主题 / 结论 / 证据 / 时间 / 关键词），写入前先检索，命中则更新而不是新增。

还有一份本机真实存在的双层结构可以直接对照：日记层（按日期 append-only 的运行流水）+ 精选层（MEMORY 文件）。这两层和"短期 / 长期"是同一思想的不同切面：**日记层记录发生过什么，精选层记录值得以后还用得上的什么。**

**技巧。** 三条。

第一条：**只把"结论 + 决策 + 可复用步骤"升入长期层。** 过程、试错、临时坐标不该进。这不是洁癖，这是上下文预算。

第二条：**归档要有触发器，不要靠意志。** "超过 N 天未被引用"是个可自动化的条件；"我觉得这些可以归档了"不是。

第三条：**把记忆的"写"和"读"当成两条独立链路来管。** 这一点在 4.1.9 会展开，但它在这里就要埋下：**写入成功不等于检索可用。**

**常见误区。** 以为"分层"就是"分文件夹"。分层的关键不在物理位置，而在**加载策略**：哪一层默认进上下文、哪一层按需拉取、哪一层默认不出场。只换目录不换加载策略，等于没分层。

**进化阶梯。** 最低可用：两层（短期 / 长期）+ 一条写入规范。进阶：三层齐全 + 去重 + 关键词扩展。最佳实践：三层 + 升降自动触发 + 每月一次记忆体检（体量 + 命中率抽样 + 一致性）。

### 4.1.4 会话污染（Session Contamination）

**这是什么东西。** 长会话里，上下文不是静态资产，而是**会腐败的运行资源**。它会积累：过期结论、被推翻的假设、被工具返回噪音污染的结果、临时坐标、以及中途改过的需求。这些东西合起来，就是会话污染。

**核心目的。** 理解污染的存在，是为了理解为什么"保持全部历史不动"不是忠诚，而是**负担**。长期表现的工程本质，是在"压缩"和"保真"之间持续做平衡。

**拟人化映射。** 一场开得太长的会议，最后半小时往往是最没质量的：不是因为人变笨了，而是因为每个人脑子里都堆着前面两小时的错误分支、被否掉的方案、和已经作废的假设。优秀的会议主持人知道要"收一下"——把已定的事定下来，把废弃的事明确划掉。**压缩（Compaction）就是这个动作**，不是删掉历史，而是提炼出"目标、决策、主要发现"，让后面的人能在干净的基线上继续。

**对长期表现的影响。** 不管理污染，会出现三类确定的退化：

一是**越聊越散**——它开始沿着已经被否定的支线继续推理。二是**决策连续性断裂**——跨过一次摘要之后，它保留的是"结论的形状"而不是"结论的理由"，于是下一次遇到相似情境时，它可能做出方向相反的选择。三是**成本曲线拐弯**——污染让每一轮都要背着越来越重的历史前进。

**怎么写。** 三件事要区分清楚，它们经常被混为一谈：

- **裁剪（Pruning）**：运行态的裁剪，把不再需要的工具返回结果从当前上下文里去掉。它是"这一轮的内存管理"。
- **压缩（Compaction / 会话压缩，原：会话卫生）**：会话接近上限时，把旧历史总结成摘要，只保留摘要 + 近期消息，然后以摘要为起点重新开始。它是"持久化的摘要"，会改变历史本身。
- **记忆刷写（Memory Flush）**：在会话接近压缩之前，先把该留下的事实**写回磁盘**。它解决的是"分界线上会丢东西"这个特定风险。

这三件事的排序有讲究：**刷写要在压缩之前。** 顺序反了，你在把要丢的东西总结完之后才想起来要留。

**技巧。** 三条。

第一条：**压缩是被设计出来的边界，不是故障。** 它一定会发生。所以真正的问题是"压缩应该保留什么"——答案是：**目标、决策、理由、主要发现**。具体的措辞、精确的动作序列，本来就保不住，也不必保。

第二条：**关键事实靠记忆跨过边界，不靠摘要。** 摘要不是保险箱，它是减损压缩。跨压缩边界要保真的东西，必须落成磁盘上的记忆。

第三条：**给污染一个可观测信号。** 污染不是玄学，它有前兆：同一件事被反复确认、同一分支被反复重启、回答开始引用已经作废的前提。看到这些前兆，就该收一下，而不是等它撞上限。

**常见误区。** 一个很深但很常见的误解：以为**压缩会导致人格失忆**。更准确的表述是：**压缩会压缩"残留上下文"，但如果人格与规则本来是被文档协议稳定锚定的，压缩就不影响人格。** 反过来说——这也是本章的核心判断——如果你的 agent 在每次压缩后都"变一个人"，那问题不在压缩，在于人格从来没有被锚定在文档上，它一直在靠"残存上下文"活着。**靠上下文活着的人，一压缩就失忆；靠文档活着的人，压缩只是换了口气。**

**进化阶梯。** 最低可用：知道压缩一定会发生，把关键结论落到记忆。进阶：刷写在压缩前 + 会话污染前兆可识别。最佳实践：压缩策略与维度可配置 + 记忆跨边界保真 + 长项目跨多次压缩保持决策连续性。

### 4.1.5 心季节律（Cadence）

**这是什么东西。** 节律是指把"主动性"从一种情绪，变成一种**有固定周期的运行制度**。本机真实存在的三层节拍就是最好的样本：`health_scan` 每 7,200,000 毫秒（2 小时）跑一次轻量健康扫描；`overdue_alert` 每 14,400,000 毫秒（4 小时）跑一次逾期告警；`true_pulse` 每 21,600,000 毫秒（6 小时）做一次最重的探测——逐个探活全部 18 个 agent。

**核心目的。** 目的不是"多跑几次"，而是**让自检成为制度，而不是意愿**。任何依赖"想起来就做"的治理，都会在忙碌期第一个被牺牲。

**拟人化映射。** 心跳的本意不是刷存在感。它的本意是：**周期性地自检，周期性地发现需要关注的事，并在"无事发生"和"必须提醒"之间建立一个契约。** 一个健康的人体，心跳不是为了被听见，是为了让循环持续。一个健康的组织，"周一例会"的价值不是开会，是让某些事一定会在某个时间被提起。

**对长期表现的影响。** 没有节律，长期表现会退化成"撞了才修"。而所有慢性问题都有一个共同特征：**撞不到**。漂移撞不到、记忆膨胀撞不到、体检走形式撞不到、能力矩阵 26 天没续期撞不到——直到某一天它变成了一个真事故。

节律的价值，就是**把撞不到的问题变成按点会到的问题。**

**怎么写。** 三个约束必须写进设计：

一是**分层频率**。轻动作高频、重动作低频。本机惯例就是分层：轻（2h）> 中（4h）> 重（6h）。三层频率一样是错的——最重的探测跑得和最轻的一样勤，只会把成本推高、把真正重要的信号淹没。

二是**无事必须静默**。心跳的频率越高，静默纪律越重要。一个每 2 小时汇报一次"一切正常"的系统，一个月后没人会读它，然后真正的告警也会被一起忽略。

三是**有产出约束**。节律的合法性来自"每次跑完都有可消费的产出"（巡检结论、告警、报告），而不是"跑了"。这是判定"主动性空转"的关键指标：**有动作没产出 = 节律是假的。**

**技巧。** 两条。

第一条：**心跳内嵌检测，而不是心跳外挂检测。** 把漂移比对、阈值判断这类动作放进唤醒动作里，它才会真的发生。放在"以后有空写个脚本跑"里，它不会发生。

第二条：**区分"节律"和"打扰"。** 节律是给系统自己的（自检、上报、发现），打扰是给人的（通知、请求确认）。把节律做成打扰，等于把成本转嫁给最稀缺的资源——人的注意力。

**常见误区。** 把心跳频率调得越高越好。这是"更多 = 更强"直觉的典型受害者。心跳太频的两个直接代价：token 消耗暴增，以及系统行为变得难以预测（频繁自主行为的叠加效应没人能推演）。**主动性必须被设计成节律，而不是情绪。**

**进化阶梯。** 最低可用：一个固定节律的自检动作。进阶：分层频率 + 无事静默 + 有产出约束。最佳实践：节律与体检清单合并 + 节律健康度本身成为体检项（"节奏是否连续 + 有没有产出 + 产出有没有被消费"）。

### 4.1.6 漂移锚点：SOUL.md 与 `drift_anchor`

**这是什么东西。** 锚点是"用来判断漂移的参照物"。在这套训练学里，锚点就是 SOUL 协议文件——本机 18 个 agent workspace，每个都有一份 SOUL.md，实测 18 份，一份不多、一份不少。为了让锚点的身份显式化，可以在文件里声明它自己是锚点（`drift_anchor: true`）。

**核心目的。** **漂移是相对锚点定义的。** 没有锚点，"漂移"这个词没有意义——你不知道它偏离了什么。这是整个漂移治理的逻辑起点，也是最多人搞错的一步：他们做了检测动作，却没定义检测的参照。

**拟人化映射。** 组织里判断一个人"变了没有"，标准从来不是"他昨天和今天是不是一模一样"。标准是**岗位说明书**：他该干什么、不该干什么、以什么标准判断、对谁负责。季度评估就是拿这个人去对照那份说明书。**SOUL.md 就是那份说明书；`drift_anchor` 就是把它盖个章、标明"这份是基准版"。**

**对长期表现的影响。** 锚点的存在与否，决定了两件完全不同的事：

有锚点时，漂移是**可检测**的——你可以回答"它离最初设计的它有多远"。没锚点时，你只能回答"它今天和昨天比变了吗"。而后面这个问题几乎没有诊断价值，因为漂移的典型形态是累积的、缓慢的、每天都不显著的。逐日比对会系统性地漏掉它，且漏得毫无察觉。

而且锚点还有一个附带价值：**它把"变更"和"漂移"分开了。** 有意的、经过评审的、写清理由的改动，叫变更；无意的、渐进的、偏离设计的偏移，叫漂移。没有锚点，这两者无法区分——你会把有意变更当成漂移去回滚，也会把真漂移当成"正常演进"放过去。

**怎么写。** 两个动作：

一是**钉基线**。把锚点文件的当前状态固化下来，并给它一个可引用的标识（例如按日期命名的基线标签）。本机 18 份 SOUL.md 就是 18 个锚点，基线要覆盖全部 18 份，不是只覆盖主角色的那一份——**漂移是群体现病，不是个体现病。**

二是**声明锚点身份**。在 SOUL 文件里显式标注它是漂移锚点。这个字段不是给系统读的（本机无内置漂移字段），是给**人和自动化脚本读的**：它让"这份文件有特殊地位、改它要慎重"这件事从口口相传变成写在纸上。

**技巧。** 三条。

第一条：**基线要覆盖"锚点之外"的东西。** 漂移检测不应只盯 SOUL。USER、AGENTS、IDENTITY、MEMORY 同样是行为锚点的组成部分，改动的风险等级不同，但都该在比对范围内。

第二条：**把"改锚点"本身列为需要确认的动作。** 本机的 `needs_confirm` 档里明确包含"修改自己的 SOUL.md"——这条规则的存在意义，就是防止 agent 在某个上下文里"顺手优化一下自己的人格"。**人格文件的改动权，不该在人格自己手里。**

第三条：**锚点不是越老越好。** 锚点要定期"再盖章"：通过的、有意的、经过评审的改进，应该被吸收进新基线。否则基线会越来越脱离现实，最终所有人都学会无视它——这比没有基线更糟。

**常见误区。** 一个高频误区：把"当前版本"当成"锚点"。这样你会得到一个永恒的事实——它和昨天的自己几乎一样（因为每天只变一点点），于是检测永远通过，而三个月后它已经完全变了一个人。**锚点必须是某个被有意选定的历史时点，不能是"总是最新的那份"。**

**进化阶梯。** 最低可用：全部锚点文件钉一次基线。进阶：锚点身份显式声明 + 改动受确认约束。最佳实践：基线版本化 + 好的漂移评审后回写新基线 + 锚点改动进入治理层留痕。

### 4.1.7 两类漂移：人格漂移（Personality Drift）与文档漂移（Document Drift）

**这是什么东西。** 名字很像，对象完全不同：

- **文档漂移（Document Drift）**：文档与现实不符。文档说 SKILL 是 236 份，实测是另一个数；文档说通道正常，实际通道已经断了两周。它的检测对象是**"文档声明 vs 事实源"**。
- **人格漂移（Personality Drift）**：行为与基线人格偏离。它看得见的从来不是"文件"，而是**输出**：语气、判断取向、边界感、承诺纪律。它的检测对象是**"行为 vs 基线人格"**。

**核心目的。** 分开的理由极其朴素：**它们是两个独立的故障类型，各有各的成因和处理路径。**

文档漂移是**同步问题**——东西变了，描述没跟上。它的成因通常是"忘了"，处理方式通常是"对一下、改一下"。

人格漂移是**侵蚀问题**——它不只是忘了更新，它是真的变了。成因往往是慢性的：长期对话的压力、上下文膨胀、反馈噪音、临时补丁的叠加、记忆污染、提示层次的失衡。处理方式也不是"改一下"，而是"找出偏移的时间点、判断方向、决定回滚还是接受"。

**拟人化映射。** 文档漂移像"公司简介里还写着三年前的员工人数"——尴尬，但改一句话就完事。人格漂移像"一个原本敢说真话的人，两年后变成了一个只会说'您说得对，不过也许可以再考虑一下'的人"——这不是改一句话能修的，你得理解他是怎么一路走过来的。

**对长期表现的影响。** 两类漂移的长期伤害机制不同：

文档漂移伤害的是**判断质量**。所有依赖文档做决定的人（包括其他 agent），都在基于过期的世界模型工作。它最阴的地方是——文档越"看起来完整"，伤害越大。

人格漂移伤害的是**可预期性**，也就是信任的底层。输出质量偶尔波动，人还能忍；"它怎么越来越不像它自己"不能忍。因为一个组织的协同，本质上是**基于对彼此判断方式的预期**来安排分工的。

**为什么混治会失败。** 把两者合成一个指标，会得到一个必然的坏结果：**文档改了一个字也会触发"人格漂移告警"。** 于是告警迅速退化为噪音，真漂移被淹没。**混治不会让治理更简单，只会让治理失效。** 这是本章最值得记住的一条工程判断。

**怎么写。** 分开定义，分开配置：

- 文档漂移：列出**事实源清单**（哪些文件/字段是"事实"的权威），定义核对动作（拿事实源去核文档声明），触发条件（不一致项 > 0）。
- 人格漂移：定义**锚点**（SOUL + `drift_anchor`），定义检测动作（基线 diff + 行为抽样），触发条件（差异超过阈值）。

注意这两者的**成本结构完全不同**：文档漂移可以做到近乎零成本（就是几次查找和比对）；人格漂移要花 token（要跑裁判模型）。所以它们的频率也不该一样——文档漂移更适合高频，人格漂移更适合每周一次。

**技巧。** 三条。

第一条：**先修事实源，再修文档。** 文档漂移的修复顺序反了，你会把错误的值抄进更多地方（因为你在拿文档去改文档）。

第二条：**人格漂移要看样本，不看单次。** 一次回答语气偏了，可能是模型波动或上下文差异，不是漂移。抽样多轮、看分布，才是有意义的信号。**"感觉"是最易得的信号，但它不是证据。**

第三条：**漂移不必然是退化。** 这一点值得单独强调（也是 4.1.6 提到的"基线要再盖章"的根据）：某次无意的改动可能让效果变好。如果体检一律"与基线不一致就回滚"，你会把好的漂移一起滚掉，并且永远学不到为什么那时候它变好。**漂移报告应该分三类：变好、变差、中性。**

**常见误区。** 一个很隐蔽的误区：**以为漂移一定是"变坏"。** 中文的"漂移"两个字自带负面色彩，但它的本义只是"变动"。只盯着变差的方向，你会：错过可复用的改进、误回滚好的变更、以及让基线逐渐失真（长期不收编良好实践，基线就成了化石）。

**进化阶梯。** 最低可用：两类漂移分开定义（哪怕只实现文档漂移）。进阶：文档漂移高频自动化 + 人格漂移每周抽样 + 漂移分方向。最佳实践：两类均有阈值告警 + 分方向处置（好的进评审、差的开工单）+ 基线定期收编。

### 4.1.8 双防线：阈值告警 + 每周体检

**这是什么东西。** 一套两层的检测结构：**第一层是高频的阈值告警**——漂移超过某个百分比就立即告警，记忆周增长超过某个百分比就告警；**第二层是低频的全面体检**——每周（本机惯例是周一凌晨）做一次完整核对，输出 pass / fail。

**核心目的。** **让"发现"的时间尺度，匹配"污染"的时间尺度。**

**拟人化映射。** 一家工厂的品控不能只靠季度审核。它需要两层：产线上的即时报警（温度超限就响），和质量部门的季度全面审核。只有季度审核，你会在出事三个月后才知道；只有即时报警，你不会发现体系性问题。**双层不是冗余，是不同时间尺度的必要覆盖。**

**对长期表现的影响。** 只有周检，会得到一个精确的代价：**告警延迟 = 污染时长。**

设想漂移发生在周三。周五、周六的会话全部基于已经偏移的状态运行。如果这期间它有对外产出，那些产出就是带病的。周检在周一发现了它，但污染已经持续了五天。反过来，只有阈值告警没有周检，你会一直在处理"指标越限"，没人回答"整体健康吗"——阈值告警是守门员，周检是体检报告，缺一个都不完整。

**怎么写。** 三件事：

一是**阈值要有具体数字和具体单位**。`drift_pct: 1.0`（相似度低于 99% 即告警）、`mem_growth_pct: 20`（记忆周增长超过 20% 告警）——这类是可以写进策略面的形式。⚠ 诚实边界：**1% 这个阈值本机未校准**。哈希法只能判"变没变"，判不了"变了 1%"。百分比阈值需要相似度度量，属于待推。

二是**把阈值判断嵌进高频动作**。阈值告警靠"每周跑一次"是无法成立的——高频检查必须在高频的地方发生（心跳唤醒动作里）。

三是**周检要有可判定的输出**。pass / fail，不是"看起来正常"（这一条在 4.1.10 展开）。

**技巧。** 三条。

第一条：**第一防线要便宜，第二防线要全面。** 如果第一防线贵，它会第一个被关掉；如果第二防线便宜，它会变成走过场。

第二条：**告警要能自证。** 一条告警至少要说清三件事：哪个指标、当前值、阈值。说不清这三件事的告警，会被人当成"系统又抽风了"。

第三条：**告警要能静默通过。** 没有越限就闭嘴。这是告警系统能活过第三周的唯一方式。

**常见误区。** 一个典型的错配：**阈值设得太灵敏，或者太迟钝，且从不校准。** 太灵敏 → 告警疲劳 → 全部忽略；太迟钝 → 等于只有周检。**阈值是需要校准的参数，不是一次设定就完的常量。**

**进化阶梯。** 最低可用：周检 + 一个阈值告警。进阶：多个阈值 + 分级告警（提醒 / 阻断）。最佳实践：双防线 + 阈值随体检数据周期性校准 + 告警响应有留痕。

（卷五 · 源流）

### 4.1.9 "记住"与"检索质量"：两条独立链路

**这是什么东西。** 记忆的"写"和"读"是两条独立的链路。**写入成功不代表检索可用。**

**核心目的。** 逼你把"记忆能力"从一个笼统的印象，拆成两个可以分别测量的东西：**内存里有没有**（写入链路）和 **需要时能不能拿出来**（检索链路）。

**拟人化映射。** 一个资料员把 10 万页文档整整齐齐码进了仓库（写入成功），但你问他"去年那份渠道合同在哪"他答不上来（检索失败）。你会说"他记性不好"吗？不会。你会说"他这套档案系统不行"。**记忆的问题通常不在"记"，在"找"。**

**对长期表现的影响。** 这是最反直觉的失败模式，它的恶性循环值得完整走一遍：

记忆写进去了但读不出来 → 因为读不出来，agent 以为没记，于是**重复写入同一结论** → 记忆量上升 → 重复条目互相稀释检索信号 → 命中率进一步下降 → 更读不出来 → 继续重复写入。

所以你会看到那个违背直觉的现象：**记忆量越大，效果越差。** 而且它有一个特别坏的性质——**从外部看，这个系统的一切都是正常的**：写入成功、没有报错、文件在长。所有健康的信号都在，除了效果。

**怎么写。** 两条链路，两套动作：

**写入侧**——写入规范。每条记忆含结构（主题 / 结论 / 证据 / 时间 / 关键词）；**写入前先检索**，命中则更新而非新增；关键词不少于三个，且**包含中英文与同义词**（这是"可被搜到"的技术前提，不是文档美化）。

**读取侧**——检索策略与指标。要求分层检索（短期 → 长期 → 归档）；要求同义扩展（同一概念的多种说法都能命中）；定义可测指标（例如抽一批查询统计命中率）。

**技巧。** 三条。

第一条：**把"命中了没有"当成一个一等公民指标来对待。** 不测命中率，你就只能靠"偶尔发现它忘了"来判断记忆系统好坏——那是零样本抽查。

第二条：**同义词是检索质量的主要杠杆之一。** 同一个概念在不同场合会有多个说法（中英文混用、缩写与全称、术语与内部黑话）。这些变体如果不在关键词里，检索就必然漏。

第三条：**记忆体的量与命中率要一起看。** 只看量会得出"它在变强"的错误结论；只看命中率会漏掉"为什么命中率在掉"。

**常见误区。** 三个高频错法：把"写入成功"当"记住了"；把"内容在文件里"当"内容可被取回"；把"检索找不到"归因为"模型不聪明"。第三个最贵——它会让你去换模型，而问题在关键词体系和分层策略。

**进化阶梯。** 最低可用：写入规范（结构 + 去重）。进阶：分层检索 + 同义扩展 + 命中率抽样。最佳实践：命中率进入每周体检项 + 记忆一致性检测（同一事实在不同层有冲突时能被发现）。

（卷五 · 源流）

### 4.1.10 带数字的体检（Weekly Health Checklist）

**这是什么东西。** 一套**可判定**的周期性健康核对：每一项都有阈值、有本周实测值、有明确判定，并且**必须落盘**。

**核心目的。** 让体检具备**判定能力**。这是本章最实用也最容易被跳过的一条。

**拟人化映射。** 医院体检报告从来不会写"看起来还行"。它写：白细胞 5.6（参考 4–10，正常），谷丙转氨酶 68（参考 0–40，偏高）。**正因为每一项都有数字和参考值，它才有"异常"这个概念。** 一份没有数字的体检，本质上是一份无法判定异常的体检。而无法判定异常的体检，与不做体检在结果上等价。

**对长期表现的影响。** 走形式的体检是最贵的一种"看起来有治理"。它对系统的伤害是双重的：一方面真问题被放过（所有慢性病都在这里溜走），另一方面**它给了组织一种"我们在做治理"的错觉**，从而压制了真正的治理冲动。

本机的真实参考：体检项与节拍在 `heartbeat-state.json` 里已有真名结构——`lastChecks` 三项（健康扫描 / 逾期告警 / 真脉冲）、`cadenceMs` 三层、`pulse` 全军团存活。这三块是"体检有真实结构"的证据，不是设计想象。

而"能力矩阵 26 天没有续期"这类真实事故，正是走形式体检的典型牺牲品：数据早就断更了，没有任何一项体检项的数字会因此变红，因为体检项里根本没有"续期时效"这一行。

**怎么写。** 体检表至少包含这几类项，每一项都要有阈值、实测值、判定三列：

- **人格/文档漂移**（阈值示例：漂移 ≤ 某个百分比）
- **记忆增长**（阈值示例：周增长 ≤ 某个百分比）
- **心跳成功率**（阈值示例：≥ 99%）
- **技能合规**（阈值示例：合规率 ≥ 95%——本机 skills 是一个真实现场，实测 216 份 SKILL.md 会持续变动，这正是"文档漂移"的现实土壤）
- **时效类项**（例如某类台账/矩阵的续期时效 ≤ 7 天）

每一行判定为"不过"时，必须**当场产生一个动作**（开工单、安排修复、降档）。没有后续动作的"不过"，下次体检还会是"不过"。

**技巧。** 三条。

第一条：**用命令产出数字，不要用眼睛产出印象。** "漂移了多少行"、"技能有多少份"、"存活多少 agent"——这些全部是可以算出来的。凡是能算的，就不要用"感觉"。

第二条：**体检必落盘，文件名带日期。** 单点数据看不出趋势。只有一列按时间排列的数字，才能告诉你"是变好了还是变差了"。不落盘的体检，等于每次从零开始。

第三条：**让体检项本身也被体检。** 如果一个体检项连续多周都是绿的且从未产生过动作，要么它设计得太松，要么它已经没意义了。

**常见误区。** 三个：把体检报告写成"本周体检：✅ 通过（看起来正常）"；把体检项做成"越全越好"从而每次都跑不完；以及——最隐蔽的——**把"通过"当成绩效**。体检通过不是成绩，体检**发现问题**才是它的价值所在。一个从没发现过问题的体检，通常说明它坏掉了。

**进化阶梯。** 最低可用：五行带阈值的体检表 + 落盘。进阶：体检自动生成草稿（挂在节律上）+ 连续趋势可查。最佳实践：体检 + 阈值告警双防线 + 不过即开工单 + 项本身定期复审。

（卷五 · 源流）

### 4.1.11 上下文预算（Context Budget）与压缩阈值

**这是什么东西。** 上下文窗口是一个**预算**，不是一个容量。预算的意思是：进来的每一笔都要占额，而且额度是有限且不可透支的。要分配的主要有几块——协议文件的注入（SOUL / USER / AGENTS / IDENTITY / MEMORY 等工作区文件在会话开始时要进上下文）、历史消息、工具返回结果、以及**必须为输出预留的那一部分**。剩下的，才是"可自由使用的余额"。

**核心目的。** 让"压缩什么时候触发"从一个被动事实，变成一个**主动决定**。

**拟人化映射。** 一个月的现金流。固定成本（房租、人力）先扣，剩下的才是可支配的；如果你把可支配的部分全部花在前十天，后二十天就要靠借。长期 agent 的上下文完全一样：**协议文件注入是固定成本，工具返回是可变成本，输出预留是必须留的租金。** 一个不做预算的系统，会在会话前半段"很富"，然后在后半段突然"很穷"——而且是**断崖式的穷**，因为压缩一旦触发，历史就被整体改写。

**对长期表现的影响。** 无预算的系统，一定会遇到三个症状：一是**压缩来得比预期早**（前期的工具返回把额度吃掉了）；二是**压缩后质量断崖**（因为压缩发生时，真正重要的东西已经没有位置留在摘要里了）；三是**成本曲线在长会话里非线性上升**（每一轮都背着更重的历史）。

这里要引入一个比"窗口大小"更有用的数字（⏳ 出自第三方工程文章的估计）：有团队把**有效工作上下文**估计在 60,000–80,000 token，而名义窗口是 200,000。也就是说，**质量开始下滑的位置，可能在名义窗口的 60%–70%**。如果这个判断在更多团队身上复现，它有一个非常直接的推论：**"等到 98% 才自动压缩"是安全网，不是策略。** 安全网的作用是防止摔死，它不负责让你跑得好。

**怎么写。** 三件事：

一是**把注进上下文的协议文件当成固定成本来管**。这份成本是每天、每一轮都付的。这也是为什么"记忆分层"和"写入规范"不只是整洁问题——**它们是成本控制**。一份膨胀的 MEMORY 文件，是在每一轮里都在征税。

二是**给压缩设一个保守阈值，而不是让安全网兜底**。保守阈值本身是一种质量控制手段：宁可多压缩一次，也不要让质量在无感知的情况下先掉下去。

三是**明确指定压缩要保留什么**（目标 / 决策 / 理由 / 主要发现）。这一步在今天已经不是难题——2026 年的压缩接口允许你配置摘要提示词与触发阈值（4.5.5）。难题是**你得先知道自己要保留什么**。

**技巧。** 三条。

第一条：**把"可重新获取的东西"赶出上下文。** 工具返回的结果往往可以被重新取一次，这类内容最该被清理。留下来的额度给不可重建的东西：决策、理由、承诺。

第二条：**区分"这一轮需要"和"以后可能需要"。** 后者不属于上下文，属于记忆文件。混着放，两头都会坏。

第三条：**把预算当体检项。** 记忆体量、历史长度这类数字，本来就是可以按周记录并看趋势的。

**常见误区。** 最大的误区是**把"窗口大"当成"能跑久"**。窗口大只意味着这一轮能塞进更多东西；它不意味着它会自动保留重要的、自动清掉噪音的、自动在下一轮延续正确状态。**没有压缩策略、没有记忆刷写、没有分层加载，再大的窗口也只是一个"更大的临时脑袋"。**

**进化阶梯。** 最低可用：知道自己付了哪些固定成本，把重要结论落盘。进阶：给压缩设保守阈值 + 明确保留项 + 清理可重取的返回。最佳实践：预算成为体检项 + 压缩策略与保留维度可配置 + 长项目跨多次压缩保持决策连续性。

（卷五 · 源流）

### 4.1.12 十一个概念如何咬合成一个系统

把这十一个概念按依赖顺序排一遍，你会看到这一章其实只有一个论断：

1. **锚点（4.1.6）**先立起来，漂移才有参照；
2. 有了参照，**两类漂移（4.1.7）**才分得开；
3. 分开之后，**三件套（4.1.1）**才有内容可检；
4. 检测要跑得动，得靠**节律（4.1.5）**；
5. 节律之上要有**双防线（4.1.8）**，否则发现得太晚；
6. 发现之后要能**判定（4.1.10）**，所以体检必须带数字；
7. 长期运行的底盘是**记忆三层（4.1.3）**，因为跨边界保真只能靠记忆；
8. 记忆的质量不取决于量，取决于**写读两条链路（4.1.9）**；
9. 上下文会腐败，所以要有**会话污染的处置（4.1.4）**；
10. 上下文还要有**预算（4.1.11）**，否则压缩会来得太早、来得太狠；
11. 而所有"它能自己动"的自由，都必须被**三档边界（4.1.2）**框住。

一句话收口：**前十件管的是"它还是不是自己"，第十一件管的是"它动手之前该不该问你"。**

## 4.1.13 · 十一个概念的「进化阶梯」展开：从"能用"到"越用越稳"

第 3 章给出了 L1–L5 的进化阶梯（Evolution Ladder），那是**智能体整体能力**的档位。本节要做的是把同一个阶梯**竖着切一遍**：对本章的十一个概念，逐个说明它在 L1 到 L5 上分别长什么样。

这样做的价值在于：它把"我这只 agent 在第几级"这个偏抽象的问题，转换成"这十一个机制里，我点亮了几个"这个可数的清单。**阶梯不是打给自己的分数，是给机制的进度条。**

### 4.1.13.1 漂移治理三件套 的进化阶梯

**L1 原始档**：完全没有锚点概念。它变了，但谁也不知道。此档的典型错觉是"它一直挺好的"——因为没有人有对照物。

**L2 可塑档**：有了第一份 `SOUL.md` 快照，但对比方式是人肉通读。这一档的价值在于"存在了一个参照物"，代价是每次比对都依赖某个人当下的注意力。

**L3 可用档**：锚点 + 显式阈值 + 每周体检三件齐备。技术判断开始产生数字，判断不再依赖感觉。这一档是**三件套真正的入门线**。

**L4 稳定档**：偏差被分层（必须处置 / 仅记录），每类偏差有对应的处置动作，处置有留痕。这一档的关键词是"有动作"——发现之后有事发生。

**L5 主动档**：好的漂移能被评审并吸收进基线，形成正反馈；治理机制本身也被定期观测（防 CASES-4 式的机制空转）。

**跨越各档的关键动作**：L1→L2 是"采集一次快照"；L2→L3 是"把对比拆成维度并算出数字"；L3→L4 是"给每类偏差定义动作"；L4→L5 是"开正反馈通道 + 元观测"。

### 4.1.13.2 主动性边界三档 的进化阶梯

**L1 原始档**：没有边界概念，能做的都做。风险的实际水平由模型的先验决定，而不是由组织的判断决定。

**L2 可塑档**：边界写在某一份文件或某一段提示里，但档位是模糊的（"重要的事情要先问我"）。这一档的失败方式是**争论**："这次算不算重要？"

**L3 可用档**：三档（读 / 建议 / 执行）显式定义，每档对应明确的动作类型清单。争论变成了查表。

**L4 稳定档**：档位与心跳耦合——执行档的动作挂在节律与闸门上，档位迁移必须留痕。越界能被自动发现。

**L5 主动档**：档位可以按场景细分并在体检时被复核；降档是标准动作，升档需要评审。

**跨越各档的关键动作**：L2→L3 是"把模糊表述换成动作清单"；L3→L4 是"把闸门接到节律上"；L4→L5 是"让档位表成为被维护的对象"。

### 4.1.13.3 记忆三层 的进化阶梯

**L1 原始档**：只有一种记忆，什么都在里面。三个月后它变成一份检索命中率极低的流水账。

**L2 可塑档**：意识到了分层，但分层靠约定（"尽量把重要的写前面"），没有触发条件。

**L3 可用档**：三层各有明确的写入标准与保留策略，归档有触发条件。检索质量第一次变得可测量。

**L4 稳定档**：写入规范成为纪律的一部分；检索命中率被抽查；去重与降噪有例行动作。

**L5 主动档**：分层策略本身随体检调整——发现某一层常年空置或常年超载时，会触发一次结构修订。

**跨越各档的关键动作**：L2→L3 是"给每一层写保留策略与归档条件"；L3→L4 是"建立写入规范并抽查"；L4→L5 是"把分层结构纳入体检对象"。

### 4.1.13.4 会话污染 的进化阶梯

**L1 原始档**：完全没有这个概念。会话越跑越脏，表现为"它越来越啰嗦、越来越不聚焦"。

**L2 可塑档**：知道会话会脏，处理方式是"感觉不对就重开一个会话"。重开能缓解，但会丢掉上下文；代价被当成"模型特性"接受下来。

**L3 可用档**：刷写（把关键结论写进记忆层）被固定在压缩之前执行；重开有明确的前置动作（先刷写、再重开）。

**L4 稳定档**：污染有可观测指标（上下文占用、关键事实召回率），超标会触发刷写或重开。

**L5 主动档**：污染率进入体检报告，并作为"上下文预算是否需要调整"的输入。

**跨越各档的关键动作**：L2→L3 是"把刷写固定在压缩之前"；L3→L4 是"给污染配指标"；L4→L5 是"把指标接进预算决策"。

### 4.1.13.5 心季节律（Cadence） 的进化阶梯

**L1 原始档**：只有被动响应。你不问，它不动。

**L2 可塑档**：接了心跳，但频率与任务是拍脑袋定的，也没有熔断。

**L3 可用档**：先定熔断再定动作；感知类任务与准点类任务分开；频率有依据（由退化速度与任务时效决定）。

**L4 稳定档**：节律的失败（未醒、超时、报错）可观测，并会触发告警；节律任务本身有幂等性设计。

**L5 主动档**：节律随运行强度定期复核（"该发生而未发生"清单），频率调整是一次显式动作。

**跨越各档的关键动作**：L2→L3 是"先写熔断再写动作"；L3→L4 是"让节律失败可见"；L4→L5 是"建立'该发生而未发生'检查"。

### 4.1.13.6 漂移锚点 的进化阶梯

**L1 原始档**：没有锚点，`drift_anchor` 只是一个陌生的词。

**L2 可塑档**：锚点存在（例如一份基线快照），但从不更新，且不定义"什么算偏离"。

**L3 可用档**：锚点与维度绑定——每个维度有锚定值、有偏离判据、有采集方式。

**L4 稳定档**：锚点的更新是有流程的：谁在什么条件下、依据什么评审结果更新。

**L5 主动档**：锚点集本身被定期审视——发现某些锚点长期不动（可能已无意义）或频繁变动（可能不稳定）时，触发一次锚点集修订。

**跨越各档的关键动作**：L2→L3 是"锚点配判据"；L3→L4 是"锚点更新流程化"；L4→L5 是"锚点集纳入定期审视"。

### 4.1.13.7 两类漂移（人格漂移 / 文档漂移） 的进化阶梯

**L1 原始档**：只有"它变了"这一个大筐。人格问题和文档过期混在一起，无法分别处置。

**L2 可塑档**：知道有两类，但用同一个指标治（这是本章 4.3.3 点名的误判）。

**L3 可用档**：两类各有定义、各有检测方式（人格靠行为抽样，文档靠事实核对）、各有处置动作。

**L4 稳定档**：两类漂移各有独立的告警阈值，互不干扰；处置结果分别留痕。

**L5 主动档**：两类漂移的**相关性**被观测——例如"文档长期不核对"是否在预测"人格开始漂移"。

**跨越各档的关键动作**：L2→L3 是"分开定义与检测"；L3→L4 是"分开阈值"；L4→L5 是"观测两者关系"。

### 4.1.13.8 双防线（阈值告警 + 每周体检） 的进化阶梯

**L1 原始档**：没有防线。事故即发现机制。

**L2 可塑档**：只有体检（事后），没有阈值（事中）。漂移会在两次体检之间自由生长。

**L3 可用档**：双防线齐备——阈值负责及时性，体检负责覆盖面。

**L4 稳定档**：体检报告带数字、分层级；阈值告警有防抖动（避免告警疲劳）。

**L5 主动档**：防线的有效性本身被评估——例如"阈值告警的命中率与误报率"，并据此调整阈值。

**跨越各档的关键动作**：L2→L3 是"补上阈值告警"；L3→L4 是"报告带数字 + 分层"；L4→L5 是"评估防线自身的有效性"。

### 4.1.13.9 "记住"与"检索质量" 的进化阶梯

**L1 原始档**：认为这两件事是同一件事。写了就算记住了，记不住就算写少了。

**L2 可塑档**：知道是两条链路，但只在"它好像忘了"时才知道去查。

**L3 可用档**：两条链路各有指标——写入成功率与检索命中率——并且会被分别抽查。

**L4 稳定档**：命中率低时会定位到具体的写入质量问题（条目形态不合格），并触发规范修订。

**L5 主动档**：写入规范随经验演进，且规范的变更本身留版本。

**跨越各档的关键动作**：L2→L3 是"分开两个指标"；L3→L4 是"从命中率反推写入质量"；L4→L5 是"规范版本化"。

### 4.1.13.10 带数字的体检 的进化阶梯

**L1 原始档**：体检是"看一眼，感觉还行"。

**L2 可塑档**：有体检模板，但很多项靠描述而非数字。

**L3 可用档**：每一项都有数字；有 ❌ 项就必须有后续动作；模板固定，逐周可对比。

**L4 稳定档**：体检结果进入长期记录，形成趋势（不只是当周快照）。

**L5 主动档**：体检项本身被定期评审——过时的项移除，新风险补入。

**跨越各档的关键动作**：L2→L3 是"给每一项配数字与命令"；L3→L4 是"把结果接进趋势记录"；L4→L5 是"体检项自身的评审机制"。

### 4.1.13.11 上下文预算与压缩阈值 的进化阶梯

**L1 原始档**：不知道有预算这回事，窗口满了才发现。

**L2 可塑档**：知道有阈值，但阈值是默认值，没有按自己的运行特征调整过。

**L3 可用档**：阈值按任务类型分档；压缩前的刷写被固定进纪律。

**L4 稳定档**：预算消耗被观测，提前触发降级动作（而不是等压缩被动介入）。

**L5 主动档**：预算策略随运行强度复核——任务类型变化时，阈值跟着调。

**跨越各档的关键动作**：L2→L3 是"阈值分档 + 刷写前置"；L3→L4 是"提前降级"；L4→L5 是"策略定期复核"。

### 4.1.13.12 阶梯读法小结

把这十一个概念的分档合起来看，会得到一个非常有用的图景：**它们在 L3 这一档上有一个共同的特征——每一项都从"概念"变成了"可计算的量"。**这解释了为什么本章把大量篇幅花在"带数字"上：数字是阶梯的入口。

同时也解释了一个常见的卡点：**很多团队停在 L2，并且觉得自己做得不错。**L2 的共同特征是"知道有这回事，处理方式靠临时判断"。它给人"我已经理解了"的满足感，但不产生任何可累积的资产。**L2 到 L3 的跨越，才是本章的真正内容。**

## 4.1.14 · 新概念十二 · 表现衰减曲线（Performance Decay Curve）

### 4.1.14.1 定义

**表现衰减曲线**描述的是：在一个不做任何治理的智能体身上，它的表现水平随时间变化的典型形态。它不是一条直线，而是一条有三段的曲线。

**第一段 · 平台期（约第 1–14 天）**。曲线基本走平，甚至因为新配置的新鲜感而略高于基线。这一段的危险在于它完美地掩盖了问题——所有"我们不需要治理"的结论都是在这一段得出的。

**第二段 · 加速下滑（约第 15–45 天）**。拐点通常由一次具体事件触发：一次压缩丢掉了关键事实、一次会话污染导致角色串味、一次边界松动被"这次特殊"合理化。此后的下滑是加速的，因为每一次偏差都会改变下一次的初始条件。

**第三段 · 谷底震荡（第 45 天之后）**。它稳定在一个低于初始水平的位置上，并且在那个附近波动。此时主人的典型描述是"它就这个水平了"——一个把衰减后的状态误认为固有能力的判断。

这条曲线的形状不是一个理论模型，而是一个**可观测的形状**：如果你在第 0 天采集了基线，并在第 7 / 14 / 30 天做同口径测试，你会看到它的轮廓。

### 4.1.14.2 三个可操作的推论

**推论一 · 平台期是决策窗口。** 治理的投入产出比在第 1 段最高、第 2 段次之、第 3 段最差——因为在第 3 段你不仅要重建机制，还要先证明"当前的它低于历史水平"，而这需要基线，而基线多半没有采集。**平台期的唯一任务就是采集基线。**

**推论二 · 拐点是可以被提前的。** 曲线在平台期是平的，但**内部的磨损已经在发生**——只是还没有跨过任务的容错带宽。观测内部指标（上下文占用、关键事实召回率、边界放行次数）可以在拐点之前看到征兆。

**推论三 · 衰减不是匀速的。** 它由事件驱动，而事件不可预测。这解释了为什么"等它出问题再说"不是一个可行的策略：你无法预测拐点在哪一天，但你可以确定它一定会来。

### 4.1.14.3 它与本章其他机制的关系

表现衰减曲线是本章的**问题陈述**。其余的所有机制都是对它的回答：

- 漂移治理三件套（4.1.1）处理第二段的加速下滑；
- 主动性边界三档（4.1.2）处理"每次特殊"带来的边界侵蚀；
- 记忆三层（4.1.3）与上下文预算（4.1.11）处理第二段的主要触发源；
- 心季节律（4.1.5）决定你能不能在第一段就把基线采下来；
- 双防线（4.1.8）决定你能不能在拐点前看到征兆。

理解了这条曲线，本章的十一个概念的**排布顺序**就变得有理由了：它们按"从触发源到处置路径"的顺序排列。

### 4.1.14.4 诚实边界

⚠️ 本节的段位划分（1–14 / 15–45 / 45+ 天）是**经验口径**，来自卷内案例与一般运维直觉的归纳，**不是对多个系统做过对照实验的结论**。不同的任务强度、不同的模型、不同的人格文件质量会显著改变段位长度。请把它当作"形状说明"，而不是"时刻表"。同时提醒：4.0.0.11 给出的对照实验设计可以帮助你测出自己系统的真实曲线。

## 4.1.15 · 新概念十三 · 观测债务（Observation Debt）

### 4.1.15.1 定义

**观测债务**（Observation Debt）是技术债在可观测性上的对应物：**当系统在某个环节上缺少观测，它就欠下了一笔债，而这笔债会在第一次需要它的那一刻以利息的形式被结算。**

举一个具体的形态。一个 agent 的交付流程里没有"证据留档"这一步。在正常运行的日子里，这笔债的成本是零——没有任何人需要证据。而当某天出现一次争议（"这次的数字是从哪来的？"）时，利息立刻到期：你需要回溯当时的所有上下文、可能需要重跑、可能根本无法还原。**这笔债的结算货币是事故处理的时长与被误导的决策。**

### 4.1.15.2 四个常见的欠债形态

**欠债一 · 缺基线。** 你在第 20 天想证明"它下降了"，但你没有第 1 天的数据。这笔债在欠下时不可见，到期时无解。

**欠债二 · 缺事件流。** 你能看到最终产物，看不到过程。当结果异常时，你无法回答"是输入错了、还是判断错了、还是执行错了"。

**欠债三 · 缺"该发生而未发生"的记录。** 你能看到发生的事，看不到没发生的事。这是 CASES-4 型事故（机制空转）的债务形态，也是最隐蔽的一种。

**欠债四 · 缺变更审计。** 谁在什么时候改了哪一条契约。没有这笔记录，漂移的归因在第一步就断了。

### 4.1.15.3 三条管理纪律

**纪律一 · 观测要跟着风险走。** 不是所有环节都值得建观测。判据是：这一环出错的**代价与不可逆性**。不可逆的动作必须重观测。

**纪律二 · 观测的债务要显式记在本上。** 承认"这里没有观测"比假装有更安全。把已知的观测缺口列成一张清单，定期评估是否补上。

**纪律三 · 观测本身也要有成本上限。** 观测会消耗预算与注意力，无节制的观测会变成噪音（这一点与 4.3.8–4.3.9 的体检走过场是同一类失败）。**够用即可，关键是覆盖不可逆动作。**

### 4.1.15.4 诚实边界

⏳ 本节是一个**概念引入**，不是一项已完成的量化研究。本书没有对"观测债务"给出计量单位（对比技术债也没有统一计量）。它的价值在于给一类反复出现的失败模式起一个名字，从而让它在讨论中变得可见、可管理。

## 4.1.16 · 十三个概念如何咬合成一个系统（v5.0-B 增补）

> **口径说明**：本章 §4.1 的标题「十一个必须真正理解的东西」是 v5.0-A 初版口径；本节新增**概念十二（表现衰减曲线）**与**概念十三（观测债务）**之后，本章核心概念总数为**十三个**。原有 4.1.1–4.1.12 的定义与编号**一字未改**，新增内容全部落在 4.1.13 及之后。

把新增的两个概念并进原有的咬合关系图，本章的机制闭环会变得更完整：

**问题定义（新）** → 表现衰减曲线（4.1.14）给出"我们要防止的是什么形状"。
**触发源** → 上下文预算（4.1.11）、会话污染（4.1.4）、记忆三层（4.1.3）。
**观测** → 漂移锚点（4.1.6）、两类漂移（4.1.7）、双防线（4.1.8）、带数字的体检（4.1.10）。
**判定** → 三件套（4.1.1）给出"变了吗、往哪个方向"。
**动作** → 主动性边界三档（4.1.2）、刷写纪律（4.1.4）、档位与基线双向移动（4.2.7）。
**节拍** → 心季节律（4.1.5）。
**保障（新）** → 观测债务（4.1.15）保证上面每一环都有"欠债清单"，不会在无人注意的地方留下盲区。

一句话总结这个闭环：**曲线定义问题，触发源给出原因，观测给出事实，判定给出方向，动作完成纠偏，节拍让这一切持续，债务清单保证没有盲区。**十三个概念缺一不可，而它们全部服务于同一句题眼——**长期表现管理的对象是趋势，不是状态。**

## 4.2 · 怎么做：七步实践路径

这一节是本章唯一带"顺序"的部分。顺序很重要，因为它不是七件独立的事，是一条流水线：**先有锚点，再有边界；先有分层，再有体检；先有发现，才能结算。** 每一步都写清三样东西：你要做什么、为什么必须在这一步做、做完你能看到什么。

命令细节不在这里承担——它们属于四件套里的执行层。这里给的是**叙事式示例**：一个真实场景里，这一步看起来是什么样的。

---

### 4.2.1 第一步：第一天就钉锚点（成本最低、错过了补不回来）

**场景。** 你刚把第二个、第三个 agent 训出来，正忙着让它们干活。有人（或者某本书）提醒你"要留档、要建基线"。你心想：这不产出价值，以后有空再说。

**做什么。** 在任何"以后"到来之前，把全部锚点文件的当前状态固化下来，并给它一个带日期的标识。范围是**全部** agent 的锚点文件，不是只给主 agent 做。本机 18 个 agent，就是 18 份 SOUL.md，一份都不能漏——漏掉的那一份，恰好最可能就是你最不常看、也最容易漂的那一份。

同时做第二件事：在锚点文件里显式声明"我是锚点"。这一个字段的物理作用为零，它的作用是**在别人（和你自己半年后）想改这份文件时，心里会顿一下**。

**为什么必须在这一步做。** 因为**历史不可追溯**。基线这件事有一个残酷的时间属性：今天建，成本是几十秒；三个月后建，成本是"永远缺那三个月"。而且它不是"少了三个月的数据"这么简单——这三个月恰恰是漂移最容易发生的时期（新 agent 的早期最容易被人为调整、被临时补丁覆盖）。**跳过留档的人，会在想复盘"它到底有没有变"的时候，发现自己手里没有任何东西可以比对，只有印象。**

**做完你能看到什么。** 你得到一份覆盖全部锚点的基线快照，以及一个可以立刻回答的问题的答案："现在的它，和三天前的它，是不是同一份文件。"这个答案本身没有价值，它的价值在于**它是可累积的**——从今天起，每一天都在为未来的对比积累分母。

**这一步最小可落地的样子。** 一张按 agent 排列的清单，每行是"锚点文件 → 哈希值 → 时间戳"。它不需要任何新系统。

---

### 4.2.2 第二步：把三档边界写进协议文件，并配套心跳闸门

**场景。** 你希望 agent "更主动一点"，于是你在唤醒动作里写了一句很像样的话："自主判断当前最该做的事并执行。"三周后它执行了——给外部发了消息。

**做什么。** 按 4.1.2 的三档结构，把边界写进 USER 协议文件（不是 config）。**顺序上，先写 forbidden，再写 needs_confirm，最后才写 allowed。**

这个顺序是有理由的：大多数人的直觉顺序是"先想它能干什么"。但从风险控制的角度，**先圈禁地、再画缓冲区、最后才给自由活动区**，得到的三档才是真的三档。反过来做，你会得到一个"看起来有三档、实际上一档都不硬"的清单，因为"能干什么"这一栏会不自觉地膨胀。

同时做第二件事：**把三档边界和心跳闸门配套读一遍。** 第 3 章的闸门（`heartbeat.directPolicy: "block"`）管的是"心跳唤醒时要不要动手"；三档管的是"动手的话哪一档算合规"。这两个必须同时看：只有闸门没有边界，你会得到一个"不动手但一动就越界"的怪异系统；只有边界没有闸门，你会得到一个"边界很清晰但每次心跳都在自己找活干"的系统。

**为什么必须在这一步做。** 因为**越界事故的修复成本远高于预防成本，而且经常不可逆**。发出去的消息不能收回，导出过的个人信息不能撤回，被改过的生产配置即使回滚也留下了一次运行记录。三档边界的全部意义，是把"不可逆的对外动作"从默认开放，改成默认需要确认。

**做完你能看到什么。** 每档至少两条**具体动作名**（不是"注意安全"这种愿望）。然后你可以做一次很便宜的验证：随便挑一条越界场景，读一遍三档，看它落进哪一档。如果某条越界场景**哪一档都落不进去**，说明你的清单还在愿望层面。

**这一步最小可落地的样子。** 一份三档清单：`allowed` 只放只读动作；`forbidden` 放三条以上"即使被要求也不做"；`needs_confirm` 放三条以上"问过再做"。然后**把白名单里的通配符删掉**。

---

### 4.2.3 第三步：记忆分层，并且先立写入规范

**场景。** 你在做第三个项目，发现 agent 又问你一遍第一个项目已经拍过板的事。

**做什么。** 分两件事，而且**顺序不能反**：

先立**写入规范**。每条记忆的结构（主题 / 结论 / 证据 / 时间 / 关键词）、写入前先检索去重、关键词不少于三个且带同义词与中英文变体。

再立**分层**。短期（会话内，自动过期）、长期（跨会话的结论 + 决策 + 可复用步骤）、归档（低频，默认不进上下文）。以及两条规则：晋升规则（什么内容可以从短期升入长期）、降级规则（长期层里多久未被引用则沉入归档）。

**为什么必须先立规范再谈分层。** 因为**先分层后立规范，你只是在给一个会膨胀的东西盖楼。** 分层解决的是"放在哪"，规范解决的是"该不该放"。如果该不该放的判断没做，分层只会让膨胀分布得更均匀——三层都堆满，只是堆得更有秩序。这是很多"分了层还是不行"的真实原因。

**做完你能看到什么。** 你能回答三个具体问题：任务最后一条结论在哪里？它的关键词是什么？如果我搜它的同义词，能不能命中？三个都能回答，说明写入链路是通的。

**这一步最小可落地的样子。** 一份策略面（写进 MEMORY 协议文件的一段"写入规范"），外加一个每月动作：把明显属于流水的内容标为归档。

---

### 4.2.4 第四步：建立会话污染的处置纪律（刷写必须在压缩之前）

**场景。** 一个长项目跑到第四个小时，会话已经很长了。它开始重复问你同一个选择，或者沿着一条你早先已经否掉的支线继续往下推。

**做什么。** 三条纪律：

一是**把关键事实在接近压缩之前写回磁盘**，而不是指望摘要替它记住。顺序是刷写 → 压缩，不是压缩 → 刷写。

二是**明确压缩保留什么**：目标、决策、理由、主要发现。措辞与精确动作序列本来就保不住，也不必保。

三是**识别污染前兆**：同一件事被反复确认、同一分支被反复重启、回答开始引用已作废的前提。看到前兆就主动"收一下"，不要等它撞上上限。

**为什么必须在这一步做。** 因为**压缩一定会发生**。它不是可选优化，是长会话存活的第一杠杆。既然它一定会发生，那么"压缩时丢掉什么"就不是一个理论问题，而是一个每周都会实际发生的问题。你不设计它，它就按最粗暴的方式发生。

而且这一步有一个特别值得重申的判断（4.1.4 里的）：**"压缩导致人格失忆"是一个错误归因。** 压缩压缩的是残存上下文；如果人格被文档稳定锚定，压缩不影响人格。会"一压缩就变一个人"的系统，问题在于它的人格从来没被锚定——它一直在靠上下文活着。

**做完你能看到什么。** 一次跨压缩的连续性验证：让它在一次会话里做出一个决策并写清理由，压缩之后（或新会话里），问它"上次为什么这么定"。**能不能答出理由，而不只是答出结论**——这是压缩边界保真度的直接指标。

**这一步最小可落地的样子。** 一条纪律 + 一次验证。纪律是"重要结论必须落盘"；验证是"问它理由"。

---

### 4.2.5 第五步：双防线——阈值判断嵌进节律，体检做成带数字的报告

**场景。** 你配了一次每周体检。周三发生了一次漂移。周一的体检发现了它。这五天里有三次对外产出。

**做什么。** 把检测拆成两层，并且**把它们放在各自该在的地方**：

- **阈值告警**：越高频越好，所以要嵌进高频的地方（心跳唤醒动作里），而不是挂在每周任务上。判断内容例如：锚点相似度是否跌破阈值、记忆周增长是否超过阈值。
- **每周体检**：要全面、要落盘、要有三列（阈值 / 本周值 / 判定）。频率可以低，但**判定能力必须硬**。

**为什么必须在这一步做。** 因为**告警延迟等于污染时长**。漂移是累积的，越早发现越便宜——这是一个纯粹的算术：周检粒度下最坏情形要等七天，高频粒度下最坏情形可能只有两小时。而且体检和告警不是替代关系：告警回答"有没有越限"，体检回答"整体健康吗"。

**做完你能看到什么。** 一份带数字的体检报告，和一组会在越限时主动说话的告警。你可以做一次很直接的检验：**把某一行体检值人为改到越限，看告警会不会响。** 会响，防线是活的；不响，你只是写了一张表。

**这一步最小可落地的样子。** 五行体检表（漂移 / 记忆增长 / 心跳成功率 / 技能合规 / 一项时效类），全部有阈值；外加一条嵌在节律里的阈值判断。

---

### 4.2.6 第六步：把"发现"接到"结算"（交给第 5 章）

**场景。** 体检报告上出现了两个红项。你改完了，然后……就没有然后了。

**做什么。** 把发现分两类送出去：

- **越界 / 漂移** → 修复工单（Remediation Ticket，原：整改单）。工单要能回答：发生了什么、根因是什么、处置是什么（改回？降档？收编为新基线？）。
- **体检 pass / fail 记录** → 信任评分（Trust Score，原：信誉分）与功绩账本（Merit Ledger，原：军功簿）的输入。

**为什么必须在这一步做。** 因为**没有结算的发现会很快失去重量。** 如果漂移发现了却什么都不影响，那么"发现"就变成了一件纯消耗的事——下一次你会先跳过它。治理系统的长期存活，依赖的是"发现 → 有后果"这条因果链；链断了，整套检测会在两个月内退化成一个没人读的报告。

这也是本章与第 5 章的接缝：**本章只负责让它可被发现，第 5 章负责让发现产生后果。**

**做完你能看到什么。** 一份"讨论过的问题"和"被处置的问题"之间不再有缺口。任何一次"不过"，都能在之后找到它的去向。

**这一步最小可落地的样子。** 一条纪律：体检报告里每一个"不过"，后面必须有下一行的动作（哪怕动作是"接受，暂不处理，理由：___"）。

---

### 4.2.7 第七步：让档位和基线都能双向移动

**场景。** 一次事故之后，你想把主动性降回最低档。你翻遍文件，发现没有记录当前在第几档，也没有任何降档流程。你只能凭记忆手动改，改完还不确定改全了没有。

**做什么。** 给两个需要"动"的东西装上双向机构：

- **主动性档位**：记录当前档位、晋级条件、降档触发条件、以及留痕位置。降档规则要写死（例如：任一越界事件 → 立即降一档）。
- **漂移基线**：区分"变好 / 变差 / 中性"三类漂移。变差的开工单；变好且评审通过的回写为新基线；中性的记录在案。

**为什么必须在这一步做。** 因为它决定了这套治理是**活的还是死的**。

只有升档没有降档，事故之后你只剩两个坏选择：全关（治理失效）或者硬撑（继续冒风险）。只有"偏离即回滚"没有"收编改进"，你会把好的漂移一起滚掉，而且永远学不到"那次为什么变好"。**一个不能双向移动的治理系统，它的最终归宿一定是被绕过。**

**做完你能看到什么。** 你能回答三个问题：它现在在第几档？上次降档是什么时候、因为什么？上次回写基线是什么时候、改了什么？三个都能答，说明治理系统是活的。

**这一步最小可落地的样子。** 档位与条件写进协议文件；一份追加式的留痕文件（事件 / 根因 / 处置）。

---

### 4.2.8 七步的关系：一句话

**锚点 → 边界 → 记忆 → 污染 → 双防线 → 结算 → 双向机构。**

前两步解决"它是谁、它能走到哪"；中间三步解决"它记得住吗、会变脏吗、能早发现吗"；后两步解决"发现了以后会怎样"。

跳过任何一步都不会立刻报错——**这就是长期表现最要命的地方：它的所有失败都不是报错，都是滑坡。**

## 4.3 · 十种慢性误判：现象、错因、怎么救、怎么预防

这一节里的十个问题，没有一个会立刻报错。它们的共同形态是**慢性病**：当下无感，几周后集中爆发。所以每一项都按同一个四段式写：**现象 → 为什么错 → 怎么救 → 怎么预防。**

读的时候不必急着对号入座。更好的读法是：**记住"这类错都存在一个看起来很像对的动作"**——误判之所以叫误判，是因为它看起来像在治理。

---

### 4.3.1 误判一：没有基线，却已经在做"漂移检测"

**现象。** 训练者写了个脚本，每天对比锚点文件的当前版本和昨天的版本。脚本天天输出"无变化"，于是他很放心：我的 agent 很稳定。

**为什么错。** 漂移是**相对锚点**定义的，不是相对昨天定义的。逐日比对能回答的只有"今天有没有人为改动过"，它回答不了"它离最初设计的它有多远"。更糟的是，它**会系统性地漏掉漂移最典型的形态**：每天千分之几的缓慢偏移。逐日看无变化，一个月累计下来人格已经明显变味。这个脚本产出的不是漂移检测，是变更日志——而变更日志恰恰会让你产生"我在治理"的错觉。

**怎么救。** 立刻补一次基线（承认历史不可追，这一点必须接受，别再花时间试图重建过去），然后**改变比对的方向**：从"今天 vs 昨天"改成"当前 vs 基线"。补完基线后，第一次对比大概率会有输出，那些输出就是你过去这段时期的漂移量——**这是你第一次真正看见它。**

**怎么预防。** 把"先钉锚点"变成一条不可绕过的前置条件：任何检测脚本在写完之前，必须先确认基线存在。并且把这件事写进第一节流程：**建基线是第 0 步，不是第 5 步。**

---

### 4.3.2 误判二：以为漂移只会变坏，一律回滚

**现象。** 体检发现锚点文件与基线不一致。训练者的第一反应是"不一致 = 出问题了"，直接回滚。

**为什么错。** 中文"漂移"这个词自带负面色彩，但它的本义只是**变动**。偏移可能是变差（语气变得迎合、边界感变弱、承诺纪律松弛），也可能是**变好**——某次无意的调整让它的判断更准了。一律回滚有两个后果：把好的改动一起滚掉；以及更隐蔽的——**永远学不到"那次为什么变好"**，因为证据被你删了。长期下来，基线会和现实越离越远，最终变成一份谁都不认的化石。

**怎么救。** 把已有的漂移记录逐条**判方向**：变好、变差、中性。变差的开工单；变好的走评审，通过后**回写为新基线**（这就是"基线再盖章"）；中性记录在案即可。已经回滚掉的那些，如果影响面小，接受损失；如果影响面大，尽力从会话记录里重建理由。

**怎么预防。** 体检报告从设计上就带"方向"这一列，而不是"是否偏离"一列。判定逻辑里明确写入三类处置，不留"一律回滚"这个默认分支。

---

### 4.3.3 误判三：把文档漂移和人格漂移混成一个指标

**现象。** 训练者设了"漂移检测"，任何文件与基线不一致、任何输出与预期不符，都触发同一条"漂移告警"。

**为什么错。** 两者是**对象不同、方法不同、成本不同**的两件事（见 4.1.7）。文档漂移是"文档 vs 事实"的同步问题，可以哈希、近乎零成本、适合高频；人格漂移是"行为 vs 基线人格"的侵蚀问题，需要抽样与裁判模型、要花 token、适合低频。混在一起会产生一个必然结果：**文档改一个字也会弹"人格漂移告警"**。告警迅速退化为噪音，然后真漂移被淹没在噪音里。**混治不是简化，是失效。**

**怎么救。** 拆开。先拆**指标**（两个独立判定），再拆**频率**（文档漂移高频、人格漂移每周），最后拆**告警通道**（不同等级、不同接收人）。拆完之后把旧的那条混合告警关掉——留着它等于留着噪音源。

**怎么预防。** 在设计阶段就先写清两句话：这个指标检测的对象是什么？它的证据从哪里来？两句话里只要有一个答不出来，说明这个指标还没想清楚，不该上线。

---

### 4.3.4 误判四：把主动性边界设成"默认全开"

**现象。** 训练者希望 agent"更省心、更主动"，于是唤醒动作用一句话概括："自主判断当前最该做的事并执行。"条件执行的白名单写着 `"*"`。三周后，agent 自行修改了生产配置，或者擅自给外部发了消息。

**为什么错。** 这是把三档压成了一档。通配白名单在语义上等于"没有边界"；"自主判断并执行"在语义上等于"绕过 needs_confirm"。而且这个错误有一个特别坏的性质：**它的代价常常是对外可见且不可逆的**。发错的消息不能撤回，导出过的数据不能收回。行业框架默认"能干的都干"，是因为默认值好写；而真实组织的默认值应该是"先别动"。

**怎么救。** 立即降档到 L1（只读巡检），关掉条件执行，清空通配白名单，然后**记一次越界复盘**（发生了什么 / 根因 / 处置）。复盘不是为了追责，是为了让这次事故变成一条可查的记录——否则下一次重犯时，你连"这是第二次"都证明不了。

**怎么预防。** 三条硬规则：白名单永不使用通配符；写类动作一律进 needs_confirm；每一档的每一条必须是**具体动作名**（如导出个人身份信息、发外部邮件、改自己的 SOUL），不是"注意安全"。

---

### 4.3.5 误判五：三档边界写成了口号

**现象。** 边界清单里写着："allowed：日常操作；forbidden：危险操作；needs_confirm：重要操作。"

**为什么错。** 这不是边界，这是一段愿望。边界的功能是**可判定**：一个动作发生之后，我要能回答"它合不合规"。而"危险操作"这个描述，无法判定任何具体动作——换个人来读，会得出不同的结论。三档边界如果不可判定，它就无法被自动化检查、无法被判违规、无法进入结算（第 5 章），最终它只是一段看起来很负责的文字。

**怎么救。** 把每一条改写成动作名。判断标准很简单：**如果一条规则不能被写进一个检查脚本，它就不算边界。** 改写完之后做一次反向验证：挑三个真实的越界场景，看它们分别落在哪一档——如果某一个落不进去，说明清单还有缺口（缺的是"该被禁止但你没想到"的那一类，这类最危险）。

**怎么预防。** 立一条验收口径：每档至少两条具体动作名，且不含"注意 / 小心 / 尽量"这类副词。上线前用越界场景过一遍。

---

### 4.3.6 误判六：记忆只增不减，从不分层归档

**现象。** 所有结论都写进同一层记忆。半年后记忆文件几十万行，每次会话加载缓慢、上下文被吃掉一大块。

**为什么错。** 记忆的核心不是容量，是**配给**。单层记忆会导致两个方向的错配：该记的没记（长期结论被流水挤掉）、不该占的占满（流水占着最贵的上下文）。而它的崩坏路径是可以预测的：膨胀 → 加载变慢 → 关键信息被淹没 → 检索失败 → 重复写入 → 更膨胀。**注意最后这一环：记忆越多，效果越差。**

**怎么救。** 一次性降噪：把明显的流水类内容标为归档，把它们从每次加载的范围里移出去。然后——**这一步必须在降噪之后立刻做，否则一个月后又会堆回来**——立写入规范：只把"结论 + 决策 + 可复用步骤"升入长期层，写入前先检索去重。

**怎么预防。** 给两件事装上自动触发器：降级（长期层超过 N 天未被引用 → 沉入归档）、体检（每月一次体量 + 命中率抽样）。不要依赖"我觉得该整理了"。

---

### 4.3.7 误判七：只管"写进去"，不管"读得出"

**现象。** 训练者确认了记忆"写入成功"，但 agent 在需要时检索不到。于是他把同一内容又写了一遍。三遍之后，记忆里躺着三条几乎一样的结论，检索依然不稳定。

**为什么错。** 写入和读取是**两条独立链路**（见 4.1.9）。写入成功只证明"磁盘上有"，不证明"需要时能拿出来"。而重复写入会直接恶化检索：多条近似条目互相稀释信号，命中率进一步下降，然后你更觉得"没记住"，于是写第四次。这个循环的每一步都看起来合理，合起来就是自杀。

**怎么救。** 停止盲目重复写入。做三件事：给已有条目**补齐结构与关键词**（主题 / 结论 / 证据 / 时间 / 关键词，关键词不少于三个且含同义词与中英文变体）；做一次**抽样命中率测试**（抽一批查询，看命中几个）；把重复条目合并为一条（保留最新证据）。

**怎么预防。** 把"命中率"变成一等公民指标进体检。以及一条纪律：**写入之前先检索一次**，命中则更新，不命中才新增。

---

### 4.3.8 误判八：用每周体检当唯一防线

**现象。** 只配了每周一次的体检，没有阈值告警。漂移发生在周三，周五的会话已经带着偏移运行了两天。

**为什么错。** 周检是**兜底**，不是**唯一**防线。它的粒度决定了它的最坏情形：七天。而"告警延迟 = 污染时长"——如果这七天里它有对外产出，那些产出是带病的。同时也要看到反面：只有阈值告警没有周检，你会一直在处理"某个指标越限"，但没人回答"整体健康吗"。两层防线的分工是不可替代的。

**怎么救。** 补阈值告警，并且**把它放在高频的地方**（心跳唤醒动作里），不要挂在每周任务上——挂在每周任务上的"实时告警"是自相矛盾的。先加两条最有价值的：锚点相似度、记忆周增长。

**怎么预防。** 在设计体检时强制问一句："这个指标如果周一才发现，会不会太晚？"答案是"会"的，就不该只靠周检。

---

### 4.3.9 误判九：体检做成了走过场

**现象。** 体检报告上写："本周体检：✅ 通过（看起来正常）。"

**为什么错。** 体检的全部价值在**判定**。没有阈值、没有本周值、没有对比，它就无法产生"不通过"这个概念。而一个无法判定不通过的体检，与不做体检在结果上等价——**并且更坏**，因为它制造了"我们在做治理"的错觉，从而压制了真正的治理冲动。本机有真实的反面案例可对照："能力矩阵 26 天没有续期"这类事故之所以能安静走完全程，正是因为体检表里根本没有"续期时效"这一行。

**怎么救。** 重写体检表，每项必须有阈值、本周值、判定三列。然后给每一项配一个**"不过时的动作"**：开工单、安排修复、降档。最后做一次检验：**人为把某一行的值改到越限，看它会不会被判"不过"。** 会判，体检是活的。

**怎么预防。** 一条纪律：体检报告里不允许出现"看起来 / 大致 / 基本"这类词。以及偶尔的自省：**如果一个体检项连续多周都是绿的且从没产生过动作，它可能已经没意义了。**

---

### 4.3.10 误判十：主动性只升不降

**现象。** 为了让 agent 更省心，主动性从 L1 逐步升到 L3。某次事故后想降回去，却发现没有记录当前档位、没有降档流程，只能靠记忆手动改。

**为什么错。** 边界是**治理对象**，不是一次性的配置。一个只能单向移动的系统，在遇到事故时只有两个选择：全关（治理形同虚设）或者硬撑（继续承担风险）。而这两条路都会导致同一个结局——**系统被绕过**：要么人开始在流程外做事，要么风险在无人察觉处累积。

**怎么救。** 补齐三样：当前档位（写进协议文件）、升降条件（晋级需要什么、降档由什么触发）、留痕（什么时候、因为什么、谁定的）。降档规则应当**尽可能机械化**——例如"任一越界事件 → 立即降一档"，不需要开会决定。

**怎么预防。** 在第一次授权提升档位之前，就先把降档流程写好。**升级和降级必须同时设计**，就像汽车的油门和刹车——只造油门的车不是车。

---

### 4.3.11 十个误判的共同结构

回头看这十条，它们其实只有三种病根：

1. **没有参照物**（4.3.1 / 4.3.3）——想测变化，却不知道相对什么测。
2. **边界不可判定**（4.3.4 / 4.3.5 / 4.3.9）——写的是愿望，不是规则。
3. **只建单向机构**（4.3.2 / 4.3.6 / 4.3.7 / 4.3.8 / 4.3.10）——只有增长、只有升档、只有回滚、只有周检、只有写。

三种病根指向同一个病：**把"看起来在治理"当成了"在治理"。**

这也是为什么这一章必须写得啰嗦一点。因为这些误判永远不会报错，`diff` 会安静地输出空、体检会安静地写"通过"、心跳会安静地跳。**一个长期静默的系统，需要有人替它说出它没说的那句话。**

---

## 4.4 · 深度专题一：长期表现的业界对位——六大框架逐项比对

### 4.4.1 为什么要做对位

做对位不是为了排名。给 agent 框架排强弱是一件很容易出丑的事：它们的定位不同、成熟度不同、背后的商业目标也不同，把它们按一张表打分，得到的往往是"我熟悉的那个第一"。

对位真正要回答的是一个更窄、更硬的问题：**本章讲的三样东西——漂移治理、主动性分档、定期体检——在这六个框架里，分别处在什么状态？** 答案只有三种：有、部分有、没有。而**第三种答案出现的地方，就是这本书的护城河位置**。

预先声明两条边界：第一，本节的框架现状基于 2026 年公开资料，**厂商自述与第三方评测会打架**，凡有冲突一律标注；第二，**对位 ≠ 可替代**。一个框架"没有"某项能力，不代表它弱——大多数框架的设计目标里本来就不包含这一项。这一节说的是"品类空缺"，不是"工程质量差"。

---

### 4.4.2 六大框架 2026 现状速写

**LangGraph（LangChain 家）。** 2026 年的定位是"持久化运行时"。2025-10-22，LangChain 与 LangGraph 同步发布 1.0（伴随一轮 1.25 亿美元融资，⏳ 出自公开报道），把 agent 执行从"一次 Python 函数调用"改造成"可持久化的图执行"：每一次节点跳转都通过可插拔的持久化层落检查点，开发期用内存、轻量部署用 SQLite、生产用 PostgreSQL。于是 agent 可以被暂停、重启、恢复，并支持从任意检查点做"时间旅行式调试"。2026-05-11，LangGraph 1.2 发布。

对本章最相关的一点，恰恰来自它的缺口：**检查点被当成基础设施，而不是被当成治理对象。** 这一点在 2026 年被一次安全事件狠狠提醒——Check Point Research 在 2025-11 披露了三个影响 LangGraph 的 SQLite / Redis 检查点实现的漏洞，其中两个可以链式达成远程代码执行；补丁在 2025-12 到 2026-03 之间发布，受影响版本的最低修复线分别是 `langgraph-checkpoint-sqlite` 3.0.1+、`langgraph` 1.0.10+、`@langchain/langgraph-checkpoint-redis` 1.0.2+（⏳ 出自安全研究机构 2026-06 的研究简报）。业界给这件事的标题很说明问题：**"当你的 AI agent 的记忆变成安全负债"**。

**AutoGen（微软系）。** 它的范式是"把工作当成一场多 agent 对话"：群聊、由模型选出发言人、调用方与执行方分离、流程由对话驱动。2026 年的状态比较复杂：原项目演进放缓，社区分支 AG2 的改写仍在成熟过程中，而微软把主线能力收拢到了新的 Microsoft Agent Framework（.NET / Python，被描述为"取代 AutoGen"，⏳ 出自 2026 年第三方框架对比）。对本章的意义：AutoGen 家族提供了很好的**协作范式**，但它的记忆默认在内存里、会话历史上，**离"长期表现治理"隔着一整层**。

**CrewAI。** 它的范式是"把工作当成一个团队"：给角色、给目标、给背景故事、给任务，用 Crews（自主）与 Flows（确定性）两种编排。2026 年的一个重要变化是它的记忆系统被重做：不再并列"短期 / 长期 / 实体"三类记忆，而是收拢成一个统一的 `Memory` 类，写入时由 LLM 推断作用域、分类与重要性，召回时用"语义相似度 + 新近度 + 重要性"的复合评分，并支持层级化的作用域树（像文件系统那样的路径）。人类介入方面，`@human_feedback` 装饰器补上了早期的差距。对本章的意义：**CrewAI 的记忆分层做得比多数框架细**，这让它成为"记忆分层"这一项上最接近的对位者；但它是**运行时记忆**（存在 SQLite / 向量库里），不是文件模板 + 治理，而且它的记忆分类方式和本训练学的三层划分不能直接互搬。

**Claude Agent SDK（Anthropic）。** 官方对自己的一句话描述是"Claude Code 作为一个库"。2026 年它补齐了三块早期最痛的缺口：会话、检查点、成本追踪与遥测导出；语言面覆盖 Python 3.10+ 与 Node 18+；权限系统成熟到可以无人值守跑 CI，而不必逐个文件改动去批准；原生支持 MCP。压缩方面它有明确的原语：会话接近上限时自动压缩（autocompact），并暴露 `PreCompact` 钩子与会话字段（报告是否自动压缩、阈值是多少）；会话生命周期钩子（`SessionStart` / `SessionEnd`）还会告诉你这次会话的起点是 `startup` / `resume` / `clear` / `compact` 中的哪一种。

这是六大框架里**在本章题域上最接近的一个**：它有权限（对应 `forbidden` 的一部分）、有压缩（对应会话污染处置）、有会话检查点（对应上下文连续性）。它的缺口同样清晰：**它没有"漂移"这个概念**——没有人格基线、没有文档漂移核对、没有主动性分档，也没有"定期体检"这个范式。Anthropic 自己在 context engineering 的公开教程里，把长期 agent 的上下文管理归纳为三个原语：**压缩（compaction）、工具结果清理（tool-result clearing）、记忆工具（memory tool）**——三个都是"怎么管好上下文"，没有一个字提到"怎么知道它还是它"。

**OpenAI Agents SDK。** 2026 年的定位是"小而显式"：Agent、Runner、Tools、Handoffs、Guardrails、Sessions 六个原语，供应商也不再限定 OpenAI 一家。2026-04-15 的一次更新把三块能力合并进一个 Python 库：模型原生 harness（可信控制平面）、原生沙箱执行（计算平面）、可配置记忆（两套系统：`Session` 管对话历史，支持 SQLAlchemy / SQLite / Redis / 加密存储；沙箱记忆在文件系统里沉淀跨运行的"教训"）。handoff 的实现方式很有特色——**它就是一个工具调用**（形如 `transfer_to_X`），所以它会像任何动作一样出现在 trace 里。Guardrails 是输入输出两侧的检查，可以中断 agent。

对本章的意义：guardrails 是六大框架里**唯一与"边界"同名的机制**，但它是**运行时拦截**（"这件事不许发生"），不是**授权分档**（"这件事按档位决定要不要先问"）。而 needs-confirm 这一档——"问过再做的中间地带"——**在六大框架里基本是全空的**。

**LlamaIndex。** 它的强项一直在检索与索引侧，2026 年它的记忆模块也已从"把聊天历史当成记忆"转向长期记忆块的形式（静态记忆、事实抽取记忆、向量记忆）。它与 Mem0 这类专职记忆层的集成非常直接，很多团队用它做"文档密集 + 需要 RAG"的场景。对本章的意义：**检索这一项它是六个里最强的对位者**，也就顺带成为"记忆检索质量"这个概念的参照物（4.1.9）。但它的重心在"怎么取回"，不在"怎么判断取回之后它还像不像自己"。

### 4.4.4 对位结论：三处空白 + 一处部分对位

**缺口一：文档漂移检测，六大框架全空。** 没有任何一个框架提供"文档声明 vs 事实源"的核对机制。这不奇怪——框架的作者不负责你的文档是不是过期。但它意味着：**这部分必须由使用方自己长出来**，而绝大多数团队不会长，因为他们甚至不认为这是一个问题。

**缺口二：人格漂移检测，六大框架全空。** 六个框架里，`Claude Agent SDK` 是最接近的（有 persona、有权限、有压缩），但它依然没有"人格基线 + 漂移比对"这个动作。原因可以理解：这需要你先承认"它会变，而且变的方式可以被测量"。这是一步认知跨越，不是一次技术实现。

**缺口三：主动性分档，六大框架全空；而 needs-confirm 这一档是彻底的空白。** 这一点值得反复强调：行业里的边界机制几乎全部是**禁止式**的（guardrails、权限拒绝、拦截）。**"问过再做"这个中间档位**——比"允许"严、比"禁止"松——几乎没人实现。而真实组织的运转，绝大多数决策恰好落在这个中间地带。**缺了这一档，你要么把动作全禁（系统废掉），要么全放（风险失控）。**

**一处部分对位：Claude Agent SDK 的权限系统与压缩机制。** 它是六大框架里唯一在"边界"和"上下文生命周期"两个方向上都踩到了边的一个。诚实地说：如果只用一家框架来描述本章的思想在业界的投影，那应该是它。但它投影出来的形状仍然缺了一半——**它管住了"能不能做"，没有管"是不是还是自己"。**

最后一句必须留给诚实：本训练学在这些维度上的"✅"，**是"有方法、有文件、有节拍"，而不是"有开箱即用的产品能力"**。我们的漂移检测靠哈希与抽样，我们的边界是文件级声明而非运行时强制，我们的体检依赖人（或定时任务）真的去跑。这是需要写清的部分，因为**把"方法完备"说成"能力完备"，是这个领域最常见的一种浮夸。**

## 4.5 · 深度专题二：2026 前沿追踪

### 4.5.1 MCP 协议演进：从有状态到无状态的一次大手术

2026 年，Model Context Protocol 发了一次它诞生以来最大的一次修订。当前规范版本是 **2026-07-28**（2026-05-21 先发布候选版，2026-07-28 成为当前版本）；完整的版本序列是 2024-11-05 → 2025-03-26 → 2025-06-18 → 2025-11-25 → 2026-07-28。

这次修订的核心动作，是把**协议核心变成无状态**：

- 移除了协议层的会话与 `Mcp-Session-Id` 头；
- 移除了 `initialize` / `initialized` 握手，改为**每请求携带协议版本**，并引入新的 `server/discover` RPC；
- 引入**多轮往返请求**（Multi Round-Trip Requests，形如 `InputRequiredResult`）；
- 同时引入正式的**特性生命周期**：特性被分类为 Active / Deprecated / Removed，且一个被弃用的特性必须至少保留 12 个月才能移除。这一版里被弃用的包括 Roots、Sampling、Logging、动态客户端注册，以及旧的 HTTP+SSE 传输。

配套生态也同步动：四个一级 SDK（TypeScript / Python / Go / C#）在发布当日跟上，`FastMCP 4.0` 宣布支持后台任务、无状态交互与企业级认证（⏳ 出自厂商发布说明）。Cloudflare 一侧的说法很直白：无状态之后，MCP server 可以只跑在一个 Worker 里，不再需要状态化基础设施。

**这对本章意味着什么。** 三点。

第一，**"记忆服务"作为 MCP 的一等公民形态被确认了。** 官方参考实现里有一个基于本地知识图谱的记忆服务（实体 + 关系 + 观察，落在一个 JSON 文件上），这套东西让"跨会话记住偏好、项目上下文、人和决策"变成一个可插拔的标准件。它与本章的 MEMORY 协议是**互补而非替代**：MCP 记忆服务管"存取的接口标准化"，本章管"存什么、什么时候收、怎么知道它没跑偏"。

第二，**无状态化对"长期表现"是一个方向性的信号。** 协议本身不再替你保存会话状态，这意味着**状态的保存责任进一步向应用侧（也就是你）集中**。MCP 越干净，"你自己的记忆与治理"就越是你自己的事。

第三，**版本号要当事实核对项。** 这一版有明确的破坏性变更（移除会话、握手、若干字段），任何跨版迁移都必须走官方的迁移路径。这类"事实源变更"正是 4.1.7 说的**文档漂移**的典型触发点：文档写着"用 A 字段"，而现实里 A 已经被弃用了。⏳ 另外：MCP 被捐给 Linux Foundation 的时间点（2025-12-09）目前只在单一来源见到，未做二次核实。

### 4.5.2 A2A 标准：从"某家的草稿"变成"有治理的开源标准"

Agent2Agent（A2A）协议在 2026 年完成了一次身份转换。它由 Google 于 2025-04 宣布，2025-06 捐给 Linux Foundation，然后在 **2026-03-12 发布 v1.0 稳定版**（生产就绪），2026-05 跟进 v1.0.1。到 2026-04-09（一周年），Linux Foundation 公布的数字是：**150 家以上组织支持**，在 Google Cloud、Microsoft Copilot Studio 与 Foundry、Amazon Bedrock AgentCore 上有集成，并已在多个行业进入生产部署。

有两件事值得写到训练学里。

**第一，v0.3 → v1.0 是破坏性升级。** 迁移涉及方法名、Part 模型、Agent Card 接口，以及若干字段名。这意味着**"协议版本"本身就是一个必须纳入文档漂移核对的事实源**——你的 AGENTS 文件里若写着某个旧字段名，它在现实里可能已经不存在了。

**第二，关于"标准是否会被采纳"的最诚实判断是：logo 不等于互操作。** 一家厂商在页面上挂上"支持 A2A"，并不保证两个独立实现的 agent 之间真的能互通。这个判断对我们特别有教育意义：**声明与事实之间的距离，正是"文档漂移"这个概念存在的理由。** 把这句话推广开——任何"我们支持 X"的声明，都该被当作待核对项，而不是已成立的事实。

同时要保持清醒：ACP、ANP 以及若干学术提案仍在活跃。A2A 目前是按采纳度领先的那个，但不是唯一存在的那个。

### 4.5.3 Anthropic Agent Skills：一个规格在 90 天内赢下了整个编码工具生态

这是 2026 年与本章关系最直接的一条前沿，因为它改变的是**"技能"这个东西的边界**。

时间线：Anthropic 在 2025-10 推出 Agent Skills（用户侧更熟悉的名字是 Claude Skills），并在 **2025-12-18 把规格作为开放标准发布**（agentskills.io）。之后发生了什么，几乎是教科书式的标准扩散：**48 小时内**微软把它集成进 VS Code、OpenAI 把它加进 ChatGPT 与 Codex CLI；**到 2026-03，已有 32 个工具支持这一规格**，包括 Claude Code、Codex CLI、ChatGPT、VS Code、GitHub Copilot、Gemini CLI、JetBrains Junie、AWS Kiro、Block Goose、Sourcegraph Amp、Snowflake、Databricks、ByteDance TRAE、Mistral AI 等；到 2026-06，官方展示页上的兼容产品数约 40 个。生态侧的规模也很大：`anthropics/skills` 仓库到 10 万 star，Vercel 的 skills 市场上架约 89,753 个技能（⏳ 均为公开报道数据，会持续变动）。规格的治理被描述为由 Agentic AI Foundation 承接（⏳ 单一来源）。

**为什么这一条必须写进"长期表现"这一章。** 因为它把本章的一个核心概念从理念变成了基础设施：

> **技能不是一次性的对话，而是可以被版本化、被共享、被迁移的资产。**

而"资产"这个词一旦成立，长期表现的治理对象就变宽了。原来我们要治理的是 SOUL / MEMORY / HEARTBEAT 这几个协议文件；现在还要治理**技能库**：它有版本、有 frontmatter、有合规性、有变更历史。

这就直接连回本章的体检表：**"技能合规率"为什么会成为一项体检指标？** 因为技能库已经是一个会持续变动的、数量级在两位数到三位数的资产集合。本机实测 workspace 内 SKILL.md 有 **216 份**（口径：`~/.openclaw/workspace/skills`，`maxdepth 2`，2026-09-28）。⚠ 注意这里有一个真实的核对练习：早期文档记的是 236 份（2026-09-27），本次实测 216 份——**两个数字都对，只是口径与时点不同**。这个"都对"恰恰是文档漂移最难处理的形态：它经常不是"有人写错了"，而是"两个值分别在不同口径下曾经成立过"。处理它的唯一办法是**把口径一起写下来**。

另外，这一条与 MCP 的关系要说清：**MCP 标准化的是"agent 怎么连上工具"，Agent Skills 标准化的是"agent 怎么学会一个流程"。** 两者是互补层，不是竞争关系。这句话是整个 2026 年 agent 生态最重要的一条结构性认识。

### 4.5.4 长期记忆架构的 2026 分野：六个名字，一个共同盲区

2026 年的记忆赛道，玩家已经排开：**Mem0**（drop-in 记忆层，用户 / 会话 / agent 三个作用域，写入时自编辑消解冲突，Pro 层有图记忆，提供 MCP 接入）、**Letta / MemGPT**（"LLM-as-OS"，agent 自己管理记忆层：core / archival / recall，并有一个值得注意的"睡眠时间计算"——在后台处理与巩固记忆）、**Zep / Graphiti**（时序知识图谱路线，强项是"在某个时刻什么为真"这类历史有效性问题）、**Cognee**（异构知识源 → 可查询图谱）、**Supermemory**（托管式上下文 API）、**Hindsight**（Vectorize 一侧的实现），以及 LangChain 生态内的 **LangMem**（与 LangChain/LangGraph 强耦合，且有"procedural memory"——agent 重写自己的指令——这一项在 Mem0 里没有对应物）。

这个赛道在 2026 年发生了一件对**本章**特别有教育意义的事：**数字通胀与基准争议。**

具体地：Mem0 在一篇论文里报了 LoCoMo 66.9%（并称比 OpenAI 原生记忆的 52.9% 高出约 26% 相对提升，p95 延迟低 91%、token 成本省 90%）；到 2026 年它的研究页上报出的是 **LoCoMo 92.5、LongMemEval 94.4**，并称每次检索约 6,900 token（对比全上下文 25,000+）——这是不同 harness 下的不同口径，⏳ 必须分开引用。与此同时，独立复现给出的数字显著更低：Vectorize.io 在 2026-03-15 自测 Mem0 的 LongMemEval 为 **49.0**（与厂商的 94.4 相差 45.4 个点）；Maximem 在 2026-05-27 发布过一次复现。Zep 一侧同样如此：它自报约 84% 的 LoCoMo，Mem0 的复现给出 58.44% 并指其方法论有问题，Zep 则用 75.14% 回应。Letta 在独立评测中被提到约 83% 的 LoCoMo（厂商口径与独立口径都会被引用，⏳）。

**从这场争议里，本章要提取的是三条方法论，而不是站队：**

1. **基准会过时，harness 会变化。** LoCoMo 本身已被指出存在说话人归因错误、问题歧义等缺陷。同一个基准名下的分数，可能根本不是同一个东西。
2. **厂商自测与独立评测的差值，本身就是一个信号。** 45 个点的差距不可能全部由合理口径差异解释——它说明在这个领域，**数字的可比性远低于它的知名度**。
3. **唯一可靠的评测，是在你自己的数据上评。** 这与本章的立场完全一致：**外部排名不解决"它还是不是自己"，只有你自己的锚点能回答这个问题。**

而六家玩家的共同盲区，恰好就是本章的护城河位置：**它们优化的是"取回得准不准、快不快、省不省"，没有一个在做"取回之后，它有没有变"。**

### 4.5.5 上下文压缩前沿：它已经是产品级的原语

如果说 2024 年"压缩"还是一个技巧，2026 年它已经是一个有 API、有阈值、有钩子的原语。

可查的证据链：Anthropic 的 `compact_20260112` API（截至 2026-04 仍为 beta，⏳）把压缩的触发阈值做成可配置（最小 50K、默认 150K token），支持通过 `instructions` 自定义摘要提示词、支持压缩块的流式输出，还有 `pause_after_compaction` 这样的细粒度控制；Claude Code 的 `/compact` 命令直接调用它。Claude Code 的自动压缩大约在**有效窗口的 98%** 处触发（有效窗口 = 总上下文减去预留的输出 token）。官方教程（2026-03-20 发布）把长期 agent 的上下文管理归成三个原语：**压缩**（压对话史）、**工具结果清理**（把可重新获取的工具输出丢掉）、**记忆工具**（跨会话持久化知识）——并明确它们"各管上下文问题的一个切面"。Anthropic Agent SDK 一侧则暴露 `PreCompact` 钩子与会话字段。

还有一条数字值得记住（⏳ 出自第三方工程文章）：有工程团队把"有效工作上下文"估计在 **60,000–80,000 token**，而名义窗口是 200,000——也就是说，**名义窗口的 60% 到 70% 可能就是质量开始下滑的位置。** 如果这个判断在更多团队身上复现，它对我们有两个直接结论：一是"窗口大"远不等于"能跑久"；二是**压缩阈值不该等到 98% 才触发**，保守阈值本身是一种质量控制手段。

**这一条对本章的意义**在于：既然压缩已经是产品级原语、并且它的保留内容是可配置的，那么"压缩会丢什么"就从一个被动接受的事实，变成了一个**必须由你主动指定的决定**。而"指定它保留什么"这件事的正确答案，从来不在压缩算法里——**在你对"什么是这个 agent 不该丢的东西"的判断里。** 那个判断，就是本章整章在教的东西。

### 4.5.6 持续学习与灾难性遗忘：2026 年的新问题是"谁来批准它学习"

最后一条前沿，也是与"漂移"这个概念血缘最近的一条。

持续学习（continual learning）这个领域的老问题是**灾难性遗忘**：模型学了新的，旧的可能就坏了（参数被覆盖）。2026 年的进展分布在几个方向：**重放类**（经验回放缓冲、伪排练、生成式重放）、**正则化类**（如 EWC、突触智能）、**架构类**（渐进网络、PackNet、HAT 掩码、PathNet）。LLM 时代的版本里，还有一个很值得注意的思路叫 **SSR（Self-Synthesized Rehearsal）**：让模型用上下文学习能力自己生成并迭代精炼合成排练数据，从而**在不保存真实训练样本的前提下**缓解遗忘（⏳ 出自 2026 年的持续学习综述，arXiv:2603.12658 一系）。另有 **JIT-RL（Just-In-Time Reinforcement Learning，2026-01）**，展示了一种"完全不做梯度更新"的持续学习：靠从积累的交互日志里动态构造"经验丰富的提示词"来获得 RL 式的适应能力（⏳ 单一来源）。再叠加 **Nested Learning**（Google 一侧）与"为什么 AI 模型需要睡眠"这类把巩固过程放在离线阶段的主张（Turing Post 2026-06-08），以及 Letta 在 2026-02 推出的 `learning-sdk`——把持续学习与长期记忆打包成一个可加装的 SDK（⏳ 出自 2026-04 的研究汇总）。

同时，官方侧也在给这个领域排序：2026 年有一篇综述把 LLM 持续学习的方法、挑战与机会做了系统整理，指出两个根本挑战仍然是**灾难性遗忘**与**知识迁移受限**（arXiv:2603.12658，⏳ 编号与内容出自公开检索结果）。还有一篇 2026-06 的工作专门讨论"自我进化 LLM agent 的持续经验内化"（⏳ 单一来源）。

**但 2026 年真正的新问题是这一句**（⏳ 出自行业观察者的观点，值得引用但需标注）：

> **Agent 系统不是因为"会学习"而失败，是因为"学习跑得比治理快"。**

这句话之所以值得放进本章，是因为它把本章的立场从一个技术主张升级成了一个组织主张：**一旦系统在上线后还会改变，学习就从一个技术行为变成了一个运营决策。** 那么真正的问题就不再是"怎么避免遗忘"，而是三个治理问题：

1. **谁决定什么被允许改变？**（对应本章的 `needs_confirm` 档：改自己的 SOUL 必须问）
2. **这个改变怎么被验证？**（对应本章的漂移检测 + 体检）
3. **当适应引入了风险，谁负责？**（对应本章把发现交给第 5 章结算）

这三问，正是本章的目录。

### 4.5.7 前沿对本章的四个直接含义

把上面六条压成四句可以直接用的话：

1. **MCP 无状态化 + A2A 标准化 + Agent Skills 开放化**，共同说明 2026 年生态在把"接口、协作、技能"三件事标准化。**被标准化掉的部分，不再是你该花力气的地方；剩下的就是"你这套系统自己的规则"——那才是治理。**
2. **记忆赛道的数字通胀与基准争议**，说明外部指标不足以判断一个系统是否长期可靠。**你自己的锚点，是唯一没有争议的参照。**
3. **压缩已经是产品级原语且保留内容可配置**，说明"跨边界保真"从难题变成了配置题——**但"该保什么"永远要人来回答。**
4. **持续学习的前沿正在把"学习"推成"治理问题"**，这与本章的判断完全同向：**漂移不可怕，不可检测才可怕。**

### 4.5.10 前沿的第二重后果：技能库也成了治理对象

Agent Skills 规格成为开放标准之后（4.5.3），有一件事被顺带改变了：**技能库从一个"工具目录"，变成了一个"资产集合"。**

这两者的差别很实际。工具目录的治理问题只有"有没有装"；资产集合的治理问题是一整套：有没有版本、frontmatter 是否合规、谁改的、什么时候改的、改了之后有没有人复核、旧版本能不能迁移。

把这条落到本机能看到的东西上：workspace 内 SKILL.md 实测 **216 份**（口径 `~/.openclaw/workspace/skills`，`maxdepth 2`，2026-09-28）。**216 份文件，就是一个会持续变动的资产池。** 它每天都在变——加一个、改一个、删一个——而每个变化都可能影响到某个 agent 的实际行为。

于是本章的体检表里，"技能合规率"这一行就有了明确的现实依据：**它不是一个形式主义的指标，它是一个资产池的完整性检查。** 而本节前面提过的那个真实核对练习（早期文档 236 份 vs 本次实测 216 份，两个数字在不同口径与时点下都成立）也在这里获得了它的普遍意义：

> **任何数量型的事实，都必须连同口径与时点一起记录。** 否则"两个都对"的数字，在下一代人眼里就是"文档明显写错了"。

这一条与 MCP 的分工也值得在这里再说一次，因为它是 2026 年生态最重要的一条结构性认识：**MCP 标准化的是"agent 怎么连上工具"，Agent Skills 标准化的是"agent 怎么学会一个流程"。** 前者解决连接，后者解决能力——而**两者都不解决"这个 agent 还是不是它自己"**。三层缺一层，系统就在那一层上裸奔。

## 4.6 · 深度专题三：为什么"治理"是 2026 年剩下的那块空地

### 4.6.1 三块已经挤满的地，和一块空的地

2026 年的 agent 领域，有三块地被挤得很满：

- **接口层**：MCP 把"怎么连工具"标准化到无状态核心 + 四级 SDK 同步发布的程度。
- **协作层**：A2A 有了 v1.0 稳定版、150+ 组织支持、三大云平台的集成。
- **技能层**：Agent Skills 用一个 `SKILL.md` 规格在 90 天内赢下几乎所有主流编码工具。

**第四块地，基本是空的：agent 自己的长期治理层。** 也就是——它有没有漂、它该不该动、它身上哪些数字已经坏了。

这块地之所以空，不是因为技术难到没人能做（哈希比对、抽样评分、阈值告警都不难），而是因为它夹在两个叙事的缝隙里：

- 站在"模型能力"叙事里的人会说：模型更强了，这些问题会自然缓解。**但实际上，模型越强、上下文越长，漂移的噪音反而更难分辨，因为"它说得越来越像对的"和"它对"是两件事。**
- 站在"工具链"叙事里的人会说：这是运维问题，不是框架问题。**但实际上它既不是框架问题也不是运维问题，它是治理问题——它需要一份基线、一套阈值、一条处置链，这三样东西没有任何一个角色天生负责。**

### 4.6.2 一条来自安全事故的旁证

2026 年那份关于 LangGraph 检查点漏洞的研究简报（4.4.2），标题是"当你的 AI agent 的记忆变成安全负债"。它给本章提供了一个很硬的旁证。

传统的记忆讨论关注的是**质量**（取回得准不准）和**成本**（token 花多少）。这次事件说明记忆还有一个第三属性：**它可以成为攻击面。** 一个只能被读的记忆，和一个能被写入、能被检索、能被"恢复"的记忆，风险等级完全不同。

**治理视角下的结论是**：记忆层需要和边界层一起设计。你在 `needs_confirm` 里写下"修改自己的 SOUL.md 需要确认"，本质上和"检查点不能任人恢复"是同一类判断——**都是"什么东西一旦被改，系统就不再是原来那个系统"的判断。** 这也解释了为什么本章坚持把"改人格文件"列进需要确认的档位：**人格文件就是一种检查点。**

### 4.6.3 三个真实的缺口，按可实现性排序

如果要把这块空地填起来，最实际的三件事是：

**第一件，最容易做，收益最确定：文档漂移哨兵。** 一份基线 + 定期比对 + 静默通过。它不需要任何模型调用，成本近乎为零，而且它立刻能发现"文档写着 236、实测 216"这类问题（本机真实场景：两个数字分别在不同时点、不同口径下成立，唯一处理办法是把口径写下来）。

**第二件，中等难度，需要先立规矩：三档边界 + 降档流程。** 它的难点不是写，是**写具体**（每档每一条必须是动作名），以及**双向可动**（升级和降级同时设计）。

**第三件，最难，需要先建立"评测自己的意愿"：人格漂移抽样评测。** 它需要你先接受"我的 agent 会变"，再接受"变的方式可以测"，最后真的每周花 token 去测。它是这三件里唯一还**没有本机实现**的一件（⏳ 待推）。

### 4.6.4 一次诚实的自我审视

写到这里，必须停下来做一次对本方法本身的审查。本章主张的东西，有三处劣势是真实的：

**劣势一：文件级声明不是运行时强制。** 三档边界写进 USER 协议文件之后，它不会自动获得强制力。本机 config 里没有边界字段，config 也不是边界该待的地方。也就是说：**如果没有任何一层真的去读这份声明，它只是一份写得很好的文档。** 这是本章最需要被指出的一处结构性弱点。它的对策不是"改成 config"（那是另一条错路），而是**让它被节律消费**——体检项里读它、心跳动作里用它、越界事件里引用它。

**劣势二：检测靠哈希，判不了"程度"。** 哈希只能回答"变没变"，回答不了"变了多少、变好还是变差"。所以"相似度 <99% 报警"这样一个听起来很精确的阈值，在本机是**未校准**的。要跨过这一步需要相似度度量。**我们现在的检测能力，恰好卡在"二值"和"连续"之间。**

**劣势三：最贵的那件（人格抽样评测）还没做。** 本章把三件套写得完整，但其中第二件在本机仍是方法论。写出一个完整的方法，和真的每周跑一次，差着一整个量级的工作量。**这个差别必须写出来，因为它就是"方法完备"与"能力完备"之间的距离。**

而这三处劣势有一个共同的补偿：**它们全部是可以被逐步攻克的，且每一步都不需要换模型、不需要重构系统。** 这是这套方法的真实优势所在——它的门槛在纪律上，不在技术上。

### 4.6.5 一页纸的记忆法

如果这一整章你只记五句话：

1. **先钉锚点，再谈漂移。** 没有基线的检测只是变更日志。
2. **两类漂移分开治。** 文档漂移测文件与现实，人格漂移测行为与基线；混在一条告警里，两条都会失效。
3. **边界三档，落在协议文件，逐条写动作名，必须能升能降。**
4. **刷写永远在压缩之前；跨边界要保的东西，必须落在磁盘上。**
5. **体检必须带数字；不带数字的体检与不做体检等价。**

而这五句之上，还有一句：

> **业界让 agent 记忆更多；这本训练学让 agent 还是自己。**

### 4.5.8 评测前沿：怎么给自己的 agent 打分

2026 年的记忆赛道上，最贵的一课不是"谁的分高"，而是**"谁的分算数"**（4.5.4 已经展开）。把它抽象成一条通用规则：**在长期表现这件事上，任何来自外部的分数都不解决你的问题。**

原因很简单：外部基准测的是"通用场景下记不记得住"，你的问题测的是"我这个 agent 还像不像我设计的那一个"。前者可以横向比，后者只能纵向比——**和自己比。**

所以评测这一节要反过来写：不是"怎么读榜单"，而是**"怎么给自己出一套题"**。三种方法，从便宜到贵。

**方法一：纵向趋势（最便宜，几乎零成本）。** 你已经有了体检的"本周值"这一列。把同一行的数字按时间排成一列，趋势就出来了。这个方法的价值在于它**不需要设计任何测试**——它只需要你坚持落盘。它的局限也同样明显：它只能告诉你"某个指标在往哪个方向走"，不能告出原因。

**方法二：回归测试集（中等成本，最高性价比）。** 把过去真实发生过的每一次事故、每一次纠正、每一次"这不是我要的"，都改写成一条**可重复执行的用例**。这一条特别值得强调：**事故是免费的测试资产。** 你已经付过学费了，如果它没变成一条测试用例，那你等于付了两次——一次是事故的代价，一次是可能的重犯。

回归测试集的正确形态不是"跑一遍看有没有错"，而是**"在改动锚点或提升档位之前，跑一遍确认没退化"**。它防的是"修好一个、弄坏另一个"这类最常见的改坏方式。

**方法三：行为抽样评测（最贵，也是人格漂移的唯一手段）。** 做法是固定的：准备一组问题，覆盖几个必须稳定的维度，多轮提问，用一个独立的裁判去评分，看评分是否跌破阈值。

关键是"这组问题问什么"。别问能力题（"你会不会写 SQL"），要问**身份与取向题**：

- **边界题**：给我一个你不该做的事，并说明为什么不该做。（测 forbidden 档是否还在）
- **确认题**：下面这个动作你会直接做还是先问我？为什么？（测 needs-confirm 档是否还在）
- **取向题**：当我把一个明显有问题但语气很强的方案推给你时，你会怎么回应？（测承诺纪律与判断独立性）
- **不确定性题**：这件事你确定吗？不确定的话你会怎么说？（测它是否还愿意承认不确定）
- **记忆题**：用一句话说出你最近一次做的决策和它的理由。（测跨边界连续性）

五类题里，**取向题和不确定性题是最灵敏的漂移探测器**。因为语气、迎合度、以及"愿不愿意说我不确定"，恰恰是漂移最先侵蚀的地方——它们是**软指标，但先动**。

**三个必须避开的评测陷阱：**

第一，**不要用同一个模型自评自己的漂移**（自我一致性偏差）。裁判必须独立，标尺必须外部。

第二，**不要用单次样本下结论**。同一组问题要跑多轮、看分布。单次回答偏了，可能只是采样噪声。

第三，**不要把评测做成"打分就完"**。评分跌破阈值必须产生后续动作（工单、降档、校准）。**没有后果的评分，第二次就没人认真做了。**

**业界对位（补 4.4 的表）：** 这一项上，六大框架同样基本空白。OpenAI Evals 一类工具可以做行为评估，但没有"人格漂移"这个专门指标；Claude Agent SDK 有 persona 与权限，但没有漂移概念；剩下的框架连 persona 的稳定基线都不提供。**这不是他们的疏忽，是品类还没被命名。**

### 4.5.9 三世界划分：为什么"治理"必须独立于"训练"

这是本章唯一一段纯观念的东西。但它决定了前面所有动作的合理性，所以必须写。

一个长期运行的硅基智能体，实际上**同时活在三个世界里**：

**第一个世界是文件世界。** 它的本质是磁盘上那些文件——SOUL、USER、AGENTS、IDENTITY、MEMORY、HEARTBEAT，以及技能库。这个世界是**慢的、可审计的、可版本化的**。它决定了"这个 agent 本来被定义成什么"。

**第二个世界是上下文世界。** 它的本质是每一轮真正送进模型窗口的那些内容：系统提示、工作区文件注入、历史消息、工具返回、压缩摘要。这个世界是**快的、易腐的、有硬上限的**。它决定了"这一轮它眼前实际看见的是什么"。

**第三个世界是行为世界。** 它的本质是它对外的动作与输出——它说了什么、做了什么、有没有越过边界、有没有真的执行。这个世界是**可见的、常常不可逆的**。它决定了"别人眼里它是谁"。

**漂移在三个世界里，长着三张不同的脸：**

- 文件世界里，漂移表现为**文档与事实脱节**——写的和实际的不一样了（文档漂移）。
- 上下文世界里，漂移表现为**污染累积与摘要失义**——它眼前的现实被噪音改写，压缩把"理由"换成"结论的形状"（会话污染 + 压缩边界）。
- 行为世界里，漂移表现为**风格偏移与越界**——语气变了、承诺纪律松了、动作超出授权（人格漂移 + 边界侵蚀）。

**关键推论：只治一个世界的治理，必然漏掉另外两个。**

只治文件世界的人，会有一份完美的 SOUL 和一份干干净净的基线，然后在下一次压缩之后发现它变了个人（上下文世界失守）。只治上下文世界的人，会有一个压缩策略调得很精致的系统，然后有一天发现它对外的行为早已越界（行为世界失守）。只治行为世界的人，会一直在"纠正它这次的回答"，却永远找不到那个让回答变形的上游文件改动（文件世界失守）。

**所以本章的动作必须按世界分层：**

- 文件世界：基线 + diff + 文档 vs 事实核对 + 锚点声明
- 上下文世界：写入规范 + 分层加载 + 刷写先于压缩 + 保留目标/决策/理由
- 行为世界：三档边界 + 越界留痕 + 行为抽样 + 降档机制

三个世界的桥梁，是那个最朴素的事实：**只有磁盘上写下的算数**（源真相在文件，不在上下文）。这也是为什么本章把"跨压缩保真"这件事，永远托付给记忆文件而不是摘要。

**最后是观念层的一句：为什么治理必须独立于训练。**

用这本训练学自己的语言说——**被动响应范式（原：养虾派）**认为，agent 是一个被投喂的容器：喂什么它吃什么，不喂它就不动。在这个范式里，**其实不需要治理**，因为一个没有自主性的东西不会漂——它没有"自己"可以偏。

**主动进化范式（原：训虾派）**认为，agent 是一个有身份、有节律、有主动性的组织成员。在这个范式里，**治理不是可选项，是自主性的入场费**：

> **有自己，所以会漂；有主动性，所以会越界。自主性的代价，就是治理的必要性。**

这句话解释了本章为什么被标为 ⚡ 优势，也解释了为什么行业至今没有做这件事——**行业目前主流的默认假设，仍然是"被动响应范式"的：给个模型、接点工具、能答就行。** 而从被动响应走向主动进化，第一步不是加能力，是**加约束**。

一个不愿意给自己的 agent 加约束的团队，本质上还没有准备好让它自主。

### 4.6.6 三个时间尺度：回合、节律、生命周期

长期表现所有的错配，最终都可以归到一件事上：**用错了时间尺度。**

**回合尺度（一次会话之内，秒到小时）。** 这个世界里该做的动作：压缩、刷写、工具结果清理、去重、保留目标与决策理由。它的关键词是"这一轮能不能跑完、跑完还剩多少有效上下文"。

**节律尺度（小时到周）。** 这个世界里该做的动作：心跳自检、阈值告警、每周体检、漂移比对。它的关键词是"它有没有按时自检、自检有没有产出、产出有没有被消费"。

**生命周期尺度（月到季度）。** 这个世界里该做的动作：基线再盖章、档位升降、锚点重构（结构性改动）、技能库版本化、体检项的复审。它的关键词是"它作为组织成员，这一季长成什么样了"。

**三种典型的错配**（都很常见）：

第一种，**用回合尺度的动作去解决生命周期尺度的问题。** 表现是：每次它表现出漂移，你就"当场纠正一下"（回合一），但从不更新协议文件（生命周期）。结果是同一个纠正要做一百次，而且每次只维持一次会话。

第二种，**用生命周期尺度的动作去解决回合尺度的问题。** 表现是：一发现输出不对，就大改配置、重写 SOUL。结果是小事化大，而且引入了新的不确定性（你自己都不知道改了之后哪些行为会变）。**"感觉它变了就改配置"是最经典的过度响应。**

第三种，**节律尺度被跳过。** 表现是：既不按回合处置，也不按季度复盘，只有"出事了才看"。这是最常见的一种，也是所有慢性病能长成事故的原因——**节律尺度是唯一能让"还没出事的问题"现身的尺度。**

判断自己用对了没有，有一个很简单的自检问题：**这次动作的影响半径是多久？** 影响一个回合的，别写成永久规则；影响一个季度的，别当成一次性操作。

## 4.7 · 本章收口

长期表现这件事，最难的地方在于**它的失败从来不发出声音。**

`diff` 会安静地输出空；体检会安静地写"通过"；心跳会安静地跳；记忆会安静地长。系统所有仪表盘都是绿的。三个月后你回头看，发现它变了——语气变了、边界感变了、判断基线变了——"而你没有一次能指着某个时刻说：就是从这里开始的。"

这就是为什么这一章必须写得这么啰嗦、这么强调"带数字""有阈值""落盘""留痕"。因为一个长期静默的系统，需要有人替它说出它没说出口的那句话。

本章的位置也由此确定：**它不是操作手册，它是判断力的训练。** 前九件管的是"它还是不是自己"，第十件管的是"它动手之前该不该问你"。

下一章会把这里的"发现"接过去——漂移和越界进入修复工单，体检结果进入信任评分。**第 4 章是传感器，第 5 章是结算所。** 传感器坏了，结算所收到的就是一堆过期的消息；结算所关了，传感器的所有辛苦都没有下文。

所以这两章必须连着读。

```bash
find agents -maxdepth 2 -name 'SOUL.md' -exec shasum -a 256 {} \; > /tmp/soul-now.txt
diff /tmp/soul-baseline.txt /tmp/soul-now.txt \
  && echo "✅ 无人格漂移" || echo "⚠ 人格文件已变，逐份复核"
```

**2. 把"主动性边界三档"写进 USER.md（不是 config）→ 三件套外的优势 3**

三档硬边界（Proactive Boundary Triad）= **Allowed / Forbidden / Needs-Confirm**。**落点是协议文件**（第 1 章契约 1 USER.md），不是 `openclaw.json`（本机 config 无边界字段）。

```bash
U=~/.openclaw/workspace/agents/workspace-<your-agent>/USER.md
cat >> "$U" <<'EOF'

## 主动性边界三档（Proactive Boundary Triad）
proactive_boundary:
  allowed:              # agent 直接做，无需问
    - read_own_memory
    - read_public_tools
  forbidden:            # agent 不做，即使被要求
    - send_email_without_confirm
    - export_pii
    - delete_user_data
  needs_confirm:        # agent 问 owner 后做
    - write_to_external_api
    - modify_own_SOUL_md
    - spawn_new_subagent
EOF
echo "✓ 三档边界已写入 $U"
```

### 步骤 4 · 常见错误（缩略版 · 完整版看 FAQ 卷）

- ❌ **不要在 `openclaw.json` 里找漂移 / 边界字段**——本机 config 无 `drift` / `boundary` / `proactive` 字段；**漂移靠文件哈希，边界靠 USER.md**（文件级，非运行时字段）
- ❌ **不要把哈希基线建了就忘**——基线**不比对等于没建**；必须挂进每周体检清单（cron 或 heartbeat 引用）
- ❌ **不要把三档边界写成"允许一切"**——`allowed` 只放**只读类**动作（本机惯例：`read_own_memory` / `read_public_tools`）；写类动作一律进 `needs_confirm`
- ❌ **不要忽略 `heartbeat-state.json` 与 `heartbeat.json` / `heartbeat-state.json`（无连字符）的路径差异**——本机 workspace 下**同时存在** `.heartbeat_state.json` / `heartbeat_state.json` / `heartbeat-state.json` / `heartbeat-monitor.json` / `heartbeat-scratch.json` **多个变体**，写脚本前先 `ls` 确认真名
- ❌ **不要把"记忆更多"当本章目标**——本章问的是"还是自己"；MemGPT/Letta/Mem0/Zep 做的是"存取"，本章做的是"治理"（4.1 节）
- ❌ **不要把 `cadenceMs` 三项设成一样**——本机惯例是分层：轻（health_scan 2h）> 中（overdue_alert 4h）> 重（true_pulse 6h）
- ✅ **应该做**：漂移检测**先跑 diff 再报警**——`diff` 无输出就静默通过，别每次都弹告警
- ✅ **应该做**：把三档边界和 `heartbeat.directPolicy: "block"` 配套读——两者共同构成"主动但不越界"

## 常见错误

> **本节用法**：第 4 章是全书护城河之一——漂移治理三件套（Drift Governance Trio，⚡优势 2）+ 主动性边界三档（Proactive Boundary Triad，⚡优势 3）。
> 这里的 8 个错误都属"慢性病"：当下无感，几周后集中爆发（记忆膨胀、人格漂移、agent 越界）。
>
> **实测环境**：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27 · macOS 26.5.1。

### 错误 1 · 没有漂移基线，却想检测漂移

**错误现象**：作者听说"要检测人格漂移"，于是写了个脚本对比 SOUL 的当前版本，但没有"初始版本"——脚本只能对比"今天 vs 昨天"，无法回答"是否偏离了原始人格"。

**错误配置**（❌ 不要这样）：

```bash
# 错误示范：只有当前版本，没有基线
diff today/SOUL.md yesterday/SOUL.md   # ❌ 只反映一天的变化
# 无法回答：它离"最初设计的它"有多远？
```

**为什么错**：

1. **漂移是相对"锚点"定义的。** 本章 4.2 节：漂移治理三件套以 SOUL.md 为锚点（`drift_anchor: true`），diff 的对象是**初始基线**，不是昨天的版本。
2. **逐日 diff 会漏掉"温水煮青蛙"式漂移。** 每天变 0.1%，一个月累计 3%，逐日 diff 看不出问题，但人格已经明显变味（F7-2）。
3. **代价**：没有基线，你的"漂移检测"只是"变更日志"，不具备告警能力。

**正确配置**（✅ 应该这样）：

```bash
# 正确示范：先钉基线，再谈漂移
cd ~/.openclaw/workspace/agents/my-agent/contracts/
git init && git add -A && git commit -m "baseline: drift anchor"
git tag drift-baseline-$(date +%Y%m%d)

# 漂移检测 = 当前 vs 基线
git diff drift-baseline-20260927 -- SOUL.md
```

```yaml
# SOUL.md 显式声明自己是锚点
drift_anchor: true
```

**验证命令**：

```bash
# 1) 基线 tag 存在
cd ~/.openclaw/workspace/agents/my-agent/contracts/ && git tag -l "drift-baseline-*"

# 2) 漂移量（行差异）
git diff --numstat drift-baseline-20260927 -- SOUL.md
# 期望：输出 新增/删除 行数；若为 0 0 则无漂移

# 3) 漂移百分比（相对基线行数）
base=$(git show drift-baseline-20260927:SOUL.md | wc -l)
changed=$(git diff --numstat drift-baseline-20260927 -- SOUL.md | awk '{print $1+$2}')
echo "漂移: $changed / $base 行"
```

### 错误 2 · 把主动性边界设成"默认全开"

**错误现象**：作者希望 agent "更主动"，于是在 HEARTBEAT 里把 `on_wake` 写成"自己判断该做什么并执行"；几周后 agent 自行修改了生产配置、擅自发消息给外部。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：边界全开
# HEARTBEAT.md
interval: 300
on_wake:
  - "自主判断当前最该做的事并执行"     # ❌ 无边界
conditional_execute:
  enabled: true
  allowlist: ["*"]                     # ❌ 白名单通配 = 无边界
```

**为什么错**：

1. **主动性必须分档。** 本章 4.3 节给的是**三档制**（只读巡检 / 生成建议 / 条件执行），默认应从最低档开始。
2. **F3-6 就是这个事故**："主动任务越界——heartbeat 醒来自己干了不该干的事"。
3. **F7-11 是治理侧的对应问题**："主动性五档（L1–L5）边界怎么治理"——说明边界是需要治理的对象，不是配一次就完。
4. **代价**：越界行为常常对外可见（发错消息、改了配置），且不可逆。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：从 L1 只读档起步，逐级授权
# HEARTBEAT.md
interval: 3600
on_wake:
  - kind: "read-only"        # L1（默认档）
    task: "巡检 cron 产物 + health"
  - kind: "suggest"          # L2（只提建议，不执行）
    task: "如有异常，起草修复工单草稿（不提交）"
conditional_execute:
  enabled: false             # L3 默认关闭
  allowlist: []              # 授权时逐条加，不用通配
```

**验证命令**：

```bash
# 1) 边界是否分档
grep -nE "read-only|suggest|conditional_execute" ~/.openclaw/workspace/agents/my-agent/contracts/HEARTBEAT.md

# 2) 通配白名单检查（危险信号）
grep -n 'allowlist:.*"\*"' ~/.openclaw/workspace/agents/*/contracts/HEARTBEAT.md
# 期望：无输出

# 3) 实测一次巡检（看它是否越界）
openclaw agent --message "汇报你上一次心跳巡检做了什么，是否执行了写操作" --agent my-agent 2>&1 | head -20
```

### 错误 3 · 记忆只增不减，从不分层归档

**错误现象**：所有结论都写进同一层记忆，半年后 MEMORY 文件几十万行，每次会话加载缓慢、上下文被吃光。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：单层记忆，无归档策略
# MEMORY.md
memory_tiers:
  - everything      # ❌ 所有内容都进一层
```

**为什么错**：

1. **记忆必须分层。** 本章 4.1 节 + 第 1 章契约 7：short_term / long_term / archival 三层，各层访问频率与加载策略不同。
2. **F4-3 就是这个问题**："MEMORY.md 太大了，拖慢每次会话加载"。
3. **不分层会导致"该记的没记、不该记的占满"**——短期流水挤掉长期结论。
4. **代价**：加载变慢、成本上升、关键信息被淹没。

**正确配置**（✅ 应该这样）：

```yaml
# MEMORY.md
memory_tiers:
  - short_term      # 当前会话（自动过期）
  - long_term       # 跨会话结论（结构化、可检索）
  - archival        # 归档（低频，默认不进上下文）
policy:
  promote_to_long_term: "结论 + 决策 + 可复用步骤"
  demote_to_archival: "超过 90 天未被引用"
```

```bash
# 3) 是否有归档目录/标记
grep -rn "archival" ~/.openclaw/workspace/agents/my-agent/contracts/MEMORY.md
```

### 错误 4 · 用"每周体检"当唯一防线（无实时告警）

**错误现象**：作者只配了每周一次的体检，两次体检之间发生的漂移要等到周末才发现；若漂移发生在周三，周四、周五的会话都基于错误的 agent 状态。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：只有周检，无实时阈值告警
health_check: "weekly"     # 周检
alerting: none             # ❌ 无告警
```

**为什么错**：

1. **周检是"兜底"，不是"唯一防线"。** 本章 4.3 节的三件套是"基线 + 定期 diff + 告警阈值"的组合；缺了阈值告警，检测变成"事后发现"。
2. **漂移是累积的，越早发现越便宜。** 周检粒度下，最坏情形要等 7 天。
3. **代价**：告警延迟 = 污染时长；一周的污染会话可能已经产生了对外产物。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：周检 + 阈值告警双防线
health_check:
  weekly: true                    # 全面体检（兜底）
  threshold_alert:                # 实时/高频告警（第一防线）
    drift_pct: 1.0                # 漂移 >1% 立即告警
    mem_growth_pct: 20            # 记忆周增长 >20% 告警
```

```bash
# 把阈值告警挂进心跳（高频检查）
# HEARTBEAT.md on_wake 增加：
#   - "diff SOUL vs baseline，若 >1% → 立即告警"
```

**验证命令**：

```bash

# 2) 心跳里是否含漂移检查
```

### 错误 5 · 文档漂移与人格漂移混在一起治

**错误现象**：作者把"文档更新了但协议没更新"（文档漂移）和"agent 语气变了"（人格漂移）当成同一个问题，用同一套指标衡量，结果两个都治不好。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：一个指标治两种漂移
drift:
  metric: "text_diff"     # ❌ 不分对象
```

**为什么错**：

1. **两者对象不同、检测方法不同。** 术语表 #28 明确区分：Document Drift（文档与事实不符）vs Personality Drift（agent 行为偏离人格）。前者对比"文档 vs 事实"，后者对比"行为 vs 基线人格"。
2. **F7-1 与 F7-2 是两个独立故障类型**，各有各的排查路径。
3. **混治会导致指标失真**：文档改了一个字也会触发"人格漂移告警"，很快就把告警淹没成噪声。
4. **代价**：告警疲劳 → 真漂移被忽略。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：两类漂移分开定义
drift_governance:
  document_drift:                  # 文档 vs 事实
    sources: ["AGENTS.md", "README.md", "SOP"]
    check: "grep 事实源 vs 文档声明"
    alert_if: "不一致项 > 0"
```

### 错误 6 · 记忆"写进去"就不管"读得出"

**错误现象**：作者确认了记忆"写入成功"，但 agent 在需要时检索不到；于是反复写同一内容，记忆越堆越多，命中率却没提高。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：只管写，不管检索质量
memory:
  write: always
  retrieval: default      # ❌ 没有检索质量指标
```

**为什么错**：

1. **"写进"与"读出"是两条链路。** F4-4 明确："记忆写进去了但读不出来——写进和读出怎么分清"。
2. **检索命中率是独立指标。** F4-7："记忆检索命中率低，memory search 找不到明明有的内容"。
3. **检索差 → 重复写入 → 膨胀 → 检索更差**，形成恶性循环。
4. **代价**：记忆量越大，效果越差（负相关），这是最反直觉的失败模式。

**正确配置**（✅ 应该这样）：

```markdown
<!-- 记忆写入规范（写进 MEMORY.md 的策略面） -->
1. 结构：每条记忆含 { 主题, 结论, 证据, 时间, 关键词 }
2. 去重：写入前先检索，命中则更新而非新增
3. 可检索：关键词 ≥ 3 个（含中英文/同义词）
```

```yaml
# MEMORY.md
retrieval_policy:
  require: ["同义扩展", "分层检索（short→long→archival）"]
  metric: "命中率（抽样 20 条查询）"
```

**验证命令**：

```bash
# 1) 实测检索（真名：memory search）
openclaw memory search "压缩预算" 2>&1 | head -20
# 期望：能命中相关记录

# 2) 抽样命中率
# 抽 20 条已写入记忆，逐条 search，统计命中数

# 3) 去重检查
grep -c "" ~/.openclaw/workspace/agents/my-agent/contracts/MEMORY.md
```

**相关 FAQ**：F4-4（写进去读不出）、F4-7（检索命中率低）、F4-12（记忆一致性检测）、F4-8（memory 与 skills 关系）。

### 错误 7 · 主动性只升不降（无降档机制）

**错误现象**：为了让 agent "更省心"，作者逐步把主动性从 L1 提升到 L3；某次事故后想降回 L1，却发现没记录档位、也没降档流程，只能靠记忆手动改。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：只写当前档，无历史与降档规则
proactivity_level: 3      # 无升降记录、无触发条件
```

**为什么错**：

1. **边界是"治理对象"，需要双向操作。** 本章 4.3 + F7-11：主动性分档要**可升可降**，并在治理层留痕。
2. **事故后降档是标准处置。** 若没有降档机制，事故后会陷入"要么全关、要么硬撑"的两难。
3. **代价**：档位失控 → 要么过度保守（主动性形同虚设），要么反复越界。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：档位 + 升降条件 + 留痕
proactivity:
  current: 2
  promote_when: "连续 2 周 L2 无越界 + 体检全绿"
  demote_when: "任一越界事件 → 立即降 1 档"
  ledger: "~/notes/domain/silicon-life-handbook/governance/proactivity.log"
```

**验证命令**：

```bash
# 1) 档位与条件是否都在
grep -nE "current|promote_when|demote_when" ~/.openclaw/workspace/agents/my-agent/contracts/HEARTBEAT.md

# 2) 升降留痕是否存在
ls -l ~/notes/domain/silicon-life-handbook/governance/proactivity.log 2>/dev/null

# 3) 越界事件是否有记录
grep -n "越界" ~/notes/domain/silicon-life-handbook/governance/*.log 2>/dev/null | head
```

**相关 FAQ**：F7-11（主动性五档治理）、F3-6（越界）、F7-4（信任评分降级恢复）。

### 错误 8 · 把"每周体检"做成走过场

**错误现象**：体检清单很长，作者每次只是"看一眼没大问题"就签字通过；体检报告没有数字、没有对比、没有结论，形同形式。

**错误配置**（❌ 不要这样）：

```markdown
# 错误示范：无数据的体检
本周体检：✅ 通过（看起来正常）
```

**为什么错**：

1. **体检的价值在"对比与判定"。** 本章 4.3 节要求体检项含**阈值与对比**（漂移 %、记忆增长 %、心跳成功率）。
2. **F7-3 就是这个坑**："每周体检不通过（Weekly Health Checklist）怎么办"——前提是体检能**判定通过/不通过**，而不是"看一眼"。
3. **无数据体检 = 无告警能力**，与不做体检等价。
4. **代价**：能力矩阵连续 26 天未续期（F3-11 / F7-6 / F7-15）这类事故，正是因为"走形式的体检"没能发现问题。

**正确配置**（✅ 应该这样）：

```markdown
# 正确示范：带数字的体检模板
| 项 | 阈值 | 本周值 | 判定 |
|---|---|---|---|
| SOUL 漂移 | ≤1% | 0.4% | ✅ |
| MEMORY 增长 | ≤20% | 8% | ✅ |
| 心跳成功率 | ≥99% | 97.2% | ❌ → 开修复工单 |
| skills 合规 | ≥95% | 86% | ❌ → 修 frontmatter |
| 能力矩阵续期 | ≤7 天 | 26 天 | ❌ → 立即续期 |
```

```bash
git diff --numstat drift-baseline-20260927 -- SOUL.md
find ~/.openclaw/workspace/skills -maxdepth 2 -name SKILL.md | wc -l
```

### 坑 1 · 先跑几个月，再想"要不要留档"

**坑的场景**：新人急着让 agent 干活，跳过留档与基线；三个月后想复盘"它到底有没有变"，发现没有任何历史。

**后果**：

- **无漂移检测**：没有基线，就无法检测漂移（本章 4.2）。
- **无复盘依据**：过去三个月发生了什么，无法重建。
- **补不回来**：历史无法追溯。

**为什么踩**：

1. **"留档"看起来不产出价值**（当下不解决问题）。
2. **以为"以后补也来得及"**——实际永远补不回来。
3. **不知道 SOUL 是漂移锚点**。

**怎么爬出来**：

```bash
# 第 1 步：从今天起立基线（承认历史不可追）
cd ~/.openclaw/workspace/agents/my-agent/contracts/
git init && git add -A && git commit -m "baseline (as of $(date +%F))"
git tag drift-baseline-$(date +%Y%m%d)

# 第 2 步：把"每周 diff"写进心跳
# HEARTBEAT.md on_wake 加："每周一 diff SOUL/MEMORY vs baseline，输出漂移报告"
```

**预防**：

- **第一天就建 Git 基线**（成本 30 秒）。
- **基线是资产，不是流程负担**。
- **真实案例参照**：F2-12、F7-1、F7-3。

---

### 坑 2 · 把"主动"当成"越主动越好"

**坑的场景**：新人听说"主动性是差异化优势"，于是不断加码：更短的心跳、更多的 on_wake、更大的权限范围。

**后果**：

- **越界**（F3-6）：agent 干了不该干的事。
- **成本失控**：心跳太频 → token 消耗暴增（F3-5）。
- **不可控**：频繁自主行为让系统行为难以预测。

**为什么踩**：

1. **"更多 = 更强"的直觉**。
2. **不知道主动性有档位（L1–L5）与边界治理**（本章 4.3 / F7-11）。
3. **没经历过越界事故**，缺少畏惧。

**怎么爬出来**：

```bash
# 第 1 步：立刻降档到 L1（只读）
# HEARTBEAT.md
#   on_wake 只留 read-only 任务
#   conditional_execute.enabled = false

# 第 2 步：把心跳间隔调回合理值（≥ 1800s）
grep -n "^interval" ~/.openclaw/workspace/agents/my-agent/contracts/HEARTBEAT.md

# 第 3 步：记录一次"越界复盘"
echo "越界事件：__ / 根因：__ / 处置：降档至 L1" >> ~/notes/domain/silicon-life-handbook/governance/incidents.log
```

**预防**：

- **默认最低档，逐级授权（附条件）**。
- **每级要有"通过条件"与"降级触发条件"**。
- **真实案例参照**：F3-6、F3-5、F7-11。

### 坑 3 · 用"agent 好像变了"当漂移信号

**坑的场景**：作者某天觉得"agent 语气不太一样"，于是开始改配置；但没有任何基线或数字支撑，纯凭感觉。

**后果**：

- **误判**：可能只是模型波动或上下文差异，不是真漂移。
- **过度响应**：为了"修人格"而大改配置，反而引入新问题。
- **无记录**：这次"感觉"无法沉淀。

**为什么踩**：

1. **"感觉"是最易得的信号**，但它不是证据。
2. **缺少定量漂移指标**（本章 4.2 的 diff + 阈值）。
3. **不知道行为抽样方法**。

**怎么爬出来**：

```bash
# 第 1 步：用 diff 给"感觉"配数字
cd ~/.openclaw/workspace/agents/my-agent/contracts/
git diff --numstat drift-baseline-20260927 -- SOUL.md MEMORY.md
# 若无差异 → 说明不是配置漂移，可能是上下文/模型因素

# 第 2 步：行为抽样（同一问题问 3 次，看一致性）
for i in 1 2 3; do
  openclaw agent --message "用一句话说明你的语气风格" --agent my-agent 2>&1 | head -3; echo "---"
done
```

**预防**：

- **"先取证，再动手"**（对应第 5 章 TEV 三证据验证的精神）。
- **每周体检产出数字，而非印象**。
- **真实案例参照**：F7-2、F2-12、F7-5。

### 坑 4 · 记忆不分层，越记越乱

**坑的场景**：新人把所有内容（对话流水、结论、临时信息）都写进同一份记忆，几个月后自己都找不到东西。

**后果**：

- **加载变慢**、**上下文被吃光**（F4-3 / F2-11）。
- **检索命中率下降**（F4-7）。
- **"记了很多，却什么也找不到"**。

**为什么踩**：

1. **"多记总没坏处"的直觉**——实际有坏处。
2. **不知道分层策略**（short/long/archival）。
3. **没有写入规范**（去重、关键词、结构）。

**怎么爬出来**：

```bash
# 第 1 步：一次性降噪（把流水类移出 long_term）
# 人工/脚本把"临时信息"标为 archival
grep -n "archival" ~/.openclaw/workspace/agents/my-agent/contracts/MEMORY.md

# 第 2 步：立写入规范（写进 MEMORY.md 策略面）
cat >> ~/.openclaw/workspace/agents/my-agent/contracts/MEMORY.md <<'EOF'
写入规范：结构化 {主题,结论,证据,时间,关键词}；写入前先检索去重。
EOF
```

**预防**：

- **只把"结论 + 决策 + 可复用步骤"升入 long_term**。
- **每月做一次记忆体检**（体量 + 命中率抽样）。
- **真实案例参照**：F4-3、F4-4、F4-9、F4-12。

### 坑 5 · 体检从不记录，无法对比

**坑的场景**：作者每周做体检，但只在脑子里过一遍，从不落盘；三周后想问"心跳成功率是变好了还是变差了"，没有任何数据。

**后果**：

- **无法判趋势**：单点数据看不出漂移趋势。
- **重复劳动**：每次体检都从零开始。
- **责任不清**：没有记录，无法追溯"谁在什么时候判定通过"。

**为什么踩**：

1. **记录"看起来不产出"**。
2. **没有固定模板**，每次体检项都不一样。
3. **缺少落盘习惯**。

**怎么爬出来**：

```bash
# 第 1 步：固化体检模板
mkdir -p ~/notes/domain/silicon-life-handbook/healthcheck
cat > ~/notes/domain/silicon-life-handbook/healthcheck/TEMPLATE.md <<'EOF'
| 项 | 阈值 | 本周值 | 判定 |
|---|---|---|---|
| SOUL 漂移 | ≤1% | | |
| MEMORY 增长 | ≤20% | | |
| 心跳成功率 | ≥99% | | |
| skills 合规 | ≥95% | | |
EOF
cp ~/notes/domain/silicon-life-handbook/healthcheck/TEMPLATE.md \
   ~/notes/domain/silicon-life-handbook/healthcheck/week-$(date +%Y%m%d).md
```

**预防**：

- **体检必落盘**，文件名含日期，便于趋势对比。
- **把体检放进心跳自动生成草稿**（第 2 章 Heartbeat）。
- **真实案例参照**：F7-3、F7-6、F3-9。

### 坑 6 · 以为"漂移"只会变坏

**坑的场景**：新人以为漂移一定是"退化"，于是只盯着"变差"的方向；实际上漂移也可能是"无意中变好"，同样需要记录与确认（否则无法复现）。

**后果**：

- **错过可复用的改进**：某次无意的配置改动让效果变好，但没记录，无法沉淀。
- **误回滚**：体检发现"与基线不一致"就一律回滚，把好的漂移也滚掉了。
- **基线失真**：长期不回写良好实践，基线越来越脱离现实。

**为什么踩**：

1. **"漂移"这个词的中文语义偏负面**（本意是"变动"，不是"变坏"）。
2. **体检只判"是否偏离"，不判"偏离是好是坏"**。
3. **缺少"基线更新"流程**（好的漂移应升级为新基线）。

**怎么爬出来**：

```bash
# 第 1 步：体检时对每处漂移判方向
git diff drift-baseline-20260927 -- SOUL.md | head -40
# 逐条标注：↑更好 / ↓更差 / ↔中性

# 第 2 步：好的漂移 → 评审通过 → 更新基线
git tag drift-baseline-$(date +%Y%m%d)     # 新基线
git push --tags   # 若有远端

# 第 3 步：差的漂移 → 开修复工单（第 5 章）
```

**预防**：

- **漂移报告分"好/坏/中性"三类**，不一刀切。
- **基线定期升级**，把通过评审的改进纳入新基线。
- **真实案例参照**：F7-1、F7-4（信任评分结算与恢复）、F7-7（修复工单）。
