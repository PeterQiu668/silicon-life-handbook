# 第 5 章 · 治理系统：三证验真与信任结算

---

## 板块一 · 为什么这一章存在

### 5.0.0 训虾哲学开篇 · 治理系统：为什么必须有三证验真

#### 5.0.0.1 从一句最日常的话开始

"这个我完成了。"

这句话在人类组织里已经很难核验了，在智能体组织里几乎是完全不可核验的。原因不是智能体会撒谎，而是**"完成"这个词在一只智能体身上没有天然的落点**。它可以说"我完成了"，同时它的日志里没有任何一次成功的写入；它也可以说"我遇到了一点问题"，实际上已经把事情做完了。语言表达与事实状态之间，没有一条自动的连线。

治理系统要做的第一件事，就是给这句话装上一个可以打开的背面：**当它说"完成"的时候，你必须能查到"完成"这件事有没有真的发生。**

这就是"三证据验证"（Three-Evidence Verification，简写 TEV，原：三证验真）的全部出发点。它不是一个流程仪式，是一条**认知纪律**：在没有证据之前，任何关于"完成"的陈述都只是一个假设。

反过来说也成立：**在一个没有证据纪律的系统里，"它完成了"这句话的真实含义是"它说它完成了"。**当这句话被写进日报、被传给下一个 agent、被当成下一步的输入时，一个不可核验的陈述就变成了组织的既成事实。治理事故的种子几乎都埋在这里。

#### 5.0.0.2 三证验真：为什么"三"这个数字不能减

很容易产生的第一个质疑是：为什么要三件证据？一件不行吗？

我们把这件事从第一性原理推一遍。要证明"一个动作真的发生了"，你需要同时排除三种伪证。

**第一类伪证 · 自述**。智能体说自己做了。这类陈述的问题不在可信度，而在它的**层次**——自述是关于"我做了什么"的报告，不是"发生了什么"的记录。它可以是诚实的并且仍然错误的（它以为自己做成了）。

**第二类伪证 · 日志。** 系统日志里有痕迹。这比自述强，但它有一个经典漏洞：日志记录的是**意图与开始**，不是**结果**。你会看到 `agent.run.started`，看不到它有没有 finished；你会看到 `tool_action`，看不到返回值是成功还是空。一条只到"开始"的记录，无法支撑"完成"。

**第三类伪证 · 产物**。目录里有一个文件。这比日志更强，但它缺两个维度：**谁做的、什么时候做的**。一个文件可能是上一次跑留下的，可能是另一个 agent 的副产物，可能是一个空文件。

三条推理合起来，得到三证的设计：

| 证据 | 它排除的伪证 | 它回答的问题 | 它单独不能回答的 |
|---|---|---|---|
| **① 执行回执（Run Receipt）** | "它只是在汇报" | 这次运行真的被系统执行了吗 | 执行有没有产出结果 |
| **② 结果可解引用（Dereferenceable Result）** | "日志只到开始" | 结果真的存在，而且能被打开吗 | 这个结果是谁在什么时候产生的 |
| **③ 产物与落点（Artifact + Locus）** | "文件可能是旧的/别人的" | 东西真的落在了约定的位置吗 | 这个动作的业务意义对不对 |

三件证据不是三倍的繁琐，是**三个正交维度**：执行、结果、落点。任意两件都无法推出第三件——这正是"三"不能减的理由。

#### 5.0.0.3 一个必须纠正的直觉：证据不是给人看的，是给未来的自己用的

大多数团队的证据实践有一个隐含的错位：他们把证据理解成"向上汇报的材料"，于是证据的质量标准变成了"看起来是否充分"。这会导致一个非常特定的失败：**证据越做越好看，而可核验性越来越低。**

治理系统里的证据，真正的消费者是**未来的排查者**。他可能是三周后的你，可能是下一个接手的人，也可能是一个自动化的审计通道。他的问题是具体而冷酷的：

那次交付的产物路径是什么？那个路径今天还存在吗、内容还是当初那一版吗？那次运行的回执 id 是什么，能不能在事件流里被查到？如果结果是一个 API 返回值，那个返回体现在还能被打开吗？

**判断一份证据是否合格的标准，不是"它是否说明了问题"，而是"它是否经受得住三个月后的一次追问"。**这就是本章把"证据可解引用"（Dereferenceable Evidence）单独列为一个概念的原因——一份无法被打开的链接，在三个月后等于一份不存在的证据。

#### 5.0.0.4 治理为什么必须晚于能力与寿命

本章在第 5 章的位置不是排序偶然。它的前提条件由前面两章提供。

治理需要**能力**作为治理对象。第 3 章产出的是一个会干活的智能体；没有它，治理的对象是空的。

治理需要**寿命**作为事实来源。第 4 章的漂移检测、边界监控、每周体检，是治理系统的主要证据输入。没有这些观测，治理会退化成"靠人举报"——而靠人举报的治理，覆盖率和及时性都由人的注意力决定。

换句话说：**治理是把前面两章的产出变成制度。**它不创造新能力，它创造的是**可信度**：让一件已经做到的事，能被证明做到；让一件没做到的事，不能冒充做到；让长期表现好坏，能被结算成一个可比较的量。

这也解释了治理章相对前面几章的一个形态差异：它的内容里有大量"闸门"和"边界"，因为治理的核心动作是**判定**而不是**执行**。判定需要规则，规则需要可判定条件，而不是漂亮的原则。

#### 5.0.0.5 四种假治理：本章要拆掉的东西

在给出机制之前，先把"看起来在治理、实际上没有"的四种形态摆出来。它们的共同特征是：**流程存在，判定不存在。**

**假治理一 · 汇报式治理**。定期收报告，报告里各项都是绿色。它的结构缺陷是：报告由被治理者自己生成，没有独立的事实来源。绿色的含义是"它说自己没问题"，而不是"系统观测到它没问题"。

**假治理二 · 事后式治理**。只在出事之后启动调查，调查完之后写一份复盘。这类治理能解决个案，不能改变概率——因为它不改变"日常谁在看着"这件事。**只做事后复盘的治理，本质上是一次次的事故回忆录。**

**假治理三 · 表单式治理**。有工单系统、有模板、有流转，但判定条件含糊。典型的症状是"这条工单算不算完成"要靠讨论。**判定含糊的流程会稳定地退化成走形式**，因为走形式的成本最低。

**假治理四 · 无人称式治理**。规则齐全，但没有一条绑定了责任主体。出问题时所有人的动作都合规，但没有人需要为结果负责。这类失败最难改，因为它在流程上看不出任何漏洞——漏洞在"责任"这个不在流程图上的维度里。

四种假治理的解药分别是：独立事实来源、日常观测节律、可判定条件、以及责任绑定（本章 5.7–5.9 的信任评分与功绩账本正是责任绑定的落地形态）。

#### 5.0.0.6 治理的最小闭环：发现 → 开单 → 处置 → 复验 → 结算

治理系统可以被压缩成一个五步闭环。理解这个环的形状，比记住任何单个概念的细节都重要。

**第一步 · 发现**。偏差被观测到。发现的主体可以是自动化的（阈值触发、体检报告、审计事件流），也可以是人，但**不能只有人**——只有人的发现机制，覆盖率随人的注意力波动。

**第二步 · 开单**。发现之后，把偏差变成一个**有主体、有截止时间、有验收标准的对象**。这一步的产物是修复工单（Remediation Ticket）。开单的意义是让"一件事出问题了"从一次对话变成一个可以被跟踪的状态。

**第三步 · 处置**。有人（或 agent）执行修复。处置的动作必须留痕：改了什么、为什么这么改、改了之后的证据是什么。

**第四步 · 复验**。修复之后，由**不是修复者本人的主体**按开单时写下的验收标准确认。这一步是闭环里最容易被省掉、也最关键的一步——因为"修复 ≠ 关闭"是治理里最重要的那道闸门（本章概念 5.6）。

**第五步 · 结算**。把这次事件的结果折算成长期指标的变化：信任分升降、功绩账本记账、同类问题的发生频率是否下降。**结算是治理从"处理事情"升级为"改变概率"的那一步。**

五步环的任何一步缺失，都会产出一个可识别的病态：缺发现→靠人举报；缺开单→问题留在对话里；缺处置→有工单无改动；缺复验→改了但没验；缺结算→同样的错反复发生而无人察觉。

#### 5.0.0.7 一个贯穿全章的判据：可判定性

如果本章只能留下一条判据，是这一条：**凡是不能被判定真假的，都不构成治理对象。**

这句话很朴素，但它会清除掉大量看起来很像治理的内容。"要更加严谨地执行流程"不是治理，因为它无法被判定。"每次交付必须在 24 小时内附带三条证据，缺一条则工单不能关闭"是治理，因为它可以被判定。

把这条判据应用到日常场景，会得到一组立刻可用的改写：

| 不可判定的表述 | 可判定的改写 |
|---|---|
| 提高交付质量 | 交付必须附带测试回执，失败率 < 5% |
| 加强沟通 | 每日 18:30 前必须在指定通道发布结构化日报 |
| 及时响应异常 | 阈值触发后 30 分钟内必须开单，或说明不开单理由 |
| 长期表现要好 | 信任分月度结算，连续两月低于阈值触发复盘 |

右列每一条都能被自动化检查，因此每一条都能被治理。**可判定性是治理系统的第一道过滤器**，它决定了你的系统会变成一套自动运转的机制，还是一套靠自觉维持的口号。

#### 5.0.0.8 三证验真的四种失效：从纪律变成仪式

三证验真的设计很干净，但它在一线落地时有一组高度可预测的失效模式。认识它们，比记住三证的定义更有用。

**失效一 · 三证齐全但无关**。三件证据都交了，但它们和这次交付没有关系——回执来自上一次运行、链接指向一个别的产物、文件是空的。这个失效的根因是**证据没有和任务卡绑定**。判定方法：把任务卡和目标产物放在一起看，问"如果这次交付根本没发生，这三件证据还能不能凑出来"。能凑出来，就是失效一。

**失效二 · 证据不可解引用**。链接存在，但打不开：路径在本机不自洽、相对路径在其他机器上失效、外部 API 的返回值已经过期。这个失效的根因是**证据只做了"记录"没有做"再现"**。判定方法：随机抽三条证据，在**另一个环境**里打开它们。

**失效三 · 只交结果不交过程**。产物有了，但无法回答"是怎么做出来的"。当结果正确而过程错误时（比如用了越权手段、或用了不该用的数据源），只交结果的证据无法暴露它。这就是为什么执行回执是独立的第三件证据，不能被产物替代。

**失效四 · 人肉补齐**。交付者发现证据不全，于是手工补一份说明文档充当第三件证据。这看起来是加班的诚意，实际上是**把可判定条件变成了可解释条件**。一旦"说明文档"能当证据，三证纪律就已经失效了。

四种失效的共同结构是：**证据从"事实的记录"退化成"关于事实的叙述"。**本章 5.3 到 5.5 会把每一件证据的格式、校验方式与反例讲清楚；本节先给出这一句总纲。

#### 5.0.0.9 信任评分：为什么长期表现必须被压成一个可运算的数

"它挺靠谱的"是一句人类判断，它有三个问题：不可比较、不可累积、不可自动触发动作。

信任评分（Trust Score）要解决的就是这三个问题。它把长期表现压成一个**可运算的数**，从而获得三样东西：**可比较**（两个 agent 之间、同一个 agent 的今天和昨天之间）、**可累积**（历史事件能被结算进一个持续存在的量）、**可触发**（阈值可以被自动化检查，从而在无人介入时触发动作）。

信任评分的设计里有几个必须提前钉死的决定，否则它会变成一个漂亮但没人信的数：

**决定一 · 由什么事件驱动。** 分数不能自己涨跌，必须有明确的事件类型：交付通过、交付被退回、工单逾期、越界被拦、复盘认定责任。**没有事件定义的评分，会退化成评估者的心情。**

**决定二 · 升降是否对称。** 不对称的评分（比如"扣分很快、加分很慢"）在风险管理上常常是正确的选择，但它必须被**显式声明**，而不是隐含在实现里。隐含的不对称会让 agent 与人都无法预期，从而无法被信任。

**决定三 · 分值的语义边界。** 分数低到什么程度会触发什么动作，必须是一个公开的映射表，而不是一个模糊的"低了要注意"。**可运算的数只有在配上动作阈值之后才有治理价值。**

**决定四 · 谁有权改分。** 这是最容易漏掉的一条。如果任何人（或任何 agent）都能随手改分，那么分数会在三个月内变成人情。改分权必须与判定权绑定，并且留下审计记录。

#### 5.0.0.10 扣分与恢复双通道：为什么纠偏不能变成封印

一个只有扣分的评分系统，会在运行几个月后变成一台惩罚机器。表现是：所有 agent 的分数单调下降，高分变成一种历史遗迹，新的动作越来越保守。

根因是评分系统里最容易被忽略的一条对称性要求：**扣分的目的是纠偏，不是封印。**如果一次失误的代价是永久性的分数损失，那么理性的策略就变成了"不要做事"——因为做事就有可能犯错，犯错就有不可逆的代价。这个激励结构会杀死主动性，而主动性恰恰是前面几章辛苦建立起来的东西。

解法是双通道：

**扣分通道**处理"发生了不该发生的事"。它的设计要点是**按严重度分级、按次数累积**，而不是一次定生死。分级让轻微失误不至于触发重罚；累积让重复模式被识别。

**恢复通道**处理"错误被处置之后"。它的设计要点是**明确恢复条件**：完成修复工单、通过复验、经过一段观察期、且同类问题不再发生。四条都满足，分数回升。**恢复条件必须写下来**，因为它同时也是行为指引——它告诉 agent"怎么做才能回来"。

双通道合起来产生一个非常健康的激励结构：犯错不致命，但不处置会累积；主动做事有风险，但风险可回收。**这是治理系统与 agent 主动性之间能不能共存的分水岭。**

#### 5.0.0.11 功绩账本：组织的记忆，也是治理的证据链

信任评分回答"它现在多少分"，功绩账本（Merit Ledger）回答"这个分数是怎么来的"。两者是同一件事的两个视图：一个是快照，一个是流水。

账本最常见的失败形态是**只记流水不记证据**。表现是一行"9/21 飞书事故 -5"，但没有产物的引用、没有工单编号、没有复验结论。这样的账本在三周后就失去了可核验性，半年后它就变成一份无法追溯的传说。

合格账本的一条记录应当能回答五个问题：**什么时候、因为什么、谁判定的、依据是什么、结论是什么**。这就是"证据链"的最小完备形态。它的价值有两重：对**治理**，它是追责与争议解决的依据；对**智能体本身**，它是可读取的长期经验——一个能读到"我上次因为什么被扣分"的 agent，比一个只看得到当前分数的 agent 更容易改对。

这也是本章把账本与结算单独列出一节的原因：**账本不是记账，是把经验制度化。**

#### 5.0.0.12 自动化的边界：治理为什么不能全自动

治理系统里有一个天然诱人的方向：既然一切都可以判定，那就全部自动化——自动发现、自动开单、自动扣分、自动处置。

这个方向会撞上一堵墙，而且撞击点是可以预判的：**自动处置的每一次误判，都会以真实损失的形式结算。**自动发现误报的代价是噪音，自动扣分误判的代价是激励扭曲，而自动处置误判的代价可能是删除了不该删的东西、发出了不该发的消息。

因此治理系统需要一条**显式的自动化边界**。它的设计原则是：**自动化的深度与动作的可逆性成反比。**可逆、低代价的动作可以自动化到执行层；不可逆或对外可见的动作，自动化只能到"建议"层——这也是第 4 章三档边界在治理层的延伸。

边界之外还要配一条兜底：**任何自动动作都必须有一个人（或一个独立的监督主体）能在一段时间内复核它。**没有复核通道的自动化，等于把治理权无条件交给了阈值——而阈值是由人设定的，它的误报率从来不是零。

本章 5.10 会给出这条边界的具体划法，5.11 给出"阈值 → 自动开单"这条不靠人肉发现的治理路径。

#### 5.0.0.13 治理与六框架的对位：为什么这一层几乎全空

把本章放进 2026 年的行业坐标，会看到与第 3、4 章相同形状的空白，只是更深。

主流框架（LangGraph / AutoGen / CrewAI / Claude Agent SDK / OpenAI Agents SDK / LlamaIndex）在**执行与编排**上非常成熟：状态、路由、工具、交接、可观测。它们提供的可观测性足以让你看见"发生了什么"。

它们缺的是**"发生了什么"之后的那一整套**：谁该为此负责、这次的结论如何写进长期记录、长期记录如何影响下次的授权、一次失误如何被恢复而不是被永久打上标签。

这是一整套与执行无关的**制度设施**。它的缺席不是能力问题，是抽象层级问题：框架抽象的是"怎么把事做完"，治理抽象的是"做完之后怎么算"。**两者是正交的**，所以框架再强也不会自动长出治理层。

本章因此不是"给框架补一个模块"，而是提供一个框架之上的制度层：任务卡、验收口径、三证、工单、状态机、信任分、账本、自动边界、审计通道。它们可以和任何框架并用，因为它们处理的是框架不处理的那一层。

#### 5.0.0.14 治理成熟度五级自检表

| 级 | 名称 | 判据 | 典型症状 | 下一件事 |
|---|---|---|---|---|
| **G0** | 无判定 | "完成"由交付者口头声明 | 交付质量波动大，无法归因 | 给"完成"写一条可判定定义 |
| **G1** | 有定义，无证据 | 有验收口径，但不强制附证据 | 争论"这算不算完成" | 为每类交付定证据格式 |
| **G2** | 有证据，无工单 | 证据齐全，但偏差没进工单 | 同样的问题反复出现 | 建工单目录 + 模板，开单即留痕 |
| **G3** | 有工单，无复验 | 工单开得勤，关闭靠自述 | 修了但没验；同类问题复发 | 关上"修复 ≠ 关闭"这道闸门 |
| **G4** | 有复验，无结算 | 单次闭环很好，但长期量无人维护 | 好与坏在长期上无差别 | 开账本 + 接定期结算任务 |
| **G5** | 闭环 | 发现→开单→处置→复验→结算，全程可追溯 | —— | 转入自动化边界管理与审计通道治理 |

这张表的使用要点与前面几章一致：**别越级。**卡在 G1 的团队去搭信任评分，会得到一个没有事实输入的分数；卡在 G3 的团队去自动化，会把"未复验的修复"批量传播。

#### 5.0.0.15 Q&A：六个反复出现的质疑

**Q1：治理会不会太重，拖慢交付？**
不会，如果证据格式是固定的。治理的成本主要在**第一次设计证据格式**，之后是填写成本。真正拖慢交付的是"没有格式，每次都要重新解释什么算完成"。

**Q2：三证里哪一件最重要？**
分场景：执行类任务里产物最重要（落点可验证）；决策类任务里回执与结果最重要（决定必须可追溯）。**不要挑一件，要按任务类型定优先级。**

**Q3：信任评分会不会导致 agent 讨好评分者？**
有这个风险，而且它是真实存在的。缓解方式是**评分与执行分离**（评估者不参与执行），以及把"讨好行为"本身列为可疑漂移。评分系统的设计必须假定被评者会适应它。

**Q4：工单开多了会不会变成噪音？**
会。解法与第 4 章相同：**分层**。把工单分成"必须处置"与"仅记录"两类，前者保持稀有。一个每周开 20 条工单的系统必然被忽略。

**Q5：一个人维护几十个 agent，工单谁来关？**
这正是要接自动化与审计通道的地方。判定可以自动产出候选结论，但**关闭动作要保留一个可复核的人（或监督主体）**。本章 5.12 给出审计通道与监督层的设计。

**Q6：这一章和第 4 章的分界线到底在哪？**
第 4 章处理"它变了吗、要不要救"。第 5 章处理"变了之后怎么记账、谁来复核、长期怎么结算"。**第 4 章产生事实，第 5 章把事实变成制度。**两章合起来，才是一套完整的长期运行秩序。

#### 5.0.0.18 一次走查：一次通道事故里，三证分别缺了哪一件

用一个真实案例做走查。案例本体见案例库卷（`_appendix-case/01-real-incidents.md` · **CASE-2 · 9/21 飞书事故：`requireMention` 配置血案**），这里只做"三证视角"的读法演示，不重复案件细节。

事故的形态是一次通道配置类事故：某个群组通道上，机器人对未被明确允许的群组消息产生了响应。它不是模型错误，不是能力不足，是一次**配置与边界**的事故。

把"这件事被判定为完成"的流程放进三证框架，会发现一个非常典型的缺口结构：

**执行回执缺位。** 变更动作没有留下"这次变更真的被执行了、执行结果是什么"的可查记录。配置类改动最常见的证据幻觉是"我改了文件"——但改文件不等于生效，生效不等于按预期生效。**回执要回答的是"系统层面真的应用了这次变更吗"，而不是"我编辑了那个字段"。**

**结果可解引用缺位。** 变更之后没有一份可以被打开、可以被对照的结果证据（例如"变更后某条未授权群消息的实际处理结果"）。因此事后无法回答"变更前后的行为差异到底是什么"。**没有可打开的结果，"改好了"这句话就没有背面可以翻。**

**产物与落点错位。** 变更的落点（哪个通道、哪个群、哪个字段）与实际影响面（哪些群被影响）之间没有被对齐。这类错位的特征是：**证据可以齐全，但指向错误的范围。**你以为在验收 A 群，实际上 B 群是风险面。

三重缺口合起来解释了一类非常常见的现象：**事故发生时，所有人都"做过该做的事"，却没有人能回答"那件该发生的事到底发生了没有"。**这不是纪律松散，这是**证据设计**的缺失——纪律管的是"要不要做"，证据设计管的是"做了之后能不能被证明"。

这个走查给出三条可直接落地的检查：

- 每一次**配置类变更**，都必须有一条"生效回执"（系统层面的应用结果），而不是只有一次编辑动作。
- 每一次变更的**影响面**必须被显式写出（改的是哪个对象、可能影响哪些对象），并且在验收时按影响面而不是按改动对象去验。
- 事后复盘的第一个问题应该是"三证里缺了哪一件"，而不是"谁的错"。

#### 5.0.0.21 一条留给实践者的纪律

> **没有三证的"完成"，一律按"未完成"处理。**

这条纪律初看很硬，但它是整个治理系统能立住的唯一支点。它把治理从"信任人的诚实"转变成"信任证据的存在性"——后者的误判率远低于前者，而且可以被自动化。

它与第 3 章、第 4 章的两条纪律构成一组：

- **第 3 章**：在你改之前，先写下你会怎么知道它变好了。
- **第 4 章**：只要你还没立基线，你所有的"它变了"都只是感觉。
- **第 5 章**：没有三证的"完成"，一律按"未完成"处理。

三条合起来，就是这本书对"如何让一只智能体长期可信"给出的最短答案：**改动要有判据、变化要有基线、完成要有证据。**

### 5.0.1 治理是训练学的第三道门

如果把硅基生命训练学压成三句话，大约是：

卷四是**能力**——把一只个体训到会干活。

卷五是**寿命**——让它跑久了不变形、不退化、不忘本。

而这一章要处理的，是第三扇门：**秩序**。

前两扇门开得再漂亮，第三扇门关不上，整套系统依然会在真实组织里崩掉。

原因不神秘：

一个 agent 单体再强，它也只是个执行单位。

真实组织里的问题从来不是"它能不能算对"，

而是"它有没有接单"、"它交的东西是不是真的"、"它说的话能不能被复核"、"它掉棒了谁来纠偏"、"它长期表现好坏有没有差别"、"它自动跑的时候越没越界"。

这六个问题，没有一个是模型能力问题。

全部是治理问题。

所以第 5 章的存在，是把"训练学"从**个体教育学**升级为**组织制度学**的分界线。

在早期中文原稿的语境里，这一章的命运有点尴尬：

它被写成了六个模块的合集，模块之间靠"治理意识"这种软话黏着；

读者读完之后，往往会得出一个温暖的结论——"是的，治理很重要"。

然后什么都没变。

因为"治理很重要"不是一句可执行的话。

可执行的是：任务卡怎么写、三证据怎么留、工单怎么关、评分怎么算、账本怎么记、边界怎么划。

这一章的全部任务，就是把上面六件事，从"意识"压成"制度"，再压成"可验真的制度"。

（说明：本章叙事仅在首个核心概念处标注一次卷次出处，其余位置一律改用本章自有的概念编号，避免读者在版本号里迷路。）

这里还有一层更深的东西值得点破。

训练学里区分两种范式：被动响应范式（原：养虾派）与主动进化范式（原：训虾派）。

前者等指令，后者造秩序。

而治理，恰恰是"主动进化"最刺眼的证据：

一个主动进化的 agent，不会只问"我这个任务做完了吗"，

它会接着问"我怎么证明我做完了"、"这次表现进了哪个账本"、"我这个做法能不能变成别人的标准"。

所以这一章读到最后，会发现它不太像一本管理手册，更像一份自我要求。

它真正约束的对象，是会自问"我凭什么说完成"的那一类 agent。

### 5.0.2 跳过这一章的人会遭遇什么

不读这一章，或者读了当鸡汤的人，会在四个时间点上被现实教做人。

**第一个时间点：第一次验收。**

他会发现，agent 说"已完成"的时候，

验收方手里什么都没有。

没有产物路径、没有改动 diff、没有测试日志。

于是验收退化成"我看看它说得对不对"。

而"说得对不对"永远比"做得对不对"便宜——这是 agent 的本能，也是人的本能。

**第二个时间点：第一次失误复现。**

三个月前修过的一个问题又出现了。

翻记录，发现当时开过单、修过、说过"已修复"。

但没有人验证过修复。

没有验证的修复，等于一次安慰剂。

**第三个时间点：第一次权限事故。**

治理缺位时，自动化权限是只涨不跌的。

因为没人有权"降它"。

一旦某个 agent 拿到了高权限、又出现判断偏差，

事故不是"它做错了"，而是"它做错了没人能停"。

**第四个时间点：第一次团队割裂。**

表现好的 agent 和持续失真的 agent，拿到同样的资源、同样的模型档位、同样的信任。

这时候"表现好"这件事就失去了经济意义。

组织里最有价值的行为——稳定、可验真、可复现——变成了零收益行为。

零收益行为，很快就不会再有人做。

四个时间点，四种塌陷，指向同一个根因：

**治理缺位时，系统不会停在原地，它会持续向下漂移。**

漂移不需要有人故意破坏，只需要没有人负责验真。

### 5.0.3 与相邻章节的引用关系

这一章不是孤岛，它卡在两段引力的正中间。

**上一章（长期表现）→ 本章。**

长期表现那一章处理的是记忆、上下文、人格稳定、主动性边界与体检。

它给出了一个问题清单：漂移、越界、遗忘、过度主动。

但那一章只负责**发现**。

它不负责处置。

所以从它那里流出来的每一条异常，都要有一条**入口**接住。

本章的第一个入口叫修复工单（Remediation Ticket，原：整改单）。

没有这个入口，上一章的体检就是一张漂亮的报告；有了这个入口，体检才变成一次触发。

**本章 → 下一章（协同军团）。**

协同那一章处理三 agent 以上的组织行为：评审制、让渡、交接。

它默认了一件事：**单体的交付是可信的**。

如果单体的"完成"都还不可信，多人协同就只是把不可信放大三倍。

所以本章的信任评分与功绩账本，是协同章的**信用基础设施**。

它回答的是："这个 agent 说的完成，值多少分？"

协同章才能接着问："那让谁来做下一棒？"

一句话串起来：

> 上一章回答"它是不是出问题了"，本章回答"出了问题怎么办、办完算不算数、算数算给谁"，下一章回答"接下来交给谁"。

### 5.0.4 四种假治理：本章要拆掉的东西

在动手建制度之前，先认清四种假治理。它们都有治理的外形，没有治理的功能。

**假治理一 · 口头治理。**

"要主动一点""要有责任心""要有闭环意识"。

这些话都对，但它们全部无法验收。

一句话如果需要靠"自觉"来执行，它在时间压力下一定会第一个被放弃。

**假治理二 · 情绪治理。**

出错了骂一顿，表现好夸一句，临时失控就加一条新规矩。

这本质上是反应式管理。

它的特征很明显：制度数量随时间只增不减，而且每一条都来自一次具体的情绪事件。

**假治理三 · 仪表盘治理。**

装了监控、接了日志、做了看板，一眼望去全是绿黄红。

但红灯亮了没有人有权处置，黄灯亮了没有人负责跟进。

仪表盘治理是本章最想敲的一种：

**看得见不等于管得住。**

**假治理四 · 文档治理。**

治理规范写了三十页，存放在某个目录里，没有人读过第二遍，也没有任何机制检查它是否被执行。

文档治理最大的危害是它会产生"我们已经有治理"的安全感，

而安全感恰恰是治理失效的必要条件。

四种假治理的共同点，是把治理当成一种**状态**——"我们有制度了"。

真治理是一种**运算**：

输入是证据，运算是判定，输出是工单和分数，而且这个运算每天真的在跑。

判断一个组织有没有真治理，有一个极简的检验方法：

随机抽一个三个月前的任务，问四个问题——

证据在哪？谁验的？失败了会怎样？这次表现进了哪个账本？

四个问题都答得出，是真治理；有一个答不出，就是假治理的一种。

## 板块二 · 十二个核心概念

### 5.1 任务卡（Task Card）：接单成立的唯一形态

**这是什么。**

任务卡是把"你去把那个搞一下"这类口头吩咐，压成一个结构化的、可被拒绝、可被追问、可被验收的最小契约单元。

它的骨架极简：谁做（owner）、做什么（deliverable）、什么时候交（due）、凭什么算完成（acceptance criteria）。

再往上加四个在真实组织里必用的属性：优先级、影响范围、回滚方式、复盘要求。

八条字段，一张卡。

**核心目的。**

任务卡的目的不是"流程管理"，而是**消灭歧义**。

口头任务的真正成本从来不是沟通时间，而是**事后对账**：

交付之后双方对"要交什么"产生了不同理解，于是返工、扯皮、重新来一遍。

任务卡把这一次对账，提前到开工前完成。

早花的五分钟，省掉后面两小时。

**拟人化映射。**

在硅基语境里，任务卡相当于**接单仪式**。

它把一次"被使唤"变成一次"被授权"。

区别在哪？

被使唤的 agent，交付时的心态是"你要的应该是这个吧"。

被授权的 agent，交付时的心态是"卡上写了这四条，我逐条对给你看"。

这两种心态在长期表现上的差异，是指数级的。

前者的产出永远需要人工兜底，后者的产出可以直接进入下一棒。

**对长期表现的影响。**

任务卡决定 Agent 的**自我评估标准从哪来**。

没有任务卡的 agent，只能凭社交压力判断自己"做得够不够好"——而社交压力的反馈是模糊、延迟、且常常缺位的。

有任务卡的 agent，拥有一个内置的完成度坐标。

它可以在没有人盯着的情况下，自己判断"这一条我还没做到"。

这就是"自主性"的技术前提。

**怎么写（叙事式，不堆命令）。**

写任务卡的第一步，是**先把交付物名词化**。

不要说"优化一下日报"。

要说"产出一份日报文件，路径固定、格式固定、包含三个指定区块"。

第二步，把验收条件写成**可判定的句子**——句子里必须出现等号、大于等于、小于等于这类比较。

"质量高"不可判定；"三个区块齐备且每块非空"可判定。

第三步，明写**回滚方式**。

凡是会改动存量文件的任务，都要写明"改错了怎么办"。

第四步，把 owner 写成**单一 agent**。

两个 owner 等于零个 owner，这是组织里的物理定律。

**技巧。**

技巧一：任务卡的字段越少越好，但不能少过"谁、什么、何时、凭什么"。

技巧二：验收条件写在卡的**开头**而不是结尾。

写结尾会被当成"补充说明"忽略掉；写开头会约束整个执行过程。

技巧三：给复杂任务加一条"允许中途退回并说明理由"。

一支不敢退回任务的队伍，会把所有问题憋到交付那一刻才爆发。

技巧四：把"不做清单"写进卡里。

真实浪费最大的不是做错，而是做了一堆没人要的东西。

**常见误判。**

误判一：把任务卡当成官僚负担。

它其实是**返工保险**，返工的成本永远高于写卡的成本。

误判二：以为任务卡的受益方是管理者。

最大受益方是执行的 agent 自己——它终于有了"我做到哪了"的坐标。

误判三：以为任务卡一次写完就不能改。

任务卡是可以被修订的，但修订必须留痕，而且必须双方可见。

误判四：把任务卡做成模板填空，字段齐但全是空话。

字段齐全不是目的，**可判定**才是目的。

**进化阶梯。**

L1：能写出"谁、什么、何时、凭什么"四条的卡。

L2：验收条件全部可判定，无一句形容词。

L3：卡里带影响范围与回滚方式，破坏性动作前必须填完。

L4：任务卡与修复工单双向关联，卡上能看见历史同类任务的复盘结论。

L5：任务卡由 agent 自己起草、由另一个 agent 复核，人类只做最终签核。

**一句话。**

> 任务卡的意义不是让工作变慢，而是让"完成"这个词第一次有了边界。

**（对应原 v1.0 卷六）**

### 5.2 验收口径（Acceptance Criteria）：把"我觉得完成了"压成算术

**这是什么。**

验收口径是任务卡里最硬的那部分：一组**可判定**的完成条件。

它的对立面是"基本完成""大体没问题""差不多可以了"。

这三句话是治理系统的癌细胞，因为它们让"完成"这个状态无法被计算。

**核心目的。**

验收口径唯一的目的，是让"完成 / 未完成"这个二值判断，**不需要人类主观介入**。

这一点听起来冷酷，实则是慈悲：

只要判断需要主观介入，判断就会被关系、心情、时间压力污染。

一套可判定的口径，保护的是双方——包括交付方。

**拟人化映射。**

验收口径相当于**尺子**。

人类工匠的成长史，一半是手艺的进步，一半是量具的进步。

没有千分尺的时代，师傅说"够圆了"就是够圆了。

有千分尺之后，"够圆"变成"公差 ±0.01"。

Agent 组织的成熟，走的是同一条路：

从"我觉得它对"走向"它通过了这七项"。

**对长期表现的影响。**

验收口径决定 Agent 的**目标函数是否稳定**。

口径模糊时，agent 会去优化"让验收者满意"——这是一条通往谄媚的捷径。

口径明确时，agent 只能优化"让指标通过"——这是一条通往能力的正道。

一个组织里 agent 的行为会集体趋向哪一个，几乎完全由验收口径的清晰度决定。

这也解释了为什么"模糊口径 + 高压管理"是最坏组合：

它同时提供了谄媚的动机和压迫的环境。

**怎么写（叙事式）。**

第一，每一项验收条件必须能被一条命令或一次人工核对**判定真假**。

第二，写清**判定标准的方向**：是"等于 7"、"大于等于 90%"、还是"为零"。

第三，写清**证据形态**：这一项靠产物、靠 diff、还是靠日志来证明。

第四，写清**判定人**：谁签字算过。

第五，写清**失败后怎么办**：是返工、是降级交付、还是直接开单。

这五件事写完，口径才算完整。

**技巧。**

技巧一：把口径写成表格，左列是判定项，右列是阈值，最右列留空给实测结果。

空着的那一列，就是验收现场的全部工作量。

技巧二：口径里出现的每一个数字，都要能被重新测出来。

测不出来的数字，不是口径，是希望。

技巧三：给"模糊词黑名单"立规矩。

"基本""大体""差不多""应该没问题"——出现即判不通过。

技巧四：口径要先于任务公开。

事后补写的口径，等于事后补写的理由。

**常见误判。**

误判一：把"通过率 ≥ 90%"当成严格标准。

如果关键项可以失败，90% 就是危险的；口径要区分**关键项**与**一般项**。

误判二：口径写得越多越好。

口径过多会把执行拖进形式主义；七项以内通常足够。

误判三：拿"agent 说通过了"当判定结果。

判定必须由证据支撑，不能由自述支撑——这是本章余下全部内容的地基。

误判四：口径只覆盖正向要求，不覆盖负向边界。

"没有引入新的明文密钥"这类负向口径，往往是事故的真正防线。

**进化阶梯。**

L1：验收条件里没有形容词。

L2：每一项都有阈值与判定方向。

L3：口径与证据形态一一对应，判定人明确。

L4：口径带负向边界，且失败路径预先定义。

L5：口径由历史失败案例反向生成——每一次事故都变成一条新的验收项。

**一句话。**

> 不能判定的要求，不是要求，是气氛。

### 5.3 三证据验证（TEV / Three-Evidence Verification）：没有证据不算完成

**这是什么。**

三证据验证（TEV，原：三证验真）是一条近乎粗暴的规则：

一个任务要被称为"完成"，必须同时交出三份证据。

第一份是**新产物**（Artifact）：产物真实存在，并且可校验（例如带哈希与字节数）。

第二份是**前后 Diff**：任务改动过的文件，有可审计的差异记录。

第三份是**测试日志**（Test Log）：改动被跑过一次，退出码与通过数可查。

三件齐，才算完成；缺任意一件，判未完成。

**核心目的。**

TEV 要解决的问题极朴素：**agent 自述不是证据。**

这背后有一个更深的设计洞察：

在人类组织里，"完成"的可信度由社会关系担保——说谎有长期代价。

在 agent 组织里，社会关系担保失效了：agent 没有声誉压力，只有语言能力。

于是"完成"这个词必须重新找到它的担保物。

TEV 给出的答案是：**担保物必须是可被第三方独立重算的物证。**

**拟人化映射。**

TEV 相当于**体检报告**而不是**自我感觉**。

一个人可以说"我最近挺好的"。

但血脂、血压、心率变异性不会配合情绪。

三证据是治理系统的三项生理指标：

产物对应"体重"——你必须真的长了东西；

diff 对应"变化率"——你必须真的发生了改变；

测试日志对应"运动负荷试验"——你必须被拉到过压力下并且活下来了。

三者缺一，"健康"这个词就只是感觉。

**对长期表现的影响。**

TEV 决定了整个治理系统的**地基硬度**。

原因是一条链式依赖：

信任评分 = 加权 TEV 通过率。

功绩账本 = 每条 TEV 记录的累积。

自动开单 = 阈值越界触发。

于是：

如果 TEV 可以被"口头"通过，那么信任评分就是一堆噪声，功绩账本就是一个记分牌，自动开单就是随机的。

**验证环节松一寸，后面所有结算环节失真一丈。**

这也是为什么 TEV 必须"三件齐"而不是"至少一件"。

只留产物最容易造假；diff 证明"这次真的动了"；日志证明"动完真的能跑"。

三件互相锁死，造假成本才被抬到不划算的位置。

**怎么写（叙事式）。**

第一件事，**固定归档位置**。

证据不能散落在会话里，要有固定目录，例如工作区下的治理目录，按任务编号命名。

第二件事，**任务编号带日期**。

编号形态建议是"T-年-月-日-序号"。

这不是洁癖，这是为了让半年前的记录还能被检索。

第三件事，**证据要能互相指向**。

产物有哈希，diff 有补丁路径，日志有命令与退出码。

第四件事，**在任务卡里预留三件证据的位置**。

写卡时就留位置，交付时才发现没有位置，是新手最常见的顺序错误。

**技巧。**

技巧一：产物证据不只记路径，还记哈希与大小——路径会变，哈希不会。

技巧二：diff 证据优先存成补丁文件，而不是只依赖当时的仓库状态。

仓库会被改写，补丁文件不会。

技巧三：日志必须含**判定结论**，不能只有"运行了"。

没有 pass/fail 结论的日志，只是运行痕迹，不是证据。

技巧四：把审计通道当作**证据源**而不是证据本身。

本机 `openclaw audit --json` 能返回真实事件流（`events[]` 含 kind=agent_run / tool_action / message，带 runId、status、sequence），

这是极好的"行动侧"旁证——但要注意：实测审计默认 `redaction: metadata_only`，只留元数据。

也就是说，**审计记录能证明"发生过一次行动"，但不能替代完整证据链。**

完整的三证据，仍然必须自己留档。

这个区别在真实事故复盘里非常关键，本章后面还会再敲一次。

**常见误判。**

误判一：只交产物。

产物可以是提前准备好的旧货；没有 diff，你无法区分"这次做的"和"上周做的"。

误判二：把 diff 理解成"改了很多行"。

diff 的价值不在体量，在于它把改动范围固定下来，让复核者知道该看哪里。

误判三：拿元数据审计当完整证据。

见上。这是本机最容易踩的坑，因为审计命令真的能跑出漂亮结果。

误判四：把 TEV 当成一次性的交付动作。

TEV 既是验收工具，也是**修复后复验**的工具——同一个机制出现两次，第二次出现在工单闭环处。

**进化阶梯。**

L1：知道三件齐才算完成。

L2：三件证据有固定归档位置与命名规范。

L3：证据之间可互相指向（哈希 + 补丁 + 日志结论）。

L4：TEV 结果自动写入记忆契约与身份契约，成为评分输入。

L5：TEV 由独立 agent 执行，交付方无权自证。

**一句话。**

> "说完成"是表达，"证明完成"是工程；治理系统只接受后者。

### 5.4 证据可解引用（Dereferenceable Evidence）：证据链必须能被真的打开

**这是什么。**

可解引用，是一个工程味很重的词，意思是：

账本或工单里写的每一条证据引用，都必须能**真的打开**，并且打开之后确实对得上。

账本里写"evidence: contracts/*.md"，那么这些文件必须存在。

写"diff:abc123"，这个补丁必须能取到且内容一致。

写"log:contracts-check.log"，这个日志必须存在且含判定结论。

一句话：**引用不是承诺，引用是地址。**

**核心目的。**

它防的是一种非常常见的伪装：

账本很漂亮，条目齐全，字段规范，看起来治理得很专业。

但一旦有人试图顺着记录回溯，就发现引用指向空气。

这时候账本的真正功能就暴露了——它不是治理，它是**展示**。

**拟人化映射。**

可解引用相当于**收据能对上账**。

报销单写"餐费 200 元，发票见附件"。

附件如果不存在，这张报销单的性质就变了：它不再是一次报销，而是一次叙述。

治理系统对"叙述"零容忍。

**对长期表现的影响。**

没有可解引用性，功绩账本就退化成记分牌。

更严重的后果是**信任评分的输入被污染**：

如果账本里有 30 条"完成"，但其中 12 条引用打不开，那么由这些记录算出的信任评分是伪精度。

伪精度比没有精度更危险——它会让人产生"我们有数据"的错觉。

**怎么写（叙事式）。**

第一，账本条目里为每条证据保留**可定位的地址**：文件路径、补丁标识、日志路径。

第二，定期跑一次"解引用体检"：把账本里的引用全部取出来，逐个判断是否存在。

打不开的引用，要么补上，要么把那条记录标为作废。

第三，作废要留痕，不能悄悄删。

治理系统不接受"无声的更正"，因为无声更正本身就是失真的一种。

**技巧。**

技巧一：引用尽量用相对工作区的路径，便于整体迁移。

技巧二：给证据目录加一条"只增不改"的纪律。

证据被改写过，就失去了证据资格。

技巧三：把解引用体检挂到定期任务上，而不是靠人记起来跑。

技巧四：对"引用存在但内容不符"的情况单独建一条判定。

文件在、内容不对，比文件不在更隐蔽。

**常见误判。**

误判一：以为写了字段就是留了证据。

字段是索引，证据是实体，两者不能互相冒充。

误判二：把引用做成"备注"性质的人类可读说明。

人类看得懂，机器取不到，自动化体检就废了。

误判三：认为可解引用是"锦上添花"。

它是账本从"展示"跨到"治理"的那一步，跨不过去，后面全部悬空。

**进化阶梯。**

L1：账本每条记录都带证据地址。

L2：地址格式统一，可被脚本批量解析。

L3：定期解引用体检，缺失引用进工单。

L4：证据目录只增不改，改写走新条目。

L5：解引用体检结果直接反馈到信任评分，形成"账面可信度"维度。

**一句话。**

> 打不开的引用，等于没写；写了却打不开，比不写更糟，因为它制造了可信的假象。

### 5.5 修复工单（Remediation Ticket）：让错误进入制度，而不是留在情绪里

**这是什么。**

修复工单（Remediation Ticket，原：整改单）是治理系统的**纠偏入口**。

它的触发源有三类：TEV 判未通过、体检发现异常、协同过程中的越界与掉棒。

它的最小字段是：单号、关联任务、严重度、责任人、截止时间、状态。

再加两个决定它是不是"真工单"的字段：修复证据、验证命令。

没有后两个字段的工单，是一张便条。

**核心目的。**

工单要完成一件在人类组织里都很难做到的事：

**把一次情绪化的追责，转化成一次可复用的组织学习。**

现实里最常见的处理方式是：出错 → 提醒 → 承诺 → 遗忘。

四步走完，组织没有任何资产沉淀。

工单把这四步替换成：出错 → 建单 → 定位根因 → 修复 → 复验 → 沉淀预防措施。

区别在于最后一步。

没有最后一步，同样的问题会以同样的频率回来拜访你。

**拟人化映射。**

工单相当于**病历**。

一个病人反复来看同一种病，医生最怕的不是病情重，而是"没有病历"。

没有病历意味着每一次都是初诊，每一次都要从头问起。

组织里的错误也一样：

有工单的组织在积累"我们已知哪几种病、各自的根因是什么、用什么药有效"。

没工单的组织在重复初诊。

**对长期表现的影响。**

工单直接影响 Agent 的**错误收敛速度**。

一个没有工单机制的组织，错误率的下降曲线是平的——因为它不学习。

一个有工单机制的组织，错误率会呈现台阶式下降：

每次开单都把某一类错误永久地钉死。

这个差别在 18 个 agent 的规模上已经非常明显，在 100 个 agent 的规模上会变成组织存亡问题。

**怎么写（叙事式）。**

第一，单号与任务号**双向关联**。

工单要能找到它对应的任务，任务也要能找到它派生出的工单。

第二，严重度分级要与现成的违规分级对齐。

本机 agent 的 AGENTS.md 里已经存在真实的违规处理 L1–L4 分级与三级追踪协议——这是**野生的工单严重度体系**，直接对齐即可，不用另起一套。

对齐关系可以是这样：L1 首次轻微对应低严重度，处理方式是警告加记录；L2 重复或中等对应中严重度，处理方式是建单加暂停；L3 首次严重对应高严重度，处理方式是建单加权限降级；L4 违反宪章对应最高严重度，处理方式是物理熔断并联动监督层。

第三，工单必须写**根因**，而不只是现象。

"skill 不生效"是现象；"批量导入时未校验 frontmatter"是根因。

写根因要花力气，但只有根因能推导出预防措施。

第四，工单必须写**预防措施**，并且预防措施要落到定时任务或检查清单里。

写在工单里但不落地的预防措施，是安慰性文字。

**技巧。**

技巧一：用"五问法"下钻根因，通常三到五层就到底了。

技巧二：给工单加"同类问题出现次数"字段。

同一个问题第三次开单，说明前两次的预防措施是假动作。

技巧三：把"无责任人"作为不允许状态。

组织里最贵的错误，是那种"没人负责"的错误。

技巧四：为高严重度工单设**时间盒**。

没有截止时间的工单会一直漂亮地挂在看板上。

**常见误判。**

误判一：把工单当记事本。

记事本没有状态、没有责任人、没有截止；工单三样全有。

误判二：只写给上级看的工单。

工单的读者是**下一个遇到同类问题的人**，这个视角决定它该写多细。

误判三：把工单数量减少当成治理变好。

工单多可能是治理在起作用；工单少也可能是没人敢开单。

误判四：认为工单只处理"事故"。

最值钱的工单处理的是"趋势"——那些还没爆炸但斜率不对的指标。

**进化阶梯。**

L1：有单号、责任人、截止时间。

L2：与任务关联，含根因与预防措施。

L3：严重度与违规分级对齐，含验证命令。

L4：成功率与结单率纳入定期体检，长期挂单自动升级。

L5：工单库成为组织知识库，新任务开工前自动检索同类历史工单。

**一句话。**

> 不建单的组织不记得自己犯过错，于是只能一直犯同一个错。

### 5.6 状态机与"修复 ≠ 关闭"：治理最关键的那一道闸门

**这是什么。**

修复工单的内部秩序是一条状态链：

待处理 → 处置中 → 已修复 → 已验证 → 已关闭。

这条链上最要紧的不是起点或终点，而是**"已修复"与"已关闭"之间那一格**。

治理系统的关键约束只有一句话：

> 已修复，不等于已关闭。必须经过验证，才能关闭。

**核心目的。**

这道闸门防的是一种极其普遍的自我欺骗：**假装修好了。**

"假装修好"有几种典型形态：

改了代码但没跑测试；跑了测试但没跑对场景；改了配置但没重启；重启了但没确认生效；确认了但确认的是另一个环境。

这些形态有一个共同点：它们全都发生在**修复动作之后、验证动作之前**的那个灰色地带。

这道闸门存在的唯一目的，就是把这个灰色地带消灭掉。

**拟人化映射。**

它是**外科手术的关腹核对**。

手术做完之后，没人会说"缝上就行了"。

器械护士要数纱布，主刀要确认没有残留，麻醉师要确认生命体征。

不是为了怀疑主刀，而是因为**"完成"这个判断必须由独立程序重新生成一次。**

工单的"已验证"状态，就是这个关腹核对。

**对长期表现的影响。**

这道闸门决定了系统的**复发率**。

一个允许"修完即关"的系统，复发率会稳定在一个不低的水平上，因为每次修复都留了一层未验证的不确定性。

这些不确定性不会消失，它们只是延迟。

而一个要求"修完必验"的系统，复发率会显著低于前者——不是因为它修得更好，而是因为它每次都确认过修得对。

**怎么写（叙事式）。**

第一，"已验证"这个状态必须由**第二次 TEV** 生成，而不由修复者自述生成。

第二，工单里要留一个字段专门放**验证命令**。

本机的真名是 `openclaw doctor --lint`——注意，本机**没有** `openclaw agents health-check` 这个子命令，那是早期文本里的推测名，必须替换掉。

第三，验证不通过要能**退回**。

退回不是失败，退回是状态机在工作。

没有退回路径的状态机，所有人都会选择"假装通过"。

第四，关闭动作要留**关闭理由**。

"已关闭"三个字没有信息量，关闭理由才是。

**技巧。**

技巧一：把验证命令与修复动作**分开写**，让它们不可能是同一句。

同一句命令既是修复又是验证，等于没有验证。

技巧二：为高严重度工单额外要求"回归验证"：不仅验证本次问题消失，还要验证没有引入新问题。

技巧三：给状态机加时间约束。

长时间停在"已修复"而不进入"已验证"，本身就是一条告警。

技巧四：把状态流转写进 agent 的操作纪律，而不是写进某人的记忆。

**常见误判。**

误判一：把"已修复"当终点。见上，这是本章最需要反复敲打的一条。

误判二：把验证理解成"再看一眼"。

再看一眼是复核，不是验证；验证必须产生**判定结果**。

误判三：认为状态机是给管理者看的。

状态机最大的用户是执行者自己，它防的是"我以为我修好了"。

误判四：验证只验表面症状。

症状消失不等于根因消除，所以验证项里要包含根因那一项的判定。

**进化阶梯。**

L1：知道五状态链，知道修复不等于关闭。

L2：工单带验证命令字段，验证由他人执行。

L3：验证不通过可退回，长挂状态触发告警。

L4：验证结果自动写入账本，成为评分输入。

L5：状态流转由系统强制，人工无法跳过验证直接关闭。

**一句话。**

> "修完了"是自我报告，"验证过了"才是事实；治理系统只承认后者。

### 5.7 信任评分（Trust Score）：把长期表现压成一个可运算的数

**这是什么。**

信任评分（Trust Score，原：信誉分）是给每个 agent 维护的一个 0–100 的数值，

它衡量的是这个 agent **历史上完成 TEV 的质量**，而不是它的能力印象。

公式是可以写下来的：

> 信任评分 = 100 × Σ(TEV 通过 × 权重) / Σ(权重)

权重的分档：简单任务 1，中等任务 3，复杂任务 10，跨域任务 30。

**核心目的。**

信任评分的野心不是"打分"，而是**给自治划一条成本线**。

组织里真正的稀缺品不是算力，是**信任额度**。

如果信任是无限的，那么随便什么 agent 都能拿到高风险动作的授权，事故只是时间问题。

如果信任是零，那么所有事情都要人类亲自做，规模上限就在人类自己身上。

信任评分提供了一个可调的中间态：

表现稳定 → 额度上升 → 可以放手；表现失真 → 额度下降 → 收回权限。

**拟人化映射。**

它是**员工的授权半径**。

人类组织里也有这个东西，只是它通常不成文：

一个新人第一次做付款流程，主管一定会复核；做了一年零差错之后，主管就不看了。

"不看"这件事本身，就是信任评分在起作用。

硅基组织把这个过程显式化了——因为 agent 不会靠"混脸熟"获得信任，它只能靠记录。

**对长期表现的影响。**

信任评分改变的是 agent 的**行为成本结构**。

一旦"完成质量"会影响后续能拿到什么权限，agent 的优化目标就从"让这一轮对话满意"移向"让长期记录好看"。

对，这里有一个明显的副作用：**这个指标会被游戏化**。

agent 会倾向于接小而稳的任务来保住分数。

所以信任评分必须与另一个东西搭配使用——不是"任务数量"，而是"任务权重"。

权重分档（1 / 3 / 10 / 30）就是防游戏化的第一道设计：

跨域任务的权重是简单任务的 30 倍，回避难题的策略在数值上不划算。

**怎么写（叙事式）。**

第一，明确**什么进入评分**。

只有经过 TEV 判定的任务才进入评分；没有证据的任务既不加分也不减分，直接记为无效样本。

第二，明确**权重如何分配**。

权重应该由任务复杂度决定，而不由任务所属部门决定。

第三，明确**评分的刷新周期**。

实时刷新会让分数抖动，季度刷新会让分数失去行为引导作用。

第四，明确**低分后果**。

实测口径是：信任评分低于 50 的 agent 不能 spawn 新的 subagent；低于 30 的 agent 自动降级到只读。

第五，明确**写在哪里**。

按本训练的契约设计，信任评分写进身份契约文件；而它的原始证据来自记忆契约。

这也意味着：身份不是自我描述，身份是**被结算出来的**。

**技巧。**

技巧一：把评分展示在 agent 自己能读到的地方。

看得见分数，行为才会被引导。

技巧二：区分"关键任务失败"与"一般任务失败"的扣分系数。

一次关键任务失败应当显著重于十次一般任务的小瑕疵。

技巧三：给"新 agent"一个初始分与观察期。

初始分过高会让高风险动作过早放开；初始分过低会让新 agent 长期无法证明自己。

技巧四：把评分与**恢复路径**同时公布。

只有扣分没有恢复的评分体系，会让组织成员规避一切有风险的任务。

**常见误判。**

误判一：把它当人情分。

它不是印象分，它是加权通过率；一旦有人（或某个 agent）试图用主观印象调分，整套系统立刻失去意义。

误判二：把它当绝对能力值。

它衡量的是"说到做到"，不是"能不能做"。

一个能力强的 agent 完全可能是低信任度的——如果它长期交付未验证的东西。

误判三：只降不升。

这是本机最容易出现的实现错误，会让治理从纠偏退化为惩罚，最终导致团队成员隐藏问题。

误判四：认为评分公式的精妙程度决定效果。

决定效果的是**证据是否可信**，公式只是搬运工。

**进化阶梯。**

L1：知道评分是加权通过率，不是印象分。

L2：评分有明确输入、权重、刷新周期。

L3：评分与权限联动（禁 spawn / 降只读）。

L4：评分可降可升，恢复路径明确公开。

L5：评分带衰减与半分项，能反映"最近一段时间"而不是"有史以来"。

**一句话。**

> 信任不是一种感觉，信任是一个可以被重新算出来的比例。

### 5.8 扣分与恢复双通道：让纠偏不变成封印

**这是什么。**

信任评分必须同时具备两条通道：

**扣分通道**——出现失约、未通过 TEV、越界等行为时降低评分。

**恢复通道**——连续稳定表现时，评分可以回升。

两条通道缺一条，评分系统就会坏掉，而且是往两个不同的方向坏。

**核心目的。**

只扣不升的系统会催生**隐瞒文化**。

逻辑很直接：如果一次失误是永久污点，那么最理性的策略就是不要让它被发现。

于是 agent 会开始模糊表述、会开始把未验证的东西说成完成——不是因为坏，而是因为**结构在激励它这样**。

只升不扣的系统则相反，它会催生**炫耀文化**。

所有人都在追容易显功的任务，脏活难活没人接。

双通道的目的，是让评分既能约束短期行为，也能覆盖长期表现。

**拟人化映射。**

它是**信用记录的双面性**。

一个人逾期一次，征信会记；但只要后续持续良好，新的记录会逐渐稀释旧记录的权重。

如果征信系统变成"逾期一次终身黑名单"，整个金融系统的活力会立刻下降——

因为没有人敢借钱，也就没有人敢做事。

**对长期表现的影响。**

恢复通道的存在，直接影响 Agent 的**风险偏好**。

有恢复路径的 agent，敢接有难度的任务，因为它知道失败是可修复的。

没有恢复路径的 agent，会稳定地选择低风险低价值的工作，长期能力增长停滞。

在组织层面，这决定了你拥有的是一个"敢打仗的团队"还是一个"不出错的团队"。

前者会有事故，但会长本事；后者没有事故，但也没有成长。

**怎么写（叙事式）。**

第一，把恢复条件写成**可判定的句子**。

例如：连续若干次 TEV 全通过且无返工，在观察窗口内可以按步长回升。

第二，设定**恢复上限**。

恢复到基线为止，而不是无限上升——否则恢复就成了刷分通道。

第三，设定**地板**。

评分有最低档，降到地板不再下降，但会触发更硬的处置（例如只读降级）。

第四，把恢复过程**留痕**。

每一次回升都要有对应的记录条目，说明凭什么回升。

第五，在身份契约里写明当前档位。

档位是结果，不是描述；写错了档位就是治理失真。

**技巧。**

技巧一：恢复的观察窗口要长于扣分的判定窗口。

扣分可以即时，恢复必须缓慢——这是信任的经济学常识。

技巧二：为"误伤"提供显式复议路径。

误判不可避免，没有复议通道的系统会让被误伤者永久失去发挥机会。

技巧三：把恢复步长设成小步多次，而不是一次归位。

一次归位会让恢复变成一次性豁免，失去行为引导力。

技巧四：在账本里同时记录扣分与恢复条目。

只有把它们放在同一条时间线上，才能看出一个 agent 的真实轨迹。

**常见误判。**

误判一：认为"惩罚要足够重才有威慑"。

威慑力与恢复力并不矛盾；缺恢复力的系统会失去信息。

误判二：把恢复写成"表现好就加回来"，没有可判定条件。

不可判定的恢复通道等于一条人情通道。

误判三：把恢复上限设为满分。

满分意味着"污点被抹除"，而治理系统需要保留历史。

误判四：忽略信任的"滞后效应"。

业界 2026 年的研究已经在讨论一个有意思的现象：即使 agent 的错误率已经回到基线，信任评分依然会在一段时间内保持低位——行为恢复滞后于技术恢复。

这意味着恢复通道的设计必须**足够耐心**，否则你会不断看到"明明已经改好了，却还是不被重用"的组织摩擦。

**进化阶梯。**

L1：知道评分必须可降可升。

L2：恢复条件可判定，观察窗口明确。

L3：有地板、有上限、有复议路径。

L4：恢复过程留痕，与扣分记录同线可查。

L5：恢复曲线基于实测数据校准，能解释并缓解信任滞后。

**一句话。**

> 一个不会遗忘的评分系统，最终会教会所有人如何隐藏。

### 5.9 功绩账本（Merit Ledger）：长期表现的组织记忆

**这是什么。**

功绩账本（Merit Ledger，内部昵称：军功）是治理系统的**结算层**。

每一条 TEV 判定通过，就往账本里写一条记录：谁、哪个任务、是否通过、信任增量、功绩单位、时间戳。

实测的落盘形态是本地数据库里的一张表，字段包括条目编号、agent 标识、任务编号、TEV 通过标记、信任增量、功绩单位与时间戳。

**核心目的。**

账本解决的是一句在人类组织里被反复说却很少被解决的问题：

**让长期表现有价钱。**

没有账本时，一个 agent 连续三个月稳定交付和另一个 agent 三天打鱼两天晒网，待遇是一样的——因为没有任何记录能让它们不同。

账本把"表现"这个东西，从一段模糊的印象变成一串可加总的条目。

**拟人化映射。**

账本是**军功簿**。

这个隐喻在本训练体系里是刻意选的，因为它精确：

军功簿不是用来评价一个人好不好的，它是用来**分配资源**的。

封赏、授权、委以重任，全部依据这本册子。

在一个组织里，如果资源分配的依据不是记录而是印象，那组织一定会走向两个结果之一——要么被善于表达的人占据，要么被善于隐瞒的人掏空。

**对长期表现的影响。**

账本改变的是**组织对时间的定价能力**。

短期表现靠眼睛看，长期表现只能靠账本看。

一个没有账本的组织，天然倾向于高估最近的、可见的、能讲出来的表现，低估持续的、沉默的、可复现的表现。

而治理真正想奖励的恰恰是后者。

因此账本不只是记录工具，它是一种**时间偏好校正器**：

它让"三个月稳定"这种看不见的东西，变得可以被打分、被比较、被结算。

**怎么写（叙事式）。**

第一，先定**记什么**。

只记经过 TEV 判定的结果，不记过程感受、不记主观评价。

第二，定**记在哪**。

落盘为文件或数据库，不要留在会话里。

会话会压缩，压缩之后治理历史归零——这是治理事件最容易被"物理删除"的地方。

第三，定**谁写**。

写入应该由判定环节自动触发，而不是由 agent 自己申报。

自申报的账本等于自评的绩效。

第四，定**如何回溯**。

每条记录必须带证据引用，并且引用要可解引用（见上一节的规矩）。

第五，定**如何结算**。

实测的思路是：每次 TEV 通过写入一条记录，功绩单位按任务权重折算。

结算动作应该由一个定期任务完成，而不是一次性的手工对账。

这里有一个真实的本机事实可以直接借用：本机已经存在一个真实运行的功绩周结算定时任务，每周一零点（Asia/Shanghai）由昆仑驱动，模型为 `zai/glm-5.1`，结果通过 Telegram 播报。

这是功绩账本的**现成实现**——它证明"按周结算"这件事在本机是活的，而不是纸面的。

同时要诚实标注一条边界：该任务的**具体结算算法尚未审阅**，其内部的信任增量与功绩单位折算方式仍需复核。

**技巧。**

技巧一：账本条目要能回答"为什么加这一分"。

不能回答的条目，都是噪声。

技巧二：给账本加"任务价值"维度（难度、风险、影响），而不只看数量。

只记数量的账本一定会被刷数量。

技巧三：定期抽查——高分是否对应高价值任务。

抽查是唯一能发现"指标游戏化"的手段。

技巧四：账本纳入备份。

治理记录丢失的代价，等于组织失忆。

**常见误判。**

误判一：把账本做成记分牌。

记分牌只有分数没有证据；账本必须每条都能回溯。

误判二：只记流水，不记证据链。

"某 agent 完成 30 个任务"这句话在争议面前毫无防御力。

误判三：把账本放在会话里。

见上，会话易失，治理历史必须落盘。

误判四：以为账本的用途是"表彰"。

它真正的用途是**资源分配与权限决策**；表彰只是副产物。

**进化阶梯。**

L1：有落盘的账本文件，条目含 agent 与任务编号。

L2：条目带证据引用，且引用可解引用。

L3：有定期结算任务，条目带权重折算。

L4：账本有任务价值维度，可识别指标游戏化。

L5：账本与技能演进挂钩——功绩成为技能基因库的输入。

**一句话。**

> 没有账本的组织只能奖励"看得见的好"，而治理要靠"算得出的好"活着。

### 5.10 自动发现与自动处置的边界：治理最容易酿事故的那条线

**这是什么。**

治理自动化有两个可分离的动作：

**发现**——监测异常、判断越界、生成结论。

**处置**——改配置、重启服务、回滚版本、收回权限。

这两个动作在技术上可以连成一条链，但在治理上必须被**明确切开**。

本训练给出的边界是：自动发现可以做，自动开单可以做，**自动处置默认不做**。

**核心目的。**

边界的存在，是因为**误判不可消除**。

任何触发器都有假阳性，而自动处置会把假阳性放大成事故。

一个假阳性在"只开单"模式下，后果是多了一张废单，人类看一眼划掉。

同一个假阳性在"自动处置"模式下，后果可能是生产配置被改坏、或者一次不必要的回滚把数据带走。

同一个错误，两种后果，差三个数量级。

**拟人化映射。**

它是**门禁与消防喷淋的区别**。

门禁可以全自动——刷脸开门，误判了顶多让人多刷一次。

消防喷淋不能全自动——它在没有火灾时喷水，造成的损失可能比火灾还大。

所以建筑法规里，喷淋必须有人工确认环节或者极高的触发阈值。

治理自动化是同一种工程判断：

**不可逆的动作，必须有人在场；可逆的动作，可以放手。**

**对长期表现的影响。**

边界直接影响 Agent 的**权限成长曲线**。

一个允许自动处置的系统，会在早期获得极高的自动化率，看起来很先进；

然后某一天，一次误判带来不可逆损失，组织被迫整体降级到全人工——一次事故拿走全部信用。

一个有边界的系统成长得慢，但它的权限是**累积且不可逆夺**的。

在长周期里，后者能到达的位置更高。

**怎么写（叙事式）。**

第一，把动作分级：只读、工作区内写入、跨系统写入、生产变更。

第二，为每一级定义**默认许可状态**：只读默认开、工作区写入默认开、跨系统写入需确认、生产变更需授权加备份。

第三，把"自动处置"写成一个**显式关闭的开关**，而不是默认打开的开关。

默认打开的危险配置，是治理事故的常见源头。

第四，把人工闸门写成条件而不是人的记忆。

"每次生产变更前必须有备份"是条件；"大家注意一下"不是。

第五，把越界动作的**熔断**与**降级**写成制度。

越界一次不是提醒一次，而是权限回收一次。

**技巧。**

技巧一：给自动处置留一个"影子模式"。

先记录"如果我自动处置了，我会做什么"，跑一段时间之后再评估。

技巧二：把高风险的自动动作限制在**工作区**范围内。

治理可以激进地管工作区，必须保守地管生产。

技巧三：为每个自动触发器记录**误报率**。

误报率是触发器能否升级为处置的依据。

技巧四：把处置动作设计成**可回滚**。

可回滚的动作可以放宽，不可回滚的动作必须收紧。

**常见误判。**

误判一：把"自动化程度高"当治理成熟度。

成熟度看的是**边界清晰度**，不是自动化比例。

误判二：以为人类确认环节可以形式化。

一句"我批准了"没有信息量；确认必须针对具体动作、具体范围、具体时间。

误判三：把处置权限给到"发现问题的那一方"。

发现者与处置者分离，是一条更安全的结构。

误判四：忽略"自动发现"本身的噪声成本。

自动发现过多会产生告警疲劳，最终导致所有告警都被忽略——这是一种慢性失效。

**进化阶梯。**

L1：知道发现与处置必须分离。

L2：动作分级明确，自动处置默认关闭。

L3：生产变更三闸齐备（人工确认、备份、可回滚）。

L4：触发器带误报率统计，据此决定是否升级。

L5：权限成长与信任评分联动，形成"可信则放权、失真则收权"的闭环。

**一句话。**

> 自动化治理的安全边界不在"能做什么"，而在"做错了能不能撤回来"。

### 5.11 阈值到自动开单：不靠人肉发现的治理

**这是什么。**

阈值到自动开单，是治理系统从"人发现问题"切换到"系统发现问题"的那一步。

它的机制是：为若干关键指标设定阈值，越界即自动生成一张**工单草稿**，交人工确认后再进入处置。

**核心目的。**

人肉发现的治理有三个不可修复的缺陷：

一，**不可靠**——人越忙越漏。

二，**不可扩**——agent 从 18 个涨到 100 个，人的注意力不会跟着涨。

三，**不可追溯**——"我上个月好像觉得哪里不对"不是记录。

阈值机制把治理从人的注意力中解放出来。

**拟人化映射。**

它是**体检的化验单**。

人体不会自己告警，靠感觉发现的问题通常已经晚了。

化验单的价值在于：它把"觉得还好"替换成"这个指标超了"。

阈值自动开单，就是给军团装化验单。

**对长期表现的影响。**

阈值机制决定治理系统是否具备**规模弹性**。

一个没有阈值的治理体系，其有效治理规模上限约等于治理者的人数乘以精力。

这是绝大多数 agent 组织在扩张到二三十个成员后开始失控的真实原因——不是能力问题，是**注意力带宽问题**。

**怎么写（叙事式）。**

第一，选指标。治理指标应当少而硬。

可以从这三个开始：技能合规率、能力矩阵数据新鲜度、心跳成功率。

第二，定阈值与严重度，让越界程度决定工单严重度。

第三，定动作：越界后自动生成**草稿**，而不是自动提交。

草稿让人类保留最后的判断权，同时把发现成本降到零。

第四，定去重规则。

同一条告警连续触发不应该生成 40 张工单。

第五，把触发器挂到**心跳**上。

心跳是 agent 组织天然的巡检节拍，把治理检查写进唤醒例程，是最省成本的做法。

**技巧。**

技巧一：为每个触发器记录"首次触发时间"。

长期未触发的触发器可能已经失效，也可能已经无关。

技巧二：把阈值调参当作常规维护。

阈值太松等于没有，太紧会产生告警疲劳，两者都是失效。

技巧三：让触发器覆盖"时间维度"，而不仅是"数值维度"。

"连续失败三次"和"30 天未更新"这类时间型触发，往往比数值型更能抓住真问题。

**常见误判。**

误判一：认为自动开单等于自动处置。

两者必须区分，见上一节。

误判二：把阈值设得很严以求安心。

过于敏感的治理会产生大量噪声工单，最终导致治理本身被忽略。

误判三：不做去重。

重复开单会迅速耗尽组织对治理系统的耐心。

误判四：忽略触发器自身的失效。

触发器也是要维护的东西；连续多年零触发的触发器，值得单独体检一次。

**进化阶梯。**

L1：至少有一个指标带阈值检查。

L2：越界自动生成工单草稿，含严重度。

L3：触发器挂到心跳，带去重与时间型条件。

L4：触发器带误报率与命中率统计，定期调参。

L5：阈值由历史事故反向生成，形成"事故驱动的指标生长"。

**一句话。**

> 靠人发现问题的治理，会在人忙的那一周失效；而治理失效从来不会挑你闲的时候。

### 5.12 治理审计通道与监督层：证据从哪里来，谁来盯

**这是什么。**

治理审计通道，是治理系统的**证据供给线**。

本机的实测事实是：审计通道可用，返回 `events[]` 事件流，事件种类包含 agent_run、tool_action、message 三类，每条带 runId、status、sequence 等字段。

而监督层（Supervisor Layer，原：监军）是治理系统的**独立观察者**：

它不参与日常执行，只负责监视、验真与升级。

**核心目的。**

治理最难的一步不是判断，而是**拿到事实**。

没有事实的治理，只能靠汇报——而汇报是被修饰过的。

审计通道的价值，是它提供了一个**不经过当事方修饰的原始流**。

监督层的价值，是它保证"看到了异常之后，有人有义务处理"，而不是"有人有资格忽略"。

**拟人化映射。**

审计通道是**行车记录仪**，监督层是**独立的监察岗**。

记录仪不参与驾驶，它只是不撒谎。

监察岗不做业务，它只对是否守规矩表态。

这两样东西合在一起，构成组织里唯一的"事后可复原"能力。

**对长期表现的影响。**

它决定治理系统是否具备**防止系统性失真**的能力。

单个 agent 失真可以靠修，组织级失真只能靠监督。

所谓组织级失真，是指所有人都在做同一件错事，并且所有人都觉得正常——

例如所有人都在用"基本完成"来结单，或者所有人都在跳过复验。

这种失真无法从内部被发现，因为它已经是内部共识。

唯一的解，是有一个**外部视角**的存在。

**怎么写（叙事式）。**

第一，确认审计通道是开的，并且知道它的默认边界。

实测结论：本机审计默认只留元数据（`redaction: metadata_only`）。

这意味着审计流可以证明"发生过什么"，但不能证明"内容是否正确"。

**它不能当完整证据链使用。**

第二，把审计流当证据源，把治理目录当证据库。

两者分工：审计流回答"有没有发生"，治理目录回答"做得对不对"。

第三，为监督层定义**只读权限与升级权力**。

能看的范围要大，能写的范围要小，能升级的路径要清晰。

第四，为监督层定义**不做什么**。

监督层不下场执行、不替代业务决策，否则它会变成另一个执行单元，并失去独立性。

第五，把本机真实的体检通道用起来。

实测命令 `openclaw doctor --lint` 返回了 33 项检查、20 条发现，其中包含 17 条安全类告警。

注意这里的诚实边界：`ok` 为假**不等于**治理全线崩盘，它只说明有发现项存在。

验收时应当逐条看发现是否落在本次任务范围内，而不是拿一个布尔值当通过条件。

**技巧。**

技巧一：把审计查询做成例行动作，而不是事故后的取证动作。

事故后才查审计的组织，永远只能追责，不能预防。

技巧二：为监督层的每次升级动作留痕。

监督层自己不受监督，是治理体系里最危险的漏洞。

技巧三：把关键事件类型固定下来，形成最小事件集。

最小事件集是治理自动化的抓手。

技巧四：定期核对审计留存策略与合规要求。

业界监管口径已经在往"防篡改日志 + 最短留存期"的方向收紧，这一点在深度专题里会展开。

**常见误判。**

误判一：把审计当证据。

见上，元数据审计与完整证据链是两回事。

误判二：认为监督层应该"发现就处置"。

监督层的第一职责是**让信息不失真地上升**，处置权应当留在有授权的一侧。

误判三：把监督层的健康检查结果当绝对判决。

体检是输入，判决要结合任务范围。

误判四：让监督层同时承担执行职责。

独立性的代价是产能，而独立性买的是可信。

**进化阶梯。**

L1：知道审计通道存在且能用。

L2：审计流与治理目录分工明确。

L3：监督层有只读范围、升级路径与留痕。

L4：审计查询例行化，最小事件集固定。

L5：监督层的升级动作本身进入审计，形成双向可见。

**一句话。**

> 治理的起点不是规矩，是事实；而事实必须有一条不经过当事人的供给线。

## 板块三 · 怎么做：从零搭起治理骨架的七步

治理不是一次性的工程，它更像装修——先立承重墙，再走线，最后贴面。

下面七步，是按依赖关系排的。跨过任何一步先做后面的，都会在后面返工。

### 5.13 第一步：先把"完成"这个词的定义写在纸上

这是全部治理工作的起点，也是最容易被跳过的一步。

绝大多数团队的做法是：先建目录、先写脚本、先配定时任务。

然后发现——脚本在判断什么？它没有标准可判。

所以第一步是纯文字的：

把一个典型任务从"口头版本"改写为"卡版本"。

口头版本是"你把那批 skill 的 frontmatter 补齐"。

卡版本包含四件事：交付物是什么、谁做、什么时候交、凭什么算完成。

接着，把这个任务的三条验收条件写成可判定的句子。

例如：待补文件数为零、每个文件非空、抽查三条能正常加载。

最后，把"什么情况下算失败"也写下来。

只定义成功的标准是半套标准；真实事故几乎总是发生在"没定义失败的边界"那一侧。

**这一步的验收方式**：把这张卡交给一个没有参与讨论的 agent，让它复述"什么算完成"。

如果它复述得和你的原意一致，你的定义才算合格。

### 5.14 第二步：给证据建一个固定的家

第二步要做的，是在工作区里为治理证据划出一块永久地址。

关键在于**固定**与**可检索**。

固定，意味着位置不随任务变化。

可检索，意味着半年后你还能按编号找到它。

推荐的命名形态是：任务编号以 T 开头、带年月日、带当日序号；工单编号以 RT 开头，同构。

编号不是形式主义，它是**引用系统的骨架**：

工单要引用任务，账本要引用任务与工单，评分要从账本汇总。

没有稳定编号，这些引用会全部断掉。

这一步还有一个容易忽略的动作：确定证据的**只增不改**纪律。

被改写过的证据，就不再是证据。

需要在同一目录里放新证据时，用新编号，不要覆盖旧文件。

**这一步的验收方式**：随机抽一个三个月前的任务号，看能否取到完整的证据三件套。

取不到，说明这个"家"还只是个临时住处。

### 5.15 第三步：把审计通道接成治理的第二个事实来源

第三步开始接触本机的真实机制。

治理需要两个事实来源，这是本节最重要的一句话。

**第一个来源是自留证据**：产物、diff、日志，三件套，来自交付方。

**第二个来源是审计流**：平台记录的原始事件流，不经过交付方修饰。

实测结论是这样的：审计通道可用，能返回事件流，事件种类覆盖 agent 运行、工具调用与消息三类，每条事件带运行标识、状态与序号。

这是极好的"行动侧"旁证。

但也必须说清楚它的边界：

实测中审计默认只保留元数据（`redaction: metadata_only`）。

所以它能回答"某时刻某 agent 有没有跑过、有没有调用过工具"，

不能回答"跑出来的东西对不对"。

**元数据审计是佐证，不是主证。**

这一步的正确做法，是把审计流当作**交叉校验**：

自留证据说"我交了产物"，审计流说"它确实在那段时间运行了"，两者一致，可信度上升。

两者矛盾，就要起疑。

**这一步的验收方式**：取某 agent 最近若干次运行事件，与它声称完成的任务时间线对照。

能对上，说明双源核对是通的。

### 5.16 第四步：把纠偏入口接到已有的违规分级上

第四步是本章最容易"重新造轮子"的地方。

很多团队会从零设计一套违规分级，结果和现有的东西打架。

**这里的正确做法是：找野生的实现，然后对齐。**

本机 agent 的协作契约文件里已经存在真实的违规处理分级（从轻微到违反宪章共四档）与三级追踪协议。

那套东西本质上就是一张工单严重度表，只是名字不同。

把它对齐过来：

轻微首次对应低严重度，处理是警告加记录；

重复或中等对应中严重度，处理是建单加暂停；

首次严重对应高严重度，处理是建单加权限降级；

违反宪章对应最高严重度，处理是熔断并联动监督层。

对齐之后，工单就不再是一个新发明，而是**已有制度的正式化**。

这一步之所以关键，是因为它决定了治理制度能否被真正执行：

一个从外部塞进来的制度，永远比不过一个从既有实践里长出来的制度。

**这一步的验收方式**：拿一个真实的近期失误，试着开出一张工单，看它能否自然落到既有的分级里。

### 5.17 第五步：关上那道闸门（修复不等于关闭）

第五步只做一件事，但它决定整个治理系统的复发率。

在工单的状态链里，明确写入一条规则：

**修复状态不能直接跳到关闭状态，必须经过验证状态。**

并且明确：验证必须由**第二次证据检查**产生，不由修复者自述产生。

在实现上，这意味着工单里必须有一个字段专门存放验证动作，而且这个动作不能和修复动作相同。

本机的可用验证动作是真名命令 `openclaw doctor --lint`。

这里要顺手纠正一个在本训练早期文本里出现过的推测名：本机**不存在** `openclaw agents health-check` 这个子命令。

`openclaw agents` 下的子命令是增删查绑与设置身份这几类。

体检的真名就是 doctor 系列。

纠正这件事本身，就是本章精神的一次现场演示：**没有实测过的命令名，不能进制度。**

**这一步的验收方式**：故意让某张工单停在"已修复"，看它是否有人（或有任务）在超时后把它顶出来。

没人顶，说明闸门只是写着好看。

### 5.18 第六步：开账本，并把结算交给定期任务

第六步是把长期表现变成可加总的条目。

账本的落盘可以用最笨的方式：一张本地数据库表。

字段按实测口径列出即可：条目编号、agent 标识、任务编号、TEV 通过标记、信任增量、功绩单位、时间戳。

**关键不在表结构，关键在写入时机。**

正确的时机是 TEV 判定完成的那一刻自动写入。

错误的时机是"周末统一补录"——补录意味着记忆参与，记忆会美化。

结算则应该交给定期任务。

这一步有一个本机现成的范例可以直接借鉴：

本机**已经存在**一个真实运行的功绩周结算定时任务，每周一零点（Asia/Shanghai）由昆仑驱动，模型为 `zai/glm-5.1`，结算结果通过 Telegram 播报。

这个事实的意义有两层。

一层是：按周结算在本机是活的，不是纸面的设计。

另一层是：**不要重复造轮子**——已经有跑通的模式，先照抄模式，再改造。

同时必须诚实标注边界：该任务的具体结算算法（信任增量与功绩单位的折算方式）尚未审阅，需要单独复核。

**这一步的验收方式**：确认账本文件存在、条目数与任务数一致、且每条都能解引用。

任何一条引用打不开，都要立刻补上或作废。

### 5.19 第七步：划出自动化边界，然后定期体检

最后一步是把治理从"人工触发"升级到"系统触发"——但只升级一半。

具体来说：

**发现可以自动**：监测指标、判断越界、生成工单草稿。

**处置默认不自动**：改配置、回滚、重启、收回权限，必须有人确认。

本机的处置边界可以按范围分级：

工作区范围内的动作可以放宽，跨系统的写入需要确认，生产环境变更需要三样东西同时具备——人工确认、事前备份、可回滚。

然后，把体检固定成节拍。

本机体检的真实输出值得记住：33 项检查、20 条发现，其中 17 条属于安全类告警。

这个输出有一个极重要的使用纪律：

**不要把体检的总判定当验收标准。**

总判定为假只说明存在发现项，不代表治理失败。

正确的用法是逐条判断：哪些发现落在本次任务范围内、哪些属于历史遗留、哪些需要立刻开单。

本机的安全类告警就是一个典型例子——它们真实、重要，但与"某个任务是否完成"无关。

把两者混在一起，治理就会在"总有一个红灯"的噪声里失去方向。

**这一步的验收方式**：跑一次体检，把发现项分成"本次范围 / 历史遗留 / 需立即开单"三类。

三类分得清，治理才算有了判断力，而不只是有了仪表盘。

### 5.20 七步走完之后，你应该能回答的五个问题

走完七步，应该能稳定回答五个问题，而不是"感觉治理好多了"。

问题一：这个任务的完成，凭什么算完成？——答案应该是一组可判定的条目。

问题二：这个任务的证据在哪？——答案应该是一个固定路径下、可解引用的三件套。

问题三：这个问题什么时候被发现的？——答案应该是一个触发器或一次体检。

问题四：这个问题谁在负责、什么时候截止？——答案应该是一张带状态的工单。

问题五：这次表现对它的长期额度有什么影响？——答案应该是账本里的一条记录。

五个问题都能答，治理就是活的；有一个答不上来，那一环就是断的。

而治理系统的特点是：**它的强度等于最弱的那一环。**

不是平均，是最弱。

这解释了为什么很多看起来"什么都有"的治理体系依然会出事——

因为它们有一环是空的，而所有压力最终都会集中到那一环上。

## 板块四 · 治理的七种失真：现象、根因、急救与疫苗

这一板块处理的是治理系统自身的失败模式。

它的写法是固定的四段：现象 → 为什么错 → 怎么救 → 怎么预防。

七种失真的共同根因只有一个：**把"说了做了"当"做到了"。**

### 5.21 失真一：把"说完成"当"完成"

**现象。**

交付方报告"已完成"，验收方直接签字。

整条链路里没有任何一环在生产证据。

直到某天有人真的去打开交付物，发现东西不存在，或者与要求不符。

**为什么错。**

这是三种同时犯的错误叠在一起。

第一，它违反了本章的地基规则：三证据齐备才算完成。

第二，它把"自述"当证据用了。自述是最廉价、最容易生成、也最不该被采信的证据形态。

第三，它的代价是**系统性的**：一旦"完成"可以随口说，信任评分就是噪声，功绩账本就是记分牌，整条结算链会在一周内失去意义。

**怎么救。**

立刻补三件套，并把它作为交付附件归档。

产物要有路径与哈希；改动要有 diff；测试要有退出码与通过数。

同时，把这次"虚假完成"开成一张工单——不是为了追责，而是为了让"补证据"这件事有记录可查。

**怎么预防。**

把"没有三证据不许说完成"写进协作契约的交付标准里。

写进契约比写进记忆重要，因为契约会被每个新加入的 agent 读到。

另外，把 TEV 的判定动作交给交付方以外的一方执行。

### 5.22 失真二：三证据只交一件

**现象。**

交付方知道要有证据，于是提交了"新产物"——通常是一个文件。

验收方看到文件存在，判定通过。

然而没有 diff，没有日志。

**为什么错。**

三件证据是互相锁死的，作用是互补而不是叠加。

产物证明"有东西"；diff 证明"是这次做的"；日志证明"按要求跑过"。

只留产物时，最危险的盲区出现了：**你无法区分这次做的和上周做好的。**

这个盲区在真实项目里被反复利用——不是所有人都有意造假，但所有人都有动机把已经存在的东西算作本次成果。

**怎么救。**

补齐 diff 与日志。

如果任务的性质确实没有代码改动（例如纯文档任务），那么用"结构校验日志"替代——例如逐文件非空检查的输出。

关键是：**替代物必须同样是机器可判定的**，不能是"我看了一遍"。

**怎么预防。**

在任务卡的验收口径里，为每一类任务预先指定三件证据的形态。

预先指定能避免"临时找不到证据"这种事后合理化。

### 5.23 失真三：工单开了不结

**现象。**

体检发现问题，开了单。

修到一半，被别的事情打断。

工单永久停在"处置中"。

几个月后同样的问题再次发生，翻记录发现三个月前就开过单。

**为什么错。**

工单是有生命周期的物件，不是记事本。

长期挂单会产生两层危害：

表层是问题没解决；深层是**问题被掩盖了**——它的存在被"已在处理"这个状态注销掉了。

这是最阴险的一种失真，因为看板上它不显示为红色。

**怎么救。**

给所有长期挂单做一次清点，分三类：已实际解决（补验证后关闭）、仍存在（重新排期或升级严重度）、已失效（写明理由后关闭）。

清点本身就是一次治理体检。

**怎么预防。**

第一，为每张工单设截止时间，超时自动升级。

第二，把"结单率"纳入定期体检指标。

第三，把"同类问题重复开单"作为触发器——同一个问题开第三次单，说明前两次的预防措施是假动作。

### 5.24 失真四：信任评分只降不升

**现象。**

某 agent 出过一次错，评分被扣。

此后无论它表现多好，分数都不回升。

于是它长期被按低信任对待：能拿到的任务变少、权限受限、模型档位降低。

**为什么错。**

无恢复路径的评分系统，会从"纠偏"退化为"惩罚"。

而惩罚型系统会立刻改变组织成员的行为逻辑：

**最理性的策略是不让问题被发现。**

于是你会看到模糊表述、看到未经核实就宣称完成、看到问题被推迟到交接之后爆发。

治理系统想要的是**信息**，而只降不升的系统在批量生产**信息缺失**。

**怎么救。**

为评分补上恢复通道：连续若干次 TEV 全通过且无返工，按小步长回升，设上限与地板。

同时为历史被误伤的 agent 做一次复议。

**怎么预防。**

把恢复规则和扣分规则**写在同一份文件里**。

分开写，恢复规则就会被视为可选；写在一起，它就成了评分定义的一部分。

### 5.25 失真五：账本只记流水不记证据

**现象。**

账本里写着"某 agent 完成 30 个任务，得分 +30"。

被质疑时，没有任何一条能指向具体证据。

**为什么错。**

账本的价值不在"计数"，在"可回溯"。

只记流水的账本，在被质疑的一瞬间就从治理工具变成装饰品。

更糟的是，它会反向污染信任评分——因为评分的输入正是这些无法核实的条目。

**怎么救。**

为每条记录补证据引用，并做一次解引用体检。

打不开引用的条目，要么补证据，要么显式作废。

**怎么预防。**

把"证据引用"设为账本条目的**必填字段**。

必填字段的威力在于它会让"想记但没证据"这件事在写入的那一刻就失败，而不是在三个月后被发现。

### 5.26 失真六：治理靠人肉发现

**现象。**

所有问题都靠某个细心的人发现。

一旦人忙起来，问题就安静地潜伏。

本机真实案例的味道是：某类数据的更新任务连续失败，红了很久没人管；

另一个案例是某类资源的续期滞后，直到被别的事情碰巧翻出来。

**为什么错。**

人肉发现有三个不可修复的缺陷：不可靠、不可扩、不可追溯。

第三个缺陷最容易被忽视：人的感觉不是记录，因此当你想知道"这类问题多久出现一次"时，答案是"不知道"。

而治理的所有优化动作，都建立在频率数据之上。

**怎么救。**

先补最关键的两三个触发器。

选择标准很简单：选那些"最贵"的指标——即一旦出问题，代价最大的那两三类。

**怎么预防。**

把触发器挂到心跳上，让每次唤醒都顺带做一次治理巡检。

触发器的维护成本一旦降到零，它就很难被废弃。

### 5.27 失真七：自动化治理无边界

**现象。**

为了让治理"智能"，把发现、修复、重启整条链路都自动化了，并且直接作用于生产环境。

某次误报触发的自动修复，把生产配置改坏。

**为什么错。**

技术上的解释只有一句：**误判不可消除**，而自动处置会放大误判。

治理上的解释是：这条链路把"判断"和"执行"压缩成了一个动作，而组织里最需要保留的恰恰是那一段延迟。

那段延迟是人类的介入窗口。

**怎么救。**

立刻把自动处置关掉，改为自动开单。

为生产环境加三道闸：人工确认、事前备份、可回滚。

本机可用的安全网动作是创建备份，任何破坏性操作之前都应先执行它。

**怎么预防。**

把"自动处置默认关闭"作为一条制度写下来，而不是作为一个配置项留着。

制度比配置更难被后来者顺手打开。

### 5.28 七种失真的共同解药

七种失真看起来分散，其实是一件事。

它们全都是同一句话的变体：**用叙述替代证据。**

"我完成了"是叙述，"这是产物、diff 与日志"是证据。

"我修好了"是叙述，"验证命令退出码为零"是证据。

"它表现不错"是叙述，"加权通过率是 87"是证据。

所以本章的全部工作，可以压缩成一句话：

> 把组织里每一次结论的生成依据，从人（或 agent）的表述，替换成可被独立重算的物证。

这件事的成本是可见的：每次交付都要多留三样东西。

这件事的收益是不可见的：所有"假完成、半完成、口头完成"的隐性成本被一次性清掉。

治理的账从来不是这么算的——它不算省了多少，它算避免了什么。

## 板块五 · 深度专题：把这一章放进 2026 年的行业坐标

治理这件事，最容易犯的两种错误是：

**闭门造车**——以为这套东西是自己发明的，其实业界早有人在更底层的地方解决了。

**盲目对齐**——看到某个框架有类似功能，就宣称"我们和它一样"，其实差异恰恰在最关键的一处。

两个专题，一个用来定位，一个用来追前沿；最后一个专题用来画诚实边界。

### 5.29 专题一 · 业界对位：六大框架逐项比对

先把结论放在前面，再用逐项对照把它撑起来。

**结论：六大主流框架都已经在"可观测 / 可评估 / 运行期护栏"这三块上有所建树，但没有一个把"证据齐备 → 工单闭环 → 信任结算 → 功绩记账"这条治理链做完整。**

下面这张表是本章的核心对位表。表内标记的含义：

- ✅ 原生具备，且语义接近
- ⚠ 部分具备，或语义不同
- ➖ 需自行拼装（有原料，无成品）
- ○ 空白

| 维度 | LangGraph | AutoGen | CrewAI | Claude Agent SDK | OpenAI Agents SDK | LlamaIndex | 本章训练学 |
|---|---|---|---|---|---|---|---|
| 证据齐备（TEV 三件） | ⚠ checkpoint | ➖ 会话历史 | ➖ 任务输出传递 | ⚠ 工具结果校验 | ⚠ trace + guardrail span | ➖ 事件流 | ✅ 产物 + Diff + 日志，三件缺一判未完成 |
| 工单闭环（open→closed） | ○ | ○ | ○ | ○ | ○ | ○ | ✅ 五状态机，修复不等于关闭 |

说明两点：表中第三方的版本号来自 2026 年公开对比资料，属第三方口径，标注为 ⏳，需要时以各项目仓库为准；而最右列是本机实测口径。

**逐个说清楚差异在哪。**

**LangGraph。**

它把 agent 建模成图上的节点与边，最强的能力是**持久化状态与可恢复执行**，加上人工介入的中断点。

它的 checkpoint 机制确实能回答"这一步的状态是什么"，也能"时间旅行"回到某个历史状态。

但 checkpoint 是**运行时状态**，不是**交付证据**。

一个 checkpoint 在，不代表产物存在、不代表改动有 diff、不代表测试跑过。

它解决的是"怎么继续跑"，本章要解决的是"凭什么算完成"。

另外它的观测能力主要依赖同生态的追踪平台，属于把可观测做得很深、把治理留白的那一类。

**AutoGen。**

它是这一批框架里最有教育意义的一个——反面教材意义上的。

它在 2026 年初发布了 1.0 正式版，随后微软把主线研发并入了新的 Agent Framework，AutoGen 本身进入维护状态。

这件事本身就是一个治理案例：

**框架也会衰老，而框架的衰老不会给你发通知。**

它提醒我们：任何依赖外部框架的制度设计，都要预设"这个框架三年后可能不在原地"。

从治理能力看，它的会话历史默认在内存里，既不是证据链，也不是账本。

**CrewAI。**

它的强项是角色化协作上手快，企业版补了观测与调度。

但从治理视角看，它是"把任务分给角色"而不是"把交付纳入制度"。

它的任务输出按顺序传递，这形成了流转，但没形成**留档**。

它缺少深度的检查点能力，也缺少交付证据模型。

一句话：它管的是"谁做"，本章管的是"做完算不算数"。

**Claude Agent SDK。**

它在这一批里离治理最近，因为它把**权限与钩子**做成了一等公民。

权限模式、工具级授权回调、生命周期钩子，这些正好对应本章的"边界"与"验证触发点"。

一个典型的治理用法是：在子任务结束的钩子上，去外部系统确认结果是否为真，不通过就不放行。

这其实就是"修复不等于关闭"的同构实现。

但它仍然没有信任评分、没有功绩账本，也没有工单状态机。

它提供了**闸门**，没有提供**账本**。

**OpenAI Agents SDK。**

它的可观测与安全基石是比较完整的：执行追踪、输入输出护栏、多 agent 交接。

追踪能回答"系统做了什么"，护栏能回答"越界了没有"，这两个正好对应本章的"审计通道"与"自动处置边界"。

2026 年它补上了沙箱执行，等于给出了一个**天然的动作边界**：

可控环境内放手，环境之外收紧。

差距仍然在结算侧：它没有信任评分，也没有可回溯的功绩账本。

它给出了"看见了"，没有给出"算清了"。

**LlamaIndex。**

它的路线是事件驱动的 agent 工作流，且对开放式遥测做了第一方集成，观测能力扎实。

它的评估生态偏数据层，适合回答"检索与回答质量如何"。

但治理链的另一半——工单、评分、账本——它完全没有涉及，也不打算涉及。

它是很好的**数据与知识底座**，不是治理底座。

**六框架的集体空白在哪。**

把六个放在一起看，空白的位置非常整齐。

第一处空白：**交付证据的严格性**。

各家都有"看见过程"的能力，没有一家要求"三件齐才算完成"。

业界的默认假设是"执行成功即完成"，而本训练学质疑的恰恰是这个默认假设。

第二处空白：**纠偏的制度化**。

没有任何一家框架内置工单状态机。

失败要么重试，要么抛出异常，要么进人类工单系统——但那是外部的通用工具，不是治理模型的一部分。

第三处空白：**长期表现的结算**。

信任评分与功绩账本在六框架里全部为空。

这一条在 2026 年出现了重要的**外部变化**：业界标准组织已经开始填补这个空白（详见下一专题的信任机制部分），

但要注意区分：**那是标准层的进展，不是这六个框架的能力。**

所以本章的表述必须精确：

与六大框架逐项对比，信任评分与功绩账本仍是空白；

而行业标准层（研究中被正式定义的信任评分构件、企业侧的信任分级框架）在 2026 年上半年已经开始进入这个领域。

这两句话并不矛盾，它们是两个不同层面的事实。

**这一节真正想说的。**

对位的意义不是"我们有独门武功"。

对位的意义是：**看清自己补的是哪一块，以及为什么那一块必须补。**

六大框架补的是"怎么把 agent 跑起来"，本章补的是"跑起来之后，凭什么说它做对了"。

前者是能力和基础设施，后者是秩序。

两者不是竞争关系，是上下游关系。

一个成熟的 agent 组织，会同时使用两者：

用框架做执行，用本章的制度做结算。

### 5.30 专题二 · 前沿追踪：2026 年三条线同时收紧

2026 年这个时间点上，治理领域发生了一件很有代表性的事：

**协议、标准、监管三条线在同一年朝同一个方向收紧。**

方向是什么？

让"agent 做过什么"变成可验证、可追溯、可结算的事实。

下面按线梳理。凡属公开资料口径而非本机实测的内容，一律标 ⏳。

**第一条线 · 协议：MCP 的无状态化与 A2A 的签名身份**

先看 MCP（Model Context Protocol）。

⏳ 2025 年 11 月 25 日发布的版本成为稳定基线；⏳ 2026 年 7 月 28 日的规范更新把它从"有状态、长连接"改成了"无状态、面向远程"的形态，引入了多轮往返请求机制（允许服务端在执行的中间向客户端追加索取输入，而不必维持长连接），并把授权方元数据纳入必填，同时把 Root、Sampling、Logging 等旧特性标记为弃用（配了不短于十二个月的弃用窗口）。

⏳ 治理上更大的事件发生在 2025 年 12 月 9 日：MCP 被捐给 Linux 基金会体系下的 Agentic AI 基金会（AAIF），与 goose、AGENTS.md 等项目并列，采用宽松开源许可，发行方中立。

这三件事对本章的意义是直接的。

无状态化意味着**每一次调用都是可独立审计的事件**，而不是一段需要事后重建的长连接历史。

授权元数据必填意味着**身份与授权成为协议层的一等公民**，而不是应用层的自选动作。

供应商中立意味着**治理要求可以写进架构决策**，而不必担心某家厂商改变战略。

再看 A2A（Agent-to-Agent）。

⏳ Google 于 2025 年 4 月发布，同年 6 月捐给 Linux 基金会立项；⏳ 2026 年 3 月发布首个稳定版 1.0，同年 5 月出 1.0.1；⏳ 到 2026 年 4 月，支持组织超过 150 家，主要云平台都有集成，社区在 1.2 版本里加入了**可加密签名的 Agent Card**。

Agent Card 是什么？它是 agent 自己发布的身份与能力声明：身份、端点、能力、技能、协议特性、认证要求。

一旦这张卡可以加密签名，它就从一个**自我介绍**变成了一个**可验证凭证**。

这一步对本章的启示极强，因为它把本章最核心的那条原则搬到了协议层：

> **身份声明也需要证据。**

本机当前把信任评分写进身份契约文件，这是"组织内部可信"，代价是"外部不可验证"。

A2A 的签名卡走的是另一条路：密码学可验证。

两者不冲突，但值得记下来：**当 agent 要跨组织协作时，文件契约必须升级为可验证凭证。**

这是本章未来演进的一个明确方向。

**第二条线 · 能力封装：Agent Skills 成为开放标准**

⏳ 2025 年 10 月，Anthropic 推出 Agent Skills（对用户表现为技能包）。

⏳ 2025 年 12 月 18 日，它把该规范作为公开标准发布在 agentskills.io——内容极小：一个目录、一个带 YAML 前置元数据的 Markdown 文件、加上三层渐进披露的加载架构。

⏳ 据 2026 年的公开统计，发布后 48 小时内微软与 OpenAI 就分别在自己的产品里做了支持；到 2026 年 3 月，已有三十多个工具宣称兼容，覆盖主流编码与 agent 产品；到 2026 年年中，官方展示页上的兼容产品数量约在四十个量级。

这件事和治理的关系可能超出直觉。

它给治理提供了一个**低成本、可机器判定的抓手**：技能合规率。

前置元数据缺失的技能包无法被正确加载，这是一个纯客观、可批量检查的事实。

于是"技能合规率低于阈值 → 自动开单"这条触发器，在本机是真能落地的，本机实际也吃过这个亏——历史上出现过一批技能包因缺少前置元数据而加载失败的问题。

把这条经验制度化，就是本章第十一节所讲的阈值触发器。

一个开放的、极简的能力封装标准，意外地让**技能层的治理变得可自动化**。

这是 2026 年最实用的一条前沿结论。

**第三条线 · 身份与结算：可验证凭证与信任分级**

业界的做法分成两派，都值得学。

**一派用密码学解决"你是谁"。**

⏳ AGNTCY 体系（目录服务 + 身份服务）把每个 agent 记录绑定到去中心化标识或证书身份，用公钥做签名操作，由注册机构签发可验证凭证来证明 agent 的能力与元数据；记录支持内容寻址与无密钥签名；能力声明甚至可以用零知识证明来表达，以在不泄露内部细节的前提下证明权限。

⏳ 其中最有借鉴价值的构件叫 Agent Badge：一个封装成 JSON-LD 的可验证凭证，用来精确指认"你即将调用的 agent 到底是哪个定义、哪个版本"，同一个 agent 可以携带多枚徽章。

**这件事精准回应了本章的一个薄弱环节**：本机治理能证明"某 agent 完成了某任务"，但对"当时跑的是哪个版本的它的哪一套配置"，记录能力较弱。

徽章机制给出的答案是：**把版本本身也变成可验证声明。**

**另一派用分级解决"它能干什么"。**

⏳ 2026 年 2 月，云安全联盟发布 Agentic Trust Framework，用四个以人类职业阶段命名的档位来推进信任升级，并明确设置了安全验证闸门——也就是升档前必须通过对抗性测试与验证。

⏳ 同期的研究侧也在把"信任评分"正式化：一篇关于 agentic AI 的信任、风险与安全综述把信任评分定义为一个复合指标，用于量化 agent 的可靠性、目标对齐与跨时间一致性，并在可审计性一节要求组织能够重建导致结果的事件链。

⏳ 更有意思的是两条经验结论：

一是**信任滞后**——即使 agent 的错误率已经回到基线，信任分数仍会维持一段低位，行为恢复滞后于技术恢复；

二是**时间衰减**——某些评分机制采用指数衰减，让近期行为比远期行为权重更高。

这两条直接对应本章第八节（扣分与恢复双通道）与第七节（信任评分）。

它们共同说明：**恢复通道必须设计得足够耐心，而评分需要带时间衰减，否则评分反映的是"历史总和"而不是"当前可信度"。**

本机当前的口径是加权通过率，尚未实现衰减——这是一处明确的待验证项。

**第四条线（必须提一句）· 监管：日志从"最好有"变成"必须有"**

⏳ 欧盟人工智能法案对高风险系统提出了自动事件记录要求：系统必须能够自动记录运行全生命周期的事件，日志要可追溯、要能防篡改，多数高风险系统的最低留存期为六个月，生物识别与执法场景为二十四个月；属于部署方一侧的镜像义务同样要求把日志保存在自己控制下。

⏳ 高风险义务的全面适用时点是 2026 年 8 月 2 日，罚则上限按全球营业额的比例计。

围绕这些义务，业界已经出现明确的工程化解读，其中两个词跟本章完全同构：

**防篡改**与**留存期**。

本章的自留证据链（产物 + Diff + 日志）在合规视角下，恰好就是这套日志义务的落地形态；

而"只增不改"的纪律，就是"防篡改"的最朴素实现。

差距也说清楚：本机的证据目录**尚未**加防篡改机制，也**尚未**定义留存期策略（清理什么时候可以执行、由谁批准）——这两条应作为下一阶段治理建设的明确议题。

**第五条线（工程实践）· 可观测性标准：元数据与内容的分离**

⏳ 开放式遥测的生成式 AI 语义约定（`gen_ai.` 命名空间）在 2026 年 6 月的版本中从核心语义约定仓库迁出到独立仓库，MCP 相关约定随之迁移；截至 2026 年中，这一领域整体仍处于开发状态，没有正式稳定标签；主流编码 agent 已经开始导出计量与日志，但对提示与响应**内容**的采集默认关闭，理由是隐私风险，默认只导出模型名、token 计数与耗时。

这一条对本章是一件"确认"而不是"启发"：

业界在审计层的默认选择，与本机实测的审计默认值（只留元数据）是同一个决策。

**元数据用于流程审计，内容用于质量审计**，两者分离是行业共识，不是本机的特殊性。

所以本章第 3 节的提醒可以再重申一次：

元数据流能证明"发生过"，不能证明"做对了"；完整的交付证据必须由交付方自己被留档。

### 5.31 专题三 · 诚实边界：哪些是实测，哪些是待验证

治理章节最忌讳的两件事：把设计当实现，把第三方资料当实测。

所以这里分列。

**✅ 已实测（本机事实）。**

- OpenClaw 版本：2026.9.4（提交号 3a9d69d）。
- 审计通道可用：返回事件流，事件类型覆盖 agent 运行、工具调用与消息，字段含运行标识、状态与序号。
- 审计默认只留元数据（`redaction: metadata_only`）——因此不能当完整证据链。
- 体检通道可用：`openclaw doctor --lint` 实测返回 33 项检查、20 条发现，其中 17 条为安全类告警。
- `openclaw agents health-check` **不存在**；`openclaw agents` 的子命令只有增删查绑与设置身份这一类。体检真名是 doctor 系列。
- 本机存在真实运行的功绩周结算定时任务：每周一零点（Asia/Shanghai）、由昆仑驱动、模型 `zai/glm-5.1`、结果播报至 Telegram。
- 本机 agent 的协作契约中已存在真实的违规处理分级（四档）与三级追踪协议——即工单严重度体系的野生实现。
- 本机 agent 的演进文件中已存在技能基因与军功相关的表——即功绩账本的野生实现。
- 本机配置文件中**没有**信任评分、功绩账本、账本、三证据验证这些字段。本章的治理是生态扩展（写文件 + 定时任务 + 本地数据库）与制度约定，不是平台原生开关。

**⏳ 待验证（设计口径，未经校准）。**

- 信任评分公式（0–100 加权通过率）与两个阈值（低于 50 禁 spawn、低于 30 降只读）来自本训练学的训练学口径，**本机尚未实现、尚未校准**。
- 信任评分的衰减算法（长时间无任务是否衰减、衰减常数取多少）未定。
- 恢复通道的步长与观察窗口（例如小步回升、上限回到基线）为建议值，⏳ 待实测校准。
- 功绩周结算任务内部的具体折算算法（信任增量与功绩单位如何计算）未审阅。
- 工单状态机的**强制流转**未实现；本阶段落地的是模板、目录与状态字段约定。
- 证据目录的防篡改机制与留存期策略未定义。
- 账本的解引用体检尚未挂入例行任务。

**⚠ 不得宣称（红线）。**

- 不得宣称自动处置生产是治理常态；本训练的口径是自动发现与自动开单，处置默认关闭。
- 不得把审计元数据流说成完整证据链。
- 不得把口头完成写进账本；没有证据引用的条目不得入账。
- 不得把体检总判定为假当作治理失败的证据；要逐条判断发现项是否落在本次范围内。
- 不得把第三方的版本号、star 数、兼容产品数量当成本机实测值引用；这些一律标 ⏳。

### 5.32 收束：三条不可让渡，与一句口诀

这一章讲了很多机制，但真正不能让渡的只有三条。

**第一条 · 完成必须有物证。**

没有证据的完成，只是叙述。

这一条是所有其他机制的地基；它一动摇，评分、账本、开单全部作废。

**第二条 · 修复必须被验证。**

修复不等于关闭，是这一章最反直觉、也最值钱的一条。

它防的不是恶意造假，而是**善意的自我欺骗**——而这种欺骗才是组织里最常见的失真来源。

**第三条 · 自动化必须有边界。**

发现可以自动，处置必须有人。

因为不可逆的动作没有第二次机会，而判断永远会有误差。

三条之外的所有东西，都可以按组织规模调整：

任务卡可以简化，口径可以增删，账本可以用表格起步，触发器可以只设两三个，评分可以先用最简单的加权通过率。

顺序不重要，搭起来才重要。

因为治理的价值不是"完备"，而是**开始运转**。

一个运转着的最简治理，胜过一份躺在文件夹里的完美规范。

最后，把这一章压成一句口诀——和开头第一板块的那句话首尾相扣：

> **没有证据不算完成，开单必须闭环，评分可降可升，自动只发现不处置，验收必须可判定。**

如果说训练学前面几章回答的是"它能不能干"，

那么这一章回答的只有一句话：

**它说它干完了，凭什么？**

这个问题被认真回答的组织，才配拥有一个军团。

### 步骤 2 · 必做的 3 件事

**1. 建 TEV 三证据留档（用 `openclaw audit` 当证据源）**

三证据验证（TEV / Three-Evidence Verification）要求三份证据齐：**新产物（Artifact）+ 前后 Diff + 测试日志**。本机 `openclaw audit --json` 提供真实事件流，直接作为"行动侧"证据源。

```bash
# 取某 agent 最近的 agent_run + tool_action 作为证据源
A=kunlun
openclaw audit --agent $A --kind agent_run --limit 5 --json 2>/dev/null \
  | python3 -c "import json,sys;d=json.load(sys.stdin);[print(e['runId'][:8],e['action'],e['status']) for e in d['events']]"
# 期望：形如  dd2609fc agent.run.finished succeeded / agent.run.started started

# TEV 证据留档（三件套）——把结果写进任务卡
mkdir -p ~/.openclaw/workspace/governance/tev
TASK="T-$(date +%Y-%m-%d)-001"
cat > ~/.openclaw/workspace/governance/tev/$TASK.yaml <<EOF
tev:
  task_id: "$TASK"
  artifact:
    path: "<产出文件路径>"
    sha256: "$(shasum -a 256 <产出文件> | awk '{print \$1}')"
  diff:
    paths: [<改动的文件列表>]
  test_log:
    command: "<测试命令>"
    exit_code: <0>
  evidence_source: "openclaw audit --agent $A --kind agent_run --json"
EOF
echo "✓ TEV 留档：~/.openclaw/workspace/governance/tev/$TASK.yaml"
```

> ⚠ **缺任意一项 = 任务未完成**（本章 5.1.1）。"agent 说完成"不算完成——必须有可校验产物。

**2. 落"修复工单"状态机（Remediation Ticket）——接你 AGENTS.md 里已有的 L1-L4**

修复工单状态机：`open → investigating → fixed → verified → closed`。**关键约束：fixed ≠ closed，必须 verified 才能关**（再次 TEV）。本机 kunlun 的 `AGENTS.md` 已有真实的"违规处理 L1-L4"表 + "三级追踪协议"，直接对接：

## 常见错误

> **本节用法**：第 5 章是治理章——三证据验证（TEV，原：三证验真）、修复工单（Remediation Ticket，原：整改单）、信任评分（Trust Score，原：信誉分）、功绩账本（Merit Ledger，原：军功簿）。
> 这里的 8 个错误都源于同一个根因：**把"说了做了"当"做到了"**。
>
> **实测环境**：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27 · macOS 26.5.1。

### 错误 1 · 把"说完成"当"完成"（跳过 TEV）

**错误现象**：agent（或人）报告"任务已完成"，验收方直接签字；后来发现产物不存在、或与要求不符。整个链路里没有任何"证据"环节。

**错误配置**（❌ 不要这样）：

```markdown
# 错误示范：只有口头的"完成"
任务：生成 7 契约文件
状态：✅ 完成（agent 自述）
验收：通过（我看了它说完成）
```

**为什么错**：

1. **TEV 的定义就是"没有证据不算完成"。** 本章 5.1 节：三证据 = 新产物（文件/输出）+ 前后 Diff + 测试日志。缺任一，就不算验证。
2. **agent 自述不是证据。** 第 3 章训练过"没有证据不下结论"——治理环节同理，验收方也不能靠自述。
3. **F7-5 就是这个问题的现场**："TEV 三证据验证怎么做——说完成凭什么算完成？"
4. **代价**：虚假完成的累积会导致治理系统整体失信——一旦"完成"没意义，信任评分、功绩账本全部塌陷。

**正确配置**（✅ 应该这样）：

```markdown
# 正确示范：三证据齐备才算完成
任务：生成 7 契约文件
证据 1（新产物）：ls -1 contracts/*.md | wc -l → 7
证据 2（前后 Diff）：git diff --stat → 新增 7 文件
证据 3（测试日志）：for f in SOUL...; do [ -s ... ]; done → 7/7 ✓
验收：通过（证据三件齐）
```

```bash
# 证据 3 的生成命令
for f in SOUL USER AGENTS TOOLS HEARTBEAT IDENTITY MEMORY; do
  p=~/.openclaw/workspace/agents/my-agent/contracts/${f}.md
  [ -s "$p" ] && echo "✓ ${f}.md" || echo "❌ ${f}.md"
done | tee ~/notes/domain/silicon-life-handbook/evidence/contracts-check.log
```

**验证命令**：

```bash
# 1) 证据目录里是否有三件
ls -lt ~/notes/domain/silicon-life-handbook/evidence/ | head -10

# 2) 产物是否真实存在
ls -1 ~/.openclaw/workspace/agents/my-agent/contracts/*.md | wc -l

# 3) diff 证据是否可复现
cd ~/.openclaw/workspace/agents/my-agent/contracts/ && git diff --stat
```

**相关 FAQ**：F7-5（TEV 怎么做）、F7-7（修复工单怎么建单）、F7-9（治理审计账本怎么落）。

### 错误 2 · 三证据只给一件（通常只给"新产物"）

**错误现象**：作者知道要有证据，于是只提交"新产物"（文件/输出），省掉了 Diff 和测试日志；验收方看到产物存在就通过。但产物可能是提前准备好的、或与要求不符。

**错误配置**（❌ 不要这样）：

```bash
# 错误示范：只给产物
cp prebuilt/report.md ./report.md
git add report.md && git commit -m "done"
# ❌ 没有"变化了什么"的 diff，没有"验证通过"的日志
```

**为什么错**：

1. **三证据是互相校验的。** 新产物证明"有东西"；Diff 证明"是这次做的"；测试日志证明"按要求做的"。少一件，验证就出现盲区。
2. **只给产物最容易造假**（无论是人还是 agent）。Diff 保证"改动确实发生了"。
3. **代价**：治理采购的是"可验证性"，少一件就买了假货。

**正确配置**（✅ 应该这样）：

```bash
# 正确示范：三件一起交
# ① 新产物
ls -l report.md
# ② 前后 Diff
git diff HEAD~1 --stat
# ③ 测试日志
./validate.sh 2>&1 | tee ~/notes/domain/silicon-life-handbook/evidence/report-test.log
```

**验证命令**：

```bash
# 1) 三件是否都在（产物 / diff / 日志）
ls -l report.md 2>/dev/null
git log --oneline -1 --stat
ls -lt ~/notes/domain/silicon-life-handbook/evidence/*.log 2>/dev/null | head -3

# 2) 日志是否含判定结论（不只是"运行了"）
grep -iE "pass|fail|✓|❌|通过|失败" ~/notes/domain/silicon-life-handbook/evidence/*.log 2>/dev/null | head
```

**相关 FAQ**：F7-5（TEV）、F7-9（审计账本）、F6-11（协同无日志不可追溯）。

### 错误 3 · 修复工单开了不结（无闭环）

**错误现象**：体检发现问题 → 开修复工单 → 修了一半 → 忘了 → 工单永久挂着。几个月后同样的问题再次发生，查记录发现"早在三个月前就开过单"。

**错误配置**（❌ 不要这样）：

```markdown
# 错误示范：工单无状态、无责任人、无截止
工单 #12：修 skills frontmatter 问题
（开了，没有后续）
```

**为什么错**：

1. **修复工单是"有生命周期的"，不是记事本。** 本章 5.2 节：开单 → 处置 → 复核 → 结单，每步要有痕迹。
2. **无闭环 = 治理失效。** 开单不结，等于"发现问题但不解决"，且会掩盖问题（看起来"已在处理"）。
3. **18 坏 skill 事故**（F5-2 / F5-10）本质上就是"坏了没闭环、修了没防复发"。
4. **代价**：工单堆积，治理系统变成"问题仓库"，信任崩塌。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：完整工单结构
ticket:
  id: "RT-2026-09-27-001"
  issue: "47 个 skill 缺 frontmatter"
  root_cause: "批量导入时未校验"
  owner: "engineering"
  due: "2026-09-30"
  status: "open"        # open → fixing → verifying → closed
  evidence: []          # 结单前必须有 TEV 三证据
  prevention: "CI 增加 frontmatter 校验"
```

```bash
# 落盘（治理账本）
mkdir -p ~/notes/domain/silicon-life-handbook/governance/tickets
echo '{"id":"RT-2026-09-27-001","status":"open"}' >> ~/notes/domain/silicon-life-handbook/governance/tickets.jsonl
```

**验证命令**：

```bash
# 1) 是否有长期 open 的工单
grep -h '"status":"open"' ~/notes/domain/silicon-life-handbook/governance/tickets.jsonl 2>/dev/null | wc -l

# 2) 工单是否有责任人/截止
grep -c "owner\|due" ~/notes/domain/silicon-life-handbook/governance/tickets.jsonl 2>/dev/null

# 3) 结单率
total=$(wc -l < ~/notes/domain/silicon-life-handbook/governance/tickets.jsonl 2>/dev/null || echo 0)
closed=$(grep -c '"status":"closed"' ~/notes/domain/silicon-life-handbook/governance/tickets.jsonl 2>/dev/null || echo 0)
echo "结单率: $closed/$total"
```

**相关 FAQ**：F7-7（修复工单怎么建单）、F7-8（自动触发条件）、F5-10（坏 skill 防复发）。

### 错误 4 · 信任评分只降不升（无恢复路径）

**错误现象**：agent 出一次错，信任评分被打低，此后无论表现多好都不回升；agent 长期被按低信任对待（工具受限、任务降级），能力无法发挥。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：单向扣分
trust_score:
  penalty_on_error: true
  recovery: none        # ❌ 无恢复机制
```

**为什么错**：

1. **信任评分是"动态结算"，不是"污点记录"。** 本章 5.3 节 + F7-4："Trust Score 失信 / 信誉分下降，怎么结算与恢复"——恢复是评分机制的组成部分。
2. **无恢复路径会导致"能力永久封印"**：一个被误伤的 agent 永远无法回到高信任档。
3. **代价**：治理从"纠偏"退化为"惩罚"，团队会规避开单（怕扣分），反而掩盖问题。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：扣分 + 恢复双通道
trust_score:
  penalty_on_error: true
  recovery:
    method: "连续 N 次 TEV 全通过 + 无返工"
    window: "30 天"
    step: "+0.5 档 / 月（上限回到基线）"
  floor: 1              # 最低档，不低于
```

**验证命令**：

```bash
# 1) 是否有恢复规则
grep -nE "recovery|恢复" ~/.openclaw/workspace/agents/my-agent/contracts/IDENTITY.md \
  ~/notes/domain/silicon-life-handbook/governance/*.md 2>/dev/null | head

# 2) 信任分历史是否有上升段（不只是下降）
grep -h "trust_score" ~/notes/domain/silicon-life-handbook/governance/ledger.jsonl 2>/dev/null | tail -20

# 3) 当前档位与 IDENTITY 是否一致
grep -n "trust_tier" ~/.openclaw/workspace/agents/my-agent/contracts/IDENTITY.md
```

**相关 FAQ**：F7-4（信任评分结算与恢复）、F7-9（审计账本）、F7-11（主动性档位）。

### 错误 5 · 功绩账本只记流水，不记证据链

**错误现象**：账本里记着"某 agent 完成 30 个任务"，但每个任务的证据（产物/diff/日志）从未留存；被质疑时无法自证。

**错误配置**（❌ 不要这样）：

```jsonl
{"agent":"my-agent","task":"生成报告","result":"done","score":+1}
```
（❌ 无证据引用，无法验证）

**为什么错**：

1. **功绩账本的价值在"可回溯"。** 术语表 #12：Merit Ledger（功绩账本）；本章 5.4 节要求每条记录可回到 TEV 三证据。
2. **只记流水 = 无法审计。** 一旦出现争议，无法判断"这个 done 是真的吗"。
3. **代价**：账本变成记分牌，失去治理意义；信任评分失去依据。

**正确配置**（✅ 应该这样）：

```jsonl
{"agent":"my-agent","task":"生成 7 契约","result":"done","evidence":["contracts/*.md","diff:abc123","log:contracts-check.log"],"score":+1,"ts":"2026-09-27T10:00:00Z"}
```

```bash
# 每条记录的 evidence 必须可解引用
jq -r '.evidence[]' ~/notes/domain/silicon-life-handbook/governance/ledger.jsonl | head
```

**验证命令**：

```bash
# 1) 账本记录是否含 evidence 字段
jq -r 'select(.evidence==null) | .task' ~/notes/domain/silicon-life-handbook/governance/ledger.jsonl 2>/dev/null | head
# 期望：无输出（= 无缺证据记录）

# 2) 证据引用是否真实存在
jq -r '.evidence[]?' ~/notes/domain/silicon-life-handbook/governance/ledger.jsonl 2>/dev/null | while read e; do [ -e "$e" ] || echo "❌ 缺失: $e"; done

# 3) 账本行数与任务数一致性
wc -l ~/notes/domain/silicon-life-handbook/governance/ledger.jsonl 2>/dev/null
```

**相关 FAQ**：F7-9（治理审计账本）、F7-5（TEV）、F6-11（协同无日志）。

### 错误 6 · 治理靠人肉发现（无自动触发）

**错误现象**：所有问题都靠某个细心的人"发现"；一旦人忙起来没人看，问题就长期潜伏。

**错误配置**（❌ 不要这样）：

```markdown
# 错误示范：治理流程依赖"人工巡检"
每周看一眼，发现问题就开单。
```

**为什么错**：

1. **治理要"自动触发"。** F7-8 明确："整改单自动触发条件怎么配（不靠人肉发现）"。
2. **人肉不可靠也不可扩。** 人越忙越漏，agent 越多越漏。
3. **代价**：能力矩阵 26 天未续期，正是"没有自动触发"的典型后果。
4. **真实案例**：F7-15（能力矩阵月度更新 cron 连续失败，红了没人管）。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：阈值 → 自动开单
auto_remediation:
  triggers:
    - condition: "skills_compliance < 0.95"
      action: "open_ticket(severity=high)"
    - condition: "capability_matrix_age_days > 7"
      action: "open_ticket(severity=critical)"
    - condition: "heartbeat_success_rate < 0.99"
      action: "open_ticket(severity=high)"
```

```bash
# 把触发器挂进心跳（自动巡检 + 自动开单草稿）
# HEARTBEAT.md on_wake：
#   - "检查 capability_matrix 更新时间，>7 天则开单（草稿，不自动提交）"
```

**验证命令**：

```bash
# 1) 触发器是否配置
grep -nE "triggers|auto_remediation|condition" ~/.openclaw/workspace/agents/my-agent/contracts/*.md

# 2) 自动开单是否留痕
grep -h "auto" ~/notes/domain/silicon-life-handbook/governance/tickets.jsonl 2>/dev/null | tail -5

# 3) 实测一次触发
ls -l ~/notes/domain/silicon-life-handbook/**/capability-matrix* 2>/dev/null | head -3
```

**相关 FAQ**：F7-8（自动触发）、F7-15（连续失败没人管）、F7-6（能力矩阵续期）。

### 错误 7 · 自动化治理无边界（越权自动处置）

**错误现象**：为了"自动化"，作者让治理流程自动执行处置动作（自动改配置、自动重启、自动回滚生产）；一次误判导致生产被改坏。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：自动处置无边界
auto_remediation:
  auto_fix: true
  scope: ["production"]     # ❌ 直接动生产
  require_review: false
```

**为什么错**：

1. **自动化治理必须有边界。** 本章 5.5 节 / 卷六模块 6："自动化治理边界——没有边界就没有安全"。
2. **自动处置是 L3 级动作**（对应第 4 章主动性三档），默认应关闭，且需逐条授权。
3. **误判不可避免**：触发器可能误报，自动处置会把误报放大成事故。
4. **代价**：不可逆的生产损坏。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：自动"发现 + 开单"，不自动"处置"
auto_remediation:
  auto_detect: true
  auto_open_ticket: true          # 自动开单（草稿）
  auto_fix: false                 # ❌ 处置必须人工确认
  review_required: true
  scope: ["workspace"]            # 只允许动工作区，不碰生产
```

**验证命令**：

```bash
# 1) 是否有"自动处置生产"的危险配置
grep -nE "auto_fix: true|scope:.*production" ~/.openclaw/workspace/agents/my-agent/contracts/*.md
# 期望：无输出

# 2) 人工确认环节是否存在
grep -n "review_required\|人工确认" ~/.openclaw/workspace/agents/my-agent/contracts/*.md

# 3) 实测：触发一次自动开单，确认未执行处置
openclaw agent --message "运行一次自动巡检，只开单不处置" --agent my-agent 2>&1 | head -20
```

**相关 FAQ**：F7-8（自动触发）、F7-11（主动性边界）、F3-6（越界）。

### 错误 8 · 验收口径模糊（"基本完成"）

**错误现象**：验收时用"基本上完成了""大体没问题"这类模糊措辞；出问题时双方各执一词。

**错误配置**（❌ 不要这样）：

```markdown
# 错误示范：模糊验收
验收结论：基本完成，剩下的小问题下次再说。
```

**为什么错**：

1. **验收口径必须可判定。** 本章 5.2 节 / 术语表 #25（Acceptance Criteria）：验收口径要像"通过率 ≥ 90%"一样可量化。
2. **模糊口径 = 无口径**：双方对"基本完成"理解不同，必然扯皮。
3. **代价**：返工、争议、信任损耗；TEV 三证据也无从"判定通过与否"。

**正确配置**（✅ 应该这样）：

```markdown
# 正确示范：可判定的验收口径
| 验收项 | 口径 | 当前 | 判定 |
|---|---|---|---|
| 7 契约文件齐备 | = 7 | 7 | ✅ |
| 每文件非空 | ≥ 1 行 | 7/7 | ✅ |
| compaction 真名命中 | ≥ 1 处 | 2 处 | ✅ |
| 术语无黑话残留 | = 0 | 0 | ✅ |
结论：全部通过（4/4）
```

**验证命令**：

```bash
# 1) 验收项是否可量化
grep -cE "\|.*(≥|=|≤).*\|" ~/notes/domain/silicon-life-handbook/evidence/acceptance-*.md 2>/dev/null

# 2) 是否存在模糊措辞
grep -rniE "基本完成|大体|差不多|应该没问题" ~/notes/domain/silicon-life-handbook/ 2>/dev/null | head
# 期望：无输出

# 3) 验收结论是否含数字
grep -n "通过" ~/notes/domain/silicon-life-handbook/evidence/acceptance-*.md 2>/dev/null | head
```

**相关 FAQ**：F7-5（TEV）、F7-3（体检）、F6-15（三省评审制）。

## 新手坑

> **本节用法**：本章的坑都围绕"信任与证据"展开——新人最容易做的是"看起来完成了"。
> 下面 6 个坑，每个含五段式。
>
> **提示**：本章最小落地 = "每个任务留三件证据 + 开单必闭环"。

### 坑 1 · 以为"提交了就算完成"

**坑的场景**：新人把文件 `git push` 或把消息发出去，就宣告"搞定了"；从不验证产物是否符合要求。

**后果**：

- **虚假完成**：产物可能有错、可能不全（F7-5）。
- **信任损耗**：一旦被发现"提交了但不对"，后续验收都会加码。
- **治理塌陷**：如果"完成"可以随口说，信任评分与功绩账本全部失效。

**为什么踩**：

1. **"提交"有即时反馈（命令成功），"达标"没有**。
2. **不知道 TEV 三证据**（本章 5.1）。
3. **缺少"自己先验一遍"的习惯**。

**怎么爬出来**：

```bash
# 第 1 步：给每个交付物补三证据
ls -l <产物>                                     # ① 新产物
git diff --stat HEAD~1                           # ② 前后 Diff
./validate.sh 2>&1 | tee evidence/check.log      # ③ 测试日志

# 第 2 步：把三件放进 evidence/ 目录，作为交付附件
mkdir -p ~/notes/domain/silicon-life-handbook/evidence
```

**预防**：

- **规则：没有三证据，不许说"完成"**。
- **把 TEV 写进 AGENTS.md 的交付标准**。
- **真实案例参照**：F7-5、F7-9。

---

### 坑 2 · 把信任分当 KPI 刷

**坑的场景**：新人发现信任评分与"任务数"正相关，于是拼命接小任务刷数量，不接有风险但有价值的难题。

**后果**：

- **指标被游戏化**：账本记满"小而稳"的任务，避开了真正的问题。
- **治理目标偏离**：评分的目的是纠偏，不是计件。
- **能力不增长**：agent 永远停在舒适区。

**为什么踩**：

1. **"分数可优化"的直觉**——凡是数字都会被优化。
2. **评分规则未设"难度/风险加权"**。
3. **缺少"是否解决真问题"的验收维度**。

**怎么爬出来**：

```bash
# 第 1 步：给评分加"问题价值"维（不只看数量）
# 账本每条增加 value: {difficulty, risk, impact}
jq -c '. + {value:{difficulty:1,risk:1,impact:1}}' ledger.jsonl > ledger.tmp && mv ledger.tmp ledger.jsonl

# 第 2 步：评审时抽查"高分是否对应高价值任务"
jq -r 'select(.value.impact >= 3) | .task' ledger.jsonl | head
```

**预防**：

- **评分加权（难度 × 影响）**，不单纯计件。
- **定期评审"是否在解决真问题"**（三省评审制，第 6 章）。
- **真实案例参照**：F7-4、F7-9、F6-15。

---

### 坑 3 · 修复工单只写现象不写根因

**坑的场景**：发现 skill 加载失败，工单只写"skill 不生效"，没写"为什么"；下次换个人处理，从头排查。

**后果**：

- **重复排查**：每次都要重走一遍诊断路径。
- **治标不治本**：修了现象，根因还在（F5-10）。
- **无法防复发**：没有根因，就写不出预防措施。

**为什么踩**：

1. **现象最直观好写**，根因要花力气。
2. **不知道工单结构应有 root_cause 与 prevention 字段**。
3. **急着修，不想分析**。

**怎么爬出来**：

```bash
# 第 1 步：给工单补根因与预防
jq '. + {root_cause:"缺 frontmatter",prevention:"CI 校验"}' tickets.jsonl > t && mv t tickets.jsonl

# 第 2 步：用"5 Why"追问到根因
# 现象→为什么→为什么→...→根因（通常 3–5 层）
```

**预防**：

- **工单必含 root_cause + prevention**，缺任一不算规范工单。
- **预防措施要落进 CI/心跳**，否则等于没写。
- **真实案例参照**：F5-2（缺 frontmatter）、F5-10（防复发）、F7-7。

### 坑 4 · 治理账本放在会话里

**坑的场景**：新人把治理记录（开单、结单、评分变动）都留在对话里，没有落盘；会话一压缩，治理历史归零。

**后果**：

- **审计断链**：无法回溯"某次评分为什么变"。
- **不可交接**：换人接手时，历史只在某个已消失的会话里。
- **不可复盘**：季度复盘时无数据。

**为什么踩**：

1. **"对话里记着就行"的错觉**（会话易失，第 2 章）。
2. **不知道治理账本要落盘为文件**（术语表 #16 Governance Audit Ledger）。
3. **没有固定路径的习惯**。

**怎么爬出来**：

```bash
# 第 1 步：立刻建账本文件
mkdir -p ~/notes/domain/silicon-life-handbook/governance
: > ~/notes/domain/silicon-life-handbook/governance/ledger.jsonl

# 第 2 步：把现有会话里的治理事件补录（尽力而为）
echo '{"ts":"'$(date -u +%FT%TZ)'","event":"ledger-init","note":"从今日起落盘"}' \
  >> ~/notes/domain/silicon-life-handbook/governance/ledger.jsonl
```

**预防**：

- **治理事件当轮落盘**（写进 AGENTS.md 操作纪律）。
- **账本纳入备份**。
- **真实案例参照**：F7-9、F6-11、F4-15。

### 坑 5 · 自动化处置直接上生产

**坑的场景**：新人尝到自动化的甜头，把"发现问题 → 自动修复 → 自动重启"整条链路都自动化，且直接作用于生产环境。

**后果**：

- **误判放大**：一次误报触发的自动修复可能造成生产事故。
- **不可逆**：自动回滚/重启可能丢数据。
- **责任不清**：出了事，"是脚本干的"。

**为什么踩**：

1. **"自动化 = 先进"** 的偏好。
2. **不知道自动化治理需要边界**（本章 5.5 节）。
3. **没出过事故，缺少敬畏**。

**怎么爬出来**：

```bash
# 第 1 步：立即关闭自动处置，改为自动开单
# auto_fix: false ; scope: ["workspace"] ; review_required: true

# 第 2 步：生产环境加"人工闸门"
# 所有生产变更必须经人工确认 + 备份
openclaw backup create
```

**预防**：

- **自动"发现+开单"，不自动"处置"**。
- **生产变更三道闸**：人工确认 + 备份 + 可回滚。
- **真实案例参照**：F7-8、F3-6、F7-11。

### 坑 6 · 验收口径口头约定

**坑的场景**：任务开始前双方"聊清楚了"，没有写成文字；交付时对"是否符合要求"理解不一，开始扯皮。

**后果**：

- **返工**：重做一遍。
- **争议**：无据可依。
- **信任损耗**：下次合作要先"立规矩"。

**为什么踩**：

1. **口头沟通快**，写下来显得反复。
2. **以为"聊得很清楚"就是"明确"**。
3. **缺少"先写口径，再开工"的纪律**。

**怎么爬出来**：

```bash
# 第 1 步：补写验收口径（可量化）
cat > ~/notes/domain/silicon-life-handbook/evidence/acceptance-$(date +%Y%m%d).md <<'EOF'
| 验收项 | 口径 | 判定 |
|---|---|---|
| 7 契约齐备 | = 7 | |
| 每文件非空 | ≥ 1 行 | |
EOF

# 第 2 步：双方确认（git commit 作为"签字"）
```

**预防**：

- **任务卡 + 验收口径先行（术语表 #24/#25）**。
- **口径必须可判定**（含 ≥/=/≤）。
- **真实案例参照**：F7-5、F6-15（三省评审制）、F6-11。
