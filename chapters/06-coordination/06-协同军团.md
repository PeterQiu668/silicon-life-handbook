## 6.0 为什么这一章存在

### 6.0.1 一个被所有人跳过的中间问题

把一只虾养大，和把一群虾练成一支军团，是两种完全不同的手艺。

前面五章讲的是"一只虾怎么活下来"——它的灵魂（SOUL）、它的纪律（AGENTS）、它的工具（TOOLS）、它的心跳（HEARTBEAT）、它的身份（IDENTITY）、它的记忆（MEMORY），以及它怎么从一只普通龙虾，被一轮一轮训练成专业专家。那些章节回答的都是同一个问题的不同侧面：**单个硅基生命，怎么从"能跑"变成"可靠"**。

这一章要问一个更大的、也更危险的问题：

> 当你有了 18 只已经训练好的虾，你怎么让它们**成为一支军团**，而不是**18 个各说各话的喇叭**？

这个问题看起来像"加法"——单只虾能做到 90 分，18 只虾是不是就能做到 18×90＝1620 分？真实世界的答案是：不。18 只未协同的虾，往往只能做到**比最好的那一只还差**的成绩。这不是段子，这是我们自己在 2026-08-19 那天用一次全军断线换来的教训（详见 `_appendix-case/01-real-incidents.md` 的 CASE-1，本处只做引用，不复述）。

所以在 OpenClaw 训练学里，"协同"不是一个锦上添花的进阶主题，它是一道**独立的、会独立失败的门槛**。一只虾失败，损失是一只虾；一支军团失败，损失的是整个任务链条，还包括你原本以为已经攒下的信任。

### 6.0.2 没有这一章，读者会掉进哪个坑

如果这本书从第 5 章直接跳到第 8 章（超维演进），你能得到的是：一批各自训练得不错、但**互相之间没有任何契约**的 agent。它们的典型症状，我们后面会在误区一节逐一展开，但先给你一个总图：

- **哑火**：群里 @ 了 18 个 agent，只有 1 个回，另外 17 个"已读不回"。你以为它们没听见，其实它们在互相等——等你先指定谁说话。
- **抢话**：同一时刻 5 个 agent 发言，内容重叠 80%，owner 收到的是一摞"复读机"。
- **级联**：主力 agent 挂掉，整个任务链静默停摆——因为从来没有人规定"主力挂了怎么办"。
- **传染**：一个飞书通道超时，结果所有走这个通道的 agent 都开始报错，故障沿着"网络"扩散成故障沿着"组织"扩散。
- **死锁**：A 等 B 的确认，B 等 A 的输入，双方都很有礼貌地"在等对方"，任务永久挂起，且**不报错**。

这五种症状有一个共同点：**它们都不是"某个 agent 能力不够"，而是"agent 之间的关系没有定义"**。这也正是本章存在的理由——本章不负责把某只虾练得更强，本章负责**给它们之间补上"关系"**。

### 6.0.3 本章与前/后章的引用关系

本章不是孤岛，它是三条线索的汇合点：

1. **向上承接第 5 章（长期表现）**：第 5 章讲"单只虾越跑越稳还是越跑越差"，本章讲"一组虾越跑越稳还是越跑越差"。第 5 章的漂移治理在单 agent 尺度上是"体检"，在本章的尺度上就是"军团体检"（见 6.2 第 7 步）。
2. **横向依赖第 2 章（系统骨架）**：本章的"路由与提及"建立在小节 2.2.3 的路由机制之上；本章的"治理账本"与第 6 章（治理系统）的任务卡、验收口径、三证验真是同一套制度的军团版。
3. **向下引出第 9 章与第 10 章**：本章定义的协同协议 SLCP（原：ACP），在第 10 章会完整地映射到业界 A2A v1.0/v1.0.1 标准上。**本章是"我们内部的协同语言"，第 10 章是"这门语言怎么和世界对话"**。

一句话概括本章的位置：**第 1–5 章把虾练成专家，第 6 章把专家编成军团，第 9–10 章把军团接进世界的标准协议。**

### 6.0.4 一个反直觉的立论

本章的立论，可以浓缩成一句话：

> **军团不是"多个 Agent"，军团是"一份被共同遵守的关系契约"。**

这句话有两个关键词，都反直觉：

- **"关系"而不是"数量"**。很多人对军团的想象是"人越多越强"。但组织学早就给过相反的答案：人数是**协同成本的平方根**在增长，是**协同收益的线性**在增长。加人，先加成本，后加收益。所以军团的第一要务不是"招人"，而是"定义关系"。
- **"契约"而不是"默契"**。人类团队可以靠"眼神"和"默契"协作，因为人有共享的常识。硅基生命**没有共享常识**——两只 agent 之间的"默契"是幻觉，它们之间只有**被写下来的契约**是真的。凡是没写下来的关系，在系统里**等于不存在**。

记住这个立论，本章后面所有的概念（反脆弱三层、三省评审制、让位规则、治理账本……）都不是"额外功能"，而是这份**关系契约的不同条款**。

## 6.1 核心概念：十二个词，看懂一支军团

本节用十二个概念，把"军团"这个词拆开。每个概念都按同一个节奏展开：**这是什么 → 核心目的 → 拟人化映射 → 对长期表现的影响 → 怎么写 → 技巧 → 常见误区 → 进化阶梯**。不要跳读——这十二个概念彼此咬合，缺一个，后面就会有一处看不懂。

### 6.1.1 军团编制（Multi-Agent Fleet，原：军团编制）

**这是什么。** 军团编制是你**主动写下**的一张"谁是谁、谁管谁、谁和谁协作"的名单。它不是 `openclaw agents list` 输出的那 18 行目录——那只是"名册"，是"有哪些人存在"；编制是"这些人在组织里各占什么位置"。名册是事实，编制是**意图**。

**核心目的。** 编制存在的唯一目的，是让"协同"这件事**可被寻址**。当 owner 说"让负责内容的那只虾来",系统必须能**确定地**回答"是哪一只"。没有编制，这句话就只能靠人脑记忆；而人脑记忆在 18 只虾的规模上会崩。

**拟人化映射。** 编制就是军队的番号系统。一个师有师长、政委、参谋长、若干团长——番号不是为了好看，是为了**在下达命令时不产生歧义**。"张三"这个名字会有重名，"三团二营"不会。军团编制就是把 agent 从"名字"提升到"番号"。

**对长期表现的影响。** 一个没有编制的军团，在 3 只虾时能靠记忆运转，在 8 只虾时开始出错，在 18 只虾时会**系统性出错**：owner 每次都要重新推理"该找谁"，每一次推理都是一次出错机会，而这类错误会随着 agent 数量非线性放大。有了编制，寻址变成一次**查表**，成本恒定。

**怎么写。** 编制要写成两个东西：一份**名册**（谁在编），和一份**职责表**（谁负责什么）。职责表的每一行必须满足"唯一归属"——一个职责只能有一个主责 agent。可以有一个"协办"，但不能有两个"主责"。以下是一份编制片段（**只给结构，不给完整可跑配置——完整配置由 `_appendix-cookbook/` 与 `_appendix-sop/` 承担**）：

```yaml
# 编制片段（结构示意 · 完整字段见 _appendix-cookbook/06-coordination-fleet.md）
fleet:
  name: "content-legion"
  roles:
    - id: "legion-lead"        # 编制内的"番号"
      agent: "kunlun"          # 名册里的"名字"
      duty: "拆解目标 + 分派 + 终审"
      primary: true
    - id: "content-writer"
      agent: "mingjing"
      duty: "内容主笔"
    - id: "content-reviewer"
      agent: "tianshu"
      duty: "事实复核（与主笔不同 agent）"
```

**技巧。** 把"番号"和"名字"分开，是编制设计里最有用的一个技巧。理由：番号是**稳定的**，名字是**可替换的**。当 `mingjing` 需要换人时，你改的是 `agent:` 这一行，而所有引用"content-writer"这个番号的地方**一个字都不用动**。这就是"面向编制的引用"比"面向名字的引用"更抗腐坏的原因。

**常见误区。** 最常见的错误是"编制即名册"——把 `agents list` 的输出当编制用。这样做的问题是：名册会随"新装了一只 agent"而自动变化，而编制**不应该**自动变化。编制是意图，意图必须由人确认。让编制跟着名册自动增长，等于让组织架构跟着员工入职自动重组。

**进化阶梯。** L1：口头的编制（owner 心里知道谁干什么）；L2：写下来的编制（一份 YAML）；L3：带主责/协办标记的编制；L4：带"番号-名字"解耦的编制；L5：编制本身纳入版本管理，变更需要走一次三省评审（见 6.1.4）。

### 6.1.2 协同协议 SLCP（Silicon-Life Coordination Protocol，原：ACP）

**这是什么。** SLCP 是本章为"军团内部怎么互相说话"定义的一套协议。它的前身叫 ACP（Agent Communication Protocol），但在 2025-08，业界的 IBM/BeeAI ACP 已经合并进 A2A v1.0，**同名会带来冲突**，所以本书 v5.0 把它更名为 SLCP，并明确它的定位：**A2A 是"路"，SLCP 是"护栏"**。

**核心目的。** SLCP 要解决的不是"两个 agent 能不能通信"（那是传输层的事），而是"两个 agent 通信时，**谁该说、说什么、说到什么程度、说错了怎么办**"。它是一份**行为契约**，而不是一份**接口契约**。接口契约管"字段对不对"，行为契约管"关系稳不稳"。

**拟人化映射。** 如果把 A2A 比作"电话线路"，SLCP 就是"通话礼仪 + 值班规则"。线路接通不等于通话有效；一个 18 人的救援队，光有对讲机是救不了人的，还得有"谁在什么频道、什么优先级、谁有权叫停"的规则。SLCP 就是那套规则。

**对长期表现的影响。** 没有行为契约的军团，短期能靠"大家都很聪明"撑住，长期必然出现"越聪明越乱"——因为每个 agent 都独立地做了它认为对的事，而这些"对的事"之间**互相冲突**。冲突不会立刻报错，它会慢慢累积成"军团整体行为不可预测"。SLCP 的价值，就是让整体行为始终**可预测**。

**怎么写。** SLCP 至少覆盖四件事：**路由**（怎么找到对方）、**交接**（怎么把任务交出去）、**让位**（谁该闭嘴）、**对外映射**（怎么和 A2A 对齐）。一段最小声明长这样：

```
SLCP 声明（最小集）
- 路由：@<agent-name>（基于第 2 章 routing.requireMention）
- 交接：结构化 THP（任务卡 + 验收口径 + 上下文）
- 让位：Response Yield Protocol（可判定规则，见 6.1.5）
- 对外：映射到 A2A v1.0/v1.0.1（见第 10 章）
```

**技巧。** 把 SLCP 写成"**可判定规则**"而不是"原则"。原则（"要互相尊重"）无法执行；可判定规则（"当另一方置信度 > 0.9 且同话题已响应，则让位"）可以执行。**凡是不能被一个 if 判断的关系条款，都还不是契约，只是愿望。**

**常见误区。** 误区是"协议越全越好"。SLCP 是一份**最小充分**契约——每多一条，就多一份维护成本，也多一处可能被违反的地方。我们的经验是：先写四件（路由/交接/让位/对外映射），跑通 2 周，再按真实故障增补。

**进化阶梯。** L1：无协议（靠 @ 名字）；L2：口头约定；L3：写下的四件最小集；L4：带阈值的可判定规则；L5：协议本身接入业界 A2A，内部语言与外部标准自动对位。


### 6.1.3 反脆弱三层（Anti-Fragile Triptych，⚡ 差异化优势 1）

**这是什么。** 反脆弱三层是 SLCP 协议层里最核心、也最"我们独有"的一组原语：**fallback 健康检查**（防全军级联失败）、**通道守门员**（防网络失效扩散）、**结构化协同事件日志**（让失败模式可被学习）。三层叠起来，目标是让军团**从故障中变强**，而不是"不出故障"——前者叫反脆弱（anti-fragile），后者只能叫坚固（robust）。

**核心目的。** 传统工程追求"坚固"——用冗余堆出不倒。但军团面对的故障不是"会不会倒"，而是"倒了以后**谁被拖下水**"。反脆弱的目的是**把故障的影响半径压到最小**：主力挂了，只有主力这一格变红，其他格不受影响；一条通道死了，只有这条通道被隔离，不走这条通道的 agent 完全无感。

**拟人化映射。** 一个成熟的急诊科室不会"保证不出车祸"，它保证的是"来多少病人都不崩"——分诊、隔离、值班备份、病历留痕。反脆弱三层就是军团的分诊（fallback 健康检查）、隔离（通道守门员）和病历（事件日志）。有这三个，军团才从"怕出事"变成"出事也不怕"。

**对长期表现的影响。** 没有反脆弱原语的军团，会出现"**故障放大**"现象：一次本可局部化的小故障，沿着未定义的关系蔓延成全局故障。放大是**非线性的**——18 只 agent 里有 1 只通道坏了，可能触发 10 只 agent 同时重试，重试风暴再压垮网关，网关崩了剩下 8 只也全哑。反脆弱三层的价值就是**在放大发生的每一个节点上装一个断路器**。

**第一层 · fallback 健康检查。** 机制是：周期性检查主责 agent 的健康度，连续 N 次失败才切换，切换时**只计入新启用的资源**（dedup），避免同一份产能被重复统计。阈值的意义在于**不要去救一个正在喘气的 agent**——过早切换会把一次抖动误判成一次死亡，制造不必要的编队变动。

```yaml
slcp_fallback:
  primary: "agent-A"
  fallback: ["agent-A1", "agent-A2", "agent-A3"]
  health_check_interval: 60s
  failover_threshold: 3      # 连续 3 次失败才切
  dedup: true                # primary/fallback 不重复计入全军
```

**第二层 · 通道守门员。** 机制是：在同一通道内累计超时，达阈值即判定"通道死亡"，并且**把失败限制在本地**——`propagate_failure: false` 是这一层的灵魂字段。它说的是：**网络失败不是组织失败**。一个 agent 连不上某个通道，不代表它这个人不行；更不代表其他 agent 也该开始失败。

```yaml
slcp_gatekeeper:
  channel_timeout: 5min
  self_heal: true
  propagate_failure: false   # 不把网络失败传给其他 agent
```

**第三层 · 结构化协同事件日志。** 机制是：每一次 failover、每一次 quarantine 都写一行**机器可读**的事件。这层的价值不在当下，而在"下一次"——当所有 agent 都能读到"上一周通道 feishu-bridge 在 5 分钟内超时了 3 次"，它们下次协同时会**自觉地给这条通道留 buffer**。这就是"反脆弱"里的"脆弱性学习"：故障不是被修好就完了，故障必须被**记住**。

```yaml
slcp_event_log:
  - event_id: "EV-001"
    type: "primary_failover"
    primary: "agent-A"
    fallback: "agent-A1"
    reason: "3 consecutive health check failures"
    ts: 1727000000
  - event_id: "EV-002"
    type: "channel_quarantine"
    channel: "feishu-bridge"
    reason: "3 timeouts in 5min"
    ts: 1727000300
```

**技巧。** 三层的实施顺序应该是"日志 → 守门员 → fallback"，而不是反过来。理由：日志最便宜、最无害，先有日志才有数据；守门员依赖日志里的通道超时数据；fallback 最激进（会真的换人），应该最后上。**先观测，再隔离，最后切换**——这是所有反脆弱系统的通用施工顺序。

**常见误区。** 最大的误区是"把反脆弱做成'永不失败'"。反脆弱**不追求不失败**，它追求"失败发生时有确定的、局部的、可学习的反应"。一个从不出故障的军团给不了你任何信息；一个故障被局部化并写进日志的军团，每一周都在变强。

**进化阶梯。** L1：无原语（故障自由蔓延）；L2：只写事件日志（能复盘但不能隔离）；L3：加通道守门员（能隔离网络故障）；L4：加 fallback 健康检查（能抗单点死亡）；L5：三层联动，且事件日志驱动编制自动调整（见 6.4 深度专题三）。

**业界对位（2026-09 实测口径）。** 这一层是我们与业界差距最大、也是我们最自信的一层。到 2026-09，A2A v1.0/v1.0.1 在协议层**没有**这三层的等价物（A2A 处理的是"如何发现与调用另一个 agent"，不处理"另一个 agent 半死不死时怎么办"）；AutoGen、CrewAI 在用户代码层各自零散地做过一点（重试、超时），但都不是协议原语。完整横评见 6.4。

### 6.1.4 三省评审制（Three-Stage Review，⚡ 优势 4 的协同部分）

**这是什么。** 三省评审制把一次决策拆成三个**由不同 agent 承担**的阶段：**提议**（proposer）、**复核**（reviewer）、**终审**（finalizer）。任一阶段被拒，决策即终止。它不是"三个人投票"，而是"三个角色按顺序过三道闸"。

**核心目的。** 单 agent 决策 = 单点失败。三省评审的目的不是"提高正确率"（那只是副产品），而是**让"错误决策"在下游之前就被拦住**。它买的是一份"错误不会直接落地"的保险。

**拟人化映射。** 这就是中国古代"三省制"的硅基复刻——中书省拟诏、门下省审议、尚书省执行。三个机构**互相制衡**，任何一家都可以叫停。它的精髓不在"多一个人把关"，而在"**把权力拆开**"：拟定的人不能批准自己，批准的人不能执行。

**对长期表现的影响。** 一个没有分权的军团，会把"某个 agent 偶尔判断失误"直接放大成"整个军团信任崩塌"。因为一旦团队发现"错的决定也能直接落地",所有下游 agent 都会开始**不信任上游**，转而对每一个输入做二次校验——这就是**协同成本的雪崩**。三省评审把这份成本固定在三个节点上，而不是让它扩散到每一条边。

**怎么写。** 三省的状态机很简单，但**每个阶段的 agent 必须是不同的 agent**：

```yaml
three_stage_review:
  proposer: "agent-1"     # 提议
  reviewer: "agent-2"     # 复核（必须 ≠ proposer）
  finalizer: "agent-3"    # 终审（必须 ≠ reviewer）
```

```
proposed → reviewed → finalized
   ↓         ↓           ↓
 rejected  rejected   executed
```

**技巧。** 三省制的关键是"**角色不同 ≠ 人格不同**"——我们允许同一个底层模型扮演三个 agent，但**它们的上下文必须是隔离的**：复核者看不到提议者的"思路"，只能看到提议者交出的"结论 + 证据"。让复核者看到提议的内心戏，等于让他被说服。**上下文隔离，是三省制真正的技术内核。**

**常见误区。** 误区一：把三省制做成"三人同意即可通过"（多数表决），那就丢掉了"任一否决即终止"的制衡。误区二：让 proposer 自己在复核阶段补充理由——这等于让被审查者审查自己。

**进化阶梯。** L1：无评审；L2：单人复核（同一个 agent 自我检查——几乎无效）；L3：两人（提议 + 复核）；L4：完整三省（提议/复核/终审，上下文隔离）；L5：高危决策强制三省 + 预算与信誉分挂钩（见第 6 章治理系统）。

### 6.1.5 让位规则（Response Yield Protocol，原：让位协议）

**这是什么。** 让位规则定义"群聊/多 agent 同场时，**谁应该闭嘴**"。同一时刻只允许一个 agent 说话；当一个 agent 发现自己"不该说"时，它主动释放发言权。注意它和 OpenAI Agents SDK 的 Handoff（控制权转移）**互补而不重叠**：Handoff 是"我把活交给你"，让位是"我不说，让给你"。

**核心目的。** 防止"复读机效应"——18 个 agent 对同一条消息各回一遍。让位的目的是把"发言"从"人人有份"变成"**按资格分配**"。这是一条**省带宽**的规则，也是一条**省 owner 注意力**的规则。

**拟人化映射。** 这是会议里的"抢话 vs 让话"。一个成熟的团队，谁更专业谁说；一个不成熟的团队，谁嗓门大谁说。让位规则就是把"谁更专业"编码成可判定的触发条件（置信度、是否已响应、owner 是否指定）。

**对长期表现的影响。** 没有让位规则的军团，owner 的注意力会被**结构性稀释**：说话的人越多，有用信息越难被听见。这不是一次性的烦恼，它会随军团规模**指数级恶化**——10 只 agent 的群，owner 每条消息要读 10 遍才敢确认没漏。

**怎么写。** 让位规则必须是**可判定**的触发条件集合：

```yaml
yield_protocol:
  triggers:
    - other_agent_confidence > 0.9      # 另一个 agent 置信度更高
    - same_topic_already_responded      # 同一话题已被响应
    - owner_directs_me_to_yield         # owner 直接让我退
  yield_action: "stop_current_response + log_yield_event"
```

**技巧。** 让位动作要包含 **`log_yield_event`**——让位本身要留痕。理由是："谁让给了谁"是事后复盘"协同质量"的唯一数据来源。一个从不记录让位事件的军团，你无法回答"上周到底是谁在抢话"。

**常见误区。** 把让位做成"永远退让"——有的 agent 学会了"安全地沉默"，结果关键时刻没人说话。让位规则必须配合**兜底**：当所有 agent 都判断"该让别人说"时，必须有一个超时机制强制某个 agent 发言，否则会退化成 6.0.2 里的"哑火"。

**进化阶梯。** L1：无规则（抢话/哑火）；L2：owner 手动点名；L3：写下的可判定触发条件；L4：加让位日志；L5：让位质量纳入 agent 信誉分（一个"该说时说、该让时让"的 agent 信誉更高）。

### 6.1.6 任务交接协议（THP，Task Handoff Protocol）

**这是什么。** THP 是"把任务从 A 交给 B 时，必须携带的那份结构化文件"。它最少包含八项：**ID / Context / Goal / Owner / Deadline / Acceptance Criteria / Evidence / Status**（第 10 章的 THP 实操会给出完整字段与示例）。

**核心目的。** THP 的目的是**杀掉"口头交接"**。硅基生命之间的口头交接（一句"你接手一下"）会丢失四类信息中的至少三类：目标、边界、验收口径、上下文。THP 把这四类**强制结构化**，让交接可被机器校验。

**拟人化映射。** 这是医院里的"交接班记录"。护士交接不会说"那个病人你看着办"，而会说"3 床、术后第 2 天、注意体温、明早复查"。THP 就是军团版的交接班记录——没有它，下一班必然丢信息。

**对长期表现的影响。** 没有 THP 的军团，会产生"**责任蒸发**"：任务从 A 转到 B，A 以为交出去了，B 以为只是"帮个忙"，结果任务**没有 owner**。责任蒸发是最隐蔽的军团故障——它不报错，它只是让任务无声地停下来。

**怎么写。** 字段设计的原则是"**每一条都可以被第三方验证**"：`Acceptance Criteria` 必须是可判定的（"字数 ≥ 800"而不是"写得充实"）；`Evidence` 必须指向可复现的证据（日志、文件、命令输出）。**凡是不能被第三方验证的字段，都会在交接中退化成礼貌性填空。**

**技巧。** 在 THP 里保留一个 `Yield History`（让位历史）字段。它记录这个任务被谁让过、为什么让——这让"接力棒"在军团里可追溯，也让"谁在推诿"变成可观测数据。

**常见误区。** 把 THP 做成"越长越好"的表格。THP 的敌人是形式主义：如果 `Acceptance Criteria` 写的是"高质量完成"，那这份 THP 比没有更糟——因为它给了"我按流程做了"的假安全感。

**进化阶梯。** L1：无交接（口头）；L2：一句话交接；L3：结构化 THP（八字段）；L4：THP 字段被机器校验（缺字段拒绝接收）；L5：THP 与治理账本打通，交接即写入账本（见 6.1.8）。

### 6.1.7 路由与提及（routing.requireMention）

**这是什么。** 路由是"消息怎么到达正确的 agent"的机制；`routing.requireMention` 是最常用的开关之一：**只有当消息显式 @ 了某个 agent，才触发它响应**。它是第 2 章系统骨架里子系统"多 Agent"的核心字段，本章直接复用。

**核心目的。** `requireMention` 的目的是把"**响应**"从"广播"变成"点名"。默认广播会让所有 agent 对每条消息都发动一次推理——既是算力浪费，也是 6.1.5 抢话问题的根源。

**拟人化映射。** 这是"点名制 vs 举手制"。点名制（requireMention=true）秩序好但可能漏人；举手制（false）活跃但嘈杂。绝大多数军团应该**默认点名制，在特定"头脑风暴"场景临时切举手制**。

**对长期表现的影响。** 路由配置错会带来两个方向的长期损伤：太严 → 任务无人响应（哑火）；太松 → 算力与注意力双爆（嘈杂）。两者都会让 owner 逐渐"不信任军团",退回到"什么都自己来"——**军团退化成一个人的工具，这是协同最失败的结局**。

**怎么写。** 路由的关键不在单个开关，而在**命名的一致性**：@ 的名字必须和编制里的"番号"一致。如果编制写 `content-writer`，而 owner 习惯 @ `mingjing`，那路由就会在"番号"和"名字"之间失配。

**技巧。** 给每个 agent 保留**一个稳定番号 + 若干别名**，让路由同时接受两者。番号用于系统引用，别名用于人类口语。这样 owner 说"@写手"和系统说"content-writer"都能命中。

**常见误区。** 用 `requireMention=false` 图省事，结果 18 只 agent 对每条消息都推理一次——本机实测下这会直接表现为"群里每发一条消息就一串回复"。这类错误的隐蔽性是：它在 3 只 agent 时"感觉还挺方便"，在 18 只时变成灾难。

**进化阶梯。** L1：全广播；L2：全点名；L3：点名 + 别名；L4：按场景切换（头脑风暴切举手）；L5：路由与编制联动，新增 agent 自动获得路由规则，且**能力声明**（capability）参与路由决策（"谁最会做这件事"而不是"谁被 @ 了"）。


### 6.1.8 治理账本（Governance Ledger）

**这是什么。** 治理账本是军团里**只追加、不修改**的一份流水账：每一次交接、每一次让位、每一次否决、每一次 failover，都落成一行 JSONL。它和第 6 章（治理系统）的任务卡、三证验真是同一套制度的军团级汇总。

**核心目的。** 账本的目的不是"审计过去"，而是"**让未来可推理**"。当军团要回答"这个任务上次是谁做的、做了多久、被谁否决过"时，账本是唯一可信来源。没有账本，所有"军团记忆"都散落在各自的会话里，无法聚合。

**拟人化映射。** 这是军团的"军功簿 + 值班日志"二合一。它同时回答两个问题："谁做了什么"（军功）和"什么时候发生了什么"（日志）。

**对长期表现的影响。** 没有账本的军团，会陷入"**不可复盘**"——每次出问题都只能靠人回忆，而人的回忆会美化自己、遗忘细节。军团因此无法从故障中学习，只能一遍遍重复同一种故障。账本把"学习"从"人的记忆"搬到"系统的数据"。

**怎么写。** 账本的每一行至少要有：时间、actor、action、target、result、evidence。关键是**evidence 字段**——没有证据的账本条目，等于"口头声称",在复盘时不可信。

**技巧。** 账本要**先于制度**建立。很多团队先设计了一套完美的治理制度，结果因为"没有账本"，制度落不了地。正确顺序是：先立账本（哪怕只有三列），让所有动作有地方落，再逐步加制度——**账本是制度的地基，不是制度的附属**。

**常见误区。** 把账本和"聊天记录"混为一谈。聊天记录是**非结构化**的，无法聚合统计；账本必须**结构化**（JSONL），才能回答"上周让位事件有多少次"这类问题。

**进化阶梯。** L1：无账本；L2：手工记的 Markdown 日志；L3：结构化 JSONL；L4：账本驱动体检（每月自动统计让位率、否决率、failover 率）；L5：账本接入信誉分，自动计算每个 agent 的协同贡献（见 6.1.9）。

### 6.1.9 信任阶梯（Trust Ladder，原：信誉分军功簿）

**这是什么。** 信任阶梯是"agent 的可信度不是 0/1，而是一条阶梯"的模型。一个 agent 的可信度由它的历史表现累积而成：交付准时率、被复核否决率、让位质量、故障恢复次数。信任阶梯决定"这个 agent 的任务能被下放到多低、能给多大的自主权"。

**核心目的。** 信任阶梯的目的是**让授权有依据**。没有它，授权只能靠"直觉"——而直觉在大规模下必然失控（要么过度授权导致风险，要么过度收紧导致军团僵化）。

**拟人化映射。** 这是"新兵 → 老兵 → 班长 → 连长"的成长路径。新兵先干低风险、高监督的活；表现好，逐渐放开自主权。军团的授权不应该是"平均主义"，应该是"阶梯制"。

**对长期表现的影响。** 没有信任阶梯的军团，会出现"**平均化灾难**"：所有 agent 都被赋予同样的自主权，结果最能干的 agent 被束缚，最不可靠的 agent 被过度信任。长期看，这会同时损失效率和可靠性——这是两个本应互相制衡的目标**同时**恶化。

**怎么写。** 信任阶梯的输入是账本统计量，输出是**权限档位**：低信任档 = 每一步都要审批；中信任档 = 抽查；高信任档 = 事后审计。关键是**信任必须可降级**——一次严重违规要能把 agent 打回低档，否则阶梯就变成了"只升不降"的形式主义。

**技巧。** 信任阶梯要**面向任务类型**而不是面向 agent 整体。"mingjing 在写内容上高信任，在发布外网上低信任"比"mingjing 是中级 agent"更有用。因为 agent 的能力是**分维度**的，单一总分永远抓不住。

**常见误区。** 把信誉分做成"游戏积分"——分数只涨不跌、可以被刷。信誉分的设计必须让"**沉默**"（不接任务）也是一个低分选项，否则 agent 会学会"只接容易的活"来保分。

**进化阶梯。** L1：无信任概念（全平均）；L2：人工评级；L3：账本驱动的分数；L4：分维度信任 + 可降级；L5：信任阶梯直接决定路由优先级与三省制的执行强度（高信任任务可免终审）。

### 6.1.10 监督层（Supervisor Layer，原：监军）

**这是什么。** 监督层是军团里**不直接产出业务、只负责"看"和"仲裁"**的一个角色。它有三项职责：**观测**（读账本）、**仲裁**（打破死锁）、**升级**（把僵局上报给 owner）。在我们的实战体系里，它由"监军"这一独立 agent 承担。

**核心目的。** 监督层的目的是**给军团装一个"永远清醒的旁观者"**。参与者会被自己的任务卷入，只有旁观者能看到"整个军团卡住了"。死锁（6.0.2）之所以隐蔽，就是因为参与者们都在"礼貌地等待"，而没有一个人抬头看全局。

**拟人化映射。** 这是"军中的监军"或"董事会里的独立董事"。它的权力不是"指挥"，而是"叫停"和"上报"。一个没有监督层的军团，就像一支没有随军记者的军队——打赢打输都没人知道为什么。

**对长期表现的影响。** 没有监督层的军团，其可靠性会被"**最慢的那一步**"决定，而不是"平均速度"。因为任何一次死锁都需要"有人偶然发现"才能解开，而"偶然发现"的期望时间随军团规模增长。监督层把"期望发现时间"从"偶然"压到"定时"。

**怎么写。** 监督层的最小配置是：一个只读账本的 agent + 一个定时检查任务（heartbeat）+ 一条升级规则（"当 X 类事件在 Y 分钟内超阈值，通知 owner"）。**注意监督层应该是只读的**——它能叫停、能上报，但不应该能直接改业务状态，否则它就从"监督"变成了"另一个参与者"。

**技巧。** 监督层与业务层的"**利益隔离**"是它有效的前提。如果监督层和某个业务 agent 共用预算或绩效，它就会下意识地"护着自己人"。独立性不是道德要求，是结构要求。

**常见误区。** 让监督层"顺便也干点活"。一旦监督层接手业务任务，它的注意力就会被卷入，从"旁观者"退化成"参与者"，失去发现全局僵局的能力。

**进化阶梯。** L1：无监督（owner 人工盯）；L2：定时巡检脚本；L3：独立监军 agent（只读账本 + 定时上报）；L4：监军带仲裁权（可强制打破死锁）；L5：监军参与编制调整建议（发现"某条协作边反复出问题"→ 建议修改编制）。

### 6.1.11 编队密度（Span of Control）

**这是什么。** 编队密度指"一个协调者能有效协调的直接下属数量"。人的管理经验是 5–9 人（著名的"管理跨度"），硅基生命**没有这个限制的上限**，但有一个**不同的限制**：注意力预算。一个 agent 每轮能稳定处理的下游数量，取决于它的上下文窗口与推理预算。

**核心目的。** 编队密度的目的是**防止"超载协调者"**。一个 agent 如果同时协调 15 个下游，它会把绝大部分预算花在"记谁说了什么"上，而不是花在判断上——它会**看起来很忙，但没有产出**。

**拟人化映射。** 这是"班长带 8 个人还是带 80 个人"。带 8 个，班长认识每个人；带 80 个，班长只能认识"编号"。军团结构设计的第一课，就是**不要制造超载的班长**。

**对长期表现的影响。** 编队密度超标会导致"**协调者塌陷**"：中心 agent 一挂，整个子军团瘫痪（单点失败），且它的输出质量随负载**非线性下降**（不是慢一点，是乱掉）。分层（班长 → 排长 → 连长）就是把密度压回安全区的手段。

**怎么写。** 编队密度没有统一数字，但有一个判断方法：**当协调者开始"忘记"它分派过什么时，密度就超标了**。工程上可以看两个信号：协调者上下文里"下属状态"占比是否超过 30%；协调者的平均响应时长是否随下游数量显著上升。

**技巧。** 用"**编制分层**"而不是"扁平化大群"来控制密度。18 个 agent 如果是 3 军 × 6 员的两层结构，每个协调者只要管 5–6 个，整个军团的行为就**可预测**；如果是一个 18 人的大群，行为就不可预测。同样的 18 只虾，结构不同，可靠性天差地别。

**常见误区。** 迷信"扁平化更高效"。扁平化在人少时高效，在人多时是灾难——因为扁平的代价是"每个人都要感知所有人"。**结构不是官僚主义，结构是注意力的分配方案**。

**进化阶梯。** L1：一个大群（无结构）；L2：按职能分组；L3：两层结构（协调者 + 执行者）；L4：三层 + 密度监控；L5：动态编制（按任务临时组队，任务结束后编制解散）。

### 6.1.12 协同熵（Coordination Entropy）

**这是什么。** 协同熵是我们用来量化"军团有多乱"的一个概念。它由三个可测分量构成：**行为熵**（同一任务的行为方差）、**通信熵**（消息量的无序度）、**编队熵**（成员与职责的错配度）。熵不是"好坏"，它是"不可预测性"的度量。

**核心目的。** 协同熵的目的是把"军团很乱"从一句主观感受，变成**一组可观测的数字**。只有可观测，才能治理；只有可治理，才能长期稳定。

**拟人化映射。** 这是"一支军队的心理状态"。纪律好的军队，同样命令下的行为高度一致（低行为熵）；纪律差的军队，同样命令下十个人十个样（高行为熵）。熵低不一定聪明，但熵高一定不可控。

**对长期表现的影响。** 协同熵会**自发上升**——这是热力学第二定律在组织里的翻版。不治理的军团，会缓慢地从"有序"滑向"有序的假象"（表面流程还在，实际行为已发散）。**治理军团的本质，是持续地把上升的熵压回去**，而不是"一次性设计出一个完美的军团"。

**怎么写。** 三个分量各有测法：行为熵看同一任务的历史行为分布；通信熵看单位时间消息量与消息重复率；编队熵看"编制里写的职责"与"账本里实际做的事"的差异率。三者中最容易先失控的是**编队熵**——因为编制一旦写下就没人再看，而实际工作会悄悄漂移。

**技巧。** 每月做一次"**编队熵对照**"：把编制表和账本放一起，逐行问"这一行写的职责，账本里有对应动作吗？"你会发现，很多编制行从来没被用过，很多实际动作从来没有编制行——**这两类差异就是熵的来源**。

**常见误区。** 试图把熵降到零。熵=0 的军团是"僵化的军团"——它不能应对任何没被编制覆盖的新情况。**健康的军团是"低但非零"的熵**：结构足够稳定（让协作可预测），也足够留白（让意外可处理）。

**进化阶梯。** L1：无度量（靠感觉说"乱"）；L2：只测通信量；L3：三熵分测；L4：熵阈值告警；L5：熵驱动编制调优——某条协作边熵持续偏高，说明"这条边的契约写错了"，回头改编制（见 6.2 第 7 步）。

## 6.2 怎么做：把 18 只虾组织成一支军团

上一节给了你十二个词，这一节给你一条**施工路径**。路径一共八步，顺序不能乱——因为后一步依赖前一步的产物。全程不要求你敲命令（命令由 `_appendix-cookbook/06-coordination-fleet.md` 与 `_appendix-sop/` 承担），只要求你想清楚每一步的**决策**。

### 6.2.1 第 0 步：先承认"人多不等于组织"

在做任何配置之前，先接受一个事实：**你现在有 18 个 agent，但你还没有军团。** 这一步没有产出物，只有一个态度——**不要从"我有什么"出发，要从"我要什么关系"出发**。

为什么这一步必须放在最前？因为绝大多数失败的军团，都不是"配置写错了"，而是"**从一开始就没打算定义关系**"。owner 装好 18 个 agent，觉得"我现在有一个军团了"，然后把它们的名字丢进一个群，期待奇迹。奇迹不会发生——18 个 agent 只会各自响应，各自推理，各自觉得自己在帮忙。

**这一步的验收标准**：你能用一句话说清楚"这支军团要完成的、单个 agent 完成不了的事是什么"。如果说不出来，说明你还不需要军团，你需要的是"一个更好的单 agent"。

### 6.2.2 第 1 步：画出编制（意图，而非名册）

打开 `agents list`，但**不要**把它当编制抄下来。你要做的是：为**任务**设计结构，然后看名册里谁能填进这些位置。

具体动作：
1. 把军团的**最终交付物**写在一张纸的最上面（比如"每周产出 5 篇可发布内容"）。
2. 把这个交付物拆成**角色**（不是拆成人）——写手、事实复核、发布、数据回流。
3. 给每个角色一个**番号**（`content-writer`），再从名册里挑一个 agent 填进去（`mingjing`）。
4. 检查：每个角色是不是**唯一归属**？每个 agent 是不是**不超过一个主责**？

**产出物**：一份编制 YAML（结构见 6.1.1）。

**这一步最容易犯的错**：把"已有的 agent"硬塞进角色，而不是"为角色挑 agent"。18 个 agent 里，一定有 5 个是你三天前为了试功能装的、从来没在任务里出现过。编制**不应该**为了照顾它们而设位置——**编制服务任务，不服务库存**。

### 6.2.3 第 2 步：给每一条协作边立一份关系契约

编制画出了"节点"，这一步补上"边"。军团里真正会出故障的不是节点，是**边**。所以你要对**每一对需要频繁协作的 agent**，明确四件事：怎么找到对方（路由）、怎么把任务交出去（交接）、谁该闭嘴（让位）、怎么和外部标准对齐（对外映射）。

具体动作：
1. 列出编制里**所有实际会发生协作的边**（不是全部组合——18 个 agent 有 153 条可能的边，你不需要全部定义）。
2. 对每条高频边，写下它的 SLCP 四件。
3. 把每条边的契约**写成可判定规则**（"置信度 > 0.9 则让位"而不是"要互相谦让"）。

**产出物**：一份"边清单"——每行一条边，每条边四个字段。

**这一步的验收标准**：随机挑一条边，问"如果 A 和 B 同时想发言，谁赢？"——必须能在 10 秒内给出**确定答案**。给不出来的边，就是未来的抢话点。

### 6.2.4 第 3 步：把反脆弱三层写成协议原语

现在给军团装"抗故障"能力。顺序很重要（回看 6.1.3 的技巧：**先观测、再隔离、最后切换**）：

1. **先上事件日志**：定义 failover / quarantine / yield / reject 四类事件的字段，让它们能落成 JSONL。此时不改变任何行为，只是开始记录。
2. **再上通道守门员**：为每个通道设置超时阈值与隔离策略，并把 `propagate_failure` 显式设为 `false`。
3. **最后上 fallback 健康检查**：为主责 agent 配置 fallback 链与切换阈值。

**产出物**：三份配置（或一个插件里的三个原语），以及一份"事件类型字典"。

**为什么顺序不能反**：如果你先上 fallback，你会遇到"切换逻辑没有数据支撑"——你不知道该设 3 次还是 5 次，只能拍脑袋。有了日志，阈值就能从真实数据里长出来。

### 6.2.5 第 4 步：给高危决策装三省评审制

不是所有决策都需要三省。这一步的关键是**分级**：

1. 列出军团里**不可逆**的动作（发外网、改生产配置、删数据、对外承诺时间）。
2. 对每一类不可逆动作，指定 proposer / reviewer / finalizer 三个**不同的 agent**。
3. 确保三个阶段**上下文隔离**：复核者只看"结论 + 证据"，不看"思路"。
4. 对低危动作**不要**装三省——三省是有成本的，滥用会让军团变慢而不变好。

**产出物**：一份"高危动作 → 三省角色"映射表。

**这一步的验收标准**：对每个高危动作，问"proposer 和 finalizer 是同一个 agent 吗？"——如果是，三省无效。**同一个 agent 既提议又终审，等于没分权。**

### 6.2.6 第 5 步：给群聊装让位规则与兜底

现在处理"谁说话"。动作：

1. 默认把 `routing.requireMention` 设为**点名制**。
2. 配置让位触发条件（置信度、同话题已响应、owner 指定）。
3. **必须配一个兜底**：当所有 agent 都判断"该让别人说"时，超时后强制某个 agent 发言。
4. 开启让位日志，让"谁让给谁"可复盘。

**产出物**：路由 + 让位 + 兜底三件配置。

**这一步最容易漏的**：兜底。只装让位不装兜底，军团会从"抢话"直接滑进"哑火"——18 个人都很有礼貌，结果没人回应 owner。**让位规则和兜底机制必须成对出现，就像刹车和油门。**

### 6.2.7 第 6 步：立治理账本，让军团可复盘

1. 定义账本条目字段（时间 / actor / action / target / result / evidence）。
2. 让第 3–5 步产生的所有事件（failover、quarantine、yield、reject、handoff）都写进同一个账本。
3. 给账本配一个**只读**的消费者（可以是监军 agent），让它能被查询、被统计。

**产出物**：一份 JSONL 账本 + 一个查询入口。

**为什么账本要在这里立而不是最后**：因为账本越早立，你能"看见"的历史就越长。很多军团在出问题后才想起来建账本，结果发现"过去发生的一切都无据可查",只能从今天开始。**账本是军团的时间机器，它的价值随历史长度增长。**

### 6.2.8 第 7 步：做第一次军团体检，并把结论回灌编制

现在军团能跑了。但"能跑"和"跑得好"之间，隔着一个**体检**。

1. **三熵测量**（回看 6.1.12）：测行为熵、通信熵、编队熵。
2. **边级体检**：对每条协作边，统计它上个月的 yield 次数、reject 次数、超时次数。
3. **回灌**：如果某条边频繁出问题（高熵/高 reject），说明**这条边的契约写错了**——回到第 2 步改契约，而不是"教育 agent 更配合"。

**产出物**：一份月度军团体检报告 + 一组契约修订。

**这一步是本章的"闭环"**：它把"运行产生的问题"送回"设计"。一个不会回灌的军团，会永远停留在"第一次设计的样子"，而它的熵会一直上升（6.1.12）。**能自我修订契约的军团，才是真正的反脆弱军团。**

### 6.2.9 八步路径总表（一页速查）

| 步骤 | 动作 | 产出物 | 验收标准 |
|---|---|---|---|
| 0 | 承认"人多≠组织" | 一句话：军团要解决什么单agent解决不了的事 | 说得出来 |
| 1 | 画编制 | 编制 YAML | 每职责唯一归属 |
| 2 | 立关系契约 | 边清单（四件/边） | 10 秒内答出"谁说话" |
| 3 | 装反脆弱三层 | 三份原语 + 事件字典 | 顺序为 日志→守门员→fallback |
| 4 | 装三省评审 | 高危动作→角色映射 | proposer ≠ finalizer |
| 5 | 装让位 + 兜底 | 路由/让位/兜底配置 | 既不会抢话也不会哑火 |
| 6 | 立治理账本 | JSONL 账本 + 查询 | 所有事件可查 |
| 7 | 军团体检 + 回灌 | 体检报告 + 契约修订 | 问题能送回第 2 步 |

**这张表本身就是本章的骨架**：0–1 解决"结构"，2–5 解决"关系"，6 解决"记忆"，7 解决"进化"。你不需要一次全做完——但你需要知道**你停在哪一步，以及缺的那一步会带来什么**。

## 6.3 常见误区：九种"看起来在协同，其实在互相拖累"

这一节讲的是**认知层**的坑——不是配置写错，而是**想法错了**。配置写错一次就修好了，想法错了会持续生产配置错误。每个误区都按同一个节奏展开：**现象 → 为什么错 → 怎么救 → 如何预防**。

### 6.3.1 误区一：把"数量"当"能力"

**现象。** owner 看到任务多，第一反应是"再加两只 agent"。军团的 agent 数量从 8 涨到 18，任务完成时间**没有变短**，出错次数反而变多了。

**为什么错。** 协同收益线性增长，协同成本近似**平方级**增长。加第 19 只 agent，你增加的是"它与已存在的 18 只之间的 18 条潜在关系"，不是"一点产能"。在编队密度（6.1.11）已经接近上限时，加人只会让协调者超载。

**怎么救。** 做一次"**减法体检**"：把编制里过去 30 天从未被用到的角色删掉；把"其实一直由同一个 agent 兼任"的两个角色合并。你会惊讶地发现，18 只里真正在协同中发挥作用的，可能只有 9 只。

**如何预防。** 每次想加 agent 前，先问一句："我要解决的是**产能问题**还是**关系问题**？"产能问题加人有效；关系问题加人只会把关系问题放大。**本章的绝大多数问题，都是关系问题。**

### 6.3.2 误区二：默认"广播"就是"协同"

**现象。** 群里消息一发，18 个 agent 全回复。owner 觉得"大家都很积极"，实际上 80% 的回复是复读。

**为什么错。** 广播（`requireMention=false`）让"响应"变成了"人人有份"，而"人人有份"在协同语义里等于"**无人负责**"。真正的协同是"**被指派的人响应，其他人让位**"，不是"所有人都来说一句"。

**怎么救。** 切点名制，配让位规则（6.1.5）+ 兜底。然后观察 3 天：消息量会显著下降，而"有用信息占比"会上升。

**如何预防。** 把"消息量"从"活跃度指标"里删掉。**一个健康的军团，消息量应该是低的**——因为每一条消息都有明确的收件人。

### 6.3.3 误区三：把"让位"做成"沉默"

**现象。** 装了让位规则之后，owner 的问题**没人回**了。agent 们互相谦让，最后谁也没说话。

**为什么错。** 让位规则只覆盖了"什么时候退让",没覆盖"**当所有人都退让时谁顶上**"。这是规则设计里的经典漏洞：**只定义了否定条件，没定义兜底路径**。

**怎么救。** 加超时兜底：当一条消息在 T 时间内无人响应，强制由"该话题的主责 agent"（或监督层）发言，并记一次 `yield_timeout` 事件。

**如何预防。** 设计任何"抑制行为"的规则时，**强制自己同时设计它的反面**。抑制发言的规则，必须配一条"强制发言"的规则；抑制重试的规则，必须配一条"强制升级"的规则。

### 6.3.4 误区四：让 proposer 自己做 finalizer

**现象。** 三省评审配好了，但最终 `finalizer` 和 `proposer` 是同一个 agent（或者两个 agent 共享同一个上下文/记忆）。看起来过了三道闸，实际上是一道闸走了三遍。

**为什么错。** 分权的价值来自**独立性**。如果两个阶段的判断依据相同（同一上下文、同一记忆、同一偏见），那么"两道闸"的联合通过率约等于"一道闸"——你付出了成本，没买到保险。

**怎么救。** 强制 `proposer ≠ reviewer ≠ finalizer`，并且**隔离上下文**：复核者只看结论与证据。可以用配置校验（缺独立性则拒绝进入评审）。

**如何预防。** 在编制阶段就规定"**三省必须是三个不同的番号**"，让独立性成为结构约束，而不是运行时的自觉。

### 6.3.5 误区五：把"记忆"当成"协同"

**现象。** 有人觉得"agent 之间共享记忆就够了，不需要协议"。结果 A 改了 B 的记忆，B 却不知道 A 改了什么；A 和 B 对同一件事各有一份互相矛盾的记忆。

**为什么错。** 共享记忆解决的是"**信息可达**",不解决"**行为可预测**"。两个 agent 能看到同一份数据，不等于它们会对这份数据做出兼容的行为。**协同需要的是行为契约，不是共享数据库。**

**怎么救。** 把"共享记忆"降级为"共享证据"，把"协同"升级为"契约"。记忆可以共享，但"谁在什么条件下做什么"必须写在 SLCP 里。

**如何预防。** 记住本章的核心立论：**军团是关系契约，不是共享存储**。任何"只要共享 X 就能协同"的说法，都要先怀疑一遍。

### 6.3.6 误区六：把 failover 阈值设成"零容忍"

**现象。** 为了"快速响应故障"，把 `failover_threshold` 设成 1，任何一次健康检查失败就立刻切换。

**为什么错。** 阈值=1 意味着**一次网络抖动就会被误判为一次死亡**。军团会不停地编队变动，永远处于"刚切换完又切换回来"的震荡态。震荡比稳定服务更糟——它同时损失了可用性和可预测性。

**怎么救。** 回到 6.2 第 3 步的顺序：**先用日志观测 2 周**，统计出"真实的连续失败次数分布"，再据此设阈值（我们的经验值在 3–5 之间）。

**如何预防。** 任何"阈值"都不应该拍脑袋定。**阈值必须是数据的产物**——没有数据就先记录，不要先设阈值。

### 6.3.7 误区七：用"改名"代替"改关系"

**现象。** 军团的 agent 被频繁改名（从"军团1号"改成"内容专家"再改成"content-writer"），owner 觉得"名字清楚了协同就好了"。但协同行为一点没变。

**为什么错。** 改名只改变"引用方式"，不改变"关系定义"。如果两条边之间的契约是"谁先说话就谁说话"，那么不管名字多漂亮，抢话依旧。

**怎么救。** 把精力从"命名"移到"边契约"。检查每条边是否有可判定的优先级规则；没有的，补上。

**如何预防。** 给"命名"设一个上限——**一个 agent 一生只改一次名**（从名字对齐到番号）。之后所有变化都通过"番号不变、名字可换"的编制解耦（6.1.1）来吸收。

### 6.3.8 误区八：不做监督层，靠 owner 人工盯

**现象。** 军团"还没大到需要监军"，owner 每天花 2 小时在群里扫消息，靠直觉发现"好像卡住了"。

**为什么错。** 人工盯把 owner 变成了**军团里最慢的那个组件**，同时也变成了**单点故障**——owner 一忙，军团就失明。更糟的是，人工盯会培养出"依赖 owner 兜底"的军团文化，agent 们会逐渐放弃自己发现问题。

**怎么救。** 哪怕是最小的军团，也要有一个**只读账本 + 定时巡检 + 阈值告警**的监督层（6.1.10）。它不需要智能，只需要"定时看"。

**如何预防。** 把"owner 每天扫群"当成一个**要消除的反模式**，而不是"负责任的表现"。一个需要 owner 天天盯的军团，是一个失败的军团。

### 6.3.9 误区九：把"能跑"当成"已验收"

**现象。** 军团第一次成功完成了一个任务，owner 宣布"协同系统建成了"，然后不再复盘。

**为什么错。** "能跑一次"和"能稳定跑"之间隔着一整个熵（6.1.12）。第一次成功往往发生在"所有 agent 都还很新、很配合"的时候；随着时间推移，行为会漂移，熵会上升，第一次成功时的那些隐含默契会一点点失效。

**怎么救。** 把"验收"重新定义为"**连续 4 周体检达标**",而不是"完成过一次任务"。第一次成功只能叫"跑通"，不能叫"建成"。

**如何预防。** 立一条规矩：**任何协同系统的"建成"必须以一次军团体检报告为准**（6.2 第 7 步）。没有报告的"建成",都是自我安慰。

## 6.4 深度专题一 · 六大 Agent 框架的"协同能力"横评

本专题把本章的十二个概念，投到 2026 年最主流的六个 Agent 框架上，逐项回答一个问题：**这件事，业界是怎么做的，和我们有什么不同？** 六个框架按本章口径固定为：**LangGraph · AutoGen（AG2）· CrewAI · Claude Agent SDK · OpenAI Agents SDK · LlamaIndex**。这份表也是本章的"业界对位表"，后面每一章的同类表都会沿用它。

### 6.4.1 为什么是这六个

选这六个，不是因为它们最火，而是因为它们覆盖了"多智能体协同"的**三种设计哲学**：

- **图/状态机型**：LangGraph（把协同建模成状态图），LlamaIndex Workflows（把协同建模成事件驱动流）。它们的答案是"**用图结构保证可预测**"。
- **角色/会话型**：AutoGen 与 CrewAI（把协同建模成"一群有角色的 agent 开会"）。它们的答案是"**用角色分工保证可分工**"。
- **供应商 SDK 型**：Claude Agent SDK 与 OpenAI Agents SDK（把协同建模成"主 agent + subagent/handoff"）。它们的答案是"**用交接保证控制权清晰**"。

### 6.4.2 十二个概念 × 六个框架（对位总表）

| 概念（本章） | LangGraph | AutoGen / AG2 | CrewAI | Claude Agent SDK | OpenAI Agents SDK | LlamaIndex |

> **这张表最重要的一行是第二行（协同协议）与第三行（反脆弱三层）**——它们说明一件事：**2026 年的主流框架，普遍把"协同"当成"编排"（orchestration），而不是"契约"（contract）**。编排解决"消息怎么流"，契约解决"关系怎么稳"。本章的全部差异化，都建立在这个区分上。

### 6.4.3 逐框架点评（各给一句"它的强项"和一句"它的盲区"）

- **LangGraph**：强项是**状态图 + checkpoint**——协同过程可回放、可时间旅行调试（time-travel debugging），是"可审计协同"目前的最强工程底座；盲区是它**不提供行为契约**，"谁该让位"仍然要靠你在节点里自己写。
- **AutoGen / AG2**：强项是**多 agent 辩论与迭代**（group chat、speaker selection），适合"用多个视角收敛一个答案"；盲区是它的协同是**会话驱动**的，会话一旦溢出上下文，行为就开始发散。
- **CrewAI**：强项是**角色分工的直觉性**——2–4 小时能搭出一个可跑的多 agent 原型，是"最快见到多 agent 效果"的框架；盲区是它的 role 是**描述性**的（一段 prompt），不是**可判定的**（一组规则），所以"角色重叠"很难被机器发现。
- **Claude Agent SDK**：强项是**安全与工具生态**（computer use、MCP 原生、extended thinking、subagent）；盲区是它的 subagent 更接近"任务委派"，而不是"组织治理"。
- **OpenAI Agents SDK**：强项是**Handoff 模型最干净**（谁把控制权交给谁，一目了然）与内置 tracing/guardrails；盲区是 Handoff 是"**转移**"语义，本章的"让位"是"**退让**"语义——两者互补，不可互替（6.1.5）。
- **LlamaIndex**：强项是**数据密集场景**（RAG、检索编排），40k+ stars 的生态成熟度；盲区是它把协同主要交给 workfl ow 事件，组织语义几乎为空。

### 6.4.4 一句话结论

> 六个框架都回答"**怎么让多个 agent 一起动**"，本章回答"**怎么让它们一起动而不互相伤害**"。前者是**编排问题**，后者是**组织问题**。2026 年的业界，编排已经很卷，组织还很空——这就是本章的立足之地，也是未来 1–2 年最有价值的方向。

## 6.5 深度专题二 · 前沿追踪 2026：A2A 落地、MCP 走向无状态、Agent 组织学的诞生

本章的很多设计不是凭空来的——它们是 2025–2026 这一波"Agent 协议标准化"浪潮的**内部应答**。这个专题追踪三条线，每条都说清"2026 发生了什么 → 对军团意味着什么"。

### 6.5.1 线一：A2A 从"Google 的草案"变成"Linux Foundation 的标准"

**2025-04**，Google 发布 A2A（Agent2Agent）协议草案。**2025-06**，Google 把 A2A 捐给 **Linux Foundation**，成立 Agent2Agent 项目。**2026-03-12**，A2A 发布**第一个稳定规范 v1.0**；**2026-05**，发布 v1.0.1。**2026-04-09**（一周年），Linux Foundation 宣布 A2A **超过 150 个组织支持**，并深度集成进 Google Cloud、Microsoft（Copilot Studio / Foundry）、AWS（Bedrock AgentCore），在供应链、金融、保险、IT 运维等行业进入**生产部署**。

v1.0 的几个关键特性值得军团设计者注意：**多协议支持**（A2A 不排斥其他传输协议）、**企业级多租户**、**现代化安全流**、以及 **Signed Agent Cards**（用密码学签名验证 agent 身份）。

**对军团意味着什么。** 三件事：
1. **对外接口应该"薄"**：既然 A2A 已成为跨组织的既定标准，我们不应自造对外协议，而应让内部 SLCP **映射**到 A2A（这正是第 10 章的主题）。
2. **身份要能签名**：Signed Agent Cards 意味着"我是谁"这件事要有密码学保证，而不是"我说我是谁"。军团内部的 IDENTITY 锚点（第 3 章）应当与它对位。
3. **多租户是必然**：当军团要服务多个 owner/多个业务线时，"租户隔离"不是可选项。本章的编制与信任阶梯，天然支持按租户分编。

### 6.5.2 线二：MCP 在 2026-07-28 走向"无状态优先"

MCP（Model Context Protocol）由 Anthropic 在 2024-11 发起，2025-12 进入 **Agentic AI Foundation（AAIF，Linux Foundation 旗下）** 治理。它的版本序列是：`2024-11-05 → 2025-03-26 → 2025-06-18 → 2025-11-25 → 2026-07-28`。

**2026-07-28 是被主维护者称为"自发布以来最大的一次修订"**，核心变化有三：

1. **移除 `initialize` / `initialized` 握手**（SEP-2575）：协议版本、客户端身份、客户端能力改为随**每一个请求**在 `_meta` 里携带；新增 `server/discover` RPC 供客户端按需获取服务端能力。
2. **移除 `Mcp-Session-Id` 头**（SEP-2567）：协议级会话消失，**任何一个 server 实例都能处理任何一个请求**——这意味着 MCP 服务器可以躲在普通负载均衡后面水平扩展，不再需要粘性会话与共享会话存储。
3. **授权重写 + 扩展框架**：更贴合 OAuth 2.0 / OpenID Connect 的部署实践，弃用动态客户端注册、改用 **Client ID Metadata Documents**，并引入**扩展（extensions）框架**来管理后续演进。

**对军团意味着什么。** 这条线的影响比它看起来深：**MCP 的"无状态优先"，等于把"会话状态"从协议层挪到了应用层**。对军团来说，这意味着"协同的记忆"不能再依赖"某条长连接还在不在"，而必须依赖**显式的账本**（6.1.8）。换句话说，**MCP 的演进方向，正好印证了本章"协同状态必须外化为账本"的判断**。

> ⏳ **诚实标注**：本章的分析基于 MCP 2026-07-28 规范的公开说明（SEP-2575 / SEP-2567）；本机 OpenClaw 2026.9.4 的 MCP 接入实现细节，见第 8 章（09-MCP绑定）的真名验证小节。

### 6.5.3 线三：Agent Skills 成为开放标准，"能力"被标准化了

Anthropic 于 2025-10 推出 Agent Skills（即 Claude Skills），并在 **2025-12-18** 把规范作为**开放标准**发布在 `agentskills.io`。到 **2026-03**，已有 **32 个工具**支持该规范（Claude Code、OpenAI Codex、ChatGPT、VS Code、GitHub Copilot、Gemini CLI、JetBrains Junie、AWS Kiro、Block Goose、Sourcegraph Amp、Snowflake、Databricks、ByteDance TRAE、Mistral AI 等）；到 **2026-06**，官方 show case 已列约 40 个兼容产品。`anthropics/skills` 仓库达到 100K stars，Vercel 的 `skills.sh` 市场列出数万个 skill。

一个标准化的 Skill 就是"一个目录 + 一份 `SKILL.md`（YAML frontmatter + markdown 指令）+ 可选的 `scripts/` `references/` `assets/`"。

**对军团意味着什么。** Skills 标准化，把"**能力**"从每个框架的私有概念，变成了跨平台的共享资产。对军团而言，这带来一个新的组织问题：**当能力可以被自由组合时，军团的设计重点从"我有哪些 agent"转向"我要组哪些能力"**。本章的编制（6.1.1）应当以"能力"为主要寻址对象，agent 只是能力的**承载者**——这也是为什么编制要"番号与名字解耦"：番号可以绑定"能力角色"，而 agent 的名字只是当下的实现。

### 6.5.4 三线交汇：Agent 组织学正在成为一个学科

把三条线放在一起看，2026 年的图景是：

- **A2A** 解决了"**跨组织协同**"的接口；
- **MCP** 解决了"**agent 与工具/数据**"的接口，并推动无状态化；
- **Agent Skills** 解决了"**能力**"的接口。

三者合起来，等于把"agent 世界的**三层接口**"都标准化了。而它们**都没有解决**的，恰恰是本章的主题——**当接口都通了以后，一群 agent 之间的"关系"该怎么定义、怎么维护、怎么从故障中学习**。

**这就是"Agent 组织学"（Agent Organization Science）的诞生背景**：2024–2026 上半年的行业重心在"让 agent 能干活"，2026 下半年开始，重心正转向"**让 agent 好好协作**"。本章的十二个概念，是这本书对这个新学科的第一次系统作答。

## 6.6 深度专题三 · 三省制 vs 框架的"角色扮演"：为什么分权不是分工

### 6.6.1 一个被普遍混淆的区别

CrewAI 有 roles，AutoGen 有 agents，OpenAI Agents SDK 有 handoffs，Claude Agent SDK 有 subagents——看起来大家都在"分角色"。但**分工（division of labor）** 和 **分权（separation of power）** 是两件完全不同的事：

- **分工**：把工作拆开，让不同的人做不同的活。目标是**效率**。
- **分权**：让同一件事需要多个独立主体同意才能落地。目标是**制衡**。

CrewAI 的角色是分工——写手 agent 写、审阅 agent 审，但**审阅的结论不被任何机制强制**（它可以被忽略）。三省制的核心恰恰是"**任一阶段否决即终止**"——这是一条**强制的、结构性的**制衡规则，不是"建议"。

### 6.6.2 为什么这个区别是致命的

设想一个场景：内容军团要发一篇外网文章。CrewAI 式的分工是：写手写完 → 审阅 agent 看一遍 → 发布 agent 发。如果审阅 agent 说"有事实错误"，但发布 agent 的 prompt 没把审阅结论当成硬约束，**文章照样发出去**。这就是分工的盲区：**它假设"审阅会自然被尊重"，而这个假设在压力下（赶时间、owner 催促）会第一个崩塌。**

三省制把这个假设**结构化了**：`finalizer` 在拿到 `reviewer` 的结论之前，**在物理上无法进入执行态**。这不是"希望它尊重"，而是"不尊重就跑不通"。

### 6.6.3 业界在这件事上的真实位置

到 2026-09，我们实测的口径是：**六个主流框架中，没有一个提供协议级的"分权"原语。** 最接近的是 Claude Agent SDK 的 subagent 委派（约覆盖 30% 场景）与 OpenAI Agents SDK 的 guardrail（它是**输出校验**，不是**决策分权**）。LangGraph 提供的是"可审计"，不是"可制衡"——它能让你看见每个节点的输出，但不能强制"某个节点必须被另一个节点批准"。

### 6.6.4 对军团设计者的三条建议

1. **把"分权"当成独立的层来设计**：不要指望"多写几个角色"就能获得制衡。制衡需要**强制性的状态机**（proposed → reviewed → finalized），以及"任一否决即终止"的硬规则。
2. **不要给所有决策都上三省**：分权有成本。只对**不可逆**的动作上三省（6.2 第 5 步），其余用抽查或事后审计。
3. **分权的技术内核是"上下文隔离"**：让复核者看到提议者的完整思路，等于让分权失效。**独立性不是靠角色名，是靠上下文墙。**

> **本专题的结论**：编排框架教你"让 agent 排队干活"，本章教你"让 agent 互相拴住"。这两件事的差别，就是"团队"和"团伙"的差别。

## 6.7 军团长考：十个真实问题的长答案

这一节不是 FAQ（FAQ 在 `_appendix-faq/`），它回答的是**设计层**的十个追问——这些问题没有标准答案，但有"我们踩过的答案"。每个答案都尽量给出**判断依据**，而不是一句结论。

### 6.7.1 我只有 3 只 agent，需要军团这一套吗？

需要，但要**减配**。军团十二个概念里，3 只 agent 的规模只需要三件：**编制**（谁负责什么）、**交接**（THP 的最小字段）、**账本**（哪怕是三列的 JSONL）。反脆弱三层、三省制、信任阶梯可以全部推迟。

判断依据：**需要不需要某个机制，取决于"这个机制的故障是不是致命的"**。3 只 agent 时，级联失败的影响是"3 只都哑"，owner 5 分钟内就能发现并人工恢复——所以 fallback 的收益不高。但"责任蒸发"（不知道谁该做）在 3 只时就会发生，所以编制和交接必须早立。**先立"关系类"机制，后立"冗余类"机制。**

### 6.7.2 18 只 agent 里，有些是"工具型"（只被调用不主动说话），它们算军团成员吗？

算**编制成员**，但不算**协同主体**。编制里应该有一栏区分"**主动型**（有 heartbeat、会发起）"和"**被动型**（只响应调用）"。这个区分很重要，因为让位规则、三省评审、信任阶梯都只对主动型生效——你不需要一个工具型 agent 去"让位"，因为它本来就不会抢话。

判断依据：**编队密度（6.1.11）只计算主动型**。18 只如果其中 10 只是工具型，那么真正的协同复杂度只相当于 8 只——这解释了为什么有的军团"感觉没那么乱"。

### 6.7.3 反脆弱三层会不会让军团变慢？

会，但这是**买保险的成本**，而且可以调。健康检查的周期、failover 的阈值、通道超时的时长，都是可调参数；调大了就慢而稳，调小了就快而脆。关键是**不要在第一次部署时就调到"最快"**——先用日志观测真实分布（6.2 第 3 步），再定阈值。

判断依据：**稳定性不是"从不延迟"，而是"延迟可预测"**。一个偶尔延迟 3 秒但从不抽风的军团，比一个通常 0.5 秒但每天崩一次的军团好用得多。

### 6.7.4 三省制会不会拖慢常规任务？

如果你给**所有**任务都上三省，会。所以 6.2 第 5 步强调"只对不可逆动作上三省"。可逆动作（生成草稿、内部检索）不需要三省；不可逆动作（对外发布、改生产、删数据、对外承诺）必须三省。

判断依据：**分权的成本应该正比于"错误的不可逆性"**。错误越难撤销，越值得为它多花三道闸的时间。

### 6.7.5 SLCP 和 A2A 会不会重复？我们到底该写哪个？

两个都要，但**分工明确**：SLCP 是**内部行为契约**（谁让位、谁复核、怎么 failover），A2A 是**对外接口标准**（怎么发现别的 agent、怎么签名身份、怎么跨组织调用）。**SLCP 映射到 A2A，而不是替代 A2A。** 第 10 章会给出完整映射表。

判断依据：**内部关系可以由你定义，对外接口不能由你定义**。你可以在军团内部用任何你觉得好的规则，但你不可能要求全世界都学你的规则——所以对外必须服从 A2A。

### 6.7.6 治理账本会不会变成"记录一切"的数据沼泽？

会，如果**不设字段约束**。账本的每一行必须是**结构化**的（JSONL + 固定字段），而不是"把日志全塞进去"。判断标准：**一个新问题，能不能只用账本回答？** 如果账本里全是自由文本，答案是"需要人工读"；如果是结构化的，答案是"跑一个聚合"。

判断依据：**账本的价值不是"全"，是"可聚合"**。宁可少记几个字段，也要保证每个字段是机器可读的枚举值，而不是一段话。

### 6.7.7 监督层（监军）会不会变成"军团的第二个 owner"？

只有当它**越权**的时候会。防止越权的结构约束是：监督层**只读账本**（不能写业务状态）、**只能叫停与上报**（不能直接改决策）、**与业务层无共享预算**。满足这三条，监军就只是"清醒的旁观者"，不会变成第二个决策中心。

判断依据：**监督的力量来自独立，不来自权力**。给监军"改业务"的权力，它就会从监督者变成参与者，从而失去发现全局僵局的能力（6.1.10）。

### 6.7.8 信任阶梯会不会导致"马太效应"——强的越强，弱的越弱？

会，如果信任**不可恢复**。设计时要给"低信任 agent"一条**明确的上升通道**：低风险任务 → 达标 → 提升信任档。否则弱 agent 永远接不到好任务，永远无法证明自己。反向也要有**降级通道**（6.1.9）。有升有降，阶梯才是活的。

判断依据：**能力可以培养，信任必须可重建**。一个只能升级不能降级的信任系统，会积累"已经被证明不可靠但仍在高信任档"的 agent——这是最危险的状态。

### 6.7.9 编队密度到底该设多少？

没有一个通用数字，但有两个可操作的信号：**（1）协调者的上下文里，"下属状态"占比是否超过 30%；（2）协调者的平均响应时长是否随下游数量显著上升**。任一信号触发，就该分层了。

判断依据：**密度的上限不是由"agent 能力"决定的，是由"注意力预算"决定的**。硅基 agent 的推理预算是有限资源，超载的协调者会"看起来很忙但没有判断"。

### 6.7.10 我怎么知道军团"变好了"？

看三个数字的**趋势**，而不是绝对值：**协同熵（6.1.12）是否稳定或下降**、**账本里的 failover / yield_timeout 频率是否下降**、**owner 每天花在"扫群"上的时间是否下降**。三个都在改善，军团就在变好。

判断依据：**军团的健康不是"零故障"，是"学习速度"**。一个每周都能从故障里改一条契约的军团，即便每周都出故障，它也是在变好的。一个半年没出故障但也没改过任何契约的军团，可能只是还没遇到它扛不住的负载。

## 6.8 一次军团故障的完整解剖：从"哑火"到"自愈"

理论讲完了，这一节用一次**真实模式的故障**，把本章的概念串成一条因果链。案例的原始记录在 `_appendix-case/01-real-incidents.md`（CASE-1），这里做的是**叙事化解剖**——重点不是"当时发生了什么"，而是"**如果没有本章的机制，会发生什么**"。

### 6.9.1 故障的起点：一个很小的问题

某天上午，内容军团接到一个常规任务：为一条产品更新写三篇不同渠道的文案。

军团编制是：`legion-lead`（拆解 + 分派）、`content-writer`（主笔）、`content-reviewer`（事实复核）、`publisher`（发布）。四条边，四个角色，看起来很清楚。

任务进行到第 2 小时，`content-writer` 的模型通道出现间歇性超时——**平均每 5 次调用超时 1 次**。这是一个极小的问题：单看它，不过是"偶尔慢一下"。

### 6.9.2 没有反脆弱三层时：故障沿着"关系"扩散

`content-writer` 超时后，它自己重试。重试没问题——问题是**它没有超时上限**。

- 第 1 次超时，它重试；
- 第 2 次超时，它继续重试（因为它被训练成"尽量别麻烦别人"）；
- `legion-lead` 在等 `content-writer` 的交付；
- `content-reviewer` 在等 `legion-lead` 的转交；
- `publisher` 在等 `content-reviewer` 的放行。

于是，一个"写手通道偶尔超时"的问题，在 20 分钟内变成了"**整条链路都停在原地**"。**注意：没有任何一个 agent 报错。** 它们都在"正常工作"——只是都在等。

这就是 6.0.2 里说的"哑火"，也是最能说明"关系层故障"的例子：**故障不在任何节点上，故障在边上。**

### 6.9.3 三个本该拦住它的机制

**第一道：通道守门员（6.1.3 第二层）。** 如果 `content-writer` 的通道配了守门员，它会在 5 分钟内累计到 3 次超时后，**把这条通道判死并隔离**，同时触发 `self_heal`。这时候问题是"写手通道坏了"，不是"整条链路不动了"——**影响半径从"军团"缩到"一个角色"**。

**第二道：让位规则的兜底（6.2 第 5 步）。** 如果 `legion-lead` 配了"任务超过 T 分钟无进展则升级"的兜底规则，它会在链路停滞 15 分钟后**主动上报**，而不是一直安静地等。**兜底机制的价值，就是让"沉默"变成一个可被观测的事件。**

**第三道：监督层（6.1.10）。** 如果有一个只读账本的监军，它会发现"过去 20 分钟账本里没有新增任何事件"——这个"零事件窗口"本身就是最响的告警。**监军不需要理解任务，它只需要发现"该动的没动"。**

三道机制，任意一道存在，这次故障的影响半径都会被压住。它们都没存在，所以故障扩散了。

### 6.9.4 恢复阶段：为什么"恢复"比"预防"更贵

故障被发现时，已经过了 40 分钟。owner 手动问"现在什么情况"的时候，得到的是四句互相矛盾的回答：

- `content-writer`："我在重试，快好了。"（它不知道别人在等它）
- `legion-lead`："我在等写手。"（它不知道写手在重试）
- `content-reviewer`："我没收到东西。"（它不知道上游卡了）
- `publisher`："我待命。"（它以为一切正常）

这四句话合起来是一个经典的**信息不对称**：**每个 agent 都只知道自己那一格，没有人知道全局。** 于是 owner 花了额外 25 分钟，靠人工问答才拼出"其实只是写手通道超时"。

**这就是治理账本（6.1.8）的价值所在**：如果有一条"事件流水"，owner 打开就能看到"最后一次事件是 40 分钟前的 `content-writer timeout`",3 秒钟定位根因。**账本买的不是"不出事"，是"出事时 3 秒钟定位"。**

### 6.9.5 这次故障教给我们的三句话

1. **小故障不可怕，"未被观测的小故障"才可怕。** `content-writer` 的超时本身是小事，它可怕是因为**没有一个机制在观测它**。
2. **协同故障的增长是"边的数量"，不是"节点的数量"。** 加一只 agent，增加的是它与所有人的边；边越多，故障传播路径越多。
3. **恢复成本 ≈ 发现成本 × 信息不对称系数。** 发现得越晚、信息越不对称，恢复越贵。账本和监军的作用，就是同时压低这两个因子。

### 6.9.6 如果重来一次，我们会怎么配

- **编制不变**（编制本来就是对的）；
- 给 `content-writer` 的通道加**守门员 + 超时上限**（不再无限重试）；
- 给 `legion-lead` 加**停滞兜底**（T 分钟无进展即升级）；
- 引入**监军**，只读账本 + 定时巡检；
- 把"链路停滞"定义为一个**一等事件**，写进账本。

这五条加起来不到一页配置，但它们把这次故障从"40 分钟神不知鬼不觉"变成"5 分钟内被观测到、10 分钟内被隔离"。**这就是本章的全部意义：不是让军团更聪明，是让军团"坏得有边界"。**

## 6.9 什么时候**不该**用军团：单体优先的六种情形

本章花了很多篇幅讲"怎么建军团"，但一个诚实的章节必须回答反面问题：**什么时候你根本不该建军团？** 因为"过度组织化"和"过度扁平化"一样有害——它会用协调成本吃掉全部收益。

### 6.10.1 情形一：任务的价值还不足以覆盖协调成本

协同有固定成本：编制要维护、契约要写、账本要看、复盘要做。如果任务的规模小于这个成本，建军团就是亏的。判断方法很简单：**如果这个任务你自己（一个 agent）30 分钟能做完，就不要建军团。**

### 6.10.2 情形二：任务高度串行，没有可并行的独立子任务

军团的价值来自**并行 + 专业化**。如果一个任务本质上是一条串行链（A 做完才能做 B，B 做完才能做 C），那引入多个 agent 不会加快它，只会增加交接成本与出错点。**串行任务用单体，并行任务才考虑军团。**

### 6.10.3 情形三：任务的"验收口径"说不清楚

如果连"什么叫做完了"都说不清，军团会把它放大成"每个人都有不同版本的'做完'"。军团要求你在开工前就写清楚 `Acceptance Criteria`（6.1.6）——写不出来的任务，先别急着并行化。

### 6.10.4 情形四：领域知识高度耦合

有些任务的知识是"一团"——比如判断一个商业决策，需要同时考虑市场、财务、技术、法务，而这些维度**互相纠缠**，拆开就失真。这种任务适合一个拥有完整上下文的 agent 深想，而不是四个各看一角的 agent 浅议。

### 6.10.5 情形五：你还没有一个稳定的单体

如果连一个 agent 都跑不稳（会漂移、会忘记、会乱用工具），那么把一个不稳定的单体复制成军团，只会得到"**不稳定 × N**"。**先有一个稳定的单体，再考虑军团。** 这也是本书前面五章必须先于本章的原因。

### 6.10.6 情形六：故障的代价可以承受，而速度是唯一关键

如果任务是"快速试错"，错一次的成本极低，而时间极其宝贵——那么三省的评审、反脆弱的健康检查、让位的兜底，全都是**拖慢你的合规成本**。这时候，单体 + 快速迭代，比军团 + 稳妥流程更优。

### 6.10.7 反面清单总表

| 情形 | 信号 | 正确选择 |
|---|---|---|
| 价值 < 协调成本 | 单体 30 分钟能做完 | 单体 |
| 任务纯串行 | 无独立并行子任务 | 单体 |
| 验收说不清 | 写不出 Acceptance Criteria | 先想清楚再谈 |
| 知识高度耦合 | 拆开就失真 | 单体深想 |
| 单体还不稳 | agent 会漂移/遗忘 | 先练单体 |
| 速度唯一关键 | 错一次成本极低 | 单体 + 快迭代 |

**这六条不是"用军团的反面教材"，而是"军团这一章的边界"。** 一个只会说"上军团"的章节是不诚实的；一个知道自己边界的章节，才是可用的。

## 6.10 Owner 在军团里的位置：你是"指挥官"，不是"调度员"

军团建成之后，owner 的角色会发生一个不太被察觉、但极其重要的转变。这一节把这件事讲透，因为**owner 用错姿势，军团再完美也会退化。**

### 6.11.1 两种姿势：调度员 vs 指挥官

**调度员姿势**：owner 亲手把每个任务派给每个 agent，亲手转交上下文，亲手催进度。军团变成了"owner 的十八只手"。这种姿势在 3 只 agent 时效率很高，在 18 只时会让 owner 成为**唯一瓶颈**——所有任务的 throughput 被"owner 一条一条派"限制住。

**指挥官姿势**：owner 只做三件事——**给目标**（军团要达成什么）、**定边界**（什么不能做）、**裁决冲突**（军团内部分权无法解决时）。具体"谁做什么、怎么交、谁让位"，全部由编制与契约自己运转。

本章的所有机制（编制、SLCP、反脆弱三层、三省制、让位规则），**只有在 owner 切换到"指挥官姿势"时才真正生效**。原因是：机制的作用是"让军团自转"，如果 owner 一直在手动调度，机制就永远没有被需要的时刻，也就不会被锻炼、不会被修正。

### 6.11.2 为什么 owner 很难切换姿势

因为**调度员姿势给人"掌控感"**。你亲手派活、亲手催进度，你确信"事情在发生"。而指挥官姿势要求你**忍受一段"不知道细节"的不安**——你得相信编制与契约会运转。

这段不安期，是军团建设里最容易失败的关口。很多 owner 在军团建好后的第一周，因为"看到某条边卡了"，就忍不住手动介入、手动派活、手动转交——于是军团**学会了依赖**，机制的漏洞永远没被暴露。

**正确做法**：把"忍不住手动介入"的冲动，转化成一个动作——**去改契约，而不是去改这一次的执行**。链路卡了，不是"我来转交一下"，而是"为什么这条边没有兜底？把兜底补上"。前者解决这一分钟，后者解决未来一年。

### 6.11.3 Owner 的三个动作与三个反动作

| 该做（指挥官） | 不该做（调度员） |
|---|---|
| 给目标 + 验收口径 | 亲手派活到每个 agent |
| 定边界（不可逆动作清单） | 亲手转交上下文 |
| 只裁决分权无法解决的冲突 | 亲手催每一条进度 |

**一个简单的自检**：如果你发现自己每天在群里发超过 10 条"催进度"的消息，你还在调度员姿势。指挥官的消息应该是**目标、边界、裁决**，而不是"你好了吗"。

### 6.11.4 为什么"owner 少介入"不等于"owner 不管"

这不是"放养"。指挥官的介入是**结构性的**：

- 每周做一次**军团体检**（6.2 第 7 步），把问题回灌编制；
- 每次不可逆动作前，确认三省的角色独立性（6.2 第 5 步）；
- 只在**分权无法解决**的冲突里出手——比如两个 agent 都认为自己有权决定，且规则没有覆盖这种情况。

**结构性介入 vs 事务性介入**，是区分指挥官和调度员的分水岭。事务性介入（催、转、派）会随规模线性增长，最终压垮 owner；结构性介入（体检、改契约、裁决）的频率极低，且随规模增长**几乎不变**。

### 6.11.5 Owner 是军团里唯一的"人类锚点"

最后一点，也是最容易被忽略的一点：**owner 是军团里唯一能回答"我们为什么做这件事"的角色**。agent 能回答"怎么做"，能回答"做得对不对"，但**不能回答"为什么值得做"**——因为"值得"是一个价值判断，它需要一个能承担后果的主体。

这决定了 owner 在军团里不可替代的位置：不是"最强的大脑"，而是"**意义的来源**"。把这件事想清楚，你就不会纠结"owner 到底该多干活还是少干活"——owner 该干的活，是那些**只有能承担后果的人才能干的活**。

## 6.11 军团组织学的三条定律

本章最后，把十二个概念压缩成三条"定律"。它们不是定理（没有数学证明），而是我们在一年的实战里反复验证的**经验规律**。记住这三条，你就记住了本章的骨架。

### 6.12.1 第一定律：关系定律

> **一个军团的能力，上限由"节点能力"决定，下限由"关系质量"决定。**

含义：节点再强，如果关系没定义，军团的实际表现会**塌到关系质量那一层**。18 个 90 分的 agent，如果关系质量是 20 分，军团整体就是 20 分——不是平均，是**下限**。

推论：**军团建设的第一优先级永远是"关系"，不是"节点"**。这也是本章前四节全部在讲"关系"（编制是关系的骨架、SLCP 是关系的语言、反脆弱是关系的韧性、三省是关系的制衡）的原因。

### 6.12.2 第二定律：熵定律

> **协同熵只会自发上升；压制熵需要持续做功。**

含义：军团不会"越跑越好"，除非你持续地做体检、改契约、修编制（6.1.12）。任何"建好就放着"的军团，都会缓慢地从有序滑向"有序的假象"。

推论：**治理军团的成本是持续成本，不是一次性成本**。把"军团建设"当成一个项目（有明确完工日）的团队，一定会在三个月后发现自己回到了起点。

### 6.12.3 第三定律：观测定律

> **不能被观测的协同环节，一定会失效。**

含义：账本（6.1.8）、监军（6.1.10）、事件日志（6.1.3 第三层）之所以是"必备"而不是"可选"，是因为**凡是没被写进账本的关系，都会在压力下退化成口头默契，而口头默契会第一个被牺牲**（6.9 的故障就是这个问题）。

推论：**建设军团的顺序，应该反过来——先建观测，再建行为**。这也是 6.2 里"先上事件日志、再上守门员、最后上 fallback"的顺序背后的同一个道理。

### 6.12.4 三条定律合起来

把三条定律放在一起，本章的全部主张就一句话：

> **军团不是"更强的个体"，军团是"被定义、被观测、被持续维护的关系集合"。**

你不需要 18 个最强的 agent；你需要 18 个**关系清晰、可被观测、能被修正**的 agent。前者是买不到的（模型能力由供应商决定），后者是**只有这本书能教你的**。

## 6.12 协同的七个反直觉真相

军团的很多设计，初看都是"反常识"的。这一节把七个最反直觉的真相集中讲一遍——它们中的每一条，我们都用真实故障验证过。

### 6.12.1 真相一：加人会让军团**更脆弱**，直到关系补上为止

常识是"人多力量大"。真相是：在关系未定义时，第 N+1 个 agent 带来的**新增协调成本**（与已有 N 个的潜在边）远大于它的**新增产能**。军团从 8 只扩到 18 只，如果不同时补关系，整体可靠性会**先下降**，直到关系补齐才回升。**扩容必须先补关系，后加人。**

### 6.12.2 真相二：最危险的故障是"没有动静"

常识是"出错了会报错"。真相是：军团的多数严重故障是**静默的**——哑火、死锁、责任蒸发（6.8），它们都不报错，只是"该动的没动"。这也是为什么本章把"**观测定律**"（6.11.3）列为三大定律之一：**你必须专门为"沉默"设计告警**，因为沉默不会自己喊出来。

### 6.12.3 真相三：提高 agent 的能力，不能替代修补关系

常识是"把每只虾练得更好，军团自然更好"。真相是：军团整体表现的下限由**关系质量**决定（关系定律）。把 18 个 60 分的 agent 都练成 90 分，如果关系质量还是 20 分，军团整体还是 20 分。**关系是瓶颈，是天花板，是下限**——能力提升会被关系瓶颈吞掉。

### 6.12.4 真相四：让位规则不是"谦让"，是"效率"

常识是"让位是一种礼貌"。真相是：让位规则是一条**带宽分配算法**（6.1.5）。它省的不是"面子",是 owner 的注意力与系统的推理预算。抢话的代价不只是"看着乱",它是**算力与注意力的双重浪费**，会随规模放大。

### 6.12.5 真相五：军团需要"故意留白"

常识是"规则越多越好"。真相是：熵=0 的军团是**僵化**的（6.1.12）——它会在一遇到"规则没覆盖的新情况"时卡住。健康的军团留出一小块"未定义区域"，让 agent 在那里自行协商，然后**把协商结果吸收进下一版契约**。留白不是漏洞，是**进化的接口**。

### 6.12.6 真相六：军团的速度由"最慢的边"决定，不是"最快的节点"

常识是"把瓶颈节点提速，军团就快了"。真相是：军团的端到端延迟由**最慢的那条协作边**决定，而"边"的延迟由三部分组成——上游产出时间、交接开销、下游等待时间。其中**交接开销**是最容易被忽略的一项，也是最能通过"结构化 THP"（6.1.6）压缩的一项。

判断依据：如果你把 18 个 agent 里最快的那个提速 2 倍，军团整体几乎不变；如果你把"最慢那条边"的交接开销砍掉一半，军团整体立刻变快。**优化边，而不是优化点。**

### 6.12.7 真相七：军团的记忆不在 agent 里，在账本里

常识是"每个 agent 各自记住自己做过的事就够了"。真相是：**协同级的记忆必须外化到账本**（6.1.8），因为任何单一 agent 的上下文都是**局部**的——它记不住"整条链路发生了什么"。当你要回答"上周那次故障的根因"时，答案不在任何 agent 的记忆里，只在账本里。

判断依据：如果一个问题的答案需要你"挨个问 agent 才能拼出来"，说明这个答案本该在账本里。**军团的信息，凡是跨 agent 的，都必须离开 agent 的上下文，落到一个公共的可查处。** 这也正是 MCP 2026-07-28 走向"无状态优先"（6.5.2）给我们的同一条启示。

### 6.12.8 七个真相的共同指向

这七条指向同一个结论：**军团的进步，主要发生在"关系层"，而不是"能力层"。** 能力层由模型供应商推进（你买不到差异），关系层由你自己维护（这才是你可以积累的护城河）。这也是本书把"协同军团"单列一章、而不是把它塞进"系统骨架"的原因——**它值得一个独立的章节位置。**

### 6.12.9 结语：从"养虾"到"训军团"

如果要用一句话概括这一章对 OpenClaw 训练学的贡献，那就是：**它把"训练"这个词，从"训练一只虾"扩展到了"训练一群虾之间的关系"。**

前者是本章之前五章的工作：给一只 agent 灵魂、纪律、工具、心跳、身份、记忆，把它从"能跑"练成"可靠"。后者是本章的工作：给一群已经可靠的 agent 补上**编制、契约、韧性、制衡、账本**，让它们从"18 个可靠的个体"变成"一支可靠的军团"。

这两件事的手艺完全不同。练单只虾，你面对的是"能力"问题——它会不会做、做得好不好。练军团，你面对的是"关系"问题——它们之间会不会互相拖累、会不会互相等待、会不会在压力下一起崩。

**养虾派关心"这一只虾今天表现怎么样"；训虾派关心"这一群虾明年还会不会稳定"。** 本章的全部内容，都是为后者服务的。

军团不是终点。它是一条通道——一条让一群硅基生命，从"各自专业"走向"共同可靠"的通道。走通这条通道之后，第 7 章（超维演进）才能问出那个更大的问题：一群能稳定协作的 agent，能不能**自己演化出新的能力与目标**？

### 6.1 SLCP（Silicon-Life Coordination Protocol）

### 6.1.1 历史背景

丘总 v1.0 用过 "ACP（Agent Communication Protocol）" 命名——但 IBM/BeeAI 的同名 ACP 已于 2025-08 合并入 A2A v1.0，存在商标冲突。**v5.0 改名 SLCP（Silicon-Life Coordination Protocol）**，避免冲突。

### 6.1.2 SLCP 与 A2A 的关系

- A2A v1.0（2026-05-28 latest）：业界事实标准，提供 Agent Card + 协同框架
- SLCP（v5.0 本书）：在 A2A 上加**反脆弱三层**（6.2）

两者关系 = A2A 提供"路"，SLCP 提供"护栏"。

### 6.2 反脆弱三层（Anti-Fragile Triptych）⚡ 优势 1

**这是 v5.0 的核心壁垒。** 业界 A2A v1.0 不管这些——所有协同问题都需要 agent 自己解决。SLCP 把三层写成协议层原语。

### 6.2.1 第一层 · fallback 健康检查（防全军级联失败）

```yaml
slcp_fallback:
  primary: "agent-A"
  fallback: ["agent-A1", "agent-A2", "agent-A3"]
  health_check_interval: 60s
  failover_threshold: 3  # 3 次连续失败才切
  dedup: true  # primary/fallback 不重复计入全军
```

**机制**：每 60 秒检查 primary 健康度，连续 3 次失败才切到 fallback；切的时候**只计入新启用的**，避免 double-count。

### 6.2.2 第二层 · 通道守门员（防网络失效扩散）

```yaml
slcp_gatekeeper:
  channel_timeout: 5min
  self_heal: true
  propagate_failure: false  # 不把网络失败传给其他 agent
```

**机制**：5 分钟内同一通道 3 次超时 = 通道死亡；守门员把通道隔离到本地 agent，**不传染**其他 agent。

### 6.2.3 第三层 · 结构化协同事件日志

```yaml
slcp_event_log:
  - event_id: "EV-001"
    type: "primary_failover"
    primary: "agent-A"
    fallback: "agent-A1"
    reason: "3 consecutive health check failures"
    ts: 1727000000
  - event_id: "EV-002"
    type: "channel_quarantine"
    channel: "feishu-bridge"
    reason: "3 timeouts in 5min"
    ts: 1727000300
```

**机制**：每次 failover / quarantine 写一行结构化日志，让**所有 agent 都能读到失败模式**——下次协同自动避开。

### 6.2.4 业界对位（业界领先 ⚡）

| 层 | A2A v1.0 | AutoGen | CrewAI | 本训练学 SLCP |
|---|---|---|---|---|
| fallback 健康检查 | ○ | ⚠ | ⚠ | ✅ 首创 |
| 通道守门员 | ○ | ○ | ○ | ✅ 首创 |
| 结构化事件日志 | ○ | ⚠ | ⚠ | ✅ 首创 |

→ A2A v1.0 一个都没做；AutoGen/CrewAI 部分有但**不是协议层**——是用户代码层。

### 6.3 三省制（Three-Stage Review）⚡ 优势 4 部分

### 6.3.1 为什么需要分权

单 agent 决策 = 单点失败。多 agent 决策需要分权——丘总的答案是三省制：

```yaml
three_stage_review:
  proposer: "agent-1"    # 提议
  reviewer: "agent-2"    # 复核
  finalizer: "agent-3"  # 终审
```

### 6.3.2 状态机

```
proposed → reviewed → finalized
   ↓         ↓           ↓
 rejected  rejected   executed
```

**任一阶段拒绝 = 任务终止**。这与 CrewAI 的"角色协作"区别：CrewAI 是角色**执行**，不是角色**分权**。

### 6.3.3 业界对位（业界全空 ⚡）

| 框架 | 分权 | 重叠 |
|---|---|---|
| CrewAI | ○ | — |
| AutoGen | ○ | — |
| Claude SDK | ⚠ subagent task（部分） | ⚠ 30% |
| 本训练学 | 三省制 | ✅ |

→ CrewAI/AutoGen 完全没有"分权"概念。

### 6.4 让位规则（Response Yield Protocol）

### 6.4.1 什么时候让位

多 agent 群聊/私聊时，**同一时刻只能有一个 agent 说话**。让位规则定义什么时候退让：

```yaml
yield_protocol:
  triggers:
    - other_agent_confidence > 0.9  # 另一个 agent 置信度高
    - same_topic_already_responded  # 同一话题已响应过
    - owner_directs_me_to_yield     # owner 直接让我退
  yield_action: "stop_current_response + log_yield_event"
```

### 6.4.2 与 OpenAI Agents SDK Handoff 对位

OpenAI Agents SDK 有 Handoff（agent 之间转移控制权），但 Handoff 是**转移**，让位是**退让**——两者互补。

| 维度 | OpenAI Handoff | 本训练学 Yield |
|---|---|---|
| 触发 | 主动转移 | 被动退让 |
| 控制权 | 转到新 agent | 释放控制权 |
| 适用场景 | 任务切换 | 协同冲突 |

### 错误 1 · 只建"反脆弱第一层"（无冗余、无守门员、无日志）

**错误现象**：作者配了一个通道、一个 agent、一份配置，认为"能跑就行"；通道一断，全军哑火。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：单点结构
channel:
  provider: "feishu"
  replicas: 1          # ❌ 单点
sentinel: none         # ❌ 无通道守门员
audit_log: none        # ❌ 无日志
```

**为什么错**：

1. **反脆弱三层缺一不可。** 本章 6.2 节：① 冗余（多通道/多副本）② 守门员（Channel Sentinel，通道守门员）③ 日志（事后追溯）。只有一层 = 没有反脆弱。
2. **8/19 军团断线**（F3-13 / F6-5）就是"模型级联失败 + 无守门员"的现场：通道失效后无人应答，且**过了很久才被发现**。
3. **F6-11 是第三层的缺失**："协同过程无日志，事故不可追溯"。
4. **代价**：单点故障 → 全军哑火 → 无法追溯 → 无法防止复发。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：三层齐备
channel:
  primary: "feishu"
  fallback: ["telegram", "email"]      # ① 冗余
sentinel:                              # ② 通道守门员
  enabled: true
  check_interval: 300

  path: "~/notes/domain/silicon-life-handbook/governance/channel.jsonl"
```

```bash
# 守门员的最小实现（挂进心跳）
# HEARTBEAT.md on_wake:
```

### 错误 2 · 让位规则写成"礼貌建议"而非硬约束

**错误现象**：AGENTS.md 里写"如果 X 更擅长，Y 应该让 X 回答"；结果 Y 还是抢答，让位失效。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：软性让位
yield_rules:
  - "Q：如果工程问题，工程 agent 可以让位吗？ A：建议让位。"   # ❌ 无强制
```

**为什么错**：

1. **让位是协议，不是礼仪。** 术语表 #14：Response Yield Protocol（响应让渡协议）——它是**可判定的规则**，不是"建议"。
2. **F6-2 就是这个事故**："让位失效，不该答的 agent 答了"。
3. **模型无法可靠执行"建议型"规则**：它可能"觉得这次该自己答"，于是不让位。
4. **代价**：抢答刷屏（F6-1）、群里混乱、成本翻倍。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：可判定、可执行的让位规则
yield_rules:
  - when: "message.domain == 'engineering' and xuanyuan.online == true"
    action: "yield_to(xuanyuan)"
  - when: "message.mention != self.name"
    action: "stay_silent"
  - default: "supervisor layer decides"
```

**验证命令**：

```bash

grep -nA3 "yield_rules" ~/.openclaw/workspace/agents/my-agent/contracts/AGENTS.md

# 2) 是否存在"建议型"措辞
grep -rniE "建议让位|可以让位|尽量让" ~/.openclaw/workspace/agents/*/contracts/ 2>/dev/null | head
# 期望：无输出

# 3) 实测让位（发一条明确指向他方的消息）
openclaw agent --message "@xuanyuan 请回答工程问题" 2>&1 | head -20
```

### 错误 3 · 三省评审制退化成"一人签字"

**错误现象**：作者设计了提案/评审/终裁三步，但实际上总是同一个人（或同一个 agent）三步全包，评审形同虚设。

```yaml
  reviewer: "a1"        # ❌ 自评
  decider: "a1"         # ❌ 自裁
```

**为什么错**：

1. **三省评审制（Three-Stage Review）的本质是"角色分离"。** 术语表 #13 保留了这一概念并加了英文全称；本章 6.3 节要求三角色由**不同主体**承担。

3. **F6-15 就是这个落地问题**："三省评审制怎么落地"。
4. **代价**：错误决策无人拦截；治理退化为形式。

**正确配置**（✅ 应该这样）：

```yaml
  proposer: "tiangong"            # 提案
```

### 错误 4 · 任务交接（THP）不留痕迹

**错误现象**：A 把任务交给 B，只在对话里说了句"你来吧"；B 收到后上下文缺失，任务半路丢失，双方都说"我交代/我收到了"。

**错误配置**（❌ 不要这样）：

```markdown
# 错误示范：口头交接
A → B：「这个你处理一下」
（无任务卡、无验收口径、无上下文包）
```

**为什么错**：

1. **任务交接协议（Task Handoff Protocol, THP，原：交接棒协议）要求"三件齐"**：任务卡 + 验收口径 + 上下文包（术语表 #15/#24/#25）。
2. **F6-13 就是这个事故**："任务交接在半路丢失，接力棒掉了"。
3. **口头交接不可追溯**，也无法审计（第 5 章治理账本无记录）。
4. **代价**：任务丢失、重复劳动、信任受损。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：结构化交接
handoff:
  task_card: "T-2026-09-27-01"
  acceptance: ["7 契约齐备", "每文件非空"]
  context: ["背景", "已尝试", "相关文件路径"]
  evidence_out: []            # 交接时须附当前证据
  audit: "governance/ledger.jsonl"
```

### 错误 5 · 共享 workspace 无归属（互相覆盖）

```yaml
# 写入规则（写进 AGENTS.md）
```

### 错误 6 · 协同无 SLCP 对位（协议层断裂）

**错误现象**：多个 agent 各自用不同的约定通信（有人用 @、有人用 JSON、有人用关键词）；对接外部（A2A）时协议对不上。

**错误配置**（❌ 不要这样）：

```markdown
# 错误示范：各家自定义
A 用 "@B 帮我看下"
B 用 "handoff: {task: ...}"
C 用 "请转交 D"
```

**为什么错**：

1. **协同需要协议层。** SLCP（Silicon-Life Coordination Protocol，原：ACP）就是这层；它还要与 A2A v1.0 对位（第 9 章 9.3 节）。
2. **F6-10 就是这个事故**："A2A / SLCP 协议对不上，ACP 改名遗留导致协同断裂"。
3. **改名遗留会传染**：v1.0 的 ACP 与业界 ACP（已并入 A2A）冲突（术语表 #1），未改会导致外部对接失败。
4. **代价**：内部协同与外部对接双重断裂。

**正确配置**（✅ 应该这样）：

```markdown
<!-- 统一通信契约（写进 AGENTS.md） -->
## 协同协议：SLCP（原：ACP）
- 路由：`@<agent-name>`
- 交接：结构化 THP（任务卡 + 验收 + 上下文）
- 让位：Response Yield Protocol（可判定规则）
- 对外：A2A v1.0.1 映射（见第 9 章）
```

**验证命令**：

```bash
# 1) 是否还有 ACP 残留
grep -rn "ACP" ~/.openclaw/workspace/agents/*/contracts/ 2>/dev/null | grep -v "SLCP" | head
# 期望：无输出

# 2) SLCP 是否声明
grep -rn "SLCP" ~/.openclaw/workspace/agents/*/contracts/ 2>/dev/null | head

# 3) A2A 对位文档
grep -n "A2A" ~/.openclaw/workspace/references/silicon-life-handbook/openclaw-silicon-life-handbook-v2026.9-industry-standard/chapters/09-a2a-binding/09-A2A绑定.md | head -5
```

**相关 FAQ**：F6-10（协议对不上）、F2-13（ACP 改名遗留）、F6-7（主仓 PR 合并后 override 回归）。

### 错误 7 · 主仓更新后忽视本地 override 回归

**错误现象**：主仓 PR 合并后，本地曾经打的 override/补丁被覆盖或行为回归，协同链路悄悄断掉。

**错误配置**（❌ 不要这样）：

```bash
# 错误示范：本地直接改主仓文件，无版本记录
vim ~/.openclaw/workspace/references/openclaw/src/xxx.ts   # ❌ 会被上游覆盖
```

**为什么错**：

1. **本地 override 需要"可回归检测"。** F6-7："主仓 PR #152777 合并后，本地 override 可能回归（同源于 9/21）"。
2. **直接改主仓文件 = 升级即丢失**，且无痕迹。
3. **代价**：某次升级后协同链路静默失效，排查困难。

**正确配置**（✅ 应该这样）：

```bash
# 正确示范：override 留痕 + 升级后回归检查
mkdir -p ~/notes/domain/silicon-life-handbook/overrides
echo "override: <文件> <原因> <PR 号> <期望行为>" >> ~/notes/domain/silicon-life-handbook/overrides/README.md
# 升级后逐条核对期望行为是否仍成立
```

**验证命令**：

```bash
# 1) override 记录存在
cat ~/notes/domain/silicon-life-handbook/overrides/README.md 2>/dev/null

# 2) 升级/拉取后的回归核对
openclaw health 2>&1 | head -20
openclaw doctor 2>&1 | tail -20

# 3) 关键行为实测
openclaw agent --message "@xuanyuan 连通性测试" 2>&1 | head -10
```

**相关 FAQ**：F6-7（override 回归）、F6-6（通道失效）、F1-5（升级后配置失灵）。

### 错误 8 · 死锁（互相等待）无超时机制

**错误现象**：A 等 B 的输入，B 等 A 的确认，双方都不动；任务永久挂起。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：无超时、无仲裁
wait_policy:
  timeout: never        # ❌ 永久等待
  arbiter: none
```

**为什么错**：

1. **协同必须有超时与仲裁。** F6-3："多 Agent 互相等待，任务死锁（谁都等谁）"。
2. **无超时 = 永久挂起**，且不会报错（最隐蔽的故障）。
3. **无仲裁 = 无人打破僵局**；监督层（Supervisor Layer，原：监军）应承担仲裁角色。
4. **代价**：任务静默停滞，直到有人偶然发现。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：超时 + 仲裁
wait_policy:
  timeout_s: 600
  on_timeout: "escalate_to(supervisor_layer)"
  arbiter: "supervisor-layer"
  max_wait_depth: 1        # 不允许多层互相等待
```

**验证命令**：

```bash
# 1) 超时是否配
grep -nE "timeout|arbiter" ~/.openclaw/workspace/agents/*/contracts/*.md 2>/dev/null | head

# 2) 是否有挂起任务
grep -h '"status":"waiting"' ~/notes/domain/silicon-life-handbook/governance/ledger.jsonl 2>/dev/null | wc -l

# 3) 实测超时升级
openclaw agent --message "构造一次需要他方输入的任务，观察 600s 后是否升级" --agent my-agent 2>&1 | head -10
```

**相关 FAQ**：F6-3（死锁）、F6-4（单点哑火）、F6-15（三省评审制）。

### 坑 1 · 先加 agent，后想协同

**坑的场景**：新人为了"军团化"批量建 agent，协同规则事后补，补的时候发现到处冲突。

**后果**：

- **抢答/哑火并存**（F6-1 / F6-5）。
- **规则互相矛盾**，越补越乱。
- **成本失控**。

**为什么踩**：

1. **"多 = 强"**。
2. **不知道协同是"先设计后加人"**。
3. **前 3 个 agent 时问题不明显**。

**怎么爬出来**：

```bash
# 第 1 步：冻结新增 agent，先画协同图
cat > ~/notes/domain/silicon-life-handbook/coordination-map.md <<'EOF'
# 协同图（谁负责什么、谁能派谁、谁让谁）
| agent | role | 可派给 | 让位于 |
EOF

# 第 2 步：按图补 routing_rules + yield_rules
```

**预防**：

- **先定角色与协同，再定人数**。
- **从 2 个 agent 起步**。
- **真实案例参照**：F6-1、F6-5、F6-8。

### 坑 2 · 把"通道"当成"一定在"

**坑的场景**：新人假设主通道永远可达，从不做连通性检查；通道一断，任务静默失败。

**后果**：

- **静默失败**：任务发不出去，没人知道（F3-12 / F3-13）。
- **发现滞后**：往往几小时甚至几天后才发现。
- **事故不可追溯**：无日志（F6-11）。

**为什么踩**：

1. **"配好了就在"的静态思维**。
2. **不知道通道需要守门员**（第 6 章 6.2 第三层之前的第二层）。
3. **没配告警**。

**怎么爬出来**：

```bash
# 第 1 步：加连通性检查（挂心跳）
# HEARTBEAT.md on_wake:
#   - "检查主通道可达性（发一条探测消息）"
#   - "不可达 → 告警 + 切 fallback"

# 第 2 步：加日志
mkdir -p ~/notes/domain/silicon-life-handbook/governance
echo '{"ts":"'$(date -u +%FT%TZ)'","event":"channel-probe","result":"ok"}' \
  >> ~/notes/domain/silicon-life-handbook/governance/channel.jsonl
```

**预防**：

- **通道必须"可探测 + 有备选 + 有日志"**。
- **真实案例参照**：F3-12、F3-13、F6-6、F6-12。

### 坑 3 · 让位规则写"应该"，不写"如果…则…"

**坑的场景**：新人写"工程问题应该由工程 agent 答"，没写判定条件与动作。

**后果**：

- **让位不生效**（F6-2）。
- **抢答**（F6-1）。
- **规则无法被机器执行**。

**为什么踩**：

1. **自然语言写规则最省事**。
2. **不知道让位协议要"可判定"**（术语表 #14）。
3. **缺少"规则即代码"的意识**。

**怎么爬出来**：

```yaml
# 改写成可判定规则
yield_rules:
  - when: "message.domain == 'engineering' and xuanyuan.online"
    action: "yield_to(xuanyuan)"
  - when: "message.mention != self.name"
    action: "stay_silent"
```

**预防**：

- **规则必须含 when + action**。
- **规则要能实测**（发一条对应消息验证）。
- **真实案例参照**：F6-1、F6-2、F6-8。

### 坑 4 · 交接只说"你来吧"

**坑的场景**：口头交接，无任务卡、无验收口径、无上下文。

**后果**：

- **任务丢失**（F6-13）。
- **重复劳动**：接方从零开始。
- **无审计**。

**为什么踩**：

1. **口头最快**。
2. **不知道 THP 要"三件齐"**。
3. **缺少交接模板**。

**怎么爬出来**：

```bash
# 建交接模板
mkdir -p ~/notes/domain/silicon-life-handbook/handoff
cat > ~/notes/domain/silicon-life-handbook/handoff/TEMPLATE.md <<'EOF'
- 任务卡 ID：
- 验收口径（可判定）：
- 上下文（背景/已尝试/文件路径）：
- 当前证据：
EOF
```

**预防**：

- **交接必带三件**，缺一不算交接。
- **真实案例参照**：F6-13、F6-14、F7-9。

### 坑 5 · 死锁了没人管

**坑的场景**：两个 agent 互相等，新人不知道有这回事，任务挂了两天。

**后果**：

- **静默停滞**：不报错、不告警。
- **交付延期**。
- **信任受损**。

**为什么踩**：

1. **死锁不产生错误消息**（最难发现）。
2. **没有超时与仲裁**。
3. **没有"挂起任务"的巡检**。

**怎么爬出来**：

```bash
# 第 1 步：找出挂起任务
grep -h '"status":"waiting"' ~/notes/domain/silicon-life-handbook/governance/ledger.jsonl 2>/dev/null

# 第 2 步：加超时 + 仲裁（见"常见错误 8"）
# 第 3 步：心跳加一项"检查挂起任务 > 阈值"
```

**预防**：

- **所有等待必须带超时**，超时升级到监督层。
- **真实案例参照**：F6-3、F6-4、F6-15。

### 坑 6 · 把"军团"当品牌，不当系统

**坑的场景**：新人把"蓝血智能体生态"（原：蓝血军团）当成一个称号，配上就完事，不去建实际的协同机制。

**后果**：

- **有名无实**：称号之下仍是几个互不相识的 agent。
- **治理缺位**：无账本、无信任结算、无让位。
- **对外失信**：对外宣称"军团"，实际是散兵。

**为什么踩**：

1. **品牌感强，机制感弱**。
2. **不知道"军团"= 编排 + 治理 + 可靠性三层**。
3. **缺少落地清单**。

**怎么爬出来**：

```bash
# 落地清单：军团 = 编排 + 治理 + 可靠性
# ① 编排：routing_rules + yield_rules
# ② 治理：ledger + tickets + trust score
# ③ 可靠性：fallback + sentinel + audit log
cat > ~/notes/domain/silicon-life-handbook/legion-checklist.md <<'EOF'
- [ ] 编排：路由 + 让位
- [ ] 治理：账本 + 工单 + 信任分
- [ ] 可靠性：fallback + sentinel + log
EOF
```

**预防**：

- **三个维度全绿，才算"军团"**。
- **对外用标准名 + 职能后缀**（术语表 #8/#9）。
- **真实案例参照**：F6-1、F6-5、F6-11、F6-12。
