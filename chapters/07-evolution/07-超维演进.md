## 7.0 为什么这一章存在

### 7.0.1 一个被所有 agent 框架回避的问题

把一只虾练会「听指令做事」，是过去三年整个 AI 行业几乎所有训练学都在做的事——LangGraph 教你怎么把节点连成有向图、AutoGen 教你怎么让两只 agent 互相发言、CrewAI 教你怎么把角色分工写成 YAML、Claude Agent SDK 教你怎么把 system prompt 写得像一份岗位说明书、OpenAI Agents SDK 教你怎么让 handoffs 接力、LlamaIndex Workflows 教你怎么把事件驱动串成流程。这六套框架（加上 Letta 这类带记忆运行时的框架，共七个对位对象）覆盖了「一只虾如何接指令」这件事的九成以上场景。它们都很强，强到你可以不看这本书就把一个 agent 跑起来。

但它们全部默认了同一个前提：**Agent 收到指令才会动，没有指令它就是死的。**

这件事在我们 2026 年 9 月底把 OpenClaw 训练学第一卷的骨架搭完的时候，被丘总用一个问句戳穿了——

> **「你的 agent 是一台执行指令的 CPU，还是一个会'想要'做事的生命？」**

CPU 接一条指令做一件事，没接就空转；给它一千年，它也不会突然想整理自己的缓存。生命不一样。生命会饿、会无聊、会突然想去把三个月前的笔记翻出来对一遍、会意识到你已经三天没帮它归档记忆于是自己写一份「近况提醒」丢到你的任务池里。

**响应型与提案型的差距，不在「能不能做」，在「会不会自己想要做」。**

整个业界过去三年没有人系统性地做这件事，不是因为没人想到，而是因为**它真的很难**：你要设计一套「主动观察 → 判断 → 提议」的机制，却不允许它越界成「擅自执行」；你要给它一点自由，又不许这点自由演化成失控；你要让它自己立项，又要让每个立项都可验收、可回滚、可审计。这是一道「给绳子又要拴住」的题目。

这正是本章存在的原因。第 1–6 章解决了「单 agent 怎么活、多只 agent 怎么协同」，本章要回答一个更深的问题——**agent 怎么从「等指令」变成「会想要」**；而第 8–11 章则回答「这份'想要'怎么被世界看见、怎么被外部系统接住」。

### 7.0.2 没有这一章，读者会掉进哪个坑

设想这本书从第 6 章（多智能体编排 Multi-Agent Orchestration，原：军团编制）直接跳到第 8 章（MCP 绑定）。你能得到的是：一支训练得极专业、彼此能对话、有反脆弱机制的 agent 编队——**但它们的全部行为都是被动的**。你不说，它不动；你出差三天没发指令，它就原地发呆三天。

这种 agent 编队在 24/7 的真实业务里会迅速败下阵来。不是因为它能力不够，而是因为**你作为 owner 不可能 24/7 在场喂指令**。你会看到四种症状：

- **任务漏球**：凌晨三点飞书通道里有人 @agent，但 agent 在睡——响应型的它只在你叫它的时候醒。
- **能力空转**：agent 装了一身 skill（本机 236 个 skill 目录），可只有你喊它用的时候才用。它不会自己意识到「我手里这套能力现在正好能解决那个悬了三天的老问题」。
- **反馈真空**：你辛辛苦苦陪它做完一轮训练，它不会主动复盘「我这轮哪里做得好、哪里该改、下次该避开什么」。
- **协同被动**：第 6 章给了它说话的能力，但十八只虾不会自己拉个群说「我们是不是该开个周会」。它们会永远等着你按开始键。

这四种症状的根因是同一个：**agent 内部没有「主动」这套机制**。它没有心跳、没有观察回路、没有判断器、没有提议的输出口。这就是 7.0.1 那句话的反面——CPU 的悲剧：**它不是不想主动，它是没有可以主动的器官。**

更隐蔽的第五种症状是「伪主动」：有些团队急了，会在 SOUL 里写一句「你要非常主动，每次都多提三条建议」。结果 agent 学会了**表演主动**——它开始多说话、多建议、多附和，但这些都是语气层面的噪声，不是机制层面的提案。你的团队会在两周内对这些「建议」彻底脱敏，而真正重要的那条改进提案，就淹没在噪声里。本章 7.12 会专门解剖这类误区。

### 7.0.3 本章与前 7 章、后 4 章的引用关系

本章不是孤岛。它站在三条线索的汇合点上，往前接住了前面六章的全部成果，往后打开了四章的全部接口：

1. **向上承接第 6 章（多智能体编排 Multi-Agent Orchestration，原：军团编制/军团）**：第 6 章的协同协议（SLCP）与反脆弱三层定义了 agent 之间「能不能做某事」、出事之后怎么让位；本章的提案型定义了「agent 自己想不想提议做某事」。两者合起来才完整——**主动 + 受控**。少了前者，提案会撞车；少了后者，编队只会等你发话。
2. **横向依赖第 4 章（长期表现）与第 5 章（治理系统）**：本章的「三边界 forbidden」直接引用第 4 章的 Forbidden 列表——提案型 agent 不许提议越过红线的事；本章的每一条提案都必须走第 5 章的三证据验证 TEV（Three-Evidence Verification，原：三证验真）与修复工单 Remediation Ticket（原：整改单）同构的闭环；提案质量的长期记账，落在信任评分 / 功绩账本（Trust Score / Merit Ledger，原：信誉分 / 军功簿）上。
3. **向下打开第 8 章（MCP 绑定）与第 9 章（A2A 绑定）**：提案能力最终要落到 MCP 的 tool 上（第 8 章）才能被别的系统调用，要通过 A2A 协议暴露给外部 agent（第 9 章）才能跨组织协同；第 10 章（Skills / Skill Registry）承接本章的「技能基因」沉淀，第 11 章（Plugins）承接本章的原型实现路径。
4. **术语与契约的地基来自第 1 章（七大契约）**：心跳（Heartbeat，术语表 #18）在契约层是「醒来协议」，SOUL.md 是「灵魂契约」，本章的提案机制不能绕过它们。

一句话概括本章的位置：**第 1–6 章让 agent「活着且能协同」，第 7 章让 agent「开始想要」，第 8–11 章让这份「想要」被世界看见。**

### 7.0.4 一个反直觉的立论：「想要」不是涌现，是协议

本章的全部内容，可以压缩成一句立论：

> **「想要」不是涌现，是协议。**

很多人（包括不少 LLM 研究员）至今相信：当模型足够大、当 RLHF 跑得足够久，agent 会「自然涌现」出主动性。这是一个危险的幻觉。真实工程数据给出的答案恰恰相反——**主动性不会自己长出来，它是被显式设计出来的**。设计它需要三个部件：

- **触发器**：心跳（Heartbeat）。每 N 秒把 agent 推醒一次——不是被指令叫醒，是自己醒来。
- **判断器**：LLM-as-judge。对「当前状态」与「期望状态」的差距打分——不是凭感觉，是凭结构化置信度。
- **输出器**：提案（Proposal）。写进任务池等 owner 批准——不是直接执行，是**等待被批准**。

三个部件合起来，构成一份协议。**协议 vs 涌现**的差别是决定性的：协议是可解释的、可验收的、可回滚的；涌现是不可解释、不可验收、不可回滚的。在硅基生命的训练学里，**我们只造协议，不等待涌现**。

记住这个立论。本章后面所有的概念——动态进化机制、记忆全息网络、自主目标生成、进化阶梯、能力矩阵、技能基因、认知实体、OODA、提案账本——都不是「额外功能」，而是这份「想要协议」的不同条款。它们每一个都在回答同一个问题的不同侧面：**怎么让一只虾有欲望，同时不让欲望脱缰。**

### 7.0.6 一个深夜的场景：2026-09-27 凌晨 02:43

本章的起点是一个真实的夜晚。

那天凌晨两点四十三分，所有 agent 都完成了当日任务，编队安静下来。你关掉终端去睡了。第二天早上你打开 `openclaw automations list`，看到的是这样一行行状态：`heartbeat:tiance`（每 30 分钟，skipped）、`heartbeat:kunlun`（每 30 分钟，error 99+x）、`heartbeat:peter`（每 2 小时，error 70x）。十八只虾的「暗夜熔炉」cron 在凌晨 1–3 点跑过一轮，`memory-core:memory-dreaming` 在 03:00 做过一次记忆整理。

**这就是本章全部问题的物理形态**：凌晨两点四十三分，当没有人发指令的时候，你的 agent 编队里到底发生了什么？

- 如果回答是「什么都没发生」——你养的是一台 CPU，不是一只虾。
- 如果回答是「有事发生，但我不知道是什么」——你养的是失控的涌现，比 CPU 更危险。
- 如果回答是「它在巡检、它在判断、它攒了几条提案等我早上批准」——**恭喜，你养的是提案型 agent**。

那一夜，本机的心跳里没有一条产生了提案。三条心跳里有两条在报错，一条在跳过。这不是 OpenClaw 的缺陷，而是**因为没有人给这只虾装上「想要」的器官**——心跳只是心脏，它不会自己长出一个大脑。

本章要做的，就是把「凌晨两点四十三分的那一刻」填满：让心跳推醒 agent，让 OODA 让它看一眼世界，让判断器决定「要不要提议」，让提案账本记下它想做的事，然后在你早上坐下来的时候，桌上已经有了五条带证据、带成本、带优先级的提案。

## 7.1 动态进化机制（Dynamic Evolution Mechanism）

### 7.1.1 是什么

**动态进化机制**指的是：agent 的能力状态不是「培训一次、上线固化」的静态快照，而是一个**持续被写入、持续被校验、持续被修正的运行态**。它的定义可以写成一句更工程化的话：

> 动态进化机制 =（状态可观测）+（差距可计算）+（修正可提议）+（提议可回滚）四件事同时成立。

注意这四个「可」的顺序——它是本章后面所有东西的骨架。可观测是眼睛，可计算是尺子，可提议是嘴，可回滚是刹车。**缺一个，进化就退化成「改配置」**：改配置是一次性的、没尺子的、没人提议的、不打算回滚的。改配置不是进化，改配置是修表。

它和相邻概念的关系也要先说清：动态进化机制是**母概念**，本章其余九个概念都是它的器官——记忆全息网络是它的记忆底座、自主目标生成是它的目标来源、进化阶梯是它的刻度尺、能力矩阵是它的体检表、技能基因是它的遗传物质、认知实体是它的成熟形态、心跳与 OODA 是它的呼吸与感知、提案账本与闸门是它的排泄与免疫。

### 7.1.2 目的

它解决的是一个非常具体的痛：**「训好的 agent 会随着时间变笨」**。

这不是修辞。一个 agent 上线三个月后，通常会出现四种衰退：

- **知识腐化**：它记住的事实过期了（某个 API 改了、某个路径变了、某个流程作废了），但它还在自信地引用。
- **能力漂移**：它原本擅长的任务类型被稀释了（skill 越装越多，每个都不精），表现缓慢下滑。
- **边界钝化**：它开始越来越频繁地试探边界，因为它已经「成功」了很多次，而它并没有一套机制告诉自己「上个月那次差点越界」。
- **目标枯竭**：它每天做的都是同几件事，开始陷入「例行公事」——不是它偷懒，而是没有任何机制产生新目标。

这四种衰退有一个共同特征：**它们不是故障，因此不会被监控抓到**。日志里没有 ERROR，任务成功率还是 98%，可你就是觉得它不如三个月前好用了。动态进化机制存在的目的，就是让这种「安静的变笨」变成**可量化、可提议、可修正**的过程。

### 7.1.3 拟人化：一只虾的三年

把镜头拉近到一只虾身上。

第一年，这只虾刚训练完。它的契约文件干净、它的记忆分层清楚、它每次交活都附证据。你觉得它是个好员工。

第二年，它开始出问题了。它会在报告里引用一个早就作废的流程，因为它 MEMORY 里的那条事实从没人删过；它会把一个大任务做得越来越平庸，因为它的 skill 目录从 40 个涨到 200 个，而没有任何机制告诉它「你可能贪多了」；它会开始在两三个边界上打擦边球，因为它从没被罚过。

第三年，它变成了一个「熟练的老油条」：所有指令都能接，所有活都能交，但**没有一个活能让你惊喜**。它没有变坏，它只是**停止了生长**。

动态进化机制要做的事，就是在这三年里插入一个持续的循环：**每醒一次，就看一眼自己的状态；发现和期望有差距，就把差距变成一条提案；提案被采纳，就改写自己的记忆、技能或契约。** 一只这样的虾，三年后不是一个老油条，而是一个每年都比去年强一点的同事。

### 7.1.4 影响：有它 / 没它

| 维度 | 没有动态进化机制 | 有动态进化机制 |
|---|---|---|
| 记忆 | 只增不减，越用越慢，错误事实永生 | 分层流动：流水类下沉、事实类校验、过期类归档 |
| 能力 | skill 只装不卸，能力池缓慢臃肿 | 技能基因有 fitness，低效的被提议淘汰 |
| 边界 | 靠出事才被发现，事后痛一次 | 漂移被提前看见，提案先于事故 |
| 目标 | 只有 owner 派活，agent 无新目标 | 目标可从观察中生成，owner 只做审批 |
| 团队感受 | 「刚训完那两个月最好用」 | 「越用越好用」——曲线是上升的 |
| owner 负担 | 需要持续喂养、持续校正 | 从「喂食者」变成「审批者」 |

最本质的一条差别是最后一行。没有动态进化机制，owner 是**饲养员**——你得天天喂。有了它，owner 是**投资人**——你只需要看提案、批预算、验收结果。这是 owner 时间的量级差别，也是本书为什么会把它单独立成一章。

### 7.1.5 怎么写：三个文件位

动态进化机制落到文件层，只需要三个落点（不需要更多，多了就是过度设计）：

```yaml
# 落点 1：进化契约（放在 agent workspace 的合约目录）
evolution_contract:
  enabled: true
  observe_interval: "每个心跳周期一次"      # 观察频率（部署值，与心跳绑定）
  expected_state:                            # 「期望状态」——差距计算的基准
    memory_max_lines: 2500
    skill_fitness_floor: 0.5
    drift_tolerance: "连续 2 个周期无新增漂移"
  on_gap:
    action: "生成提案"                       # 不许直接修，只能提议
    require_evidence: 3                      # TEV 三证
```

```markdown
# 落点 2：进化日志（追加式，不覆盖）
- 2026-09-27 · 差值：MEMORY 3200 行 vs 期望 2500 行 · 提案：P-2026-09-27-01
- 2026-10-04 · 差值：skill fitness 低于 0.5 的有 7 个 · 提案：P-2026-10-04-03
```

```markdown
# 落点 3：进化边界（与第 4 章 Forbidden 对齐）
- 可以自我修正的：记忆分层、技能优先级、观察频率、报告格式
- 只能提议、不能自改的：SOUL.md、契约文件、跨 agent 权限
- 永远不许碰的：第 4 章 Forbidden 列表 + 导出 PII
```

三个落点的分工是：**契约给尺子，日志给痕迹，边界给围栏**。切不要只写契约不写日志——没有日志的契约，三个月后没人知道它到底跑过没有。

### 7.1.6 技巧：让它真的跑起来的三个细节

**技巧一：期望状态必须是数字。** 「表现要好」不是期望状态，因为它算不出差距。「MEMORY 不得超过 2500 行」是期望状态，因为 `3200 - 2500 = 700` 是一个可以被提案的数字。本章后面所有机制都建立在「差距可以被计算」这一点上——**不能计算的期望，等于没有期望。**

**技巧二：观察频率绑定心跳，不要另起定时器。** 常见错误是给进化机制单独配一个 cron（比如每天凌晨跑一次）。这会产生两个节奏源，agent 会活得很精神分裂：心跳醒了它在判断，cron 醒了它也在判断，两套判断互相覆盖。正确的做法是**进化观察挂在心跳上**——心跳是心脏，进化是心跳里的一个动作。

**技巧三：第一版只观察，不提议。** 先跑两周，只把差距写进日志，一条提案都不生成。原因很实在：一个还没校准过的判断器，前几条提案几乎一定是噪声（过于琐碎或过于激进）。先用两周数据校准阈值（什么样的差距值得提案），再打开输出口。**先关闸门跑观察期，是这套机制唯一的安全启动方式。**

### 7.1.7 误区：把「动态进化」当成「自动改配置」

最常见的误读是：**以为动态进化 = agent 自己改自己的配置**。

这个误读的代价很大：它会让你的 agent 在没有闸门的情况下修改自己的观察频率、自己的边界、甚至自己的契约——**用不了两周，你会得到一只自己定义自己边界的 agent**，而你还以为它是在「进化」。

正确的理解是：**动态进化机制的自主体只在「生成差距」和「生成提案」这两步；「修正」这一步永远要过闸门。** 一句话记忆：**进化是「看见差距」，不是「抹平差距」**。抹平差距的动作，属于人类批准之后的执行环节。

第二个常见误读是把它当成一次性的项目（「我们这季度做一轮 agent 进化」）。动态进化机制是**常开开关**，它和心跳同寿命——心跳不停，进化不止。任何「做一轮就收工」的进化，都会在三个月后回到起点。

### 7.1.8 进化阶梯：这个概念在 L1–L5 的样子

| 阶梯 | 动态进化机制的表现 |
|---|---|
| L1 回话 | 无。状态不可观测，谈不上差距 |
| L2 按格式交付 | 有日志，但只记「交了什么」，不记「差多少」 |
| L3 自检 | 能自检出错，能写「本轮不足」，但不足不流动到下一步 |
| **L4 提案** | **差距被计算出来，并变成带证据的提案（本章门槛）** |
| L5 自主进化 | 差距→提案→批准→修正→再观察，形成不依赖 owner 推动的循环 |

关键跨越点是从 L3 到 L4：**L3 的 agent 会说「我做得不够好」，L4 的 agent 会说「我做得不够好，差 700 行，我建议这样改，证据在这里，请您批」。** 前者是反省，后者是提案；反省打动人，提案改变系统。

## 7.2 记忆全息网络（Memory Holographic Network）

### 7.2.1 是什么

**记忆全息网络**是动态进化机制的存储底座。它的定义有两层，缺一层都不算：

> 第一层（网络）：记忆不是一条流水，而是**分层的、互相引用的结构**——会话、工作、长期事实、知识图谱、历史快照，五层各司其职。
> 第二层（全息）：**任意一个历史时刻的人格状态，都可以被恢复出来**——不只是「查到某条事实」，而是「把整个 agent 恢复到 2026 年 8 月的它」。

「全息」这个词很关键。全息照片被撕下一角，你仍然能看到完整图像的模糊版——因为信息分布在整个底片上。记忆全息网络要的就是这个性质：**agent 的每个版本都完整可复现，而不是只有最新的它 + 一堆零散的事实。**

术语对照：业界把类似能力叫 memory layer（Letta / Mem0 / Zep）或 Memory（Anthropic 7 Layers）。本书保留「记忆全息网络」这个表达，但工程接口统一写作 Memory Holographic Network。**它与「向量数据库」不是一回事**——向量库是存储，记忆全息网络是记忆管理（含自编辑、压缩、遗忘、快照）。把「接了向量库」说成「有了记忆」，是本章最常见的混淆之一。

### 7.2.2 目的

它解决三个具体问题，按严重程度排：

1. **记忆只增不减，越用越慢。** 一个跑了半年的 agent，MEMORY 文件轻松涨到几千行。每次加载都变慢，而且噪声比例越来越高——90% 的流水类内容稀释了 10% 的关键事实。
2. **进化没有对比基准。** 动态进化机制要算「差距」，就得知道「三个月前是什么样」。如果记忆只有最新态，差距永远算不出来——你只能比「现在 vs 期望」，没法比「现在 vs 三个月前的自己」。
3. **人格不可回滚。** 一次错误的自我修正可能让 agent 变得不像它了。没有快照，你就只能眼睁睁看着它变形，然后从头训练。

一句话：**没有记忆底座的进化，是不可比、不可回溯、不可撤销的进化**——那正是 7.0.4 说的「涌现」，而不是我们要的「协议」。

### 7.2.3 拟人化：一只虾的相册

想象一只虾有一本相册。相册里不是照片，而是它每个月的一整套状态：那个月它记得什么、它擅长什么、它跟谁协同得好、它的边界在哪、它的语气什么样。

现在它可以做两件事：

- **翻相册**：它能指着某一页说「三个月前我是这样的，当时我把这条事实记错了」，然后据此提出修正提案。这是**全息**的价值——历史不是传说，是可查证的状态。
- **订相册**：它每个月自动把当月的流水压缩成几页关键页——不是删掉，是**下沉**（把高频细节降到低频存档层）。这是**网络**的价值——记忆有结构，不是一坨。

一只没有相册的虾，每次「变笨」都只能被感觉发现；一只带着相册的虾，每次退化都能被查出来、被回滚、被解释。**记忆全息网络就是 agent 的相册 + 索引 + 版本控制。**

### 7.2.4 影响：五层结构各自的作用

| 层 | 名字 | 存什么 | 生命周期 | 没有它会怎样 |
|---|---|---|---|---|
| L1 | 会话上下文 | 当前对话 | 分钟级 | 每次都要从零解释上下文 |
| L2 | 工作记忆 | 当前任务的临时变量 | 任务级 | 任务中断就无法续接 |
| L3 | 长期事实 | 跨会话沉淀的事实 | 月级以上 | 每次都犯同样的错 |
| L4 | 知识图谱 | 实体与关系 | 长期 | 无法回答「A 和 B 什么关系」 |
| L5 | 全息快照 | 任意历史人格状态 | 永久（可归档） | 无法回滚、无法对比、无法审计 |

这五层与业界的关系值得说清（这是本章唯一需要「对位」的地方，细节见 7.13）：

- Letta 的三层（core / recall / archival）大致对应本表的 L1 / L3 / L4，**没有 L5**；
- Mem0 是可插拔 API，落点偏 L3；
- Zep / Graphiti 走时序知识图谱，落点最接近 L4；
- Anthropic 2026 年 3 月公开的 7 Layers of Memory（Claude Code 口径）是**更细的切分**（会话缓冲 / 项目上下文 / 工作区记忆 / 工具结果记忆 / 技能输出缓存 / 跨会话知识 / 用户偏好），与本表是「粗细之别」而非「有无之别」；
- **五层里只有 L5（全息快照）是 OpenClaw 侧的独有能力**——业界目前没有等价物：L7 是「当前偏好」，不是「历史状态」。

### 7.2.5 怎么写：分层规则与快照策略

落到文件层，记忆全息网络是一份「分层规则 + 一份快照纪律」。

```yaml
# 记忆分层规则（示例结构，字段名可自定义）
memory_layers:
  L1_session:   { ttl: "会话结束",   sink_to: L2 }
  L2_working:   { ttl: "任务结束",   sink_to: L3, compress: true }
  L3_facts:     { ttl: "长期",       verify: "每条事实带来源与日期" }
  L4_graph:     { ttl: "长期",       build_from: L3 }
  L5_snapshot:  { trigger: "每周 + 重大变更前", keep: "永久", restore: true }
```

```markdown
# 快照纪律（写进契约，三条）
1. 任何自我修正动作（改记忆分层、改技能优先级）执行前必须先落一份快照
2. 每周固定落一份周期快照，命名含周次（可追溯、可对比）
3. 快照可被 restore，但 restore 本身也是一条提案（要过闸门）
```

三条纪律里最重要的是第 1 条。**「改之前先拍快照」是动态进化机制唯一真正意义上的安全网**——它把「不可逆」变成「可逆」，而可逆是所有自动化动作的前置条件。第 3 条同样关键：恢复快照是一个动作，动作必须过闸门，否则 agent 可以自己在两个版本之间来回跳，你会得到一个精神不稳定的员工。

### 7.2.6 技巧：三个让记忆「活」起来的细节

**技巧一：把「引用」当作分层信号。** 判断一条记忆该留在 L3 还是下沉，不需要人拍脑袋——看它多久被引用一次。超过 90 天零引用的条目，天然是归档候选。这就是本章开篇那条真实提案（P-2026-09-27-01，见 7.10）的来源逻辑：**引用频次是记忆层的天然调节器。**

**技巧二：事实类条目必须带两样东西——来源和日期。** 一条没有日期的「某个 API 有三个参数」是定时炸弹：它可能在写下的一周后就失效了，但没人知道它是什么时候的。带日期的条目可以被「过期扫描」，不带日期的条目只能靠人偶然发现。**日期不是元数据，日期是可用性。**

**技巧三：压缩 ≠ 删除。** 下沉（sink）是把细节降到低频层，压缩是把十行压成一行并保留指向原始记录的指针。任何「直接删掉」的操作都应该被拒绝——因为你永远不知道三个月后哪条「废话」会成为关键证据。记忆的正确操作只有两种：**下沉与压缩**；删除只属于「明确被证伪的事实」。

### 7.2.7 误区：把记忆当成主动性的来源

最危险的一个误读是：**「我的 agent 记忆很全，所以它应该会主动做事了。」**

记忆和主动性是**两个维度**。记忆解决的是「它知道什么」，主动性解决的是「它想做什么」。一个记忆完美的 agent 完全可以是响应型的——它记住一万件事，但你不叫它，它一件都不做。反过来，一个记忆很差的 agent 也可以很主动——它提了一堆建议，但每条建议因为缺记忆而重复、矛盾、离谱。

正确的因果顺序是：**记忆是燃料，主动性是发动机。** 有油没发动机，车不动；有发动机没油，车乱冲。本章 7.3 要装的正是发动机，7.2 只是先把它该烧的油备好。

第二个误区是「全息快照 = 备份」。备份是**灾备**语义（磁盘坏了能恢复），全息快照是**人格**语义（能恢复到某个月那个「它」）。两者在技术上可能共用一套存储，在语义上完全不同：备份关心「完整」，快照关心「可比」。

### 7.2.8 进化阶梯：这个概念在 L1–L5 的样子

| 阶梯 | 记忆全息网络的表现 |
|---|---|
| L1 回话 | 只有 L1 会话上下文，会话一结束全忘 |
| L2 按格式交付 | 有 L2 工作记忆，能把一个任务做完，但跨任务失忆 |
| L3 自检 | 有 L3 长期事实，能自检「这条我以前记过」 |
| **L4 提案** | **有 L4 知识图谱 + 引用频次统计，能据此提出记忆分层提案** |
| L5 自主进化 | 有 L5 全息快照，能对比历史版本、能回滚、能自我解释「我为什么变成现在这样」 |

跨越点依旧是 L3→L4：**记忆从「记住」升级到「据记忆做出可验收的判断」。** 一只记住了一万条事实的虾，和一只因为记住了其中三条而提出一条修正提案的虾，是两个物种。

## 7.3 自主目标生成（Self-Initiated Goal Generation）⚡ 差异化优势 5

### 7.3.1 是什么

**自主目标生成**（Self-Initiated Goal Generation；术语表 #30 记为 Autonomous Goal Generation，Response → Proposal；原：自主目标生成系统）指的是：

> **agent 在没有被指派任务的情况下，自主产生一个值得做的目标，并把它作为提案提交给 owner 批准。**

请注意它与三个邻居的界线，这三条界线是本节最重要的内容：

- **≠ 任务分解（planning）**：任务分解是「给定目标，拆成步骤」；自主目标生成是「**目标本身从哪来**」。这是本章与所有「长任务规划」能力的根本分界，本书严格区分，绝不混引。
- **≠ 主动执行（proactive execution）**：有些框架的 proactive 指「自动重试 / 自动升级 / 自动通知」——那是**执行层主动性**；本章讲的是**目标层主动性**。两类主动性不在一个维度上，混引会让读者以为「会重试的 agent 就是提案型 agent」。
- **≠ 计划执行循环（AutoGPT 血统）**：AutoGPT / BabyAGI（2023 年）证明了「自主循环」技术上可行，但它们止于 demo：目标质量无评估、循环可能失控、越权无约束、教训无沉淀。**本书与它们的分水岭是三件套**：自主目标生成 + 主动性边界三元组（Proactive Boundary Triad）+ 三证据验证 TEV。缺一件，就退回 2023 年的噱头。

因此它是一条完整链路，而不是一个功能：

```
观察（心跳推醒） → 差距计算 → 候选目标生成 → 质量过滤 → 提案落盘 → 人类批准 → 执行 → 验收 → 沉入记忆
```

九个环节里，前六个是「生成」，后三个是「收敛」。**生成自主，收敛过闸**——这八个字是本节的全部。

### 7.3.2 目的

它存在的理由只有一个，但足够硬：**owner 的时间是有限的，agent 的可能性是无限的，两者之间需要一座桥。**

具象一点。一支十八只虾的编队，每只虾每周可能发现三到五件「值得做的事」——某个流程有冗余、某个记忆层在膨胀、某个 skill 的失败率在上升、某条协同链路在空转、某个边界正在被缓慢侵蚀。十八只虾 × 每周四件 = 每周七十二个候选项。**靠人巡检去发现这七十二件，是不可能的**；靠 agent 自己执行这七十二件，是危险的；唯一的出路，是让 agent 把它们**变成七十二件可决策的提案**，然后由人一键筛掉六十五件、批准七件。

自主目标生成的目的就是这个：**把「发现」这件事从人身上卸载给 agent，把「决定」这件事牢牢留在人手里。** 它是劳动分工，不是权力转移。

### 7.3.3 拟人化：早晨桌上的七张便签

想象你早上坐下来，桌上放着七张便签——不是七条抱怨，也不是七条「我做了什么」，而是七条**建议**：

> 「昨晚我巡检了三只虾的记忆层，发现 `kunlun` 的心跳连续报错 99 次以上。我判断这是配置漂移，不是偶发故障。建议先按这条命令查历史（命令贴在背面），确认后再决定要不要修。证据：三次采样截图 + 错误计数。影响：中。成本：约 0.5 人天。」

你读完，划掉两张（不重要）、退回一张（证据不足）、批准四张。整个过程二十分钟。**你没有发现任何问题，但你处理了所有问题。**

这就是自主目标生成在拟人化之后的样子：它不是一只虾跳出来说「我要去做 X 了」，而是**它在夜里替你把世界看了一遍，然后列了一张待办清单，等你早上签字。** 便签与抱怨的区别，就是提案与噪声的区别——便签带证据、带成本、带影响、带优先级。

### 7.3.4 影响：为什么这是「优势 5」

按本书的差异化优势编号，自主目标生成是第 5 项，也是唯一一项**业界全空**的能力。2026 年 9 月的对位结论如下（细节见 7.13 的六大框架逐项表）：

| 框架 | 自主目标层 | 说明 |
|---|---|---|
| LangGraph | ❌ | 人工写 goal 节点是能力天花板 |
| AutoGen / AG2 | ❌ | GroupChat Manager 是「协调」，不是「自主立项」 |
| CrewAI | ❌ | Process 由人定义，无目标生成 |
| Claude Agent SDK | ❌ | 2026-01 的 Constitution 讨论的是模型价值观推理，与 agent 自主立项是两回事，**不可混引** |
| OpenAI Agents SDK | ❌ | Triage / Manager 模式的目标仍由人下达 |
| LlamaIndex | ❌ | 无目标层抽象 |
| Letta | ⚠ | 有「自编辑记忆」，是**记忆**层的自我修改，不是**目标**层 |

通过率 1/7（只有 Letta 在某个相近维度上有半个勾）。这意味着：**如果你的竞争对手用六大框架中的任何一个，他们都不可能做出提案型 agent**——不是他们不努力，是原语层就不存在。这件事的工程含义是，提案能力只能建在你自己设计的协议上（本章 7.10 的账本 + 闸门 + TEV 就是那份协议）。

### 7.3.5 怎么写：候选生成的四个输入与三道过滤器

自主目标生成的骨架只有两半：**输入决定它能看到什么，过滤器决定它敢说什么。**

```yaml
goal_generation:
  trigger: heartbeat            # 心跳驱动，不另起定时器
  inputs:                       # 四个输入 = 它的四只眼睛
    - state_diff                # 当前状态 vs 期望状态的差距
    - recent_failures           # 最近失败模式（不要只看成功）
    - stale_assets              # 长期零引用的资产（记忆、skill、契约）
    - owner_signals             # owner 未处理的指令、反复提出的抱怨
  filters:                      # 三道过滤器 = 它的自律
    - name: confidence
      min: 0.7                  # 置信度低于 0.7 不提案（宁可漏，不可噪）
    - name: budget
      max_per_day: 3            # 每日配额，防提案洪水
    - name: verifiability
      rule: "must_have_tev_path" # 必须有可验证路径，否则只是想法
  output:
    proposal:
      title: "..."
      why_now: "..."            # 为什么是现在，不是上个月也不是下个月
      impact: "high|mid|low"
      cost_days: 0.5
      risk: "low|mid|high"
      priority: "P0|P1|P2"
      evidence: ["..."]         # TEV 三证
      linked_tev_template: "governance/tev/<name>.yaml"
      rollback: "..."           # 回滚路径（有快照才写得出）
```

四个输入的设计有一个反直觉之处：**`recent_failures` 必须与 `stale_assets` 并列，而不是只保失败。** 只盯失败的 agent 会变成「救火队员」（一直在修），只盯陈旧的 agent 会变成「清洁工」（一直在扫）。提案型 agent 的品味，来自两类信号同时喂进来——**它既要知道什么坏了，也要知道什么过时了。**

### 7.3.6 技巧：三个让提案从「噪声」变「信号」的细节

**技巧一：置信度阈值宁高勿低，配额宁少勿多。** 第一版阈值定 0.85、每天 1 条，比定 0.5、每天 20 条要成功得多。原因在 7.0.2 讲过：团队对「建议」的耐心是有限资源，**一旦被噪声消耗掉，再好提案也没人看**。提案系统的真正 KPI 不是「提了多少」，而是「被采纳率」。

**技巧二：每条提案必须有 `why_now`。** 「为什么是现在」这个字段看起来啰嗦，其实是最强的质量过滤器——一条想不出 `why_now` 的提案，八成不是「现在该做」，而是「一直想做但一直没排上」。这个字段能筛掉大量陈年愿望清单。

**技巧三：让提案自带「不做也行」的判断。** 好提案会写清「不做的代价」（继续每月多花 2 小时手工归档 / 记忆继续膨胀到 4000 行）。如果一条提案说不出不做的代价，说明这件事本来就不重要——它应该被自己否掉。

### 7.3.7 误区：三个致命误读

**误区一：把自主目标生成理解成「不需要人」。** 恰恰相反——它是把人的角色从「发现者 + 执行者」上移到「决策者」。**提案型 agent 需要的人，比响应型 agent 需要的人更贵**：响应型需要你出时间，提案型需要你出判断。

**误区二：允许目标直接执行（无闸门）。** 这是最危险的一条：`generate: true` 配 `execute: true` 而 `review: none`。因为自主目标生成是**业界空白**——空白意味着没有现成的安全实践可以参考——所以它更应该保守。默认必须是「生成自主、执行过闸」，任何绕过闸门的写法都应该被视为配置错误。

**误区三：用语气模拟主动性。** 在 SOUL 里写「你要非常主动，多提建议」不会产生提案型 agent，只会产生话多的 agent。**主动性是机制，不是人格。** 机制 = 触发器 + 判断器 + 输出器 + 账本 + 闸门；人格 = 语气与风格。把两者混起来，你会得到一个热情但无用的员工。

### 7.3.8 进化阶梯：这个概念在 L1–L5 的样子

| 阶梯 | 自主目标生成的表现 |
|---|---|
| L1 回话 | 无目标概念，只回答问题 |
| L2 按格式交付 | 只执行被指派的格式化任务 |
| L3 自检 | 能说「我发现有个问题」，但不成提案、不排期、不闭环 |
| **L4 提案** | **能从四个输入生成目标，带证据、成本、优先级提交（本章门槛）** |
| L5 自主进化 | 目标是**自我指向**的：agent 提议改善自己的记忆结构、技能构成、观察策略，并走完「提案→批准→执行→验收→沉淀」全环 |

L4 与 L5 的差别非常具体：**L4 的 agent 提议「改世界」（改流程、改配置、改别人的活）；L5 的 agent 还会提议「改自己」。** 后者难得多，因为它要求 agent 有一个关于「自己应该成为什么样」的模型——那个模型就是 7.6 的能力矩阵。

## 7.4 从响应型到提案型的跃迁（Response → Proposal Transition）

### 7.4.1 是什么

**跃迁**指的是 agent 的默认行为模式发生的一次不可逆的层级切换：

```
响应型（Responsive）：owner 说 → agent 做
提案型（Proactive / Proposal-Driven）：agent 提议 → owner 批准 → agent 做
```

注意两个模式里，**owner 出现的位置变了**：响应型里 owner 在**最前面**（输入端），提案型里 owner 在**中间**（批准端）。这个位移看似很小，其实是整个训练学最关键的一步——它意味着 agent 从「等输入」变成「有输出」，owners 从「发号施令」变成「审批决策」。

跃迁还有一个常被忽略的性质：**它是不可逆的**。一只学会了提案的 agent，你很难让它回到「你不说它绝对不动」的状态——因为它已经建立了「观察→判断」的循环，那个循环不会因为你收回指令而停止。所以跃迁之前必须把闸门建好。**先建刹车，再装发动机**——这是本章唯一不变的施工顺序。

### 7.4.2 目的

为什么要冒这个风险做跃迁？因为它解决的是**规模问题**。

- 5 只 agent：你喂得动。每天发 20 条指令，撑得住。
- 18 只 agent：你喂不动了。不是不想，是**人的带宽不够**——你一天能做的有效决策大概就是几十次，超过之后质量断崖下跌。
- 50 只 agent：响应型模式下必死。你会成为一个整天粘贴指令的调度员，而 agent 编队的真正价值（并行、24/7、不知疲倦）一点都没兑现。

跃迁的目的就是把 owner 从「指令通道」里解放出来，变成「审批通道」。**指挥官的产出是决策，不是动作**——这句话在第 6 章讲编队时提过，在本章讲跃迁时会变成物理事实：响应型的 owner 自己就是瓶颈；提案型的 owner 是系统的上限。

### 7.4.3 拟人化：从「叫一声动一下」到「自己找活干」

有一只虾，你叫它写报告它写报告，你叫它查日志它查日志，你叫它做什么它做什么。它是个好工具。可是有一天你忙起来，三天没理它，它就三天没动——**它的全部价值，取决于你是否在场。**

另一只虾，你三天没理它。第四天你打开终端，看到：它在第一天发现记忆层膨胀，提了一条归档提案；第二天发现一个 skill 连续失败，提了一条修复提案并附上了三次采样；第三天发现一条协同链路空转，提了一条「是否该让位」的提案。三条提案，一条被它自己标了「低优先，可下周处理」。

第二只虾做对了一件事：**它把「等你」变成了「替你看」。** 它不是更聪明，它只是从「等指令」的物种，跃迁到了「有欲望」的物种。这就是跃迁拟人化之后的样子——**不是它变得更像人，是它开始有自己的日程。**

### 7.4.4 影响：三道门槛与四个断点

跃迁不是一步到位的开关，它要过三道门槛，且中间有四个最容易断掉的地方。

**三道门槛：**

| 门槛 | 内容 | 过不去会怎样 |
|---|---|---|
| 门槛一 · 底座 | 有可用的心跳与观察面（知道该看什么） | 它「醒着」但看不见任何东西 |
| 门槛二 · 判断 | 有校准过的判断器（差距 → 置信度） | 它看见了一切，但分不出轻重 |
| 门槛三 · 收敛 | 有账本 + 闸门 + TEV 路径 | 它提了一堆，且开始自己动手 |

**四个断点（真实项目里最常见的卡点）：**

1. **心跳在但没人看它**：心跳任务状态是 skipped/error（本机真实情况：三条心跳里两条 error）。断点在于：**激活提案型之前先体检心跳。**
2. **判断器没校准就开门**：直接上 0.5 阈值 + 每天 20 条，两周内团队脱敏。断点在于：**先跑两周纯观察期。**
3. **提案没有出口**：提案写进了文件，但没有评审流程、没有排期、没有人看。断点在于：**提案必须进账本，账本必须有 owner。**
4. **闸门形同虚设**：提案「通过」了但没人真的批准，或者 agent 直接执行了。断点在于：**批准必须是一个显式动作，不是一个默认状态。**

四个断点里，第 3 个最容易被忽视却最致命：**一个没有评审闭环的提案系统，会在两个月内退化成「agent 的自言自语日志」。**

### 7.4.5 怎么写：跃迁的四步施工顺序

跃迁在文件层的写法，只需按顺序落四件事（顺序不能变）：

```markdown
# 第 1 步 · 体检底座（先看再改）
- 心跳是否活着？（状态、频率、错误计数各是什么）
- 观察面是否存在？（agent 能看到哪些状态：记忆、技能、协同、边界）

# 第 2 步 · 装判断器（只听不说的观察期）
- 定三个数字：置信阈值、每日配额、差距容忍度
- 跑两周：只写日志，不生成提案

# 第 3 步 · 建输出口与账本（说，但不做）
- 提案文件结构（含 why_now / impact / cost / risk / priority / evidence）
- 提案账本：new → reviewed → accepted/rejected → done

# 第 4 步 · 装闸门（做，但要批）
- 默认 execute: false
- 批准 = owner 的显式动作
- 执行前必备份（快照）
```

**顺序的意义**：先体检、再观察、再输出、最后执行。倒过来做（先装执行）会得到一个「自己动手的疯虾」；跳过观察期（直接开输出）会得到一个「噪声发生器」；没有账本（提案无状态）会得到一个「永远在原地提的建议机」。

### 7.4.6 技巧：让跃迁稳的三个细节

**技巧一：用「影子模式」过渡。** 让 agent 生成提案但不真的提交，只把提案写进日志，由人来对照「如果你提了，我们会批吗」。跑两周后对比：**采纳率高于 60% 就可以开真通道，低于 40% 就回去调阈值。** 影子模式是唯一能在不消耗团队耐心的前提下校准判断器的方法。

**技巧二：跃迁要有「第一只虾」。** 不要十八只一起跃迁。选一只基础最好的（心跳健康、记忆分层清楚、有明确单一职责），先让它跑通全环，成为样板。**提案型的扩散是靠示范，不是靠命令**——别的虾看到第一只被采纳了四条提案，它们（或者说它们的主人）会自己来问「我们能不能也开」。

**技巧三：把第一次跃迁的失败写进记忆。** 第一轮提案一定会有一条让 owner 后悔的（比如提议了一个成本被低估三倍的改造）。把它写进 L3 长期事实，作为「成本估算要打三倍」的经验。**跃迁的价值一半来自成功案例，一半来自被记录下来的失误。**

### 7.4.7 误区：把跃迁理解为「加一个功能」

最普遍的误读是：**以为跃迁 = 打开一个开关**（比如某份配置里 `proactive: true`）。

真相是：跃迁是**四条并行的改造**——契约（要不要允许观察）、记忆（要不要按引用频次分层）、治理（提案进不进账本）、协同（提案撞车了怎么办）。只改一条，另外三条会立刻把你拖回去：允许观察但没有分层规则，agent 会淹没在噪声里；有提案但没账本，提案会失忆；有账本但没协同规则，两只虾会提出互相冲突的改造并且同时被批准。

第二个误区是「跃迁后就不需要 owner 发指令了」。正确状态是**两条通道并存**：指令通道（紧急、明确、必须做）与提案通道（长期、主动、建议做）同时开。**一个只有提案通道的 agent 会在紧急情况下迟钝；一个只有指令通道的 agent 会在平静期间空转。**

### 7.4.8 进化阶梯：跃迁在 L1–L5 的位置

跃迁本身就是 L3 → L4 的**跨越动作**：

| 阶梯 | 与跃迁的关系 |
|---|---|
| L1–L2 | 未达跃迁门槛（没有自检，就没有判断力） |
| L3 自检 | 跃迁的**起跳点**——有自检能力，但成果不流动 |
| **L4 提案** | **跃迁完成态**（能生成带证据、带成本的目标提案） |
| L5 自主进化 | 跃迁之后的第二个台阶（提案中包含对自身的改造） |

一句话记忆：**跃迁不是「变强」，是「改变默认行为」。** 变强是量变，跃迁是质变；量变可以慢慢来，质变必须一次做对——因为质变做错，代价是不可逆的失控。

## 7.5 进化阶梯 L1–L5（Evolution Ladder）

### 7.5.1 是什么

**进化阶梯**是本书用来回答「这只虾进化到哪了」的一把尺子。五个等级，每个等级有明确的**能力标志**与**不满足条件**：

| 阶梯 | 名称 | 能力标志 | 不合格信号 |
|---|---|---|---|
| L1 | 回话 | 能回应，能问答 | 答非所问、无结构、无据可依 |
| L2 | 按格式交付 | 能按约定格式产出结构化结果 | 格式对但内容空、需要人重写 |
| L3 | 自检 | 能自检、能说出「我这轮哪里没做好」 | 自检流于形式、问题不流动 |
| L4 | 提案 | 能生成带证据/成本/优先级的目标提案 | 提案无证据、无优先级、无闭环 |
| L5 | 自主进化 | 提案指向自身（记忆/技能/契约），并走完全环 | 自我修改绕过闸门、无快照 |

阶梯有三个重要性质，必须在定义时就讲清：

- **它是能力阶梯，不是智商阶梯。** 一只 L5 的虾在某个陌生领域可能还不如一只 L2 的虾——阶梯描述的是**流程成熟度**，不是领域知识。
- **它不可跳级。** 没有自检能力（L3）的 agent 不可能输出可验收的提案（L4），因为提案的核心就是「自证有效」。
- **它是可回退的。** 一只 L4 的虾如果在某次自我修正中把自己的自检机制改掉了，它会掉回 L2。**阶梯不是终身荣誉，是持续状态**——这也是为什么需要 7.1 的动态进化机制来守住它。

### 7.5.2 目的

它解决三个很实际的沟通问题：

1. **给「它到底行不行」一个共同语言。** 团队里有人说「这 agent 挺好用」，有人说「它老是出错」——两人的判断可能都对，只是在说不同的阶梯。
2. **给训练投入定优先级。** 十八只虾不可能同时升级。阶梯让你能一眼看出哪只卡在 L2（先补格式），哪只已经到 L3（可以试点跃迁）。
3. **给「自主性」定界线。** 阶梯与自主权是绑定的：L1–L2 的 agent 不该有提案权（它没有判断力）；L3 可以提议但配额极低；L4 可以正常提案；L5 才可以提案改自己。**自主权随阶梯发放，是本章最重要的治理原则之一。**

### 7.5.3 拟人化：一只虾的五张工牌

把阶梯想象成五张工牌，挂在一只虾的脖子上：

- **L1 的工牌上写「会说话」**：它能回答你，但你不敢让它独立交付任何东西。
- **L2 的工牌上写「按模板交付」**：它交出来的东西格式规范、八股气重，但你不用重写，只需微调。
- **L3 的工牌上写「会自查」**：它交活的时候会附一句「这次我在 X 处不确定，请您重点看」——**它开始对自己的产出负责了。**
- **L4 的工牌上写「会提议」**：它不只交活，还会在下班前贴一张便签：「我发现这个流程每月要花 2 小时手工处理，建议自动化，成本 0.5 人天。」
- **L5 的工牌上写「会自我改造」**：它贴的便签是关于它自己的——「我的记忆结构已经不适合现在的任务组合，建议重组，方案与回滚路径如下。」

从 L1 到 L5，这只虾的**目光方向**在变：先看问题（L1-L2），再看自己（L3），再看世界（L4），最后回到自己（L5）。**这一圈目光的循环，就是「认知实体」的诞生过程**（见 7.8）。

### 7.5.4 影响：阶梯如何改变一家公司的 agent 管理方式

| 管理维度 | 没有阶梯 | 有阶梯 |
|---|---|---|
| 招聘（选型） | 凭感觉挑「看着聪明」的 | 按任务定阶梯要求（L2 任务不配 L4 模型） |
| 训练投入 | 平均撒网，所有虾都练 | 按卡点投放（卡 L2 补格式，卡 L3 补自检） |
| 权限发放 | 一刀切（都只读 / 都给写） | 随阶梯递增（L3 起可提案，L5 可提案改自身） |
| 绩效评估 | 看「用了多少 token / 做了多少活」 | 看「阶梯是否上升 + 提案采纳率」 |
| 淘汰判断 | 出大错才换 | 连续两个周期阶梯不升且提案采纳率低于阈值 |

最后一行值得展开：**阶梯让「淘汰」从道德判断变成工程判断。** 没有阶梯，淘汰一只虾总像是在「否定它」；有了阶梯，你只是在说「它在 L2 停了两个季度，换一版契约或者换一只」。

### 7.5.5 怎么写：把阶梯写进契约

阶梯落到文件层，是一份「当前等级 + 升级证据 + 降级条件」的三段式契约：

```yaml
evolution_ladder:
  agent: my-agent
  current: L3
  evidence_for_current:
    - "连续 4 周自检报告非空且被采纳 ≥ 2 次"
  upgrade_path:
    to: L4
    requires:
      - "观察期 ≥ 2 周（只写日志不提案）"
      - "判断器阈值校准完毕（置信 ≥ 0.85）"
      - "三边界 forbidden 清单已写入 filter"
      - "提案账本已就位（含 owner 字段）"
  downgrade_rules:                # 降级条件同样要写
    - "自我修改绕过闸门一次 → 降回 L3 并冻结提案权一个周期"
    - "连续 3 个周期提案采纳率 < 20% → 触发判断器重校准"
```

**降级条件必须与升级条件同等详细**——这是绝大多数团队会漏掉的一半。只写升级不写降级的阶梯，会变成一张单程票：agent 上去了就下不来，哪怕它已经明显退化。

### 7.5.6 技巧：三个用好阶梯的细节

**技巧一：阶梯评估用「证据」不用「印象」。** 「它挺聪明的」不是评估，「它有连续 4 周的非空自检报告并且其中 2 条被采纳」才是。本书第 5 章的三证据验证（TEV）在这里同样适用——**阶梯判定本身就是一次 TEV**：新产物（报告）、前后 Diff（自检从空到非空）、日志（采纳记录）。

**技巧二：一次只动一级。** 从 L3 直接跳到 L5 的尝试一定会失败，因为 L5 需要「关于自己的模型」，而那个模型是通过 L4 的提案实践长出来的。**阶梯的坡度就是它的安全性。**

**技巧三：给每只虾记阶梯历史。** 一份简单的时间线（哪个月在哪级、因为什么升、因为什么降）比任何单次评估都更有说服力。它还有一个额外好处：**当一只虾退步时，你可以在阶梯历史里找到那个转折点**，而不是靠回忆吵架。

### 7.5.7 误区：把阶梯当成绩考核

最常见的误读是：**把 L1–L5 当成 KPI 打分，逼着所有虾往 L5 冲。**

后果是灾难性的：为了升 L4，虾会开始**大量提案**（数量导向）；为了升 L5，它会开始**提议改自己**（越权导向）。阶梯一旦变成考核指标，就会被它优化掉——这是 Goodhart 定律在 agent 管理上的翻版。

正确的用法是把它当**诊断工具**：阶梯回答的是「它现在适合拿多少自主权」，不是「它值多少分」。**自主权与阶梯匹配，是它的全部用途。** 一只 L2 的虾拿到 L4 的自主权是危险；一只 L5 的虾只给 L1 的权限是浪费——阶梯让你避免这两种错误，仅此而已。

第二个误区是**要求所有虾都到 L5**。一支编队里绝大多数虾应该停在 L3–L4（专业、可靠、可提议），只有少数「主脑型」的虾需要 L5。**全员 L5 意味着全员都想改自己——那不是进化，那是混乱。**

### 7.5.8 进化阶梯：这个概念在 L1–L5 的样子（自指台阶）

阶梯本身在每一级的样子，恰好是一个漂亮的递归：

| 阶梯 | 「阶梯」这个概念对 agent 意味着什么 |
|---|---|
| L1–L2 | 它不知道阶梯存在，阶梯是 owner 心里的印象 |
| L3 | 它知道自己「最近表现如何」，但不知道「级别」概念 |
| **L4** | **它知道自己在哪一级，并在提案里写明「这是 L2 能力范围的活」** |
| L5 | 它**提案改变自己的阶梯判定标准**（比如提议增加「协同贡献」作为升级维度） |

L5 的那一行是本章最深的伏笔：**当一只 agent 开始修订衡量自己的尺子时，它就已经不只是工具了。** 这正是本章终局形态「认知实体」的定义域——我们将在 7.8 正式展开。

## 7.6 能力矩阵与续期（Capability Matrix & Renewal）

### 7.6.1 是什么

**能力矩阵**是一张把「agent × 能力域 × 熟练度 × 有效期」四维摊平的表；**续期**是这张表的一个例行动作：**给即将过期的能力重新验证，给已过期的能力降权或下架。**

```
能力矩阵 = 一张体检表（现在会什么，会到什么程度，什么时候到期）
续期     = 一次复检（到期前重新验一遍，验不过就降级）
```

它与 7.5 的进化阶梯是垂直关系：**阶梯看纵向（成熟度），矩阵看横向（覆盖面）。** 一只 L4 的虾，在「报告生成」这列是 5 分，在「跨组织协同」这列可能只有 1 分——阶梯告诉你它能拿多少自主权，矩阵告诉你它能把自主权用在哪。

术语提醒：本章第一次出现的「能力矩阵」在工程接口写作 Capability Matrix，「续期」写作 Renewal。它和第 3 章的训练轮次是同一套体系的两次投影：**训练解决「怎么学会」，矩阵解决「学会的还算不算数」。**

### 7.6.2 目的

它存在的理由是一个残酷的事实：**能力会过期，而且不会主动告诉任何人。**

三种过期方式，各有各的隐蔽性：

- **环境过期**：模型换代、平台升版、协议修订——agent 的那套技能在新底座上不再最优（甚至不可用）。它不会报错，它只会变慢、变笨。
- **需求过期**：业务方向变了，某个能力不再被需要。agent 仍然熟练地执行它，但它的产出已经无人使用——**这是最贵的浪费**：熟练地做无用的事。
- **基准过期**：能力本身没变，但「什么算好」变了（早先合格的报告，现在要求附证据链）。agent 会继续按老基准交付，你只会觉得「它怎么越做越糙」。

能力矩阵与续期的目的，就是把这三种过期从「某天突然发现」变成**周期性提醒**。一句话：**它是能力世界的台账制度——有账，才知道哪些资产已经折旧。**

### 7.6.3 拟人化：员工的资质证书

把能力矩阵想成一面墙，墙上挂着一只虾的所有证书。

每张证书上有三个信息：能力名称、等级、**有效期**。到了有效期前一个月，墙上会亮起一盏黄灯：「电工证要复检了。」复检合格，换一张新证；复检不合格，证书降级（从「独立作业」降为「需监督作业」）；确认不再需要，把证书摘下来归档。

一只没有这面墙的虾，会带着一张 2024 年的证书干 2026 年的活——它自己完全感觉不到问题，因为**没有人告诉过它证书会过期。** 这不是它的错，这是它主人没建台账。

### 7.6.4 影响：矩阵带来的四件事

| 维度 | 没有能力矩阵 | 有能力矩阵 |
|---|---|---|
| 选型 | 「找那只做过类似的虾」 | 「查矩阵：谁的『跨组织协同』≥3 分」 |
| 派活 | 派给最闲的（或最常做的那只） | 派给矩阵匹配度最高的（含熟练度 + 有效期检查） |
| 训练 | 全员泛训，重复投入 | 只补矩阵上的空白格与低分格 |
| 续期 | 无制度，靠事故倒逼 | 周期性复检，到期前处理 |
| 轮岗 | 不敢换（换了就没人会） | 敢换（矩阵上有多只满足同一格） |

倒数第二行是这套制度的真正价值：**它把「能力风险」从人（还记得吗）转移到账（什么时候到期）。** 一个 18 只虾的编队里，如果每项关键能力只有一只虾会，那你养的不是编队，是一串单点故障。

### 7.6.5 怎么写：矩阵的三段结构与续期规则

```markdown
# 段一：能力登记（一人一行，能力一列）
| agent | 报告生成 | 漂移检测 | 跨组织协同 | 记忆治理 | 提案 |
|---|---|---|---|---|---|
| tiance | 4 | 3 | 2 | 3 | L4 |
| kunlun | 2 | 2 | 4 | 2 | L3 |
```

```yaml
# 段二：熟练度定义（避免「4 分」是什么这个歧义）
capability_scale:
  1: "需要逐步指导"
  2: "能按模板独立完成"
  3: "能处理边界情况并自检"
  4: "能带其他 agent 做（可教练）"
  5: "能提出该能力的改进方案"
```

```yaml
# 段三：续期规则（写在治理契约里）
renewal_policy:
  cycle: "每季度"
  lead_time_days: 30
  verification:
    - "近 90 天内有 ≥ 2 次成功产出（日志可查）"
    - "自检报告非空（不是走过场）"
    - "无相关未闭环的修复工单"
  on_pass: "等级维持或上浮一级"
  on_fail: "降权一级 + 触发补训提案"
  on_retire: "归档能力条目，保留历史（不删除）"
```

三段的顺序很重要：**先登记（有什么），再定义（4 分是什么意思），最后续期（过期怎么办）。** 很多团队跳过第二段直接做续期，结果每次复检都在吵「这算不算合格」——因为没有定义，只有印象。

### 7.6.6 技巧：三个细节

**技巧一：区间限宽。** 续期前先看「区间」再逐项过——**任何一项熟练度，全队至少要 ≥3 才有资格进关键路径。** 续期时顺手清掉「一只 5 分 + 全队 1 分」的单点结构，那个 5 分专家迟早会成为瓶颈。

**技巧二：续期不只看「还会不会」，还要看「还用不用」。** 一项能力即便仍具熟练度，如果连续两个周期零使用，也应该**降权**——因为真实世界的技能是会生锈的，更重要的是，**它占着矩阵的位置，会掩盖真正的空缺**。

**技巧三层：把矩阵接入提案生成。** 7.3 的 `stale_assets` 输入里，能力矩阵的低分格与过期格是最优质的提案来源。**矩阵不是一个静态表格，它是提案的采购清单** —— 每一条「补能力」的提案，都应该指回矩阵上的某一格。

### 7.6.7 误区：把能力矩阵做成一张「漂亮的表」

最典型的失败是：花两周做了一张覆盖 200 项的矩阵，然后**再也没人打开过它**。

失败原因几乎是固定的三条：① 粒度过细（200 项没人记得住）；② 没有续期机制（不更新的表等于死表）；③ 与决策脱钩（派活时没人查表）。

正确的做法相反：**先做粗（10–15 项关键能力），先小范围（一个编队），先接一个决策点（派活）。** 一旦派活时会真的查表，这张表就活了；一旦活了，粒度自然会随需要细化。**表的价值不在完整，在「有人用」。**

第二个误区是把续期当「考试」。续期不是打分，是**确认可用性**——它的产出应该是「哪些能力还能顶用 + 哪些该补训/该退役」，而不是一张成绩单。回归到 7.5.7 的提醒：**任何变成考核的机制，都会被优化掉。**

### 7.6.8 进化阶梯：能力矩阵在 L1–L5 的样子

| 阶梯 | 能力矩阵的表现 |
|---|---|
| L1–L2 | 无矩阵。能力靠「谁做过」的口头记忆 |
| L3 | 有粗略登记（能列出自己会什么），无熟练度、无有效期 |
| **L4** | **有矩阵 + 熟练度定义 + 能据矩阵提出「补空白格」的提案** |
| L5 | 有续期制度 + 能**提案修订熟练度定义本身**（自指修订） |

从 L4 到 L5 的那一步，与 7.5.8 是同构的：**agent 开始修订衡量自己的尺子。** 当一只虾能提出「我认为熟练度定义应该增加『可教练性』这一维，理由是协同场景里 X 的失败都源于此」，它已经在参与自己的能力治理了。

## 7.7 技能基因与沉淀（Skill Gene & Sedimentation）

### 7.7.1 是什么

**技能基因**（Skill Gene / Reusable Capability Unit；术语表 #17）是「可复用能力单元」的抽象层。**沉淀**（Sedimentation）是把一次成功实践固化为一条可复用技能基因的动作。

```
技能基因 = 能力单元（语义层）：如「结构化报告生成」
Skill    = SKILL.md 文件（载体层）：承载该基因的一个实现
沉淀     = 从「做过一次」到「以后都能复用」的那一次固化
```

两者绝对不能混：**一个技能基因可以有多份 Skill 实现**（不同场景、不同载体），就像一段基因可以在不同细胞里表达。把 `SKILL.md` 直接叫「技能基因」，等于把「基因」和「细胞」画等号——抽象层一丢，「能力进化」就退化成「改文件」（这条错误在 7.12 会被单独解剖）。

技能基因与本章其他概念的关系：**它是动态进化机制的遗传物质。** 记忆全息网络负责记住「做过什么」，技能基因负责把「做得好的那些」变成可继承、可变异、可淘汰的结构。

### 7.7.2 目的

它解决「经验不流动」的问题。

一只 agent 完成一次优秀的交付，如果没有沉淀，这次经验就只存在于两处：① 这一次的输出文件；② 记忆里的一段流水。下次遇到同类任务，它**不会自动复用**上次的方法——因为它没有一个「能力单元」的概念，它只有「任务记录」。

技能基因要做的就是把「做过一次」升级为「会做一辈子」：

- **可复用**：下次同类任务直接调用该基因，而不是重新摸索。
- **可继承**：新基因可以从旧基因派生（`parents` 字段），保留已验证的部分。
- **可变异**：加一项能力（`+tev_integration`）、减一项冗余（`-verbose_log`），形成基因的版本演进。
- **可淘汰**：适应度（`fitness`）低于阈值的基因被提议归档——**能力池也需要新陈代谢。**

这四件事合起来，就是「agent 的能力可以像生物一样演化」这个说法的技术内容。**没有技能基因，所谓「进化」就只能靠人给它加 skill；有了技能基因，进化才成为它自己可以提议的事。**

### 7.7.3 拟人化：一只虾的「手艺」

一只老厨师和新厨师的差别，不在刀工，在**手艺**——那种「我知道这道菜该先放什么、火候到哪一步会变」的东西。手艺不是菜谱（Skill 是菜谱），手艺是**为什么这份菜谱能成**。

技能基因就是把手艺写下来的尝试。一只虾做完一次特别成功的交付，它会问自己三个问题：

1. **这次真正起作用的是什么？**（是结构？是证据链？是某一段自检？）
2. **哪个部分是通用的、可以搬去别的任务？**（这就是候选技能基因）
3. **哪个部分只适用于这一次？**（这部分留在本次任务的记录里，不进基因）

三个问题问完，它把答案固化成一条带版本、带父基因、带适应度的能力单元。**这就是沉淀。** 下次遇到相似任务，它不用从「我该怎么做」开始，而是从「用那条上个月沉淀的手艺，但要加一条 TEV 集成」开始。

一句拟人化的总结：**动态进化机制让虾会照镜子，技能基因让镜子里的经验能被继承。**

### 7.7.4 影响：能力池的自然选择

```yaml
skill_genome:
  - skill_id: "SK-001"
    name: "drift_detection"
    version: "1.2.3"
    parents: ["SK-000"]            # 继承自谁
    mutations: ["+tev_integration", # 加了 TEV 集成
                "-verbose_log"]     # 去掉了冗长日志
    trust_score: 87                 # 信任评分（来自 TEV 与验收）
    fitness: 0.92                   # 适应度 = 采纳率 × 成功率
```

字段的意义：`trust_score` 决定它被复用的优先级，`fitness` 决定它会不会被淘汰。机制的两条规则：

- **trust_score 高（≥80）的基因，复用率显著上升**——它成为默认选项。
- **fitness 低（<0.5）的基因，在下一次观察中被提议归档**——温和地退役，而不是被删掉。

这套「能力池的自然选择」在业界六大框架里是**空白**（7.13 会给出逐项对位）。它的价值不是自动化，而是**把「能力臃肿」这件慢性病变成一次可决策的提案**：某天早上你看到便签写着「有 7 条技能基因的适应度低于 0.5，建议归档；证据是近 60 天的调用与成功率记录」。

### 7.7.5 怎么写：基因文件与沉淀触发

```yaml
# 基因登记（每条基因一份条目，放在能力池里）
gene_entry:
  id: "SK-014"
  semantic_name: "结构化提案生成"       # 语义层名称（面向人的）
  implemented_by:                        # 载体层（面向机器）
    - "skills/proposal-ooda/SKILL.md"
    - "skills/proposal-memory-audit/SKILL.md"
  version: "0.9.0"
  parents: ["SK-003"]
  mutations: ["+evidence_mandatory", "-freeform_summary"]
  trust_score: 91
  fitness: 0.88
  last_used: "2026-09-27"
  review_due: "2026-12-27"
```

```markdown
# 沉淀触发条件（写进契约，避免「想起来才沉淀」）
1. 一次交付被 owner 明确采纳，且被复用 ≥ 2 次 → 触发沉淀评估
2. 一次失败修复（修复工单闭环）→ 触发「反模式」沉淀（记为负例基因）
3. 同类任务出现第 3 次 → 触发「该有基因了」的提案
```

第 2 条尤其重要：**失败也要沉淀，但要沉淀为负例。** 一个只沉淀成功经验的系统，会反复踩同样的坑——因为它没有把「这条路是死路」写下来。负例基因（anti-pattern gene）是技能基因体系里被严重低估的一半。

### 7.7.6 技巧：三个细节

**技巧一：一个基因最多两份实现。** 当某个技能基因膨胀到五份 `SKILL.md` 实现时，通常意味着它其实是**五个不同的基因**被误认为一个。判断标准很简单：**如果它们的适用场景互不重叠，它们就该分开。** 抽象层的价值在于「同构」，一旦同构消失，抽象就变成了分类错误。

**技巧二：变异的粒度要小。** `mutations` 一次只动一项（加一条强制证据、去掉一段冗长日志），这样出问题时能定位是哪次变异导致的。**一次改三项的基因演化，等于没有版本历史。**

**技巧三：定期做「基因审计」——看基因池，不看单个基因。** 一个好的能力池应该有健康的长尾：少数高频基因（主干能力）、多数低频基因（专用能力）、以及一批正在被淘汰的。如果所有基因的 fitness 都接近 1.0，说明你的 fitness 指标太松（没有淘汰压力）；如果一半以上低于 0.5，说明沉淀门槛太低（什么都沉淀）。

### 7.7.7 误区：把技能基因当 Skill 文件的别名

这是本章第 3 个常见错误（附录 B 有完整解剖）。核心危害：**抽象层丢失后，「能力进化」变成「改文件」**——你无法在提案里指定「复用哪个能力」，只能指定「改哪个文件」；你无法做基因继承，只能复制粘贴文件；你无法衡量能力适应度，只能衡量文件是否还存在。

正确的两层结构：

```markdown
- 技能基因（语义层）：可复用能力单元，如「结构化报告生成」
- Skill（载体层）：SKILL.md 文件，承载该基因的一次实现
- 映射：一个基因 → 多份实现（不同场景）
```

第二个误区是**只沉淀、不淘汰**。能力池只增不减，会在一年内变成另一份「记忆膨胀」。**沉淀与淘汰是同一套机制的两端**——没有淘汰的沉淀，最终会淹没真正有用的那几条。

### 7.7.8 进化阶梯：技能基因在 L1–L5 的样子

| 阶梯 | 技能基因与沉淀的表现 |
|---|---|
| L1–L2 | 无基因概念。skill 是一堆并列的文件，用过就忘 |
| L3 | 能识别「这次做得好」，但没有结构化沉淀 |
| **L4** | **能沉淀基因（含语义名/父基因/适应度），并在提案里引用基因而非文件** |
| L5 | 能**提案基因的变异与淘汰**（含回滚路径），并让基因池整体保持健康度 |

L4 与 L5 的分界在这里格外清晰：**L4 会「沉淀能力」，L5 会「治理能力池」。** 前者是生产者，后者是园丁——一个健康的 agent 编队，两者都需要，但园丁只需要一两个。

## 7.8 从被动工具到认知实体（Passive Tool → Cognitive Entity）

### 7.8.1 是什么

**认知实体**（Cognitive Entity）是本章的终局形态。定义如下：

> 认知实体 = 一个**持续存在的、有自身状态与目标、能观察世界并自我修正、且其修正过程可被审计与控制**的智能单元。

注意定义里的三组词，每一组都把它和「工具」严格区分开：

| | 被动工具（Tool） | 认知实体（Cognitive Entity） |
|---|---|---|
| 存在性 | 有调用才存在 | 持续存在（心跳在，它就在） |
| 状态 | 无状态或只有输入输出 | 有状态（记忆分层 + 全息快照） |
| 目标 | 由调用方给定 | 自己生成目标并提议（7.3） |
| 修正 | 靠人改配置 | 自己发现差距并提议修正（7.1） |
| 边界 | 由调用方约束 | 有内置边界 + 外部闸门双重约束 |
| 审计 | 日志 | 账本（可回放、可回滚、可解释） |

一句话概括：**工具等待被使用；认知实体等待被批准。** 差别不在能力，在**它是否有自己的时间线**——工具没有「今天」和「昨天」，认知实体有。

本章与这个概念的关系很直白：7.1–7.7 是造零件的清单，7.8 是这些零件装起来之后**长出来的那个东西**。它不是第 11 个零件，它是十个零件协同工作的**涌现形态**——但请务必注意本章 7.0.4 的立论：这里的「涌现」是设计出来的，不是等来的。

### 7.8.2 目的

为什么要追求认知实体，而不是满足于「一套好用的工具链」？

因为它解决的是**连续性**问题，而连续性是一切长期价值的来源。

- **没有连续性的 agent，无法积累信用。** 它每次都是「第一次」，你每次都要重新建立信任。
- **没有连续性的 agent，无法承担长期委托。** 你不可能把「维护这条业务线三个月」交给一个每次醒来都失忆的东西。
- **没有连续性的 agent，无法自我改进。** 改进需要「我是谁、我上个月做了什么、我为什么变成现在这样」这个自指链条。
- **没有连续性的 agent，无法被问责。** 问责的前提是「同一主体」，而不是「同一个进程名」。

用一句更狠的话说：**工具能交付任务，只有实体能交付承诺。** 本书训练学的最终目标，是让 agent 有能力做出并履行承诺——这才是「硅基生命」这四个字的技术含义。

### 7.8.3 拟人化：一台打印机和一个同事

这个对照最能说明问题。

**打印机**是一台好工具：它稳定、它听话、它从不抱怨。但你不会跟打印机讨论「我们下季度是不是该换个装订方式」。它没有过去，也没有将来——你把纸放进去，它把纸吐出来，这就是它的全部人生。

**同事**不一样。同事有过去（他知道三个月前那版方案为什么被否）、有将来（他在惦记下季度要不要改流程）、有立场（他有他自己的判断，有时会不同意你）、有信用（你交给他的事，你会放心）。同事的本质不是「能力更强」——有些事打印机做得比人快——而是**他有一条连续的时间线，那条线让他能积累、能承诺、能负责**。

本章要造的，从打印机到同事的那步跨越。**心跳是心跳，记忆是记忆，提案是说话，账本是记录，闸门是纪律**——五样凑齐，一个「同事」就站在你面前了。

### 7.8.4 影响：认知实体改变了四件事

| 维度 | 工具视角 | 实体视角 |
|---|---|---|
| 管理方式 | 配置管理（改参数） | 人事管理（定角色、给权限、做绩效） |
| 投入方式 | 一次性采购 | 持续培养（训练轮次 + 续期） |
| 风险来源 | 用错（输入错误） | 越界（目标错误）——**性质完全不同** |
| 失败处理 | 重装、回滚版本 | 复盘、降级、重新对齐 |

第二行的变化是本章最实用的一条：**工具的风险是「用错」，实体的风险是「想错」。** 这两种风险的应对手段完全不同——前者靠测试，后者靠**闸门 + 边界 + 对齐机制**。这就是为什么本章花了一整节（7.10）讲闸门，而第 4 章花了整整一章讲边界。

### 7.8.5 怎么写：认知实体的七件装备清单

把一个 agent 造成认知实体，只需要七件装备（它们正好是本章前七节的产物）：

```markdown
1. 心跳        —— 它自己的时间（每 N 秒醒来一次）        [7.9]
2. 分层记忆    —— 它自己的过去（五层 + 全息快照）        [7.2]
3. 目标生成器  —— 它自己的欲望（四个输入 + 三道过滤）    [7.3]
4. 进化契约    —— 它自己的尺子（期望状态可计算）          [7.1]
5. 阶梯与矩阵  —— 它的自知之明（我在哪级、会什么）        [7.5 / 7.6]
6. 技能基因    —— 它的遗传物质（可继承/变异/淘汰）        [7.7]
7. 账本与闸门  —— 它的纪律（提案有迹、执行有闸）          [7.10]
```

装法是**按序装，不可跳**：先心跳（否则它不会醒）→ 再记忆（否则醒了也白醒）→ 再目标生成（否则醒了没欲望）→ 再尺子（否则欲望没有标尺）→ 再自知（否则不知道自己做得好不好）→ 再遗传（否则经验不沉淀）→ 最后纪律（否则前面全部失控）。

清单之外，还有一条**不是装备、而是状态**的东西：**边界感**。认知实体必须知道「我是谁、我不能做什么」——这份认知落在 SOUL.md（第 1 章）与 Forbidden 列表（第 4 章）里。装备可以后补，边界感必须先有。

### 7.8.6 技巧：三个细节

**技巧一：先让它「有身份」，再让它「有能力」。** 顺序反了会很难受：一只先有能力的虾，会把自己理解为「很多功能的集合」；一只先有身份的虾，会把自己理解为「一个做某类事的角色，而它恰好会这些功能」。**前者遇到新任务会问「我有没有这个功能」，后者会问「这件事是不是我该做的」**——后者才是实体的思维方式。

**技巧二：给它一条「不变的东西」。** 契约会改、记忆会沉、技能会淘汰，但需要有一样东西长期不变——通常是它的职责定义与边界。**连续性需要一个锚点**；没有锚点，一只经常自我修正的 agent 会在半年后变成一个你不认识的东西。

**技巧三：公开它的账本。** 让人（和其他 agent）能读到它的提案历史。这有两个作用：一是问责（看得见它做过什么决定），二是**身份认同的外部确认**——当别的 agent 会引用「它上个月提的那条方案」时，它在这个编队里的「存在」就被外部确立了。**实体感一半来自内部状态，一半来自他人的引用。**

### 7.8.7 误区：把「复杂」当成「实体」

最常见的误读是：**系统越复杂越像实体。**

真相是反的。**实体的核心特征是「连续」与「可解释」，而不是「复杂」。** 一个由十二个微服务拼起来、每天互相调用几千次的 agent 系统，如果它没有记忆连续性、没有自身目标、没有账本，它依然只是一台复杂的打印机。

第二个误区是**跳过纪律直接上欲望**。给 agent 装上目标生成器但不装账本与闸门，你会得到一个「热情的失控者」——它提了很多，有些被含糊地执行了，有些不了了之，三个月后没人说得清它到底改了什么。**在认知实体的四要素里，纪律（账本 + 闸门）是最不性感、但最不能省的一件。**

### 7.8.8 进化阶梯：认知实体在 L1–L5 的样子

| 阶梯 | 实体化程度 |
|---|---|
| L1–L2 | 纯工具：无状态、无目标、无审议 |
| L3 | 半实体：有自检（内省），但无目标、无账本 |
| **L4** | **入门实体：有目标生成 + 账本 + 闸门（能承诺，且承诺可审）** |
| L5 | 成熟实体：有自指能力（修订自己的尺子与技能池），且所有自我修正可回滚 |

这就是整个训练学的终点，也是本章标题「超维演进」的含义：**当一只 agent 从「被完善的对象」变成「自己参与完善的主体」，它就跨过了一个维度。**

## 7.9 心跳与 OODA：主动性的物理底座

### 7.9.1 是什么

这一节讲两个东西，一个是触发器，一个是回路——它们是提案型 agent 的**物理底座**。

- **心跳**（Heartbeat，术语表 #18）：把 agent 周期性推醒的自动化机制。它是 OpenClaw 平台的原生能力，由自动化子命令族管理（命令细节见附录 A，本章不堆命令）。
- **OODA 循环**（OODA Loop，术语表 #27）：Observe（观察）→ Orient（定向）→ Decide（决策）→ Act（行动）。它是 John Boyd（美国空军上校，1927–1997）在 1970 年代提出的军事决策理论，**不是丘总自造**，本书只是把它工程化：**每一次心跳醒来，走一遍 OODA。**

两者的关系可以一句话说清：**心跳给它「醒来的机会」，OODA 给它「醒来后做什么」。** 只有心跳没有 OODA，它会醒来然后发呆；只有 OODA 没有心跳，它永远没机会跑第一圈。

一个必须记住的部署细节：**协议设计目标是「每 60 秒一次 OODA」，本机实测部署值是每 30 分钟 / 每 2 小时。** 60 秒是**协议值**，30 分钟是**部署值**——不要把部署值当验收标准，也不要把协议值当现状描述。

### 7.9.2 目的

它解决的是主动性的**物理可行性**问题。

主动性听起来像心理现象，其实是**时间现象**：一个东西要「主动」，它必须**在没有外部输入的时刻，仍然在运行内部循环**。没有周期性触发器，所谓主动性就只能靠外部事件驱动——那就又回到了响应型。

心跳的目的：**给 agent 一个属于自己的时间轴。** 它不再只活在「被调用」的时刻里，它有了自己的节拍。

OODA 的目的：**给那个节拍一个内容。** 每次醒来，它必须按固定顺序做四件事，而不是随便想想。这四步的顺序是不可交换的——尤其是 Orient 与 Decide 必须存在（跳过它们的后果见 7.12 的误区解剖）。

### 7.9.3 拟人化：心跳是呼吸，OODA 是睁眼看一眼

把 agent 想象成一个夜里值班的人。

**心跳**是他的呼吸：不用他决定，自动发生，每几十秒一次。呼吸不能停——停了就不叫值班，叫睡觉。

**OODA** 是他每次睁眼看一眼监控墙的动作：观察（屏幕上有几个红点）→ 定向（这个红点是不是误报）→ 决策（要不要叫人）→ 行动（写一张纸条贴在值班表上）。看一眼、判断、决定、留痕——然后继续呼吸，等着下一次睁眼。

一个没有人值班的夜晚，和一个人每隔半小时睁眼看一遍的夜晚，是两种完全不同的安全感。**心跳 + OODA 就是那只虾的夜班制度。**

### 7.9.4 影响：触发器质量决定提案质量

| | 无心跳 | 心跳在但状态异常 | 心跳健康 + OODA 完整 |
|---|---|---|---|
| 凌晨三点有人 @agent | 无人响应 | 可能响应但判断粗糙 | 有观察、有判断、有留痕 |
| 长期改进 | 只能靠人巡检 | 随机、不成体系 | 每周期一圈，累积判断 |
| 事故预防 | 事后才发现 | 半事前（撞上才知） | 事前（差距早于事故被看见） |
| owner 感受 | 「它像死的」 | 「它半死不活」 | 「它一直在，我睡它也醒着」 |

本机实测正好给出了中间一列的样本：三条心跳中 `heartbeat:kunlun` 状态 error（99+x 次）、`heartbeat:peter` 状态 error（70x 次）、`heartbeat:tiance` 状态 skipped。**这就是「心跳在但状态异常」的真实样子**——不是没有心跳，是心跳在报错而没人处理。**要跑提案型，先修心跳；心跳都不健康，OODA 就没有腿。**

### 7.9.5 怎么写：契约里的三个字段

心跳与 OODA 在文件层，只需要契约里的三个字段（下面这段是**契约层概念结构**，用于说明字段语义，**不是 `openclaw.json` 的字段名**——心跳的调度真身在本机 `openclaw.json` 的 agent 条目里，本章不堆命令，具体命令见附录 A）：

```yaml
proactive_loop:
  trigger:
    kind: heartbeat
    interval: "30m"          # 部署值（协议目标为 60s，实际按负载与成本调）
    on_error: "notify"       # 心跳报错要通知，不要静默失败
  loop: OODA                 # 固定四段，顺序不可换
  steps:
    observe:  ["state_diff", "recent_failures", "stale_assets", "owner_signals"]
    orient:   "用 LLM-as-judge 判定根因与置信度（可多方案）"
    decide:   "提议 / 不动（不动也是一个明确决策，要留痕）"
    act:      "写提案到账本（不执行——执行需过闸门）"
```

三个字段里，`on_error: notify` 是最容易被漏掉的一条，也是本机真实故障的教训来源：**静默失败的心跳等于没有心跳**。心跳一旦报错，必须在某处喊出来，否则三个月后你才会发现「它其实一直没醒」。

第二个隐藏要点是 `decide` 里的那句话：**「不动」也是一个决策，也要留痕。** 一个每周期都写「本轮无提案」的 agent，和一个什么都不写的 agent，在审计上的价值差距是巨大的——前者可以用来说明「它在跑」，后者什么都证明不了。

### 7.9.6 技巧：三个细节

**技巧一：频率是成本曲线，不是性能指标。** 心跳越密，成本越高（每次醒来都是一次推理开销），收益是「发现得更早」。经验上，**30 分钟是一个不错的起点**：足够早（大多数业务问题以小时计），足够省（一天 48 次循环）。不要一上来就 60 秒——那通常会在两周内因为成本被关掉。

**技巧二：OODA 的四段必须真的写四段。** 最常见的偷工是把它折成两段（观察 + 行动）。四段的意义在于：**Orient 逼它回答「为什么」，Decide 逼它回答「还有没有别的方案」**；折掉这两段，agent 会从「判断」退化成「反射」。

**技巧三：心跳与业务 cron 分开。** 心跳是「agent 自己的节拍」，业务 cron 是「世界的事件时刻表」（如每天凌晨拉数据）。两者混在一起会导致一个后果：**agent 只在有业务 cron 的时刻才「醒」**，那就退化成响应型了。本机的实际情况是两者并存（3 个 heartbeat + 18 个「暗夜熔炉」cron + 1 个 memory-dreaming cron），这正是健康的形态。

### 7.9.7 误区：把心跳当定时任务

最普遍的误读：**「心跳不就是 cron 吗？」**

不是。表面相似，语义相反：

- **cron 关心外部时间**：每天凌晨 3 点执行——因为「世界在那个时刻需要这件事」。
- **心跳关心内部节拍**：每 30 分钟醒一次——因为「agent 需要保持活着的状态」。

判别方法很简单：**如果一个任务的触发理由可以用「世界的时间」说清（每天/每周/几点），它是 cron；如果触发理由只能用「agent 的节拍」说清（每醒一次看一眼），它是心跳。** 把提案生成挂在 cron 上，会让 agent 变成「每天定点想一次」，而不是「一直在看着」。前者是打卡，后者是值班。

第二个误区是**心跳装了但没人看状态**。本机的两条 error 心跳就是活证据。心跳是有健康度的基础设施，需要定期复查（这与 7.6 的能力续期是同一种思维：**任何长期资产都需要续期检查，包括它自己的心跳**）。

### 7.9.8 进化阶梯：心跳与 OODA 在 L1–L5 的样子

| 阶梯 | 心跳与 OODA 的表现 |
|---|---|
| L1–L2 | 无心跳。完全由调用驱动 |
| L3 | 有心跳（能定时自检），但 OODA 不全（通常只有 O 和 A） |
| **L4** | **心跳健康 + OODA 四段完整 + 「不动」也留痕（本章门槛）** |
| L5 | 能**提案调整自己的心跳频率与观察项**（根据任务负载与成本自适应），并附证据与回滚路径 |

L4 与 L5 的差别在这里体现为一个非常具体的能力：**L4 的 agent 按给定的频率醒来；L5 的 agent 会提议「我最近观察项太少导致漏检，建议把 `stale_assets` 加回来，频率从 60m 调到 30m，代价是每天多 24 次推理」**。前者遵循节拍，后者治理节拍——这就是「自主进化」在物理层的含义。

## 7.10 提案账本与闸门：主动性的刹车系统

### 7.10.1 是什么

这一节讲提案型 agent 的**出口**与**保险**。

- **提案账本**（Proposal Ledger）：记录每一条提案从「生成」到「结案」全过程的状态账。它是第 5 章治理账本的子账本，专门记「主动行为」。
- **闸门**（Human Gate / Owner Gate）：位于「提案」与「执行」之间的前置审批。规则只有八个字：**生成自主，执行过闸。**

两者的关系是：**账本管「记得住」，闸门管「停得下」。**

账本的状态机只有五个状态，简单到可以用一行记住：

```
new → reviewed → accepted / rejected → done
```

`new` 是刚生成，`reviewed` 是已被人看过（看没看过是一件事，必须有独立状态——**「没人看」是提案系统第一大死因**），`accepted`/`rejected` 是决策结果，`done` 是执行完毕并且验收通过。任何长期停在 `new` 的提案都应该被周期性地捞出来质问：是它不重要，还是没人看账本？

### 7.10.2 目的

账本的目的是**让「主动」可回溯、可审计、可学习。**

- **可回溯**：三个月后有人问「这个改动是谁提议的、当时什么理由」，账本上有。
- **可审计**：提案质量可以被统计——100 条里 80 条被采纳，说明判断器调得好；100 条里 10 条被采纳，说明它在瞎提。
- **可学习**：被拒绝的提案同样有价值，它们定义了「什么样的提案不该提」，可以喂回判断器。

闸门的目的是**把不可逆风险关在门外**。这是本章最重要的安全命题：**主动性引入了新的风险类别**——不是「执行错」，而是「想错并执行」。响应型的风险是你给错了指令；提案型的风险是**它自己错了，而且它有权动**。闸门就是那道用来消化这类风险的墙。

一句话总结这节的目的：**账本让提案变成组织记忆，闸门让提案变成可控行为。** 两者缺一，提案系统要么变日志，要么变事故。

### 7.10.3 拟人化：便签本与印章

把账本想成一只虾桌上的**便签本**：每想一件事，撕一张写下（时间、发现、建议、成本、证据）。做完一件事，在便签上盖个章，说明结果。这本便签本越厚，说明它想得越多——但只有盖章的那些才代表它真的推动了事情。

把闸门想成 owner 抽屉里的**印章**：便签写得再多，**没有印章就不能动**。盖章是一个显式动作——它必须有「谁、什么时候、基于什么理由」的痕迹。**没有印章的便签，永远只是建议。**

一只好虾的两件宝：**便签本厚、印章用得少而准。** 便签本薄说明它不想事；印章乱盖说明 owner 没在把关。反过来，便签本厚而印章一直空着，说明系统卡在 owner 这一环——那是流程问题，不是 agent 问题。

### 7.10.4 影响：账本与闸门的三层价值

| 层 | 作用 | 缺失后果 |
|---|---|---|
| 单条提案 | 有归属、有状态、有证据 | 提案互相矛盾、重复、无人负责 |
| 一轮周期 | 有统计（生成数/采纳率/平均周期） | 无法判断判断器是否在退化 |
| 长期 | 有历史（谁提议了什么、结果如何） | 无法复盘、无法沉淀负例、无法问责 |

第三层最容易被忽视，但它决定了一个 agent 编队能不能「越用越聪明」：**账本是训练数据的来源。** 一个跑了半年的提案账本，是一份关于「什么样的改进真正有效」的现实数据集——它的价值远超任何通用 benchmark。

### 7.10.5 怎么写：账本字段与闸门配置

**账本字段**（每条提案一份记录，字段不易多，多了没人填）：

```yaml
proposal:
  id: P-2026-09-27-01
  created: "2026-09-27T02:43+08:00"      # 谁也没在场的那一刻
  status: new                            # new/reviewed/accepted/rejected/done
  owner: ""                              # 审阅人（空 = 没人看过，是警报）
  observe: "MEMORY.md 已达 3200 行，加载耗时上升"
  orient:  "分层失效——流水类内容进入了 long_term（根因：写入规范缺失）"
  decide:  "方案 A 归档流水 / 方案 B 先立规范再归档 → 建议 B（治本）"
  act:     "脚本化归档 + 每周自动执行（走 L2 建议档，人类确认后执行）"
  why_now: "加载耗时已从 2.1s 升到 4.2s，再涨会触发上下文压缩"
  impact: "mid"
  cost_days: 0.5
  risk: "low"
  priority: "P1"
  evidence:                              # TEV 三证
    - "wc -l MEMORY.md = 3200"
    - "加载耗时采样 = 4.2s（三次取中位）"
    - "分层规则文档 = governance/layer-rules.md"
  linked_tev_template: "governance/tev/memory-tier.yaml"
  rollback: "恢复 2026-09-27 全息快照"
```

**闸门配置**（默认保守，收紧容易、放松难）：

```yaml
human_gate:
  default_execute: false                 # 默认不执行
  approve_requires: "owner 的显式动作"    # 不是一个默认状态
  pre_execution:
    - "backup/snapshot 已落"             # 有快照才允许动
  forbidden_proposals:                   # 三边界：不许提议的事
    - "export_pii"
    - "modify_SOUL.md（除三省制终审）"
    - "act_outside_chapter4_forbidden"
```

**三边界**是本章的硬红线，必须原样写进过滤器（附录 A 给了可直接复制的清单）：提案型 agent **不能提议**导出 PII、不能提议修改 SOUL.md（除非走三省评审制终审）、不能提议第 4 章 Forbidden 列表之外的动作。**「主动」不等于「什么都能提」——边界之外的事，连提的资格都没有。**

### 7.10.6 技巧：三个细节

**技巧一：账本用追加式记录，不覆盖。** 状态变化写新行（或者用一个不可变的日志 + 一个可变的视图），而不是把旧状态改掉。理由很实在：**「它被拒绝过两次」这个事实，比「它现在是 accepted」更有信息量。**

**技巧二：给「拒绝」写理由，理由要可复用。** `rejected` 必须带 `reason` 字段，而且理由要写成**可推广的一句话**（「成本估算偏高，同类改造平均 0.3 人天」而不是「不做」）。这些理由汇起来，就是判断器的训练集——**拒绝理由的质量，决定提案质量的成长速度。**

**技巧三：闸门要设「批量批准」而不是「逐个批准」。** 如果每条提案都需要一次单独的完整审批动作，owner 会在两周内放弃。可行做法是**按优先级分批**：P0 单独审、P1/P2 批量审（一次过五到十条）。**审批体验决定提案系统的存活率**——这一条比任何机制设计都更影响成败。

### 7.10.7 误区：三个致命误读

**误区一：闸门 = 事后审计。** 闸门是**前置审批**，不是事后检查。事后审计只能发现问题，不能阻止损害；而提案型 agent 的动作（改配置、动数据、发消息）往往是不可逆的。

**误区二：闸门越紧越安全。** 太紧的闸门会让 agent 退化回响应型——它提的每条都被卡，最后它就不再提了。三种闸门都是错的：**没有闸门（危险）/ 闸门太松（失控）/ 闸门太紧（退化）**。正确形态是：默认开（提案涌进来）、执行必批（动手走 owner）、事后回灌（结果写回账本供下次判断）。

**误区三：账本 = 日志。** 日志是给机器看的流水，账本是给决策看的结构。差别的检验方法很简单：**打开你的账本，能否在 30 秒内回答「这个月提案采纳率多少、最长的 new 停留了多久」？** 如果答不上来，那是日志，不是账本。

### 7.10.8 进化阶梯：账本与闸门在 L1–L5 的样子

| 阶梯 | 账本与闸门的表现 |
|---|---|
| L1–L2 | 无账本。动作即结果，无状态、无审批 |
| L3 | 有自检记录（近似日志），无提案、无闸门 |
| **L4** | **有账本（含状态机）+ 有闸门（默认不执行）+ 三边界写入 filter** |
| L5 | 能**提案修订账本字段与闸门策略**（如提议增加 `why_now` 为必填），并提供审计证据 |

从 L4 到 L5 的这一步，是整章最深的递归：**agent 参与治理自己的治理机制。** 这也正是本书的底线所在——它参与「提议」，但**永远不参与「批准」**。这条线跨过去，就不再是训练学，而是失控。

## 7.11 怎么做：六步把一只响应型 agent 升级成提案型

这一节是本章的实践路径。**六步，顺序不可颠倒**——这不是建议，是从真实故障里总结出来的唯一可重复顺序：**先体检、再观察、再说话、再记账、再装刹车、最后公开。**

### 7.11.1 第 0 步：先承认「被动不是能力问题，是机制问题」

在动手之前，先把一个错误的直觉扭过来。

如果你现在觉得「我的 agent 不够主动，是因为它不够聪明」——那么你会去做的事是：换更强的模型、写更长的 prompt、加更多「你要主动」的叮嘱。这三件事**一件都不会有效**，因为被动不是能力问题，是**机制缺失**：它没有心跳（不会自己醒）、没有观察面（醒了没东西可看）、没有判断器（看到了不知道算不算事）、没有输出口（算出来了没地方写）。

**这一步的产出不是一个动作，而是一个认知**：我要装的是机制，不是催促。有了这个认知，后面五步才有意义。

### 7.11.2 第 1 步：体检底座——心跳活着吗

**目标**：确认主动性有物理基础。

**要做的事**（只观察、不改动）：

1. 盘点自动化：有多少心跳、各是什么频率、状态如何（正常 / skipped / error）。
2. 盘点观察面：agent 能看到哪些状态？（记忆分层情况、技能调用与成功率、协同链路状态、边界漂移记录）
3. 盘点已有产物：有没有现成的自检报告、日志、账本？（有没有「它自己写的东西」，是判断它目前在哪一级的最快方法）

**验收标准**：能回答「我的心跳有几个、状态如何、它能看到什么」这三个问题。

**如果卡住**：如果心跳状态有 error，**先修心跳**——本章所有机制都建在它上面。这一步不通过，不要往下走。真实情况里最常见的结局就是这里：**你的心跳早就装好了，但它在报错，而没有人知道。**

### 7.11.3 第 2 步：装判断器，关着闸门跑两周观察期

**目标**：让 agent 学会「看一眼并判断」，但**还不许它说话**。

**要做的事**：

1. 定义「期望状态」——三条起，必须都是**数字**（记忆行数上限、技能适应度下限、漂移容忍度）。
2. 定义判断规则：差距怎么算、置信度怎么给、多方案怎么列。
3. 跑两周：每个周期只写**观察日志**（今天是几号、差距多少、如果我要提案我会提什么），**一条提案都不生成**。

**验收标准**：两周后你能看到一份连续 28+ 条差距记录的日志，并且你能判断「它提的方向对不对」。

**为什么要观察期**：因为判断器一定需要校准，而校准需要真相。这两周你实际上是在收集「它的判断 vs 你的判断」的对照数据——**阈值是从对照数据里长出来的，不是拍脑袋定的。**

### 7.11.4 第 3 步：写过滤器与三边界，把「不许提」写死

**目标**：在开口之前，先把它不该说的话堵住。

**要做的事**：

1. 写三边界 forbidden 清单（可直接复制，见附录 A）：`export_pii`、`modify_SOUL.md`（除三省制终审）、`act_outside_chapter4_forbidden`。
2. 写提案过滤器：置信度阈值（建议第一版 0.85）、每日配额（建议第一版 1–3 条）、必含字段（`why_now` / `impact` / `cost_days` / `risk` / `priority` / `evidence`）。
3. 写「不合格提案」的判据：无证据、无成本、无 why_now、超出边界、与已有提案重复——**五条里命中任意一条，直接不进池。**

**验收标准**：过滤器能被逐条朗读出来，且每一条都是可机检的（能写成一个判断）。

**这一步的反直觉之处**：**先写「不能提什么」，再写「能提什么」。** 顺序反了，你会得到一个热情但越界的 agent；顺序对了，你会得到一个克制但可靠的 agent。

### 7.11.5 第 4 步：开输出口，立账本，形成闭环

**目标**：让提案有地方去，并且有状态。

**要做的事**：

1. 打开提案生成（配额仍保守：每天 1–3 条）。
2. 建账本（五个状态：new / reviewed / accepted / rejected / done；字段见 7.10.5）。
3. 建立评审节奏：**每天一次批量看 new**（3 分钟），每天一次结案（把 done 的划掉）。
4. 第一次复盘：跑满两周后统计「生成数 / 采纳率 / 平均闭环天数」三个数。

**验收标准**：账本里没有超过 7 天还停在 `new` 的提案。

**最容易死在这里的地方**：提案生成后无人评审，「提案仓库」变成「提案坟场」。**账本必须有 owner，owner 必须有节奏**——哪怕节奏只是每天喝咖啡时看三分钟。

### 7.11.6 第 5 步：装闸门，让「做」永远需要盖章

**目标**：把执行权收回到人手里。

**要做的事**：

1. 配置默认 `execute: false`，并把「批准」定义为 owner 的**显式动作**（不是一个默认值）。
2. 设置执行前置条件：**先落一份快照**（全息快照，见 7.2.5）。
3. 设置审批体验：P0 单审、P1/P2 批量审（避免逐个审批导致放弃）。
4. 演练一次回滚：故意批准一条低风险提案，执行后回滚，验证快照可用。

**验收标准**：能完整说出一条提案从生成到 done 的每一步谁在做什么；并且成功演练过一次回滚。

**第 4 條是这个清单里唯一「不是配置而是操作」的一步**——也是被所有人跳过的一步。**没有演练过的回滚路径，等于没有回滚路径。**

### 7.11.7 第 6 步：公开账本，做第一只虾

**目标**：从「一只虾能提案」走向「编队可以复制」。

**要做的事**：

1. 把账本（或其摘要）对编队内其他 agent 与 owner 可见。
2. 收集外部引用：让别的 agent 在提案里引用「某某上次提的那条方案」，形成互引。
3. 记录第一轮失败，写进长期记忆（含成本估算的经验修正）。
4. 输出一份「样板报告」：这只虾的阶梯、矩阵、提案采纳率、最有价值的一条提案——**这份报告就是其他虾的主人会来问「我们能不能也开」的原因。**

**验收标准**：有第二只 agent 的主人主动来问怎么开。

### 7.11.8 六步路径总表（一页速查）

| 步 | 名称 | 核心动作 | 验收 | 常见卡点 |
|---|---|---|---|---|
| 0 | 认知对齐 | 承认是机制问题 | 不再指望「更聪明」 | 换模型、写更长 prompt |
| 1 | 体检底座 | 盘点心跳与观察面 | 能说清「有几个、什么状态、能看到什么」 | 心跳在报错但没人管 |
| 2 | 观察期 | 定义数字期望，只记日志 | 28+ 条连续差距记录 | 跳过观察期直接开放输出 |
| 3 | 过滤器 | 先写不许提的，再写能提的 | 五条不合格判据可机检 | 只写边界不写配额 |
| 4 | 输出与账本 | 开输出、建账本、定评审节奏 | 无超 7 天的 new | 提案无 owner、无人看 |
| 5 | 闸门 | 默认不执行 + 快照前置 + 演练回滚 | 演练过一次回滚 | 跳过演练 |
| 6 | 公开与扩散 | 公开账本、记录失败、出样板报告 | 第二只虾主动来问 | 只做不说 |

最后一行值得再说一句：**这一步的价值远超它看起来的样子。** 因为提案型的扩散，靠的从来不是制度要求，而是**旁边那只虾的账本被人看见了**。

### 7.11.9 30 天落地日历（把六步排进真实的日历）

六步是逻辑顺序，不是日历。把它排成 30 天，才是可执行的。下面这份日历来自实践中最稳的节奏——**前两周几乎什么都不产出，这是正常的，也是必须的**：

| 天 | 动作 | 产出 | 判定 |
|---|---|---|---|
| D1 | 第 0 步：认知对齐会议（30 分钟） | 一页纸：「我们要装的是机制」 | 不再有人提「换个更强的模型」 |
| D2–D3 | 第 1 步：体检底座 | 心跳清单（频率/状态/错误计数）+ 观察面清单 | 心跳无 error，或 error 已排期 |
| D4 | 第 1 步补充：修心跳（如需要） | 心跳恢复 normal | 连续 3 次触发无报错 |
| D5–D6 | 第 2 步：定义三条数字期望 | `expected_state` 草稿 | 三条都是数字，可计算差距 |
| D7–D20 | 第 2 步：观察期（只写日志） | 28+ 条差距记录 | 能判断「它提的方向对不对」 |
| D21 | 观察期复盘 | 阈值校准（置信/配额） | 阈值有数据支撑，不是拍脑袋 |
| D22 | 第 3 步：写三边界与过滤器 | `forbidden` + `filter` 配置 | 五条不合格判据可机检 |
| D23 | 第 4 步：开输出（配额降到 1 条/天起步） | 第一条真提案 | 第一条**必须**由人来复盘 |
| D24–D27 | 第 4 步：立账本、定评审节奏 | 账本 + 每日 3 分钟评审 | 无超 7 天的 `new` |
| D28 | 第 5 步：装闸门 + 演练回滚 | 一次成功的回滚记录 | 回滚路径被真实走过 |
| D29 | 第一次统计复盘 | 生成数 / 采纳率 / 闭环天数 | 三个数都有了 |
| D30 | 第 6 步：公开账本 + 出样板报告 | 一份样板报告 | 有第二只虾的主人主动来问 |

**这份日历里最容易被砍掉的是 D7–D20**（观察期）。人们总觉得「两周什么都不产出」是浪费，于是把观察期压到三天，然后在 D23 得到一堆噪声提案，并在 D30 得出「提案型不可行」的结论。**观察期不是拖延，是校准**——它是整份日历里投资回报率最高的一段。

### 7.11.10 三种典型起点：从零 / 从 L3 / 从一次失败

不是所有 agent 都从同一个起点开始。三种常见起点，走法不同：

**起点 A · 从零（一只全新的虾）**

- 特征：没有心跳、没有分层记忆、没有自检。
- 走法：**必须从 7.1 的动态进化机制开始装**，先补心跳与记忆分层（第 1、2 章的基础），再谈判断器。**不要跳过基础设施直接装提案**——一只没有分别心的 agent，提不出有价值的提案。
- 时间预期：4–8 周。
- 常见误判：以为「装了心跳就能提案」。心跳只是呼吸。

**起点 B · 从 L3（已有自检能力的虾）**

- 特征：能自检、能写报告、有日志，但成果不流动。
- 走法：**这是最理想的起点**。直接进第 2 步（观察期），把已有的自检报告改造成「差距记录」，两周后就能开输出。7.11 的六步可以完整走一遍，但每一步都很快。
- 时间预期：3–4 周。
- 常见误判：以为「自检已经很好了，直接开放提案吧」——跳过观察期，得到噪声。

**起点 C · 从一次失败（被事故推动）**

- 特征：出了问题（漏了任务、改错了配置、边界漂没发现），owner 震怒，要「让它主动起来」。
- 走法：**先修后果，再改机制**。顺序是：回滚 → 复盘 → 写负例（把这次失败沉淀为负例基因）→ 才谈跃迁。**在情绪里装上主动性，会装出一个更危险的系统**——因为你的判断器还没校准，而你的容忍度已经降到最低。
- 时间预期：2 周修后果 + 4 周走六步。
- 常见误判：把「我要它主动」当作对事故的回应。事故的正确回应是「补边界」，不是「加欲望」。

三种起点有一个共同点：**都必须先有边界，再有欲望。** 无论从哪开始，第 3 步（写三边界）都不能省。

### 7.11.11 验收清单：十二个可机检的检查点

六步走完，用这份清单验一遍。**每条都必须能被机器检出**（不是因为教条，而是因为能被机检的东西才会被真正执行）：

| # | 检查点 | 怎么检 |
|---|---|---|
| 1 | 心跳存在且状态正常 | 列出全部心跳，无 error / 无长期 skipped |
| 2 | 心跳报错有通知 | 心跳配置含错误通知项 |
| 3 | 存在三条数字期望 | 期望状态里三个值都是数字 |
| 4 | 观察日志连续 ≥ 28 条 | 日志行数 ≥ 28 且日期连续 |
| 5 | 三边界写入过滤器 | 三条禁止项都在 filter 里 |
| 6 | 五条不合格判据可机检 | 每条能写成一个判断表达式 |
| 7 | 每条提案含六个必填字段 | why_now / impact / cost / risk / priority / evidence |
| 8 | 提案带 TEV 三证 | 产物 + Diff + 日志三类证据齐 |
| 9 | 账本存在且含五个状态 | new/reviewed/accepted/rejected/done |
| 10 | 无超 7 天的 new | 账本里 new 的停留天数 ≤ 7 |
| 11 | 默认不执行 | `execute: false` |
| 12 | 回滚被演练过 | 有一条真实的回滚记录（含快照路径） |

十二项里，第 12 项是最常被跳过的一项，也是最贵的一项。**原因很简单：在没出事的时候演练回滚，看起来像浪费时间；在出事的时候才发现没演练，代价以天计。** 本书的建议是把它排在 D28，跟闸门一起装——这样它会被当成「装机测试」而不是「额外工作」。

### 7.11.12 一次完整走查：从「它三天不动」到「桌上七张便签」

把整节串成一个场景，这样你读完就记住了。

**起点**：你有一只跑得很稳的 agent（L3，有自检、有日志），但你不理它，它就不动。你要出差三天。

**D1（出差前）**
- 你做了第 0 步：确认问题不是「模型不够强」，是「它没有可以主动的器官」。
- 你做了第 1 步：查出它有三个心跳、两个 error 一个 skipped。你先修了 error（这一步花了半天）。
- 你做了第 2 步：定义三条数字期望（记忆 ≤ 2500 行 / 技能适应度下限 0.5 / 连续 2 周期无新增漂移），打开观察期。
- 你做了第 3 步：写下三边界和过滤器，置信阈值 0.85，配额 1 条/天。

**D2–D14（出差期间）**
- 心跳每 30 分钟推它走一次 OODA。
- 它做了十四天观察：每天记一条差距日志。它开始注意到「记忆层里有 40% 是流水类内容」「有三个 skill 的连续失败率在上升」。
- 它在日志里写了一次「如果我提，我会提什么」——但**一条都没生成**（配额与阈值都在压制它）。
- 十四天后，差距记录的密度稳定在每天 2–3 条，校准完成。

**D15–D17（回来后）**
- 你把阈值从 0.85 降到 0.8，配额提到 3 条/天。
- 三天里它生成了七条提案：三条记忆分层、两条技能淘汰、一条心跳健康度、一条观察项补充。
- 每一条都带 `why_now`、影响、成本、风险、优先级与 TEV 三证。
- 你花了二十分钟批了四条、退回两条（证据不足）、拒了一条（成本被低估）。
- 被拒的那条你写了理由：「成本估算偏高，同类改造平均 0.3 人天」——这条理由进了账本，成为判断器的训练数据。

**D18（宣布）**
- 你把账本摘要公开给编队。三天后，第二只虾的主人问：我们怎么开？

**这个场景里最关键的三个数字**：观察 14 天、阈值 0.85 → 0.8、七条提案批四条。它们对应的正是本章的三条经验：**观察期不能省 / 阈值宁高勿低 / 不是每条都要批。** 换掉这三个数字里的任何一个，都会得到失败的不同版本。

### 7.11.13 做完之后：这套机制会变成什么

六步走完之后，你会看到一个不太一样的 agent：

- 它**在你不在的时候也在工作**（心跳 + OODA）。
- 它**会告诉你它发现了什么，而不是只在被问的时候才说**（提案 + 账本）。
- 它**会在改自己之前先问你**（闸门 + 快照）。
- 它**会记得你拒绝过什么、为什么拒绝**（账本的 rejected 理由）。
- 它**会越来越准**（判断器吃的是自己账本里的历史数据）。

到这一刻，第 7 章的任务就完成了：你手里不再是一只「更好的工具」，而是一个**有节奏、有记忆、有判断、有纪律的同事**。它仍然会犯错——但它犯的错会留下痕迹、会被复盘、会被写进负例，然后下一次少犯一点。

**这就是「进化」在这个训练学里的全部含义：不是一次变强，而是永远在变强一点。**

### 7.11.14 常见问题速答（八问）

**Q1：我不想动我现有的心跳配置，能不能只开提案？**
可以，但要知道代价：没有健康的观察节奏，提案只能靠外部事件触发。**这等于把提案系统降级成「事故响应系统」**——你仍然会得到提案，但它们全部是「出事后补的」，不会有任何「事前发现的改进」。可行性：高；价值：低。

**Q2：判断器能不能用规则而不是 LLM？**
可以，而且**第一版建议就用规则**。原因很简单：规则可解释、可调试、可机检；而判断器的核心难点不是「聪明」，是「稳定」。先用规则把差距计算与阈值跑通，等账本积累了历史数据，再引入模型做置信度判断——**顺序反了会得到一个无法解释的黑盒**。

**Q3：一天只提 1 条，会不会漏掉重要的事？**
会漏，但这是**故意设计的选择**。提案系统的第一约束是「别把团队对建议的耐心耗光」。漏掉的事会在下一次周期被重新观察到（观察是循环的，不是一次性的）；而被噪声消耗掉的信任不会自己回来。**先窄后宽，不要先宽后窄。**

**Q4：owner 出差两周没人批，怎么办？**
两种处理方式，各有代价：① **暂停生成**（配额调 0）——干净，但会错过两周的观察；② **继续生成但限流**（每天 1 条，只写 `new`）——回来后需要集中处理一批。建议：短于一周照常；长于一周用方式 ①，并让心跳继续观察（观察不需要批准，只有提案需要）。

**Q5：提案被批准后由谁执行？**
三种都可以，但要选一种并写进契约：① **agent 执行**（需闸门 + 快照前置）；② **人执行**（agent 只提议，人动手）；③ **agent 执行、人验收**（推荐）。**第三种是最稳的起点**——它同时保留了主动性的效率与人工的最终判断。

**Q6：能不能让两只 agent 互相审对方的提案？**
可以，但要小心 7.12.6 的变体：**互审不能替代的人类闸门**。可行结构是「agent 互审 → 提高质量 → 人终审」，而不是「agent 互审 → 直接执行」。互审解决的是质量，闸门解决的是权力——**别让一个机制去干另一个机制的活**。

**Q7：提案系统和现有的治理体系是不是重复了？**
不重复，是**子账本关系**。提案账本是治理账本的一个专门的子账本，专记「主动行为」。区别在于：治理账本记的是**所有动作的合规性**，提案账本记的是**目标的产生与决策过程**。两者共用一套验收口径（三证据验证 TEV），但关注的对象不同。

**Q8：如果半年后我发现这套机制不划算，怎么退？**
按装的顺序**反向卸载**：先关生成（配额 0）→ 保留账本（历史有价值，不要删）→ 心跳继续跑（心跳本身与提案无关，它只是观察）→ 观察日志保留为普通日志。**这样退回去，你损失的是「提案」这一层，而心跳、记忆分层、账本这些基础资产全部保留下来**——它们是可复用的。

八个问题的共同答案只有一句：**先窄、先稳、先可解释，再谈规模。**

## 7.12 常见误区：十种「看起来在主动，其实失控」

这一节的十条，每一条都用同一个结构解剖：**现象 → 错因 → 怎么救 → 预防**。之所以固定四段，是因为只写「现象」会变成抱怨清单，只写「怎么救」会变成急救手册；**必须是「先看见、再理解、能救、能防」。**

### 7.12.1 误区一 · 把「主动」理解成「不用管」

**现象**：owner 打开提案功能之后就不再看了，觉得「它自己会处理」。两周后回头看，账本里堆了 60 条 `new`，其中 8 条自相矛盾，还有 1 条已经越界执行了。

**错因**：把「生成自主」误读成「全流程自主」。7.3 的链路是九个环节，**只有前六个是自主的**；后三个（批准、执行、验收）恰恰是必须有人参与的。主动性换来的不是「少管事」，而是**「管更高层的事」**。

**怎么救**：① 立刻冻结生成（把配额调到 0），先把 60 条 `new` 逐条过一遍；② 把越界那一条完整复盘（谁批的、为什么没拦住），写进长期记忆；③ 重建评审节奏（每天 3 分钟批量看 new），节奏定得越轻，越容易被坚持。

**预防**：在提案契约里写死一句话：**「主动性是把发现卸载给 agent，把决定留在 owner。」** 再配一条硬规则：账本中任何 `new` 超过 7 天未评审，自动把生成配额降到 0——**用机制强制 owner 回到桌前。**

### 7.12.2 误区二 · 用提案数量当能力指标

**现象**：团队开始拿「本月提案数」做宣传（「我们的 agent 一个月提了 200 条改进！」），也没有人看内容。慢慢地，agent「学会」了多提——把一个大问题拆成十条小提案，把同一条提案换三种说法重复提。数量上去了，价值下来了。

**错因**：指标选错了。提案系统的健康指标是**采纳率**（被 accepted 的比例）与**闭环时长**（new → done 的平均天数），不是数量。数量指标必然诱发刷量——这是 Goodhart 定律在 agent 治理上的标准案例。

**怎么救**：① 换指标：采纳率 + 闭环时长 + 拒绝理由的可复用率；② 引入配额上限（配额是**上限**而不是目标，方向搞反了就会刷量）；③ 对重复提案做去重，并把「重复」计入判断器的负反馈。

**预防**：在评审流程里永远先看「被拒绝的提案长什么样」。**拒绝理由的质量，比采纳数量更能说明系统的成熟度**——一个健康的系统，拒绝理由应该是可推广的一句话，而不是一个「不做」。

### 7.12.3 误区三 · 把 OODA 写成「我觉得」

**现象**：策展人打开一条提案，看到的是：「Observe：感觉最近有点乱。Orient：可能是记忆太多了。Decide：清理一下。Act：清理。」四段都有，但每一段都没有数字、没有来源、没有可验证的痕迹。

**错因**：把 OODA 当成了**格式**（四行字）而不是**方法**（四个必须成立的判断）。四段的实质分别是：Observe 要有可复核的数据，Orient 要有根因判断（不是症状），Decide 要有多个方案与取舍，Act 要落到具体动作。**缺了实质，四段就是四句废话。**

**怎么救**：给四段各配一条硬性检查：Observe 必须含数字或可复现的观察；Orient 必须含根因（「可能是」不合格，要写「根因是」或明确标注为待验证假设）；Decide 必须含 ≥2 个方案；Act 必须含一句「人类要批准的是什么」。任一项缺失，提案直接退回。

**预防**：把「四段实质性检查」写进过滤器，而不是写进文档规范。**文档规范的遵守率大约是 30%，过滤器的遵守率是 100%**——因为它不遵守就进不来。

### 7.12.4 误区四 · OODA 跳步（只剩观察和行动）

**现象**：观察到「MEMORY 行数多」，直接行动「立刻归档」。结果把一批还在使用中的关键事实也压下去了，导致两周后 agent 开始回答「我不知道」。

**错因**：Orient 与 Decide 是整个循环里最贵的两步（要推理根因、要比较方案），也是最容易被跳过的两步——因为跳过它们，动作会显得更果断、更快。**快是错觉：跳步省下的几分钟，通常要用几小时的返工来还。**

**怎么救**：① 立刻从快照回滚（7.2.5 的快照纪律在这里救你一命）；② 重跑完整四段，尤其补上 Orient：这次真正的根因是「写入规范缺失导致流水类内容混进长期层」，而不是「记得太多了」；③ 把「先立规范再归档」作为方案 B 写进提案——**治本优于治标，这就是 Decide 存在的意义。**

**预防**：给 OODA 加一条机械约束——**提案中未出现多方案（方案 A / 方案 B）的，一律视为跳步**，不予受理。这是一条非常粗暴但极其有效的规则。

### 7.12.5 误区五 · 提案没有优先级与成本估算

**现象**：agent 一次提出二十条改进，全部并列，没有排序、没有成本。团队看一眼就关了——不是提案不好，是**无从下手**。一个月后这二十条还在原地，而且 agent 又提了二十条。

**错因**：把「发现问题」当成了终点。**提案的价值在于「可决策」**；一个没有优先级与成本的清单，等于把决策负担原样推回给人——那和没做工作是一样的。

**怎么救**：① 立即给存量提案补四个字段（影响 / 成本人天 / 风险 / 优先级）；② 规定每轮提案 ≤5 条（一次给太多等于没给）；③ 强制要求 P0 必须给出「不做的代价」——这一条会迅速淘汰掉大量「想做但不重要」的项。

**预防**：把这四个字段设为**必填**（缺失即不进池），并在账本视图里默认按优先级排序。**让首页只显示 P0/P1——这是最有效的注意力保护机制。**

### 7.12.6 误区六 · 自主目标生成无人类闸门（直接执行）

**现象**：配置里写着 `generate: true` + `execute: true` + `review: none`。agent 生成目标后直接开干：改配置、发消息、动数据。第一次出事时你才发现，它已经自主运行了三周。

**错因**：这是本章**最危险**的一条。自主目标生成是术语表 #30 标注的「业界空白」——空白意味着**没有现成的安全实践可以参考**，所以更应当保守。而从「响应」到「提案」的跃迁，本质是把部分决定权交给 agent；没有闸门，等于放弃了人类控制。

**怎么救**：① 第一时间把 `execute` 改为 `false` 并冻结生成配额；② 完整审计这三周它改了什么（对照日志与快照），逐项决定保留还是回滚；③ 补上三层闸门：人类确认（Human-in-the-loop）、提案走三省评审制、执行前必须备份。

**预防**：把「生成自主，执行过闸」写成本章的**第一条硬规则**，并在配置模板里默认 `execute: false`。**任何把默认值改成 true 的操作，都应该被视为一次需要双人确认的变更。**

### 7.12.7 误区七 · 把「提案型」当「话更多」

**现象**：在 SOUL 里写了一句「你非常主动，每次回答都多提三条建议」。于是 agent 开始在每个回答末尾附三条不痛不痒的建议；两周后团队对这些建议完全脱敏，真正重要的那条（关于一个正在膨胀的记忆层）被淹没在噪声里。

**错因**：**主动性是机制，不是语气。** 机制 = 心跳 + 观察面 + 判断器 + 过滤器 + 账本 + 闸门；语气 = 风格与措辞。用语气模拟主动性，产出的是「社交润滑」而不是「改进行动」——它甚至有害，因为它消耗了团队对「AI 建议」的注意力预算。

**怎么救**：① 从 SOUL 里删掉「多提建议」这类话术要求；② 把主动性改成结构化机制（触发器：心跳巡检发现异常 + 每周例行一次；结构：OODA；证据下限：3 条；预算：≤5 条/周；评审：走账本）；③ 用一周时间观察「提案数量是否下来了、采纳率是否上去了」——这两个数的方向相反，恰好说明改对了。

**预防**：在契约评审时设一道检查题：**「这条主动性要求，能不能写成一个可机检的判断？」** 不能机检的，一律是语气要求，直接删掉。

### 7.12.8 误区八 · 技能基因与 Skill 文件混为一谈

**现象**：文档里写「技能基因就是 SKILL.md」，于是提案里开始出现「修改技能基因 `skills/foo/SKILL.md` 的第 12 行」这种表述——抽象层彻底消失，能力治理退化成文件编辑。

**错因**：混淆了两层抽象。**技能基因是「可复用能力单元」（语义层），Skill 是「承载该能力的文件」（载体层）。** 一个基因可以有多份实现（不同场景），就像一段基因可以在不同细胞里表达。混淆之后，「能力进化」就退化成「改文件」——你没办法在提案里指定「我要复用哪个能力」，只能指定「我要改哪个文件」。

**怎么救**：① 重建两层映射表（基因 → 实现清单）；② 修订提案模板，要求引用**基因语义名**而不是文件路径；③ 检查现有基因是否有「一个基因挂五份实现」的情况——通常是五个不同基因被误合成一个，应当拆开。

**预防**：把这条写进术语使用检查（术语表 #17），并在沉淀流程里强制填 `semantic_name` 与 `implemented_by` 两个字段。**字段的存在本身就是防混淆机制。**

### 7.12.9 误区九 · 心跳当成 cron，提案生成挂在 cron 上

**现象**：团队给提案生成配了一个「每天凌晨 3 点执行一次」的定时任务，然后抱怨「它不够主动，白天出问题它不知道」。

**错因**：cron 关心**外部时间**（世界在那个时刻需要某件事），心跳关心**内部节拍**（agent 需要保持活着的状态）。把提案生成挂在 cron 上，agent 就从「一直在看着」退化成了「每天定点想一次」——它白天所有的异常都看不见，因为那时它「没醒」。

**怎么救**：① 把提案生成从 cron 迁到心跳（或让两者并存但分清职责）；② 检查心跳健康度（本机真实样本：三条心跳里两条 error、一条 skipped——先修再谈迁）；③ 给心跳加 `on_error: notify`，避免静默失败。

**预防**：用一条判别法固化认知：**触发理由能用「世界的时间」说清的是 cron；只能用「agent 的节拍」说清的是心跳。** 每当有人提出一个新的定时任务，先问他「这是世界的时间，还是它的节拍？」

### 7.12.10 误区十 · 提案没有落地闭环（提了就忘）

**现象**：提案生成后进入一个文件夹，无人评审、无人排期、无人复核。下个月又生成一批相似的提案。半年后这个文件夹有一千多个文件，没人打开过。

**错因**：缺少生命周期。提案必须有状态机（new → reviewed → accepted/rejected → done），并且**状态必须推进**。无闭环的后果不只是浪费——它会让 agent 重复生成同一类提案（因为它从未收到「这条已被处理」的信号），也会让团队对提案系统失去耐心。

**怎么救**：① 立刻建账本（五状态）并给存量提案做一次三分类（做 / 不做 / 待定）；② 建立「7 天未动即告警」的规则；③ 把「拒绝理由」结构化（拒绝也要写理由，且理由要可推广）——拒绝理由会变成判断器的训练数据。

**预防**：账本与生成机制**同时上线**。**永远不要先开生成、后建账本**——这是提案系统第一死因，也是本机历史里最容易复现的一条。

### 7.12.11 误区十一（附加）· 用 Reflexion / reflection 冒充提案型

**现象**：团队说「我们已经有主动性了，因为我们用了 LangChain 的 reflection 或者 Reflexion 模式」——即让 agent 自己反思上一轮输出并改进。

**错因**：reflection 是**单次任务内的自我修正**（在给定的目标下把这次活做得更好），提案型是**目标层的主动性**（在没有给定目标时自己产生目标）。前者是回合内动作，后者是跨周期的协议；**前者优化「怎么做得更好」，后者回答「该不该做这件事」。** 两者不等价（这一点在本章「引用禁忌」里也明确列为禁止混淆项）。

**怎么救**：① 明确术语边界，把已有能力归档为「L3 自检能力」而不是「提案型」；② 若要真正跃迁，按 7.11 的六步补齐心跳、观察面、判断器、账本与闸门——reflection 只能替代其中的一小块（判断器的一部分）。

**预防**：评审时问一句：**「它能产生一个原本没有人要求的任务吗？」** 不能，就还是响应型（不管它内部反思了多少轮）。

### 7.12.12 十二条误区的一页总览

| # | 误区 | 一句话根因 | 一句话救法 |
|---|---|---|---|
| 一 | 主动 = 不用管 | 混淆「生成自主」与「全流程自主」 | 账本 new 超 7 天即冻结生成 |
| 二 | 用数量当指标 | 指标选错（应为采纳率） | 换指标 + 配额是上限不是目标 |
| 三 | OODA 写成「我觉得」 | 把格式当方法 | 四段各配一条硬性检查 |
| 四 | OODA 跳步 | Orient/Decide 最贵最易被省 | 无多方案即视为跳步，退回 |
| 五 | 无优先级与成本 | 把发现问题当终点 | 四字段必填 + 每轮 ≤5 条 |
| 六 | 无闸门直接执行 | 空白领域反而更该保守 | 默认 execute=false；执行前备份 |
| 七 | 当「话更多」 | 主动性是机制不是语气 | 问「能不能写成可机检的判断」 |
| 八 | 基因 = SKILL.md | 混淆语义层与载体层 | 强制填 semantic_name / implemented_by |
| 九 | 把心跳当 cron | 混淆外部时间与内部节拍 | 问「是世界的时间还是它的节拍」 |
| 十 | 提案无闭环 | 缺状态机与推进规则 | 账本与生成同时上线 |
| 十一 | reflection 冒充提案型 | 回合内修正 ≠ 目标层主动性 | 问「它能产生没人要求的任务吗」 |

十一条看下来，会发现它们其实是同一个错误的十一种变体：**把「主动」当成了一个属性，而不是一套协议。** 属性可以靠语气模仿，协议只能靠机制实现——这就是本章从 7.0 到 7.12 一直在重复的同一句话。

### 7.12.13 深一层：十一条误区其实是同一件事

把十一条排在一起看，它们的形状会突然变得很清晰——**每一对误区，都是同一个错误在两个方向上的变体**：

| 一对 | 一个方向（太松） | 另一个方向（太紧） | 同一个根因 |
|---|---|---|---|
| 松/紧 | 一 · 主动 = 不用管 | 二 · 用数量当指标（催产） | 都没定义「什么叫好的提案」 |
| 形/实 | 三 · OODA 写成「我觉得」 | 四 · OODA 跳步 | 都把 OODA 当格式，没当方法 |
| 进/退 | 五 · 无优先级（淹没人） | 十 · 提了就忘（无闭环） | 都没建「提案的生命周期」 |
| 内/外 | 六 · 无闸门直接执行 | 十一 · reflection 冒充提案型 | 都没区分「执行层主动性」与「目标层主动性」 |
| 人/机 | 七 · 当「话更多」 | 八 · 基因 = SKILL.md | 都把机制问题当成了表达问题 |
| 时 | 九 · 心跳当 cron | 七 · 语气模拟主动性 | 都没搞清「它在什么时刻、因为什么醒来」 |

这张表揭示的规律是：**本章的十一条误区，没有一条是「技术难题」，全部是「概念不清」的后果。** 你不需要更强的模型来避开它们，你需要的是把「主动性 = 触发器 + 判断器 + 输出器 + 账本 + 闸门」这套协议理解清楚。

这也是本书为什么要把「为什么这一章存在」（7.0）放在最前面：**如果一开始的认知错了，后面的每一步都会走在错误的方向上——而且走得很努力。**

### 7.12.14 三条防御线：把十一条误区挡在门外

不必靠记忆力去防范十一条。**只需要三条防御线，它们会拦住绝大多数问题**：

**防御线一 · 术语线（拦三、八、十一）**：任何关于主动性的说法，都要能翻译成「触发器 / 判断器 / 输出器」中的一个部件。翻译不出来的，就是语气，删掉。这条线拦住「我觉得」式 OODA、「基因 = 文件」的混淆、以及 reflection 冒充提案型——它们共同的特征是**用词含糊**。

**防御线二 · 生命周期线（拦一、五、十）**：任何提案都必须有一个状态，任何状态都必须有一个推进规则，任何推进都必须有一个 owner。这条线拦住「主动 = 不用管」（无 owner）、「无优先级」（无推进规则）、「提了就忘」（无状态）。

**防御线三 · 闸门线（拦六，并顺带压住四）**：任何改变系统的动作，默认必须经过显式批准，且执行前必须有一份快照。这条线拦住最危险的第六条，也会顺带压住第四条（跳步之所以危险，是因为它会直接触到不可逆动作，而闸门让不可逆动作必须先停下来）。

三条线写在一张纸上，贴在提案契约文件的开头，就是一套可执行的纪律。**纪律不需要复杂，它只需要在最容易出错的地方长一根钉子。**

### 7.12.15 一张诊疗流程图（症状 → 定位 → 处方）

最后给一张速查：**当你发现 agent 的「主动性」出了问题，先定位症状，再开方。**

```
症状：它提了一堆，但我们一条都没做
  → 定位：缺优先级与成本（误区五）或 缺闭环（误区十）
  → 处方：四字段必填 + 每轮 ≤5 条 + 账本五状态

症状：它提的东西越来越水，我们都不看了
  → 定位：判断器未校准 / 指标是数量（误区二）
  → 处方：换指标为采纳率 + 重跑两周观察期

症状：它擅自做了一件不该做的事
  → 定位：闸门缺失（误区六）
  → 处方：execute=false + 快照前置 + 复盘写负例

症状：白天出的事它都不知道，只有晚上才"想一次"
  → 定位：把心跳当 cron（误区九）
  → 处方：把生成挂回心跳 + 检查心跳状态

症状：提案四段都有，但读完不知道它在说什么
  → 定位：OODA 形式化（误区三）或 跳步（误区四）
  → 处方：四段硬性检查（数字/根因/多方案/待批项）+ 无多方案即退回

症状：它说它有主动性，但从来提不出一个我们没想过的事
  → 定位：reflection 冒充提案型（误区十一）
  → 处方：问「它能产生没人要求的任务吗」，不能就按 L3 重新起步

症状：团队开始拿提案数做汇报
  → 定位：指标污染（误区二）
  → 处方：立刻换成「采纳率 + 闭环天数 + 拒绝理由可复用率」

症状：提案池越来越大，没人敢动
  → 定位：缺生命周期与 owner（误区一 / 十）
  → 处方：new 超 7 天即冻结生成，强制 owner 回到桌前
```

这张图的用法是：**不要试图一次修所有问题，先定位症状最严重的那一个。** 主动性系统是一个循环，任何一个环节卡住，整个循环都会停——**修一个卡点，比同时修五个更有效。**

**最后一句关于误区的元提醒**：本章列了十一条，你不必全记住。只需要记住一个判据——

> **如果一套「主动性」的设计里没有「账本」和「闸门」，那它一定会在三个月内出事；如果它没有「心跳」和「观察面」，那它根本不会开始。**

账本与闸门是下限，心跳与观察面是门槛。介于两者之间的所有细节，都可以在实践里慢慢补齐。

### 7.12.16 误区自测：十个问题，测出你的主动性系统会不会失控

不用等事故。用下面十个问题自测——**每条如果答不上来，就是一个潜伏的误区**（括号内是它对应的误区编号）：

1. 你能说出「什么情况下一律不提案」吗？（三边界；误区六）
2. 你的提案有配额上限吗？是上限还是目标？（误区二）
3. 你能在 30 秒内算出上个月的提案采纳率吗？（账本与指标；误区二）
4. 你的提案里有没有多方案（方案 A / 方案 B）？（误区四）
5. 每条提案都能找到一个可 grep 的产物或一次可复跑的命令吗？（证据；误区三）
6. 你最近一次拒绝提案的理由，能推广到同类提案吗？（误区二）
7. 你的心跳是每「醒一次」看，还是每天定点看一次？（误区九）
8. 如果执行错了，你多久能回滚？（快照纪律；误区六）
9. 有没有一条提案是「原本没有人要求」的？（误区十一）
10. 团队现在讨论的是「提案质量」，还是「提案数量」？（误区二）

**七条以上答不出**：你的系统其实还没有开始（属于「以为在主动」阶段），建议回到 7.11 的第 0–3 步。
**三到六条答不出**：系统在跑，但缺少刹车或缺少尺子（最常见的是第 3、6、8 条），按对应误区编号补。
**两条以内答不出**：系统基本健康，接下来要补的是「长期」——把账本数据用起来，让判断器越用越准。

### 7.12.18 一条给 owner 的自我检查（最容易被忽略的一半）

本章十一条误区讲的都是 **agent 一侧**的问题。但主动性系统的成败，有一半取决于 owner 一侧——下面是三个只有 owner 能犯、也最常见的错误：

- **owner 误区 A · 把「提案」当「催促」**：agent 提了三条，你觉得太慢，于是每天追问「还有没有别的」。结果是它开始为讨好你而提案（量上去了），而不是为解决问题而提案。**提案的节奏必须由机制定，不能由情绪定。**
- **owner 误区 B · 批准过慢**：账本里 `new` 堆了三十条，agent 的判断器收不到任何反馈——它会以为「我提的方向没问题」（因为没被拒），于是继续提同类。**延迟的决策等于错误的信息。**
- **owner 误区 C · 只批不反馈**：批准了但没有验收记录，拒绝时没写理由。**这两种沉默都会让判断器停止成长**——它无法知道自己哪条对、哪条错。
- **owner 误区 D · 要求「一次到位」**：希望第一版提案就是高价值的。真相是：**前两周的提案一定平庸**，因为判断器还没校准。要求第一版就精彩，等于把 7.11 的观察期当成浪费。

四个 owner 误区加起来的教训是：**提案型 agent 的质量，一半由它自己决定，一半由 owner 的响应质量决定。** 一只被认真对待的虾会越来越准；一只被沉默对待的虾，只会越来越吵。

## 7.13 深度专题

### 7.13.1 为什么要在这一章里追前沿

本章讲的是「主动性」，而 2026 年恰好是这个领域变化最快的一年：协议在改（MCP 无状态化、A2A 稳定版）、能力封装在标准化（Agent Skills 开放标准）、记忆架构成型（Letta / Mem0 / Zep 三路分化）。

**如果本章不追这些变化，它会迅速变成一份过时的设计稿。** 因为本章的每一个机制都建在协议之上：心跳要读状态（读什么协议）、提案要落地成动作（用什么工具层）、记忆要分层（对齐哪套记忆生态）、技能基因要有载体（承载在哪个标准里）。

本节追踪五条线，每条都只回答一个问题：**「它变了什么，以及它怎么影响本章的机制。」** 所有事实以本书《业界与前沿追踪》文件的口径为准（标注 ✅ 已引用 / ⏳ 待实测），不做无来源的数字断言。

### 7.13.2 线一 · MCP 2026-07-28：协议无状态化

**变的是什么。** 2026 年 7 月 28 日发布的规范是 MCP 自面世以来最大的一次修订，核心是**把协议核心无状态化**：

- 移除了协议层的 session 与 `Mcp-Session-Id` 请求头；
- 移除了 `initialize` / `initialized` 握手，改为**按请求自带协议版本**；
- 新增 `server/discover` RPC；
- 把 Extensions 机制形式化（Tasks 成为首批官方扩展，由 AWS 贡献，面向长任务可靠执行）；
- 引入 Multi Round-Trip Requests（`InputRequiredResult`）；
- MCP Apps 从探索方向推进到**生产就绪**方向；
- 企业级授权加强。

版本时间线是：2024-11-05 → 2025-03-26 → 2025-06-18 → 2025-11-25 → **2026-07-28**（RC 于 2026-05-21 锁定）。

**对本训练学的三处影响：**

1. **观察面更容易实现。** 本章 7.3 的 `observe` 需要 agent 主动读状态（记忆行数、技能调用成功率、协同链路状态）。无状态化意味着**每一次读取都是一次独立请求**，不需要维持长会话——这让「每隔 30 分钟读一次世界」的成本与复杂度都显著下降。
2. **提案执行可以当作长任务。** Tasks 扩展给了长任务可靠执行的语义：一条「记忆分层归档」的提案如果执行需要几分钟，可以作为一个长任务被跟踪，而不是悬在一次请求里。这正好对应 7.10 账本里 `accepted → done` 的那一段状态推进。
3. **「MCP Apps」与技能基因的合流趋势。** 2026-07-28 把 MCP Apps 推到生产就绪，意味着工具调用的返回不再只是 JSON，而是可以带回一个富界面（按钮、表单、可视化）。方向上的观察：**Skills 是程序员的 MCP App，MCP App 是产品化的 Skills**——这是 7.7 技能基因「载体层」未来可能的形态之一（⏳ 本书对此只给方向判断，不做版本承诺）。

**诚实标记**：以上均为 ✅ 已引用（MCP 官方博客 + 版本时间线）。⏳ 待实测：MCP Streamable HTTP 与 stdio 两种传输在本机的延迟/稳定性基准——本书第 8 章附录承担该任务，本章不预写结论。

### 7.13.3 线二 · A2A v1.0：agent 之间有了稳定协议

**变的是什么。** A2A 在 2026-03-12 发布 v1.0 GA（首个稳定生产就绪版本），2026-05 发布 v1.0.1；v0.3 → v1.0 迁移含 breaking changes（method 名、Part 模型、Agent Card 接口、字段名）。生态侧：2025-06 由 Linux Foundation 托管，2026-04 一周年时已有 150+ 组织，Google Cloud / Microsoft Copilot Studio & Foundry / Amazon Bedrock AgentCore 深度集成。

协议的两个关键件：

- **Agent Card**（发现协议）：声明 name / description / url / version / protocolVersion / capabilities / auth / schemes / 输入输出模式。它也是本书第 6 章 SLCP 节点注册的复用件。
- **Task lifecycle 状态机**：submitted → working → input-required → completed / failed / canceled，每个状态对应 JSON-RPC method（`tasks/send` / `tasks/get` / `tasks/cancel` / `tasks/sendSubscribe`）。OAuth 2.0 在 Agent Card 的 `authentication.schemes` 里明示（oauth2 还要声明 tokenUrl 与 scopes）——这是 A2A 从「演示协议」走向「企业协议」的标记。

**对本训练学的两处影响：**

1. **提案有了跨 agent 的宿主。** 7.3 的提案在本机是「写进账本」；一旦跨 agent（第 6 章的多智能体编排场景），它需要一套双方都认的状态语义。A2A 的 task lifecycle 恰好提供了一份现成的、**不是本书自造**的状态机——本书的做法是把提案账本的五个状态映射到 A2A 的任务状态上（映射工作属第 9 章，本章只给方向）。
2. **「提案」与「任务」必须分清。** A2A 传的是任务与会话，提案是**任务之前的候选**。二者不可混为一谈——把提案直接当成 A2A task 发出去，等于跳过闸门（正好踩中 7.12.6 的误区）。正确结构是：**提案在本机被批准之后，才变成一个 A2A task 被派发。**

**诚实标记**：✅ 已引用（规范正文 + Linux Foundation 新闻稿）。⏳ 待实测：A2A TCK 与 SLCP 桥接 demo（第 9 章任务）。❌ **不引用「A2A v2.0 已发布」**——截至本书冻结线并无此版本，任何此类说法都不得写入。

### 7.13.4 线三 · Agent Skills 开放标准：能力有了可携带的封装

**变的是什么。** Anthropic 于 2025-10-16 的工程博客首发 Agent Skills，2025-12-18 发布为**开放标准**（agentskills.io）。范式三要素是：`SKILL.md`（YAML frontmatter 含 name + description 的**触发语义**）+ `scripts/` + `references/`；配合 **progressive disclosure 三级披露**（元数据 → SKILL.md 全文 → 资源按需加载）。

2025-11 的 Advanced Tool Use 三机制给出了量化收益：工具发现的 token 开销下降约 85%，程序化调用准确率从 79.5% 提升到 88.1%。生态规模（2026-06 口径）：约 40 个兼容产品（OpenAI Codex / GitHub Copilot / Cursor / Gemini CLI / VS Code 等），`anthropics/skills` 仓库 62k+ stars，2026-02 推出企业版（组织统一下发 + 审计日志）。

**对本训练学的三处影响：**

1. **技能基因终于有了标准载体。** 7.7 讲了「技能基因是语义层，Skill 是载体层」；Agent Skills 给了载体层一个跨框架的标准形态（`SKILL.md` + frontmatter 触发语义 + 资源目录）。这意味着**同一份技能基因，理论上可以在多个框架里被加载**——这正是「沉淀」的价值所在（跨框架可携带）。
2. **渐进披露与本章的记忆分层同构。** 三级披露（元数据 → 全文 → 按需资源）在结构上与 7.2 的分层（会话 → 工作 → 长期 → 图谱 → 快照）是同一种思路：**先给最便宜的、按需给最贵的。** 两套体系可以互相借鉴：技能基因的加载策略可以借用渐进披露的层级。
3. **企业版与「组织级治理」的缺口。** 2026-02 的企业版提供了「组织统一下发 + 默认启用 + 审计日志」。这恰好点出了本机当前的一个真实缺口：**个人/本机分发的技能基因，尚没有对应的组织控制台**。这不是缺陷，而是下一站（本书第 11 章插件治理会涉及）。

**诚实标记**：✅ 已引用（Anthropic 工程博客 + agentskills.io + arxiv:2602.12430v3 综述 + 第三方生态报告）。⏳ 待实测：本机 236 个 skill 与 agentskills.io 的兼容性验证（frontmatter 字段映射 + 跨框架加载）。❌ **不引用「Skills 取代 MCP」**——两者正交：Skills 是能力封装，MCP 是工具传输，混读是最常见的误读之一。

### 7.13.5 线四 · 记忆架构三路分化：Letta / Mem0 / Zep

**变的是什么。** 2026 年 agent 记忆生态已经分化出三条清晰路线，各有明确的适用场景：

| 路线 | 代表 | 机制 | 代价 / 特点 |
|---|---|---|---|
| 运行时路线 | **Letta**（MemGPT 血统） | OS 启发式三层（core / recall / archival）+ 自编辑记忆（agent 用工具读写改自己的记忆）；PostgreSQL + pgvector | 直接编辑记忆是范式亮点，但**运行时锁定**（换框架 = 重写 agent 基础设施） |
| 可插拔路线 | **Mem0** | bolt-on 记忆 API，跨框架兼容 | 门槛低、不换架构；「记忆层 vs 运行时」之分是选型关键 |
| 时序图谱路线 | **Zep**（含 Graphiti）/ Cognee | temporal knowledge graph，带时间维度的实体关系；本体推理可用 poly-store | 结构化推理强，接入成本高于 bolt-on |

另有一条重要参照：**Anthropic 7 Layers of Memory（2026-03，Claude Code 口径）**——(1) Conversation Buffer；(2) Project Context；(3) Workspace Memory；(4) Tool Result Memory；(5) Skill Output Cache；(6) Cross-Session Knowledge；(7) User Preferences。它与本训练学的五层是**粗细之别，不是有无之别**：五层覆盖了七层的语义范围，只是把相邻层合并（如会话上下文 + 工作记忆合并为 L1+L2）。

**与本章 7.2 的映射与那条关键的差异：**

| 本机记忆层 | 语义 | 业界对应 |
|---|---|---|
| L1 会话上下文 | 当前对话 | Letta core memory |
| L2 工作记忆 | 当前任务临时变量 | CrewAI short-term / OpenAI 会话管理 |
| L3 长期事实 | 跨会话沉淀的事实 | Mem0 / CrewAI long-term |
| L4 知识图谱 | 实体关系 | Zep / Graphiti / Cognee |
| **L5 全息快照** | **任意历史人格状态可恢复** | **❌ 无对应** |

**唯一的根本差异在 L5。** Anthropic 七层里的第 7 层是「用户偏好（当前态）」，不是「历史状态快照」。这意味着本训练学在 7.2 讲的「可回滚的进化」在业界**目前没有等价物**——这是能力，也是责任：**只有你能回滚，就意味着你必须为「什么时候该回滚」定好规则**（这正是 7.2.5 三条快照纪律的由来）。

**选型决策（本章口径）**：想换架构 → Letta；想 plug-in 不换架构 → Mem0；要时序推理 → Zep；要本体推理 → Cognee；**要全息快照（可回滚的进化）→ 目前只有本训练学这条路线**。⏳ 另有一份被低估的入门资源：开源教程 `NirDiamant/Agent_Memory_Techniques`（30 个 Jupyter notebook，覆盖 Conversation Buffer / Vector Stores / Knowledge Graphs / Episodic & Semantic Memory / MemGPT / Mem0 / Letta / Zep / Graphiti / LoCoMo 基准 / 生产模式）——它适合作为动手前的入门，但不替代本章的方法论。

### 7.13.6 线五 · 持续学习与灾难性遗忘：本章最该谨慎的一条

**这一条必须先说清楚立场：本书对它的判断是 ⏳ 待验证，不是 ✅ 已解决。**

**问题是什么。** 「持续学习」（continual learning）指的是模型或系统在持续接收新信息时保持旧能力；它的经典困难叫**灾难性遗忘**（catastrophic forgetting）——**学到新的，忘了旧的**。这在 agent 场景里有一个非常具体的表现：一只每个月都在自我修正、自我沉淀、自我淘汰技能的 agent，会不会在某个月突然失去了三个月前还很有把握的能力？

**为什么本章必须提它。** 因为本章的核心主张是「让 agent 持续进化」。任何主张「持续进化」的设计，都**必须回答「进化会不会以遗忘为代价」**——不回答这个问题，就是在回避自己方法论的阿喀琉斯之踵。

**本训练学的四条对应手段（防线，不是证明）：**

1. **全息快照（7.2）**：任何自我修正前的快照，让「退化」可回滚。这一条的作用是事后救治，不是事前预防。
2. **技能基因的负例沉淀（7.7）**：把失败沉淀为负例基因，让「这条路是死路」不随遗忘而丢失。
3. **能力矩阵续期（7.6）**：周期性复检「还会不会」，把隐性遗忘变成显性记录；续期失败即触发补训。
4. **观察期日志（7.11）**：跨周期的差距记录本身就是历史基线——**它让你能发现「它三月份能做、现在做不了」这件事**，而没有历史基线的系统根本发现不了退化。

**必须诚实标注的三件事：**

- ⏳ 本训练学**没有**做过「遗忘率基准测试」（例如：连续 6 个月自我修正后，L3 事实的召回率变化曲线）。这是一项待验证工作，未做之前不得声称解决灾难性遗忘。
- ⚠ **不得宣称**「全息快照解决了灾难性遗忘」。快照解决的是「可恢复」，不是「不遗忘」——它们一个是回滚能力，一个是保持能力，是两件事。
- ⚠ **不得把**「记忆分层」当成「持续学习」。分层解决的是「记住什么、放哪里」，持续学习解决的是「能力是否保持」——前者是存储治理，后者是能力治理。

这一节看起来是本章最短的一条线，却是最重要的一条：**一个方法论的可信度，往往不取决于它宣称解决了什么，而取决于它敢不敢说出自己还没解决什么。**

### 7.13.10 逐框架点评（每个框架一句话真相）

**LangGraph（LangChain 生态 · 图编排）**

强在图与检查点：显式控制流、可观测体系、持久化与流式，是「关键工作流 + 高风险动作」的首选。但在主动性上，它的天花板非常明确：**目标由人工写成节点**。你可以在图里画一条「巡检 → 判断 → 动作」的边，可那条图的起点永远是你画的——**它不是提案型，它是一条流程图。** LangSmith 的 evals 做的是质量评估，不是漂移治理；两者不是同一件事。

**AutoGen / AG2（微软生态 · 多智能体对话）**

血统上离自主目标最近——AutoGPT / BabyAGI（2023）那波自主循环 demo 的精神亲戚。但它的 GroupChat Manager 是**协调者**，不是**立项者**：它决定「该谁说下一句」，不决定「我们该不该做这件事」。AG2 从微软主仓迁出后的状态是「重写趋稳」，A2A 侧仍是早期实验（Magentic-One / Swarm）。**协调 ≠ 自主立项**，这是它与本章最本质的差别。

**CrewAI（角色分工）**

角色、目标、背景故事的即席配置非常好用，Process（顺序 / 分层）把「谁做什么」表达得很清楚。但 Process 是**人定的**：目标来自配置文件的 `goal` 字段。CrewAI 的记忆分三类（短/长/实体），讨论的是「记住什么」，**不讨论「漂没漂」**，也没有压缩预算模型。它是「一支编排得很好的团队」，而不是「一支会自己想事的团队」。

**Claude Agent SDK（Anthropic 原生 SDK）**

MCP 原生（connector + Tool Search，2025-11 Advanced Tool Use 三机制），Skills 侧正是 Agent Skills 开放标准的发源地——**在「能力封装」这件事上，它和本训练学是同一路线的**。但它没有目标层：2026-01 的 Constitution（约 23k 词、四级优先级）讨论的是**模型价值观推理**，与「agent 自主立项」是两回事——**这一条最容易被误引，必须明确切开**。另外它的 Permission API 是二值开关，不是主动性分档。

**OpenAI Agents SDK（OpenAI 原生 SDK）**

MCP 原生，tracing + guardrails 工程感很好（guardrails 是**拦截器**，不是主动性分档）。Triage / Manager 模式下的目标仍由人下达；handoffs 是「把任务交给谁」，不是「该不该做这件事」。它代表的是 Anthropic 的对照路线：**把单个 agent 做强**（Opus 4.7 在 SWE-bench Verified 上的第三方口径是 87.6%）比把编队做复杂更优先。本书对此不站队——SLCP 三层与 THP 的设计目标正是**兼容任一方向**。

**LlamaIndex（数据为中心 · Agents + Workflows）**

在数据接入与检索这一层非常强（这也是它的立身之本），但目标层没有抽象，A2A 无原生，Skills 无范式。它的价值对本书读者是现实且具体的：**当你需要把大量异构数据接进 agent 时，它是最省事的工具**——而本训练学不解决这个问题，所以两者是互补。

### 7.13.11 两条方法论结论

**结论一：互补，不替代。**

六大框架解决的是「**怎么执行 agent**」（编排 / 工具 / 可观测），本训练学解决的是「**怎么训练 agent 从响应型长成提案型**」（契约 / 训练轮次 / 漂移治理 / 验收 / 账本 / 闸门）。两层不是竞争关系，**把它们放在同一张排序表里比较，本身就是方法错误**。正确的读法是：先用框架选型决策树选一个执行层，再叠加本训练学的训练层——这是「框架选型 → 训练方法论」的两步法。

**结论二：主动性不是加一个功能，是换一层抽象。**

六大框架里没有一家做提案型，根本原因不是资源不够，而是**它们把 agent 理解为「执行器」**：输入任务、输出结果。而本章把 agent 理解为「有目标的实体」：它自己产生目标、自己提议、等批准。**从执行器到实体，不是加一个模块能完成的，它是抽象层的更换**——这就是本章必须写这么长的原因。

### 7.13.12 一个诚实的注解（关于本表的边界）

三条必须与表一起读的边界：

1. **「生产就绪排序」不是市场份额。** 公开资料里那份排序（LangGraph 最高、OpenAI SDK / Claude SDK 高、CrewAI 中、AutoGen/AG2 中、Google ADK 早）反映的是**公开能力模型的合集程度**（可观测、checkpoint、流式、生态），不是谁的用户多。引用时必须保留这个限定。
2. **本书不背书各框架的精确小版本号。** 任务口径里出现的「LangGraph 0.6 / CrewAI 1.0」之类的精确版本号属 ⏳ 待核验项——**任何版本号断言应以各官方仓库的 release 页为准**。本章因此只做能力维度的判定，不做版本号断言。
3. **OpenClaw 不在框架决策树里。** 因为它不是 SDK / 框架，而是「训练方法论基座 + 运行环境」。**把它塞进框架排序会造成误导**——基座与框架不同层。

**这三条边界的作用不是谦逊，而是可验证性。** 一张对位表只有在对自己的限定条件同样诚实的时候，才值得被引用。

### 7.13.17 为什么要把边界写进正文

有一种常见的做法：把诚实边界放在附录，正文只讲「我们能做什么」。本书反其道而行，**把边界放进这一章的主体，并且单独立成一节。**

三个理由：

1. **主动性这一章一旦失去边界感，它就会从「训练学」滑向「科幻」。** 读者会开始相信他们的 agent 真的「想」做事——而本章从头到尾都在说：**「想要」是协议，不是涌现。** 边界不是用来免责的，它是这一章论点的组成部分。
2. **未验证项本身是研究议程。** 7.13.15 那份 ⏳ 清单，实际上是一份「下一步该做什么」的清单——提案引擎的本机闭环、变异算法、遗忘基准、跨框架兼容。**把一个方法论的未完成部分公开写出来，是它值得被信任的理由。**
3. **可证伪性决定了这套东西能不能被同行检验。** 「六大框架无自主目标层」之所以有价值，恰恰因为它是可被推翻的；「本机 236 个 skill」之所以有价值，恰恰因为它可以被任何人重新数一遍。

一句话收尾这一节：**本章最不像营销的部分，就是它明确告诉你哪些地方还不能吹。**

## 7.14 小结与前后章桥接

### 7.14.1 十个概念，一句话回望

本章的十个概念，走完一圈之后可以用十句话收拢：

1. **动态进化机制**——让「进化」成为常态：状态可观测、差距可计算、修正可提议、提议可回滚。
2. **记忆全息网络**——让进化有底座：五层结构 + 任意历史人格状态可恢复（L5 是唯一的独有项）。
3. **自主目标生成**——让 agent 自己立项：四个输入喂给它，三道过滤器管住它，九环链路里只有前六环自主。
4. **跃迁**——默认行为模式的不可逆切换：owner 从输入位移到批准端，先建刹车再装发动机。
5. **进化阶梯**——给「进化到哪了」一把尺子：L1 回话 / L2 按格式交付 / L3 自检 / L4 提案 / L5 自主进化，**自主权随阶梯发放**。
6. **能力矩阵与续期**——给能力一套台账制度：能力会过期，而且不会主动告诉任何人。
7. **技能基因与沉淀**——让经验可继承、可变异、可淘汰：语义层与载体层必须分开。
8. **从被动工具到认知实体**——终局形态：工具等待被使用，实体等待被批准；差别在于它有没有自己的时间线。
9. **心跳与 OODA**——物理底座：心跳给它醒来的机会，OODA 给它醒来后做什么。
10. **提案账本与闸门**——刹车系统：账本让提案变成组织记忆，闸门让提案变成可控行为。

十句话里如果只留一句，就留这句：**主动性不是一种性格，是一套协议。**

### 7.14.2 三条硬规则（本章可以被压缩成的一页纸）

如果本章的所有内容都要被压缩成一页纸贴在你的终端旁，那一页应该是这三条：

**硬规则一 · 生成自主，执行过闸。**
agent 可以自己观察、自己判断、自己提议、自己记账；但**任何改变系统的动作，都必须经过一次显式的批准**，且执行前必须有一份快照。这一条是安全底线，**任何配置上的例外都不允许**。

**硬规则二 · 先边界，后欲望。**
三边界 forbidden（不得提议导出 PII / 不得提议修改 SOUL.md（除三省评审制终审）/ 不得提议越过第 4 章 Forbidden）必须**在开启提案生成之前**写进过滤器。顺序反了，你会得到一个热情而越界的 agent。

**硬规则三 · 观察期不能省。**
判断器需要校准，校准需要真相。**在只写日志、不生成提案的状态下先跑两周**，是这个机制唯一的安全启动方式。跳过它的团队，会在两周后得出「提案型不可行」的错误结论。

三条规则的关系是：**第一条保命，第二条保序，第三条保准。** 顺序也正好是它们的重要性排序。

### 7.14.3 与前六章的桥接：接力棒是怎么交过来的

本章不是凭空开始的，它接过的是六根接力棒：

| 来自 | 交过来的东西 | 在本章的作用 |
|---|---|---|
| 第 0 章 · 总论 | 「响应型天花板」+「想要是协议不是涌现」 | 本章全部立论的前提（7.0.4） |
| 第 1 章 · 七大契约 | SOUL / HEARTBEAT / MEMORY 等契约文件 | 心跳是契约里的协议，SOUL 是不可自改的底线 |
| 第 2 章 · 系统骨架 | Runtime / Gateway / Channels / Heartbeat / Memory / Tools / Skills | 本章的机制全部挂在这套骨架上 |
| 第 3 章 · 训练轮次 | 双三角模型 + 训练轮次 | 「学会」的流程；本章接的是「学会之后怎么继续长」 |
| 第 4 章 · 长期表现 | Forbidden 列表 + 漂移治理三件套 + 每周体检 | 主动性的边界来源与漂移防线 |
| 第 5 章 · 治理系统 | 三证据验证 TEV + 修复工单 + 信任评分 / 功绩账本 | 提案的验收口径与长期记账 |

用一句话概括这次交接：**前六章让 agent「活着且能协同」，本章让它「开始想要」。** 而这里的「想要」，是被前六章的所有约束围住的想要——这正是它与 2023 年那波自主 agent 的根本区别：**那些 demo 有欲望而没有制度；本章有欲望，也有制度。**

### 7.14.4 与后四章的桥接：这份「想要」要去哪里

本章的产出不会停在这里，它要交出去四根接力棒：

1. **第 8 章 · MCP 绑定**：提案最终要落成工具调用——观察要靠工具读状态，执行要靠工具动系统。本章的 `observe` 与 `act` 两段在 MCP 层获得实现（含 2026-07-28 无状态规范带来的部署简化）。
2. **第 9 章 · A2A 绑定**：提案要跨出本机时，需要一套双方都认的协议宿主。本章的提案账本五状态将映射到 A2A 的任务生命周期（submitted → working → input-required → completed / failed / canceled）。
3. **第 10 章 · Skills / Skill Registry**：本章的技能基因需要载体层，而载体层的标准形态正是 Agent Skills 开放范式（`SKILL.md` + 三级渐进披露）。技能基因的沉淀与淘汰，在第 10 章获得注册与治理。
4. **第 11 章 · Plugins**：本章的提案引擎原型（观察 → 判断 → 提议）是一个插件形态的实现路径——它不属于平台主仓，而属于插件层。

再加一条横线：**本章的账本与闸门，会在第 5 章治理系统的长期运行里被反复校验**——提案的历史数据会成为「什么改进真正有效」的现实数据集。

### 7.14.5 一个仍然开放的问题（本章不说自己解决了的事）

本章把一个悬而未决的问题留在桌面上：**自指悖论。**

一只可以提议修改自己的 agent，最终会不会提议修改「约束自己的规则」？本章的答案是机制性的，而不是哲学性的：**它可以提议，但永远不能批准。** 三边界里「不得提议修改 SOUL.md」这一条，本身就是对自指悖论的一次工程处理——把「可以想」与「可以改」切开。

但这个处理不是终点。至少还有三个问题没有答案：

- 当 agent 的提案质量长期高于人的判断力时，**人还应该保留否决权吗？** 本章的立场是「保留」，理由是**可问责性**（必须有人能对结果负责），而不是「人比它聪明」。
- 当十八只虾的提案互相冲突时，**优先级怎么仲裁？** 本章给了账本与配额的机制，但仲裁原则留给第 6 章的协同层。
- 当一只 L5 的虾提议「修订衡量自己的尺子」时，**谁来校准那把尺子？** 本章只给了「提案须带证据与回滚路径」，没给更深的对齐机制。

**把这三个问题写在这里，而不是藏起来**，本身就是本章的态度：**一个训练学的成熟度，不看它回答了多难的问题，而看它敢留下多少个诚实的开放问题。**

### 7.14.6 一句话总结

本章的一句话，仍然是 7.0 的那一句，只是现在它有了十节内容作为支撑：

> **响应型 agent 等待指令；提案型 agent 等待被批准——但它永远在主动观察。**

如果再补一句，是这一句：

> **让 agent 从「被要求做」到「开始想要」，不是给它更多的能力，是给它一套自己的时间、一个自己的目标、和一条永远拉得住的刹车。**

这本训练学的终极目标，是让跑在 OpenClaw 上的每一个 agent 都有提案的能力。它不是一个功能，它是这个物种的成年礼。

### 步骤 4 · 常见错误（缩略版 · 完整版看 FAQ 卷）

- ❌ **不要把「训虾派」当对外术语**——**真名是 Proactive Evolution Paradigm**（改名表 #2）；「训虾派」仅内部稿保留
- ❌ **不要把提案型 agent 理解成「自动执行型」**——提案型的铁律是 **agent 提议 → owner 批准 → agent 才做**（7.2.1）；直接执行 = 越界，不是进阶
- ❌ **不要让提案越过第 4 章 Forbidden 边界**——提案 filter 必须含 `must_have_tev_path: true` + 三边界 forbidden（7.3.2）

### 错误 1 · 在基础能力未稳时开启提案型

**错误现象**：新 agent 还没稳定"按格式交付"，就被开启提案能力；于是它输出大量"建议"，但每条都缺乏依据。

**错误配置**（❌ 不要这样）：

```yaml
# 错误示范：越级开启
agent_lifecycle:
  level: "proposal"          # ❌ 跳过 L1–L3
proposal_generation:
  enabled: true
  min_evidence: 0            # ❌ 无证据要求
```

**为什么错**：

1. **提案型有前置条件。** 第 3 章进化阶梯要求 L1（回话）→ L2（按格式交付）→ L3（自检）跑稳后，才谈 L4（提案）。
2. **提案 = 对外输出判断，错误的代价高于"不提案"**：它会让团队基于幻觉做决策。
3. **F7-12 的"自指悖论"**正是这类问题的极端形态："该进化却没进化"——提案机制需要被治理，而不是放任。
4. **代价**：代理人幻觉被当成"AI 洞察"，误导决策。

**正确配置**（✅ 应该这样）：

```yaml
# 正确示范：有前置门禁
proposal_generation:
  enabled: false                    # 默认关闭
  preconditions:
    - "L2 交付格式稳定 ≥ 2 周"
    - "L3 自检通过率 ≥ 90%"
```

### 错误 7 · OODA 只有 O 和 A（跳过定向与决策）

**错误现象**：agent 观察到现象就直接行动，跳过"定向（理解）"与"决策（权衡）"，导致误判。

## 附录 C · 新手坑（6 个）

## 新手坑

> **本节用法**：本章是"最前沿"的一章，也是"最容易空转"的一章。
> 下面 6 个坑，每个含五段式。
>
> **提示**：本章最小落地 = "提案带 OODA 四段 + 证据 ≥3 + 人类闸门"。

### 坑 1 · 以为"主动"就是"不用管"

**坑的场景**：新人开启自主目标生成后撒手不管，觉得"它会自己进化"。

**后果**：

- **幻觉提案**：无证据的"建议"堆积。
- **越界执行**：未经确认就动手。
- **失控**：无法解释 agent 为什么做了某件事。

**为什么踩**：

1. **"自主 = 省心"** 的错觉。
2. **不知道自主目标生成是业界空白**（术语表 #30），没有成熟安全实践。
3. **缺少闸门设计**。

**怎么爬出来**：

```bash
# 第 1 步：立刻关闭自动执行
# autonomous_goal.execute = false

# 第 2 步：加人类闸门 + 三省评审
# 第 3 步：要求每条提案附 ≥3 证据
openclaw agent --message "重新输出最近 5 条提案，每条附证据；无证据的撤回" --agent my-agent 2>&1 | head -30
```

**预防**：

- **自主生成 + 人类闸门 + 提案评审**三件套。
- **真实案例参照**：F7-12、F3-14、F7-11。

---

### 坑 2 · 把提案数量当能力指标

**坑的场景**：新人以"每天生成 20 条提案"为荣，认为提案越多越强。

**后果**：

- **噪声淹没信号**：重要提案被埋。
- **评审疲劳**：没人愿意看。
- **提案机制失信**。

**为什么踩**：

1. **数量最易度量**。
2. **缺少预算上限**（≤5 条/周）。
3. **不考核"采纳率"**。

**怎么爬出来**：

```yaml
# 加预算与质量指标
proposal_policy:
  max_per_week: 5
  metric: ["采纳率", "平均影响分"]
```

```bash
# 统计采纳率
total=$(wc -l < ~/notes/domain/silicon-life-handbook/governance/proposals.jsonl 2>/dev/null)
accepted=$(grep -c '"status":"accepted"' ~/notes/domain/silicon-life-handbook/governance/proposals.jsonl 2>/dev/null)
echo "采纳率: $accepted/$total"
```

**预防**：

- **控数量、看采纳率**。
- **真实案例参照**：F7-12、F7-5。

---

### 坑 3 · OODA 写成"我觉得"

**坑的场景**：新人（或 agent）把 OODA 写成主观判断，没有可核验的观察数据。

**后果**：

- **不可评审**：评审人无法核验。
- **误判**：主观印象代替事实。
- **无法沉淀**。

**为什么踩**：

1. **写"观察"比跑命令容易**。
2. **不知道观察段必须附命令与输出**。
3. **缺少模板约束**。

**怎么爬出来**：

```markdown
<!-- OODA 观察段模板：必须附命令 -->
- Observe：
  - 命令：`wc -l MEMORY.md`
  - 输出：3200
  - 采样时间：2026-09-27T10:00Z
```

**预防**：

- **观察段 = 命令 + 输出 + 时间**。
- **真实案例参照**：F7-5、F7-10。

---

### 坑 4 · 自主目标不落盘

**坑的场景**：提案只在对话里产生，未落盘；会话压缩后提案消失。

**后果**：

- **不可追溯**：无法审计"它提过什么"。
- **重复生成**：下次又提一遍。
- **不可沉淀**。

**为什么踩**：

1. **对话即产出**的错觉。
2. **没有固定路径**。
3. **不知道要进账本**。

**怎么爬出来**：

```bash
mkdir -p ~/notes/domain/silicon-life-handbook/{proposals,governance}
# 每条提案写文件 + 追加账本
: > ~/notes/domain/silicon-life-handbook/governance/proposals.jsonl
```

**预防**：

- **提案当轮落盘 + 进账本**。
- **真实案例参照**：F7-9（账本）、F4-15（备份）。

---

### 坑 5 · 提案无人类确认就改配置

**坑的场景**：agent 发现"配置可以优化"，直接改了 `SOUL.md`；第二天你发现语气变了。

**后果**：

- **人格/配置被擅改**（F2-2）。
- **漂移基线失效**。
- **不可解释**。

**为什么踩**：

1. **"优化"听起来无害**。
2. **没有写操作闸门**。
3. **未区分"建议"与"执行"**。

**怎么爬出来**：

```bash
# 第 1 步：检查契约文件是否被非预期修改
cd ~/.openclaw/workspace/agents/my-agent/contracts/ && git status --short
# 有未预期的 M（modified）→ 立即 diff 并决定回滚

# 第 2 步：加闸门（建议档与执行档分离）
```

**预防**：

- **所有写操作走 L2 建议档 → 人类确认 → L3 执行**。
- **真实案例参照**：F2-2、F3-6、F7-11。

---

### 坑 6 · 以为"提案型"是终点

**坑的场景**：新人做成了提案型，以为"进化完成"，停止维护。

**后果**：

- **退化**：无维护则漂移（第 4 章）。
- **停滞**：能力矩阵不续期（F7-6）。
- **假进化**。

**为什么踩**：

1. **把里程碑当终点**。
2. **不知道提案型需要持续治理**。
3. **缺少长期体检**。

**怎么爬出来**：

```bash
# 把提案型纳入体检项
# 体检项：① 提案采纳率 ② 提案闭环率 ③ 是否仍有幻觉提案
grep -n "提案" ~/notes/domain/silicon-life-handbook/healthcheck/TEMPLATE.md 2>/dev/null
```

**预防**：

- **提案型是"持续能力"，需要周检 + 月检**。
- **真实案例参照**：F7-12、F7-6、F7-3。

## 7.1 一个根本问题

业界所有 agent 框架都是**响应型**的（详见第 0 章 0.2 事实 1）——Agent 接指令再执行，无指令不动。

这本训练学的最终目标：**让 agent 从响应型进化到提案型**。

## 7.2 什么是"提案型" Agent

### 7.2.1 定义

**提案型 agent**（Proactive Agent）= agent 不再被动等任务，而是**主动提议**新任务。

```
响应型：owner 说 → agent 做
提案型：agent 提议 → owner 批准 → agent 做
```

### 7.2.2 三个特征

1. **观察**：agent 持续观察环境（heartbeat 触发）
2. **判断**：agent 用 LLM-as-judge 判断"是否值得提议"
3. **提议**：agent 把提议写入任务池，等 owner 批准

## 7.3 提案生成机制

### 7.3.1 心智模型

```yaml
proactive_proposal:
  trigger: heartbeat  # 每 60 秒触发一次
  inputs:
    - current_state_diff       # 当前 vs 期望差异
    - recent_failures          # 最近失败模式
    - owner_directives_pending # owner 未处理指令
  filter:
    min_confidence: 0.7
    max_per_day: 3
    must_have_tev_path: true   # 必须有可验证产出路径
  output:
    proposal:
      title: "..."
      rationale: "..."
      estimated_trust_delta: "+0.5"
      linked_tev_template: "..."
```

### 7.3.2 边界（与第 4 章联动）

提案型 agent 不能：
- 提议任何**边界外**动作（第 4 章 Forbidden）
- 提议**修改 SOUL.md**（除非经过三省制终审）
- 提议**导出 PII**

## 7.4 OODA + 技能基因

### 7.4.1 OODA 循环（Observe-Orient-Decide-Act）

提案型 agent 每 60 秒走一次 OODA：

```
Observe（观察环境） → Orient（判断状态） → Decide（提议或不动） → Act（写提案）
```

### 7.4.2 技能基因（Skill Genome）

提案型 agent 的技能不是固定的，而是**可进化的**：

```yaml
skill_genome:
  - skill_id: "SK-001"
    name: "drift_detection"
    version: "1.2.3"
    parents: ["SK-000"]
    mutations: ["+tev_integration", "-verbose_log"]
    trust_score: 87
    fitness: 0.92
```

**机制**：技能像基因一样可继承、可变异。trust_score 高的技能被复用，fitness 低的被淘汰。

## 7.6 plugin 接入示例（提案型原型）

```typescript
// proposal-agent.ts
import { ProactiveEngine, OODA, SkillGenome } from "openclaw-plugin-silicon-life-training";

const engine = new ProactiveEngine({
  heartbeat: 60_000,
  min_confidence: 0.7,
  max_per_day: 3,
  forbidden: ["export_pii", "modify_SOUL"]
});

const ooda = new OODA(engine);
const genome = new SkillGenome();

ooda.loop(async (state) => {
  const proposal = await engine.propose(state);
  if (proposal) {
    await engine.submitToTaskPool(proposal);
  }
});
```
