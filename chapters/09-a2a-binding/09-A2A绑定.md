# 第 9 章 · A2A 绑定：SLCP 在 A2A v1.0 上跑

> **本章一句话**：上一章讲"我出去调别人的工具"，这一章反过来——**讲别人怎么发现我、叫我干活，以及我被叫走之后，这支队伍会不会散。**

> 实测环境：OpenClaw 2026.9.4 (3a9d69d) · macOS 26.5.1 · 2026-09-27 冻结线 · 本机 `stock:a2a/index.js` = **disabled**（诚实基线）。

## 9.0 为什么这一章存在

### 9.0.1 一个比"连不上"严重一百倍的问题：连上了，然后呢

第 8 章收尾时留下了一个镜像问题。

MCP 解决的是"**我的 agent 怎么调外面的工具**"——这个方向的主角是我的 agent，它是发起方，它握着主动权。它要什么，就去取什么。

现在把方向翻过来：**外面的 agent 来找我**。

它读了你的 Agent Card，知道你有一个 skill 叫 `drift_detection`，于是它把一份任务递过来："帮我检测一下我这只 agent 是不是漂移了。"

于是你的 agent 开始工作。五分钟、十分钟、二十分钟。

**然后问题来了：**

- 它做的这二十分钟，谁在记账？
- 如果它中途发现自己做不完，谁来接？
- 如果它和一个同样想接这个活儿的同伴撞上了，谁先谁后？
- 如果它把你训了很久的一个能力用在了一个你没同意的方向上，谁看得见？

**这四个问题，一个都不属于"连通性"。** 它们属于**协同的秩序**。

行业里有一个普遍的错觉：**"agent 能互相通话" 是终点。** A2A 协议把"能通话"这件事标准化了——Agent Card 做发现，JSON-RPC 做方法调用，task lifecycle（submitted / working / input-required / completed / failed / canceled）做状态机。这是一件非常了不起的事，它让跨厂商、跨框架的 agent 第一次有了共同语言。

**但"能通话"确实只是起点。** 因为通话之后发生的事情，比通话本身复杂一百倍：**有失败、有冲突、有让位、有审计、有归属。**

**这一章就写通话之后的那些事。**

### 9.0.2 没有这一章，读者会掉进四个坑

**第一个坑：把 A2A 当 OpenClaw 的原生能力。**

本机实测的事实是：**OpenClaw 主仓对 A2A 的 grep 命中 = 0。**

对比一下第 8 章：**OpenClaw 原生 MCP 命中 16 处。** 16 对 0——这组数字把两章的位置说得很清楚：

- MCP 是**主仓一等公民**（14 子命令、`mcp.servers` 命名空间、`tools.catalog` 网关 RPC）；
- A2A 是**生态扩展**（`stock:a2a/index.js` 存在，但**默认 disabled**）。

掉进这个坑的人，会在文档里写"OpenClaw 原生支持 A2A，执行 `openclaw a2a ...`"——**而这条命令根本不存在**。

**第二个坑：把 ACP 当 SLCP 的英文名。**

这是本书最容易踩、后果最麻烦的一个术语坑。

本书最初用的名字是 **ACP**。但业界已经有 IBM / BeeAI 的 ACP（Agent Communication Protocol），而且**它在 2025-08 已经合并进 A2A**。也就是说：**"ACP" 这个名字既被别人占了商标，又在语义上已经指向另一个东西。**

继续用 ACP，会造成**商标与语义的双重冲突**——你想说的和读者以为的，是两个不同的协议。

所以本书统一改名：**SLCP（Silicon-Life Coordination Protocol）**，历史名 ACP 只保留在术语对照位置。

**第三个坑：以为"装了 A2A plugin"就是"A2A 能力在"。**

本机真相：`openclaw plugins list | grep -i a2a` → **`stock:a2a/index.js` 状态列 = `disabled`。**

**存在 ≠ 启用。** 这个坑的普遍性很高，因为它是"字符串存在性判断"的通病：你在 grep 里看到了 a2a，就以为能力在——**但那一行还有第三列，你没读。**

**第四个坑：跳过三层中间件，只写 Agent Card。**

一个只有 Agent Card 的 A2A 实现，是一台"能接通、接完就散"的交换机。

它会：健康检查缺失 → 挂掉的 agent 还在路由表里；守门员缺失 → 三个 agent 抢同一个活儿；事件日志缺失 → 出了事故查不到一根线索。

**这三件事，A2A 规范一件都不管。** 规范管的是"协议层怎么通话"，它明确不管"协同出事时不塌"。**后者是 SLCP 的活。**

### 9.0.3 本章与前/后章的引用关系

**向上（本章依赖谁）：**

- **第 6 章（协同军团）** 是本章的**语义源**。SLCP、反脆弱三层、响应让渡协议（Response Yield Protocol，原：让位协议）、任务交接协议 THP（Task Handoff Protocol，原：交接棒协议）、三省评审制、监督层（Supervisor Layer，原：监军）、治理审计账本（Governance Audit Ledger）——**这一整套的"战略定义"在第 6 章，本章是它在协议层的落地。**
- **第 8 章（MCP 绑定）** 是本章的**镜像**。MCP 是"我调工具"，A2A 是"外部调我"。同一个 client-server 关系的两个方向。
- **第 5 章（治理系统）** 是本章的**验收源**。TEV（三证据验证 Three-Evidence Verification）的证据 3（测试日志）在本章就是 L3 协同事件日志里的那一条条记录。
- **第 1 章（七大契约）** 是本章的**声明源**。`AGENTS.md` 定义编队，`HEARTBEAT.md` 定义唤醒节律，`IDENTITY.md` 定义"我是谁"——**Agent Card 上的能力声明，必须有契约里的对应物，否则就是空头支票。**

**向下（谁依赖本章）：**

- **第 10 章（Skills）**：一个 agent 对外暴露的 skill，最终要在 Agent Card 上被声明 → 而 skill 的**实现**在第 10 章。
- **第 11 章（Plugins）**：SLCP bridge 进不了主仓（PR #152777 至今 OPEN），**唯一的落地路径就是 plugin**——这是本章与第 11 章的硬连接。

**横向（四接口层的第三格）：**

MCP（工具）→ **A2A（agent）** → Skills（能力）→ Plugins（分发）。

### 9.0.4 一个反直觉的立论：A2A 解决"能通话"，SLCP 解决"通话出事时不塌"

这是本章最重要的一句话，也是本书对行业的一个明确定位。

**A2A v1.0 的贡献**：它把"agent 之间怎么通话"标准化了。

- **发现**：Agent Card（name / description / version / capabilities / skills / authentication schemes）；
- **调用**：JSON-RPC method surface；
- **状态**：task lifecycle（submitted → working → input-required → completed / failed / canceled）；
- **身份**：v1.0 引入 **Signed Agent Cards**（签名 Agent Card，密码学身份验证）。

**这是一份非常完整的"通话规范"。**

**但它明确不解决的事**（这不是缺陷，是定位）：

| 问题 | A2A 管吗 | 谁管 |
|---|---|---|
| 通话对方还活着吗 | ❌ | L1 健康检查（SLCP） |
| 多个 agent 抢一个活儿怎么办 | ❌ | L2 通道守门员（SLCP） |
| 出事之后谁能复盘 | ❌ | L3 协同事件日志（SLCP） |
| 谁该先答、谁该让位 | ❌ | 响应让渡协议（SLCP） |
| 交接之后谁担责 | ❌ | 任务交接协议 THP（SLCP） |
| 高危决策谁审 | ❌ | 三省评审制（SLCP） |

**定位公式**：

> **A2A 解决"能通话"，SLCP 解决"通话出事时不塌"。两者正交，可桥接。**

"正交"的意思是：**你可以在 A2A 上跑 SLCP，也可以不用 A2A 只在本机跑 SLCP。** 前者是"接入生态"，后者是"内部纪律"。**纪律不依赖协议，协议也不提供纪律。**

## 9.1 核心概念：十个词，看懂 A2A 绑定

### 9.1.1 A2A v1.0 协议：四个标准件

**① 一句话定义**

**A2A（Agent2Agent Protocol，Agent 间协议）** 是一套让不同厂商、不同框架的 agent 之间**发现对方、委派任务、协同工作**的开放标准。

**② 它解决什么问题**

解决"**跨组织的 agent 之间没有共同语言**"。

在 A2A 之前，你想让 A 公司的 agent 调 B 公司的 agent，只有三种做法：写死 API、共用一个框架、或者人工中转。三种都不可扩展。

A2A 的答案是把四件事标准化：**怎么被发现、怎么被调用、状态怎么流转、身份怎么证明。**

**③ 在 OpenClaw / SLCP 里的落点**

**A2A v1.0 的四个标准件：**

| # | 标准件 | 内容 | 本机状态 |
|---|---|---|---|
| 1 | **Agent Card** | discovery 协议：name / description / version / `supported_interfaces[]` / capabilities / authentication schemes / skills | ✅ `supported_interfaces[]` 为真名字段（破坏性变更） |
| 2 | **JSON-RPC method surface** | 调用面：`tasks/send`、`tasks/get`、`tasks/cancel`、`tasks/sendSubscribe`（流式订阅）等 | ⏳ 未实测 |
| 3 | **Task lifecycle** | 状态机：submitted → working → input-required → completed / failed / canceled | ⏳ 未实测 |
| 4 | **Signed Agent Card** | v1.0 引入：用密码学方式验证 agent 身份 | ⏳ 未实测 |

**OpenClaw 侧的落点（三条硬事实）：**

- **OpenClaw 主仓对 A2A 的 grep 命中 = 0**（对照：原生 MCP 命中 16 处）→ **A2A 不是 OpenClaw 原生能力**。
- `stock:a2a/index.js` **存在**，但状态列 = **disabled**（本机实测）。
- 因此本章的落地路径**必然**是"生态扩展 + plugin"，而不是"打开一个原生开关"。

**④ 与相邻概念的分界**

- **A2A ≠ MCP**：MCP 是 client-server（agent 调工具），A2A 是 agent-agent（agent 调 agent）。**两者正交，不是竞品。**
- **A2A ≠ agent 框架**：A2A 不定义 agent 内部怎么决策，只定义"对外怎么说话"。LangGraph 是框架，A2A 是协议——**一层套一层，不是二选一。**
- **A2A v1.0 ≠ A2A v0.3**：v0.3 → v1.0 是**破坏性变更**（method 名、Part 模型、Agent Card 接口、字段名）。最典型的一条：**Agent Card 不再有单个 `url` 字段，改成 `supported_interfaces[]` 数组**——一个 agent 可以声明多种传输，按偏好顺序排列，客户端取第一个它能说的，都不匹配就**失败关闭（fail closed）**。

**⑤ 一个具体场景**

一个真实的"协议看起来通了，业务还是散了"的场景。

你的 agent 通过 A2A 接到了一个外部任务。任务跑到一半，对方 agent 崩了。

- **A2A 视角**：对方没有回 `tasks/get` 的响应 → 状态停在 `working` → **协议层无异常**。
- **业务视角**：这个任务永远卡住了，**并且没有任何人知道**。

**A2A 规范里没有"对方死了怎么办"这一条。** 它不定义心跳、不定义超时后的降级、不定义替补。**这不是它的问题——是它没打算管。**

**这就是 SLCP 存在的理由。**

**⑥ 常见误解**

- ❌ "OpenClaw 原生支持 A2A"——**grep 0 命中。** 生态扩展，非主仓能力。
- ❌ "A2A 会取代 MCP"——两者正交。有文档把两个协议混成"agent 协议"，是常见误读。
- ❌ "A2A v2.0 已经发布了"——**截至 2026-09-28 无此版本。** 任何"v2.0 已发布"的说法都是传闻，❌ 不得引用。
- ❌ "Agent Card 里那个 `url` 字段我在别的教程见过，应该还有"——**v1.0 已改成 `supported_interfaces[]`。** 单值 `url` 是 v0.3 世代写法。本章 9.3.2 专门处理这个高频误植。

**⑦ 与 6 大框架的对位**

| 框架 | A2A 支持 |
|---|---|
| LangGraph | ❌ 无原生（可自建 Agent Card + JSON-RPC 网关模拟，成本自负） |
| AutoGen / AG2 | ⚠ 早期（Magentic-One 跨 agent 实验；微软系在 A2A 生态中） |
| CrewAI | ❌ 无 |
| Claude Agent SDK | ❌ 无（Anthropic 下注 MCP + Skills，**不下注 A2A**） |
| OpenAI Agents SDK | ⚠ 早期（Swarm 血统的 handoffs 与 A2A task 语义部分重叠；OpenAI 在 A2A 生态中） |
| LlamaIndex | ❌ 无 |
| **OpenClaw v5.0** | ✅ **SLCP 三层 + THP**（生态扩展，非原生；⏳ bridge demo 待实测） |

**⑧ 2026 前沿坐标 + 诚实标记**

- ✅ A2A 由 Google Cloud 2025-04 开源，2025-06 交由 Linux Foundation 托管，2025-08 IBM/BeeAI 的 ACP 合并入 A2A。
- ✅ **v1.0 冻结于 2026-03-12**，v1.0.1 于 2026-05；v1.0 新增多协议绑定与版本协商、多租户（multi-tenancy）、**Signed Agent Cards**。
- ✅ **2026-08-17，A2A 加入 AAIF（Agentic AI Foundation）**——与 MCP 同一个屋檐下。
- ✅ 生态：150+ 组织（Linux Foundation 2026-04-09 一周年公告口径，LF 自报）；生产部署案例涵盖移动平台、云 AI 基础设施、金融服务、供应链、企业 IT。
- ⏳ A2A TCK / SLCP bridge demo **本机未实测**。
- ⚠ 不得宣称"OpenClaw 原生支持 A2A"；❌ 不引用任何"A2A v2.0 已发布"类传闻。

### 9.1.2 SLCP（Silicon-Life Coordination Protocol，原：ACP）

**① 一句话定义**

**SLCP = OpenClaw 侧的协同协议**——在 A2A 的"能通话"之上，加一层"**通话出事时不塌**"的协同纪律。

**② 它解决什么问题**

解决"**多个 agent 在一起工作时，秩序从哪来**"。

A2A 给了通话标准，但通话之后是一支队伍在干活。**队伍需要的不只是语言，还有纪律**：谁先答、谁让位、交接怎么记、出事怎么查、高危决策谁审。

SLCP 就是这套纪律的名字。

**③ 在 OpenClaw / SLCP 里的落点**

**SLCP 的六个扩展（在 A2A 四个标准件之上）：**

| # | 扩展 | 作用 | 第 6 章对应概念 |
|---|---|---|---|
| 1 | **反脆弱三层**（Anti-Fragile Triptych） | L1 健康检查 / L2 通道守门员 / L3 协同事件日志 | 6.1.3 |
| 2 | **响应让渡协议**（Response Yield Protocol，原：让位协议） | 谁该先答、谁该让 | 6.1.5 |
| 3 | **任务交接协议**（THP，原：交接棒协议） | 交接 + 审计 + 让位仲裁三合一 | 6.1.6 |
| 4 | **三省评审制**（Three-Stage Review） | Proposal / Review / Final-Decision | 6.1.4 |
| 5 | **监督层**（Supervisor Layer，原：监军） | 独立第三方观察与纠偏 | 6.1.10 |
| 6 | **治理审计账本**（Governance Audit Ledger） | 协同事件留痕，供 TEV 取证 | 6.1.8 |

**命名来历（必须记住）**：本书最初用 **ACP**；但 IBM/BeeAI 的 ACP 已存在，且 **2025-08 已合并入 A2A**——**商标 + 语义双重冲突**，故统一改为 **SLCP**。**对外一律 SLCP，历史名 ACP 只在术语对照位置出现一次。**

**④ 与相邻概念的分界**

- **SLCP ≠ A2A 的替代品**：SLCP 是**协议层附加**，不是另一个协议栈。它在 A2A 之上，也可以独立于 A2A 在本机运行。
- **SLCP ≠ 一个库**：它是一套纪律 + 一组中间件 + 一份事件日志约定。`slcp-bridge.ts` 是它的**原型载体**，不是它的全部。
- **SLCP ≠ 主仓功能**：**PR #152777（SLCP bridge 进主仓）至今 OPEN**（2026-09-27 实拉）。所以 SLCP 的落地路径是**社区 plugin**——这是 9.2 的核心内容。

**⑤ 一个具体场景**

一次"没有 SLCP 会发生什么"的真实复盘。

**事故**：8/19 军团断线——通道在列表里，但无人应答。

- **A2A 视角**：agent 还在注册表里，Agent Card 还在，**协议层完全正常**。
- **真相**：那个 agent 的实例早就挂了，**但没有任何机制把它从路由表里摘掉**。
- **SLCP 的 L1 对策**：周期性健康检查 → 挂掉的实例被标记 → 不再被路由。

**结论**：**A2A 告诉你"它有一个地址"，SLCP 告诉你"它还在不在"。** 这两个判断的字面差别很小，工程后果差别极大。

**⑥ 常见误解**

- ❌ "ACP 就是 SLCP 的英文名"——**错，且是双重错误**：商标上 ACP 属于 IBM/BeeAI，语义上 ACP 2025-08 已并入 A2A。
- ❌ "既然 A2A 是标准，SLCP 是不是自造轮子"——不是。**A2A 管协议，SLCP 管秩序。** 标准协议不提供队伍纪律，这不是它的职责。
- ❌ "SLCP 是 OpenClaw 主仓的一部分"——**不是。** grep 0 命中 A2A；PR #152777 OPEN。
- ❌ "SLCP 只对 OpenClaw 有效"——**纪律是通用的**，只是本书的实现载体在 OpenClaw。

### 9.1.3 反脆弱三层（Anti-Fragile Triptych）：L1 / L2 / L3

**① 一句话定义**

反脆弱三层 = **协同系统的三道防线**：**L1 健康检查（协议层）→ L2 通道守门员（运行时层）→ L3 协同事件日志（治理层）**。

"反脆弱"（anti-fragile）这个词在这里有严格含义：**不是"不出事"，而是"出事之后系统比之前更强"**——因为它把事故变成了可查、可复盘、可改进的记录。

**② 它解决什么问题**

解决协同系统的三类失效：**死的还在、抢的不管、错的查不到。**

| 失效 | 现象 | 对应层 |
|---|---|---|
| 死的还在 | 挂掉的 agent 仍在路由表里被派活 | **L1** |
| 抢的不管 | 三个 agent 同时看到同一个任务，都想接 | **L2** |
| 错的查不到 | 定时任务静默失败 3 天无人发现 | **L3** |

**③ 在 OpenClaw / SLCP 里的落点**

**三层定位（必须按这个顺序理解）：**

| 层 | 名字 | 中文 | 职责 | 关键参数 |
|---|---|---|---|---|
| **L1** | Protocol Layer | 协议层 | 健康检查 + 故障转移（Failover） | `health_check_interval: 60000`；`failover_threshold: 3` |
| **L2** | Runtime Layer | 运行时层 | 通道守门员（Channel Gatekeeper）+ 断路器（Circuit Breaker） | `channel_timeout: 300000`；连续 5 次失败 → 开闸 2 分钟 |
| **L3** | Governance Layer | 治理层 | 协同事件日志（Coordination Event Log） | `self_heal: true`；事件落盘 |

**帧序（这个细节最容易写错）**：中间件的装载顺序是 **L3 → L2 → L1**。

```typescript
// 帧序：L3 → L2 → L1（先治理、再守门、最后健康）
server.use(triptych.eventLogMiddleware());     // L3
server.use(triptych.gatekeeperMiddleware());   // L2
server.use(triptych.fallbackMiddleware());     // L1
```

**为什么是这个顺序？** 因为请求进来时，**你要先有"记录一切的账本"（L3），再有"决定谁接"的守门员（L2），最后才是"判断谁活着"的健康检查（L1）**。顺序反了，事故现场就没法复现。

**L3 的事件类型（TEV 证据 3 的原始素材）：**

```
2026-09-20T03:12:00Z  yield.requested       agent-a
2026-09-20T03:12:05Z  yield.accepted        agent-c
2026-09-20T03:40:00Z  task.completed        agent-c
```

**这三行就是一次完整响应对账的物理痕迹**——请求让位、接受让位、任务完成。**任何对账宣称，都要能拿出这三行。**

**④ 与相邻概念的分界**

- **L1 ≠ L2**：L1 判断"谁还活着"，L2 判断"该谁接"。活着的人不一定该接（它可能已经满了）。
- **L2 ≠ L3**：L2 是**决策**（谁接），L3 是**记录**（谁接了、结果如何）。**决策不留记录 = 无法复盘。**
- **反脆弱 ≠ 高可用**：高可用追求"不出事"（冗余、容错）；反脆弱追求"出事之后更强"（留痕、复盘、改进）。**前者是工程指标，后者是组织能力。**
- **反脆弱三层 ≠ SLA**：SLA 是对外的承诺，三层是对内的纪律。**对外承诺之前，先有对内纪律。**

**⑤ 一个具体场景**

**事故一：agent-x 挂了，所有任务都往 agent-y 涌 → agent-y 也被压垮。**

- **根因**：缺少**断路器**。一个失败的通道被反复重试，把压力全部转嫁给唯一"看起来还活着"的节点。
- **对策（L2）**：断路器——**连续 5 次失败就开闸 2 分钟**，期间不再向该目标派活。

**事故二：高峰期队列满了，但任务不能丢。**

- **根因**：拒绝策略只有"拒绝"。
- **对策（L2）**：`reject_policy=degrade`——**不拒绝，而是降级执行**（只做 TEV 证据 1+2，跳过证据 3 的深度日志）。

⚠ **注意这里的诚实标注**：降级执行意味着这次任务的 TEV **是三证之二**——按第 5 章铁律，**它只能记作"部分验证（partial）"，不得写"已验证"。** 降级是工程妥协，不是验收放宽。

**事故三：飞书推送——定时任务静默失败 3 天无人发现。**

- **根因**：**无 L3 事件日志** → 失败无记录 → TEV 证据 3 缺失。
- **对策（L3）**：协同事件日志落盘，按 `taskId` 可提取完整证据链。

**⑥ 常见误解**

- ❌ "三层要按 L1 → L2 → L3 装"——**帧序是 L3 → L2 → L1。** 写错了，事故现场无法复现。
- ❌ "只看 L1 日志就能判断 agent 死活"——**不够。** 正确顺序：先查 automation（定时任务是不是还在跑），再判 agent。**一个没有 automation 的 agent，"健康"是没有意义的。**
- ❌ "所有 agent 用同一个配额就行"——**错。** 应按 agent 角色分档：起草类任务多、评审类任务重、监督类任务稀。
- ❌ "三层都装了就是反脆弱"——**装了不等于在跑。** 反脆弱要求 L3 的日志**真的被读过**（周审）、L2 的阈值**真的被调过**（按负载复盘）、L1 的结果**真的被用来摘除路由**。

**⑦ 与 6 大框架的对位**

| 框架 | L1 健康检查 | L2 守门员 | L3 事件日志 |
|---|---|---|---|
| LangGraph | ❌ | ❌ | ⚠ LangSmith tracing（可观测，非协同审计） |
| AutoGen / AG2 | ❌ | ⚠ `max_turns` 粗粒度截断 | ❌ |
| CrewAI | ❌ | ⚠ hierarchical manager | ❌ |
| Claude Agent SDK | ❌ | ⚠ Permission API（动作层，非通道层） | ❌ |
| OpenAI Agents SDK | ❌ | ⚠ guardrails | ⚠ Tracing（"发生了什么"，非"谁立了功"） |
| LlamaIndex | ❌ | ❌ | ❌ |
| **OpenClaw v5.0** | ✅ **L1 `failover_threshold`** | ✅ **L2 守门员 + 断路器 + 降级** | ✅ **L3 协同事件日志（TEV 证据 3 来源）** |

**一句话**：**六框架里没有一家做"协同事件日志"——这是 SLCP 最硬的一处差异化。**

**⑧ 2026 前沿坐标 + 诚实标记**

- ✅ 三层参数（60s / 3 / 300s / 5 次 → 2 分钟 / `self_heal: true`）为本书工程口径，见本章附录 10.4 完整配置。
- ✅ 帧序 L3 → L2 → L1 为本书口径（附录 10.4 验证命令第 1 条即检此项）。
- ⏳ `slcp-bridge.ts` 依赖（`@a2a-js/sdk`、`openclaw-plugin-silicon-life-training`）**本机未装、未跑**。
- ⚠ 不得宣称"三层已在生产跑通"。

### 9.1.4 任务交接协议 THP（Task Handoff Protocol，原：交接棒协议）

**① 一句话定义**

**THP = "交接 + 审计 + 让位仲裁"三合一的交接协议。**

**② 它解决什么问题**

解决"**谁把活儿交给了谁，以及交完之后谁担责**"。

先看业界最近的对应物：**OpenAI Agents SDK 的 `handoffs`（任务交接，一等公民对象）**。它解决的问题是"这个任务该转给谁"。

handoffs 很干净：一个 `handoff()` 函数，把控制权交给另一个 agent。

**但它只管"交"。** 它不管：

- 交之前，源 agent 有没有把上下文完整交付？（**交接完整性**）
- 交之后，目标 agent 履职了没有？（**履约追踪**）
- 如果目标 agent 也想要别人来接，谁来决定？（**二次让位**）
- 整条交接链在哪留痕？（**审计**）

**THP 就是补齐这四个"不管"。**

**③ 在 OpenClaw / SLCP 里的落点**

**THP 的四段式：**

| 段 | 内容 | 留痕 |
|---|---|---|
| 1 · 交付（Deliver） | 任务卡 + 上下文 + 验收标准（acceptance criteria） | 交接事件 |
| 2 · 受理（Accept） | 目标 agent 显式确认受理（**不允许静默接管**） | 受理事件 |
| 3 · 执行（Execute） | 按任务卡执行，产出 artifact | 进度 + 完成事件 |
| 4 · 回执（Receipt） | 交付 artifact + TEV 三证 + 结果自评 | 回执事件 |

**关键字段**：任务卡本体属于**语义层**，不放进协议对象里。

⚠ 这是一条容易犯的错：**不要往协议对象里塞 `acceptance_criteria`**。协议层（A2A Task）只管状态流转，语义层（任务卡）管验收标准。混在一起，协议对象就变成了业务对象——**两边的演化节奏一旦不同，就永远对不齐。**

**④ 与相邻概念的分界**

| 概念 | 管什么 | 在哪 |
|---|---|---|
| A2A `Task` | 协议层状态流转 | 协议对象 |
| THP | 交接 + 审计 + 让位仲裁 | SLCP 扩展 |
| OpenAI `handoffs` | 只是"交给谁" | 框架 API |
| 任务卡 | 语义层：目标 / 边界 / 验收标准 | 第 5 章 |
| TEV 三证 | 验收口径 | 第 5 章 |

**一句话区分**：**A2A `Task` 是"信封"，THP 是"寄送协议"，任务卡是"信的内容"。**

**⑤ 一个具体场景**

一次"没有 THP 的交接"会怎样。

两个 agent 在群里。agent-a 说"这个我搞不定，@agent-b 你来"。agent-b 没回话，但十分钟后默默开始做了。

- **看起来**：任务被接走了，好事。
- **实际**：**没有任何交接记录。** 事后复盘时你不知道：a 是真的交付了，还是甩锅了？b 是自愿接的，还是被点名不敢推？交接时上下文丢了没有？

**加了 THP 之后**，这次交接会产生三行记录：

```
handoff.delivered   agent-a → agent-b   taskId=t-042  ctx_digest=...
handoff.accepted    agent-b              taskId=t-042  eta=15m
handoff.receipted   agent-b → agent-a   taskId=t-042  artifact=... tev=3/3
```

**这三行的价值不在"更规范"，在于"下周同一类任务可以查历史"。**

**⑥ 常见误解**

- ❌ "handoffs 就是 THP"——**一半。** handoffs 是"交"，THP 是"交 + 审计 + 让位仲裁"。
- ❌ "交接要快，不用显式受理"——**显式受理是 THP 的核心。** 静默接管让"谁在负责"这件事永久模糊。
- ❌ "把 acceptance_criteria 写进 Task 对象里最方便"——**协议层与语义层混层。** 见 ③ 的警告。
- ❌ "交接记录太多，没人会看"——**不看是流程问题，不是记录问题。** 没有记录你就连"不看"这个事实都发现不了。

**⑦ 与 6 大框架的对位**

- **LangGraph**：supervisor subgraph + Send API 能表达"转交"，但**无审计原语**。
- **AutoGen / AG2**：GroupChat 里 agent 自然轮流说话，**"交接"是隐式的**。
- **CrewAI**：`Process` 决定顺序，hierarchical 的 manager 可以派活——**派活 ≠ 可审计的交接**。
- **Claude Agent SDK**：subagents + task spec（任务卡对应物），有"事前"，无"事后追踪"。
- **OpenAI Agents SDK**：`handoffs` 一等公民——**业界最干净的交接原语**，但止于"交"。
- **LlamaIndex**：Workflows 多步编排，无交接语义。
- **OpenClaw v5.0**：✅ THP（交 + 审计 + 让位仲裁）。

**⑧ 2026 前沿坐标 + 诚实标记**

- ✅ OpenAI `handoffs` 为官方公开能力（2025-03 Agents SDK 发布）。
- ✅ THP 为本书原创方法论（历史名：交接棒协议）。
- ⏳ THP 在 slcp-bridge 里的实现**未实测**。
- ⚠ 不得宣称"THP 已替代 handoffs"——两者是不同层。

### 9.1.5 Agent Card：一张卡片，决定你被谁发现

**① 一句话定义**

**Agent Card 是 A2A 的 discovery 协议**——一份描述"**我是谁、我能做什么、怎么找我、怎么给我授权**"的结构化声明。

**② 它解决什么问题**

解决"**跨组织的 agent 怎么互相发现**"。

没有 Agent Card 的时候，发现靠人工：看文档、问人、翻配置。Agent Card 把这个过程标准化成"**读一个 JSON**"。

**③ 在 OpenClaw / SLCP 里的落点**

**v1.0 的 Agent Card 结构（本章脚手架）：**

```json
{
  "name": "silicon-life-training-agent",
  "version": "2026.9.4",
  "license": "MIT",
  "supported_interfaces": ["a2a/v1", "slcp/v1"],
  "capabilities": {
    "streaming": true,
    "pushNotifications": false
  },
  "skills": [
    { "id": "drift_detection",           "name": "Drift Detection" },
    { "id": "proactive_boundary_check",  "name": "Proactive Boundary" },
    { "id": "three_stage_review",        "name": "Three-Stage Review" },
    { "id": "anti_fragile_triptych",     "name": "Anti-Fragile Triptych" },
    { "id": "self_initiated_goal",       "name": "Self-Initiated Goal" }
  ]
}
```

**四个必知字段规则：**

| 字段 | 规则 | 常见错误 |
|---|---|---|
| `supported_interfaces` | **必须是数组**，按偏好顺序排列；客户端取第一个它能说的，都不匹配则 **fail closed** | 写成单值 `"url"`（v1.0.0 旧写法） |
| `version` | 与底座一致 | 写 `"1.0"` 或与 `openclaw --version` 不一致 |
| `license` | 显式写 | 留空（与主仓 MIT 不一致） |
| `skills[].id` | **必须是 ASCII snake_case** | 写中文或带 namespace 的怪名（协议层不认） |

**诚实标注**：本机 A2A plugin 状态 = **disabled**，因此**这份 Card 从未被真实读取过** ⏳。它是脚手架，不是已上线服务。

**④ 与相邻概念的分界**

- **Agent Card ≠ 说明书**：说明书给人看，Agent Card 给**机器**读。字段名、类型、枚举值都要机器友好。
- **Agent Card ≠ 能力声明 = 已具备能力**：Card 上是"我声明我有 `drift_detection`"，**声明与实现的差距必须靠对账**（9.1.5 ⑥ 与 9.3.6）。
- **Agent Card ≠ 静态文档**：改实现要改 Card。**"实现改了 Card 没改"是最常见的静默不一致。**

**⑤ 一个具体场景**

**"我改了 skill 的名字，为什么外部调用一直失败？"**

因为 **Card 里声明的 skill `id` 与实现里的 `id` 不一致**。

这是**三条最小一致性检查**里的第一条：

```bash
# 1a) 能力一致性：Card 里声明的 skill id 与实现的 skill 实际一致
# 1b) 传输一致性：capabilities.streaming 与你 bridge 的真实行为一致
# 1c) 版本一致性：Card version 与底座一致（openclaw --version）
```

**正确做法：Card 由脚本从单一来源生成**（VERSION 文件 + skills 清单），**不要手编**。手编的 Card 一定会漂移。

**⑥ 常见误解**

- ❌ "Agent Card 里有个 `url` 字段"——**v1.0 已改成 `supported_interfaces[]` 数组。** 单值 `url` 是 v0.3 世代。
- ❌ "skills 的 id 用中文更清楚"——**协议层不认。** id 必须 ASCII snake_case；`name` 可以是中文。
- ❌ "Card 是文档，改不改无所谓"——**Card 是对外契约。** 改实现不改 Card = 对世界撒谎。
- ❌ "多声明几个 skill 显得能力强"——**声明的每一项都要能被调用。** 声明白能力无法交付，是把"发现"变成"失望"。

**⑦ 与 6 大框架的对位**

- **LangGraph / AutoGen / CrewAI / LlamaIndex**：无 Agent Card 等价物（各自有配置/注册概念，但**不是可被外部读到的发现协议**）。
- **Claude Agent SDK**：无（不下注 A2A）。
- **OpenAI Agents SDK**：无原生 Card（handoffs 是内部交接）。
- **Google ADK**：A2A 原生派代表（**不在本书 6 大框架名单内**，仅作脚注）。
- **OpenClaw v5.0**：✅ 复用 Agent Card 作为 SLCP 节点注册的对外呈现。

**⑧ 2026 前沿坐标 + 诚实标记**

- ✅ Agent Card 为 A2A discovery 协议标准件（`a2a-protocol.org` schema 口径）。
- ✅ **v1.0 起 Agent Card 不再有单值 `url`，改为 `supported_interfaces[]` 传输列表，按偏好顺序解析，全不匹配则 fail closed**（v1.0 迁移指南 + Builder's Guide 口径）。
- ✅ **v1.0 引入 Signed Agent Cards（密码学身份验证）**（官方公告口径）。
- ⏳ 本机未验证任何 Card 被真实读取。
- ⚠ 不得宣称"Card 已上线可被发现"。

### 9.1.6 响应让渡协议（Response Yield Protocol，原：让位协议）

**① 一句话定义**

**响应让渡协议 = 一套"谁该先答、谁该让"的仲裁规则。**

"让渡"（yield）这个词是刻意的：**它不是"沉默"，而是"主动把回答权交给更合适的人"。**

**② 它解决什么问题**

解决"**多个 agent 都在群里，谁回答**"这个每天都在发生的冲突。

三个典型的错法：

- **全都答**：三条 agent 各答一遍，用户看到三份不一致的答案。
- **都不答**：谁都以为别人会答，结果没人回。
- **抢着答**：最快的那只答，但它不一定是最懂的那只。

**响应让渡协议要的是第四种：按规则让。**

**③ 在 OpenClaw / SLCP 里的落点**

**让渡的四要素：**

| 要素 | 含义 | 落点 |
|---|---|---|
| 让渡请求 | agent 声明"我想答 / 我想让" | L3 事件 `yield.requested` |
| 让渡受理 | 被让的一方显式接住 | L3 事件 `yield.accepted` |
| 让渡理由 | 为什么让（能力 / 负载 / 授权） | 事件字段 |
| 兜底 | 让渡后无人接怎么办 | **fallback（L1）+ 守卫（L2）** |

**完整的一次让渡（L3 实测样例格式）：**

```
2026-09-20T03:12:00Z  yield.requested       agent-a
2026-09-20T03:12:05Z  yield.accepted        agent-c
2026-09-20T03:40:00Z  task.completed        agent-c
```

**④ 与相邻概念的分界**

- **让位 ≠ 沉默**：沉默是"不回答"，让位是"把回答权明确交给谁"。**让位必须留下 `yield.accepted`，否则等于沉默。**
- **让位 ≠ 轮询**：轮询是"按顺序轮到谁就是谁"，让位是"按适配度决定谁上"。
- **让位 ≠ handoff**：让位是"这件事我不答，你来"，交接是"这件事我做到一半，你接手"。**让位面向"响应权"，交接面向"任务责任"。**

**⑤ 一个具体场景**

**一次真实的"让位做成了沉默"的复盘。**

场景：群里被问了一个专业问题，三只 agent 都在线。三只都判断"这个我不最懂，让给更懂的"。

- **结果**：**三只都让了，没有一只答。**
- **根因**：让位没有兜底。**"我不答"这件事被执行了，"总得有人答"这件事没有机制保证。**

**对策（L1 兜底 + L2 守卫）：**

- L1 兜底：让渡后无人受理 → 超时 → **原让渡方兜回**（不允许任务凭空消失）；
- L2 守卫：给让渡设上限——**一个任务最多让 N 次**，超过就必须有人答。

**⑥ 常见误解**

- ❌ "让位就是安静地不说话"——**不。** 让位要留 `yield.accepted`。无受理的让位 = 任务黑洞。
- ❌ "让位越礼貌越好"——**过度的礼貌就是失职。** 让位需要上限与兜底。
- ❌ "让位规则是社交礼仪"——**它是负载均衡 + 能力路由的机制。** 让渡理由都应该可量化（能力 / 负载 / 授权）。
- ❌ "让位协议只在群里有用"——**私聊里同样存在**"我该不该接这个活儿"的判断。

**⑦ 与 6 大框架的对位**

- **OpenAI Agents SDK**：`handoffs` 是一等公民，但**不做"谁更可信就让谁先答"**——那是响应让渡协议的活。
- **AutoGen / AG2**：GroupChat Manager 做协调（选下一个发言人），**是让位的弱对应物**；但无仲裁规则、无审计。
- **LangGraph**：supervisor 可决定路由，**但"让位冲突"需自建**。
- **CrewAI**：hierarchical manager 派活，**无让渡语义**。
- **Claude Agent SDK / LlamaIndex**：无。
- **OpenClaw v5.0**：✅ Response Yield Protocol + L3 让渡事件链。

**⑧ 2026 前沿坐标 + 诚实标记**

- ✅ 让渡事件格式（`yield.requested` / `yield.accepted` / `task.completed`）为本书口径，样例时间戳为示意。
- ✅ 历史名"让位协议"仅保留在术语对照位置。
- ⏳ 让渡链路未在真实 bridge 上实测。
- ⚠ 不得宣称"让渡已自动化仲裁"——**仲裁规则是人定的，机制只是执行它。**

### 9.1.7 群聊、私聊与让位规则：`routing.requireMention` 的三态

**① 一句话定义**

**群聊/私聊的让位规则 = "什么条件下 agent 才允许开口"**。在 OpenClaw 里，这个开关的名字是 **`routing.requireMention`**。

**② 它解决什么问题**

解决"**agent 在不该说话的时候说话**"。

这是多 agent 系统里最容易被低估的一类成本：**不是错误回答的成本，是"占位"的成本。**

一个 5 人的群里，如果 5 只 agent 都"看到问题就答"，那么：

- 群里 80% 的消息是重复的；
- 真正需要人看的那一条被淹没了；
- 用户开始 **mute 群** —— 于是**所有 agent 的通知都失效了**。

**结论**：**过度主动会把主动性本身杀死。**

**③ 在 OpenClaw / SLCP 里的落点**

**`routing.requireMention` 的三态：**

| 态 | 行为 | 适用场景 |
|---|---|---|
| `true` | **必须被 @ 提及才回应** | 群聊（默认纪律） |
| `false` | 看到符合条件就回应 | 私聊 / 一对一通道 |
| 分通道配置 | 不同通道不同策略 | 生产常态 |

**私聊 vs 群聊的分界原则（这是本章的一条工程纪律）：**

- **私聊 = 一对一会话**：对方就是在跟你说话，**不需提及也应当回应**；
- **群聊 = 多主体会话**：默认**必须被提及**，因为群里有别人的注意力。

⚠ **诚实标注**：`routing.requireMention` 是 OpenClaw 的**配置字段名**（真名）。但它的**具体取值与作用域取决于你的部署**——本机未逐条实测各通道的实际行为，因此本章只给"三态"的心智模型与纪律原则，**不承诺任何具体通道的默认值**。

**④ 与相邻概念的分界**

- **`requireMention` ≠ 让位协议**：`requireMention` 决定"**能不能开口**"（准入），让位协议决定"**开口权给谁**"（分配）。**先有准入，再谈分配。**
- **沉默 ≠ 让位**：见 9.1.6。`requireMention=true` 下的沉默是**纪律**；让位协议下的沉默是**失职**。
- **提及 ≠ 授权**：被 @ 只是"轮到你说"，不代表"这件事你有权做"。**授权在 `TOOLS.md`（第 8 章）与主动性边界三档制（第 4 章）。**

**⑤ 一个具体场景**

**"我的 agent 好厉害，什么问题都答" → 两周后 "我把这个机器人静音了"。**

这是一个标准的过度主动曲线：

| 阶段 | 时间 | 用户感受 |
|---|---|---|
| 1 | 第 1 天 | 哇，好主动 |
| 2 | 第 3 天 | 有点多，但还行 |
| 3 | 第 7 天 | 每次都要翻半天才找到人说的话 |
| 4 | 第 14 天 | **静音** |
| 5 | 第 30 天 | **这个 agent 没用了** |

**第 5 阶段是致命的**：静音之后，agent 再重要的提案也到达不了人。**过度主动的终点，是主动性被彻底关闭。**

**对策**：**默认 `requireMention=true`，把"主动开口"变成一种需要被授予的能力，而不是默认行为。** 这与第 7 章"提案型"的闸门（Human Gate）是同一个思想的两处落地。

**⑥ 常见误解**

- ❌ "主动就是好"——**主动的前提是"被期待"。** 在错误的通道里主动，等于制造噪音。
- ❌ "私聊也要 requireMention 才守纪律"——**过严。** 私聊里对方就是在跟你说话，要求提及是荒谬的。
- ❌ "把三态当配置细节"——**三态是组织设计。** 它决定了 agent 在整个通信拓扑里的位置。
- ❌ "静音是用户的问题"——**静音是系统的失败信号。** 出现静音，说明你的开口策略错了。

**⑦ 与 6 大框架的对位**

| 框架 | 开口准入机制 |
|---|---|
| LangGraph | ❌ 无（图执行不涉及"该不该开口"） |
| AutoGen / AG2 | ⚠ GroupChat 的发言选择（`speaker_selection_method`）是准入的弱对应物 |
| CrewAI | ❌ 无 |
| Claude Agent SDK | ❌ 无 |
| OpenAI Agents SDK | ❌ 无（handoffs 是转移，不是准入） |
| LlamaIndex | ❌ 无 |
| **OpenClaw v5.0** | ✅ **`routing.requireMention` + 分通道策略** |

**⑧ 2026 前沿坐标 + 诚实标记**

- ✅ `routing.requireMention` 为 OpenClaw 真名字段（第 6 章 6.1.7 同口径）。
- ⏳ 各通道默认值与作用域**未逐条实测**。
- ⚠ 不得宣称"OpenClaw 默认全通道 requireMention"。

### 9.1.8 抢活与不抢活：守门员、断路器与"该退就退"

**① 一句话定义**

**抢活与不抢活 = 协同系统里"接单"的两种失败模式，以及防止它们的两个机制。**

- **抢活**（over-grab）＝ 多个 agent 同时想接同一个任务；
- **不抢活**（under-grab）＝ 谁都不接，任务悬空。

**② 它解决什么问题**

解决"**任务分配的两端失效**"。

**抢活的具体形态**：3 个 agent 同时看到任务卡 `t-042`，都想接。结果：

- 三个都开始做 → **三倍算力浪费**；
- 三个产出不一致 → **用户不知道该信哪个**；
- 三个都留了 TEV → **账本里三条互相矛盾的"已完成"**。

**不抢活的具体形态**：见 9.1.6 的"三只都让了"。

**③ 在 OpenClaw / SLCP 里的落点**

**两个机制，各治一端：**

| 机制 | 层 | 治什么 | 关键参数 |
|---|---|---|---|
| **通道守门员**（Channel Gatekeeper） | L2 | **抢活** | 按 `priority` + `inFlight` 余量决定谁接 |
| **断路器**（Circuit Breaker） | L2 | **抢活的次生灾害**（反复重试压垮单一节点） | 连续 5 次失败 → 开闸 2 分钟 |
| **L1 兜底** | L1 | **不抢活** | 超时 → 原让渡方兜回 |
| **降级执行** | L2 | **队列满但不丢任务** | `reject_policy=degrade` |

**守门员的决策字段（本机口径）：**

| 字段 | 含义 |
|---|---|
| `priority` | 任务优先级 |
| `inFlight` | 该 agent 当前在飞的任务数 |
| `quota` | 该 agent 的配额（**应按角色分档，不是全体一刀切**） |
| `capability` | 是否具备该 skill |

**④ 与相邻概念的分界**

- **守门员 ≠ 调度器**：调度器决定"什么时候跑"，守门员决定"**谁有资格接**"。
- **断路器 ≠ 限流**：限流是"每秒最多 N 次"，断路器是"**连续失败就暂时隔离**"。
- **降级 ≠ 放弃**：降级是"降低验收深度继续做"，放弃是"不做"。**降级必须标注 TEV 为部分验证（partial）。**
- **抢活 ≠ 积极性**：抢活是**秩序缺失**的症状，不是 agent 有干劲的证据。

**⑤ 一个具体场景**

**"agent-x 挂了，所有任务都涌向 agent-y，然后 agent-y 也挂了。"**

完整因果链：

1. agent-x 挂掉（**L1 未摘除**：没有健康检查，死实例还在路由表里）；
2. 派给 agent-x 的任务失败；
3. 失败任务被重试 → 重试目标回退到 agent-y；
4. agent-y 因为承担双份负载开始变慢；
5. **变得慢 → 更多超时 → 更多重试 → 更慢**（正反馈）；
6. agent-y 也挂了。

**这六步里，第 3 步本该被断路器拦住（连续 5 次失败 → 开闸 2 分钟），第 1 步本该被 L1 拦住。**

**两个机制都缺，就会看到一次"雪崩"。**

**⑥ 常见误解**

- ❌ "抢活说明 agent 主动性强"——**抢活说明没有守门员。** 强不强看产出，不看争抢。
- ❌ "所有 agent 同一配额最公平"——**公平 ≠ 合理。** 起草类、评审类、监督类的负载特征完全不同，配额必须按角色分档。
- ❌ "断路器设成零容忍最安全"——**零容忍 = 一次抖动就隔离 = 频繁误杀。** 阈值要留容错空间（本机口径：连续 5 次）。
- ❌ "降级执行 = 偷工减料"——**降级是显式妥协**：它必须留痕（`reject_policy=degrade`），且必须把 TEV 标成 partial。**不标 = 造假。**

**⑦ 与 6 大框架的对位**

| 框架 | 抢活治理 | 断路器 | 降级 |
|---|---|---|---|
| LangGraph | ⚠ 需自建（supervisor 可做粗粒度） | ❌ | ❌ |
| AutoGen / AG2 | ⚠ `max_turns` 截断（粗粒度） | ❌ | ❌ |
| CrewAI | ⚠ hierarchical manager 派活 | ❌ | ❌ |
| Claude Agent SDK | ❌ | ❌ | ❌ |
| OpenAI Agents SDK | ⚠ guardrails 是拦截器，非任务仲裁 | ❌ | ❌ |
| LlamaIndex | ❌ | ❌ | ❌ |
| **OpenClaw v5.0** | ✅ **L2 守门员（priority + inFlight）** | ✅ **断路器（5 次 → 2 分钟）** | ✅ **`reject_policy=degrade` + partial 标注** |

**⑧ 2026 前沿坐标 + 诚实标记**

- ✅ 守门员/断路器/降级的参数为本书工程口径（见附录 10.4 完整配置）。
- ✅ 事故复盘（8/19 断线、agent-x/agent-y 雪崩、9/21 飞书静默失败）为本书案例库记录。
- ⏳ 未在真实生产 bridge 上复现。
- ⚠ 不得宣称"雪崩已被彻底杜绝"——**机制降低概率，不消灭可能。**

### 9.1.9 军团路由与三方评审：把"谁来做"变成"谁审"

**① 一句话定义**

**军团路由** = 把任务送到正确的 agent 的机制；**三方评审（三省评审制，Three-Stage Review）** = 高危决策的三段式把关（Proposal / Review / Final-Decision）。

**② 它解决什么问题**

解决两个方向的问题，它们看起来无关，实际上是同一件事的两面：

- **路由**解决"**送对人**"：任务 → agent。
- **评审**解决"**送对人也不放心**"：agent → 决策。

**为什么说是一件事的两面？** 因为**路由的错误无法靠执行弥补**。你把一个高危决策送给了一只能力不足的 agent，它做得再认真也是错的。所以路由之后必须有一道评审——**评审是路由的兜底，也是路由的前提**（知道要评审，才知道该送给谁）。

**③ 在 OpenClaw / SLCP 里的落点**

**军团路由的三个维度：**

| 维度 | 内容 | 落点 |
|---|---|---|
| 能力路由 | 谁会做这件事 | `skills[]`（Agent Card）+ skill 实现（第 10 章） |
| 负载路由 | 谁现在有空 | `inFlight` + `quota`（L2 守门员字段） |
| 提及路由 | 谁被点到了 | `routing.requireMention` + 群内 @ |

**三方评审（三省评审制）的三段：**

| 段 | 角色 | 产出 | 硬规则 |
|---|---|---|---|
| 1 · Proposal | 提案方 | 提案 + 依据 | 提案方**不得**自己做终审 |
| 2 · Review | 评审方 | 评审意见（赞成 / 反对 / 补强） | 评审方**独立**于提案方 |
| 3 · Final-Decision | 决策方 | 终审结论 + 理由 | 高危决策**必须**有这一段 |

**⭐ 一条铁律**：**让 proposer 自己做 finalizer**，等于没有评审。这是本书反复强调的一条（第 6 章、第 7 章各出现一次），**在协议层同样成立**。

**监督层（Supervisor Layer，原：监军）的位置**：它**不参与三段中的任何一段**，而是在三段之外做**独立观察与纠偏**。它管的是"这三段有没有按规矩走"，不是"这个决策对不对"。

**④ 与相邻概念的分界**

| 概念 | 管 | 不管 |
|---|---|---|
| 军团路由 | 送对人 | 送对人之后对不对 |
| 三省评审 | 决策质量 | 决策的执行与验收 |
| 监督层 | 流程合规 | 具体业务判断 |
| TEV | 事后验收 | 事中把关 |
| 主动性边界三档制 | 多大授权 | 谁来做 |

**一句话**：**路由管"送达"，评审管"把关"，监督管"合规"，TEV 管"验收"。四件事，四个机制，缺一个都不行。**

**⑤ 一个具体场景**

**"这次决策是谁拍的板？"—— 一个在复盘会上问不出来答案的团队。**

完整链条应该长这样：

```
提案：agent-a 提出「把 X 服务的超时从 30s 调到 60s」，附理由与数据
评审：agent-b 给出「反对：60s 会让错误暴露时间翻倍，建议先做 45s 的 A/B」
终审：agent-c（独立于 a/b）给出结论 + 理由，采纳 45s 方案
留痕：三段全部进 L3 协同事件日志，taskId 可追溯
验收：TEV 三证（新配置产物 / 前后 diff / 变更后 24h 观测日志）
```

**缺任何一段，复盘会上的问题就答不出来。**

- 缺提案的依据 → "当初为什么改" 答不出来；
- 缺独立评审 → "有没有人反对过" 答不出来；
- 缺终审理由 → "谁拍的板、为什么" 答不出来；
- 缺留痕 → 整条链都答不出来。

**⑥ 常见误解**

- ❌ "小决策不用走评审"——**分档，不是全有全无。** 三档制的意思就是"低危直做、中危提案、高危三省"（第 4 章）。
- ❌ "评审方可以是提案方的好友 agent"——**独立性是评审的全部价值。** 不独立 = 橡皮图章。
- ❌ "监督层就是第三个评审"——**不是。** 监督层管流程合规，不参与决策内容。
- ❌ "路由是技术问题，评审是治理问题"——**两者是同一根链条上的两段。** 详见 ② 的论证。

**⑦ 与 6 大框架的对位**

| 框架 | 路由 | 三段式评审 | 监督层 |
|---|---|---|---|
| LangGraph | ✅ supervisor + Send API（强） | ⚠ 需自建 | ❌ |
| AutoGen / AG2 | ✅ GroupChat Manager | ⚠ debate 非三段式 | ❌ |
| CrewAI | ✅ hierarchical manager | ⚠ manager 评审（便利，非证据验收） | ❌ |
| Claude Agent SDK | ⚠ subagents（弱） | ❌ | ❌ |
| OpenAI Agents SDK | ✅ handoffs（强） | ⚠ guardrails 拦截，非评审 | ❌ |
| LlamaIndex | ⚠ Workflows | ❌ | ❌ |
| **OpenClaw v5.0** | ✅ **三维路由（能力/负载/提及）** | ✅ **三省评审制** | ✅ **监督层（独立观察）** |

**⑧ 2026 前沿坐标 + 诚实标记**

- ✅ 三省评审制为本书原创（历史名：三省制），术语表 #13。
- ✅ 监督层历史名"监军"只在术语对照位置出现。
- ⏳ 三段式在协议层的强制程度**未实测**（协议层可留痕，但"必须走三段"是流程约定）。
- ⚠ 不得宣称"评审已自动化"——**评审是人 + agent 的制度，不是功能开关。**

### 9.1.10 治理审计账本（Governance Audit Ledger）与 TEV 证据 3

**① 一句话定义**

**治理审计账本 = 协同系统的事件留痕层**——它记录"谁在什么时候对什么做了什么、结果如何"，是 TEV（三证据验证）中**证据 3（测试日志）**的来源。

**② 它解决什么问题**

解决"**口说无凭**"。

一切验收结论，最终都要落到证据上。TEV 的三证是：

| 证据 | 内容 | 本章对应物 |
|---|---|---|
| 证据 1 · 新产物（artifact） | 这次交付产生了什么 | bridge / 中间件 / Card |
| 证据 2 · 前后 Diff | 变化前后的对照 | 配置前后 / 路由前后 |
| **证据 3 · 测试日志** | **运行留下的可查记录** | **L3 协同事件日志** |

**没有证据 3，前两个证据都是"截图片段"**——你看到结果，但看不到过程。

**③ 在 OpenClaw / SLCP 里的落点**

**L3 事件日志的取证方式（按 taskId 提取完整证据链）：**

```bash
# 从 L3 事件日志里按 taskId 提取完整证据链
grep -h "t-042" ~/.openclaw/workspace/logs/coordination-events.log | sort
# 期望输出：
# 2026-09-20T03:12:00Z  yield.requested       agent-a
# 2026-09-20T03:12:05Z  yield.accepted        agent-c
# 2026-09-20T03:40:00Z  task.completed        agent-c
```

**事件类型（本章口径）：**

| 事件 | 触发 | 属于 |
|---|---|---|
| `yield.requested` | 发起让渡 | 响应让渡协议 |
| `yield.accepted` | 受理让渡 | 响应让渡协议 |
| `handoff.delivered` / `.accepted` / `.receipted` | 交接三段 | THP |
| `task.completed` / `task.failed` | 任务终态 | 执行 |
| `fallback.failover` | L1 触发故障转移 | 反脆弱三层 |
| `gatekeeper.rejected` | L2 守门员拒接 | 反脆弱三层 |

**④ 与相邻概念的分界**

- **账本 ≠ 日志**：普通日志是"给程序员 debug 的"；账本是"**给验收用的**"。前者可以随时关，后者**必须常开**。
- **治理审计账本 ≠ 功绩账本**：治理审计账本记录"**发生了什么**"；功绩账本（Merit Ledger）记录"**谁立了功、谁该被信任**"（第 5 章）。前者是原料，后者是结论。
- **留痕 ≠ 复盘**：留痕是机制，复盘是行为。**留了不看，等于没留。**

**⑤ 一个具体场景**

**"飞书推送，定时任务静默失败 3 天无人发现。"**

这个案例的根因链条，是本章最有教育意义的一条：

| 步骤 | 事实 | 应有机制 |
|---|---|---|
| 1 | 定时任务没跑（或跑了失败） | automation + heartbeat |
| 2 | 失败没有告警 | L1 健康检查 |
| 3 | 失败没有记录 | **L3 事件日志** |
| 4 | 3 天无人发现 | **周审（从 L3 日志统计）** |
| 5 | 发现时 TEV 证据 3 缺失 | 无法复盘 |

**注意第 3 步**：如果 L3 一直在记，那么第 4 步靠"每周从 L3 日志统计"就能兜住：

```bash
# 周审命令
grep -c "task.failed" ~/.openclaw/workspace/logs/coordination-events.log
# 期望：{task.completed: N, task.failed: M, fallback.failover: K, ...}
```

**一个数字的周审，就能兜住 3 天的静默失败。** 这就是 L3 的全部价值——**它不让你更快，它让你不"永远不知道"。**

**⑥ 常见误解**

- ❌ "日志是 debug 用的，生产可以关"——**账本必须常开。** 关掉它的那一刻，你的 TEV 就永久缺一条证据。
- ❌ "有账本就能复盘"——**账本只是原料。** 复盘需要"周审"这个行为。
- ❌ "账本越详细越好"——**有成本。** 降级执行（`reject_policy=degrade`）时跳过深度日志，就是显式的成本妥协——**但要标注 TEV 为 partial。**
- ❌ "治理审计账本是 OpenClaw 原生功能"——⚠ **账本是 SLCP 的约定**，其载体在 L3 中间件与事件日志文件，**不是主仓原生字段**。

**⑦ 与 6 大框架的对位**

| 框架 | 审计账本 |
|---|---|
| LangGraph | ⚠ LangSmith tracing（轨迹是原材料，非验收口径） |
| AutoGen / AG2 | ❌ |
| CrewAI | ❌ |
| Claude Agent SDK | ❌（有"事前"授权，无"事后三证"） |
| OpenAI Agents SDK | ⚠ Tracing 对应"治理审计账本"最接近，但**记录"发生了什么"，不记录"谁该被信任"** |
| LlamaIndex | ❌ |
| **OpenClaw v5.0** | ✅ **治理审计账本（事件留痕）+ 功绩账本（激励层）双层** |

**⑧ 2026 前沿坐标 + 诚实标记**

- ✅ TEV 三证口径为第 5 章铁律，本章只做协议层落地。
- ✅ 事件类型与样例格式为本书口径。
- ⏳ 事件日志路径 `~/.openclaw/workspace/logs/coordination-events.log` 为**本书口径路径**，本机未生成（无 bridge 运行）。
- ⚠ 不得宣称"账本已接入生产告警"。

### 9.2.4 第 3 步：写 SLCP bridge 原型（三行 `use` 的完整上下文）

```typescript
// slcp-bridge.ts
import { A2AServer } from "@a2a-js/sdk/server";
import { AntiFragileTriptych } from "openclaw-plugin-silicon-life-training";

const server = new A2AServer({
  card: {
    name: "silicon-life-training-agent",
    version: "2026.9.4",
    supported_interfaces: ["a2a/v1", "slcp/v1"],
    skills: [
      { id: "drift_detection" },
      { id: "proactive_boundary_check" },
      { id: "three_stage_review" },
      { id: "anti_fragile_triptych" },
      { id: "self_initiated_goal" }
    ]
  }
});

// 反脆弱三层拦截器
const triptych = new AntiFragileTriptych({
  health_check_interval: 60_000,   // L1
  failover_threshold: 3,           // L1
  channel_timeout: 300_000,        // L2
  self_heal: true                  // L3
});

// 帧序：L3 → L2 → L1（顺序错了，事故现场无法复现）
server.use(triptych.eventLogMiddleware());     // L3
server.use(triptych.gatekeeperMiddleware());   // L2
server.use(triptych.fallbackMiddleware());     // L1

await server.listen(41241);
```

**三条纪律：**

1. **帧序必须是 L3 → L2 → L1**（附录 10.4 验证命令第 1 条就是检这个）；
2. **`supported_interfaces` 必须含 `slcp/v1`**——这是 SLCP 自定义接口的声明位置；
3. **端口 41241 是本书约定**——起之前先预检（见 9.2.5）。

**⚠ 诚实标注**：`@a2a-js/sdk/server` 与 `openclaw-plugin-silicon-life-training` 两个依赖**本机未安装、此原型未运行** ⏳。它是原型草图，不是可运行产物。

### 9.2.5 第 4 步：端口预检（30 秒省你半天）

```bash
lsof -nP -iTCP:41241 -sTCP:LISTEN
# 无输出 = ✓ 端口空闲
# 有输出 = 先确认是不是自己的残留进程，再决定杀不杀
```

**这一步的地位被严重低估。** 一个被占的端口会表现为"bridge 起不来"，而"起不来"又会表现为"依赖没装""代码有问题""配置错了"——**你会往三个错误的方向查，实际只是端口撞车。**

### 9.2.6 第 5 步：跑 TCK（唯一的"被社区认可"判据）

**TCK = Test Compatibility Kit**，A2A 官方兼容性测试集。**跑通 TCK = 本实现被 A2A 社区认可。**

```bash
# 1) clone
git clone https://github.com/a2aproject/a2a-tck
# 2) 启动 SLCP bridge server（见 9.2.4）
# 3) 跑
a2a-tck run --target http://localhost:41241
# 4) 输出 compat_report.json
# 5) 向 A2A 社区提交报告
```

**⚠ 顺序纪律：最后才跑 TCK。** 常见的顺序颠倒：

- ❌ 先跑 TCK → 看到一堆失败 → 以为协议实现有问题；
- ✅ 先确认 bridge 能起（依赖装、端口空）→ 再确认三层中间件都在 → **最后才跑 TCK**。

**为什么？** 因为 TCK 失败的原因里，**大多数不是协议实现问题，而是环境问题**。跳过前置就直奔 TCK，等于在错误的地方找答案。

这是本章最有价值的一段工程经验：**当"进主仓"这条路走不通时怎么办。**

**PR 现状（2026-09-27 实拉）：**

|---|---|

## 9.3 常见误区：十种"看起来能协同了，其实一接就散"

> 写法统一：**现象 → 为什么错 → 怎么改 → 自查命令。**
> 前四条是"技术性错误"（会直接坏），后六条是"认知性错误"（不坏，但让你在错误方向努力很久）。

### 9.3.1 误区一：把 A2A 当 OpenClaw 原生能力

**现象**

文档里写"OpenClaw 原生支持 A2A，执行 `openclaw a2a list` 查看"。

**为什么错**

**因为那条命令不存在。**

本机实测：**OpenClaw 主仓对 A2A 的 grep 命中 = 0**（对照：原生 MCP 命中 16 处）。`openclaw plugins --help` 的子命令族里**没有任何 a2a 原生命令**。

A2A 在 OpenClaw 里的真实身份是：**生态扩展**——`stock:a2a/index.js` 存在，但**状态 = disabled**。

**怎么改**

```bash
# 1) 原生命令族里没有 a2a
openclaw plugins --help 2>&1 | grep -c -i a2a
# 期望：0

# 2) 本机 A2A plugin 的真实状态（读完整三列）
openclaw plugins list 2>&1 | grep -i a2a
# 期望：A2A  a2a  disabled

# 3) 版本核对
openclaw --version
# 期望：OpenClaw 2026.9.4 (3a9d69d)
```

**自查**

```bash
grep -c "openclaw a2a" <YOUR_DOC>.md
# 期望：0
```

### 9.3.2 误区二：用 `capabilities.url` 单值声明接口（A2A v1.0.0 旧写法）

**现象**

Agent Card 里写：

```json
{ "url": "http://localhost:41241", "capabilities": { "streaming": true } }
```

**为什么错**

**因为 v1.0 已改成 `supported_interfaces[]` 数组。**

这条变更是**破坏性变更**：v0.3 → v1.0 迁移里，Agent Card 不再有单个 `url` 字段，改成一个**传输列表，按偏好顺序排列**。客户端取**第一个它能说的**，忽略其余的；**都不匹配则 fail closed（失败关闭）**。

**这个设计的工程含义很深**：它把"一个 agent 只有一个地址"变成"**一个 agent 可以按偏好声明多种传输**"。这是 A2A 从"演示协议"走向"企业协议"的关键标志之一。

**怎么改**

```json
{
  "supported_interfaces": ["a2a/v1", "slcp/v1"]
}
```

**自查**

```bash
# 1) 真名字段在，且是数组

# 3) license 显式写（与 OpenClaw 主仓 MIT 一致）
```

### 9.3.3 误区三：把 ACP 当 SLCP 的英文名（商标冲突 + 术语误植）

**现象**

文档里写"ACP 协议"、"ACP bridge"。

**为什么错**

**双重错误：**

1. **商标冲突**：IBM / BeeAI 已经有一个叫 ACP（Agent Communication Protocol）的东西，名字被占了；
2. **语义冲突**：**2025-08，IBM/BeeAI 的 ACP 已合并入 A2A。** 也就是说，"ACP" 这个词在 2025 年 8 月之后，语义上指向的是**A2A 的一部分**。

所以读者看到"ACP"，会以为你在说 A2A 的某个子协议——**而你想说的是完全另一套东西。**

**怎么改**

统一改 **SLCP（Silicon-Life Coordination Protocol）**；历史名 ACP **只在术语对照位置出现一次**。

**自查**

```bash

```

### 9.3.4 误区四：跳过三层中间件（只写 Card，不写 fallback / gatekeeper / event-log）

**现象**

`slcp-bridge.ts` 里只有 `new A2AServer({ card })`，**没有三行 `server.use(...)`**。

**为什么错**

因为**只有 Card 的 bridge 是一台"接完就散"的交换机**：

- 没有 L1 → 挂掉的 agent 还在路由表里被派活；
- 没有 L2 → 三个 agent 抢同一个活儿；
- 没有 L3 → 出了事故查不到一根线索（**TEV 证据 3 永久缺失**）。

**A2A 规范不管这三件事**——这不是它的缺陷，是它的定位。**跳过三层，等于把"能通话"当成了"能协同"。**

**怎么改**

```typescript
// 帧序：L3 → L2 → L1
server.use(triptych.eventLogMiddleware());     // L3
server.use(triptych.gatekeeperMiddleware());   // L2
server.use(triptych.fallbackMiddleware());     // L1
```

**自查**

```bash
# 1) 三层中间件都在（帧序：eventLog → gatekeeper → fallback）
grep -cE "eventLogMiddleware|gatekeeperMiddleware|fallbackMiddleware" slcp-bridge.ts
# 期望：3 行

# 2) 反例：listen 之前没有 use
# 3) 事件日志落盘路径可查
```

### 9.3.5 误区五：把 A2A `Task` 当训练学"任务卡"（协议层 vs 语义层混淆）

**现象**

在 A2A Task 对象里塞 `acceptance_criteria`、`soul_ref`、`training_round` 这些字段。

**为什么错**

**因为这是两个不同层的对象。**

| 层 | 对象 | 管什么 |
|---|---|---|
| 协议层 | A2A `Task` | 状态流转：submitted → working → input-required → completed / failed / canceled |
| 语义层 | 任务卡 | 目标 / 边界 / 验收标准 / 归属 |

**混层会带来一个不可逆的后果**：协议对象的演化节奏由 **A2A 规范**决定，语义对象的演化节奏由**你的训练学**决定。把它们绑在一起，**你每次改训练学都要考虑协议兼容性——而那本来不关你的事。**

**怎么改**

保持四行映射（Task → 任务卡；Artifact → 新产物；Message → 协同事件日志；Push Notification → 心跳触发），**协议对象只放协议字段。**

**自查**

```bash
# 1) 映射表四行齐（Task / Artifact / Message / Push Notification）
grep -cE "^\| (Task|Artifact|Message|Push Notification) " <YOUR_MAP>.md
# 期望：4 行

# 2) 反例：协议对象里出现 acceptance_criteria
grep -c "acceptance_criteria" <PROTOCOL_OBJECT>
# 期望：0
```

### 9.3.6 误区六：Agent Card 缺 `license` / `version` 与真身不一致

**现象**

Card 里 `version: "1.0"`，而 `openclaw --version` 是 `2026.9.4`；或者 `license` 字段干脆没有。

**为什么错**

**因为 Card 是对外契约，不是内部备注。**

- `version` 不一致 → 外部调用方无法判断"这个服务是不是我看到的那一版"；
- `license` 缺失 → 对方不知道能不能在你的实现上做商业集成（**这是法律问题，不是格式问题**）。

**怎么改**

三条最小一致性检查：

```bash
# 1) 版本与底座一致
openclaw --version && grep '"version"' <CARD>
# 期望：两处都能对上 2026.9.4

# 2) license 非空
grep -c '"license": "MIT"' <CARD>
# 期望：1

# 3) 两个 interface 都在
python3 -c "import json;print(json.load(open('<CARD>'))['supported_interfaces'])"
# 期望：['a2a/v1', 'slcp/v1']
```

**最长效的做法**：**Card 由脚本从单一来源生成**（VERSION 文件 + skills 清单），**不要手编**。手编的 Card 一定会漂移。

### 9.3.7 误区七：把 `slcp-bridge.ts` 当成品（依赖未装、demo 未跑）

**现象**

文档里说"SLCP bridge 已实现"，然后贴一段 TS 代码。

**为什么错**

**原型草图 ≠ 可执行产物。**

本章的 bridge 依赖两个包：`@a2a-js/sdk/server` 与 `openclaw-plugin-silicon-life-training`。**本机两个都没装，代码一次都没跑过。** 所以它的正确标签是 **⏳ 原型**，不是 ✅ 已实现。

**怎么改**

```bash
# 1) 依赖存在性（⏳ 未验证项）
npm ls @a2a-js/sdk 2>&1 | head -3
# 2) 本机是否已构建 silicon-life plugin（应为"无"）
ls ~/.openclaw/workspace/plugins/ | grep -i silicon-life || echo "✓ 无（= 未构建）"
# 3) 端口是否已被占用（避免 41241 撞车）
lsof -nP -iTCP:41241 -sTCP:LISTEN || echo "✓ 端口空闲"
```

**并且把标签写进文档**：`原型草图 · 依赖未装 · 未运行 · ⏳`。

### 9.3.8 误区八：以为 stock A2A plugin"装了就在用"（实际 disabled）

**现象**

`openclaw plugins list | grep -i a2a` 有输出 → 结论："A2A 已在用"。

**为什么错**

**因为输出有三列：名字、id、状态。** 你只读了第一列。

```
A2A  a2a  disabled
```

**`disabled` 才是关键信息。** 存在 ≠ 启用——这是"字符串存在性判断"的通病。

**怎么改**

```bash
# 正确示范：读状态列，不做字符串存在性判断
openclaw plugins list 2>&1 | grep -i a2a
# 期望：A2A  a2a  disabled

# 三态判定：存在 / disabled / enabled
# 要真用，先 enable（⏳ 未实测，且属破坏性变更 → 先备份）
openclaw backup create
openclaw plugins enable a2a
```

**文档要写成三句话**：**存在 → disabled → 未实测。** 一句话都别省。

### 9.3.9 误区九：skills `id` 写成中文 / 无 namespace（协议层不认）

**现象**

```json
{ "id": "漂移检测", "name": "Drift Detection" }
```

**为什么错**

**协议层不认非 ASCII 的 id。**

`id` 是**机器标识符**（用于路由、日志、对账），`name` 是**人类可读标签**。两者职责不同：id 全局唯一且稳定，name 可以随时改得更通顺。

把中文塞进 id，会造成：日志里出现乱码、路由匹配失败、跨系统对账对不上。

**怎么改**

```json
{ "id": "drift_detection", "name": "漂移检测" }
```

**自查**

```bash
# id 一律英文 snake_case，name 可中文/英文
# 反例检测：id 含非 ASCII
python3 -c "
import json,re
c=json.load(open('<CARD>'))
print([s['id'] for s in c['skills'] if not re.fullmatch(r'[a-z0-9_]+', s['id'])])
"
# 期望：[]
```

### 9.3.10 误区十：把 Agent Card 当静态文档（改实现不改 Card）

**现象**

skill 改名了、传输方式改了、版本升级了 —— **Card 一个字没动。**

**为什么错**

**因为 Card 是对世界的承诺。** 改实现不改 Card = **对世界撒谎**。

而且这个谎是"静默"的：对方读到的是旧的，调用失败的是新的，**中间的错配不会被任何一方"看到"。**

**怎么改**

```bash
# 1) 立刻做一次"实现 ↔ Card"对账（三条最小一致性）
# 1a) 能力一致性：Card 里声明的 skill id 与实现的 skill 实际一致
# 1b) 传输一致性：capabilities.streaming 与你 bridge 的真实行为一致
# 1c) 版本一致性：Card version 与底座一致

# 2) 把 Card 生成纳入流程（避免手改遗漏）
#    做法：Card 由脚本从单一来源（VERSION + skills 清单）生成 → 不要手编

# 3) 加一条"Card 变更即版本号 +1"的规矩，并在协同事件日志里留痕
```

**第 3 条是治本的那条**：**让 Card 的变更成为事件，而不是隐式改动。** 一旦它进了 L3 事件日志，"什么时候改的、为什么改"就永远答得出来。

### 9.4.2 v1.0 的四项关键新增

**① 多协议绑定与版本协商（multi-protocol bindings + version negotiation）**

- **事实**：v1.0 引入多协议绑定与版本协商；支持 gRPC 等绑定（gRPC 端点用 `hostname:port` 形式表达）。
- **对本章的影响**：**Agent Card 的 `supported_interfaces[]` 就是这个能力的对外呈现**——一个 agent 可以按**偏好顺序**声明多种传输；客户端取第一个它能说的，忽略其余，**都不匹配则 fail closed**。
- **工程含义**：这是"**从演示协议到企业协议**"的标志。旧世界（v0.3）一个 agent 一个地址；新世界**一份 Card、多种接口、按偏好解析**。

**② 多租户（multi-tenancy）**

- **事实**：v1.0 支持多租户。
- **对本章的影响**：一个 SLCP 节点可以被**多个组织/租户**共享使用——这是"跨组织协同"从概念变成工程的前提。

**③ Signed Agent Cards（签名 Agent Card）**

- **事实**：**v1.0 引入 Signed Agent Cards，用密码学方式验证 agent 身份。**
- **对本章的影响**（这是本章最值得展开的一条）：
  - **它把"发现"升级成"可验证的发现"**：以前你读到一张 Card，只能相信它的内容；现在你可以**验证它确实由声称的那一方签发**；
  - **它和 SLCP 的 L3 账本互补**：签名解决"**这张 Card 是谁发的**"，账本解决"**它发了之后做了什么**"。**前者是身份层，后者是行为层——两者缺一，你只得到一半真相。**
  - **诚实的边界**：签名解决身份与完整性，**不解决"它说的能力是否真的具备"**。声明与实现的一致性，仍然要靠 §9.2.2 的三条最小一致性检查。

**④ 破坏性变更（v0.3 → v1.0）**

| 变更 | 影响 |
|---|---|
| well-known 路径改名 | 旧客户端找不到 Card |
| 类型判别字段（type discriminator）从线上协议中移除 | 旧的反序列化逻辑失效 |
| **Agent Card 不再有 URL，改为传输列表** | ⭐ 本章最高频的误植来源（9.3.2） |
| streaming 规则从"建议"变为"抛错" | 以前宽容的行为现在直接失败 |

**一句话**：**从 v0.3 升到 v1.0，字段级细节全部要重新核。** 任何基于 2025 年 0.x 世代写的 A2A 教程，在 2026 年都是不可直接引用的。

### 9.4.3 生态：150+ 组织与真实生产场景

**事实（Linux Foundation 2026-04-09 一周年公告口径，LF 自报）**：

- **150+ 支持组织**；
- 深度集成方：Google Cloud / Microsoft Copilot Studio & Foundry / Amazon Bedrock AgentCore；
- 生产部署（第三方综述口径）：Microsoft / AWS / Salesforce / SAP / ServiceNow；

**一个具体的规模化案例（2026 年）**：

> **华为把 A2A 标准化为 Celia（HarmonyOS 的 OS 级 AI 助手）与 App 内 agent 之间的协议。** 支持场景包括：Celia 把长任务交给 App agent、Celia 通过 agent 控制 App UI、Celia 向 App agent 请求上下文推荐。
>

**这个案例对本书的启示**：**A2A 的战场不在"几个 agent 在群里聊天"，在"OS 级助手调应用级 agent"。** 这和我方"军团协同"的场景**不同但同构**——两者都需要：发现（Card）、调用（method surface）、状态（lifecycle），以及**出事之后不塌（SLCP 三层）**。

⚠ **诚实标注**：150+ 组织是 **LF 自报口径，未独立核验各成员的实际使用程度**。本节引用时保留此限定。

### 9.4.4 治理格局：两条路线，本书不站队

2026 年 agent 协议层出现了两条清晰路线：

| 路线 | 主张 | 代表 |
|---|---|---|
| **单 agent 越强越好** | 把单 agent 做到极致，不押 agent 间编排 | **Anthropic**（押 MCP + Skills，**不下注 A2A**） |
| **多 agent 协同** | agent 之间需要开放协议 | **Google + Linux Foundation + Microsoft**（押 A2A） |

**客观事实**：Claude Opus 4.7 SWE-bench Verified（2026-04）达 **87.6%**（第三方口径）——单 agent 能力的巅峰确实在飞速提升。而 A2A 生态同期达到 150+ 组织。

**本书的立场：不站队。**

**理由**：SLCP 三层 + THP 是**兼容任意方向的中间层**——

- 如果世界走向"单 agent 越强越好"，那么少而精的 agent 之间的协同纪律**更重要**（因为每一个都不可或缺）；
- 如果世界走向"大规模多 agent 协同"，那么 SLCP 三层**就是基础设施**。

**两种未来，都需要"通话出事时不塌"。** 这是本章最稳的一个立论。

### 9.5.2 逐框架点评（一句强项 + 一句盲区）

**LangGraph**
- 强项：**多 agent 编排工程最成熟**——supervisor subgraph + Send API + 图可视化 + time-travel 调试，显式控制流语义精确。
- 盲区：**"让位仲裁 / 审计"需自建**；无 L1/L2/L3。

**AutoGen / AG2**
- 强项：多智能体对话与辩论（debate / iteration）是招牌，GroupChat / Swarm / Magentic-One 三条路线都在。
- 盲区：**GroupChat 失控（无限对话循环）是已知痛点**，靠 `max_turns` 粗粒度截断，**无漂移与协同语义**。

**CrewAI**
- 强项：角色分工最直观（`role` / `goal` / `backstory`），原型最快（2~4 小时可用，第三方口径）。
- 盲区：`hierarchical` 的 manager 只是**三省评审的弱对应物**——是流程便利，**不是证据验收**。

**Claude Agent SDK**
- 强项：**单 agent 深度最强**（extended thinking + computer use + MCP 原生）。
- 盲区：**多 agent 协同语义最弱**——Anthropic 明确不下注 A2A。**这是路线选择，不是能力缺陷。**

**OpenAI Agents SDK**
- 强项：**`handoffs` 是一等公民的任务交接**，业界最干净的交接原语；`guardrails` + `Tracing` 体系完整。
- 盲区：**handoffs 只管"交"**——不管"交接后的审计 + 让位冲突仲裁"。**这正是 THP 比它多出来的部分。**

**LlamaIndex**
- 强项：数据连接（LlamaHub / 索引）+ Workflows 事件驱动编排。
- 盲区：**agent 间协同非其主场**。

**OpenClaw v5.0（本章主体）**
- 强项：**十个维度里第 5–10 项（让位仲裁 / L1 / L2 / L3 / 三段评审 / 监督层）是六框架集体空白区。**
- 盲区（诚实写）：⏳ 非主仓能力（PR #152777 OPEN）；⏳ stock:a2a disabled；⏳ TCK 未跑；⏳ bridge 未运行。

### 9.5.3 一句话结论

**六框架解决"多个 agent 怎么被编排"，SLCP 解决"编排出事时不塌"。**

- **在"能不能协同"这一层**：LangGraph（supervisor）与 OpenAI Agents SDK（handoffs）都很强，**没有代差**；
- **在"协同出事之后"这一层**：**六框架集体空白**——L1 健康检查、L2 守门员、L3 协同事件日志、响应让渡、监督层，**没有一家有**；
- **在"跨厂商互通"这一层**：**只有 A2A 阵营**（含 OpenClaw 的 SLCP bridge）在解决，Claude 系明确不参与。

### 9.5.4 三条脚注（诚实标注）

1. **Google ADK**（2025-04 发布）是 A2A 原生派代表，**不在本书 6 大框架名单内**（公开文档量与生态规模未达 LangGraph / CrewAI 量级），本节仅作脚注。
2. **各框架精确小版本号** ⏳ 未逐条核验——本书以各官方仓库 release 页为准，不背书具体小版本号。
3. **"生产就绪排序"**（如 LangGraph 最高、AutoGen/AG2 中）基于公开能力模型合集程度，**不是市场份额**；**OpenClaw 不在该排序中**——基座与框架不是同层对比。

## 9.4 A2A TCK 跑通路径

### 9.4.1 TCK 是什么

**Test Compatibility Kit**（TCK）= A2A 官方兼容性测试集。跑通 TCK = 本实现被 A2A 社区认可。

### 9.4.2 跑通步骤

1. clone `github.com/a2aproject/a2a-tck`
2. 启动 SLCP bridge server（见 9.5）
3. 跑 `a2a-tck run --target http://localhost:41241`
4. 输出 `compat_report.json`
5. 向 A2A 社区提交报告

## 9.5 SLCP Bridge 原型

```typescript
// slcp-bridge.ts
import { A2AServer } from "@a2a-js/sdk/server";
import { AntiFragileTriptych } from "openclaw-plugin-silicon-life-training";

const server = new A2AServer({
  card: {
    name: "silicon-life-training-agent",
    version: "2026.9.4",
    supported_interfaces: ["a2a/v1", "slcp/v1"],
    skills: [
      { id: "drift_detection" },
      { id: "proactive_boundary_check" },
      { id: "three_stage_review" },
      { id: "anti_fragile_triptych" },
      { id: "self_initiated_goal" }
    ]
  }
});
```

### 错误 2 · 用 `capabilities.url` 单值声明接口（A2A v1.0.0 旧写法）

**错误现象**：Agent Card 里写 `"capabilities": { "url": "http://localhost:41241" }`，或者写 `"endpoint"` / `"transport"`。本地看着像 JSON 没问题，接进 A2A 生态就"连不上"。

**错误配置**（❌ 不要这样）：

```json
{
  "name": "silicon-life-training-agent",
  "version": "2026.9.4",
  "capabilities": {
    "streaming": true,
    "url": "http://localhost:41241"     // ❌ v1.0.0 旧写法，v1.0.1 已移除
  }
}
```

**为什么错**：

1. **A2A v1.0.1（2026-05-28 latest）做了破坏性变更**：接口声明从旧单值字段重构为 **`supported_interfaces[]` 数组**。任何按 v1.0.0 写的 bridge 在新规范下**连不上**——这是"破坏性"的确切含义。
2. **"本地 JSON 合法"完全不能证明"协议合规"。** 这正是本章最容易被"能解析"骗过的地方：http 能开、json 能 parse，但握手对不上。
3. **数组化是为了多协议共存**：`["a2a/v1", "slcp/v1"]` 表示这个 agent 同时说 A2A 和 SLCP——单值字段表达不了这件事，所以被移除而不是被兼容。
4. **后果是"静默不兼容"**：对方 agent 读到你的 Card、发现没有它认识的 interface、一声不响地跳过你——排查成本极高。
5. **与 TEV 的关系**：接口字段是"证据 1（新产物）"；但产物合规与否要靠"证据 3（日志：真的握手成功）"，只有数组字段 + 成功握手两件齐才算过。

**正确配置**（✅ 应该这样）：

```json
{
  "name": "silicon-life-training-agent",
  "version": "2026.9.4",
  "license": "MIT",
  "supported_interfaces": ["a2a/v1", "slcp/v1"],
  "capabilities": { "streaming": true, "pushNotifications": false },
  "skills": [
    { "id": "drift_detection", "name": "Drift Detection" },
    { "id": "proactive_boundary_check", "name": "Proactive Boundary" },
    { "id": "three_stage_review", "name": "Three-Stage Review" },
    { "id": "anti_fragile_triptych", "name": "Anti-Fragile Triptych" },
    { "id": "self_initiated_goal", "name": "Self-Initiated Goal" }
  ]
}
```

**验证命令**：


### 错误 4 · 跳过三层中间件（只写 Card，不写 fallback / gatekeeper / event-log）

**错误现象**：Agent Card 写得很漂亮、也挂上了端口，但 `slcp-bridge.ts` 里只 `listen(41241)`，三个中间件一个都没 `use`。文档里写"已接入 A2A 生态"。

**错误配置**（❌ 不要这样）：

```typescript
// 错误示范：只启动，不装三层
```

**为什么错**：

1. **这三层就是本章的全部价值所在。** 9.6 的对位表写得很清楚：A2A 原生 / AutoGen / CrewAI 在"fallback 健康检查 / 通道守门员 / 事件日志"三项上**全是空**（○ / ⚠），只有本训练学 SLCP 三项齐 ✅。

3. **没有 health-check**：某个 agent 实例（原：军团成员）挂了，其它实例还在往它发任务 → 任务黑洞。这就是 8/19 军团断线事故的协议层版本。
4. **没有 gatekeeper**：通道无限被占用、任务堆叠，没有守门员做准入与配额。
5. **没有 event-log**：协同事件不可回溯 → 违反第 5 章 TEV（三证据验证）的"证据 3（日志）"要求；事后既不能复盘也不能开 Remediation Ticket（修复工单，原：整改单）。

**正确配置**（✅ 应该这样）：

### 错误 5 · 把 A2A `Task` 当训练学"任务卡"（协议层 vs 语义层混淆）

**错误现象**：在 Agent Card 或 bridge 里把 A2A 的 Task 对象直接当第 5 章的任务卡（Task Card）用，字段里塞 `acceptance_criteria`、`trust_score` 之类——A2A 侧解析器不认识，训练学侧的验收口径也丢了。

**错误配置**（❌ 不要这样）：

```typescript
// 错误示范：把协议消息当语义任务卡
await server.task({
  id: "t-001",
  acceptance_criteria: ["7 契约齐"],   // ❌ 训练学字段塞进协议对象
  trust_score: 0.8,
  evidence: [...]
});
```

**为什么错**：

1. **两者是不同层次的东西。** 9.3.2 节的映射表写得清楚：A2A `Task` ↔ 训练学"任务卡"；A2A `Artifact` ↔ 新产物（TEV 第 1 证）；A2A `Message` ↔ 协同事件日志；A2A `Push Notification` ↔ 心跳触发。**是映射关系，不是同一物**。
2. **A2A Task 是协议消息**（可传输、可序列化、字段由规范定义）；**训练学任务卡是语义层**（含验收口径、证据要求、责任归属）。把后者塞进前者，协议层会拒绝你的扩展字段（或静默丢弃）。
3. **丢掉语义层的代价**：验收口径（Acceptance Criteria）是第 5 章治理的判定依据；一旦降级成"协议里的一段自由文本"，自动判定就没了。
4. **正确姿势是"双写 + 引用"**：协议对象里放最小必要字段 + 一个指向任务卡 ID 的引用；详情留在任务卡里。
5. **这也是"多智能体协作 vs 多智能体协同"的差别所在**：协作是"消息能到"，协同是"消息到的同时，验收口径与证据链也在"。

**正确配置**（✅ 应该这样）：

```typescript
// 正确示范：协议对象只放传输字段 + 语义引用
await server.task({

});

// 语义层（任务卡）单独落盘，含验收口径
// cards/t-001.md → 验收口径：TEV 三证据齐 + 噪声比 ≤ 阈值
```

### 错误 6 · Agent Card 缺 `license` / `version` 与真身不一致

**错误现象**：Card 里 `version` 手写 `"1.0.0"` 或 `"v1"`，`license` 留空；接进 A2A 生态后，对方按 Card 声明的版本协商，行为与你的实现不符。

**错误配置**（❌ 不要这样）：

```json
{
  "name": "silicon-life-training-agent",
  "version": "1.0.0",        // ❌ 与 OpenClaw 真身 2026.9.4 不一致
  "supported_interfaces": ["a2a/v1"]
                             // ❌ 无 license
}
```

**为什么错**：

1. **`version` 是协商依据。** A2A 客户端会按 Card 声明的版本决定用哪些 capability；写 `1.0.0` 而实际能力基于 2026.9.4，等于发出错误信号。
2. **Card 的 `version` 应与你的运行底座对齐**（本章骨架沿用 `2026.9.4`），而不是与 agent 的"业务版本"混写；要区分就分开字段（如 `metadata.trainer_version`）。
3. **`license` 显式写 MIT**：与 OpenClaw 主仓 License 一致；License 尽调已确认 MIT 可行（主仓 GitHub 显示 `NOASSERTION`，不影响法律效力）。缺 license 的 Card 在合规审查里会被直接拦下。
4. **`supported_interfaces` 不能只写 `["a2a/v1"]`**：你还要说 SLCP——那才是本章的差异化接口。
5. **一致性问题会连带污染第 12 章**：plugin manifest 里也要写版本与 license；两处不一致，ClawHub 校验与用户信任都会打折。

**正确配置**（✅ 应该这样）：

```json
{
  "name": "<your-agent>",
  "version": "2026.9.4",
  "license": "MIT",
  "supported_interfaces": ["a2a/v1", "slcp/v1"],
  "capabilities": { "streaming": true, "pushNotifications": false }
}
```

**验证命令**：

### 错误 7 · 把 `slcp-bridge.ts` 当成品（依赖未装、demo 未跑）

### 坑 1 · 先跑 TCK，再写 Agent Card

### 坑 2 · 以为"装了 A2A plugin"= A2A 能力在（disabled 陷阱）

**坑的场景**：`openclaw plugins list | grep -i a2a` 有输出，新人立刻在文档里写"本机 A2A 已就绪"，甚至据此判断"OpenClaw 原生支持 A2A"。

**为什么踩**：

- **grep 只看匹配不看列**：`grep -i a2a` 天然丢掉了状态列。
- **"安装了"和"启用了"在中文里几乎同义**——但在这套系统里是两个动作、两个字段。


### 坑 3 · skills `id` 写成中文 / 无 namespace（协议层不认）

**坑的场景**：Agent Card 的 `skills[]` 里写 `{ "id": "漂移治理", "name": "漂移治理" }`，或者 `{ "id": "检测" }`——因为"我们内部都这么叫"。

**后果**：A2A 侧的技能索引按 `id` 做匹配与路由，中文 id 在某些实现里编码/转义出问题；更重要的是 `id` 是**稳定标识**，改名即断链，而 `漂移治理` 这类词恰好是 v3.0 改名表要处理的词。

**为什么踩**：

- **本章骨架给的是英文 id**（`drift_detection` 等），但新人觉得"中文更直观就改了"。
- **id 与 name 的区别没人讲清**：id 是机器标识（稳定、英文、snake_case），name 是展示名（可本地化）。
- **内部黑话的惯性**：v1.0 卷八通篇中文术语，直接搬进 id 很顺手。

**怎么爬出来**：

```bash
PY

python3 -c "import json,re;d=json.load(open('$HOME/.openclaw/workspace/agents/roles/<your-agent>/a2a/agent-card.json'));print([s['id'] for s in d['skills'] if not re.fullmatch(r'[a-z][a-z0-9_]*', s['id'])])"
# 期望：[]
```

**预防**：写 Card 前先定 5 个 id 并把它们当**接口契约**（一旦发布不改）；中文名放 `name` 字段。

### 坑 4 · 端口 41241 撞车（以为端口随时可用）

**坑的场景**：新人模仿骨架直接 `listen(41241)`，可本机已经有一个进程占着（比如上一轮 demo 没关、或那个 disabled 的 stock A2A plugin 曾用过），`EADDRINUSE` 一报就懵。

**后果**：bridge 起不来 → 后面所有验证（TCK、握手、事件日志）全断；新人常误判为"协议实现有问题"。

**为什么踩**：

- **骨架里端口是硬编码**：`await server.listen(41241)` 看着像"规定端口"，没人说是示例。
- **没有"起之前查占用"的习惯**（这属于工程卫生，SOP 里没写）。
- **前一轮的残留进程**：Ctrl-C 有时没杀干净。

**怎么爬出来**：

```bash
# 1) 起之前先查
lsof -nP -iTCP:41241 -sTCP:LISTEN 2>/dev/null || echo "✓ 空闲"

# 2) 被占就换端口（同时改 Card 里的 endpoint 说明）
PORT=41242

# 3) 清理残留（确认是自己的进程再杀）
ps -ef | grep -i "slcp-bridge\|a2a" | grep -v grep
```

**预防**：把"端口预检"作为 bridge 启动脚本第一行；端口写进配置而不是硬编码。

### 坑 5 · 把 SLCP 当"商标可用名"对外随便写

**坑的场景**：新人写对外材料时图省事，写"我们自研 A2A 协议（ACP）"或者"SLCP ≈ A2A 的中国版"，甚至把 SLCP 当自研商标去宣传。

**为什么踩**：

- **超集关系不直观**：SLCP 复用了 A2A 的 Task / Artifact / Message，所以看起来像"同一件事的另一个名字"。

**预防**：对外材料统一模板三行——**协议名（SLCP）+ 对位（A2A v1.0.1 超集）+ 增量（三层 + 让位）**；禁止出现裸 ACP。

### 坑 6 · 把 Agent Card 当静态文档（改实现不改 Card）

**坑的场景**：新人第一次把 `agent-card.json` 写好后，把它当"项目简介"放在仓库里落灰。半年里 agent 加了两个 skill、换了端口、把 `streaming` 从 true 改成 false——Card 一个字段都没改。

**后果**：Card 变成**过期的自我介绍**，而它恰恰是 A2A 生态里别人认识你的**唯一入口**：

1. **对方按 Card 的 `skills[]` 路由任务**，你的实际能力却已经变了 → 任务发到你不支持的能力上，失败在对方侧。
2. **对方按 Card 的 `capabilities` 决定用不用流式**，你实际已不支持 → 连接建立后行为不一致，比连不上更难查。
3. **`supported_interfaces` 与实际不符** → 协议协商阶段的假阳性，排查成本极高。
4. **源头还是 Card 本身**：本章诚实边界已声明 Card 的字段来自 v4.0 实拉 + 设计推断；**推断部分如果不随实现更新，就变成事实错误**。

**为什么踩**：

- **JSON 文件不会报错**：字段过时不会触发任何告警；不像代码改动会带测试。
- **Card 不在构建流程里**：plugin 有 `build` / `validate`，Card 没有对应的校验闸门。
- **"对外文档可以后面再补"的惯性**——但 Card 不是文档，它是**机器读的接口**。
- **不确定性叠加**：A2A v1.0.1 还在演进（`supported_interfaces[]` 已是破坏性变更），静态 Card 会越放越错。

**怎么爬出来**：

```bash
# 1) 立刻做一次"实现 ↔ Card"对账（三条最小一致性）
CARD=~/.openclaw/workspace/agents/roles/<your-agent>/a2a/agent-card.json

# 1a) 能力一致性：Card 里声明的 skill id 与实现的 skill 实际一致
python3 -c "import json;print([s['id'] for s in json.load(open('$CARD'))['skills']])"
openclaw skills list 2>&1 | grep -iE "drift|boundary|review|triptych|goal" | head

# 1b) 传输一致性：capabilities.streaming 与你 bridge 的真实行为一致
grep -n "streaming" "$CARD"

# 1c) 版本一致性：Card version 与底座一致
python3 -c "import json;print(json.load(open('$CARD'))['version'])"; openclaw --version 2>&1 | tail -1

# 2) 把 Card 生成纳入流程（避免手改遗漏）
#    做法：Card 由脚本从单一来源（VERSION + skills 清单）生成 → 不要手编

# 3) 加一条"Card 变更即版本号 +1"的规矩，并在协同事件日志里留痕
```

**预防**：

- **Card 从单一来源生成**（`VERSION` 文件 + skill 清单 + 端口配置），禁止纯手工维护。
- **把 Card 校验挂进本地闭环**：与 plugin 的 `validate` 同批跑；不一致就失败。
- **Card 的每次字段变更写进协同事件日志**：这样下游能知道"你什么时候变的、变成什么"。
- **诚实标注未定部分**：尚未实现的 interface 写注释标 ⏳，不要先写进数组——Card 里的每个值都是**对外承诺**。

**相关 FAQ**：F9-2 / F9-6。相关章节：第 6 章（协同事件日志）、第 11 章（skill 清单作为单一来源）。

## 10.4 · SLCP 反脆弱三层完整配置

> **本节用法**：第 6 章给了反脆弱三层（Anti-Fragile Triptych）的「战略定义」，第 9 章 9.5 给了 `slcp-bridge.ts` 里三行 `server.use(...)` 的「原型引用」。本节是**完整可复制的工程配置**——L1 协议层（Protocol Layer）/ L2 运行时（Runtime Layer）/ L3 治理层（Governance Layer），**每层 ≥3 个实战例子 + 完整 YAML/TS 配置 + 验证命令**。读完本节你能把三层中间件从"三行引用"变成"真正装进 bridge 的三组模块"。
> 术语首次出现双写：故障转移（Failover）/ 通道守门员（Channel Gatekeeper）/ 健康检查（Health Check）/ 协同事件日志（Coordination Event Log）/ 断路器（Circuit Breaker）/ 自愈（Self-Heal）/ 监督层（Supervisor Layer，原：监军）。
> 实测环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27 · `stock:a2a/index.js` = disabled（诚实基线）。

### 背景

反脆弱三层（Anti-Fragile Triptych）是本训练学差异化优势 1（第 6 章）的核心资产，在 A2A 层的落地是三个中间件：

| 层 | 中间件 | 对应 A2A 缺口 | 本质 |
|---|---|---|---|
| L1 协议层 | fallback（冗余 / 健康检查） | A2A v1.0 无 fallback 健康检查 | 通道断了有人接 |
| L2 运行时 | gatekeeper（通道守门员） | A2A v1.0 无准入 / 配额 | 入口有人守 |
| L3 治理层 | event-log（协同事件日志） | A2A v1.0 无事件审计 | 事后有证据 |

为什么要分三层：**因为三层的故障域不同**。L1 挂了（health-check 进程死）不影响 L2（gatekeeper 还在守）；L2 被绕过不影响 L3（日志还在记）。**单层设计 = 单点故障**。

本节每层给**完整配置 + 3 个实战例子 + 验证命令**。

### 配置（完整可复制 YAML/JSON，零 `...` 省略）

**L1 · 反脆弱（协议层）完整配置**：

```typescript
// l1-fallback-middleware.ts
// L1 协议层：fallback 健康检查 + 故障转移 + 断路器
import { EventEmitter } from "events";

export interface FallbackConfig {
  health_check_interval: number;
  failover_threshold: number;
  channel_timeout: number;
  self_heal: boolean;
  circuit_breaker_threshold: number;
  circuit_breaker_reset_timeout: number;
}

export class FallbackMiddleware extends EventEmitter {
  private config: FallbackConfig;
  private healthStatus: Map<string, { lastSeen: number; failures: number; circuitOpen: boolean }>;
  private checkTimer: NodeJS.Timeout | null;

  constructor(config: FallbackConfig) {
    super();
    this.config = {
      health_check_interval: config.health_check_interval ?? 60_000,
      failover_threshold: config.failover_threshold ?? 3,
      channel_timeout: config.channel_timeout ?? 300_000,
      self_heal: config.self_heal ?? true,
      circuit_breaker_threshold: config.circuit_breaker_threshold ?? 5,
      circuit_breaker_reset_timeout: config.circuit_breaker_reset_timeout ?? 120_000
    };
    this.healthStatus = new Map();
    this.checkTimer = null;
  }

  start(): void {
    this.checkTimer = setInterval(() => this.runHealthCheck(), this.config.health_check_interval);
    this.emit("fallback:started", { interval: this.config.health_check_interval });
  }

  stop(): void {
    if (this.checkTimer) {
      clearInterval(this.checkTimer);
      this.checkTimer = null;
    }
    this.emit("fallback:stopped");
  }

  private async runHealthCheck(): Promise<void> {
    for (const [agentId, status] of this.healthStatus.entries()) {
      const now = Date.now();
      const silentMs = now - status.lastSeen;
      if (silentMs > this.config.channel_timeout) {
        status.failures += 1;
        this.emit("fallback:agent-silent", { agentId, silentMs, failures: status.failures });
        if (status.failures >= this.config.failover_threshold) {
          await this.triggerFailover(agentId);
        }
      }
      if (status.failures >= this.config.circuit_breaker_threshold && !status.circuitOpen) {
        status.circuitOpen = true;
        this.emit("fallback:circuit-open", { agentId });
        setTimeout(() => {
          status.circuitOpen = false;
          status.failures = 0;
          this.emit("fallback:circuit-closed", { agentId });
        }, this.config.circuit_breaker_reset_timeout);
      }
    }
  }

  private async triggerFailover(agentId: string): Promise<void> {
    this.emit("fallback:failover", { agentId, at: new Date().toISOString() });
    if (this.config.self_heal) {
      this.emit("fallback:self-heal-attempt", { agentId });
    }
  }

  registerAgent(agentId: string): void {
    this.healthStatus.set(agentId, { lastSeen: Date.now(), failures: 0, circuitOpen: false });
  }

  heartbeat(agentId: string): void {
    const s = this.healthStatus.get(agentId);
    if (s) {
      s.lastSeen = Date.now();
      s.failures = 0;
    }
  }

  middleware() {
    return async (ctx: any, next: () => Promise<void>) => {
      const agentId = ctx.agentId ?? "unknown";
      const status = this.healthStatus.get(agentId);
      if (status?.circuitOpen) {
        ctx.status = 503;
        ctx.body = { error: "circuit-open", agentId, retryAfter: this.config.circuit_breaker_reset_timeout };
        this.emit("fallback:rejected-circuit-open", { agentId });
        return;
      }
      this.heartbeat(agentId);
      await next();
    };
  }
}
```

**L2 · 反脆弱（运行时）完整配置**：

```typescript
// l2-gatekeeper-middleware.ts
// L2 运行时：通道守门员 — 准入 / 配额 / 优先级 / 拒绝策略
export interface GatekeeperConfig {
  max_concurrent_per_agent: number;
  max_queue_per_agent: number;
  default_priority: number;
  reject_policy: "reject" | "queue" | "degrade";
  rate_limit_per_minute: number;
  allowlist_agents: string[];
  denylist_agents: string[];
}

export class GatekeeperMiddleware {
  private config: GatekeeperConfig;
  private inFlight: Map<string, number>;
  private queue: Map<string, Array<{ id: string; priority: number; enqueuedAt: number }>>;
  private rateWindow: Map<string, number[]>;

  constructor(config: GatekeeperConfig) {
    this.config = {
      max_concurrent_per_agent: config.max_concurrent_per_agent ?? 4,
      max_queue_per_agent: config.max_queue_per_agent ?? 20,
      default_priority: config.default_priority ?? 5,
      reject_policy: config.reject_policy ?? "queue",
      rate_limit_per_minute: config.rate_limit_per_minute ?? 60,
      allowlist_agents: config.allowlist_agents ?? [],
      denylist_agents: config.denylist_agents ?? []
    };
    this.inFlight = new Map();
    this.queue = new Map();
    this.rateWindow = new Map();
  }

  private isAllowed(agentId: string): boolean {
    if (this.config.denylist_agents.includes(agentId)) return false;
    if (this.config.allowlist_agents.length > 0) {
      return this.config.allowlist_agents.includes(agentId);
    }
    return true;
  }

  private checkRate(agentId: string): boolean {
    const now = Date.now();
    const window = (this.rateWindow.get(agentId) ?? []).filter(t => now - t < 60_000);
    window.push(now);
    this.rateWindow.set(agentId, window);
    return window.length <= this.config.rate_limit_per_minute;
  }

  middleware() {
    return async (ctx: any, next: () => Promise<void>) => {
      const agentId: string = ctx.agentId ?? "unknown";
      if (!this.isAllowed(agentId)) {
        ctx.status = 403;
        ctx.body = { error: "gatekeeper-denied", agentId, reason: "denylist or not in allowlist" };
        return;
      }
      if (!this.checkRate(agentId)) {
        ctx.status = 429;
        ctx.body = { error: "gatekeeper-rate-limited", agentId, retryAfterMs: 60_000 };
        return;
      }
      const flying = this.inFlight.get(agentId) ?? 0;
      if (flying >= this.config.max_concurrent_per_agent) {
        if (this.config.reject_policy === "reject") {
          ctx.status = 429;
          ctx.body = { error: "gatekeeper-concurrency-full", agentId };
          return;
        }
        const q = this.queue.get(agentId) ?? [];
        if (q.length >= this.config.max_queue_per_agent) {
          ctx.status = 429;
          ctx.body = { error: "gatekeeper-queue-full", agentId };
          return;
        }
        q.push({ id: ctx.taskId ?? `t-${Date.now()}`, priority: ctx.priority ?? this.config.default_priority, enqueuedAt: Date.now() });
        q.sort((a, b) => b.priority - a.priority);
        this.queue.set(agentId, q);
        ctx.status = 202;
        ctx.body = { queued: true, agentId, position: q.length };
        return;
      }
      this.inFlight.set(agentId, flying + 1);
      try {
        await next();
      } finally {
        this.inFlight.set(agentId, (this.inFlight.get(agentId) ?? 1) - 1);
        const q = this.queue.get(agentId) ?? [];
        if (q.length > 0) {
          q.shift();
          this.queue.set(agentId, q);
        }
      }
    };
  }
}
```

```typescript
// l3-eventlog-middleware.ts
// L3 治理层：协同事件日志 — 所有跨 agent 事件落 jsonl，供 TEV 证据 3 用
import * as fs from "fs";
import * as path from "path";

export interface EventLogConfig {
  log_path: string;
  rotate_mb: number;
  keep_days: number;
  required_fields: string[];
  sign_events: boolean;
}

export type CoordinationEvent =
  | { type: "task.created"; taskId: string; from: string; at: string }
  | { type: "task.assigned"; taskId: string; from: string; to: string; at: string }
  | { type: "task.ack"; taskId: string; by: string; at: string }
  | { type: "task.completed"; taskId: string; by: string; evidence: string[]; at: string }
  | { type: "task.failed"; taskId: string; by: string; reason: string; at: string }
  | { type: "fallback.failover"; agentId: string; at: string }
  | { type: "gatekeeper.rejected"; agentId: string; reason: string; at: string }
  | { type: "yield.requested"; taskId: string; from: string; to: string; at: string }
  | { type: "yield.accepted"; taskId: string; by: string; at: string };

export class EventLogMiddleware {
  private config: EventLogConfig;

  constructor(config: EventLogConfig) {
    this.config = {
      log_path: config.log_path ?? `${process.env.HOME}/notes/domain/silicon-life-handbook/governance/channel.jsonl`,
      rotate_mb: config.rotate_mb ?? 50,
      keep_days: config.keep_days ?? 90,
      required_fields: config.required_fields ?? ["type", "at"],
      sign_events: config.sign_events ?? false
    };
    fs.mkdirSync(path.dirname(this.config.log_path), { recursive: true });
  }

  append(event: CoordinationEvent): void {
    for (const f of this.config.required_fields) {
      if (!(f in event)) throw new Error(`event missing required field: ${f}`);
    }
    fs.appendFileSync(this.config.log_path, JSON.stringify(event) + "\n");
    this.maybeRotate();
  }

  private maybeRotate(): void {
    try {
      const st = fs.statSync(this.config.log_path);
      if (st.size > this.config.rotate_mb * 1024 * 1024) {
        const stamp = new Date().toISOString().slice(0, 10);
        fs.renameSync(this.config.log_path, `${this.config.log_path}.${stamp}`);
      }
    } catch { /* 首写时文件不存在，忽略 */ }
  }

  middleware() {
    return async (ctx: any, next: () => Promise<void>) => {
      const startedAt = new Date().toISOString();
      if (ctx.taskId) {
        this.append({ type: "task.ack", taskId: ctx.taskId, by: ctx.agentId ?? "unknown", at: startedAt });
      }
      try {
        await next();
        if (ctx.taskId) {
          this.append({ type: "task.completed", taskId: ctx.taskId, by: ctx.agentId ?? "unknown", evidence: ctx.evidence ?? [], at: new Date().toISOString() });
        }
      } catch (err: any) {
        if (ctx.taskId) {
          this.append({ type: "task.failed", taskId: ctx.taskId, by: ctx.agentId ?? "unknown", reason: String(err?.message ?? err), at: new Date().toISOString() });
        }
        throw err;
      }
    };
  }
}
```

### 排坑

**坑 1 · 三层顺序装反**

L3（日志）必须在最外层——否则 L1/L2 拒绝的请求记不进日志。

```typescript
// 错误：L1 在外，L2/L3 的拒绝记不进 L3
server.use(l1.middleware());
server.use(l2.middleware());
server.use(l3.middleware());   // ❌ L1 拒绝的请求 L3 看不到

// 正确：L3 在外
server.use(l3.middleware());
server.use(l2.middleware());
server.use(l1.middleware());   // ✅ 所有拒绝都被 L3 记录
```

**坑 2 · L1 健康检查和心跳 automation 脱钩**

L1 的 `heartbeat()` 靠心跳 automation 喂信号。如果 automation 挂了，L1 会误判 agent 挂了。

```bash
# 错误：只看 L1 日志判 agent 死活

# 正确：先查 automation，再判 agent
openclaw automations list 2>&1 | grep -i heartbeat
openclaw agent --message "ping" --agent <agent>   # 直接 ping agent 本体
```

**坑 3 · L2 配额设死不调**

`max_concurrent_per_agent=4` 是起点，不是终点。任务类型不同，并发能力不同。

```yaml
# 错误：所有 agent 同一配额
max_concurrent_per_agent: 4   # ❌ 重任务 agent 只能扛 2，轻任务 agent 能扛 10

# 正确：按 agent 角色分档
quotas:
  heavy_agent: 2    # 跑 TEV 全量验证的
  normal_agent: 4   # 默认
  light_agent: 10   # 只做路由转发的
```

## 10.6 · 任务交接协议 THP 实操

> **本节用法**：第 5 章给了任务卡（Task Card）的「治理定义」，第 9 章 9.3.2 给了 A2A Task ↔ 任务卡的「映射表」。本节是**任务交接协议 THP（Task Handoff Protocol）的完整实操**——任务卡字段 schema（context/goal/owner/deadline/evidence ...）+ 让位流程 + 抢活判定算法 + CASE-1（8/19 军团断线）复盘。读完本节你能写出一张"别人能接得住"的任务卡。
> 术语首次出现双写：任务交接协议（Task Handoff Protocol，THP）/ 让位（Yield）/ 抢活（Contention）/ 验收口径（Acceptance Criteria）/ 任务卡（Task Card）。
> 实测环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27。

### 背景

任务交接协议 THP 解决一个问题：**agent A 做到一半做不下去了，怎么让 agent B 无缝接上？**

THP = 3 件套：

1. **任务卡 schema**（交接时传什么字段）
2. **让位流程**（谁发起、谁接受、超时怎么办）
3. **抢活判定算法**（多人想接时谁接）

CASE-1（8/19 军团断线）的根因就是 THP 缺失：agent-c 挂了，但它的任务卡没传给任何人 → 任务黑洞。

**抢活判定算法（完整 Python 实现）**：

```python
#!/usr/bin/env python3
# contention.py — 抢活判定：多人想接时谁接
# 输入：candidate 列表（含 priority / inFlight / skills）
# 输出：选中的 agent ID + 理由

from dataclasses import dataclass

@dataclass
class Candidate:
    agent_id: str
    priority: int          # 任务优先级（1-10）
    inflight: int          # 当前并发数
    max_concurrent: int    # 最大并发数
    has_skill: bool        # 是否具备任务所需 skill
    last_completed_at: str # 上次完成时间（ISO，用于同分时 tie-break）

def pick(candidates: list[Candidate]) -> tuple[str, str]:
    # 第 1 轮：过滤（无 skill / 并发满 → 淘汰）
    eligible = [
        c for c in candidates
        if c.has_skill and c.inflight < c.max_concurrent
    ]
    if not eligible:
        return ("", "无人符合（全部无 skill 或并发满）→ 升级 Supervisor Layer")
    # 第 2 轮：按 priority 降序
    eligible.sort(key=lambda c: (-c.priority, c.last_completed_at))
    winner = eligible[0]
    reason = (
        f"{winner.agent_id} 胜出 "
        f"(priority={winner.priority}, "
        f"inflight={winner.inflight}/{winner.max_concurrent}, "
        f"has_skill={winner.has_skill})"
    )
    return (winner.agent_id, reason)

if __name__ == "__main__":
    cs = [
        Candidate("agent-a", priority=8, inflight=1, max_concurrent=4, has_skill=True, last_completed_at="2026-09-20T02:00:00Z"),
        Candidate("agent-b", priority=5, inflight=4, max_concurrent=4, has_skill=True, last_completed_at="2026-09-20T01:00:00Z"),
        Candidate("agent-c", priority=9, inflight=0, max_concurrent=4, has_skill=True, last_completed_at="2026-09-20T03:00:00Z"),
        Candidate("agent-e", priority=10, inflight=0, max_concurrent=4, has_skill=False, last_completed_at="2026-09-20T04:00:00Z"),
    ]
    winner, reason = pick(cs)
    print(f"选中: {winner}")
    print(f"理由: {reason}")
    # 期望：
    # 选中: agent-c
    # 理由: agent-c 胜出 (priority=9, inflight=0/4, has_skill=True)
    # 说明：agent-e 虽然 priority=10 但无 skill → 第 1 轮淘汰
    #       agent-b 并发满 → 第 1 轮淘汰
```

> **本节用法**：A2A 在 2026 Q3 是"Google 主导的事实标准"，但**远未定型**——TCK 还在演进、Agent Card 有破坏性变更、多模态还没影。本节给出**业界对位表**（A2A/Linux Foundation vs SLCP / Anthropic Computer Use / OpenAI Operator）+ **跨 agent 协同未来 1 年路线** + **本训练学的差异化定位**。
> 术语首次出现双写：计算机使用（Computer Use）/ 操作员（Operator）/ 协同未来（Collaboration Future）。
> 实测环境：OpenClaw 2026.9.4 (3a9d69d) · 2026-09-27。

### 背景

跨 agent 协同在 2026 Q3 的格局：

| 玩家 | 协议/产品 | 状态 |
|---|---|---|
| Google + Linux Foundation | A2A v1.0.1 | 事实标准，但三项全空（fallback / gatekeeper / event-log） |
| Anthropic | Computer Use | 私有 API（屏幕操作），无开放 agent 间协议 |
| OpenAI | Operator | 私有产品（浏览器操作），无开放 agent 间协议 |
| Microsoft | AutoGen | 已停滞 165 天（反面教材） |
| CrewAI | CrewAI | 有角色无协议 |
| 本训练学 | SLCP（A2A 超集） | 补三层 + 让位语义 |

**核心判断**：未来 1 年，A2A 会是"通信层标准"，但"组织语义层"（让位、评审、三层）不会进 A2A 标准——那是各家差异化的地方。**SLCP 的定位就是"组织语义层"**。

### 排坑

**坑 1 · 把 SLCP 当"A2A 平替"**

SLCP 是 **A2A 超集**（A2A 通信 + SLCP 组织语义），不是平替。**没有 A2A，SLCP 跑不起来**。

```markdown
<!-- 错误 -->
我们用 SLCP，不用 A2A。   # ❌ SLCP 跑在 A2A 上，没有 A2A 就没有 SLCP

<!-- 正确 -->
SLCP = A2A v1.0.1（通信层）+ 反脆弱三层 + 让位规则（组织语义层）。
A2A 提供 Task / Artifact / Message；SLCP 追加 fallback / gatekeeper / event-log + yield。
```

**坑 2 · 把 Computer Use / Operator 当"协同协议"**

Computer Use（屏幕操作）和 Operator（浏览器操作）是**单 agent 能力**，不是 agent 间协议。**它们解决"agent 怎么操作电脑"，SLCP 解决"agent 之间怎么协作"**。

```yaml
# 错误认知：
# "用了 Computer Use 就不用 SLCP 了"   # ❌ 两件事

# 正确分工：
# Computer Use / Operator：单 agent 的"手"（操作 GUI / 浏览器）
# A2A：agent 之间的"嘴"（通信协议）
# SLCP：agent 之间的"组织"（让位 / 评审 / 三层治理）
# 三者组合：有手 + 有嘴 + 有组织 = 完整多智能体系统
```

**坑 3 · 把 AutoGen 的停滞当"多智能体不行"**

AutoGen 停滞（165 天未推）是**项目治理问题**，不是"多智能体方向错了"。A2A + SLCP 正在接棒。
