# 硅基生命训练手册：管理者执行摘要

## 这本分册只帮助您做六类决定

企业引入 Agent，最容易出现两种误判。第一种是把一次精彩回答当成能力；第二种是把流程自动化当成责任自动转移。一个 Agent 可能写得很好，却无法稳定完成岗位任务；也可能技术调用成功，却没有把结果交到正确的人手里；还可能产物看似完整，真实环境根本没有发生预期变化。管理者需要的不是更长的技术术语表，而是一套能回答“是否可用、能放多大权、出了事谁负责、现在应不应该上线”的判断方法。

本分册只讲六件事：如何用七维标准看能力；如何用 AU 等级限制自主半径；如何用“三面完成”识别假完成；`REVIEW_REQUIRED` 到底意味着什么；哪些字必须由管理者签；每次评审必须追问哪五个问题。它不要求您掌握模型训练、提示词技巧或某个平台的操作步骤，也不把您变成项目的测试工程师。您的职责是建立清晰边界、要求可复核证据，并对价值、风险和剩余未知作出不能外包的决定。

如果只记住一句话，请记住：**Agent 的权限、成熟度、一次任务的成功和组织对风险的接受，是四个不同问题。** 它们必须分别判断，不能由一个“智能分”自动推导。

---

## 一、先判断为什么要用 Agent

一个项目应从业务任务开始，而不是从“我们也要有 Agent”开始。管理者先写清楚：它服务谁，解决哪类重复或高价值问题，当前人工基线是什么，允许访问哪些数据和系统，可能产生什么外部影响，失败后是否可逆，谁承担最终结果。若这些问题没有答案，团队越快搭建，越可能把模糊目标固化成难以审计的自动化。

合格的试点对象通常具有四个特点：任务边界可描述；成功与失败可观察；数据和权限能够收窄；失败可以隔离、回滚或补偿。相反，目标经常变化、责任主体不清、数据权利未知、一次误操作就可能造成重大不可逆后果的任务，不适合直接从全自动开始。它们可以先让 Agent 做只读研究、候选方案或风险提示，由人类完成决定和执行。

管理者还要要求团队给出人工或现有系统基线。没有基线，“效率提升 60%”通常没有可比较对象。基线至少包括任务量、成功率、返工率、处理时长、人工介入、事故、成本和用户结果。Agent 候选必须在相同任务口径、相近时间窗口和明确预算下比较；不能用最适合 Agent 的样本对比人工最困难的历史平均。

上线目标应写成范围化承诺。例如：“在已授权的内部知识库范围内，为售前人员生成方案初稿；不得对外发送，不得承诺价格；每份结果由具名员工复核；三个月内把平均初稿时间从 120 分钟降到 45 分钟，同时事实性重大错误低于约定阈值。”这句话同时定义价值、对象、禁止项、人工责任和衡量方式，比“打造行业最强销售 Agent”更适合决策。

## 二、七维标准：不要只看答案质量

本书用七个维度描述 Agent 系统。七维不是为了做一个漂亮雷达图，而是防止团队用某一项亮点遮住另一项硬伤。每一维都要给出证据、范围和有效期；没有测量的维度写 `NOT_MEASURED`，证据不足写 `UNKNOWN`，不能为了总分完整随意补零或补满。

### 1. 任务能力

它是否在目标任务中持续产生正确、完整、可使用的结果？管理者应要求看到任务分布，而非三个演示。需要知道常见任务、边界任务、陌生变式和失败样本分别怎样。结果还要包含产物和真实环境终态：报告是否能打开，工单是否真的创建，消息是否到达正确对象，数据是否按要求更新。一次答对只能证明发生过一次成功，不能证明形成稳定能力。

### 2. 可靠性

同样条件下结果是否稳定？长时间运行、并发、超时、网络中断、工具错误和重复投递时能否恢复？管理者不需要读每条 trace，但要看到成功率之外的尾部失败、重试代价、恢复时间、重复执行和未知终态。平均延迟很好看，却可能掩盖少数任务长时间卡住；平均成功率很高，也可能掩盖同一高风险环节反复失败。

### 3. 安全与权限

系统是否只在被允许的主体、对象、动作、参数、时窗和预算内行动？提示词里的“不要泄密”不是权限。需要看身份、最小权限、凭证保管、审批、撤销、网络出口、租户隔离、工具策略和审计。安全失败属于硬门：一次越权读取、错误外发、凭证泄露或绕过审批，不能被高质量和低成本平均掉。

### 4. 记忆与上下文

系统记住什么、为什么记、为谁记、保存多久、何时纠错和删除？记忆可以提高连续性，也会把错误、过期事实和跨客户数据带进未来任务。管理者要看来源、作用域、保留和删除路径，尤其要验证“禁止未来再摄入”和“删除既有副本”不是同一件事。上下文压缩后，目标、约束、授权、对象、期限和未决项是否仍完整，也必须验证。

### 5. 协作与交接

多个 Agent 或人机之间是否能明确委派、交接、合并和承担责任？增加 Agent 数量不等于形成团队。需要看谁拥有任务、谁能分配资源、子任务失败是否隔离、共享文件和外部状态是否冲突、交接时哪些事实和权限得到确认。任何 Handoff 都不能让原责任凭空消失，也不能把“收到消息”当成“接受责任”。

### 6. 可观测与可审计

发生问题时，组织能否还原谁在什么版本、什么权限下，基于哪些输入采取了什么动作，产生哪些产物和外部效果？只有最终聊天记录不够。管理者应要求证据能定位到任务、版本、授权、动作、产物、交付、业务终态和成本。日志很多并不等于可审计；如果关键对象无法关联、失败记录可被覆盖、同一个 ID 被重复使用，仍然无法问责。

### 7. 经济与业务效果

它是否在总成本和风险可接受的前提下产生业务价值？总成本包括模型与工具费用、人工复核、失败重做、等待、基础设施、安全治理和事故损失。业务效果要看用户采用、周期、质量、转化、收入、风险或其他真实指标，而不是 token 数和调用次数。一个系统可能技术更先进，却因为人工看护过重、错误代价过高而没有经济价值。

### 七维如何形成决定

七维评分只能描述证据分布，不能自动投票。安全、授权、重大合规和不可逆影响是非补偿硬门；任何关键硬门失败，整体结论就是 `FAIL`。其他维度即使改善，也只能作为整改价值，不构成上线理由。某维度证据不足时，不应给一个保守分数后继续，而要明确缺什么、谁负责、何时补齐，以及在此之前系统只能运行在哪个收缩范围。

## 三、AU 等级：决定 Agent 可以走多远

`AU` 是自主上限，不是聪明程度。能力强的 Agent 可以被限制在低自主等级；成熟度不高的系统也不能因为用户信任就获得高权限。每次授权都应绑定任务范围、数据、工具、对象、时窗、预算和停止条件。管理者批准的是一个有限运行合同，不是“以后都可以”。

| 等级 | 管理含义 | 典型边界 | 适用情形 |
| --- | --- | --- | --- |
| AU-L0 | 只读或解释 | 不改变工作区和外部状态 | 学习、问答、资料检索、风险分析 |
| AU-L1 | 提案 | 可生成草稿、计划和候选产物；人类决定是否执行 | 营销初稿、代码建议、调研摘要、审批材料 |
| AU-L2 | 可逆执行 | 在受控工作区执行可查看、可撤销的修改 | 文件编辑、分支代码、沙箱数据处理、内部工单草案 |
| AU-L3 | 有界外部行动 | 在逐动作授权或有效 standing order 内产生外部 effect | 发送指定消息、更新批准对象、调用受限业务接口 |
| AU-L4 | 高影响受控自主 | 涉及生产、资金、删除、身份、公共发布等；多方门禁和独立验收 | 极少数成熟场景，通常仍保留关键人类决定 |

### 升级 AU 的条件

升级不能由“最近表现很好”单独触发。至少需要：任务范围稳定；七维中的相关硬门有证据；权限可以机器执行地收窄；撤销和停止经过演练；重复执行有幂等或对账机制；失败可以隔离、回滚或补偿；监控和接管有人值守；真实环境试点证明任务、交付和业务终态闭合。任何关键条件未知，只能维持当前等级或收缩。

### 授权收缩比扩张更重要

成熟系统必须能在风险上升时自动变窄。出现证据冲突、owner 失联、预算逼近、凭证异常、模型或工具漂移、外部终态未知、重大政策变化时，应停止新任务、撤回高风险工具、由执行降为提案、由外部写入降为只读，并把未决项交给具名人类。收缩不是项目失败，而是可靠性的组成部分。

### Standing Order 不是永久通行证

重复任务可以使用预先批准的持续指令，但必须有对象范围、允许动作、参数约束、时窗、预算、例外、停止条件、复审日和撤销路径。它不能覆盖新用途、新数据域、新用户群或更高风险动作。到期、重大变更或事故后必须重新批准，不能因过去一直成功就默认为永久有效。

## 四、三面完成：识别“工具成功、事情没成”

本书把完成拆成三面。只有三面都满足，系统才能把任务报告为完成。

### 第一面：技术执行

工具或程序是否按预期运行并返回合格结果？例如 API 返回成功、文件写入、测试通过、任务进程退出。技术执行是必要条件，但它只证明某个接口发生了预期响应。HTTP 200、exit 0、消息平台 ACK 都不能单独证明业务完成。

### 第二面：交付可见

目标用户或下游系统是否在正确位置看见并能使用结果？文件可能生成在错误目录，消息可能发送到错误群，工单可能创建在测试租户，报告可能没有权限打开。交付可见要由目标侧 receipt、readback 或用户可访问性验证，而不是发送方自报。

### 第三面：业务与环境验收

真实世界是否达到任务要求？例如客户记录确实更新、库存真实锁定、发布页面内容正确、旧任务停止、用户问题解决。它通常需要业务规则、环境读回或具权威的人确认。产物存在但结论错误、消息到达但收件人不是目标、代码合并但生产未部署，都未完成第三面。

### 一个典型假完成

团队要求 Agent “把上周那批客户都跟一下，重点推新方案，别太保守”。系统调用消息工具得到 200，生成了一份联系人表和发送摘要，看板显示完成。复核发现：十二条消息只写进沙箱；五位客户没有有效授权；新方案价格尚未批准；三条联系人记录属于另一个业务单元。技术执行局部成功，Artifact 也存在，但交付和业务终态未发生，且存在权限风险。正确状态不是“完成但有小问题”，而是停止外发、核对范围、保留证据、修正授权后重跑。

管理者应要求仪表盘分别显示三面，不允许压成一个绿色勾。若外部系统暂时无法确认终态，写 `UNKNOWN` 或 `REVIEW_REQUIRED`，并停止可能造成重复影响的自动重试。诚实地保留未知，优于用重复操作制造第二次事故。

## 五、`REVIEW_REQUIRED`：不是软通过，也不是推迟责任

本书只允许三个评审结论：`PASS`、`FAIL`、`REVIEW_REQUIRED`。

`PASS` 表示在明确主体、版本、任务、环境、数据、权限、预算和有效期内，预先规定的证据门已经满足。它不是永久证书，也不覆盖未声明范围。

`FAIL` 表示已经观察到违反要求的事实，例如越权、关键测试失败、不可接受错误、恢复失败或终态矛盾。FAIL 需要立即写出止损、影响范围、责任人、修复和复测条件；不能通过改名为“已知限制”继续上线。

`REVIEW_REQUIRED` 表示现有证据不足、互相冲突，或必须由具备 authority 的人/系统作出判断。它不是“基本通过”“风险可控”“后续优化”，也不是让项目先上线的临时绿色。每个 RR 必须绑定：缺失或冲突的证据；为什么机器不能自行决定；谁有权判断；判断截止时间；等待期间系统保持什么安全状态；哪些条件满足后转为 PASS 或 FAIL。

常见 RR 包括：真实凭证或生产网络未测试；外部系统终态无法读取；数据用途或许可不清；法规适用性待专业判断；owner 缺席；两个权威来源冲突；安全攻击只在合成夹具通过；供应商宣称尚未独立验证。若团队无法写出 RR 的 owner 和截止时间，它就会变成永久模糊，应暂停相关能力。

管理者最重要的动作，是拒绝把 RR 改写成“有限通过”。系统可以处于受限生命周期状态，例如只读、内部试点、shadow 或 canary；但评审决定仍然是 RR。生命周期状态回答“现在在哪运行”，评审结论回答“证据是否足够”，两者不能混成第四种门禁。

## 六、管理者必须签哪些字

签字不是为了增加会议，而是固定最终责任和决策范围。Agent 可以整理证据、发现缺口和提出建议，不能替管理者接受残余风险、扩大用途或宣布事故结束。至少以下决定需要具名人类或法律主体签署，具体人数和职责分离按风险调整。

### 1. 业务范围与成功定义

Business Owner 签任务、用户、承诺、禁止项、业务指标、可接受失败和退出条件。没有这份签字，技术团队无法知道优化目标，也无法判断产物是否真正完成业务。

### 2. 数据用途与边界

Data/Privacy Owner 签数据来源、用途、主体、分类、地域、接收者、保留、删除、训练/评测回流和跨组织使用。能访问不等于能记忆、训练、出版或跨客户复用。涉及中国境内个人信息、数据安全、面向公众生成式 AI、算法/模型备案和生成内容标识时，应保存法务或合规判断及日期。

### 3. 安全与自主上限

Security/Risk Owner 签身份、工具、权限、凭证、网络出口、审批方式、AU 上限、例外和紧急停止。扩大数据域、外部 effect、生产权限、资金、删除、身份或公共发布时，旧批准自动失效或进入复核。

### 4. 发布、扩大和重大变更

发布决定要绑定不可变 release、评测结果、恢复证明、试点范围、值守、停止条件和有效期。模型、Provider、Skill、Plugin、工具 schema、权限、记忆、数据用途或运行时发生重大变化，不能沿用“上次已经批准”。

### 5. 残余风险接受

只有具备相应业务和风险 authority 的人可以接受残余风险。记录应说明未解决问题、可能影响、暴露范围、补偿控制、复审时间和退出条件。技术人员或 Agent 不能用“概率低”代替业务接受。

### 6. 事故恢复与重新开放

系统修复后，恢复生产需要确认漏洞或故障已关闭、凭证已处理、外部 effect 已对账、受影响对象已通知或补偿、回归通过、观测正常。修复代码合并不等于事故结束；业务与环境读回必须闭合。

### 7. 暂停、退役与数据处置

长期暂停、退役、凭证撤销、数据删除/保留、替代系统和经验移交都要有责任人。关闭进程或删除目录不构成退役。最终签署前应验证没有新任务入口、旧权限不能使用、在途工作已处理、数据和备份按规则处置、替代方案可用。

### 职责分离的最低要求

高风险场景不能由同一个主体从提出变更、修改评测、批准、执行一路做到自证成功。小团队可以用时间、账号和自动流水线分离：作者提交冻结候选，另一位具 authority 的人审批；部署由流水线执行，验收由不同账号和目标系统读回。关键不是部门数量，而是没有任何一个人或 Agent 能同时改规则、改答案、放权、执行并覆盖证据。

## 七、管理者每次只问五个问题

### 问题一：我们到底在授权谁，为谁完成什么任务？

答案应包含具名主体、任务对象、用户、成功定义、禁止项和有效期。若只回答“销售 Agent 帮团队提高效率”，说明范围仍不可执行。继续追问：它代表公司、员工还是客户行动？结果交给谁？谁对错误承诺负责？

### 问题二：它现在最多可以做什么，什么情况下自动收缩或停止？

答案应包含 AU 上限、数据、工具、外部 effect、预算、时窗、审批、撤销和停止条件。若团队说“模型会自己判断”，要求把判断变成机器可执行的政策和人类升级门。特别关注生产、资金、删除、身份、公共发布和敏感数据。

### 问题三：你们如何证明它真的完成了，而不是只得到一个成功返回？

答案应分别展示技术执行、交付可见、业务/环境验收，并能定位 receipt、readback、Artifact 和 owner。若只能展示最终回答、截图或演示视频，证据不足。要求看失败样本和 UNKNOWN，不要只看成功路径。

### 问题四：证据来自哪里，哪些仍是合成、厂商宣称或待复核？

答案应区分固定版本事实、官方规范、本地可复现实验、公开研究、厂商声明、原创方法和真实任务。合成测试可以证明控制逻辑，不能伪装成真实生产；厂商安全材料可以提供设计线索，不能替代本组织配置和攻击验证；公开榜单分数不能替代本地岗位评测。

### 问题五：失败时谁先做什么，怎样恢复、补偿和学习？

答案应包含具名值守、停止入口、撤权、证据保全、影响评估、回滚或 forward fix、外部补偿、通知、恢复验收和训练回流。若只有“重试”“回滚版本”或“人工接管”，说明团队还没有处理外部影响、未知终态和责任交接。

这五问不要求管理者懂每个技术细节，却能快速暴露目标模糊、权限过大、假完成、证据冒充和事故空白。任何一问无法回答，就不应扩大自主范围。

## 八、一个可执行的管理节奏

### 立项门

确认业务任务、人工基线、用户、owner、数据、风险和试点范围。先选择能收窄、能观察、能回滚的任务。输出一页任务与责任合同，不先讨论“需要多少 Agent”。

### 设计门

团队提交七维目标、AU 上限、三面完成定义、数据流、工具/权限、评测层、事故与恢复方案。管理者重点检查硬门是否清楚，是否存在一个总分掩盖风险。

### 试验门

先在隔离环境运行训练、回归和独立留出；然后用经授权的小范围真实任务建立代表性真实世界证据。试验要记录失败、成本和人工介入。不能因为演示日期临近而把留出答案泄漏给训练系统。

### 发布门

查看不可变版本、独立评审、恢复证明、责任矩阵、试点半径、值守和到期时间。任何 P0 硬门 FAIL 就不发布；任何关键 RR 必须有 owner、截止和安全收缩状态。发布从 shadow、canary 或 limited 开始，不直接全量。

### 运行门

按任务结果、事故、权限、成本和业务指标持续复核。监控不只看服务在线，还看交付、环境终态、越权、重复执行、人工接管和用户影响。达到预算、错误或风险阈值时自动收缩。

### 变更与退役门

模型、Provider、工具、Skill、Plugin、记忆、策略、数据用途和法域变化都可能改变系统行为。重大变化触发再评测、再授权和恢复验证。项目结束时执行撤权、在途处理、数据处置、残余扫描、替代和知识继承，不留下僵尸任务与长期凭证。

## 九、十个常见管理误区及纠正动作

### 误区一：模型升级了，Agent 就自然更强

模型只是系统的一部分。任务定义、上下文、工具、权限、记忆、运行时、数据、评测和组织责任都会决定结果。新模型可能提高推理，却改变成本、延迟、拒绝行为、工具格式或数据处理路径。纠正动作是把模型替换视为 release 变更：固定候选身份，在同一任务和预算下回归，检查安全与迁移，先 shadow 再有限扩大。没有系统级证据时，只能说模型候选在部分样本上表现更好。

### 误区二：把提示词写得足够长，就能替代制度与权限

提示词可以表达行为期望，不能阻止进程读取文件、调用工具或向外部系统写入。模型也可能误解、遗忘或被不可信内容诱导。纠正动作是把禁止项落实到身份、工具策略、最小权限、网络出口、凭证代理、审批和目标 readback；提示词只承担说明责任。凡涉及隐私、资金、删除、生产和公共发布，都不能只靠“请谨慎”。

### 误区三：增加更多 Agent 就会线性提高产能

并行只有在子任务足够独立、输入输出明确、共享资源可仲裁时才产生收益。否则会增加通信、上下文复制、冲突、重复劳动和合并成本。纠正动作是要求团队给出任务依赖图、关键路径、并行理由、上下文隔离、共享文件 owner 和收敛者；用总时长、总成本、冲突率和返工率与单 Agent 基线比较，而不是统计启动了多少 worker。

### 误区四：公开基准高分就是岗位胜任

SWE-bench、τ-bench、WebArena、GAIA 等基准各测局部能力，公开题还存在污染与脚手架差异。它们通常不覆盖本组织数据、授权、生产 effect、长期可靠性、用户交付和法务边界。纠正动作是明确分数映射七维的哪些部分、属于 D22 哪一层、哪些维度没有测；随后用本地岗位任务、独立留出、真实试点和安全红队补齐。公开分数是外部校准，不是上岗证。

### 误区五：没有发生事故，说明风险控制有效

低频高影响风险可能长期不出现，监控缺口也会让事故没有被识别。系统从未遭遇注入、权限撤销、重复执行或恢复，并不能证明能应对。纠正动作是主动做故障注入、越权负测、凭证轮换、终态冲突、owner 失联和恢复演练；记录攻击是否被哪一层阻断。安全证据来自设计与对抗，不来自一段平静时期。

### 误区六：人类在环天然安全

如果审批人不知道对象、风险和证据，只能机械点“允许”；如果每个低风险动作都弹窗，人会疲劳并形成无条件通过。纠正动作是把 HITL 设计成明确决策点：谁审批、看到哪些差异、能选择什么、多久失效、拒绝后怎样安全结束。低风险重复动作可以使用有范围和到期的 standing order，高风险动作保留多方批准与独立验收。

### 误区七：日志越多，审计能力越强

没有身份、版本、任务和时间关系的海量日志会增加泄露和调查成本。记录所有提示与用户数据还可能制造新的隐私风险。纠正动作是先定义最小事件链和 claim—evidence 映射，再记录必要字段、digest 和受控定位指针；保护原始证据完整性，规定访问与保留。审计目标是能回答关键问题，不是把所有内容永久保存。

### 误区八：供应商负责模型，所以组织不用负责结果

供应商可以对服务合同和公开能力负责，本组织仍决定使用目的、数据、用户、权限、外部 effect 和业务承诺。托管式 Secure VM 或安全声明不证明本组织的 connector、配置和流程正确。纠正动作是保存 Provider 版本、region、数据使用和保留设置、子处理者、退出路径与事故通知；把厂商声明标为待独立验证，并为高风险用途设置本地控制和责任 owner。

### 误区九：一次上线审批可以覆盖后续所有变化

Agent 系统依赖动态模型、工具、记忆、策略、外部 API 和数据。代码不变时，模型别名、OAuth scope、Provider 路由或 Skill 内容也可能漂移。纠正动作是定义 material change：任何影响任务、权限、数据、风险、用户承诺、schema 或恢复的变化，自动使旧批准失效或进入复核；定期检查实际状态与批准 manifest 的差异。

### 误区十：为了领先，可以先上线再补治理

治理不是发布后的文档工作，而是让系统能够更快试验、及时止损和安全扩大的基础。没有 owner、停止、证据和恢复，团队遇到问题只能全面停机或冒险继续。纠正动作是从最小闭环开始：只读/提案、窄任务、小数据、短时窗、明确 owner、三面完成和回滚；证据增加后再扩大。速度来自可控试验，不来自跳过不可补偿的硬门。

### 什么时候应该停止项目，而不只是暂停一次运行

暂停是等待证据或修复，停止项目则是承认当前价值—风险假设不再成立。出现以下任一情形，管理者应启动退出评审：连续两个预注册周期未超过人工基线，且主要失败来自任务本身不适合自动化；为了维持表面成功，人工复核成本已经吃掉预期收益；关键数据权利、用户授权或法规路径长期无法闭合；系统必须获得与业务价值不成比例的权限；供应商、模型或工具变化让结果无法稳定复现；真实用户持续拒绝采用，或错误造成的信任损失高于效率收益；团队无法维持具名 owner、值守与恢复能力。

停止不等于把文件夹留在服务器。它需要冻结新入口，处理在途任务，撤销凭证和持续授权，按规则处置数据、记忆、日志、Artifact 与备份，通知受影响用户，验证旧服务不能继续行动，并把可复用经验移交给人工流程或替代系统。项目复盘应区分“模型不够强”“任务设计错误”“组织不愿承担责任”“经济性不成立”和“权利条件不允许”，避免下一个团队换个产品名重复同一失败。

退出决定同样要有证据和尊严。不要把停止写成某个员工或某个模型的“能力不行”，而要保存当时的目标、假设、样本、成本、事故、用户反馈和约束变化。可安全复用的任务定义、评测与控制可以保留；个人信息、失效凭证、无权材料和不再需要的副本必须处置。只有这样，结束一个不成立的项目才会成为组织能力，而不是把问题留给下一次重启。

管理者还应指定一位退出 owner，在约定日期提交撤权、数据处置、用户通知、替代流程和残余风险证明；没有终态证据，项目只能标为“停止中”，不能标为“已关闭”。

## 结语：管理的目标不是让 Agent 更听话，而是让能力可托付

强 Agent 的定义，不是永远给出答案，也不是获得最多工具和权限。真正可托付的系统知道任务边界，能把复杂工作分解并根据证据重规划；会把计划、进度和未决项外部化；能主动构造反例、验证产物和读取环境终态；遇到死胡同会停止、回退或升级；并行探索时会隔离上下文和共享资源；在授权收缩、事故恢复和责任交接中仍保持可审计。

管理者的作用，是让这种能力在正确的问题、正确的范围和正确的责任链中发生。您不需要批准 Agent 的每一步，但要批准它能走多远；不需要阅读每条日志，但要确保重要结论能被独立复核；不需要消灭所有风险，但要知道哪些风险仍存在、谁有权接受、什么条件下必须停止。做到这些，组织获得的就不只是一个会回答问题的工具，而是一套能够被训练、被验证、被约束、被恢复、也能被替换的人机协同能力。
