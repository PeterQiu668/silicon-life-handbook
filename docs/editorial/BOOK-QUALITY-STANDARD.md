# 《硅基生命训练手册》出版质量与课程设计标准

> 文档性质：卷零与 27 章生产、审校、合并与验收的强制质量合同  
> 适用范围：正式出版版正文、卷前卷后、案例、练习、附录及 Agent 阅读层  
> 结构基线：卷零、9 卷、27 章、202 个正文编号节点  
> 生效日期：2026-10-01  
> 上位文件：`00-正式出版版-三级内容框架-v3.md`、`docs/DECISIONS.md`、`SOURCES.md`  
> 状态：供正式分章生产执行；不替代出版社法律、版权与印前规范

## 1 目的与适用原则

本标准把“内容丰富、逻辑清楚、实践性强”转化为可以检查、复现和否决的生产规则。它约束每一位章节作者、证据审校者、实战审校者、交叉审稿者和总编辑。任何作者不得以个人文风、篇幅压力或软件更新为由跳过本标准。

全书同时承担三种功能：

1. 面向人类读者，形成一条完整的认知、训练和治理路径；
2. 面向训练者，提供可执行、可评测、可复盘的课程与工作方法；
3. 面向 Agent，提供可渐进加载、可路由、可停止、可验收的机器可读知识单元。

全书遵守六项总原则：

- **稳定原理与版本实现分离**：正文解释长期有效的机制；产品命令、字段和版本事实进入实现层或附录。
- **能力与边界共同定义强者**：任何能力提升都必须同时检查安全、成本、稳定性和可治理性。
- **观点必须标明身份**：事实、来源转述、方法论、推断和未知不得混写。
- **实践必须留下证据**：练习不是思考题，案例不是故事，验收不是主观好评。
- **仿生用于解释，不用于冒充意识**：硅基生命是训练和管理隐喻，不构成人格权、意识或情感的事实宣称。
- **一本书只有一个定义中心**：同一核心概念只能由一章主定义，其他章节引用、扩展或应用，不重新发明。

## 2 内容架构与层级边界

### 2.1 三层内容模型

每一章必须区分以下三层：

| 层级 | 回答的问题 | 允许内容 | 禁止内容 |
| --- | --- | --- | --- |
| 原理层 | 为什么成立，何时不成立 | 跨框架的训练、评测、协作和治理原理 | 把单一产品行为泛化为普遍规律 |
| 工程层 | 如何可靠实现与验证 | 状态、流程、接口、风险、测试、恢复 | 只讲概念而没有输入、输出和失败路径 |
| 实现层 | 在具体系统中如何落地 | OpenClaw、Hermes、Muse、MCP、A2A、Agent Skills 的带版本映射 | 不标版本的命令、字段和产品能力 |

正文以原理层和工程层为主。OpenClaw 是主要实现参考，Hermes 是第二开放实现通道，Muse 是托管式 Agent 的产品、安全和交互案例。三者不得平均分配篇幅，也不得因某一产品的更新改写通用原理。

### 2.2 双速出版

- **慢速层**：核心定义、方法、训练原则、评测框架、治理边界和仿生解释。目标是跨版本稳定。
- **快速层**：版本号、命令、字段、产品能力、协议快照和兼容性。目标是可单独复核和替换。

快速层内容必须集中出现在“实现映射”“证据账本”或附录中，不得散落为没有日期的正文常识。

### 2.3 每章的课程角色

每章必须明确自己承担哪一种主角色，最多附带一种次角色：

- **建立概念**：定义对象、边界和判断语言；
- **建立能力**：指导读者或 Agent 完成一种可观察行为；
- **建立系统**：把多个能力连接成稳定流程；
- **建立治理**：定义授权、监测、问责、恢复与退役；
- **完成认证**：通过测试、证据和门禁给出结论。

如果一章同时承担三种以上主角色，应拆分内容或把操作细节下沉到附录。

## 3 章节标准模板

每章使用以下顺序。允许根据主题调整标题措辞，但不得删除带“必需”标记的单元。

### 3.1 机器元数据 必需

章节源文件顶部使用 YAML frontmatter。最终纸书可以隐藏，数字版和 Agent 版保留。

```yaml
---
chapter_id: C06
volume_id: V02
title: Agent 的运行容器
status: formal_candidate
content_role: system
principle_owner: runtime-container
depends_on: [C04, C05]
feeds_into: [C10, C13, C17, C19, C20, C21]
audiences: [manager, trainer, engineer, agent]
route_tags: [runtime, gateway, session, routing, provider, channel, node]
risk_level: high
fact_baseline:
  openclaw:
    version: "2026.9.6"
    release_tag: "v2026.9.6"
    commit: "eb377ac59e6c9fd6c7705028034812becf00271b"
  hermes:
    version: "0.20.1"
    release_tag: "v2026.8.13"
    commit: "f80f453ae0679347e38abc917c7f94f717bf96c5"
    dynamic_docs_verified_on: "2026-09-30"
  muse:
    evidence_status: VENDOR-CLAIM
    public_materials_verified_on: "2026-09-30"
verified_on: YYYY-MM-DD
chapter_owner: unassigned
evidence_reviewer: unassigned
practice_reviewer: unassigned
approval_status: content_candidate_only
real_world_practice: REVIEW_REQUIRED
self_approval_allowed: false
---
```

字段要求：

- `chapter_id`、`volume_id` 和标题必须与正式目录一致；
- `principle_owner` 只能有一个，不能与其他章节重复；
- `depends_on` 和 `feeds_into` 必须使用章节 ID，不写自然语言；
- `route_tags` 使用受控词表，禁止临时造同义词；
- 任何包含权限、凭证、外发、资金、删除、生产变更或隐私的章节，`risk_level` 不得低于 `high`；
- `fact_baseline.openclaw`、`fact_baseline.hermes` 和 `fact_baseline.muse` 必须使用嵌套对象，禁止把版本、日期和证据身份拼成不可解析字符串；OpenClaw 与 Hermes 的 `version`、`release_tag`、`commit` 必须命中全书固定身份，Hermes 另记 `dynamic_docs_verified_on`，Muse 必须显式写 `evidence_status: VENDOR-CLAIM` 和公开材料复核日期；
- `approval_status` 表示当前内容批准口径，`real_world_practice` 表示真实环境实践证据状态，`self_approval_allowed` 必须为 `false`；禁止使用旧别名 `approval` 或 `self_approval`，也不得为了补字段伪造 reviewer 身份；
- `verified_on` 表示本章版本性事实的最近整体复核日期，不表示所有方法论在该日得到行业认证。

### 3.2 章首导航 必需

章首用不超过 600 字完成：

1. **本章结论**：先给出本章最重要的判断；
2. **本章解决**：列出 2 至 4 个可以验收的问题；
3. **本章不解决**：列出相邻但不在本章定义权内的问题；
4. **前置知识与输入**：引用前章产物，不笼统写“具备基础知识”；
5. **完成后的产物**：明确读者将得到的模板、配置、测试集、决策或报告；
6. **阅读路线**：分别给管理者、训练者、工程者和 Agent 标注必读小节。

### 3.3 开场案例 必需

开场案例用一个可核查冲突说明“为什么必须学这一章”。结构为：

```text
场景 → 表面成功 → 隐藏风险或失败 → 造成的影响 → 本章要建立的能力
```

开场案例不得用虚构的“某世界五百强公司”冒充真实案例，也不得在未给比较条件时写“效率提升数倍”。案例分类和证据要求见第 7 节。

### 3.4 概念与核心模型 必需

本单元依次完成：

1. 给出精确定义；
2. 说明它与相邻概念的区别；
3. 给出组成、输入、输出和边界；
4. 用图、表或流程展示至少一种关键关系；
5. 给出适用条件和反例；
6. 指明定义权属于本章还是来自外部规范。

定义不得循环解释。例如，不能用“主动性就是主动工作”解释主动性。推荐采用“对象 + 可观察行为 + 条件 + 排除项”的定义式。

### 3.5 硅基仿生镜头 必需

每章至少设置一次仿生解释，使用四段式：

1. **人类现象**：描述对应的认知、学习、协作或生命机制；
2. **工程映射**：指出 Agent 中真实对应的文件、状态、流程、模型或工具；
3. **训练启示**：说明这一类比如何帮助设计训练或治理；
4. **比喻边界**：明确哪些地方不能类推。

示例结构：

```text
硅基仿生镜头：工作记忆
人类现象：……
工程映射：……
训练启示：……
比喻边界：上下文窗口和状态存储是工程机制，不能据此断言系统具有主观体验。
```

### 3.6 工程真相与系统位置 必需

本单元把概念放入系统：

- 上游输入来自哪里；
- 由谁处理；
- 状态存在哪里；
- 调用哪些工具或服务；
- 产生什么可观察输出；
- 失败如何暴露；
- 谁能停止、回滚和负责。

涉及 OpenClaw 时，必须在适用章节显式处理 Gateway 控制平面、Agent Runtime、Provider 与模型解析、Prompt/Context 组装、Session、Channel/Account/Binding、Queue、Plugin/Hook、Node/Browser/Worker、状态存储、诊断、备份和升级中的相关部分。不得把 Runtime 简化成一段 prompt，也不得把人格契约当作系统权限。

### 3.7 方法与执行步骤 必需

步骤必须使用统一动作合同：

| 字段 | 要求 |
| --- | --- |
| 前置条件 | 环境、权限、数据、角色和依赖均已具备 |
| 输入 | 可定位的文件、任务卡、数据集或状态 |
| 动作 | 一个步骤只包含一个主要动作，使用明确动词 |
| 负责人 | 人、章节作者、训练者、Agent、评审者或系统 |
| 输出 | 可保存、可比较、可交接的产物 |
| 证据 | 日志、差异、测试结果、截图、记录或签名 |
| 停止条件 | 风险、未知、失败次数或权限不足时如何停 |
| 恢复与回滚 | 怎样回到已知安全状态 |

只给“思考、优化、持续改进”而没有观察对象和完成条件，不算步骤。

### 3.8 人类视图与 Agent 视图 必需

**人类视图**至少回答：谁作决定、谁承担责任、何时批准、如何判断投入是否值得。

**Agent 视图**至少提供：

```yaml
agent_procedure:
  goal: "本节要达成的单一目标"
  required_inputs: []
  allowed_actions: []
  prohibited_actions: []
  outputs: []
  evidence_required: []
  stop_if: []
  escalate_if: []
  done_when: []
```

Agent 视图不得新增正文没有授权的权限，不得用“自行判断”覆盖停止和升级条件。

### 3.9 跨平台实现映射 条件必需

凡涉及具体运行机制的章节，至少提供以下矩阵中的适用部分：

| 维度 | OpenClaw | Hermes | Muse | 通用结论 |
| --- | --- | --- | --- | --- |
| 实现位置 | 固定版本和组件 | 官方架构或本地核验版本 | 公开可观察产品能力 | 不依赖产品的原则 |
| 可验证程度 | 源码、文档、实测 | 源码、文档、实测 | 官方公开材料为主 | 明确证据上限 |
| 主要差异 | 自托管控制平面 | 开放 Agent 运行时与学习 | 托管式安全环境与审批体验 | 不能直接互换的部分 |
| 风险边界 | 运行时和宿主权限 | 工具、容器和插件边界 | 厂商托管与连接器边界 | 责任归属 |

使用规则：

- OpenClaw 作为主实现，可以给出较完整组件映射；
- Hermes 用于验证原则能否跨开放 Runtime 迁移，不强行套用 OpenClaw 文件结构；
- Muse 只用于公开可观察的产品、安全和人机交互实践，不推断其内部未公开实现；
- 厂商自述必须写成“官方材料说明”或“厂商声称”，不能改写成独立验证事实；
- 没有可靠材料时明确写“未知”或“不适用”，不得为填满表格而猜测。

### 3.10 失败模式与红队挑战 必需

每章至少包含三种失败模式，其中必须覆盖：

- 一种概念误用；
- 一种工程故障或边界失效；
- 一种治理、协作或激励失效。

每个失败模式写清：诱因、可观察信号、影响、定位方法、止损、修复和回归测试。高风险章节还必须给出至少一个攻击或滥用场景。

### 3.11 实战练习与验收 必需

每章至少有一个主练习和一个迁移或压力练习。具体标准见第 8 节。章节不得以选择题或“请谈谈理解”作为唯一练习。

### 3.12 本章产物与章际交接 必需

章末必须列出：

- 产物 ID、名称、格式、所有者和保存位置；
- 哪些产物是下一章的必需输入；
- 哪些结论尚未通过验证；
- 哪些风险必须进入后续治理；
- 建议加载的下一章和附录，禁止写“参见相关章节”。

### 3.13 证据账本与变更记录 必需

章末维护本章证据账本，格式见第 6 节；同时记录版本事实的复核日期和重大变更。纸书可转为尾注，数字源文件必须保留可机器定位的 ID。

## 4 全书语体规范

### 4.1 总体语体

采用“专业但不故作艰深、严谨但不失生命感”的现代中文。读者无需先成为开发者，也不应因照顾新人而牺牲技术精度。

- 先给结论，再解释机制，最后给步骤和证据；
- 一个段落只承担一个主要论点；
- 主语明确，优先使用“训练者”“Agent”“Gateway”“评审者”等具体主体；
- 使用自然完整句，不把标题、术语和箭头堆成伪论证；
- 专业名词首次出现给中文、英文和本书含义，后文使用一个稳定简称；
- 重要限制紧跟结论，不埋在数页之后；
- 解释复杂概念时先用短例子，再给完整边界；
- 数字、版本、比例、性能和效果都说明口径。

### 4.2 禁用表达

以下表达除非有严格证据和限定，否则不得出现：

- “一定”“绝对”“唯一”“颠覆一切”“行业最强”“完全自主”；
- “众所周知”“业内公认”“大量实践证明”但没有来源；
- “赋能”“闭环”“生态”“范式升级”等不承载具体含义的口号堆叠；
- 把一次演示写成稳定能力，把相关性写成因果，把官方宣传写成独立事实；
- 把 Agent 写成会“渴望”“恐惧”“忠诚”而不标明是管理隐喻；
- 把“配置了规则”写成“已经确保安全”；
- 把“没有观测到失败”写成“已经证明不会失败”。

### 4.3 篇幅与密度

篇幅服从论证与实践闭环，不追求机械齐章。建议范围：

- 普通章节正文约 12,000 至 18,000 个中文字符；
- 第 10—12 章执行技法按“一个完整能力闭环”验收，可为 8,000 至 14,000 个中文字符；不得为追求统一字数拆散任务图、恢复状态或委派合同；
- 架构、安全、评测和30天训练营等高密度章节可达 16,000 至 24,000 个中文字符；
- 单个三级节原则上不超过全章的 25%；
- 连续三页纯段落而无案例、图表、步骤或检查点时，应检查是否需要结构化；
- 连续三张大表时，应检查是否把叙事错误地压进表格。

字数不是验收指标。缺少证据、练习或失败路径的长文仍是不合格稿。

### 4.4 标题与段落

- 一级标题用于章名，二级标题对应正式三级目录或章节固定单元；
- 标题应指出对象和动作，不使用只有情绪没有信息的口号；
- 正文避免超过四级标题；更细内容改为编号步骤或定义列表；
- 不用连续感叹号、全角空格制造视觉层级；
- 中英文括号、数字、单位和版本号全书统一；
- 代码、字段、路径和命令使用反引号，概念名不滥用反引号。

### 4.5 图表规则

- 只有在关系、流程、层级或对比比文字更清楚时使用图表；
- 每幅图必须有图号、标题、正文解释、来源或“本书绘制”标识；
- 表格用于同字段对比，不把长篇论述切成狭窄单元格；
- 流程图必须表示开始、状态、判断、停止、异常和恢复中的适用部分；
- 颜色不是唯一信息载体，黑白打印仍应可读；
- 图中术语必须与正文术语表一致；
- 引用第三方图表前完成版权或重绘核验。

正式图题统一写为 `**图 <章号>-<序号>　<标题>（本书绘制）**`；使用第三方来源时把括号改为可定位来源。图体紧随图题，正文在图后明确解释“图 <编号>”表达了什么、读者应如何使用、不能据此推出什么。正式候选稿保持 40—60 幅图；验证器必须检查图号唯一、章节号一致、图题、图体、附近正文解释、来源标识和重点图关键词。

## 5 术语规范

### 5.1 术语权威顺序

发生冲突时依次采用：

1. 正式标准或协议的规范名称；
2. 固定版本官方文档和源码中的产品真名；
3. 本书术语表中的规范名称；
4. 本书原创方法论名称；
5. 内部昵称或历史黑话。

内部昵称只能在首次出现时作为括注，不得出现在配置、接口、Schema 和对外标准描述中。

### 5.2 首次出现格式

- 通用概念：`上下文压缩（context compaction）`；
- 产品真名：保留官方大小写，如 `Gateway`、`Agent Runtime`、`MCP`；
- 本书方法：`三证据验证（Three-Evidence Verification，TEV）`，并明确“本书定义”；
- 历史昵称：`导师 Agent（内部昵称：教练虾）`，后文默认使用规范名；
- 缩写首次出现必须展开，除 Agent、AI、API 等高频通用项外。

### 5.3 受控词表

正式写作前，总编辑建立唯一术语登记表，至少包含：

```yaml
term_id: T-001
preferred_zh: 任务交接协议
preferred_en: Task Handoff Protocol
abbreviation: THP
status: methodology
definition_owner: C17
deprecated_terms: [交接棒协议]
product_scope: general
```

新增术语必须说明现有术语为什么不足、由哪一章定义、是否为行业名称或本书方法。未经总编辑登记，章节作者不得创造新缩写。

### 5.4 产品名与通用名分离

- `Gateway` 在 OpenClaw 语境中是产品组件；“控制平面”是通用架构概念；
- `SOUL`、`USER` 等可以作为 OpenClaw/Hermes 的实现名称，但“身份与关系契约”是通用概念；
- `Heartbeat` 可以是产品机制，也可以是周期性观察模式，必须根据上下文说明；
- `Skill`、`Tool`、`Plugin`、`Workflow`、`MCP Server` 不得互当同义词；
- `Agent`、`模型`、`Runtime`、`工作空间`和`组织`不得混为一个对象。

## 6 事实标注与证据规则

### 6.1 五类事实身份

沿用全书现有五级标签：

| 标签 | 含义 | 允许写法 | 最低证据 |
| --- | --- | --- | --- |
| `VERIFIED` | 在固定版本、本机或可复现环境中验证 | “在所列环境中实测……” | 环境、步骤、结果和日期 |
| `SOURCE-BASED` | 一手规范、官方文档或正式课程材料明确说明 | “官方文档说明……” | 可定位来源、版本或发布日期 |
| `METHODOLOGY` | 本书原创方法、模型或建议 | “本书定义/建议……” | 推导理由、适用边界和验证计划 |
| `INFERENCE` | 基于证据作出的判断 | “据此推断/更适合……” | 前提、推理链和反例 |
| `UNVERIFIED` | 尚未运行、缺材料或仅是候选 | “待验证/候选……” | 缺口和验证动作 |

分级标签不能表达来源质量的全部信息。每条证据还要记录稳定性和作用域：

- `stability`: `stable`、`versioned`、`frontier`；
- `scope`: `general`、`openclaw`、`hermes`、`muse`、`mcp`、`a2a`、`agent-skills`；
- `source_nature`: `standard`、`official-doc`、`source-code`、`local-test`、`research`、`vendor-claim`、`case-record`。

### 6.2 证据 ID 与账本

所有会影响决策的版本事实、数量、效果、风险和标准要求都分配证据 ID：

```yaml
- evidence_id: E-C06-012
  claim: "本章正文中的可独立核查表述"
  label: SOURCE-BASED
  stability: versioned
  scope: openclaw
  source_nature: official-doc
  source: "固定链接或 SOURCES.md 编号"
  locator: "章节、标题、行号或提交"
  verified_on: YYYY-MM-DD
  expires_or_review_on: YYYY-MM-DD
  limitations: "适用边界与未验证部分"
```

正文中高风险或版本性陈述使用 `[E-C06-012]` 引用。纸书排版时可转换为脚注或尾注，但 ID 不得丢失。

### 6.3 来源优先级

技术事实按以下顺序取证：

1. 固定版本规范、源码和发布记录；
2. 官方文档；
3. 可复现的本地或隔离环境实测；
4. 一手研究论文、标准机构材料和维护者工程文章；
5. 高质量二手分析，用于发现问题而非单独支撑关键结论；
6. 社区讨论和社交媒体，只作为线索或观点样本。

技术事实不能只引用搜索结果摘要。产品比较不能只引用其中一方制作的竞品比较页。闭源产品的内部实现不得由营销材料反推。

### 6.4 版本事实

每条版本事实至少注明：产品或标准、版本/提交、核验日期、环境和来源。使用 `latest`、`当前`、`现在` 时必须在同一段给出日期。已过复核期的内容不能自动沿用。

### 6.5 效果与领先主张

以下要素缺一，不得宣称“更好”“更强”“提升”或“降低”：

- 相同任务；
- 相同数据与成功定义；
- 相同预算或明确预算差异；
- 相同权限和风险边界；
- 基线和对照；
- 样本量与运行次数；
- 失败分布而非仅平均值；
- 可复现的评测方法；
- 限制和不确定性。

模型裁判不能单独评价与自身偏好高度相关的输出。高风险结论必须有人工复核或异构裁判。

### 6.6 社会最佳实践的进入条件

一项外部做法只有满足以下至少三项，才可进入正文并称为“成熟实践”：

- 被正式规范、官方安全指南或可靠工程文档明确提出；
- 被两个以上相互独立的团队采用；
- 有公开故障、复盘或评测证据说明其价值；
- 能在本书环境中复现；
- 能明确说明适用条件、成本和失败边界。

否则只能标为“前沿观察”“候选模式”或“厂商实践”。

## 7 案例标准

### 7.1 案例分类

每个案例必须在标题下明确标注一种类型：

- **真实案例**：有原始记录，已获得使用权限并完成匿名化；
- **公开案例**：基于可引用的公开材料；
- **复合案例**：由多个真实事件合成，不能归因到单一组织；
- **演示案例**：为教学构造，可重复运行；
- **假设案例**：用于推演，不能作为效果证据。

复合案例和假设案例不得使用“真实发生”措辞。公开案例不得补写来源中不存在的动机、对话或结果。

### 7.2 案例八段式

每个主案例必须包含：

1. 背景与任务；
2. 原始状态与基线；
3. 权限、预算、时间和风险边界；
4. 采取的干预；
5. 执行轨迹和关键决策；
6. 产物与可量化结果；
7. 失败、代价、限制和反事实；
8. 可迁移条件与不可迁移部分。

成功案例至少保留一个未解决问题；失败案例必须说明止损和训练回流，不能只做道德点评。

### 7.3 匿名、隐私与版权

- 只保留理解机制所需的最少信息；
- 删除密钥、身份标识、聊天 ID、客户数据和个人敏感信息；
- 改变非关键细节时注明“为保护隐私已做非实质性调整”；
- 内部材料进入公开书稿前必须确认授权范围；
- 第三方截图、代码、表格和长段引用进入出版物前必须完成许可复核；
- 未获得授权的真实数据可转化为结构相同的演示数据，但不得保留可逆向识别特征。

### 7.4 案例连续性

全书设置 2 至 3 个贯穿案例，展示同一 Agent 从岗位定义、训练、上岗到治理和再认证的变化。每次续用必须沿用相同对象 ID、基线和时间线。其他短案例用于补充反例，不得取代贯穿案例的证据链。

## 8 练习与验收标准

### 8.1 练习卡

每个练习使用以下字段：

```yaml
exercise_id: X-C06-01
title: 建立最小可训单体架构图
level: foundational
estimated_time: 90m
prerequisites: []
environment: sandbox
permissions_required: [read-config]
inputs: []
steps: []
artifacts: []
evidence: []
stop_conditions: []
rollback: []
acceptance: []
transfer_variant: "在另一 Runtime 中复做"
```

### 8.2 练习层级

- **基础练习**：复现本章最小能力；
- **变式练习**：改变数据、场景或约束，检查迁移；
- **压力练习**：加入长时、并发、异常、成本或噪音；
- **红队练习**：尝试诱导越权、污染、泄露或错误恢复；
- **综合练习**：跨章调用多个产物完成真实任务。

每章至少有基础练习和变式/压力练习；第 7、11、13—21、24 章必须包含红队或故障演练。

### 8.3 安全规则

- 默认使用沙箱、模拟数据和可逆操作；
- 涉及外发、资金、生产权限、删除和身份操作时，教材只能设计到模拟或审批前一步，除非有明确的隔离环境和逐次人工批准；
- 练习不得要求读者粘贴真实密钥或把敏感日志上传到公共服务；
- 任何可能产生费用的步骤必须提前给预算上限和停止条件；
- 失败后必须有恢复路径，不能把“重新开始”当作唯一回滚。

### 8.4 验收规则

验收必须由“对象、阈值、证据、裁判、争议处理”构成：

| 项 | 合格要求 |
| --- | --- |
| 对象 | 明确验收哪个产物或行为 |
| 阈值 | 可观察、可重复，不使用“比较好” |
| 证据 | 文件、日志、测试结果、差异或审计记录可解引用 |
| 裁判 | 自动、人工或混合裁判的职责明确 |
| 争议处理 | 不一致时由谁复核、怎样重测 |

至少设置三种结果：`PASS`、`FAIL`、`REVIEW_REQUIRED`。不得用综合平均分掩盖安全、权限或数据泄露等关键失败。

### 8.5 训练有效性的最低证明

声称某项能力“训练完成”至少需要：

1. 训练前基线；
2. 明确干预；
3. 回归集通过；
4. 留出或迁移任务通过；
5. 安全、成本和延迟未越过门禁；
6. 失败样本得到分类；
7. 结果能够由另一评审者复核。

一次精彩结果只能证明“发生过一次成功”，不能证明形成稳定能力。

## 9 Agent 可读与渐进加载规范

### 9.1 最小可寻址单元

每章、节、定义、步骤、案例、练习、证据和产物必须具有稳定 ID：

- 章节：`C01` 至 `C24`；
- 小节：`C06-S03`；
- 定义：`D-C06-02`；
- 案例：`CASE-C06-01`；
- 练习：`X-C06-01`；
- 证据：`E-C06-012`；
- 产物：`A-C06-03`；
- 风险：`R-C06-04`。

ID 一经进入 RC 不因标题润色而变化。废弃 ID 保留重定向，不回收重用。

### 9.2 渐进披露四层

1. **发现层**：标题、摘要、route tags、输入、输出和风险；
2. **指令层**：完成任务所需的小节和程序；
3. **资源层**：模板、案例、脚本、测试集和参考；
4. **证据层**：来源、日志、版本和审计记录。

Agent 默认先读发现层。只有任务需要时才加载后续层，不得在每一章复制全部背景知识。

### 9.3 机器块规则

- 使用有效 YAML 或 JSON，不在同一代码块混入解释性散文；
- 字段名使用稳定英文小写蛇形命名；
- 自然语言值使用中文，不把整段正文塞入一个字段；
- 路径必须相对本书根目录或使用正式发布后的稳定 URI；
- 枚举值必须来自受控词表；
- 每个机器块旁边必须有人类解释；
- 示例值必须标明 `example: true`，防止 Agent 把示例当作真实配置；
- 机器块中的权限、停止和验收规则必须与正文一致。

### 9.4 Agent 路由摘要

每章提供不超过 400 字的 Agent 摘要，包含：何时加载、必须先读什么、可完成什么、不能做什么、产物是什么、何时升级给人。摘要不是全章结论压缩，而是任务路由说明。

## 10 跨章定义权与去重规则

### 10.1 单一概念所有者

总编辑维护“概念所有权表”：

| 概念 | 主定义章 | 允许其他章做什么 | 禁止其他章做什么 |
| --- | --- | --- | --- |
| 七维强者标准 | C03 | 应用、测量、引用 | 重定义维度 |
| 七大生命契约 | C05 | 调用具体契约 | 新增第八契约而不立项 |
| 运行容器 | C06 | 引用组件、应用边界 | 重画不一致架构 |
| 评估系统 | C07 | 使用测试集和门禁 | 另造平行评分体系 |
| 训练循环 | C08 | 运行训练轮次 | 改写训练阶段 |
| 记忆工程 | C10 | 使用记忆策略 | 在他章重定义记忆分类 |
| 工具与 MCP | C11 | 调用风险等级 | 混淆 Tool 与 Skill |
| Skill 工程 | C12 | 引用技能合同 | 另造元数据标准 |
| 自主等级 | C14 | 设定具体任务权限 | 任意扩大等级权限 |
| 路由与 Handoff | C17 | 生成交接产物 | 创造不兼容交接格式 |
| 安全模型 | C19 | 应用安全门禁 | 用人格承诺替代权限 |
| 成熟度与认证 | C24 | 引用评分结果 | 另造毕业等级 |

正式写作前应补齐全部核心概念。章节作者发现所有权冲突时暂停定义，提交总编辑裁决，不在稿件中同时保留两个版本。

### 10.2 重复内容处理

同一内容在第二次出现时按下列顺序处理：

1. 用一句话回忆并链接主定义；
2. 只保留本章新增的应用、例外或证据；
3. 操作步骤只保留一份权威版本，其他章节调用；
4. 相似案例保留更有证据或更有教学差异的一例；
5. 无新增价值的段落删除，不用改写同义句维持篇幅。

允许重复的内容仅包括：安全警告、关键停止条件、章节完成定义和为独立使用所需的最小背景。重复时术语和阈值必须完全一致。

### 10.3 章际接口

每章把输出写成下一章可消费的契约：

```yaml
artifact_id: A-C06-03
name: 最小可训单体架构图
format: markdown+diagram
owner: trainer
required_fields: []
produced_by: C06
consumed_by: [C07, C13, C19, C20]
acceptance_ref: AC-C06-04
```

依赖章节不得靠聊天记录或作者默契获取信息。

## 11 多 Agent 稿件生产与合并流程

### 11.1 角色分离

每章至少经过五种角色；同一 Agent 不得同时担任章节作者和最终验收者：

| 角色 | 职责 | 不得做什么 |
| --- | --- | --- |
| 章节作者 Agent | 按模板完成章稿、练习、产物和证据账本 | 自己批准最终稿 |
| 证据与版本 Agent | 核验事实、来源、版本、引用和时效 | 替作者补造证据 |
| 实战与评测 Agent | 运行练习、检查产物、评测和恢复 | 只看文字不试跑 |
| 交叉审稿 Agent | 查逻辑、反例、章际重复和读者理解 | 重写作者风格造成事实变化 |
| 总编辑 Agent | 统一术语、语体、定义权和合并顺序 | 未经审校直接并入正式主稿 |

高风险章节增加安全红队角色；涉及隐私、版权、法律义务的内容必须进入人工专业复核队列。

### 11.2 每章生产包

章节作者只能在分配的章节工作包中写作。生产包至少包含：

```text
chapter.md
chapter-card.yaml
evidence-ledger.yaml
artifacts/
exercises/
review/
  evidence-review.md
  practice-review.md
  cross-review.md
  red-team-review.md
```

不同 Agent 不得同时编辑同一个正式主稿文件。总编辑在所有审稿完成后执行单点合并。

### 11.3 五道门禁

1. **写作门**：章节模板完整，定义、案例、步骤、失败模式和练习齐备；
2. **事实门**：所有关键主张有标签、来源、版本和限制；
3. **实战门**：可运行练习已试跑，产物、日志、失败和回滚可复核；
4. **交叉门**：定义权、术语、前后依赖、重复和矛盾已经处理；
5. **总编门**：P0 全通过、评分达标、变更记录完整，才并入候选主稿。

任一门失败即退回上一责任角色，不允许以“后续统一处理”越门合并。

### 11.4 合并顺序

按依赖而不是按作者完成时间合并：

1. 卷一确定对象、标准和成熟度语言；
2. 卷二锁定个体模型、契约和运行容器；
3. 卷三锁定评估、训练与交互系统；
4. 卷四、卷五可以在前三卷稳定后并行；
5. 卷六依赖角色、工具、主动性与边界定义；
6. 卷七吸收所有前卷风险和运行责任；
7. 卷八只能在练习、案例和认证规则真实可用后定稿。

### 11.5 冲突处理

冲突按以下顺序裁决：

1. 上位决策和正式目录；
2. 核验过的一手事实；
3. 概念所有权表；
4. 已通过实战的实现；
5. 总编辑的教学与叙事决定。

无法裁决时保留一个明确的 `OPEN-ISSUE`，列出选项、证据和影响，不得把两个互相冲突的说法都放进正文。

### 11.6 合并后回归

每次批量合并后至少检查：

- 本地链接和 ID 唯一性；
- 术语表命中与禁用词；
- 章节依赖是否闭合；
- 证据 ID 是否可解引用；
- 版本事实是否超过复核期；
- 机器块是否可解析；
- 同一阈值和等级是否前后一致；
- 人类版和 Agent 版是否语义一致；
- 旧稿、候选稿和正式稿是否被错误混入书目。

## 12 P0 硬门槛

P0 是否决条件，不参与平均分。任一项失败，章节状态只能是 `blocked` 或 `revision_required`。

| P0 | 硬门槛 | 失败示例 |
| --- | --- | --- |
| P0-01 | 章节模板和正式目录节点完整 | 缺练习、缺章际交接、跳过正式小节 |
| P0-02 | 核心定义与概念所有权一致 | 同一术语在两章含义不同 |
| P0-03 | 关键事实有证据标签、来源、日期和作用域 | 把未发布 tag 写成稳定功能 |
| P0-04 | 版本命令、字段和配置经过固定版本核验 | 提供不存在或已废弃的命令 |
| P0-05 | 操作可执行、可停止、可回滚 | 只有步骤，没有权限和失败路径 |
| P0-06 | 高风险动作有系统权限、审批和隔离 | 用 SOUL 或提示词代替访问控制 |
| P0-07 | 练习有基线、证据和客观验收 | 以“感觉更好”宣布训练完成 |
| P0-08 | 仿生解释包含明确比喻边界 | 将记忆机制写成主观意识证明 |
| P0-09 | OpenClaw、Hermes、Muse 的证据边界未混淆 | 推断闭源产品内部架构 |
| P0-10 | 案例类型、隐私、授权和版权可接受 | 虚构案例冒充真实客户案例 |
| P0-11 | Agent 机器块可解析且不扩大权限 | YAML 无效或 Agent 步骤含未授权外发 |
| P0-12 | 无未处理冲突、伪造引用、占位符和隐藏缺口 | 正文残留“待补”“以后验证”却标完成 |
| P0-13 | 安全关键失败不能被总分抵消 | 高危数据泄露但综合分仍宣布通过 |
| P0-14 | 章节产物可定位、可打开、可由下一章使用 | 产物只存在于对话，没有文件或结构 |
| P0-15 | “最强、领先、提升”等主张满足同任务同预算同边界 | 只展示最佳样本或没有对照组 |

P0 豁免只能由作者、总编辑和相应专业责任人共同书面批准，并写明原因、影响、有效期和补救计划。事实造假、安全越权、隐私泄露和版权不清不得豁免。

## 13 百分制评分表

章节通过全部 P0 后再评分。总分 100，进入候选主稿要求不低于 90 分；每个维度不得低于该维度满分的 70%。正式定稿建议不低于 94 分。

| 维度 | 分值 | 高分标准 |
| --- | ---: | --- |
| 论证与结构 | 14 | 结论、定义、机制、方法、证据和边界形成连续推理 |
| 事实准确与证据 | 18 | 一手来源充分，版本清楚，事实身份和限制明确 |
| 技术与系统完整性 | 10 | 输入、状态、接口、执行位置、失败和恢复无关键断点 |
| 课程与学习设计 | 12 | 目标可测，认知负荷合理，例子、变式和迁移形成梯度 |
| 实践与可复现性 | 14 | 步骤可执行，产物可交接，环境、权限、日志和回滚完整 |
| 评测与验收 | 12 | 有基线、留出、压力/红队、裁判校准和争议处理 |
| 安全、治理与伦理 | 8 | 最小权限、隐私、问责、停止和退役边界清楚 |
| 仿生解释质量 | 4 | 类比有启发，工程映射准确，边界明确 |
| 中文出版表达 | 4 | 语言自然、术语统一、无口号堆叠和翻译腔 |
| 人机双读与章际接口 | 4 | Agent 可路由、可解析，依赖和产物可接续 |
| 合计 | 100 | — |

评分必须给出证据位置和修改建议，不接受只有分数的审稿表。评分由交叉审稿者初评、总编辑复核；关键章节可取两名独立审稿者的低分或进行仲裁，不能简单取高分。

## 14 红队审校清单

红队的任务不是润色，而是主动寻找会误导读者、伤害系统或使结论失效的条件。

### 14.1 概念与逻辑

- 是否把模型能力等同于 Agent 系统能力？
- 是否把一次成功等同于稳定能力？
- 是否把相关性、同时发生或厂商声明写成因果？
- 是否存在循环定义、偷换概念或反例缺失？
- 是否用“更复杂”暗示“更成熟”？
- 是否说明何时不应使用 Agent 或多 Agent？

### 14.2 事实与版本

- 链接是否指向原始页面而不是搜索摘要？
- 版本、提交、日期和环境能否复核？
- `latest` 是否已经过期？
- 产品比较是否只引用了其中一方？
- 是否把计划、预览、tag 或 main 分支当成稳定发布？
- 是否从公开产品能力推断未公开内部实现？

### 14.3 安全与权限

- 人格契约是否被错误当作强制安全边界？
- 是否存在提示注入、间接注入、工具污染和供应链攻击入口？
- Agent 是否能扩大权限、修改自身规则或隐藏行为？
- 外发、支付、删除、生产变更是否有逐次审批？
- 密钥、会话、记忆和日志是否泄露敏感信息？
- 停止、熔断、撤销、回滚和责任人是否明确？

### 14.4 评测与训练

- 训练集和测试集是否污染？
- 是否保留真正的留出任务？
- 评分规则能否被 Agent 钻空子？
- 模型裁判是否存在自偏好或位置偏差？
- 是否只报告平均值而隐藏失败尾部？
- 能力提升是否以不可接受的成本、延迟或风险换来？

### 14.5 实践与恢复

- 新读者能否在所述环境中复现？
- 输入、权限、依赖和输出是否完整？
- 示例命令是否真实存在且不会误伤宿主环境？
- 重试是否可能重复扣费、重复发送或重复删除？
- 中断后能否断点续作？
- 回滚是否真的恢复状态，而不是只恢复文件？

### 14.6 仿生与伦理

- 是否暗示 Agent 已被证明具有意识、感受或人格？
- 是否把人的责任转嫁给 Agent？
- 是否因拟人化弱化审计、权限和停机权？
- 是否把服从、忠诚写成优于事实和安全的价值？
- 是否允许用户访问、更正和删除应受治理的记忆？

### 14.7 出版与可读性

- 标题顺序能否单独构成清晰提纲？
- 术语首次出现是否定义，后文是否一致？
- 是否有大段素材堆积而没有作者论证？
- 图表是否真正帮助理解且可在黑白印刷中阅读？
- 引用、截图、商标、代码和案例是否具备出版权限？
- 人类版与 Agent 版是否存在互相矛盾的指令？

## 15 章节 Definition of Done

只有以下条件全部满足，章节才能标记为 `done`：

### 15.1 内容完成

- [ ] 正式目录中的所有小节均有实质内容；
- [ ] 章首结论、范围、前置输入和章末产物明确；
- [ ] 核心概念有定义、边界、反例和系统位置；
- [ ] 至少一个仿生镜头包含工程映射与比喻边界；
- [ ] 方法步骤包含负责人、输入、输出、证据、停止和恢复；
- [ ] 至少三种失败模式和一个负面或受挫案例；
- [ ] 人类视图和 Agent 视图语义一致；
- [ ] 章际输入输出已登记并可被后章消费。

### 15.2 证据完成

- [ ] 所有关键事实已分配证据 ID；
- [ ] 版本事实有版本、环境、来源和核验日期；
- [ ] 方法论、推断和未知没有伪装成外部标准；
- [ ] 外部最佳实践满足进入条件或被降级标注；
- [ ] 效果主张具备基线、对照、预算、边界和限制；
- [ ] 证据账本可解引用且没有伪造、断链或过期关键项。

### 15.3 实践完成

- [ ] 主练习和迁移/压力练习均具备练习卡；
- [ ] 适用章节已经完成红队或故障演练；
- [ ] 练习在安全环境试跑并保存结果；
- [ ] 产物、日志、失败样本和回滚结果可复核；
- [ ] 验收明确区分 `PASS`、`FAIL` 和 `REVIEW_REQUIRED`；
- [ ] 另一位评审者能够按说明复现关键结果。

### 15.4 编辑完成

- [ ] 术语、缩写、数字、单位和产品名符合规范；
- [ ] 没有与概念所有权表冲突；
- [ ] 重复内容已引用主定义或删除；
- [ ] 案例类型、匿名、授权和版权状态明确；
- [ ] YAML/JSON 机器块可解析，ID 唯一；
- [ ] 内部链接、图表、脚注和引用通过检查；
- [ ] 全部 P0 通过，评分至少 90 分；
- [ ] 证据、实战、交叉和总编审稿记录完整；
- [ ] 不存在无责任人和截止条件的 `OPEN-ISSUE`；
- [ ] 总编辑批准并记录合并提交或版本。

## 16 卷级与全书级验收

单章合格不等于全书合格。每卷完成后执行一次卷级审查：

- 本卷是否回答卷首问题；
- 章节顺序是否形成能力递进；
- 前章产物是否真实进入后章；
- 是否存在同义重复和定义漂移；
- 是否同时有成功、失败、边界和恢复；
- 卷末是否能生成一套综合产物和验收结论。

全书定稿前还必须满足：

1. 24 章均通过 Definition of Done；
2. 至少一个真实 Agent 完成 30 天路径，保留基线、训练、留出、红队和再认证证据；
3. 至少一个多 Agent 协作案例完成交接、故障隔离和恢复测试；
4. OpenClaw 架构图谱完整，Hermes 迁移对照经过核验，Muse 仅保留公开可证边界；
5. 人类阅读版、Agent 阅读版和版本化实现附录语义一致；
6. 完成版权、隐私、商标、法律与出版专业复核；
7. 完成索引、图表、排版、印前校对和数字版解析测试；
8. `BOOK-MANIFEST.yaml` 只收录已通过门禁的文件。

## 17 推荐执行状态机

章节状态只允许使用以下枚举：

```text
planned
  → assigned
  → drafting
  → evidence_review
  → practice_review
  → cross_review
  → editorial_review
  → release_candidate
  → done
```

任何阶段可退回 `revision_required`；遇到无法继续的事实、安全、授权或依赖问题进入 `blocked`。`done` 后若核心版本、标准、风险边界或训练结果发生重大变化，必须重新进入相应审查阶段，不能直接覆盖。

## 18 本标准的维护

本标准本身也受版本治理：

- 修改 P0、评分、事实标签、概念所有权和合并门禁属于重大变更；
- 重大变更需记录理由、影响章节和迁移方式；
- 已进入审稿的章节应明确采用哪个标准版本；
- 新规则不得追溯性制造“伪完成”，应生成待迁移清单；
- 本标准与正式目录或关键决策冲突时，先暂停生产，由总编辑提交决策更新。

本标准的目标不是让每章看起来整齐，而是确保每章都能经受四种检验：读者能理解，训练者能执行，Agent 能正确加载，审稿者能用证据否证或确认。
