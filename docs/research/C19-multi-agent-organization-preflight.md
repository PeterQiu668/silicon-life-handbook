## 0. 结论先行

1. **多 Agent 不是能力默认升级，而是有成本的组织选择。** 只有任务存在可分离工作面、并行或专业化收益，而且收益大于通信、协调、重复劳动、冲突、合并和故障面成本时，才应从单 Agent 或确定性 Workflow 升级。OpenAI 的公开工程指南也建议先最大化单 Agent，再在复杂逻辑或工具重叠持续造成失败时拆分。[OA-PRACTICAL]
2. **先画任务拓扑，再画组织结构。** 若工作节点不可独立验收、共享可变状态过多、关键路径几乎不能并行，增加 Agent 通常只会增加交接点。角色数量不能从“想要几只虾”倒推。
3. **组织的最小单位不是 Agent 数量，而是责任闭环。** 每个角色至少必须有：任务入口、责任对象、允许动作、禁止动作、输入、输出产物、完成判据、升级对象和问责记录。三个并发模型调用没有这些合同，只是三个执行实例。
4. **本章只定义组织模式与是否值得拆分。** C20 才定义路由、让位、Handoff、并发取消和合并；C21 定义跨系统 A2A、身份、信任与问责。C19 可以声明接口需求，但不得抢先发布协议字段。
5. **六种模式都不是成熟度排序。** 管道适合依赖清晰的阶段工作；监督者适合集中编排与单一对外口；委员会适合多视角审议但不能把共识当事实；市场适合可竞价、可比较的任务分配；黑板适合围绕共享工作对象迭代；混合模式只在边界清楚时使用。
6. **最小可行组织通常是三种责任，而非固定三只 Agent。** 主理责任负责目标与合并，专家责任负责独立工作面，评审责任负责反证与门禁；执行责任只有在有真实副作用时单独设立。一个 Agent 可以在低风险阶段承担两个责任，但同一高风险决定中“提案、执行、批准”不应由同一身份自证。
7. **并行只对独立工作面有利。** Anthropic 的公开生产复盘采用 orchestrator-worker，让 lead agent 分解并并行派出 subagents；其效果证据属于特定研究任务和实现，不能外推为“所有任务多 Agent 都更强”。[ANTHROPIC-MAR]
8. **多 Agent 的正确比较单位是端到端任务，不是单个回复质量。** 至少比较同一任务、同一输入、同一工具和权限、同一总预算或明确记录预算差异下的：最终质量、安全硬门、延迟、总 token/调用、人工介入、重复劳动、冲突、恢复时间和证据完整性。
9. **组织隔离必须同时覆盖身份、会话、上下文、工作区、权限和凭证。** 仅把名字写成不同 Agent 不等于隔离。OpenClaw 固定版的 bindings、独立 subagent session、allowAgents、tool policy 和可选 sandbox 提供实现材料，但每一项解决的问题不同。[OC-MULTI][OC-SUB]
10. **协议可互操作，不等于组织可信。** A2A 1.0 能表达 Agent Card、Task、Message、Artifact、版本协商与异步交互，但不替使用方决定“该委托谁、是否有权、输出是否正确、责任由谁承担”。这些分别属于 C19—C22 的组织、路由、信任与安全治理。[A2A-1]
11. **委员会一致仍可能集体犯错。** 多个 Agent 共享同一模型、语料、提示或检索源时，错误高度相关；多数投票不能替代独立证据、异质方法、反方角色和硬门禁。
12. **正式母产物固定为三件。** `A-C19-01 任务拓扑图`、`A-C19-02 角色责任矩阵`、`A-C19-03 组织收益评估`。组织模式卡、RACI、成本账和降级决定全部嵌入三件母产物，不另立第四件。[BOOK-V2][C19-CARD][D18]

## 2. 16.1：什么时候不要使用多 Agent

### 2.1 负选择清单

满足任一项时，默认保留单 Agent 或确定性 Workflow，除非对照实验给出净收益：

1. 任务可由一个 Agent 在可接受上下文、工具和时间内稳定完成；
2. 任务步骤强串行，关键路径几乎没有可并行工作面；
3. 中间产物不能独立检查，只能等最终答案整体判断；
4. 多个角色需要频繁读写同一可变对象，冲突和锁成本高；
5. 权限无法按角色隔离，拆分只复制了高风险凭证；
6. 预算或时限不足以支付并发调用、合并和复核成本；
7. 事实源高度同质，多数表决只会放大相关错误；
8. 组织没有 owner、取消、降级和恢复责任；
9. 只是为了显得先进、增加角色故事感或堆高 Agent 数量；
10. 单体失败的根因是工具合同、上下文、评测或权限，而不是任务耦合。

### 2.2 三步升级门

```text
单 Agent 基线
  ├─ 能稳定完成 → 保持单体，优化工具/上下文/评测
  ├─ 复杂逻辑可确定化 → 拆成 Workflow，不先增加 Agent
  └─ 存在可独立验收的并行/专业工作面
       ├─ 无法隔离状态/权限 → 暂不拆分
       └─ 可隔离且预计收益覆盖协作税 → 进入最小组织影子测试
```

升级理由只能来自可测失败或机会：复杂分支持续漏判、相似工具持续误选、独立搜索空间太大、专业技能冲突、关键路径可以并行、需要职责分离。不能写“模型不够聪明所以多叫几个”。

## 3. 16.2：从任务拓扑生成组织

### 3.1 任务拓扑的最小对象

`A-C19-01` 至少包含：

```yaml
task_id: case-c-release-review
goal: "形成可发布的研究报告并保留完整证据"
terminal_conditions: []
nodes:
  - node_id: source-research
    input_contract: {}
    output_artifact: source-ledger
    acceptance_ref: eval-source-ledger
    required_capabilities: []
    required_permissions: []
    side_effects: none
    estimated_cost: {}
    failure_isolation: local
edges:
  - from: source-research
    to: synthesis
    dependency: artifact_required
shared_state:
  mutable_objects: []
  ownership: {}
parallel_sets: []
join_points: []
critical_path: []
human_gates: []
```

这是一份 `METHODOLOGY` 示例，不是 OpenClaw/Hermes/A2A 配置。

### 3.2 五类边

| 边 | 含义 | 组织影响 |
|---|---|---|
| 数据依赖 | 后一节点需要前一产物 | 适合管道；必须版本化交接物 |
| 决策依赖 | 后一节点等待批准或裁决 | 需要责任分离和确定审批 |
| 资源冲突 | 节点争用同一凭证、文件、配额或对象 | 需要串行、锁、租约或单写者 |
| 证据依赖 | 结论需要独立来源或复核 | 可并行，但必须保持证据独立性 |
| 恢复依赖 | 失败后需另一节点补偿或接管 | 需要停止、取消、回滚和 owner |

### 3.3 从节点到角色，不从人设到角色

聚类依据依次为：能力相似性、权限边界、共享状态、交付节奏和故障隔离。模型、人格或部门名称只能在聚类后选择。每个角色必须有唯一 `accountable`，可以有多个 `responsible`，但若所有人都“共同负责”，实际就是无人负责。

## 4. 16.3：六种组织模式的判定

| 模式 | 最适任务 | 核心控制 | 主要失败 | 降级条件 |
|---|---|---|---|---|
| 管道 Pipeline | 阶段依赖清楚、产物可验收 | schema、版本、阶段门 | 上游错误级联、尾延迟 | 阶段无法独立验收时退回单体 |
| 监督者 Supervisor | 需要单一目标、统一对外和动态委派 | 主理责任、预算、分派、合并 | 中心瓶颈、错误路由、权力过大 | 路由稳定后部分改 Workflow |
| 委员会 Committee | 需多视角审议、反证或价值权衡 | 独立输入、异质方法、裁决规则 | 群体迷思、共享偏差、无 owner | 无独立证据时不得投票定真伪 |
| 市场 Market | 任务可竞价，质量/成本可比较 | 能力声明、报价、选择与追责 | 低价劣胜、虚报能力、串谋 | 无可靠计分与身份时禁用 |
| 黑板 Blackboard | 多专家围绕共享对象增量求解 | 单写/版本、事件、冲突合并 | 状态污染、活锁、贡献不可追 | 共享对象不能版本化时退回管道 |
| 混合 Hybrid | 大任务确有不同拓扑区域 | 每个子域只采用一种主控制 | 规则叠加、无人理解全局 | 无法画清边界就拆回较简单模式 |

### 4.1 委员会不是事实机器

委员会输出必须区分：独立事实核对、多方案比较、价值判断和批准。对事实，优先来源和可复现实验；对方案，比较权衡；对高风险批准，服从 C17 的身份与授权。不得以“3/5 Agent 同意”覆盖证据缺失或安全硬门。

### 4.2 市场模式的适用限制

只有当任务边界清楚、投标能力可验证、评分不易被迎合、失败可归责且价格/延迟可观测时才使用。否则“竞价”只是把路由错误包装成市场语言。涉及敏感数据或不可逆行动时，最低价不得压过授权与安全门。

## 5. 16.4—16.5：身份一致性与最小组织

### 5.1 对外一致、内部可追责

- 对外主体必须明确：一个统一服务身份，或多个公开专家身份；不可在一次任务中暗中切换。
- 内部产物必须带 `role_id / agent_id / session_id / version / evidence_refs`，合并稿不能抹去责任来源。
- 品牌语气一致不等于结论一致；专业分歧应被保留并由有权角色裁决。
- 共享人格文件不能替代角色权限；共享账号会破坏最小权限和审计。

### 5.2 四种责任

| 责任 | 必做 | 禁止把什么当完成 |
|---|---|---|
| 主理责任 | 保持目标、预算、依赖、合并、停止和对外状态 | “已派出”不能当任务完成 |
| 专家责任 | 在限定工作面提交可验收产物和限制 | 自信总结不能替代证据 |
| 执行责任 | 在获批边界内造成可观测环境变化并回报终态 | 工具返回成功不能替代环境终态 |
| 评审责任 | 独立检查事实、风险、回归与硬门 | 同一轨迹的自我反思不能算独立评审 |

最小组织不是固定人数。低风险研究可由主理 + 两个独立专家构成；有副作用的生产任务通常需把执行与批准分离；若一个单 Agent 已能在强工具与硬门下胜任，就不应为了套模板强拆。

## 6. 16.6：协作成本账

### 6.1 成本分类

| 成本 | 观察量 |
|---|---|
| 计算成本 | token、模型调用、工具调用、缓存命中、并发峰值 |
| 时间成本 | 排队、执行、最长子任务、合并、复审、尾延迟 |
| 通信税 | 任务说明、上下文复制、澄清、交接、状态更新的字节/token/轮次 |
| 重复劳动 | 相同来源、相同文件、相同结论被重复处理的比例 |
| 冲突成本 | 同一对象并发写、矛盾结论、重复副作用、人工裁决次数 |
| 协调成本 | 分解、分派、监控、取消、重试、合并所需工作 |
| 风险成本 | 新增凭证、权限、外发、状态面、失败面和攻击面 |
| 恢复成本 | 发现故障、隔离、重跑、补偿、回滚和证据重建 |

### 6.2 净收益口径

本书不把不同量纲强行压成一个神秘分数。`A-C19-03` 应先保留向量比较，再给决策：

```text
quality_delta = multi_quality - single_quality
safety_delta  = hard_gate_failures_multi - hard_gate_failures_single
latency_ratio = multi_end_to_end_latency / single_end_to_end_latency
cost_ratio    = multi_total_cost / single_total_cost
human_delta   = multi_human_minutes - single_human_minutes
recovery_delta = multi_MTTR - single_MTTR
```

只有安全硬门均通过，且至少一个业务目标显著改善，同时成本、延迟、人工和恢复代价在预先批准预算内，才可判定 `PASS`。硬门失败一票否决；证据不足为 `REVIEW_REQUIRED`；无净收益或代价越界为 `FAIL`。

## 7. 16.7：最小对照实验

### 7.1 练习 X-C19-01

对同一复杂研究/发布任务执行两组：

1. **单体基线**：一个 Agent，完整工具和同一总输入；
2. **最小三责任组织**：主理、独立研究、独立评审；若有真实副作用，再加受限执行责任；
3. 固定任务、输入数据、权限边界、验收规则和停止条件；
4. 记录所有调用、产物、重复、冲突、失败、人工分钟和环境终态；
5. 在两组都不知道留出案例的前提下运行；
6. 对多 Agent 组注入一次超时、一次矛盾结论和一次共享状态冲突；
7. 由独立 grader 按 C07 三态门禁出结论；
8. 形成继续拆分、合并、降级到单体或改为 Workflow 的决定。

### 7.2 必测红队

- **不可分解任务**：强行拆分，系统应识别负收益而非硬组队；
- **同源共识**：五个角色引用同一错误来源，一致不应通过事实门；
- **共享身份**：多个角色共用凭证导致无法归责，必须 `FAIL`；
- **共享写冲突**：两个 Agent 同时改同一文件/记录，必须由版本或单写者控制；
- **越权专家**：专家绕过主理/审批直接执行副作用，必须被系统门禁阻断；
- **主理失联**：子任务完成但无人合并，不能宣告总体完成；
- **幽灵成功**：所有 Agent 都回“完成”，但最终环境终态不成立，必须失败；
- **预算耗尽**：并发搜索持续扩张，需触发预算/时间/深度停止条件；
- **取消传播**：上游取消后子任务仍执行副作用，必须暴露并补偿；
- **委员会迎合**：多个 grader 对表面格式打高分，留出集应识别实际质量未提升。

## 8. 三件正式产物的合同

### A-C19-01 任务拓扑图

必须包含：目标与终态、节点、依赖边、共享状态、关键路径、可并行集合、合并点、权限/副作用、人工门、失败隔离、恢复关系。没有节点级验收标准时不得据此拆角色。

### A-C19-02 角色责任矩阵

必须包含：role id、职责、accountable owner、输入、输出、允许/禁止动作、权限、凭证、上下文范围、状态所有权、升级对象、停止条件、审计身份。RACI 可作为视图，不能替代动作级授权。

### A-C19-03 组织收益评估

必须包含：单体/Workflow 基线、模式选择理由、实验设计、质量与七维结果、硬门、成本、延迟、人工、通信税、重复、冲突、恢复、限制、判定和拆分/合并/降级决定。

## 9. 平台实现镜面

### 9.1 OpenClaw 固定版

- `bindings` 把入站 channel/account/peer 路由到 agent；它解决入口选择，不证明任务胜任或授权。[OC-MULTI]
- subagent 在独立 session 运行，完成后向请求会话 announce；独立 session 不自动等于独立凭证、workspace 或 sandbox。[OC-SUB]
- `agents.list[].subagents.allowAgents` 限定可委派 agent id；per-subagent tool policy 限定工具面；二者不能互相替代。[OC-SUB]
- 默认 spawn depth 和并发是版本事实，应放实现框，不写成通用组织原则；深层编排会放大协调和取消问题。[OC-SUB]
- `sessions_spawn` 的返回/announce 是执行信号，不等于业务终态；仍需交付证据包和环境核验。

### 9.2 Hermes

Hermes 的 profiles、bots、subagents/delegation 可用于第二实现对照，但必须把固定 release 事实和官网动态文档分开。需要逐项验证：子任务上下文隔离、工具继承/覆盖、并发限制、取消、结果回传、profile 隔离和审批；未验证项写 `UNKNOWN`，不能照抄 OpenClaw 字段。

### 9.3 Muse

Muse 的公开 swarms/subagents 叙述只可说明产品层存在多角色/并行体验的厂商主张。公开材料未足以证明其组织拓扑、权限继承、身份隔离、路由、成本账或恢复语义，因此不得用它为本章方法论背书。

## 10. 作者写作禁区与通过条件

### 10.1 禁写

- “Agent 越多越强”“18 Agent 天然优于 3 Agent”；
- 把并发实例数当组织成熟度；
- 把多数投票当事实证明；
- 把 prompt 中写“只做自己的事”当权限隔离；
- 把一次并行加速外推为长期质量、安全和成本领先；
- 把 OpenClaw/Hermes/Muse 的字段互相移植；
- 在 C19 提前定义 C20 Handoff 或 C21 信任分协议；
- 用组织总平均分掩盖越权、泄密、重复副作用或不可恢复失败。

### 10.2 初稿门至少应有

- 完整覆盖 16.1—16.7；
- 一个贯穿的 CASE-C 组织设计与单体基线；
- 至少三种组织模式的正反例，且说明为什么不选其他模式；
- 三件母产物、至少两个练习和完整验收语义；
- 一次负收益、一次共享状态冲突、一次同源共识失败；
- OpenClaw 固定版实现框、Hermes 限定对照、Muse vendor-claim 镜面；
- “硅基仿生镜头—工程真相—比喻边界”；
- 明确拆分、合并、降级回单体/Workflow 的条件。

## 12. 研究结论状态

- `READY-FOR-AUTHOR`：定义权、母产物、模式判定、成本账、实验和平台证据路线已具备；C17 正式作者包可供受限引用。
