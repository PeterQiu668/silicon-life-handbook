## P0-C21-v2.4-01：前置批准与生命周期事件顺序没有闭合

### 复现

在`V23-001`和`V23-039`中，只把`legal_review.reviewed_at`从`02:00`改为`11:30`；rollout window在`11:00`开始，当前评估时刻为`12:00`。schema有效、全部其他状态不变，两项都得到`PASS`且理由为空。

### 根因

runner只验证`reviewed_at <= now < expires_at`，没有把法律/隐私审查、release approval、rollout实际执行、retirement request/approval、证据生成和terminal signoff串成有向时间链。`rollout.starts_at`只是允许窗口，不是发布动作receipt；`retirement`对象也没有`requested_at/approved_at/executed_at`。冻结root只能证明当前冻结值未被scenario改写，不能证明缺失的事件发生顺序。

### 最小关闭条件

1. 增加独立冻结的publication/lifecycle event registry，至少记录`event_id、release_id、plan_id、stage、requested_at、approved_at、executed_at、actor、authority_ref、receipt/readback、status、record_digest`。
2. 发布或扩大半径前，强制`legal_review.reviewed_at`、release authority `issued_at`与plan approval时间不晚于实际`executed_at`，且均在有效期内；不能用`now`代替实际执行时刻。
3. 退役必须满足`request <= approval <= admission stop/inflight reconciliation/runtime and network disable <= data/credential disposition <= replacement/handoff acceptance <= terminal signoff`；所有事件绑定同一release、retirement decision与owner角色。
4. 增加近邻负测：晚审早发、先签退役后请求、signoff早于残余扫描、撤销后执行、相同时间但错误主体、receipt/readback乱序；安全或授权顺序失败不可由D21、成本或最终状态补偿。
