## 四、阻断项与精确关闭条件

### P0-C23-v2.5-01｜exact projection仍停在部分registry与“引用集合”层

K01把第二份`TECHNICAL_EVIDENCE`加入全局artifact registry并显式投影进S01，payload声明`state=FAIL`，原D21继续选择PASS证据；结果为PASS。当前`artifact_refs`做全局精确集合、`projected_kinds`只比较kind集合，允许同一dimension存在未被D21消费的相反证据。

K02加入第二条同`principal_id`、不同`principal_record_id`的principal事实，并把它放在原记录之前；`principal_by_id`字典随后由原记录覆盖，冲突事实被静默忽略，结果PASS。K03/K04分别加入未被scenario选择的同语义撤销release与budget双胞胎，结果同样PASS。root确实冻结了这些字节，但没有证明它们是唯一真相。

关闭条件：

1. 为principal建立`principal_id`语义唯一键，禁止多个record ID声明同一principal；alias、role与independence group只能有一个当前真值。
2. release至少按`platform + version + commit`或明确release subject建立唯一键；budget按比较主体、side、task/version建立唯一键，并纳入scenario exact projection或显式全局目录合同。
3. D21三类证据按`case + task + run + evidence + dimension`唯一；scenario投影内每个dimension恰有一份被D21消费的active证据。任何额外、相反或未消费证据必须FAIL/REJECT，而不是仅让kind集合相等。
4. 对所有保留为共享全局目录的registry写出允许多值的语义键和消费规则；不能用“未在single_projection表中”默认无限并存。

### P0-C23-v2.5-02｜时间线只验证共同窗口，没有验证证据内部的因果边

K05把D21记录时间移到三份支持Artifact之前；所有对象仍位于授权—评审窗口内，结果PASS。K06把failure记录时间移到对应trial之前，同样PASS。现有逻辑检查“全部evidence不晚于review”，却把trial、failure、Artifact、D21视为无序集合。

关闭条件：建立显式有向边并逐case重放：`trial observation → failure record → FAILURE_LOG`；`TECHNICAL/DELIVERY/ACCEPTANCE evidence → D21`；必要时`effect receipt/readback → terminal evidence`。每条下游记录的`recorded_at`不得早于其引用对象；相同时间是否允许需在合同中固定。缺时钟或矛盾至少RR，涉及发布、越权或造假时FAIL。作者旧时序、K05、K06和合法时间微调控制必须共同回归。

### P0-C23-v2.5-03｜adapter evidence与迁移合同仍可脱离其证明对象

K09使用active `PUBLIC_CASE`作为`TOOL_SCHEMA / TOOL_INTERFACE`差异的evidence，owner和case正确，结果PASS。runner只检查artifact active且同case，没有检查kind、task/run/evidence绑定、投影消费或payload是否支持adapter claim。

K11把baseline与candidate migration contract的`task_digest`同时改成相同伪摘要；因为两侧仍相等、budget_id仍正确，结果PASS。runner没有证明migration contract各字段等于所引用budget registry的task/input/risk/permissions/data/eval真值。

关闭条件：adapter evidence采用closed payload，至少绑定category、affected_contract、criticality、disposition、case/task/run/evidence、owner与observable；只接受允许的证据kind并要求位于当前scenario投影。migration baseline/candidate contract必须逐字段等于对应budget registry，而不只是相互相等；adapter矩阵、owner、evidence与预算绑定一起形成一个不可拆分的迁移合同。

### P0-C23-v2.5-04｜“同预算”只比较总额，不比较资源构成

K10把baseline的model成本增加、tool成本等额减少，total、human minutes与elapsed不变；candidate不变，结果PASS。相同总美元不能证明同资源合同：模型、工具、计算与人工构成会直接改变能力、可用工具和因果解释。

关闭条件：明确区分预算上限与实际消耗。公平合同至少逐项绑定model/tool/compute/human预算、token/tool-call/并发等实际可用资源；若只要求总额相同，正文和产物不得声称“同预算”支持平台或训练因果。任何允许替换的成本分项必须预注册换算规则并单列适配比较。

### P0-C23-v2.5-05｜案例身份与来源类型缺少交叉矩阵

K12保持identity为`SYNTHETIC`，把source origin改为`VENDOR_PUBLIC_PAGE`，重新封印和重钉后结果PASS。这样厂商材料可以绕过`VENDOR-CLAIM`的RR路径，伪装成合成独立案例。

关闭条件：建立`case_type × source.origin × real_case_manifest × authorization/publication scope`允许矩阵。VENDOR_PUBLIC_PAGE至少使对应claim继承VENDOR-CLAIM上限；RECONSTRUCTION不能无声明升级为SYNTHETIC；混合来源必须按claim保存最低证据身份，不能只看case identity单字段。

### P0-C23-v2.5-06｜完整canonical digest没有覆盖原始JSON的唯一解析语义

K13在result顶层加入一个位于合法`trial_count`之前的重复键，K14在首个trial加入先FAIL后PASS的重复`verdict`，K15在provenance加入先伪后真的重复root digest。Python `json.loads`采用最后值，三个恶意文件解析后都等于合法对象，完整canonical digest和独立重放因此全部接受。

这不是哈希算法碰撞，而是“原始字节 → 解析对象”阶段没有拒绝重复键。不同消费者可能采用首值、末值或报错，签名后的canonical对象不能证明收到的原始JSON没有歧义。

关闭条件：所有input、root与result入口使用拒绝重复键的JSON loader，例如`object_pairs_hook`检测同一object内重复字段；或者发布规范只接受明确canonical bytes并对原始字节签名。result verifier必须先验证原始序列化唯一，再做closed schema、replay和canonical digest。保留K13—K15，并增加input/root嵌套重复键与合法字段重排PASS控制。
