## 三、P0 阻断项

### P0-C23-V28-01｜模块导出的宽松原始解析器可绕过“解析前拒绝重复键”

`review/runs/run-case-harness.py:25` 把标准库 `json.loads` 保存为模块级 `_ORIGINAL_JSON_LOADS`，`strict_json_loads` 在 `:35` 继续动态调用它。该名称虽然以下划线开头，但导入模块后可直接访问，不构成访问控制。

I30/I31/I32 分别构造包含重复键的 raw result、source 与 authority root：第一个同名键放恶意值，后一个放原合法值。正式 strict loader 会拒绝这些 raw bytes；但调用模块自身 `_ORIGINAL_JSON_LOADS` 后，重复键歧义已被“最后值覆盖”消失，随后 `verify_result` 接受对象。于是正文和 E-C23-044 关于“输入、root 与结果在解析前拒绝重复键，任何可调用路径服从统一合同”的广义主张不成立。

精确关闭条件：

1. 交付模块不得导出可用于解析未信任 raw bytes 的宽松 JSON loader；若实现严格 loader 需要标准库函数，应在闭包默认值或独立最小模块中捕获并删除模块级别名，且不能再从公开模块对象恢复。
2. 对外结果验证入口优先接收三份 raw bytes/path，在函数内部先严格解析 result/root/source，再做语义重放；对象级 API 如保留，必须明确只接收“已经由可信严格解析边界产生的对象”，不得用它证明 raw JSON 重复键安全。
3. 将 I30—I32 原样纳入回归：从交付模块查找任何宽松 parser/decoder/loads 别名均不可达；三类重复键 raw 文档必须在进入对象图前拒绝。
4. 7 个合法正控必须继续通过，尤其等价 JSON、合法 root 重钉与 CLI，防止以禁用所有解析或全拒绝伪装修复。

### P0-C23-V28-02｜同进程可变的 evaluator 与 root pin 可改变验收语义

`verify_result` 在调用时从模块全局查找 `evaluate`，而 root pin 也是可写全局 `PINNED_AUTHORITY_ROOT_DIGEST`；`validate_authority_root` 还把字符串 `PENDING` 解释为“不检查独立 pin”。

- I33 把 `evaluate` 替换为返回已重封伪造结果的函数，随后 `verify_result` 接受把真实 `FAIL` 改成 `PASS` 的结果。
- I34 构造内部自洽、语义可重放的新 source/root/result 三元组，再把 `PINNED_AUTHORITY_ROOT_DIGEST` 改为 `PENDING`；未经独立授权的新 root 被接受。

这两项不是普通数据攻击，而是**验证器与信任锚处于同一可写 Python 进程**时的完整性边界。既然本轮要求明确覆盖 monkeypatch，该边界必须被如实计为逃逸，不能用其他 29 项拒绝来平均。

精确关闭条件：

1. 生产验证路径不得接受 `PENDING`、空值或其他 sentinel 作为“跳过 pin”；预注册 pin 必须来自独立只读配置、CLI 强制参数或外部可信根，并在验证开始前 fail closed。
2. 验证器应在 fresh isolated subprocess/worker 中加载固定代码与固定 pin，校验 runner/verifier 代码摘要后执行；调用方进程对模块对象的 monkeypatch 不能影响裁决。
3. 若项目选择把“同进程任意代码执行”列为明确的非目标，必须把机器控制结论缩窄为：仅对未篡改 verifier 代码与已固定 pin 的隔离进程成立；不能继续声称“任何模块级可调用路径”都安全。按照本轮验收合同，在隔离边界或等价完整性控制落地前仍为 `FAIL`。
4. 保留 I33/I34，并新增一个合法新 root 经独立 repin 后通过的正控，以区分授权换根与关闭 pin。

## 四、P1 证据主张边界

### P1-C23-V28-01｜E-C23-044 与正文对可调用路径的覆盖范围过宽

E-C23-044 准确描述了旧 result+root envelope 函数已删除、作者 20 项攻击零逃逸；但“唯一可调用结果验证函数”和正文“任何可调用的验证别名、partial 或 CLI 都服从同一三输入合同”会让读者合理推断 raw parsing 与同进程信任锚也已闭合。本轮已经证明该推断不成立。

关闭方式二选一：

- 把证据和正文显式缩窄为“在未篡改模块、预注册 pin 未变化、三份原始文档已经由正式 strict loader 解析的前提下，公开 verify/alias/partial/CLI 进行三输入语义重放”，并把 raw parser 与同进程 arbitrary-code integrity 列为未证明边界。

下一轮应只聚焦两个根因：移除 raw permissive parser 的模块可达性，以及把 evaluator/root pin 放入不可由调用方 monkeypatch 的 fail-closed 隔离验证边界。关闭后必须原样回放本轮 34 项与 7 个正控；只有 `0 escape` 且正控全部通过，才可在离线合成范围签 `PASS_WITH_LIMITATIONS`。
