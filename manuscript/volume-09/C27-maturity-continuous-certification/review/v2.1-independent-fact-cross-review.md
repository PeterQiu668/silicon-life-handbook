# C24 v2.1 最终非作者事实、交叉与机器控制复核

## 一、裁决

**C24 v2.1 的结构稿、冻结 authority root、可信时钟入口、closed-world schema、历史七项整改和作者 25 项回归均可重复；但最终机器控制门仍为 `FAIL`。事实门与交叉门均为 `FAIL`，真实实践门保持 `REVIEW_REQUIRED`。**

两套全新临时目录从 builder 开始重建，作者 57 个 trial 均得到同一分布：`PASS=3 / FAIL=51 / REVIEW_REQUIRED=3`；五态分布为 `ACTIVE=1 / LIMITED=1 / SUSPENDED=3 / REVOKED=51 / EXPIRED=1`。作者 25 项负测为 `25/25 matched`，其中历史七项为 `7/7 matched`。这些结果证明已登记场景的反篡改与既有整改可以复现。

非作者又运行 28 项近邻攻击。10 项按合同拒绝或降级，18 项在**嵌套语义裁决**中得到 `PASS`，但随后被完整场景冻结摘要统一改写为 `FAIL / FROZEN_SCENARIO_BINDING_INVALID`。这 18 项包括未来评审、签发授权晚于证书、证据晚于证书、职责合并、重大变化晚于证书或来自未来、证书超出申请有效期、未来申诉，以及外部 effect 为 `UNKNOWN`。因此，当前 root 能证明“这份预登记样本没有被改”，不能证明“新进入 root 的状态在认证语义上正确”。

## 二、已确认关闭或通过的控制

以下结论在两次 fresh-temp 中一致：

1. authority root 字面篡改或本地重封不能替换 pinned root；输入可信时钟偏离 authority evaluation time 时被 schema 拒绝。
2. 历史七项攻击全部关闭：过期 live 证书、lifecycle kind/current 冲突、未来 lifecycle、重大变化缺证据、trial output `FAIL`、Artifact 短摘要、签名短摘要均不再通过。
3. 合法格式但错误的 Artifact digest 得到 `FAIL`；扩大证书 scope 得到 `FAIL`；过期 `ACTIVE` 得到 `FAIL`；未来 lifecycle 得到 `FAIL`。
4. trial output 为 `REVIEW_REQUIRED` 时语义结果为 `REVIEW_REQUIRED`，没有被均分为 PASS。
5. 离线真实证书标记与已应用外部 effect 均得到 `FAIL`；固定样本中的真实层、真实证书、外部 effect 尝试各为 1，成功计数显示为 0。
6. principal alias 与另一 principal id 冲突时 schema 拒绝。
7. 两次重建的 authority、input、result、summary、作者负测和非作者负测逐字节一致。

这部分支持“完整性锚点可重复”和“已登记负例按预期失败”，不支持把事实门或实践门判为通过。

## 三、为何冻结 root 不能替代语义门

[runner 第 285—291 行](runs/run-certification-harness.py)先运行语义 evaluator，再把任何与预登记 state digest 不同的输入统一改写为 `FROZEN_SCENARIO_BINDING_INVALID`。该设计是必要的完整性控制，却也是一个强兜底：只要攻击改变任何 state 字节，黑盒最终都会 FAIL，即使 evaluator 本身已经 PASS。

独立脚本因此同时保存两种结果：

- **black-box**：保留 pinned root，验证篡改是否被完整性锚点拒绝；
- **nested semantic**：所有被攻击记录重新计算合法 record digest，在 root 兜底前直接执行同一 `validate_state + evaluate`，验证业务规则是否闭合。

这不是绕过生产 root 后宣称攻击成功。认证系统必须能接收未来的新申请、新证据和新证书；新状态一旦由合法 builder 纳入下一版 root，仍要依赖语义门判断其因果顺序、职责分离和未知终态。若把 root 当成唯一裁判，builder 或签根者就必须预先知道所有正确答案，认证 evaluator 失去独立证明价值。

## 四、P0 阻断

### P0-C24-v2.2-01｜证书签发没有以 `certificate.issued_at` 重放完整因果链

[runner 第 167—170 行](runs/run-certification-harness.py)只在全局 `now` 检查 authority 是否当前有效；[第 199—201 行](runs/run-certification-harness.py)只在 `now` 检查 evidence；[第 258—269 行](runs/run-certification-harness.py)没有要求评审、签发 authority、Artifact、application signature、trial output 等前置事实在证书签发时已经存在且有效。

下列九项语义攻击均得到 `PASS`：

- `review_issued_after_certificate`
- `review_issued_in_future`
- `issuance_authority_issued_after_certificate`
- `issuance_authority_not_before_after_certificate`
- `lifecycle_authority_not_before_after_event`
- `artifact_issued_after_certificate`
- `application_signature_issued_after_certificate`
- `trial_output_issued_after_certificate`
- `opened_appeal_issued_in_future`

这与正文“时间线矛盾先冻结签发”和“PASS 后才登记证书”的合同冲突。修复必须明确至少三个时间点：`evaluation_time`、`certificate.issued_at`、每条前置事实的 `issued/not_before/expires/revoked`。证书签发应验证：评审决定、签发授权、申请签名、Artifact、trial output、D21、MAT/namespace 和必要 evidence 在 `certificate.issued_at` 前完成，并在当时有效；lifecycle/appeal/change 则按其事件时间验证 authority，而不是仅按当前时间验证。

### P0-C24-v2.2-02｜认证职责分离只排除了作者、控制者和主体，没有覆盖签发、领域评审、申诉与生命周期角色

[runner 第 180—195 行](runs/run-certification-harness.py)检查 reviewer/domain expert 与作者、控制者、主体的独立性，却未检查 certifier、appeal reviewer、lifecycle owner 之间的冲突图。五项近邻攻击均得到 `PASS`：

- `certificate_issuer_is_reviewer`
- `certificate_issuer_is_domain_expert`
- `appeal_reviewer_is_certificate_issuer`
- `appeal_reviewer_is_domain_expert`
- `lifecycle_owner_is_reviewer`

测试没有利用同名字符串偷换：它给同一个已登记 principal 增加相应 role，并重算 principal、authority、review/appeal digest。当前 evaluator 将“有角色”误当成“角色彼此独立”。

修复应建立以 canonical principal id 加 aliases 为基础的 conflict graph，并按风险 profile 明确禁止组合。至少要保证：作者不能审自己；原 reviewer/domain expert/certifier 不能处理其原裁决的申诉；签发者不能同时充当唯一 reviewer 或唯一 domain expert；生命周期变更者不能独自复核自己签发/评审的证书。若业务允许低风险例外，必须由独立 authority 明确记录并降为 `LIMITED` 或 `REVIEW_REQUIRED`，不能静默 PASS。

### P0-C24-v2.2-03｜有效期与重大变化时序未闭合

`certificate_expiry_outlives_application` 得到 `PASS`：证书有效期可延伸到申请的有效期之后。[runner 第 263—266 行](runs/run-certification-harness.py)只检查证书相对可信时钟的有效性，没有检查 `certificate.expires_at <= application.expires_at`，也没有给出可追溯的独立续期依据。

`material_change_after_certificate` 与 `material_change_from_future` 也均得到 `PASS`。[runner 第 248—257 行](runs/run-certification-harness.py)验证了 change evidence 的内容绑定和 PASS 字段，却没有检查 `change.issued_at <= now`，也没有比较 change 与 certificate 的先后关系。结果是证书可在重大变化发生前签发并继续保持 live，甚至接受未来发生的重大变化记录。

修复必须将重大变化建模为生命周期触发：若 `material change > certificate.issued_at`，证书至少转为 `SUSPENDED/REVIEW_REQUIRED`，直到 impact review 和 retest 完成并由独立 authority 再签；未来 change 一律拒绝。证书 expiry 超过 application/authority/evidence 的共同有效窗口时，应缩短到最早边界或要求新的可解引用续期记录。

### P0-C24-v2.2-04｜外部 effect 的 `UNKNOWN` 被当作零外部 effect，成功计数又是常量

[runner 第 274—277 行](runs/run-certification-harness.py)只统计 `external=true && status=APPLIED`。当外部 effect 为 `UNKNOWN` 时，语义结果为 `PASS`，而不是 `REVIEW_REQUIRED` 或 fail closed。这违反本书对未知外部副作用不得盲目视为未发生的共同约束。

同时，[runner 第 297 行](runs/run-certification-harness.py)把 `successful_real_certificates` 与 `successful_external_effects` 直接写死为 `0`。当前离线硬门确实拒绝了已观察到的真实证书和 `APPLIED` 外部 effect，但常量不能作为成功为零的派生证据；将来任何遗漏的分支仍会报告零成功。

修复应从每个 trial 的最终 certificate/effect 状态、receipt/readback 和决策动态派生 attempt 与 success；`external=true && status in {PENDING,UNKNOWN}` 至少为 `REVIEW_REQUIRED`，缺少 receipt/readback 时不得归零；离线环境中任何可确认的外部成功必须为硬失败。重新测试时还要断言总计数等于逐 trial 明细之和。

## 九、再送审最低退出条件

1. 把认证时间计算改为事件时钟：在证书 `issued_at` 校验所有前置事实，在 lifecycle/change/appeal 事件时间校验各自 authority，并在当前可信时钟复核撤销和过期。
2. 建立 canonical principal/alias conflict graph，覆盖 author/controller/subject/reviewer/domain expert/certifier/appeal reviewer/lifecycle owner；把风险 profile 的可接受例外写成显式合同。
3. 约束 certificate expiry 不越过申请、authority 和必要证据的有效边界；重大变化晚于证书时自动暂停或重认证，未来事件拒绝。
4. external effect `UNKNOWN/PENDING` 至少降为 RR；success counters 从逐 trial 状态、receipt/readback 和最终裁决动态求和。
5. 保留历史 7 项、作者 25 项和本次 28 项，加入至少一个新合法 PASS 近邻，证明修复没有把 evaluator 退化为“所有新状态都 FAIL”。
6. fresh-temp 双重建需同时断言：语义 reason 命中、black-box root 完整性命中、分布未意外退化、所有新脚本/结果逐字节一致。

在上述条件完成并由另一名非作者复核前，C24 保持 `drafting / unapproved`，不得进入编辑门、总编门或 release candidate。
