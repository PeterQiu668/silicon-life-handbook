## P0-01：证据生产—消费因果图未闭合（16 项逃逸）

### 事实

builder 的通用 evidence 构造器把证据统一写为 `11:00`，见 `build-certification-fixture.py:15-16`。但 trial 在 `11:11—11:13` 完成、output 在 `11:12—11:14` 产生，见 `:39-42`；change 是 `11:20`、review 是 `11:30`、certificate 是 `11:50`、lifecycle 是 `11:55`，见 `:55-65`。因此固定 ACTIVE 样本中的 Artifact、failure archive、cost ledger、manifest、D21 三面、change evidence、public claim evidence、lifecycle evidence，均可能早于自己声称证明或汇总的事件。

runner 当前只验证“证据不晚于证书／review／event”，没有验证“证据不早于生产事件”：

- 基础证据只要 `issued_at <= review_time`，见 `run-certification-harness.py:346-356`；
- trial output 允许 `issued_at == completed_at`，见 `:363-368`；
- holdout/grader 允许与首个 trial completion 同时，见 `:376-379`；
- review 允许与 maturity、namespace、trial output、D21 同时，见 `:404-408`；
- public claim 按 certificate 签发时点检查，但没有“claim 在 certificate 产生后”的边，见 `:417-418`；
- change evidence 只要求在 change time 仍有效，未要求其在 change 发生后生成，见 `:449-453`；
- lifecycle evidence 同样只要求在 event time 有效，未要求在 lifecycle event 后生成，见 `:484-486`。

### 独立攻击

`N01—N10` 分别把 Artifact、failure archive、cost ledger、manifest、D21 三面、change/public-claim/lifecycle evidence 移到依赖事件之前并合法重封，全部仍为 PASS。`N11—N16` 把 output、预注册或 review 依赖放到相同 timestamp，在没有 sequence/receipt 的情况下仍为 PASS。

### 影响

这是认证证据的核心真实性问题，不是格式问题。攻击者可以先生成“成功证据”，再补做甚至不做被证明事件；固定 ACTIVE 基线本身也不能作为合法正控。C07 的 trial/observable trajectory、C21 的 lifecycle evidence 和 C23 的因果档案均无法安全消费这种结果。

### 关闭条件

1. 定义并执行完整事件 DAG；至少包含 preregistration → trial start → trial completion → output → Artifact/failure/cost/manifest/D21 → review → certificate → public claim，以及 change → change evidence、lifecycle transition → lifecycle evidence。
2. 对需要严格先后的边使用 `event_sequence`、append-only receipt 或严格时间不等式；仅有同一秒 timestamp 不能证明先后。
3. 修正固定 58 场景，使全部 PASS 正控满足该 DAG；旧的因果倒置样本应 FAIL。
4. 增加每条因果边的独立负测，而不是只测“晚于证书”。

## P0-02：冻结 authority 未冻结其 principal／alias 语义（3 项逃逸）

### 事实

authority root 冻结的是 authority record projection；`auth_ok` 随后从场景本地 `principal_registry` 解析 actor、role、status 和 alias，见 `run-certification-harness.py:259-274`。principal registry 本身不在 authority root 的冻结投影内。

固定 `S24-004` 的 authority actor 是 `UNKNOWN`，原本因主体不存在而 FAIL。本轮：

- `N17` 仅给本地 certifier 增加 alias `UNKNOWN`，场景变为 PASS；
- `N18` 在本地创建 `UNKNOWN` principal 并把 certificate signer 指向它，场景变为 PASS；
- `N35` 用带不可见尾随空白的 alias 替换 signer，仍变为 PASS。

三项都没有改冻结 authority projection。这证明“actor 已冻结”并不等于“actor 的规范身份、角色、状态、有效期和 alias 已冻结”。

### 关闭条件

1. authority root 必须绑定 canonical principal projection，至少包括 canonical ID、kind、roles、status、validity、alias policy、epoch/revocation。
2. authority record 应绑定 canonical principal digest，而不是运行时自由解析本地 alias。
3. alias 需要明确的 Unicode/空白规范化、不可见字符拒绝和全局唯一性；未知 actor 不能由场景本地补录后获得历史 authority。
4. 对 REVOKED/EXPIRED/UNKNOWN actor 做跨事件时点验证和本地 shadow 回归。

## P0-03：`verify_result` 可在不提供 source／authority 时降级为自洽校验（1 项逃逸）

### 事实

`verify_result(result, authority=None, source=None)` 把根绑定和 source replay 设计成可选分支，见 `run-certification-harness.py:562-604`。`N32` 改写一个 trial decision、同步重算 distribution 与完整 decision digest，然后直接调用 `verify_result(candidate)`；结果被接受。

正式 CLI 当前会传 source 与 authority，但这个可调用入口本身是 fail-open。任何复用者若遗漏两个可选参数，得到的是“提交者自洽”，不是“独立根验证”。这与正文“来源摘要不可由 result 提交者另选”的接口承诺不一致。

### 关闭条件

1. 对外可信 verifier 必须强制要求 authority 与 source；缺一项即 FAIL。
2. 若确需内部结构校验，应另命名为 `validate_result_shape_untrusted`，返回值不得表示验证通过。
3. 对 CLI、库调用、历史 wrapper 和直接导入四类入口分别做缺参／旁路回归。
